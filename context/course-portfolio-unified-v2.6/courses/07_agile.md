## 1. Course Thesis
> Agile은 미숙한 개발을 대신하는 방법론이 아니다. SW Engineering의 기본 역량을 갖추면서, 불확실성을 작은 단위의 실행과 빠른 Feedback으로 관리하여 지속적으로 학습하고 적응하는 개발 방식이다.

과정의 목표는 Scrum 용어를 아는 것이 아니라 **현재 조직의 문제를 진단하고, Agile이 필요한 조건과 도입 순서를 판단하며, 작은 Pilot에서 Evidence를 만든 뒤 확대할 수 있게 하는 것**이다.

## Learner & Context Fit

- **Audience / Work Context:** 불확실성과 변화가 있는 환경에서 adaptive delivery를 개선해야 하는 팀·리더·PM.
- **Current Capability / Failure Mode:** framework ceremony를 도입하면 agility가 생긴다고 생각하거나 engineering capability 없이 feedback만 강조한다.
- **Target Capability:** 작은 increment와 feedback으로 uncertainty를 줄이고 framework 도입·확대 여부를 evidence로 판단한다.
- **Decision Level:** Apply / Decide.
- **Transfer:** 수업 산출물과 판단을 실제 업무의 동일 유형 결정에 재사용할 수 있어야 한다.

## Foundational Decision Lens Alignment

- **APPLY:** Lean Thinking; Systems Thinking; Empiricism / Scientific Thinking.
- **Why:** batch와 feedback delay를 줄이고 팀 local metric보다 전체 value delivery를 보며 실험으로 적응한다.
- **Rule:** 관련 없는 Lens를 과정 형식상 억지로 추가하지 않는다. Lens는 Course-owned concept를 재정의하지 않고 판단을 강화한다.

## 2. Problem It Owns
대상 조직은 다음 문제가 복합적으로 존재할 수 있다.
- 기존 Predictive/Waterfall 방식 자체도 미숙하다.
- 요구사항이 불확실하고 변경이 잦다.
- 분석·설계·코드·테스트 등 SW Engineering 역량이 약하다.
- 고객·기획·관리·개발·테스트 사이 Feedback Cycle이 길다.
- 외부 개발팀 의존도가 높고 Product Decision 권한이 분산되어 있다.
- 계약/Governance가 상세 Scope 선확정과 변경 억제를 전제로 한다.

따라서 첫 질문은 `Waterfall인가 Agile인가?`가 아니라:
> **현재 문제는 Engineering Capability, Uncertainty, Feedback, Organization, Governance 중 무엇에서 발생하는가?**

## 3. Core Narrative
`Diagnose → Stabilize → Shorten → Apply → Adapt`

- **Diagnose:** 문제를 정확히 분리한다.
- **Stabilize:** 반복 개발이 가능한 최소 Engineering Foundation을 만든다.
- **Shorten:** Work Batch와 Feedback Delay를 줄인다.
- **Apply:** Scrum 등 적합한 Framework/Practice를 적용한다.
- **Adapt:** Evidence를 보고 개선·유지·확대·중단한다.

Scrum은 출발점이 아니라 적용 단계의 Framework다.

## 4. Decisions Learner Must Make
1. 우리 문제는 Agile로 해결할 문제인가, Engineering/Governance 문제인가?
2. Prediction과 Adaptation 중 어디에 더 많은 비용을 투자해야 하는가?
3. Agile 시작 전에 필요한 최소 Engineering Capability는 무엇인가?
4. Requirement/Work를 얼마나 작게 나눌 수 있는가?
5. 누가 Product Value/Priority를 결정하고 누가 Feedback을 제공하는가?
6. Scrum의 각 요소가 어떤 문제를 해결해야 하는가?
7. 외부 개발/계약 환경에서 무엇을 고정하고 무엇을 변화 가능하게 둘 것인가?
8. Pilot을 언제 확대·유지·수정·중단할 것인가?

## 6. Key Distinctions
- Agile ≠ Scrum
- Agile ≠ 무계획
- Waterfall ≠ 악 / Agile ≠ 선
- Iteration ≠ Feedback
- Task Completion ≠ Working Increment
- Scrum ≠ Engineering Practice
- Velocity ≠ Productivity KPI
- Product Owner ≠ 단순 요구 전달자
- 외주 ≠ Agile 불가
- Scaling Framework ≠ 팀 수준 문제 해결책

## 7. Learning Outcomes
수강 후 학습자는:
1. 현재 개발 문제를 Engineering / Uncertainty / Feedback / Organization / Governance로 진단한다.
2. Predictive/Iterative/Incremental/Adaptive 접근의 적용 맥락을 구분한다.
3. Agile 도입 전에 필요한 최소 Engineering Capability를 평가한다.
4. 큰 요구를 작은 Vertical Slice와 Working Increment로 나눈다.
5. Scrum의 Accountabilities/Events/Artifacts를 해결하려는 문제와 연결한다.
6. 외부 개발/계약 제약에서 현실적인 Agile 적용 범위를 결정한다.
7. Pilot Outcome을 Evidence로 평가하여 확대·수정·중단한다.

## 8. Principles / Trade-off / Failure
| Principle | Trade-off | Failure Condition |
|---|---|---|
| Diagnose before Agile | 전환 속도는 느려 보이나 잘못된 처방을 줄인다 | 모든 실패를 Waterfall 탓으로 돌림 |
| Engineering Discipline enables Agility | 기본기 투자 필요, Change Cost 감소 | Ceremony만 도입 |
| Small Batch / Short Feedback | 계획·조정 빈도 증가, Risk 조기 노출 | Sprint만 짧고 Feedback은 장주기 |
| Working Software as Evidence | 문서 진척의 편의 감소 | Task 완료율을 실제 진척으로 봄 |
| Product Decision close to Team | Stakeholder 참여 비용 증가 | PO에게 실제 우선순위 권한 없음 |
| Pilot before Scale | 전사 확산이 느려 보임 | Big-Bang Transformation |
| Contextual Method Choice | 하나의 표준화는 약해짐 | Scrum/SAFe를 모든 상황의 답으로 사용 |

## 9. Minimum Engineering Foundation
완벽한 DevOps 환경이 전제는 아니다. 다음 질문에 대부분 Yes일 정도면 된다.
- Source 기준 버전을 알고 있는가?
- 반복 가능한 Build가 가능한가?
- 변경 기능을 빠르게 검증할 수 있는가?
- 기본 Test/Review가 존재하는가?
- Done의 의미가 팀에 공통적인가?
- 변경/결함을 추적할 수 있는가?
- Iteration마다 검증 가능한 Increment를 만들 수 있는가?

없다면 Scrum 도입과 동시에 Foundation을 보강한다.

## 10. Scrum Teaching Rule
Scrum 요소를 정의 암기로 가르치지 않는다.

| Scrum Element | 해결하려는 문제 |
|---|---|
| Product Goal | 단기 작업이 방향을 잃는 문제 |
| Product Backlog | 변화하는 요구의 단일 우선순위 |
| Sprint Goal | Sprint가 Task List로 전락하는 문제 |
| Increment | 실제 진척을 확인할 Evidence 부족 |
| Definition of Done | Done 의미 불일치 |
| Planning | Goal과 Work 정렬 |
| Daily Scrum | 실행 중 조정 지연 |
| Review | Product Feedback 지연 |
| Retrospective | 같은 작업방식 문제 반복 |
| Product Owner | Value/Priority 의사결정 불명확 |
| Scrum Master | Framework/개선 장애가 방치되는 문제 |
| Developers | 완성된 Increment에 대한 공동 책임 부족 |

## 11. External Development / Contract Context
핵심은 외부 개발 자체가 아니라 **Feedback과 Product Decision 구조**다.

판단 질문:
- 무엇을 계약상 고정해야 하는가?
- 무엇을 Reprioritize할 수 있어야 하는가?
- Increment 단위로 Acceptance/Feedback이 가능한가?
- 변경 결정권자는 누구인가?
- Scope/Cost/Schedule Trade-off 규칙이 있는가?

`Fixed detailed scope + change suppression + late acceptance + Scrum`은 구조적 충돌을 만든다.

## 15. Success Criteria
다음 상황에 대해 `전사 Scrum부터 시작하지 않는다`고 판단하고 근거를 설명할 수 있어야 한다.

`요구 변화 + 약한 Engineering + 긴 고객 Feedback + 외부 개발팀 + 변경 승인 중심 Governance`

권장 판단 흐름:
`Diagnose → Engineering Foundation → Product Decision → Smaller Increment → Shorter Feedback → Pilot Scrum → Evidence → Adapt/Scale`

## 16. Quality Gate
- Agile이 Scrum 교육으로 축소되지 않는가?
- Engineering Capability 부족을 Agile로 덮지 않는가?

- Awareness Topic이 Core를 압도하지 않는가?
- Pilot/Evidence/Stop 조건이 포함되는가?
