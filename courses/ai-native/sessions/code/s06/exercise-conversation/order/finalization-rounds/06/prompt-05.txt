앞선 아키텍처 산출물을 검토했다. 패키지 경계는 복원됐지만 업무 연관과 코드 의존을 같은 화살표로 설명하고, Order에서 모든 외부 포트로 선을 그려 객체 책임까지 확정한 문제가 남았다. 다음 기준으로 최종 Markdown 문서 전체를 다시 생성해라.

1. 산출물은 패키지 다이어그램(업무 경계와 포트 구현의 두 관점), 의존 규칙, 결제 포트 연동 규격 셋이다. 기존 스타일과 근거, 미정은 유지하고 새 정책이나 객체 협력은 추가하지 마라.
2. 도메인 모델을 경계 배치의 입력으로 삼아라. order 안에 Order·OrderItem·OrderStatus·OrderRepository, product 안에 Product·LoadProductPricePort를 명시해라. payment·delivery의 포트와 업무 자료형도 소유 패키지 안에 둬라. 이것은 대표 요소 배치이며 도메인 모델 전체를 대체하지 않는다고 밝혀라.
3. 첫 Mermaid는 업무 패키지의 경계와 대표 요소를 보여라. 실선(화살촉 없음)으로 Order—OrderItem과 OrderItem—Product의 업무 연관을 표시해라. 이는 실습 4의 연관이며 Java 객체 참조·탐색 방향·저장 방식은 정하지 않는다고 밝혀라. 점선 화살표는 order 패키지에서 payment·delivery·product 패키지로 향하는 설계상 의존만 나타내라. Order에서 포트로 직접 화살표를 그리지 말고 포트를 호출할 구체 객체와 책임은 다음 설계 활동에 남겨라. 두 선의 뜻을 범례 문장으로 구별해라.
4. 둘째 Mermaid는 paymentadapter·deliveryadapter·persistence와 포트 소유 업무 패키지 경계를 명시하고 어느 클래스가 어느 포트를 구현하는지 보여라. 외부 결제·배송 제공자와 주문 저장소는 시스템/저장소로 구분해라. 상품 포트의 소유는 첫 그림에 있고 상품 연동 구현은 이번 범위 밖이라고 설명해라. 연결이 없는 상품 포트를 둘째 그림에 떠 있게 두지 마라.
5. 두 그림은 서로 다른 질문에 답한다. Mermaid flowchart TB와 패키지별 subgraph를 사용하되 도식 크기 때문에 요소·관계를 삭제하지 마라. 패키지별 목록은 한 줄씩 하나로 유지해라.
6. 허용 목록 밖의 업무 패키지 간 의존 금지와 순환 금지는 다르다. 예를 들어 payment→delivery는 순환이 없어도 허용 목록 위반이다. 따라서 검사 가능한 금지에는 업무→연동·영속, 허용 목록 밖의 업무 간 의존, 패키지 순환을 각각 명시해라. 허용 목록을 검사하지 않는다는 이전 설명은 철회한다. 문서와 도식이 같은 규칙을 표현해야 한다.
7. 나머지 결제 규격과 미정은 앞선 합의를 보존해라. 승인·거절·확정 불가를 주문 상태와 혼동하지 마라. 추가 조사·도구 실행 없이 합의된 완성 Markdown 전체만 출력해라.
