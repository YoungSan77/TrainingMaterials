# “주문한다” 요구사항 정의서

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인할 때까지의 요구사항과 수용 기준을 정의한다.

## 목적과 범위

- 상품 조회와 장바구니 구성은 전제다.
- 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

## 기본 용어집

- **주문(Order):** 배송지가 지정되어 생성된 거래 기록
- **주문 항목(OrderItem):** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가(salePrice):** 상품 시스템이 제공하는 상품 가격
- **주문 금액(totalAmount):** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기(PENDING_PAYMENT):** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료(PAID):** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

## 대표 수용 예

공통 전제는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울인 같은 주문이다.

### 1. 카드 승인

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이고 상태는 `결제완료`다. 승인 결과를 확인할 수 있으며 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X의 승인이 거절된 주문이 `결제대기`이고 배송 요청은 0회다.
- **사건:** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

## 품질·접근 기준

# “주문한다” 정적 업무 모델

이 정적 모델은 주문·주문 항목·상품의 관계와, 주문 생성 시점의 판매가를 단가로 확정하여 각 항목의 확정 단가에 수량을 곱한 금액의 합계로 주문 금액을 유지하는 조건을 명시한다.

## 1. 용어와 속성

- 주문 `Order`
  - `orderNumber: OrderNumber`: 주문 식별 값
  - `totalAmount: Money`: 주문 항목별 확정 단가와 수량으로 계산한 주문 금액
  - `shippingAddress: Address`: 주문 생성 시 확정된 배송지
  - `status: OrderStatus`: 주문의 현재 상태

- 주문 항목 `OrderItem`
  - `quantity: Quantity`: 주문한 상품의 수량
  - `unitPrice: Money`: 주문 생성 시점의 `salePrice`로 확정된 단가

- 상품 `Product`
  - `productNumber: ProductNumber`: 상품 식별 값
  - `salePrice: Money`: 상품의 현재 판매가

- `Money`: 원 단위의 0 이상 정수
- `Quantity`: 1 이상의 정수
- `Address`: 주문에 확정된 배송지 값
- `OrderNumber`: 주문 식별 값
- `ProductNumber`: 상품 식별 값
- `OrderStatus`: 주문의 현재 상태 값. 현재 확인된 값은 `PENDING_PAYMENT`와 `PAID`이며 가능한 상태 전체가 확정된 것은 아니다.

## 2. 클래스 도식과 관계

관계선은 업무상 관계와 개수만 나타내며 연관 방향이나 저장 방식을 정하지 않는다.

```mermaid
classDiagram
    class Order {
        orderNumber: OrderNumber
        totalAmount: Money
        shippingAddress: Address
        status: OrderStatus
    }

    class OrderItem {
        quantity: Quantity
        unitPrice: Money
    }

    class Product {
        productNumber: ProductNumber
        salePrice: Money
    }

    Order "1" -- "1..*" OrderItem : 주문 항목
    OrderItem "0..*" -- "1" Product : 해당 상품
```

1. 하나의 `Order`에는 `OrderItem`이 1개 이상 있다.
2. 하나의 `OrderItem`은 정확히 하나의 `Order`에 속한다.
3. 하나의 `OrderItem`은 정확히 하나의 `Product`에 해당한다.
4. 하나의 `Product`는 0개 이상의 `OrderItem`과 관계를 맺을 수 있다.

## 3. 조건과 대표 예

- `salePrice`, `unitPrice`, `totalAmount`는 원 단위의 0 이상 정수다.
- `quantity`는 1 이상의 정수다.
- 하나의 `Order`에는 `OrderItem`이 1개 이상 있고 `shippingAddress`가 존재한다.
- 유효한 주문에서는 다음 합계 등식이 항상 성립한다.

  ```text
  Order.totalAmount
  = Σ(OrderItem.unitPrice × OrderItem.quantity)
  ```

- `unitPrice`는 장바구니에 담은 시점이 아니라 `Order` 생성 시점의 해당 `Product.salePrice`로 확정된다.
- 생성 이후 현재 `salePrice`가 변경되어도 기존 `unitPrice`와 `totalAmount`는 변하지 않는다.
- `PENDING_PAYMENT`인 기존 주문에서는 주문 항목의 구성, 각 항목의 `quantity`와 `unitPrice`, `shippingAddress`가 변경되지 않는다.

대표 주문과 판매가 변경 전후는 다음과 같다.

| 값 | 주문 생성 직후 | 판매가 변경 후 |
|---|---:|---:|
| 상품 | 펜 | 펜 |
| `OrderItem` 수 | 1 | 1 |
| `Product.salePrice` | 1,000원 | 1,200원 |
| `OrderItem.unitPrice` | 1,000원 | 1,000원 |
| `OrderItem.quantity` | 2 | 2 |
| `Order.totalAmount` | 2,000원 | 2,000원 |
| `Order.shippingAddress` | 서울 | 서울 |

생성 시점에는 `unitPrice = salePrice = 1,000원`이고, `totalAmount = 1,000원 × 2 = 2,000원`이다. 이후 현재 판매가가 1,200원으로 바뀌어도 기존 주문은 확정 단가 1,000원과 총액 2,000원을 유지한다.

## 4. 정하지 않은 항목과 기존 업무 미정

본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정하며 다른 고객의 주문 요청은 거절한다. 주문자와 수령인은 같은 사람으로 본다. 다만 회원·비회원 여부와 주문 주체, 본인 확인, 주문자 및 수령인을 나타낼 구체 타입이나 식별 정보는 정하지 않는다.

정적 모델에서 다음 사항은 정하지 않는다.

- `OrderNumber`와 `ProductNumber`의 형식 및 생성 규칙
- `Address`의 세부 항목
- `Quantity`의 구체적인 상한
- 동일 상품 주문 항목의 병합 여부와 중복 허용 여부
- 결제 이력과 승인 결과의 보존 구조
- 현재 확인된 값 이외의 `OrderStatus`

기존 업무 미정은 다음과 같다.

- 결제대기 기한과 만료 정책
- 결제 응답을 확정할 수 없을 때의 처리와 재결제 허용 여부
- 재고 판단 시점과 승인 전 재고 부족 처리
- 카드 승인 뒤 재고 부족 처리
- 배송 요청 실패 처리와 재요청 기준
- 주문 결과의 별도 통지 여부와 담당 시스템

이 미정 사항으로부터 허용 또는 금지 정책, 새로운 개념이나 상태를 도출하지 않는다.

# “주문한다” 동적 업무 모델

## 도입

이 모델은 실습 3의 요구 범위에서 같은 주문이 사건에 따라 어떻게 바뀌는지 보여 준다. 범위는 주문 생성, 카드 승인·거절, 같은 주문의 재결제, 승인 뒤의 배송 요청이다.

- `배송중`과 `배송완료`는 같은 주문의 생애주기를 이해하기 위한 **참고 상태**다. 이 두 상태를 넣었다고 실습 3의 요구 범위가 넓어지지는 않는다.
- 취소는 범위 밖이다.
- 대표 예는 모두 같은 주문 A를 쓴다. 주문 A는 펜 2개, 확정 단가 1,000원, 총액 2,000원, 배송지 서울이다. "주문 A"는 예를 들기 위해 붙인 이름이며, 주문 번호 형식은 정하지 않는다.

## 상태 기계

### 주문 생애주기 상태 기계

```mermaid
stateDiagram-v2
    state "결제대기" as Pending
    state "결제완료" as Paid
    state "배송중" as InDelivery
    state "배송완료" as Delivered

    [*] --> Pending: 배송지 지정 / 주문 생성
    Pending --> Pending: 카드 승인 거절
    Pending --> Paid: 카드 승인 완료 / 배송 요청
    Paid --> InDelivery: 배송 시작 통보
    InDelivery --> Delivered: 배송 완료 통보
```

- `결제대기`와 `결제완료`는 실습 3의 요구 범위이고, `배송중`과 `배송완료`는 생애주기 참고 범위다.
- 배송 요청은 카드 승인 완료 사건에 대한 반응이다. 배송 요청 자체는 상태 전이가 아니다.
- 결제 응답을 확정할 수 없는 경우는 전이로 그리지 않는다. 승인이나 거절로 간주하지 않는다는 규칙만 정해졌고, 그 뒤의 처리는 정하지 않았다.

## 전이 목록

| 현재 상태 | 사건 | 다음 상태 | 범위 |
|---|---|---|---|
| 초기 진입(이전 상태 없음) | 배송지 지정 | 결제대기 | 실습 3 |
| 결제대기 | 카드 승인 완료 | 결제완료 | 실습 3 |
| 결제대기 | 카드 승인 거절 | 결제대기 | 실습 3 |
| 결제완료 | 배송 시작 통보 | 배송중 | 생애주기 참고 |
| 배송중 | 배송 완료 통보 | 배송완료 | 생애주기 참고 |

상태 코드: 결제대기 `PENDING_PAYMENT`, 결제완료 `PAID`, 배송중 `IN_DELIVERY`, 배송완료 `DELIVERED`

사건별 반응은 다음과 같다.

- **배송지 지정:** 주문 A 생성. 펜 2개·단가 1,000원·총액 2,000원·서울 확정
- **카드 승인 완료:** 서울로 배송 요청 1회 발생
- **카드 승인 거절:** 배송 요청 없음. 같은 주문 A 유지
- **배송 시작 통보, 배송 완료 통보:** 정한 반응 없음

- 거절 뒤의 재결제가 승인되는 경우에 새로운 전이가 생기지는 않는다. 같은 주문 A에 둘째 행(카드 승인 완료)이 적용된다.
- "배송 요청 1회"는 배송 요청이라는 업무 사건이 한 번 일어난다는 뜻이다. 그 사건을 어디에 어떻게 남기는지, 운영상 중복을 막거나 다시 시도하는 기준은 정하지 않는다.

## 정상 승인 시퀀스

### 카드 승인 완료와 배송 요청

```mermaid
sequenceDiagram
    actor 고객
    participant 주문시스템 as 주문 시스템
    participant 결제시스템 as 결제 시스템
    participant 배송시스템 as 배송 시스템

    고객->>주문시스템: 주문 A의 카드 결제 요청
    주문시스템->>결제시스템: 카드 승인 요청(2,000원)
    결제시스템->>주문시스템: 카드 승인 완료
    주문시스템->>배송시스템: 서울로 배송 요청
```

1. 고객이 `결제대기`인 주문 A의 카드 결제를 요청한다.
2. 주문 시스템이 확정 총액 2,000원으로 카드 승인을 요청한다.
3. 카드 승인 완료가 주문 시스템에 전달된다.
4. 이 사건에 대한 반응으로 주문 A가 `결제완료`가 되고, 서울로 배송 요청이 한 번 일어난다.

도식에는 참여자 사이에 오가는 업무 사건만 그렸다.

- 화살표는 사건이 일어나는 순서만 나타낸다. 실선이라고 동기 호출을 뜻하지는 않으며, 동기·비동기 전달 방식은 정하지 않는다.
- 상태 변화는 상태 기계와 전이 목록에서 다룬다.
- 고객은 이후 주문 A의 결제완료 결과를 확인한다. 확인 경로, 별도 통지 여부, 통지 주체는 정하지 않았으므로 도식에 넣지 않았다.
- 배송 시작·완료 통보는 생애주기 참고 범위이므로 이 장면에 넣지 않았다.

## 규칙의 대표 예

네 예 모두 주문 A의 식별, 펜 2개, 확정 단가 1,000원, 총액 2,000원, 배송지 서울이 바뀌지 않는다. 예마다 「유지되는 값」 줄에서 확인할 수 있다.

### 1. 승인

- **전제:** 주문 A, `결제대기`
- **사건:** 카드 Y에 2,000원 승인 요청 → 승인 완료
- **결과:** `결제완료`, 서울로 배송 요청 1회
- **유지되는 값:** 주문 A · 펜 2개 · 확정 단가 1,000원 · 총액 2,000원 · 서울

### 2. 판매가 변경 뒤 승인

- **전제:** 주문 A, `결제대기`, 현재 판매가 개당 1,200원
- **사건:** 카드 Y에 2,000원 승인 요청 → 승인 완료
- **결과:** 승인 요청 금액 2,000원, `결제완료`, 배송 요청 1회
- **유지되는 값:** 주문 A · 펜 2개 · 확정 단가 1,000원(현재 판매가와 무관) · 총액 2,000원 · 서울

### 3. 거절

- **전제:** 주문 A, `결제대기`
- **사건:** 카드 X에 2,000원 승인 요청 → 거절
- **결과:** `결제대기` 자기 전이, 배송 요청 0회, 다른 카드로 재결제 가능
- **유지되는 값:** 주문 A · 펜 2개 · 확정 단가 1,000원 · 총액 2,000원 · 서울

### 4. 거절 뒤 재결제

- **전제:** 카드 X가 거절된 주문 A, `결제대기`, 배송 요청 0회
- **사건:** 같은 주문 A를 카드 Y에 2,000원으로 다시 승인 요청 → 승인 완료
- **결과:** 새 주문 없음, 주문 A가 `결제완료`, 카드 X 거절부터 카드 Y 승인까지 배송 요청 총 1회
- **유지되는 값:** 주문 A · 펜 2개 · 확정 단가 1,000원 · 총액 2,000원 · 서울

## 금지·참고 조건·미정·범위 밖

### 확정된 요구에 근거한 금지

- 카드 승인 완료 없이 `결제대기`에서 `결제완료`로 전이할 수 없다.
- 카드 승인이 거절되면 `결제완료`로 전이할 수 없다.
- 결제 응답을 확정할 수 없으면 승인 완료로도, 거절로도 간주할 수 없다.
- 카드 승인이 완료되기 전에는 배송을 요청할 수 없다. 거절되면 배송을 요청하지 않는다.
- `결제대기` 주문의 상품, 수량, 배송지는 바꿀 수 없다. 주문 생성 뒤 판매가가 바뀌어도 확정 단가, 총액, 승인 요청 금액은 바뀌지 않는다.
- 거절 뒤의 재결제를 새 주문으로 대신할 수 없다.

### 생애주기 참고 범위의 전이 조건

아래는 이번 모델에서 합의한 참고 조건이며, 실습 3의 요구나 수용 기준이 아니다.

- 배송 요청만으로는 `배송중`이 되지 않는다. `결제완료`에서 `배송중`으로 가려면 배송 시작 통보가 있어야 한다.
- `배송중`에서 `배송완료`로 가려면 배송 완료 통보가 있어야 한다.
- 통보가 오지 않거나 늦는 경우처럼 배송 진행 중의 다른 경우는 다루지 않는다.

### 결정하지 않고 남겨 두는 정책

- 결제대기 기한과 만료 처리
- 결제 응답을 확정할 수 없을 때의 후속 처리와 재결제 허용 여부
- 재고 판단 시점과 승인 전·후 재고 부족 시 처리
- 회원·비회원 여부와 본인 확인 방법
- 본인 주문 조건이 카드 결제 요청에도 적용되는지 여부
- 배송 요청이 실패할 때의 처리, 운영상 중복 방지와 재시도 기준
- 주문 결과를 별도로 통지할지 여부와 담당 주체

금지는 이미 정해진 규칙에 어긋나는 변화다. 미정은 허용할지 금지할지 판단할 정책이 아직 없는 사안이다. 따라서 미정 사안을 새로운 상태나 전이로 메우지 않는다.

### 범위 밖

# 아키텍처 제안

## 1. 결론

이 사례에는 **포트와 어댑터 구조를 적용한 모듈러 모놀리스**가 가장 적합하다.

- 배포 형태: 하나의 애플리케이션으로 배포하는 모듈러 모놀리스
- 내부 구조: 주문 업무를 중심으로 한 포트와 어댑터
- 모듈 경계: 주문 업무 모듈과 외부 시스템 어댑터를 분리
- 트랜잭션 경계: 주문의 생성과 상태 변경은 주문 모듈이 소유
- 외부 연동: 상품·결제·배송 시스템은 출력 포트를 통해서만 접근

이 선택은 주로 **변경 가능성**과 **현재 확인된 배포 요구**를 근거로 한다.

| 판단 기준 | 확인된 사실 | 선택에 미친 영향 |
|---|---|---|
| 변경 | 상품·결제·배송은 외부 시스템이며 연동 방식과 구현이 바뀔 수 있다. 반면 주문 금액과 상태 전이 규칙은 주문 업무에 속한다. | 업무 규칙과 외부 연동을 포트로 분리한다. |
| 배포 | 각 기능을 독립적으로 배포해야 한다는 요구가 없다. 현재 범위는 하나의 “주문한다” 흐름이다. | 우선 하나의 배포 단위를 선택한다. |
| 조직 | 상품·결제·배송별 독립 팀, 소유권, 독립 출시 주기가 제시되지 않았다. | 팀 경계를 추측해 마이크로서비스로 나누지 않는다. |

따라서 이 제안은 “모놀리스가 항상 낫다”는 판단이 아니다. 현재 자료에는 독립 배포나 조직별 서비스 소유를 정당화할 근거가 없다는 판단이다.

| 계층형 | 구조가 단순하고 익숙하다. 표현·응용·도메인·인프라 계층을 나누기 쉽다. | 외부 시스템별 경계보다 기술 계층이 앞에 드러날 수 있다. 응용 서비스가 결제·배송 클라이언트 구현에 직접 의존하기 쉽다. | 단독 채택하지 않는다. 내부 구현 원칙 일부는 사용할 수 있다. |
| 포트와 어댑터 | 주문 규칙을 외부 상품·결제·배송 시스템 및 전송 기술에서 분리한다. 테스트 대역을 붙여 수용 예와 품질 시험을 수행하기 쉽다. | 포트가 지나치게 세분되면 단순한 흐름에도 구조가 무거워질 수 있다. | 내부 구조로 채택한다. |
| 모듈러 모놀리스 | 한 번에 배포하면서도 업무 코드와 외부 연동의 경계를 코드 수준에서 통제할 수 있다. 분산 호출과 분산 운영 부담이 없다. | 독립 배포나 장애 격리가 실제 요구로 등장하면 배포 단위 재검토가 필요하다. | 현재 배포 형태로 채택한다. |
| 마이크로서비스 | 독립 배포, 팀별 소유, 개별 확장이 필요한 경우 유리하다. | 현재 자료에는 그런 요구가 없다. 결제 승인과 주문 상태 변경 사이에 분산 일관성, 장애 처리, 메시지 중복 등의 미정 정책까지 조기에 결정하게 만든다. | 현재는 채택하지 않는다. |

계층형과 포트와 어댑터, 모듈러 모놀리스는 완전히 같은 차원의 대안이 아니다. 여기서는 다음과 같이 조합한다.

- **모듈러 모놀리스**: 배포와 코드 소유 경계
- **포트와 어댑터**: 업무 코드와 외부 세계의 의존 방향
- **계층 구분**: 주문 모듈 내부의 도메인·응용 코드 정리

---

## 3. 업무 경계

현재 요구에서 독립적인 핵심 업무 경계로 확인되는 것은 `ordering` 하나다.

`payment`, `product`, `shipping`을 내부 업무 모듈로 만들지 않는다. 해당 기능은 외부 시스템이 담당하며, 이 시스템에서 필요한 것은 주문 업무가 사용하는 연동 포트와 어댑터다.

- `ordering`
  - 주문 생성
  - 생성 시점 판매가의 확정
  - 주문 금액 계산
  - 카드 승인 요청의 조정
  - 승인·거절 결과에 따른 주문 상태 변경
  - 승인 완료 후 배송 요청 지시
  - 주문 결과 조회
  - 확정된 범위의 본인 주문 접근 검사

- 외부 상품 시스템
  - 주문 생성 시 필요한 판매가 제공
  - 재고 판단 시점과 처리 정책은 미정이므로 아키텍처 흐름에 확정하여 넣지 않음

- 외부 결제 시스템
  - 카드 승인 처리
  - 승인·거절·확정 불가 결과 제공

- 외부 배송 시스템
  - 승인 완료된 주문의 확정 배송지에 대한 배송 요청 수신
  - 실패·재시도·중복 방지 정책은 미정

## 5. 포트 배치

### 입력 포트

#### `CreateOrderUseCase`

입력:

- 요청 주체를 나타내는 컨텍스트
- 상품 번호와 수량의 목록
- 배송지

책임:

1. 상품 시스템으로부터 주문 생성 시점의 판매가를 얻는다.
2. 그 판매가를 `OrderItem.unitPrice`로 확정한다.
3. 합계를 계산한다.
4. `PENDING_PAYMENT` 주문을 만든다.
5. 주문을 저장한다.

요청 주체의 구체 타입과 비회원 처리 방법은 미정이므로 회원 번호 같은 구체 필드를 확정하지 않는다.

#### `PayOrderUseCase`

입력:

- 주문 번호
- 카드 승인에 필요한 결제 정보
- 요청 주체를 나타내는 컨텍스트

책임:

1. 저장된 주문의 확정 총액을 사용한다.
2. `ApproveCardPort`로 카드 승인을 요청한다.
3. 승인 완료이면 같은 주문을 `PAID`로 변경한다.
4. 승인 완료 뒤 확정 배송지로 배송을 요청한다.
5. 거절이면 같은 주문을 `PENDING_PAYMENT`로 유지한다.
6. 확정 불가 응답이면 승인이나 거절 상태 전이를 만들지 않는다.

단, 카드 결제 요청에도 “본인 주문” 조건을 적용할지는 미정이므로 이 포트의 권한 검사 정책은 아직 확정할 수 없다.

#### `GetOrderResultQuery`

입력:

- 주문 번호
- 요청 주체를 나타내는 컨텍스트

책임:

- 본인 주문인지 확인한다.
- 주문 상태와 확인 가능한 승인 결과를 반환한다.
- 다른 고객의 주문 조회는 거절한다.

승인 결과의 저장 구조는 정적 모델에서 미정이므로 구체 저장 모델은 정하지 않는다.

### 출력 포트

#### `LoadProductPricePort`

- 주문 생성 시 상품별 현재 판매가를 얻는다.
- 주문 생성 후의 결제 과정에서는 현재 판매가를 다시 읽어 승인 금액을 계산하지 않는다.

#### `ApproveCardPort`

- 카드 승인 요청을 외부 결제 시스템에 전달한다.
- 결과를 `승인`, `거절`, `확정 불가` 중 하나의 업무 의미로 변환한다.
- 전송 시간 초과를 곧바로 거절로 바꾸지 않는다.

#### `RequestDeliveryPort`

- 카드 승인 완료 뒤 주문 번호, 주문 항목, 확정 배송지를 배송 시스템에 전달한다.
- 실패 시 재시도와 중복 방지는 미정이므로 포트의 계약에 임의의 재시도 정책을 포함하지 않는다.

#### `OrderRepository`

- 주문을 저장하고 주문 번호로 조회한다.
- 저장 기술과 데이터베이스 종류는 정하지 않는다.
- 결제 이력 및 승인 결과를 어떤 구조로 보존할지는 별도 결정이 필요하다.

## 6. 의존 규칙

### 허용

- `adapter.in`은 `application.port.in`을 호출할 수 있다.
- `application.service`는 `domain`을 사용할 수 있다.
- `application.service`는 `application.port.out`을 호출할 수 있다.
- `adapter.out`은 `application.port.out`을 구현할 수 있다.
- `domain`은 자신의 값 객체와 도메인 객체에 의존할 수 있다.
- `bootstrap`은 실행 시점 조립을 위해 포트, 서비스, 어댑터를 참조할 수 있다.
- 외부 시스템별 어댑터는 자신의 전송 모델을 내부 포트 모델로 변환할 수 있다.

### 금지

- `domain`이 상품·결제·배송 API 클라이언트나 저장 기술에 의존하는 것을 금지한다.
- `domain`이 HTTP, 메시지 브로커, ORM 같은 기술 타입에 의존하는 것을 금지한다.
- `application.service`가 외부 시스템 SDK를 직접 호출하는 것을 금지한다.
- `adapter.in`이 주문 상태를 직접 변경하거나 주문 금액을 다시 계산하는 것을 금지한다.
- `adapter.out`이 `PENDING_PAYMENT`에서 `PAID`로의 전이를 결정하는 것을 금지한다.
- 결제 어댑터가 결제 승인 금액을 현재 상품 판매가로 다시 계산하는 것을 금지한다.
- 배송 어댑터가 카드 승인 여부와 관계없이 독자적으로 배송 요청을 생성하는 것을 금지한다.
- 외부 결제 시스템의 상태 코드나 배송 시스템의 데이터 타입을 `domain`에 노출하는 것을 금지한다.
- 한 출력 어댑터가 다른 출력 어댑터를 직접 호출하는 것을 금지한다.
- 외부 시스템 장애를 근거 없이 승인, 거절, 주문 만료 또는 취소로 변환하는 것을 금지한다.
- 미정인 재고·만료·재결제·배송 실패 정책을 어댑터의 예외 처리로 몰래 구현하는 것을 금지한다.

## 7. 외부 시스템 연동 규격

아래는 업무 수준의 최소 규격이다. HTTP, 메시지, 동기·비동기 여부와 구체 필드 형식은 확정하지 않는다.

### 상품 시스템: 판매가 조회

요청:

```text
ProductPriceRequest
- productNumber
```

응답:

```text
ProductPriceResponse
- productNumber
- salePrice
- currencyOrUnit
```

규칙:

- `salePrice`는 원 단위 0 이상 정수여야 한다.
- 주문 생성 시 받은 판매가를 주문 항목의 확정 단가로 저장한다.
- 같은 상품을 여러 항목으로 허용할지 합칠지는 미정이다.
- 재고 관련 필드는 재고 판단 시점이 정해지기 전까지 필수 계약으로 넣지 않는다.

### 결제 시스템: 카드 승인

요청:

```text
CardApprovalRequest
- orderNumber
- amount
- cardApprovalData
- requestReference
```

응답:

```text
CardApprovalResponse
- requestReference
- result: APPROVED | DECLINED | UNCONFIRMED
- externalApprovalReference: 승인된 경우 제공 가능한 외부 참조 값
- declineInformation: 거절된 경우 제공 가능한 정보
```

규칙:

- `amount`는 저장된 `Order.totalAmount`와 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 `PAID` 전이를 일으킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- 카드 원문 정보를 주문 도메인에 저장할지는 정하지 않는다.
- `requestReference`의 형식, 재사용 여부, 중복 요청 처리 계약은 결제 응답 미확정 정책과 함께 결정해야 한다.

`UNCONFIRMED`는 새 업무 상태를 뜻하지 않는다. 기존의 “결제 응답을 확정할 수 없음”을 어댑터가 표현하는 결과 분류다.

### 배송 시스템: 배송 요청

요청:

```text
DeliveryRequest
- orderNumber
- shippingAddress
- items
  - productNumber
  - quantity
```

응답:

```text
DeliveryResponse
- orderNumber
- acceptanceResult
- externalDeliveryReference: 제공되는 경우의 외부 참조 값
```

규칙:

- `RequestDeliveryPort`는 승인 완료 처리 뒤에만 호출한다.
- 주문 생성 시 확정된 배송지를 전달한다.
- 거절이나 결제 응답 미확정 시에는 호출하지 않는다.
- 배송비는 범위 밖이므로 포함하지 않는다.
- 배송 요청 실패가 주문의 `PAID` 상태에 미치는 영향은 정하지 않는다.
- 전송 재시도, 중복 방지 키, 응답 시간 초과 처리는 현재 계약으로 확정하지 않는다.

### 호출자와 주문 시스템

최소 업무 요청:

```text
CreateOrder
- requesterContext
- items
- shippingAddress

PayOrder
- requesterContext
- orderNumber
- cardApprovalData

GetOrderResult
- requesterContext
- orderNumber
```

최소 결과:

```text
OrderResult
- orderNumber
- totalAmount
- status
- paymentResult: 확인 가능한 범위
```

- 인증 방식, 비회원 본인 확인 방식, 거절 응답 코드, 화면 표현은 정하지 않는다.
- `paymentResult`의 보존 구조가 미정이므로 상세 필드를 확정하지 않는다.

## 8. 주요 실행 흐름

```mermaid
sequenceDiagram

    participant In as 입력 어댑터
    participant App as 주문 응용 서비스
    participant Order as 주문 도메인
    participant Pay as 결제 출력 포트
    participant Repo as 주문 저장 포트
    participant Delivery as 배송 출력 포트

    Caller->>In: 주문 결제 요청
    In->>App: PayOrder 명령
    App->>Repo: 주문 조회
    Repo-->>App: PENDING_PAYMENT 주문
    App->>Order: 결제 가능 상태 및 확정 금액 확인
    App->>Pay: 카드 승인 요청(확정 총액)
    Pay-->>App: 승인 / 거절 / 확정 불가

    alt 승인
        App->>Order: PAID로 전이
        App->>Repo: 변경된 주문 저장
        App->>Delivery: 확정 배송지로 배송 요청
    else 거절
        App->>Order: PENDING_PAYMENT 유지
        App->>Repo: 필요한 결과 보존
    else 확정 불가
        App->>Order: 승인·거절 전이 없음
        App->>Repo: 필요한 결과 보존
    end

    App-->>In: 확인 가능한 주문 결과
    In-->>Caller: 주문 결과
```

이 도식은 업무 순서와 의존 역할을 보여 줄 뿐 다음 사항을 확정하지 않는다.

- 외부 호출이 동기인지 비동기인지
- 상태 저장과 배송 요청의 원자성
- 승인 뒤 저장 실패 처리
- 배송 실패 재시도
- 확정 불가 응답 뒤 조회 또는 재결제 처리

---

## 9. 품질 기준과 구조의 관계

동시 결제 100건 중 95건 이상이 3초 이내 완료되어야 한다는 시험 기준은 구조 선택에 다음 정도의 근거만 제공한다.

- 결제 어댑터를 테스트 대역으로 교체할 수 있어야 한다.
- 외부 시스템 호출 시간과 주문 내부 처리 시간을 분리해 측정할 수 있어야 한다.
- 주문 응용 서비스가 요청별 가변 상태를 공유하지 않아야 한다.
- 결제 결과 수신까지를 동일한 관측 구간으로 측정할 수 있어야 한다.

하지만 이 기준만으로 다음을 확정할 수는 없다.

- 서버 인스턴스 수
- 스레드 또는 이벤트 루프 모델
- 데이터베이스 종류
- 메시지 브로커 도입
- 타임아웃 값
- 독립 결제 서비스 분리

---

## 10. 결정이 필요한 질문

다음 답에 따라 포트 계약과 실행 흐름이 달라지므로 임의로 확정하지 않는다.

1. 상품 시스템에 재고 판단을 언제 요청해야 하는가? 가격 조회와 같은 호출인가, 별도 요청인가?
2. 승인 전에 재고 부족이 확인되면 주문 상태와 결제 요청은 어떻게 처리해야 하는가?
3. 승인 뒤 재고 부족이 확인되면 이미 완료된 승인과 `PAID` 주문을 어떻게 처리해야 하는가?
4. 결제 결과가 확정 불가일 때 결제 시스템에 결과 조회 기능이 있는가? 그 전까지 같은 주문의 재결제를 허용하는가?
5. 카드 결제 요청에도 “본인 주문만 가능” 규칙을 적용하는가?
6. 비회원 주문을 허용하는가? 허용한다면 조회와 결제 요청에서 본인을 어떻게 확인하는가?
7. 결제대기 기한이 있는가? 있다면 만료 시 상태와 행위는 무엇인가?
8. 배송 요청 실패가 `PAID` 상태에 영향을 주는가? 누가 어떤 조건으로 재요청하는가?
9. 배송 시스템은 중복 요청을 식별하거나 거절할 수 있는 계약을 제공하는가?
10. 승인 결과와 결제 시도 이력을 어느 수준까지 보존해야 하는가?
11. 주문 결과의 별도 통지가 필요한가? 필요하다면 주문 시스템과 별도 통지 시스템 중 누가 담당하는가?
12. 독립 배포가 필요한 조직 또는 운영 조건이 있는가? 예를 들어 결제 연동만 별도 팀이 소유하거나 독립적으로 출시해야 하는가?

마지막 질문에 독립 배포·팀 소유·확장 요구가 확인되면 마이크로서비스 분리를 다시 검토할 수 있다. 그렇지 않다면 포트 경계를 유지한 모듈러 모놀리스가 현재 요구를 가장 적은 가정으로 충족한다.
[사용자]
스타일 비교와 미정을 질문으로 되돌린 것은 받아들인다. 다만 경계와 포트의 배치를 고쳐야 한다.

1. 패키지 이름을 기술 역할이 아니라 업무로 지어라. `adapter.in`·`application.service`·`application.port.out`·`bootstrap`은 기술 역할이다. 실습 4의 용어집에 있는 업무 이름을 쓰고, 연동과 영속은 그 대상별로 나눠라 — 업무는 `order`·`payment`·`delivery`·`product`, 연동은 `paymentadapter`·`deliveryadapter`, 영속은 `persistence`다.

2. 입력 포트와 유스케이스 인터페이스는 두지 마라. 지금 필요한 것은 업무가 외부를 부르는 쪽, 즉 출력 포트뿐이다. 호출자가 들어오는 쪽은 이 과제의 범위가 아니다.

3. 포트를 한 모듈에 몰지 마라. 업무 패키지가 각자 자기 포트를 소유해야 한다 — 결제 승인 포트는 `payment`에, 배송 요청 포트는 `delivery`에, 판매가 조회 포트는 `product`에, 주문 저장 포트는 `order`에 둔다. 연동과 영속이 그 포트를 구현한다.

4. 그 배치로 패키지 다이어그램과 의존 규칙을 다시 써라. 금지는 검사가 판정할 수 있게 패키지 이름으로 적어라.

연동 규격의 내용과 미정 열두 개는 그대로 유지해라. 새 정책을 만들지 마라.

# 수정 아키텍처 제안

## 1. 선택과 판단 근거

이 사례에는 **포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 제안한다.

- **배포 근거:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직 근거:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경 근거:** 주문 규칙과 외부 상품·결제·배송 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동 패키지가 이를 구현한다.

| 후보 | 판단 |
|---|---|
| 계층형 | 기술 계층이 업무 경계보다 앞에 드러나므로 주 구조로 사용하지 않는다. |
| 포트와 어댑터 | 업무 규칙이 외부 시스템 기술에 의존하지 않게 하므로 채택한다. |
| 모듈러 모놀리스 | 현재 독립 배포 근거가 없으면서 패키지 의존은 통제할 수 있으므로 채택한다. |
| 마이크로서비스 | 독립 배포·팀별 소유·개별 확장 근거가 없으므로 현재는 채택하지 않는다. |

입력 포트와 유스케이스 인터페이스는 두지 않는다. 호출자가 주문 시스템으로 들어오는 구조는 이번 패키지 설계 범위에서 제외한다.

## 2. 업무 패키지와 포트 배치

- `order`
  - `Order`, `OrderItem`, `OrderStatus`, `Money`, `Quantity`, `Address`
  - 주문 생성, 금액 확정, 주문 상태 전이
  - `OrderRepository` 출력 포트 소유

- `payment`
  - 카드 승인 요청과 승인 결과의 업무 의미
  - `ApproveCardPort` 출력 포트 소유

- `delivery`
  - 승인 완료 뒤 발생하는 배송 요청의 업무 의미
  - `RequestDeliveryPort` 출력 포트 소유

- `product`
  - 상품 번호와 판매가의 업무 의미
  - `LoadProductPricePort` 출력 포트 소유

- `paymentadapter`
  - 외부 결제 시스템 연동
  - `payment.ApproveCardPort` 구현

- `deliveryadapter`
  - 외부 배송 시스템 연동
  - `delivery.RequestDeliveryPort` 구현

- `persistence`
  - 주문 영속화
  - `order.OrderRepository` 구현

상품 시스템 연동 구현 패키지는 제시된 패키지 이름에 포함되지 않았다. `product`가 `LoadProductPricePort`를 소유한다는 점은 확정할 수 있지만, 구현체를 `productadapter`라는 새 패키지에 둘지는 임의로 확정하지 않는다.

## 3. 패키지 다이어그램


실선 화살표는 소스 코드의 허용 의존 방향이다. 외부 상품 시스템의 점선은 호출 방향이나 코드 의존을 확정한 것이 아니라, `LoadProductPricePort` 구현체의 패키지 이름이 아직 정해지지 않았음을 나타낸다.

### 같은 내용을 목록으로 표현

- `order`
  - 주문 모델과 주문 규칙을 가진다.
  - `OrderRepository`를 소유한다.
  - 카드 승인을 위해 `payment`에 의존한다.
  - 배송 요청을 위해 `delivery`에 의존한다.
  - 주문 생성 시 판매가를 얻기 위해 `product`에 의존한다.

- `payment`
  - `ApproveCardPort`를 소유한다.
  - 외부 결제 시스템의 형식이나 SDK를 알지 않는다.

- `delivery`
  - `RequestDeliveryPort`를 소유한다.
  - 외부 배송 시스템의 형식을 알지 않는다.

- `product`
  - `LoadProductPricePort`를 소유한다.
  - 외부 상품 시스템의 형식을 업무 모델에 노출하지 않는다.

- `paymentadapter`
  - `payment.ApproveCardPort`를 구현한다.
  - 외부 결제 시스템과 통신한다.

- `deliveryadapter`
  - `delivery.RequestDeliveryPort`를 구현한다.
  - 외부 배송 시스템과 통신한다.

- `persistence`
  - `order.OrderRepository`를 구현한다.
  - 주문 저장소와 통신한다.

## 4. 패키지 의존 규칙

다음 규칙은 패키지 간 import 또는 참조 관계를 검사하여 판정할 수 있게 작성한다.

### 허용

- `order`는 `payment`, `delivery`, `product`를 참조할 수 있다.
- `paymentadapter`는 `payment`를 참조할 수 있다.
- `deliveryadapter`는 `delivery`를 참조할 수 있다.
- `persistence`는 `order`를 참조할 수 있다.
- `paymentadapter`는 외부 결제 시스템 라이브러리를 참조할 수 있다.
- `deliveryadapter`는 외부 배송 시스템 라이브러리를 참조할 수 있다.
- `persistence`는 데이터베이스 및 영속 기술 라이브러리를 참조할 수 있다.

### 금지

- `order`는 `paymentadapter`, `deliveryadapter`, `persistence`를 참조할 수 없다.
- `payment`는 `order`, `delivery`, `product`, `paymentadapter`, `deliveryadapter`, `persistence`를 참조할 수 없다.
- `delivery`는 `order`, `payment`, `product`, `paymentadapter`, `deliveryadapter`, `persistence`를 참조할 수 없다.
- `product`는 `order`, `payment`, `delivery`, `paymentadapter`, `deliveryadapter`, `persistence`를 참조할 수 없다.
- `paymentadapter`는 `order`, `delivery`, `product`, `deliveryadapter`, `persistence`를 참조할 수 없다.
- `deliveryadapter`는 `order`, `payment`, `product`, `paymentadapter`, `persistence`를 참조할 수 없다.
- `persistence`는 `payment`, `delivery`, `product`, `paymentadapter`, `deliveryadapter`를 참조할 수 없다.
- `paymentadapter`가 `payment`의 승인·거절 의미를 벗어나 주문 상태를 직접 변경하는 것을 금지한다.
- `deliveryadapter`가 `delivery`의 요청 없이 배송 요청을 생성하는 것을 금지한다.
- `persistence`가 주문 상태 전이 또는 주문 금액을 결정하는 것을 금지한다.
- 미정인 재고·만료·응답 미확정·배송 실패 정책을 어느 패키지에도 구현하지 않는다.

## 5. 외부 시스템 연동 규격

아래는 업무 수준의 최소 규격이다. HTTP, 메시지, 동기·비동기 여부와 구체 필드 형식은 확정하지 않는다.

### 상품 시스템: 판매가 조회

요청:

```text
ProductPriceRequest
- productNumber
```

응답:

```text
ProductPriceResponse
- productNumber
- salePrice
- currencyOrUnit
```

규칙:

- `salePrice`는 원 단위 0 이상 정수여야 한다.
- 주문 생성 시 받은 판매가를 주문 항목의 확정 단가로 저장한다.
- 같은 상품을 여러 항목으로 허용할지 합칠지는 미정이다.
- 재고 관련 필드는 재고 판단 시점이 정해지기 전까지 필수 계약으로 넣지 않는다.

### 결제 시스템: 카드 승인

요청:

```text
CardApprovalRequest
- orderNumber
- amount
- cardApprovalData
- requestReference
```

응답:

```text
CardApprovalResponse
- requestReference
- result: APPROVED | DECLINED | UNCONFIRMED
- externalApprovalReference: 승인된 경우 제공 가능한 외부 참조 값
- declineInformation: 거절된 경우 제공 가능한 정보
```

규칙:

- `amount`는 저장된 `Order.totalAmount`와 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 `PAID` 전이를 일으킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- 카드 원문 정보를 주문 도메인에 저장할지는 정하지 않는다.
- `requestReference`의 형식, 재사용 여부, 중복 요청 처리 계약은 결제 응답 미확정 정책과 함께 결정해야 한다.

`UNCONFIRMED`는 새 업무 상태를 뜻하지 않는다. 기존의 “결제 응답을 확정할 수 없음”을 어댑터가 표현하는 결과 분류다.

### 배송 시스템: 배송 요청

요청:

```text
DeliveryRequest
- orderNumber
- shippingAddress
- items
  - productNumber
  - quantity
```

응답:

```text
DeliveryResponse
- orderNumber
- acceptanceResult
- externalDeliveryReference: 제공되는 경우의 외부 참조 값
```

규칙:

- `RequestDeliveryPort`는 승인 완료 처리 뒤에만 호출한다.
- 주문 생성 시 확정된 배송지를 전달한다.
- 거절이나 결제 응답 미확정 시에는 호출하지 않는다.
- 배송비는 범위 밖이므로 포함하지 않는다.
- 배송 요청 실패가 주문의 `PAID` 상태에 미치는 영향은 정하지 않는다.
- 전송 재시도, 중복 방지 키, 응답 시간 초과 처리는 현재 계약으로 확정하지 않는다.

### 호출자와 주문 시스템

최소 업무 요청:

```text
CreateOrder
- requesterContext
- items
- shippingAddress

PayOrder
- requesterContext
- orderNumber
- cardApprovalData

GetOrderResult
- requesterContext
- orderNumber
```

최소 결과:

```text
OrderResult
- orderNumber
- totalAmount
- status
- paymentResult: 확인 가능한 범위
```

- 인증 방식, 비회원 본인 확인 방식, 거절 응답 코드, 화면 표현은 정하지 않는다.
- `paymentResult`의 보존 구조가 미정이므로 상세 필드를 확정하지 않는다.
- 위 규격은 업무 메시지만 나타낸다. 이를 처리할 입력 포트나 유스케이스 인터페이스의 배치는 이번 범위에서 정하지 않는다.

## 6. 결정이 필요한 질문

다음 답에 따라 포트 계약과 실행 흐름이 달라지므로 임의로 확정하지 않는다.

1. 상품 시스템에 재고 판단을 언제 요청해야 하는가? 가격 조회와 같은 호출인가, 별도 요청인가?
2. 승인 전에 재고 부족이 확인되면 주문 상태와 결제 요청은 어떻게 처리해야 하는가?
3. 승인 뒤 재고 부족이 확인되면 이미 완료된 승인과 `PAID` 주문을 어떻게 처리해야 하는가?
4. 결제 결과가 확정 불가일 때 결제 시스템에 결과 조회 기능이 있는가? 그 전까지 같은 주문의 재결제를 허용하는가?
5. 카드 결제 요청에도 “본인 주문만 가능” 규칙을 적용하는가?
6. 비회원 주문을 허용하는가? 허용한다면 조회와 결제 요청에서 본인을 어떻게 확인하는가?
7. 결제대기 기한이 있는가? 있다면 만료 시 상태와 행위는 무엇인가?
8. 배송 요청 실패가 `PAID` 상태에 영향을 주는가? 누가 어떤 조건으로 재요청하는가?
9. 배송 시스템은 중복 요청을 식별하거나 거절할 수 있는 계약을 제공하는가?
10. 승인 결과와 결제 시도 이력을 어느 수준까지 보존해야 하는가?
11. 주문 결과의 별도 통지가 필요한가? 필요하다면 주문 시스템과 별도 통지 시스템 중 누가 담당하는가?
12. 독립 배포가 필요한 조직 또는 운영 조건이 있는가? 예를 들어 결제 연동만 별도 팀이 소유하거나 독립적으로 출시해야 하는가?

추가로 패키지 배치를 완성하려면 한 가지 구조 확인이 필요하다. `product.LoadProductPricePort`의 외부 상품 시스템 구현체를 둘 `productadapter` 패키지를 추가해도 되는가? 제시된 목록에 없으므로 현재 다이어그램에서는 그 구현 위치를 확정하지 않았다.
[사용자]
포트 배치와 패키지 이름은 받아들인다. 의존 규칙을 고쳐야 한다.

1. 패키지 순환 금지가 빠졌다. 더해라. 순환이 있으면 두 패키지를 따로 바꿀 수도 따로 검증할 수도 없다.

2. 금지 목록이 쌍마다 나열되어 길다. 검사가 판정할 수 있는 최소한으로 줄여라. 업무 패키지에서 연동·영속으로 가는 의존과 패키지 사이의 순환, 이 둘이 검사가 볼 금지다. 업무 패키지끼리의 참조는 허용 목록의 반대로 읽히므로 따로 적지 마라. "주문 상태를 직접 변경하지 않는다" 같은 책임에 관한 금지는 검사가 판정하지 못하므로 의존 규칙이 아니라 책임의 약속으로 따로 묶어라.

3. 상품 시스템 연동 구현은 이번 범위 밖으로 둔다. `product`는 포트를 선언만 하고 구현 패키지는 만들지 않는다는 것을 적어라.

4. 패키지 다이어그램에서 연동·영속이 업무의 포트를 구현한다는 화살표가 업무 쪽을 향하도록 그려라. 지금 도식은 어댑터에서 포트로 가는 간선이 보이지 않는다.

연동 규격과 미정은 그대로 유지해라.

# 수정 아키텍처 제안

## 1. 선택과 판단 근거

이 사례에는 **포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 제안한다.

- **배포 근거:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직 근거:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경 근거:** 주문 규칙과 외부 상품·결제·배송 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 이를 구현한다.

| 후보 | 판단 |
|---|---|
| 계층형 | 기술 계층이 업무 경계보다 앞에 드러나므로 주 구조로 사용하지 않는다. |
| 포트와 어댑터 | 업무 규칙이 외부 시스템 기술에 의존하지 않게 하므로 채택한다. |
| 모듈러 모놀리스 | 현재 독립 배포 근거가 없으면서 패키지 의존은 통제할 수 있으므로 채택한다. |
| 마이크로서비스 | 독립 배포·팀별 소유·개별 확장 근거가 없으므로 현재는 채택하지 않는다. |

입력 포트와 유스케이스 인터페이스는 두지 않는다. 호출자가 주문 시스템으로 들어오는 구조는 이번 패키지 설계 범위에서 제외한다.

## 2. 업무 패키지와 포트 배치

- `order`
  - `Order`, `OrderItem`, `OrderStatus`, `Money`, `Quantity`, `Address`
  - 주문 생성, 금액 확정, 주문 상태 전이
  - `OrderRepository` 출력 포트 소유

- `payment`
  - 카드 승인 요청과 승인 결과의 업무 의미
  - `ApproveCardPort` 출력 포트 소유

- `delivery`
  - 승인 완료 뒤 발생하는 배송 요청의 업무 의미
  - `RequestDeliveryPort` 출력 포트 소유

- `product`
  - 상품 번호와 판매가의 업무 의미
  - `LoadProductPricePort` 출력 포트 소유
  - 이번 범위에서는 포트만 선언하며 외부 상품 시스템 연동 구현 패키지는 만들지 않음

- `paymentadapter`
  - 외부 결제 시스템 연동
  - `payment.ApproveCardPort` 구현

- `deliveryadapter`
  - 외부 배송 시스템 연동
  - `delivery.RequestDeliveryPort` 구현

- `persistence`
  - 주문 영속화
  - `order.OrderRepository` 구현

상품 시스템의 판매가 조회 규격은 정의하지만, `product.LoadProductPricePort`의 구현 위치와 구현 기술은 이번 범위 밖이다.

화살표는 소스 코드의 의존 방향을 나타낸다. `paymentadapter`, `deliveryadapter`, `persistence`에서 각 포트로 향하는 화살표는 해당 패키지가 업무 패키지 소유의 포트를 구현한다는 뜻이다.

외부 상품 시스템과 그 구현 패키지는 도식에 넣지 않는다. `product`는 `LoadProductPricePort`를 선언하지만 그 구현은 이번 범위 밖이다.

### 같은 내용을 목록으로 표현

- `order`
  - 주문 모델과 주문 규칙을 가진다.
  - `OrderRepository`를 소유한다.
  - 카드 승인을 위해 `payment.ApproveCardPort`를 참조할 수 있다.
  - 배송 요청을 위해 `delivery.RequestDeliveryPort`를 참조할 수 있다.
  - 주문 생성 시 판매가를 얻기 위해 `product.LoadProductPricePort`를 참조할 수 있다.

- `payment`
  - `ApproveCardPort`를 소유한다.
  - `paymentadapter`가 이 포트를 구현한다.

- `delivery`
  - `RequestDeliveryPort`를 소유한다.
  - `deliveryadapter`가 이 포트를 구현한다.

- `product`
  - `LoadProductPricePort`를 소유한다.
  - 이번 범위에서는 포트만 선언한다.
  - 외부 상품 시스템 연동 구현 패키지는 이번 범위에서 만들지 않는다.

- `paymentadapter`
  - `payment.ApproveCardPort`를 구현한다.
  - 외부 결제 시스템과 통신한다.

- `deliveryadapter`
  - `delivery.RequestDeliveryPort`를 구현한다.
  - 외부 배송 시스템과 통신한다.

- `persistence`
  - `order.OrderRepository`를 구현한다.
  - 주문 저장소와 통신한다.

## 4. 패키지 의존 규칙

다음 규칙은 패키지의 import 또는 참조 관계를 정적으로 검사하여 판정할 수 있게 작성한다.

### 허용

- `order`는 `payment`, `delivery`, `product`를 참조할 수 있다.
- `paymentadapter`는 `payment`를 참조할 수 있다.
- `deliveryadapter`는 `delivery`를 참조할 수 있다.
- `persistence`는 `order`를 참조할 수 있다.
- `paymentadapter`는 외부 결제 시스템 라이브러리를 참조할 수 있다.
- `deliveryadapter`는 외부 배송 시스템 라이브러리를 참조할 수 있다.
- `persistence`는 데이터베이스 및 영속 기술 라이브러리를 참조할 수 있다.

허용 목록에 없는 업무 패키지 사이의 참조는 허용하지 않는다.

### 검사 가능한 금지

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- `order`, `payment`, `delivery`, `product`, `paymentadapter`, `deliveryadapter`, `persistence` 사이에 직·간접 패키지 의존 순환이 생기는 것을 금지한다.

예를 들어 `order → payment`가 존재하면 `payment → order`뿐 아니라 `payment → X → order`와 같은 간접 순환도 금지한다. 순환이 생기면 관련 패키지를 독립적으로 변경하거나 검증하기 어려워지기 때문이다.

### 책임의 약속

다음은 import 검사로 판정하는 의존 규칙이 아니라 각 패키지가 지켜야 할 책임의 약속이다.

- `paymentadapter`는 외부 결제 결과를 `payment`가 정의한 승인·거절·확정 불가의 업무 의미로 변환한다. 주문 상태를 결정하거나 직접 변경하지 않는다.
- `deliveryadapter`는 `delivery`가 표현한 요청을 외부 배송 시스템에 전달한다. 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장하고 조회한다. 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`의 포트나 이후의 구현에서 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 5. 외부 시스템 연동 규격

아래는 업무 수준의 최소 규격이다. HTTP, 메시지, 동기·비동기 여부와 구체 필드 형식은 확정하지 않는다.

### 상품 시스템: 판매가 조회

요청:

```text
ProductPriceRequest
- productNumber
```

응답:

```text
ProductPriceResponse
- productNumber
- salePrice
- currencyOrUnit
```

규칙:

- `salePrice`는 원 단위 0 이상 정수여야 한다.
- 주문 생성 시 받은 판매가를 주문 항목의 확정 단가로 저장한다.
- 같은 상품을 여러 항목으로 허용할지 합칠지는 미정이다.
- 재고 관련 필드는 재고 판단 시점이 정해지기 전까지 필수 계약으로 넣지 않는다.

### 결제 시스템: 카드 승인

요청:

```text
CardApprovalRequest
- orderNumber
- amount
- cardApprovalData
- requestReference
```

응답:

```text
CardApprovalResponse
- requestReference
- result: APPROVED | DECLINED | UNCONFIRMED
- externalApprovalReference: 승인된 경우 제공 가능한 외부 참조 값
- declineInformation: 거절된 경우 제공 가능한 정보
```

규칙:

- `amount`는 저장된 `Order.totalAmount`와 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 `PAID` 전이를 일으킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- 카드 원문 정보를 주문 도메인에 저장할지는 정하지 않는다.
- `requestReference`의 형식, 재사용 여부, 중복 요청 처리 계약은 결제 응답 미확정 정책과 함께 결정해야 한다.

`UNCONFIRMED`는 새 업무 상태를 뜻하지 않는다. 기존의 “결제 응답을 확정할 수 없음”을 어댑터가 표현하는 결과 분류다.

### 배송 시스템: 배송 요청

요청:

```text
DeliveryRequest
- orderNumber
- shippingAddress
- items
  - productNumber
  - quantity
```

응답:

```text
DeliveryResponse
- orderNumber
- acceptanceResult
- externalDeliveryReference: 제공되는 경우의 외부 참조 값
```

규칙:

- `RequestDeliveryPort`는 승인 완료 처리 뒤에만 호출한다.
- 주문 생성 시 확정된 배송지를 전달한다.
- 거절이나 결제 응답 미확정 시에는 호출하지 않는다.
- 배송비는 범위 밖이므로 포함하지 않는다.
- 배송 요청 실패가 주문의 `PAID` 상태에 미치는 영향은 정하지 않는다.
- 전송 재시도, 중복 방지 키, 응답 시간 초과 처리는 현재 계약으로 확정하지 않는다.

### 호출자와 주문 시스템

최소 업무 요청:

```text
CreateOrder
- requesterContext
- items
- shippingAddress

PayOrder
- requesterContext
- orderNumber
- cardApprovalData

GetOrderResult
- requesterContext
- orderNumber
```

최소 결과:

```text
OrderResult
- orderNumber
- totalAmount
- status
- paymentResult: 확인 가능한 범위
```

- 인증 방식, 비회원 본인 확인 방식, 거절 응답 코드, 화면 표현은 정하지 않는다.
- `paymentResult`의 보존 구조가 미정이므로 상세 필드를 확정하지 않는다.
- 위 규격은 업무 메시지만 나타낸다. 이를 처리할 입력 포트나 유스케이스 인터페이스의 배치는 이번 범위에서 정하지 않는다.

## 6. 결정이 필요한 질문

다음 답에 따라 포트 계약과 실행 흐름이 달라지므로 임의로 확정하지 않는다.

1. 상품 시스템에 재고 판단을 언제 요청해야 하는가? 가격 조회와 같은 호출인가, 별도 요청인가?
2. 승인 전에 재고 부족이 확인되면 주문 상태와 결제 요청은 어떻게 처리해야 하는가?
3. 승인 뒤 재고 부족이 확인되면 이미 완료된 승인과 `PAID` 주문을 어떻게 처리해야 하는가?
4. 결제 결과가 확정 불가일 때 결제 시스템에 결과 조회 기능이 있는가? 그 전까지 같은 주문의 재결제를 허용하는가?
5. 카드 결제 요청에도 “본인 주문만 가능” 규칙을 적용하는가?
6. 비회원 주문을 허용하는가? 허용한다면 조회와 결제 요청에서 본인을 어떻게 확인하는가?
7. 결제대기 기한이 있는가? 있다면 만료 시 상태와 행위는 무엇인가?
8. 배송 요청 실패가 `PAID` 상태에 영향을 주는가? 누가 어떤 조건으로 재요청하는가?
9. 배송 시스템은 중복 요청을 식별하거나 거절할 수 있는 계약을 제공하는가?
10. 승인 결과와 결제 시도 이력을 어느 수준까지 보존해야 하는가?
11. 주문 결과의 별도 통지가 필요한가? 필요하다면 주문 시스템과 별도 통지 시스템 중 누가 담당하는가?
12. 독립 배포가 필요한 조직 또는 운영 조건이 있는가? 예를 들어 결제 연동만 별도 팀이 소유하거나 독립적으로 출시해야 하는가?
[사용자]
의존 규칙과 도식은 받아들인다. 연동 규격을 한 번 더 보자.

규격에 `currencyOrUnit`, `requestReference`, `externalApprovalReference`, `declineInformation`, `acceptanceResult`, `externalDeliveryReference` 같은 필드가 들어 있다. 이것들은 제공자가 정하는 전문의 형식이지 업무가 주고받는 말이 아니다. 업무 쪽에서 보내는 것과 받는 것만 남기고, 제공자의 필드 이름·참조 값·코드 체계는 연동 안의 일로 돌려라. 금액은 원 단위 정수라는 업무 규칙이 이미 있으므로 단위 필드를 따로 두지 마라.

승인·거절·확정 불가 셋을 업무의 결과로 두는 것은 맞다. 그 셋이 업무의 말이고, 그것을 무엇으로 받아 오는지는 연동이 정한다.

나머지는 그대로 두고, 품질 기준과 결정이 필요한 질문도 유지해라.

# 수정 아키텍처 제안

## 1. 선택과 판단 근거

이 사례에는 **포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 제안한다.

- **배포 근거:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직 근거:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경 근거:** 주문 규칙과 외부 상품·결제·배송 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 이를 구현한다.

| 후보 | 판단 |
|---|---|
| 계층형 | 기술 계층이 업무 경계보다 앞에 드러나므로 주 구조로 사용하지 않는다. |
| 포트와 어댑터 | 업무 규칙이 외부 시스템 기술에 의존하지 않게 하므로 채택한다. |
| 모듈러 모놀리스 | 현재 독립 배포 근거가 없으면서 패키지 의존은 통제할 수 있으므로 채택한다. |
| 마이크로서비스 | 독립 배포·팀별 소유·개별 확장 근거가 없으므로 현재는 채택하지 않는다. |

입력 포트와 유스케이스 인터페이스는 두지 않는다. 호출자가 주문 시스템으로 들어오는 구조는 이번 패키지 설계 범위에서 제외한다.

## 2. 업무 패키지와 포트 배치

- `order`
  - `Order`, `OrderItem`, `OrderStatus`, `Money`, `Quantity`, `Address`
  - 주문 생성, 금액 확정, 주문 상태 전이
  - `OrderRepository` 출력 포트 소유

- `payment`
  - 카드 승인 요청과 승인 결과의 업무 의미
  - `ApproveCardPort` 출력 포트 소유

- `delivery`
  - 승인 완료 뒤 발생하는 배송 요청의 업무 의미
  - `RequestDeliveryPort` 출력 포트 소유

- `product`
  - 상품 번호와 판매가의 업무 의미
  - `LoadProductPricePort` 출력 포트 소유
  - 이번 범위에서는 포트만 선언하며 외부 상품 시스템 연동 구현 패키지는 만들지 않음

- `paymentadapter`
  - 외부 결제 시스템 연동
  - `payment.ApproveCardPort` 구현
  - 결제 제공자의 전문, 필드 이름, 참조 값 및 코드 체계를 업무의 요청·결과로 변환

- `deliveryadapter`
  - 외부 배송 시스템 연동
  - `delivery.RequestDeliveryPort` 구현
  - 배송 제공자의 전문, 필드 이름, 참조 값 및 코드 체계를 업무의 배송 요청으로 변환

- `persistence`
  - 주문 영속화
  - `order.OrderRepository` 구현

상품 시스템의 판매가 조회 업무 규격은 정의하지만, `product.LoadProductPricePort`의 구현 위치와 구현 기술은 이번 범위 밖이다.

화살표는 소스 코드의 의존 방향을 나타낸다. `paymentadapter`, `deliveryadapter`, `persistence`에서 각 포트로 향하는 화살표는 해당 패키지가 업무 패키지 소유의 포트를 구현한다는 뜻이다.

외부 상품 시스템과 그 구현 패키지는 도식에 넣지 않는다. `product`는 `LoadProductPricePort`를 선언하지만 그 구현은 이번 범위 밖이다.

### 같은 내용을 목록으로 표현

- `order`
  - 주문 모델과 주문 규칙을 가진다.
  - `OrderRepository`를 소유한다.
  - 카드 승인을 위해 `payment.ApproveCardPort`를 참조할 수 있다.
  - 배송 요청을 위해 `delivery.RequestDeliveryPort`를 참조할 수 있다.
  - 주문 생성 시 판매가를 얻기 위해 `product.LoadProductPricePort`를 참조할 수 있다.

- `payment`
  - `ApproveCardPort`를 소유한다.
  - 승인 요청과 승인·거절·확정 불가라는 업무 결과를 정의한다.
  - `paymentadapter`가 이 포트를 구현한다.

- `delivery`
  - `RequestDeliveryPort`를 소유한다.
  - `deliveryadapter`가 이 포트를 구현한다.

- `product`
  - `LoadProductPricePort`를 소유한다.
  - 이번 범위에서는 포트만 선언한다.
  - 외부 상품 시스템 연동 구현 패키지는 이번 범위에서 만들지 않는다.

- `paymentadapter`
  - `payment.ApproveCardPort`를 구현한다.
  - 외부 결제 시스템과 통신한다.
  - 제공자의 전문을 업무의 승인·거절·확정 불가 결과로 변환한다.

- `deliveryadapter`
  - `delivery.RequestDeliveryPort`를 구현한다.
  - 외부 배송 시스템과 통신한다.
  - 업무의 배송 요청을 제공자의 전문으로 변환한다.

- `persistence`
  - `order.OrderRepository`를 구현한다.
  - 주문 저장소와 통신한다.

## 4. 패키지 의존 규칙

다음 규칙은 패키지의 import 또는 참조 관계를 정적으로 검사하여 판정할 수 있게 작성한다.

### 허용

- `order`는 `payment`, `delivery`, `product`를 참조할 수 있다.
- `paymentadapter`는 `payment`를 참조할 수 있다.
- `deliveryadapter`는 `delivery`를 참조할 수 있다.
- `persistence`는 `order`를 참조할 수 있다.
- `paymentadapter`는 외부 결제 시스템 라이브러리를 참조할 수 있다.
- `deliveryadapter`는 외부 배송 시스템 라이브러리를 참조할 수 있다.
- `persistence`는 데이터베이스 및 영속 기술 라이브러리를 참조할 수 있다.

허용 목록에 없는 업무 패키지 사이의 참조는 허용하지 않는다.

### 검사 가능한 금지

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- `order`, `payment`, `delivery`, `product`, `paymentadapter`, `deliveryadapter`, `persistence` 사이에 직·간접 패키지 의존 순환이 생기는 것을 금지한다.

예를 들어 `order → payment`가 존재하면 `payment → order`뿐 아니라 `payment → X → order`와 같은 간접 순환도 금지한다. 순환이 생기면 관련 패키지를 독립적으로 변경하거나 검증하기 어려워지기 때문이다.

### 책임의 약속

다음은 import 검사로 판정하는 의존 규칙이 아니라 각 패키지가 지켜야 할 책임의 약속이다.

- `paymentadapter`는 외부 결제 제공자의 전문을 `payment`가 정의한 승인·거절·확정 불가의 업무 의미로 변환한다. 제공자의 필드 이름, 참조 값 및 코드 체계를 업무 패키지에 노출하지 않는다.
- `paymentadapter`는 주문 상태를 결정하거나 직접 변경하지 않는다.
- `deliveryadapter`는 `delivery`가 표현한 요청을 외부 배송 시스템에 전달한다. 제공자의 필드 이름, 참조 값 및 코드 체계를 업무 패키지에 노출하지 않으며 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장하고 조회한다. 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`의 포트나 이후의 구현에서 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 5. 외부 시스템 연동 규격

아래 규격은 업무 패키지가 외부에 보내고 외부로부터 받는 **업무의 말**만 정의한다. HTTP, 메시지, 동기·비동기 여부, 제공자의 전문 형식과 필드 이름, 참조 값 및 코드 체계는 확정하지 않는다.

제공자 규격과 업무 규격 사이의 변환은 해당 연동 구현의 책임이다.

### 상품 시스템: 판매가 조회

업무가 보내는 것:

```text
ProductPriceRequest
- productNumber
```

업무가 받는 것:

```text
ProductPriceResponse
- productNumber
- salePrice
```

규칙:

- `salePrice`는 원 단위 0 이상 정수여야 한다.
- 금액 단위는 업무 규칙상 원으로 확정되어 있으므로 별도의 단위 필드를 두지 않는다.
- 주문 생성 시 받은 판매가를 주문 항목의 확정 단가로 저장한다.
- 같은 상품을 여러 항목으로 허용할지 합칠지는 미정이다.
- 재고 관련 필드는 재고 판단 시점이 정해지기 전까지 업무 규격에 넣지 않는다.
- 외부 상품 시스템의 실제 전문과 이를 변환할 구현은 이번 범위 밖이다.

### 결제 시스템: 카드 승인

업무가 보내는 것:

```text
CardApprovalRequest
- orderNumber
- amount
- cardApprovalData
```

업무가 받는 것:

```text
CardApprovalResult
- result: APPROVED | DECLINED | UNCONFIRMED
```

규칙:

- `amount`는 원 단위 0 이상 정수이며 저장된 `Order.totalAmount`와 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 `PAID` 전이를 일으킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- `APPROVED`, `DECLINED`, `UNCONFIRMED`는 `payment`가 사용하는 업무의 결과다.
- 외부 결제 시스템이 어떤 필드, 참조 값 또는 코드로 결과를 제공하는지는 `paymentadapter` 안에서 처리한다.
- 카드 원문 정보를 주문 도메인에 저장할지는 정하지 않는다.
- 외부 참조 값의 보존 여부, 중복 요청의 식별과 처리 계약은 결제 응답 미확정 정책과 함께 결정해야 하므로 업무 규격에 넣지 않는다.

`UNCONFIRMED`는 새 주문 상태를 뜻하지 않는다. 기존의 “결제 응답을 확정할 수 없음”을 나타내는 결제 업무의 결과이며, `paymentadapter`가 제공자의 응답이나 통신 결과를 이 의미로 변환한다.

### 배송 시스템: 배송 요청

업무가 보내는 것:

```text
DeliveryRequest
- orderNumber
- shippingAddress
- items
  - productNumber
  - quantity
```

현재 업무가 받는 것:

```text
정의하지 않음
```

규칙:

- 현재 요구에서 확인된 업무 사건은 승인 완료 뒤 배송 요청을 보내는 것까지다.
- 배송 제공자의 접수 결과, 참조 값 또는 코드 체계를 업무 결과로 채택할 근거가 없으므로 응답 필드를 두지 않는다.
- 외부 배송 시스템의 실제 전문이나 기술적 응답 처리가 필요하다면 `deliveryadapter` 내부에서 다룬다.
- `RequestDeliveryPort`는 승인 완료 처리 뒤에만 호출한다.
- 주문 생성 시 확정된 배송지를 전달한다.
- 거절이나 결제 응답 미확정 시에는 호출하지 않는다.
- 배송비는 범위 밖이므로 포함하지 않는다.
- 배송 요청 실패가 주문의 `PAID` 상태에 미치는 영향은 정하지 않는다.
- 전송 재시도, 중복 방지 키, 응답 시간 초과 처리는 현재 계약으로 확정하지 않는다.

### 호출자와 주문 시스템

최소 업무 요청:

```text
CreateOrder
- requesterContext
- items
- shippingAddress

PayOrder
- requesterContext
- orderNumber
- cardApprovalData

GetOrderResult
- requesterContext
- orderNumber
```

최소 결과:

```text
OrderResult
- orderNumber
- totalAmount
- status
- paymentResult: 확인 가능한 범위
```

- 인증 방식, 비회원 본인 확인 방식, 거절 응답 코드, 화면 표현은 정하지 않는다.
- `paymentResult`의 보존 구조가 미정이므로 상세 필드를 확정하지 않는다.
- 위 규격은 업무 메시지만 나타낸다. 이를 처리할 입력 포트나 유스케이스 인터페이스의 배치는 이번 범위에서 정하지 않는다.

## 6. 품질 기준과 구조의 관계

동시 결제 100건 중 95건 이상이 3초 이내 완료되어야 한다는 실습 시험 기준은 구조 선택에 다음 근거를 제공한다.

- `payment.ApproveCardPort` 구현을 테스트 대역으로 교체할 수 있어야 한다.
- 외부 시스템 연동 시간과 주문 내부 처리 시간을 분리해 측정할 수 있어야 한다.
- 결제 요청별 가변 상태를 공유하여 요청끼리 간섭하게 해서는 안 된다.
- 공통 흐름 4의 결제 요청부터 공통 흐름 5의 결과 수신까지를 같은 관측 구간으로 측정할 수 있어야 한다.
- 외부 시스템 테스트 대역이 각각 1초 이내에 응답하는 조건에서 100건을 동시에 실행하여, 95건 이상이 각각 3초 이내에 완료되는지 검증할 수 있어야 한다.

이 기준은 실습 시험용이며 실제 운영 환경의 보장 값이 아니다. 또한 이 기준만으로 다음 사항을 확정하지 않는다.

- 서버 인스턴스 수
- 스레드 또는 이벤트 루프 모델
- 데이터베이스 종류
- 메시지 브로커 도입
- 외부 연동의 동기·비동기 방식
- 구체적인 타임아웃 값
- 결제 기능의 독립 서비스 분리

## 7. 결정이 필요한 질문

다음 답에 따라 포트 계약과 실행 흐름이 달라지므로 임의로 확정하지 않는다.

3. 승인 뒤 재고 부족이 확인되면 이미 완료된 승인과 `PAID` 주문을 어떻게 처리해야 하는가?

9. 배송 시스템은 중복 요청을 식별하거나 거절할 수 있는 계약을 제공하는가?
10. 승인 결과와 결제 시도 이력을 어느 수준까지 보존해야 하는가?
11. 주문 결과의 별도 통지가 필요한가? 필요하다면 주문 시스템과 별도 통지 시스템 중 누가 담당하는가?

# “주문한다” 아키텍처 결정

## 1. 아키텍처 스타일과 근거

**포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 선택한다.

- **배포:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경:** 주문 규칙과 외부 상품·결제·배송 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 이를 구현한다.

계층형은 기술 계층이 업무 경계보다 앞에 드러나므로 주 구조로 사용하지 않는다. 마이크로서비스는 독립 배포·팀별 소유·개별 확장의 근거가 없어 채택하지 않는다.

입력 포트와 유스케이스 인터페이스는 두지 않는다. 호출자가 주문 시스템으로 들어오는 구조는 이번 패키지 설계 범위에서 제외한다.

## 2. 업무 패키지와 포트 배치

- `order`
  - `Order`, `OrderItem`, `OrderStatus`, `Money`, `Quantity`, `Address`
  - 주문 생성, 금액 확정, 주문 상태 전이
  - `OrderRepository` 출력 포트 소유

- `payment`
  - 카드 승인 요청과 승인 결과의 업무 의미
  - `ApproveCardPort` 출력 포트 소유

- `delivery`
  - 승인 완료 뒤 발생하는 배송 요청의 업무 의미
  - `RequestDeliveryPort` 출력 포트 소유

- `product`
  - 상품 번호와 판매가의 업무 의미
  - `LoadProductPricePort` 출력 포트 소유
  - 이번 범위에서는 포트만 선언하며 외부 상품 시스템 연동 구현 패키지는 만들지 않음

- `paymentadapter`
  - 외부 결제 시스템 연동
  - `payment.ApproveCardPort` 구현
  - 결제 제공자의 전문과 코드 체계를 업무의 요청 및 결과로 변환

- `deliveryadapter`
  - 외부 배송 시스템 연동
  - `delivery.RequestDeliveryPort` 구현
  - 업무의 배송 요청을 배송 제공자의 전문으로 변환

- `persistence`
  - 주문 영속화
  - `order.OrderRepository` 구현

상품 시스템의 판매가 조회 업무 규격은 정의하지만 `product.LoadProductPricePort`의 구현 위치와 구현 기술은 이번 범위 밖이다.

외부 상품 시스템과 그 구현 패키지는 도식에 넣지 않는다.

### 목록으로 표현한 동일 구조

- `order`
  - 주문 모델과 주문 규칙을 가진다.
  - `OrderRepository`를 소유한다.
  - `payment.ApproveCardPort`를 참조할 수 있다.
  - `delivery.RequestDeliveryPort`를 참조할 수 있다.
  - `product.LoadProductPricePort`를 참조할 수 있다.

- `payment`
  - `ApproveCardPort`를 소유한다.
  - 승인 요청과 승인·거절·확정 불가라는 업무 결과를 정의한다.
  - `paymentadapter`가 이 포트를 구현한다.

- `delivery`
  - `RequestDeliveryPort`를 소유한다.
  - `deliveryadapter`가 이 포트를 구현한다.

- `product`
  - `LoadProductPricePort`를 소유한다.
  - 이번 범위에서는 포트만 선언한다.
  - 외부 상품 시스템 연동 구현 패키지는 만들지 않는다.

- `paymentadapter`
  - `payment.ApproveCardPort`를 구현한다.
  - 외부 결제 시스템과 통신한다.
  - 제공자의 전문을 승인·거절·확정 불가라는 업무 결과로 변환한다.

- `deliveryadapter`
  - `delivery.RequestDeliveryPort`를 구현한다.
  - 외부 배송 시스템과 통신한다.
  - 업무의 배송 요청을 제공자의 전문으로 변환한다.

- `persistence`
  - `order.OrderRepository`를 구현한다.
  - 주문 저장소와 통신한다.

## 4. 의존 규칙

### 허용

- `order`는 `payment`, `delivery`, `product`를 참조할 수 있다.
- `paymentadapter`는 `payment`를 참조할 수 있다.
- `deliveryadapter`는 `delivery`를 참조할 수 있다.
- `persistence`는 `order`를 참조할 수 있다.
- `paymentadapter`는 외부 결제 시스템 라이브러리를 참조할 수 있다.
- `deliveryadapter`는 외부 배송 시스템 라이브러리를 참조할 수 있다.
- `persistence`는 데이터베이스 및 영속 기술 라이브러리를 참조할 수 있다.

허용 목록에 없는 업무 패키지 사이의 참조는 허용하지 않는다.

### 검사 가능한 금지

다음 규칙은 패키지의 import 또는 참조 관계를 정적으로 검사한다.

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- `order`, `payment`, `delivery`, `product`, `paymentadapter`, `deliveryadapter`, `persistence` 사이의 직·간접 패키지 의존 순환을 금지한다.

예를 들어 `order → payment`가 존재하면 `payment → order`뿐 아니라 `payment → X → order`와 같은 간접 순환도 금지한다.

### 검사로 판정하지 못하는 책임의 약속

- `paymentadapter`는 외부 결제 제공자의 전문을 `payment`가 정의한 승인·거절·확정 불가의 업무 의미로 변환한다.
- `paymentadapter`는 제공자의 필드 이름, 참조 값 및 코드 체계를 업무 패키지에 노출하지 않는다.
- `paymentadapter`는 주문 상태를 결정하거나 직접 변경하지 않는다.
- `deliveryadapter`는 `delivery`가 표현한 요청을 외부 배송 시스템에 전달한다.
- `deliveryadapter`는 제공자의 필드 이름, 참조 값 및 코드 체계를 업무 패키지에 노출하지 않으며 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장하고 조회하며, 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`의 포트나 이후의 구현에 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패 및 재시도 정책을 임의로 구현하지 않는다.

## 5. 외부 시스템 연동 규격

다음 규격은 업무 패키지가 외부에 보내고 외부로부터 받는 업무의 말만 정의한다. HTTP, 메시지, 동기·비동기 여부와 제공자의 전문 형식, 필드 이름, 참조 값 및 코드 체계는 확정하지 않는다.

제공자 규격과 업무 규격 사이의 변환은 해당 연동 구현의 책임이다.

### 5.1 상품 시스템: 판매가 조회

업무가 보내는 것:

```text
ProductPriceRequest
- productNumber
```

업무가 받는 것:

```text
ProductPriceResponse
- productNumber
- salePrice
```

규칙:

- `salePrice`는 원 단위의 0 이상 정수다.
- 금액 단위가 원으로 정해져 있으므로 별도의 단위 필드를 두지 않는다.
- 주문 생성 시 받은 판매가를 주문 항목의 확정 단가로 저장한다.
- 주문 생성 후에는 현재 판매가가 바뀌어도 확정 단가와 주문 금액을 변경하지 않는다.

미정 또는 이번 범위 밖:

- 같은 상품을 여러 주문 항목으로 허용할지 합칠지는 미정이다.
- 재고 판단 시점이 정해지기 전까지 재고 관련 필드를 업무 규격에 넣지 않는다.
- 외부 상품 시스템의 실제 전문과 `LoadProductPricePort` 구현은 이번 범위 밖이다.

### 5.2 결제 시스템: 카드 승인

업무가 보내는 것:

```text
CardApprovalRequest
- orderNumber
- amount
- cardApprovalData
```

업무가 받는 것:

```text
CardApprovalResult
- result: APPROVED | DECLINED | UNCONFIRMED
```

규칙:

- `amount`는 원 단위의 0 이상 정수이며 저장된 `Order.totalAmount`와 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 주문을 `PAID`로 전이시킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- `APPROVED`, `DECLINED`, `UNCONFIRMED`는 `payment`가 사용하는 업무의 결과다.
- 외부 결제 시스템의 필드, 참조 값 및 결과 코드는 `paymentadapter`가 업무 결과로 변환한다.

`UNCONFIRMED`는 새로운 주문 상태가 아니라 결제 응답을 확정할 수 없다는 결제 업무의 결과다.

미정:

- 카드 원문 정보를 주문 도메인에 저장할지는 정하지 않는다.
- 외부 참조 값의 보존 여부는 정하지 않는다.
- 중복 요청의 식별과 처리 계약은 정하지 않는다.
- `UNCONFIRMED` 이후의 처리와 재결제 허용 여부는 정하지 않는다.

### 5.3 배송 시스템: 배송 요청

업무가 보내는 것:

```text
DeliveryRequest
- orderNumber
- shippingAddress
- items
  - productNumber
  - quantity
```

업무가 받는 것:

```text
정의하지 않음
```

규칙:

- 현재 확인된 업무 사건은 승인 완료 뒤 배송 요청을 보내는 것까지다.
- `RequestDeliveryPort`는 승인 완료 처리 뒤에만 호출한다.
- 주문 생성 시 확정된 배송지를 전달한다.
- 카드 승인 거절이나 결제 응답 미확정 시에는 호출하지 않는다.
- 배송비는 범위 밖이므로 포함하지 않는다.
- 배송 제공자의 접수 결과, 참조 값 또는 코드 체계를 업무 결과로 두지 않는다.
- 외부 배송 시스템의 실제 전문이나 기술적 응답은 `deliveryadapter` 내부에서 처리한다.

미정:

- 배송 요청 실패가 주문의 `PAID` 상태에 미치는 영향은 정하지 않는다.
- 배송 요청의 재시도 기준과 담당 주체는 정하지 않는다.
- 중복 방지 키와 중복 요청 처리 방식은 정하지 않는다.
- 응답 시간 초과 처리는 정하지 않는다.

### 5.4 호출자와 주문 시스템

입력 포트나 유스케이스 인터페이스의 배치는 범위 밖이지만, 확인된 최소 업무 메시지는 다음과 같다.

업무가 받는 요청:

```text
CreateOrder
- requesterContext
- items
- shippingAddress

PayOrder
- requesterContext
- orderNumber
- cardApprovalData

GetOrderResult
- requesterContext
- orderNumber
```

업무가 보내는 결과:

```text
OrderResult
- orderNumber
- totalAmount
- status
- paymentResult: 확인 가능한 범위
```

미정:

- 인증 방식과 비회원 본인 확인 방식은 정하지 않는다.
- 거절 응답 코드와 화면 표현은 정하지 않는다.
- `paymentResult`의 보존 구조와 상세 필드는 정하지 않는다.
- 카드 결제 요청에도 본인 주문 조건을 적용할지는 정하지 않는다.

## 6. 결정이 필요한 질문

1. 상품 시스템에 재고 판단을 언제 요청해야 하는가? 가격 조회와 같은 호출인가, 별도 요청인가?
2. 승인 전에 재고 부족이 확인되면 주문 상태와 결제 요청은 어떻게 처리해야 하는가?
3. 승인 뒤 재고 부족이 확인되면 이미 완료된 승인과 `PAID` 주문을 어떻게 처리해야 하는가?
4. 결제 결과가 확정 불가일 때 결제 시스템에 결과 조회 기능이 있는가? 그 전까지 같은 주문의 재결제를 허용하는가?
5. 카드 결제 요청에도 “본인 주문만 가능” 규칙을 적용하는가?
6. 비회원 주문을 허용하는가? 허용한다면 조회와 결제 요청에서 본인을 어떻게 확인하는가?
7. 결제대기 기한이 있는가? 있다면 만료 시 상태와 행위는 무엇인가?
8. 배송 요청 실패가 `PAID` 상태에 영향을 주는가? 누가 어떤 조건으로 재요청하는가?
9. 배송 시스템은 중복 요청을 식별하거나 거절할 수 있는 계약을 제공하는가?
10. 승인 결과와 결제 시도 이력을 어느 수준까지 보존해야 하는가?
11. 주문 결과의 별도 통지가 필요한가? 필요하다면 주문 시스템과 별도 통지 시스템 중 누가 담당하는가?
12. 독립 배포가 필요한 조직 또는 운영 조건이 있는가? 예를 들어 결제 연동만 별도 팀이 소유하거나 독립적으로 출시해야 하는가?

# “주문한다” 아키텍처 결정

## 1. 아키텍처 스타일과 근거

**포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 선택한다.

- **배포:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경:** 주문 규칙과 외부 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 구현한다.

입력 포트와 유스케이스 인터페이스는 두지 않는다. 호출자가 들어오는 구조는 이번 패키지 설계 범위에서 제외한다.

## 2. 패키지와 포트 배치

```mermaid
flowchart LR
    subgraph Application["모듈러 모놀리스"]
        subgraph Order["order"]
            OrderModel["Order<br/>OrderItem<br/>OrderStatus<br/>Money·Quantity·Address"]
            OrderPort["OrderRepository"]
        end

        subgraph Payment["payment"]
            PaymentModel["카드 승인 요청<br/>승인·거절·확정 불가"]
            PaymentPort["ApproveCardPort"]
        end

        subgraph Delivery["delivery"]
            DeliveryModel["배송 요청의 업무 의미"]
            DeliveryPort["RequestDeliveryPort"]
        end

        subgraph Product["product"]
            ProductModel["Product<br/>ProductNumber<br/>salePrice"]
            ProductPort["LoadProductPricePort<br/>구현은 이번 범위 밖"]
        end

        PaymentAdapter["paymentadapter"]
        DeliveryAdapter["deliveryadapter"]
        Persistence["persistence"]
    end

    PaymentSystem["외부 결제 시스템"]
    DeliverySystem["외부 배송 시스템"]
    OrderStore["주문 저장소"]

    OrderModel --> PaymentPort
    OrderModel --> DeliveryPort
    OrderModel --> ProductPort
    OrderModel --> OrderPort

    PaymentAdapter -->|"구현"| PaymentPort
    DeliveryAdapter -->|"구현"| DeliveryPort
    Persistence -->|"구현"| OrderPort

    PaymentAdapter --> PaymentSystem
    DeliveryAdapter --> DeliverySystem
    Persistence --> OrderStore
```

화살표는 소스 코드의 의존 방향이다. 연동·영속 패키지에서 업무 포트로 향하는 화살표는 포트 구현을 뜻한다.

- `order`: 주문 모델과 규칙을 가지며 `OrderRepository`를 소유하고 `payment`, `delivery`, `product`의 출력 포트를 사용한다.
- `payment`: 승인 요청과 승인·거절·확정 불가를 정의하고 `ApproveCardPort`를 소유한다.
- `delivery`: 배송 요청을 정의하고 `RequestDeliveryPort`를 소유한다.
- `product`: 상품과 판매가를 정의하고 `LoadProductPricePort`를 소유하되, 외부 상품 시스템 구현은 이번 범위에서 만들지 않는다.
- `paymentadapter`: `ApproveCardPort`를 구현하고 결제 제공자의 전문을 업무 의미로 변환한다.
- `deliveryadapter`: `RequestDeliveryPort`를 구현하고 업무의 배송 요청을 제공자 전문으로 변환한다.
- `persistence`: `OrderRepository`를 구현하고 주문 저장소와 통신한다.

## 3. 의존 규칙

### 허용

- `order` → `payment`, `delivery`, `product`
- `paymentadapter` → `payment`, 외부 결제 라이브러리
- `deliveryadapter` → `delivery`, 외부 배송 라이브러리
- `persistence` → `order`, 데이터베이스 및 영속 기술 라이브러리

허용 목록에 없는 업무 패키지 사이의 참조는 허용하지 않는다.

### 검사 가능한 금지

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- 위 일곱 패키지 사이의 직·간접 의존 순환을 금지한다.

### 검사로 판정하지 못하는 책임의 약속

- `paymentadapter`는 제공자 전문을 승인·거절·확정 불가로 변환하며, 제공자의 필드·참조 값·코드를 업무 패키지에 노출하지 않고 주문 상태를 변경하지 않는다.
- `deliveryadapter`는 업무의 배송 요청만 전달하며, 제공자의 필드·참조 값·코드를 노출하거나 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장·조회할 뿐 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`와 이후 구현은 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 4. 외부 시스템 연동 규격

업무의 말만 정의한다. 전송 방식과 제공자의 전문·필드·참조 값·코드는 확정하지 않으며 해당 연동 구현이 변환한다.

### 상품 시스템

- **보냄:** `ProductPriceRequest(productNumber)`
- **받음:** `ProductPriceResponse(productNumber, salePrice)`
- **필수 규칙:** `salePrice`는 원 단위의 0 이상 정수이며 주문 생성 시 확정 단가가 된다.
- **미정·범위 밖:** 동일 상품 항목의 병합 여부와 재고 관련 규격은 미정이다. 외부 전문과 `LoadProductPricePort` 구현은 이번 범위 밖이다.

### 결제 시스템

- **보냄:** `CardApprovalRequest(orderNumber, amount, cardApprovalData)`
- **받음:** `CardApprovalResult(APPROVED | DECLINED | UNCONFIRMED)`
- **필수 규칙:** `amount`는 저장된 주문 총액과 같아야 한다. `APPROVED`만 `PAID` 전이를 일으키며, `DECLINED`는 `PENDING_PAYMENT`를 유지하고 `UNCONFIRMED`는 승인이나 거절로 해석하지 않는다.
- **미정:** 카드 원문과 외부 참조 값의 보존, 중복 요청 계약, `UNCONFIRMED` 이후 처리와 재결제 허용 여부는 정하지 않는다.

`UNCONFIRMED`는 주문 상태가 아니라 결제 응답을 확정할 수 없다는 업무 결과다.

### 배송 시스템

- **보냄:** `DeliveryRequest(orderNumber, shippingAddress, items[productNumber, quantity])`
- **받음:** 정의하지 않음
- **필수 규칙:** 승인 완료 뒤 확정 배송지로 요청하며, 승인 거절이나 결제 응답 미확정 때에는 요청하지 않는다.
- **미정:** 배송 실패가 `PAID`에 미치는 영향, 재시도 기준과 담당 주체, 중복 처리 방식 및 응답 시간 초과 처리는 정하지 않는다.

배송 제공자의 접수 결과·참조 값·코드는 업무 결과로 두지 않고 기술적 응답은 `deliveryadapter`에서 다룬다.

### 호출자와 주문 시스템

- **받음:** `CreateOrder(requesterContext, items, shippingAddress)`, `PayOrder(requesterContext, orderNumber, cardApprovalData)`, `GetOrderResult(requesterContext, orderNumber)`
- **보냄:** `OrderResult(orderNumber, totalAmount, status, paymentResult)`
- **미정:** 인증과 비회원 본인 확인, 거절 응답과 화면 표현, `paymentResult`의 보존 구조·상세 필드, 결제 요청에 본인 주문 조건을 적용할지는 정하지 않는다.

입력 포트와 유스케이스 인터페이스의 배치는 이번 범위 밖이다.

## 5. 결정이 필요한 질문

- **앞 실습의 미정 유지:** 회원·비회원과 본인 확인, 결제대기 기한, 결제 응답 미확정 후속 처리, 재고 판단 시점과 승인 전·후 부족 처리, 배송 실패·재시도, 승인 결과와 결제 이력 보존, 주문 결과 통지는 해결하지 않고 미정으로 유지한다.
- **이 아키텍처에서 확인할 질문:** 결제 시스템이 확정 불가 결과의 조회 기능을 제공하는가? 배송 시스템이 중복 요청을 식별하거나 거절하는 계약을 제공하는가? 결제 연동 등의 독립 배포·팀 소유·별도 출시가 필요한가?
[사용자 — 이전 MD 생성 요청]
범위를 좁혀 다시 생성해라. 이 문서에 담을 것은 셋이다 — 패키지 다이어그램(경계와 포트), 의존 규칙(허용·검사 가능한 금지·책임의 약속), 그리고 **결제 포트의 연동 규격** 하나다.

- 배송·상품 포트의 연동 규격은 빼라. 결제와 같은 방법이므로 한 번만 보이면 된다. 다만 두 포트가 존재한다는 것과 각자의 미정은 패키지 목록에서 한 줄로 밝혀라.
- 「호출자와 주문 시스템」 절도 빼라. 들어오는 쪽은 범위 밖이라고 한 줄만 남겨라.
- 「결정이 필요한 질문」은 빼라. 앞 실습의 미정을 유지한다는 것과, 이 작업에서 새로 생긴 질문만 패키지 목록이나 규격의 "정하지 않는 것"에 녹여라.
- 스타일과 근거는 배포·조직·변경 세 줄로 유지해라.

앞서 합의한 내용만 옮기고 새 분석·정책을 추가하지 마라. 패키지 다이어그램 Mermaid 원본과 검사 가능한 금지 둘은 그대로 보존해라.

# “주문한다” 아키텍처 결정

## 1. 아키텍처 스타일과 근거

**포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 선택한다.

- **배포:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경:** 주문 규칙과 외부 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 구현한다.

## 2. 패키지 다이어그램과 포트 배치

화살표는 소스 코드의 의존 방향이다. 연동·영속 패키지에서 업무 포트로 향하는 화살표는 포트 구현을 뜻한다.

- `order`: 주문 모델과 규칙을 가지며 `OrderRepository`를 소유하고 `payment`, `delivery`, `product`의 출력 포트를 사용한다.
- `payment`: 승인 요청과 승인·거절·확정 불가를 정의하고 `ApproveCardPort`를 소유한다.
- `delivery`: 배송 요청을 정의하고 `RequestDeliveryPort`를 소유한다. 배송 실패가 `PAID`에 미치는 영향, 재시도 기준과 담당 주체, 중복 처리 방식 및 응답 시간 초과 처리는 정하지 않는다.
- `product`: 상품과 판매가를 정의하고 `LoadProductPricePort`를 소유한다. 동일 상품 항목의 병합 여부와 재고 관련 규격은 정하지 않으며 외부 상품 시스템 연동 구현은 이번 범위에서 만들지 않는다.
- `paymentadapter`: `ApproveCardPort`를 구현하고 결제 제공자의 전문을 업무 의미로 변환한다.
- `deliveryadapter`: `RequestDeliveryPort`를 구현하고 업무의 배송 요청을 제공자 전문으로 변환한다.
- `persistence`: `OrderRepository`를 구현하고 주문 저장소와 통신한다.

호출자가 들어오는 쪽과 입력 포트 및 유스케이스 인터페이스의 배치는 이번 범위 밖이다.

## 3. 의존 규칙

### 허용

- `order` → `payment`, `delivery`, `product`
- `paymentadapter` → `payment`, 외부 결제 라이브러리
- `deliveryadapter` → `delivery`, 외부 배송 라이브러리
- `persistence` → `order`, 데이터베이스 및 영속 기술 라이브러리

허용 목록에 없는 업무 패키지 사이의 참조는 허용하지 않는다.

### 검사 가능한 금지

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- 위 일곱 패키지 사이의 직·간접 의존 순환을 금지한다.

### 검사로 판정하지 못하는 책임의 약속

- `paymentadapter`는 제공자 전문을 승인·거절·확정 불가로 변환하며, 제공자의 필드·참조 값·코드를 업무 패키지에 노출하지 않고 주문 상태를 변경하지 않는다.
- `deliveryadapter`는 업무의 배송 요청만 전달하며, 제공자의 필드·참조 값·코드를 노출하거나 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장·조회할 뿐 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`와 이후 구현은 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 4. 결제 포트 연동 규격

`ApproveCardPort`에는 업무의 말만 둔다. 전송 방식과 결제 제공자의 전문·필드·참조 값·코드는 확정하지 않으며 `paymentadapter`가 변환한다.

- **업무가 보냄:** `CardApprovalRequest(orderNumber, amount, cardApprovalData)`
- **업무가 받음:** `CardApprovalResult(APPROVED | DECLINED | UNCONFIRMED)`

### 필수 규칙

- `amount`는 원 단위의 0 이상 정수이며 저장된 주문 총액과 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 주문을 `PAID`로 전이시킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- `APPROVED`, `DECLINED`, `UNCONFIRMED`는 `payment`가 사용하는 업무 결과다.
- `UNCONFIRMED`는 주문 상태가 아니라 결제 응답을 확정할 수 없다는 업무 결과다.

### 정하지 않는 것

- 카드 원문 정보를 주문 도메인에 저장할지 정하지 않는다.
- 외부 참조 값의 보존 여부를 정하지 않는다.
- 중복 요청의 식별과 처리 계약을 정하지 않는다.
- `UNCONFIRMED` 이후의 처리와 재결제 허용 여부를 정하지 않는다.
- 결제 시스템이 확정 불가 결과의 조회 기능을 제공하는지 정하지 않는다.
- 결제 연동의 독립 배포·팀 소유·별도 출시 필요 여부를 정하지 않는다.

패키지 다이어그램을 고쳐서 다시 생성해라. 지금 그림은 패키지 다이어그램이라 할 수 없다.

1. **패키지가 패키지로 그려져 있지 않다.** `paymentadapter`·`deliveryadapter`·`persistence`도 패키지인데 클래스처럼 상자 하나로 그렸다. 일곱 패키지를 모두 같은 방식으로 그려라.

2. **도메인 클래스가 없다.** `order` 안에 `Order`가 없으면 이 그림이 무엇의 경계인지 알 수 없다. 패키지 다이어그램은 **도메인 모델을 중심으로** 그려야 한다. 실습 4의 정적 관점에 있는 개념을 각자의 패키지 안에 두어라 — 어느 개념이 어느 패키지에 사는지가 이 그림의 첫 번째 내용이다.

3. **`product`가 아무 관계 없이 떠 있다.** `order`가 주문 생성 시 판매가를 얻으려고 `product`의 포트를 쓴다. 업무 패키지 사이의 의존(`order` → `payment`, `delivery`, `product`)을 빠뜨리지 마라.

4. 포트는 그것을 **소유한 패키지 안에** 두고, 연동·영속 패키지가 그 포트를 구현하는 관계로 이어라.

5. 외부 시스템(결제·배송·상품 제공자)은 패키지가 아니다. 패키지 다이어그램에 상자로 넣지 말고, 연동이 외부와 통신한다는 사실은 글로 적어라.

6. 패키지마다 클래스를 모두 나열하지 말고 **그 패키지의 의미를 보이는 대표 클래스 셋 이내**로 추려라. 무엇이 어느 경계에 사는지가 드러나면 충분하다.

목록은 다이어그램과 같은 내용을 패키지마다 한 줄로 적어라. 의존 규칙과 결제 포트 연동 규격은 그대로 두고, 새 정책을 추가하지 마라.

- `deliveryadapter`는 업무의 배송 요청만 전달하며, 제공자의 필드·참조 값·코드를 노출하거나 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장·조회할 뿐 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`와 이후 구현은 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

# “주문한다” 아키텍처 결정

## 1. 아키텍처 스타일과 근거

**포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 선택한다.

- **배포:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경:** 주문 규칙과 외부 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 구현한다.

## 2. 패키지 다이어그램과 포트 배치

### 업무 경계

```mermaid
flowchart TB
    subgraph OrderPackage["package order"]
        Order["Order"]
        OrderItem["OrderItem"]
        OrderRepository["«port» OrderRepository"]

        Order --> OrderItem
        Order -.-> OrderRepository
    end

    subgraph PaymentPackage["package payment"]
        CardApprovalRequest["CardApprovalRequest"]
        CardApprovalResult["CardApprovalResult"]
        ApproveCardPort["«port» ApproveCardPort"]
    end

    subgraph DeliveryPackage["package delivery"]

    end

    end

    Order -. "order → payment" .-> ApproveCardPort
    Order -. "order → delivery" .-> RequestDeliveryPort
    Order -. "order → product" .-> LoadProductPricePort
    OrderItem --> Product
```

화살표는 소스 코드의 의존 방향이다. `OrderItem`에서 `Product`로 향하는 선은 실습 4에서 확인한 도메인 모델의 연관을 나타낸다.

### 포트의 구현

```mermaid

    RequestDeliveryPort["delivery.«port» RequestDeliveryPort"]
    LoadProductPricePort["product.«port» LoadProductPricePort"]
    OrderRepository["order.«port» OrderRepository"]

    subgraph PaymentAdapterPackage["package paymentadapter"]
        PaymentAdapter["PaymentAdapter"]
    end

    subgraph DeliveryAdapterPackage["package deliveryadapter"]
        DeliveryAdapter["DeliveryAdapter"]
    end

    end
```

연동·영속 패키지에서 업무 포트로 향하는 화살표는 포트 구현을 뜻한다. 외부 제공자와 주문 저장소는 패키지가 아니므로 패키지 경계 없이 표시한다. `LoadProductPricePort`의 외부 상품 시스템 연동 구현은 이번 범위에서 만들지 않는다.

- `order`: `Order`와 `OrderItem`을 소유하고 `OrderRepository`를 선언하며 `payment`, `delivery`, `product`의 출력 포트를 사용한다.
- `payment`: `CardApprovalRequest`, `CardApprovalResult`와 `ApproveCardPort`를 소유한다.
- `delivery`: `DeliveryRequest`와 `RequestDeliveryPort`를 소유한다. 배송 실패가 `PAID`에 미치는 영향, 재시도 기준과 담당 주체, 중복 처리 방식 및 응답 시간 초과 처리는 정하지 않는다.
- `product`: `Product`와 `LoadProductPricePort`를 소유한다. 동일 상품 항목의 병합 여부와 재고 관련 규격은 정하지 않으며 외부 상품 시스템 연동 구현은 이번 범위에서 만들지 않는다.

- `persistence`: `OrderPersistenceAdapter`가 `OrderRepository`를 구현하고 주문 저장소와 통신한다.

호출자가 들어오는 쪽과 입력 포트 및 유스케이스 인터페이스의 배치는 이번 범위 밖이다.

이 그림은 도메인 모델을 입력으로 삼아 업무 개념과 출력 포트가 어느 패키지 경계에 속하는지 보여 준다.

```mermaid
flowchart TB

        Order["Order"]
        OrderItem["OrderItem"]
        OrderStatus["OrderStatus"]
        OrderRepository["«port» OrderRepository"]

        Order --- OrderItem
    end

    subgraph PaymentPackage["package payment"]
        CardApprovalRequest["CardApprovalRequest"]
        CardApprovalResult["CardApprovalResult"]
        ApproveCardPort["«port» ApproveCardPort"]
    end

    subgraph DeliveryPackage["package delivery"]
        DeliveryRequest["DeliveryRequest"]
        RequestDeliveryPort["«port» RequestDeliveryPort"]
    end

    subgraph ProductPackage["package product"]
        Product["Product"]
        LoadProductPricePort["«port» LoadProductPricePort"]
    end

    OrderItem --- Product

    OrderPackage -. "의존" .-> PaymentPackage
    OrderPackage -. "의존" .-> DeliveryPackage
    OrderPackage -. "의존" .-> ProductPackage
```

범례:

- 화살촉 없는 실선은 실습 4에서 확인한 `Order`—`OrderItem`, `OrderItem`—`Product`의 **업무 연관**이다. Java 객체 참조, 탐색 방향 및 저장 방식은 정하지 않는다.
- 패키지 사이의 점선 화살표는 `order`에서 `payment`, `delivery`, `product`로 향하는 **설계상 코드 의존**이다.
- 특정 `Order` 객체에서 외부 포트로 향하는 호출 관계는 나타내지 않는다. 포트를 호출할 구체 객체와 그 책임은 다음 설계 활동에서 정한다.

그림에 배치한 클래스와 포트는 패키지 경계를 보여 주기 위한 대표 요소이며 도메인 모델 전체를 대체하지 않는다.

### 2.2 포트의 구현

이 그림은 업무 패키지가 소유한 포트를 어느 연동·영속 클래스가 구현하는지 보여 준다.

```mermaid
flowchart TB
    subgraph PaymentPackage["package payment"]
        ApproveCardPort["«port» ApproveCardPort"]
    end

    subgraph DeliveryPackage["package delivery"]
        RequestDeliveryPort["«port» RequestDeliveryPort"]
    end

    subgraph OrderPackage["package order"]
        OrderRepository["«port» OrderRepository"]
    end

    subgraph PaymentAdapterPackage["package paymentadapter"]
        PaymentAdapter["PaymentAdapter"]
    end

    subgraph DeliveryAdapterPackage["package deliveryadapter"]
        DeliveryAdapter["DeliveryAdapter"]
    end

    subgraph PersistencePackage["package persistence"]
        OrderPersistenceAdapter["OrderPersistenceAdapter"]
    end

    DeliveryAdapter -->|"통신"| DeliveryProvider
```

연동·영속 패키지에서 업무 포트로 향하는 점선 화살표는 포트 구현을 뜻한다. 외부 결제·배송 제공자는 시스템으로, 주문 저장소는 저장소로 구분한다.

`product.LoadProductPricePort`의 소유 경계는 첫 그림에 나타냈다. 외부 상품 시스템 연동 구현은 이번 범위 밖이므로 둘째 그림에는 넣지 않는다.

### 2.3 패키지별 배치

- `order`: `Order`, `OrderItem`, `OrderStatus`를 소유하고 `OrderRepository`를 선언하며 `payment`, `delivery`, `product`에 의존한다.
- `payment`: `CardApprovalRequest`, `CardApprovalResult`와 `ApproveCardPort`를 소유한다.
- `delivery`: `DeliveryRequest`와 `RequestDeliveryPort`를 소유한다. 배송 실패가 `PAID`에 미치는 영향, 재시도 기준과 담당 주체, 중복 처리 방식 및 응답 시간 초과 처리는 정하지 않는다.
- `product`: `Product`와 `LoadProductPricePort`를 소유한다. 동일 상품 항목의 병합 여부와 재고 관련 규격은 정하지 않으며 외부 상품 시스템 연동 구현은 이번 범위에서 만들지 않는다.
- `paymentadapter`: `PaymentAdapter`가 `ApproveCardPort`를 구현하고 외부 결제 제공자의 전문을 업무 의미로 변환한다.
- `deliveryadapter`: `DeliveryAdapter`가 `RequestDeliveryPort`를 구현하고 업무의 배송 요청을 외부 배송 제공자의 전문으로 변환한다.
- `persistence`: `OrderPersistenceAdapter`가 `OrderRepository`를 구현하고 주문 저장소와 통신한다.

호출자가 들어오는 쪽과 입력 포트 및 유스케이스 인터페이스의 배치는 이번 범위 밖이다.

## 3. 의존 규칙

### 허용

- `order` → `payment`, `delivery`, `product`
- `paymentadapter` → `payment`, 외부 결제 라이브러리
- `deliveryadapter` → `delivery`, 외부 배송 라이브러리
- `persistence` → `order`, 데이터베이스 및 영속 기술 라이브러리

### 검사 가능한 금지

- 업무 패키지 `order`, `payment`, `delivery`, `product`에서 연동·영속 패키지 `paymentadapter`, `deliveryadapter`, `persistence`로 향하는 의존을 금지한다.
- 업무 패키지 사이에서는 허용 목록에 없는 의존을 금지한다. 따라서 순환 여부와 관계없이 `payment → delivery` 같은 의존은 금지한다.
- 위 일곱 패키지 사이의 직·간접 의존 순환을 금지한다.

### 검사로 판정하지 못하는 책임의 약속

- `paymentadapter`는 제공자 전문을 승인·거절·확정 불가로 변환하며, 제공자의 필드·참조 값·코드를 업무 패키지에 노출하지 않고 주문 상태를 변경하지 않는다.
- `deliveryadapter`는 업무의 배송 요청만 전달하며, 제공자의 필드·참조 값·코드를 노출하거나 독자적으로 배송 요청을 만들지 않는다.
- `persistence`는 주문을 저장·조회할 뿐 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`와 이후 구현은 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 4. 결제 포트 연동 규격

`ApproveCardPort`에는 업무의 말만 둔다. 전송 방식과 결제 제공자의 전문·필드·참조 값·코드는 확정하지 않으며 `paymentadapter`가 변환한다.

- **업무가 보냄:** `CardApprovalRequest(orderNumber, amount, cardApprovalData)`
- **업무가 받음:** `CardApprovalResult(APPROVED | DECLINED | UNCONFIRMED)`

### 필수 규칙

- `amount`는 원 단위의 0 이상 정수이며 저장된 주문 총액과 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 주문을 `PAID`로 전이시킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- `APPROVED`, `DECLINED`, `UNCONFIRMED`는 `payment`가 사용하는 결제 업무 결과이며 주문 상태가 아니다.
- `UNCONFIRMED`는 결제 응답을 확정할 수 없다는 업무 결과다.

### 정하지 않는 것

- 카드 원문 정보를 주문 도메인에 저장할지 정하지 않는다.
- 외부 참조 값의 보존 여부를 정하지 않는다.
- 중복 요청의 식별과 처리 계약을 정하지 않는다.
- `UNCONFIRMED` 이후의 처리와 재결제 허용 여부를 정하지 않는다.
- 결제 시스템이 확정 불가 결과의 조회 기능을 제공하는지 정하지 않는다.
- 결제 연동의 독립 배포·팀 소유·별도 출시 필요 여부를 정하지 않는다.

- `persistence`는 주문을 저장·조회할 뿐 주문 상태 전이나 주문 금액을 결정하지 않는다.
- `product`와 이후 구현은 미정인 재고 판단 시점과 부족 처리 정책을 추가하지 않는다.
- 어느 패키지도 미정인 만료, 결제 응답 미확정 후속 처리, 배송 실패·재시도 정책을 임의로 구현하지 않는다.

## 4. 결제 포트 연동 규격

`ApproveCardPort`에는 업무의 말만 둔다. 전송 방식과 결제 제공자의 전문·필드·참조 값·코드는 확정하지 않으며 `paymentadapter`가 변환한다.

- **업무가 보냄:** `CardApprovalRequest(orderNumber, amount, cardApprovalData)`
- **업무가 받음:** `CardApprovalResult(APPROVED | DECLINED | UNCONFIRMED)`

### 필수 규칙

- `amount`는 원 단위의 0 이상 정수이며 저장된 주문 총액과 같아야 한다.
- 승인 시 현재 상품 판매가를 다시 조회하지 않는다.
- `APPROVED`만 주문을 `PAID`로 전이시킨다.
- `DECLINED`는 주문을 `PENDING_PAYMENT`로 유지한다.
- `UNCONFIRMED`는 승인 또는 거절로 해석하지 않는다.
- `APPROVED`, `DECLINED`, `UNCONFIRMED`는 `payment`가 사용하는 결제 업무 결과이며 주문 상태가 아니다.
- `UNCONFIRMED`는 결제 응답을 확정할 수 없다는 업무 결과다.

### 정하지 않는 것

- 카드 원문 정보를 주문 도메인에 저장할지 정하지 않는다.
- 외부 참조 값의 보존 여부를 정하지 않는다.
- 중복 요청의 식별과 처리 계약을 정하지 않는다.
- `UNCONFIRMED` 이후의 처리와 재결제 허용 여부를 정하지 않는다.
- 결제 시스템이 확정 불가 결과의 조회 기능을 제공하는지 정하지 않는다.
- 결제 연동의 독립 배포·팀 소유·별도 출시 필요 여부를 정하지 않는다.

# “주문한다” 아키텍처 결정

## 1. 아키텍처 스타일과 근거

**포트와 어댑터 구조를 적용한 모듈러 모놀리스**를 선택한다.

- **배포:** 독립 배포 요구가 없으므로 하나의 배포 단위로 둔다.
- **조직:** 업무별 독립 팀이나 별도 출시 주기가 제시되지 않았으므로 마이크로서비스로 분리하지 않는다.
- **변경:** 주문 규칙과 외부 시스템의 변경 이유가 다르므로 업무 패키지가 출력 포트를 소유하고 연동·영속 패키지가 구현한다.

## 2. 패키지 다이어그램과 포트 배치

### 2.1 업무 경계

이 그림은 도메인 모델을 입력으로 삼아 업무 개념과 출력 포트가 어느 패키지 경계에 속하는지 보여 준다.

```mermaid

        OrderRepository["«port»<br/>OrderRepository"]

    end

    subgraph PaymentPackage["package payment"]
        direction TB
        CardApprovalRequest["CardApprovalRequest"]
        CardApprovalResult["CardApprovalResult"]

        CardApprovalRequest ~~~ CardApprovalResult ~~~ ApproveCardPort
    end

    subgraph DeliveryPackage["package delivery"]
        direction TB
        DeliveryRequest["DeliveryRequest"]
        RequestDeliveryPort["«port»<br/>RequestDeliveryPort"]
```

범례:

- 화살촉 없는 실선은 실습 4에서 확인한 `Order`—`OrderItem`, `OrderItem`—`Product`의 **업무 연관**이다. Java 객체 참조, 탐색 방향 및 저장 방식은 정하지 않는다.
- 패키지 사이의 점선 화살표는 `order`에서 `payment`, `delivery`, `product`로 향하는 **설계상 코드 의존**이다.
- 특정 `Order` 객체에서 외부 포트로 향하는 호출 관계는 나타내지 않는다. 포트를 호출할 구체 객체와 그 책임은 다음 설계 활동에서 정한다.

보이지 않는 연결(`~~~`)은 패키지 내부 요소의 세로 배치를 위한 것이며 의미 있는 업무 관계가 아니다.

그림에 배치한 클래스와 포트는 패키지 경계를 보여 주기 위한 대표 요소이며 도메인 모델 전체를 대체하지 않는다.

### 2.2 포트의 구현

이 그림은 업무 패키지가 소유한 포트를 어느 연동·영속 클래스가 구현하는지 보여 준다.

```mermaid

    subgraph PaymentPackage["package payment"]
        ApproveCardPort["«port» ApproveCardPort"]
    end

    subgraph DeliveryPackage["package delivery"]

        OrderRepository["«port» OrderRepository"]
    end

    subgraph PaymentAdapterPackage["package paymentadapter"]
        PaymentAdapter["PaymentAdapter"]
    end
```

연동·영속 패키지에서 업무 포트로 향하는 점선 화살표는 포트 구현을 뜻한다. 외부 결제·배송 제공자는 시스템으로, 주문 저장소는 저장소로 구분한다.

`product.LoadProductPricePort`의 소유 경계는 첫 그림에 나타냈다. 외부 상품 시스템 연동 구현은 이번 범위 밖이므로 둘째 그림에는 넣지 않는다.

### 2.3 패키지별 배치

- `order`: `Order`, `OrderItem`, `OrderStatus`를 소유하고 `OrderRepository`를 선언하며 `payment`, `delivery`, `product`에 의존한다.
- `payment`: `CardApprovalRequest`, `CardApprovalResult`와 `ApproveCardPort`를 소유한다.
- `delivery`: `DeliveryRequest`와 `RequestDeliveryPort`를 소유한다. 배송 실패가 `PAID`에 미치는 영향, 재시도 기준과 담당 주체, 중복 처리 방식 및 응답 시간 초과 처리는 정하지 않는다.
- `product`: `Product`와 `LoadProductPricePort`를 소유한다. 동일 상품 항목의 병합 여부와 재고 관련 규격은 정하지 않으며 외부 상품 시스템 연동 구현은 이번 범위에서 만들지 않는다.
- `paymentadapter`: `PaymentAdapter`가 `ApproveCardPort`를 구현하고 외부 결제 제공자의 전문을 업무 의미로 변환한다.
- `deliveryadapter`: `DeliveryAdapter`가 `RequestDeliveryPort`를 구현하고 업무의 배송 요청을 외부 배송 제공자의 전문으로 변환한다.
- `persistence`: `OrderPersistenceAdapter`가 `OrderRepository`를 구현하고 주문 저장소와 통신한다.

호출자가 들어오는 쪽과 입력 포트 및 유스케이스 인터페이스의 배치는 이번 범위 밖이다.

- `order` → `payment`, `delivery`, `product`
