# “주문한다” 요구사항 정의서

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인할 때까지의 요구사항과 수용 기준을 정의한다.

## 목적과 범위

- 상품 조회와 장바구니 구성은 전제다.
- 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

## 기본 용어집

- **주문(Order):** 배송지가 지정되어 생성된 거래 기록
- **주문 항목(OrderItem):** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가(salePrice):** 상품 시스템이 제공하는 상품 가격
- **주문 금액(totalAmount):** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기(PENDING_PAYMENT):** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료(PAID):** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

## 대표 수용 예

공통 전제는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울인 같은 주문이다.

### 1. 카드 승인

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이고 상태는 `결제완료`다. 승인 결과를 확인할 수 있으며 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X의 승인이 거절된 주문이 `결제대기`이고 배송 요청은 0회다.
- **사건:** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

# “주문한다” 정적 모델 초안

이 모델은 요구사항에 명시된 개념과 제약만 표현한다. 결제·배송·재고 시스템의 내부 모델, 처리 절차, 상태 전이 및 구현 방식은 포함하지 않는다.

## 1. 용어집

| 한글 용어 | 영문 이름 | 정의 |
|---|---|---|
| 주문 | `Order` | 배송지가 지정되어 생성된 거래 기록. 주문 항목, 확정된 주문 금액, 배송지, 주문번호 및 현재 주문 상태를 가진다. |
| 주문 항목 | `OrderItem` | 주문에 포함된 상품, 수량 및 주문 생성 시점에 확정된 단가를 나타낸다. |
| 상품 | `Product` | 상품 시스템이 관리하는 주문 대상 상품. 주문 모델에서는 상품번호와 상품 시스템이 제공한 판매가를 참조한다. |
| 금액 | `Money` | 판매가, 주문 단가 및 주문 금액을 표현하는 값. 통화와 반올림 규칙은 아직 정해지지 않았다. |
| 수량 | `Quantity` | 주문 항목에 포함된 상품의 개수. 허용 범위와 단위는 아직 정해지지 않았다. |
| 배송지 | `Address` | 주문 생성 시 확정되어 배송 요청에 사용되는 주소. 세부 구성은 아직 정해지지 않았다. |
| 주문번호 | `OrderNumber` | 동일 주문을 식별하는 값. 생성 규칙과 형식은 아직 정해지지 않았다. |
| 상품번호 | `ProductNumber` | 상품 시스템의 상품을 식별하는 값. 형식은 상품 시스템의 기준을 따른다. |
| 주문 상태 | `OrderStatus` | 주문의 현재 상태. 현재 확정된 값은 `PENDING_PAYMENT`와 `PAID`다. |
| 판매가 | `salePrice` | 상품 시스템이 제공하는 상품의 현재 판매가. 주문 생성 이후 변경될 수 있다. |
| 주문 단가 | `unitPrice` | 주문 생성 시점의 `salePrice`를 주문 항목에 확정한 금액. 이후 상품의 `salePrice`가 바뀌어도 변하지 않는다. |
| 주문 금액 | `totalAmount` | 모든 주문 항목의 `unitPrice × Quantity`를 합한 금액. |
| 배송지 속성 | `shippingAddress` | 주문에 확정된 배송지. 결제대기 주문에서도 변경할 수 없다. |
| 결제대기 | `PENDING_PAYMENT` | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태. |
| 결제완료 | `PAID` | 카드 승인이 완료되어 주문이 성립한 상태. |

`unitPrice`는 요구사항의 “주문 생성 시점 판매가”와 `salePrice`의 변동 가능성을 구별하기 위한 이름이다. 이 명칭 구분이 업무 용어와 맞는지는 확인이 필요하다.

## 2. 개념과 속성

### Order

- `orderNumber: OrderNumber`
- `items: OrderItem[1..*]`
- `totalAmount: Money`
- `shippingAddress: Address`
- `status: OrderStatus`
- 주문 주체: 본인 주문 여부를 판단할 수 있어야 하지만, 회원·비회원 정책과 식별 개념은 미정이다.

### OrderItem

- `productNumber: ProductNumber`
- `quantity: Quantity`
- `unitPrice: Money`
- 특정 `Product`를 가리킨다.
- `unitPrice`는 주문 생성 시점의 `Product.salePrice`로 확정된다.

### Product

- `productNumber: ProductNumber`
- `salePrice: Money`
- 상품 시스템이 관리하는 외부 개념이다.
- 상품명, 설명, 재고 등의 속성은 현재 주문 정적 모델의 확정 범위가 아니다.

### 값 개념

- `Money`: 금액 값
- `Quantity`: 수량 값
- `Address`: 배송지 값
- `OrderNumber`: 주문 식별 값
- `ProductNumber`: 상품 식별 값
- `OrderStatus`: `PENDING_PAYMENT` 또는 `PAID`

## 3. 관계

- 하나의 `Order`는 하나 이상의 `OrderItem`으로 구성된다.
- 각 `OrderItem`은 정확히 하나의 `Product`를 참조한다.
- 하나의 `Product`가 여러 주문의 `OrderItem`에서 참조될 수 있다.
- 하나의 `Order`에는 정확히 하나의 `shippingAddress`가 확정된다.
- 하나의 `Order`에는 정확히 하나의 `OrderNumber`, `totalAmount`, `OrderStatus`가 존재한다.
- `OrderItem.unitPrice`는 연결된 `Product.salePrice`의 주문 생성 시점 값이다.
- 주문 생성 이후 `Product.salePrice`와 `OrderItem.unitPrice`는 서로 독립적으로 취급된다.

## 6. 불변 조건

다음 조건은 객체가 유효한 주문을 표현하는 동안 항상 성립해야 한다.

1. 주문 항목 존재

   ```text
   Order.items의 개수 >= 1
   ```

2. 주문 금액 계산

   ```text
   Order.totalAmount
   = Σ(OrderItem.unitPrice × OrderItem.quantity)
   ```

3. 생성 시점 가격 확정

   ```text
   각 OrderItem.unitPrice
   = 해당 항목이 주문에 포함될 때의 Product.salePrice
   ```

4. 가격 변경과 주문 금액의 독립성

   ```text
   주문 생성 이후 Product.salePrice가 변경되어도
   OrderItem.unitPrice와 Order.totalAmount는 변경되지 않는다.
   ```

5. 카드 승인 요청 금액

   ```text
   카드 승인 요청 금액 = Order.totalAmount
   ```

   이는 금액의 동일성 제약이며 결제 요청 절차를 모델링한 것은 아니다.

6. 주문 항목 식별 일치

   ```text
   OrderItem.productNumber
   = 참조하는 Product.productNumber
   ```

7. 배송지 확정

   ```text
   Order.shippingAddress는 반드시 존재한다.
   ```

8. 변경 금지

   ```text
   Order.status = PENDING_PAYMENT인 기존 Order에서는
   items, 각 항목의 quantity, unitPrice, shippingAddress가 변하지 않는다.
   ```

   이는 새로운 주문 생성 여부나 변경 처리 절차를 정의하지 않는다.

9. 주문 상태 범위

   ```text
   Order.status ∈ {PENDING_PAYMENT, PAID}
   ```

10. 동일 주문 유지

   카드 승인 거절 후 재결제하더라도 주문을 식별하는 `orderNumber`, 주문 항목, `totalAmount`, `shippingAddress`는 동일하다.

11. 주문자와 수령인

   요구사항상 주문자와 수령인은 같은 사람이다. 다만 그 사람을 나타내는 개념과 속성이 정해지지 않았으므로 현재 다이어그램에는 포함하지 않는다.

12. 접근 범위

   주문은 본인 여부를 판단할 수 있는 주문 주체와 연결되어야 한다. 다만 비회원 허용 여부와 본인 확인 방식이 미정이므로 구체적인 클래스와 관계는 확정하지 않는다.

## 7. 확인이 필요한 질문

1. `OrderItem`의 확정 가격 속성명을 `unitPrice`로 사용할 것인가, 요구사항 표현을 그대로 살려 `salePrice`로 사용할 것인가? 이 초안은 상품의 현재 가격을 `Product.salePrice`, 주문 시 확정된 단가를 `OrderItem.unitPrice`로 구분했다.
2. 회원 주문만 허용하는가? 비회원도 허용한다면 주문 주체와 본인 확인 정보를 어떤 개념으로 표현해야 하는가?
3. `Money`는 통화 정보를 포함하는가? 포함한다면 주문 하나에서 단일 통화만 허용하는가?
4. `Money × Quantity` 계산에서 소수점과 반올림 규칙은 무엇인가?
5. `Quantity`는 양의 정수만 허용하는가? 상품별 구매 단위나 최대 수량이 있는가?
6. 같은 `ProductNumber`가 한 주문에 여러 `OrderItem`으로 존재할 수 있는가, 아니면 하나의 항목으로 합쳐져야 하는가?
7. `Address`에 반드시 포함해야 하는 항목은 무엇인가? 예: 수령인명, 연락처, 우편번호, 기본주소, 상세주소.
8. 주문자와 수령인이 같은 사람이라는 규칙에서, `shippingAddress`의 수령인 정보까지 주문자 정보와 동일해야 하는가?
9. `OrderNumber`의 유일성 범위와 형식은 무엇인가?
10. 카드 승인 결과와 승인 요청 금액을 주문 결과에서 확인할 수 있어야 한다. 이를 정적 모델에 보존해야 하는 별도 업무 개념으로 볼 것인가? 현재 요구사항만으로는 결제 시도·승인 결과의 속성과 다중성이 확정되지 않는다.
11. 결제 응답 미확정 상태를 `OrderStatus`에 추가해야 하는가, 아니면 주문은 `PENDING_PAYMENT`로 유지되고 별도의 결제 결과 개념에서만 표현하는가?
12. 승인 뒤 재고 부족이나 배송 요청 실패가 `OrderStatus`의 추가 값을 요구하는가? 현재 정책이 없으므로 `PENDING_PAYMENT`와 `PAID` 외 상태는 추가하지 않았다.

## 2. 개념, 속성 및 관계

### `Order`

- `orderNumber: OrderNumber`
- `totalAmount: Money`
- `shippingAddress: Address`
- `status: OrderStatus`
- 하나 이상의 `OrderItem`으로 구성된다.
- 본인 주문인지 판단할 수 있어야 한다. 다만 주문 주체의 구체적인 타입과 식별 정보는 정해지지 않았다.

### `OrderItem`

- `quantity: Quantity`
- `unitPrice: Money`
- 정확히 하나의 `Order`에 포함된다.
- 정확히 하나의 `Product`에 해당한다.

`OrderItem`에 별도의 `productNumber` 속성을 중복해서 두지 않는다. 어떤 상품의 항목인지는 `Product`와의 관계로 표현하고, 그 상품의 식별 값은 `Product.productNumber`로 표현한다.

### `Product`

- `productNumber: ProductNumber`
- `salePrice: Money`
- 하나의 상품은 여러 주문의 주문 항목에 해당할 수 있다.
- 상품명, 설명, 재고 등은 현재 주문 분석 모델의 근거가 없으므로 포함하지 않는다.

### 값 개념

- `Money`: 원 단위의 0 이상 정수
- `Quantity`: 1 이상의 정수
- `Address`: 세부 구조가 정해지지 않은 배송지 값
- `OrderNumber`: 형식이 정해지지 않은 주문 식별 값
- `ProductNumber`: 형식이 정해지지 않은 상품 식별 값
- `OrderStatus`: 현재 확인된 값은 `PENDING_PAYMENT`, `PAID`

13. `Money`는 원 단위의 0 이상 정수다.
14. `Quantity`는 1 이상의 정수다.
15. 현재 확인된 `OrderStatus` 값은 `PENDING_PAYMENT`와 `PAID`다. 가능한 상태 전체는 아직 확정되지 않았다.

이 관계들은 업무상 다중성만 나타낸다. 어느 객체가 다른 객체를 저장하거나 참조하는지, 어떤 방향으로 탐색하는지는 나타내지 않는다.

## 5. 불변 조건

### 5.1 주문 항목 존재

```text
Order에 포함된 OrderItem 수 >= 1
```

### 5.2 금액 범위

```text
Product.salePrice >= 0원
OrderItem.unitPrice >= 0원
Order.totalAmount >= 0원
```

모든 금액은 원 단위 정수다.

### 5.3 수량 범위

```text
OrderItem.quantity는 1 이상의 정수다.
```

구체적인 상한은 없다기보다, 이번 모델에서 정하지 않은 것이다.

### 5.4 주문 금액 계산

```text
Order.totalAmount
= Σ(OrderItem.unitPrice × OrderItem.quantity)
```

합산 대상은 해당 `Order`를 구성하는 모든 `OrderItem`이다.

### 5.5 주문 단가의 의미

```text
OrderItem.unitPrice
= 해당 OrderItem이 속한 Order를 생성할 때의
  해당 Product.salePrice
```

`unitPrice`는 상품의 현재 판매가가 아니라 주문 생성 시 확정된 단가다.

### 5.6 가격 확정

```text
Order 생성 후 Product.salePrice가 변경되더라도
기존 OrderItem.unitPrice와 Order.totalAmount는 변하지 않는다.
```

이는 주문에 가격 스냅숏이 확정된다는 업무 제약이다. 가격을 복사하거나 별도 테이블에 저장한다는 구현 방식을 뜻하지 않는다.

### 5.7 배송지 존재와 확정

```text
Order.shippingAddress는 반드시 존재한다.
```

```text
status = PENDING_PAYMENT인 기존 Order의
shippingAddress는 변경되지 않는다.
```

### 5.8 결제대기 주문의 내용 고정

```text
status = PENDING_PAYMENT인 기존 Order에서는
OrderItem의 구성, 각 OrderItem.quantity 및
각 OrderItem.unitPrice가 변경되지 않는다.
```

이는 상태 전이를 정의하지 않고, 해당 상태로 표현되는 주문에 적용되는 정적 제약만 나타낸다.

### 5.9 카드 승인 요청 금액

```text
카드 승인 요청 금액 = Order.totalAmount
```

이는 주문 정적 모델의 속성은 아니지만, 확정된 주문 금액과 외부 결제 요청 금액 사이의 요구사항 제약이다. 결제 서비스나 결제 이력 개념을 추가하지 않고 별도 연계 규칙으로 남긴다.

### 5.10 주문자와 수령인

요구사항상 주문자와 수령인은 같은 사람이어야 한다. 그러나 주문자, 수령인 또는 고객을 나타내는 구체적인 타입과 속성이 정해지지 않았으므로 현재 구조에는 넣지 않는다.

### 5.11 본인 주문 접근

조회 또는 변경 요청은 본인 주문에 대해서만 인정되어야 한다. 다만 본인 여부를 판정하는 데 필요한 회원·비회원 정책과 식별 모델이 정해지지 않았으므로 `Customer`, `Member`, `customerId` 같은 개념이나 속성은 추가하지 않는다.

## 6. 초안에서 수정한 판단과 근거

1. `unitPrice`의 의미를 확정했다.

   상품의 현재 가격은 `Product.salePrice`, 주문 생성 시 확정된 단가는 `OrderItem.unitPrice`로 구분한다. 이는 추가 답변과 요구사항의 가격 고정 규칙에 근거한다.

2. `Money`와 `Quantity`의 제약을 확정했다.

   `Money`는 원 단위의 0 이상 정수, `Quantity`는 1 이상의 정수로 반영했다. 통화 속성, 소수점 및 반올림 규칙은 필요하지 않으므로 질문 목록에서 제거했다.

3. `OrderItem.productNumber`를 제거했다.

   초안에서는 `OrderItem`이 `Product`와 관계를 가지면서 `productNumber`도 별도 속성으로 가져 같은 연결을 중복 표현했다. 수정안에서는 상품 식별을 `Product.productNumber`로만 표현한다. 이는 외래 키와 같은 구현 구조로 오해될 가능성도 줄인다.

4. 방향 화살표와 합성 관계를 제거했다.

   화살표는 객체의 참조 또는 탐색 방향으로 해석될 수 있고, 합성 표기는 생명주기나 소유 구현을 암시할 수 있다. 요구사항에서 확정된 것은 관계와 다중성이므로 방향 없는 일반 관계로 표현했다.

5. 값 타입 연결선을 제거했다.

   `Money`, `Quantity`, `Address` 등의 사용은 속성 선언에서 이미 드러난다. 모든 값 타입을 별도 관계선으로 연결하면 같은 내용을 중복 표현하고 핵심 관계가 흐려지므로, 도식의 선은 `Order`–`OrderItem`–`Product` 관계에만 사용했다.

6. `OrderStatus`를 완결된 열거형으로 단정하지 않았다.

   `PENDING_PAYMENT`와 `PAID`는 현재 확인된 값이지만, 결제 응답 미확정, 재고 부족 및 배송 실패 정책이 남아 있다. 따라서 두 값만 가능한 완전한 상태 목록으로 모델링하지 않았다.

7. 구체적인 주문 주체 개념을 추가하지 않았다.

   본인 주문 확인은 요구사항으로 유지했지만 `Customer`, `Member`, `customerId` 같은 구체 타입과 속성에는 근거가 없다. 정적 구조에 추측으로 추가하지 않고 미정 제약으로 남겼다.

8. 결제 이력 개념을 추가하지 않았다.

   승인 결과와 요청 금액을 확인해야 한다는 요구는 있지만 보존 구조, 결제 시도의 다중성 및 미확정 응답 정책이 결정되지 않았다. 따라서 `Payment`, `PaymentAttempt`, `Authorization` 같은 개념은 만들지 않았다.

9. 재결제에 관한 이력 제약을 핵심 불변 조건에서 제외했다.

   “같은 주문으로 재결제한다”는 요구는 유효하지만, 결제 시도 개념 없이 이전 거절부터 다음 승인까지의 이력을 정적 구조로 표현하면 근거 없는 모델이 생긴다. 같은 주문을 유지한다는 요구는 보존하되, 결제 이력의 구조는 확정하지 않는다.

## 7. 계속 미정인 사항

- `Address`의 세부 항목
- `OrderNumber`와 `ProductNumber`의 형식
- 같은 상품이 여러 주문 항목에 있을 때의 병합 여부
- 회원·비회원 허용 여부와 본인 확인 방식
- 주문자 및 수령인을 표현할 구체적인 개념
- 결제 이력과 승인 결과의 보존 구조
- 결제 응답 미확정 정책
- 결제대기 기한과 만료 정책
- 재고 판단 시점과 재고 부족 처리
- 배송 요청 실패 처리
- 현재 확인된 값 이외의 `OrderStatus`
- 주문 결과 별도 통지 여부와 담당 시스템

# “주문한다” 정적 분석 모델 검증안

단가 확정 시점은 장바구니 적재 시점이 아니라 `Order` 생성 시점이다. 따라서 `OrderItem.unitPrice`와 현재 `Product.salePrice`의 관계는 항상 성립하는 불변 조건이 아니라 생성 시점 조건이다.

## 1. 용어와 개념

| 용어 | 영문 이름 | 의미 |
|---|---|---|
| 주문 | `Order` | 배송지가 지정되어 생성된 거래 기록 |
| 주문 항목 | `OrderItem` | 주문에 포함된 상품, 수량 및 주문 생성 시 확정된 단가 |
| 상품 | `Product` | 상품 시스템이 관리하는 주문 대상 |
| 금액 | `Money` | 원 단위의 0 이상 정수 |
| 수량 | `Quantity` | 1 이상의 정수. 상한은 정하지 않음 |
| 배송지 | `Address` | 주문에 확정된 배송지 값. 세부 항목은 정하지 않음 |
| 주문번호 | `OrderNumber` | 주문 식별 값. 형식은 정하지 않음 |
| 상품번호 | `ProductNumber` | 상품 식별 값. 형식은 정하지 않음 |
| 주문 상태 | `OrderStatus` | 주문의 현재 상태를 나타내는 값 |
| 판매가 | `salePrice` | 상품의 현재 판매가 |
| 주문 단가 | `unitPrice` | 주문 생성 시점의 `salePrice`로 확정된 단가 |
| 주문 금액 | `totalAmount` | 주문에 포함된 모든 항목의 `unitPrice × quantity` 합계 |
| 배송지 속성 | `shippingAddress` | 주문 생성 시 확정된 배송지 |

현재 확인된 `OrderStatus` 값은 `PENDING_PAYMENT`와 `PAID`다. 이것이 가능한 상태 전체라는 의미는 아니다.

## 2. 개념과 속성

### `Order`

- `orderNumber: OrderNumber`
- `totalAmount: Money`
- `shippingAddress: Address`
- `status: OrderStatus`
- 하나 이상의 `OrderItem`과 관계를 맺는다.

### `OrderItem`

- `quantity: Quantity`
- `unitPrice: Money`
- 정확히 하나의 `Order`에 속한다.
- 정확히 하나의 `Product`에 해당한다.

### `Product`

- `productNumber: ProductNumber`
- `salePrice: Money`
- 0개 이상의 `OrderItem`에 해당할 수 있다.

본인 주문 확인은 필요한 요구지만 주문 주체의 구체적인 개념과 속성은 정해지지 않았으므로 모델에 추가하지 않는다.

## 3. 클래스 다이어그램

값은 속성 타입으로만 표현한다. 관계선은 업무상 관계와 개수만 나타내며 참조·탐색 방향이나 저장 방식을 뜻하지 않는다.

```mermaid
classDiagram
    class Order {
        orderNumber: OrderNumber
        totalAmount: Money
        shippingAddress: Address
        status: OrderStatus
    }

    class OrderItem {
        quantity: Quantity
        unitPrice: Money
    }

    class Product {
        productNumber: ProductNumber
        salePrice: Money
    }

    Order "1" -- "1..*" OrderItem : 주문 항목
    OrderItem "0..*" -- "1" Product : 해당 상품
```

## 4. 다이어그램을 읽는 목록

1. 하나의 `Order`에는 `OrderItem`이 1개 이상 있다.
2. 하나의 `OrderItem`은 정확히 하나의 `Order`에 속한다.
3. 하나의 `OrderItem`은 정확히 하나의 `Product`에 해당한다.
4. 하나의 `Product`는 `OrderItem` 0개 이상에 해당할 수 있다.
5. `Order`는 `orderNumber`, `totalAmount`, `shippingAddress`, `status`를 각각 하나씩 가진다.
6. `OrderItem`은 `quantity`와 `unitPrice`를 각각 하나씩 가진다.
7. `Product`는 `productNumber`와 현재 `salePrice`를 각각 하나씩 가진다.

같은 상품의 항목을 합칠지는 정하지 않았으므로, 한 주문 안에서 같은 `Product`에 해당하는 `OrderItem`이 여러 개 존재하는 것을 금지하지 않는다.

## 5. 조건의 구분

### 5.1 항상 성립하는 불변 조건

유효한 주문을 어느 시점에 보더라도 성립해야 한다.

```text
Order에 속한 OrderItem 수 >= 1
```

```text
Order.totalAmount
= Σ(OrderItem.unitPrice × OrderItem.quantity)
```

```text
Money 값은 원 단위의 0 이상 정수다.
```

따라서 다음 값은 모두 0 이상 정수다.

```text
Product.salePrice
OrderItem.unitPrice
Order.totalAmount
```

```text
OrderItem.quantity는 1 이상의 정수다.
```

```text
Order.shippingAddress는 존재한다.
```

### 5.2 주문 생성 시점에 성립하는 조건

`unitPrice`는 주문 생성 순간의 판매가와 같아야 한다.

```text
OrderItem.unitPrice
= 해당 Order를 생성하는 시점의 해당 Product.salePrice
```

이는 생성 이후에도 `unitPrice = 현재 salePrice`가 계속 성립해야 한다는 뜻이 아니다.

주문을 생성할 때 금액도 다음과 같이 확정된다.

```text
생성된 Order.totalAmount
= Σ(생성된 각 OrderItem.unitPrice × quantity)
```

### 5.3 생성 전후 또는 변경 전후를 비교하는 조건

주문 생성 이후 상품의 현재 판매가가 바뀌어도 기존 주문의 확정 가격은 바뀌지 않는다.

```text
Product.salePrice(before) ≠ Product.salePrice(after)일 수 있다.

기존 OrderItem.unitPrice(before)
= 기존 OrderItem.unitPrice(after)

기존 Order.totalAmount(before)
= 기존 Order.totalAmount(after)
```

`PENDING_PAYMENT`인 기존 주문에서는 주문 내용과 배송지도 변경되지 않는다.

```text
OrderItem 구성(before) = OrderItem 구성(after)
각 OrderItem.quantity(before) = quantity(after)
각 OrderItem.unitPrice(before) = unitPrice(after)
shippingAddress(before) = shippingAddress(after)
```

이 조건은 상태가 어떻게 바뀌는지 또는 외부 시스템을 어떤 순서로 호출하는지를 정의하지 않는다.

## 6. 대표 주문에 대입한 확인

대표 주문은 다음과 같다.

```text
상품: 펜
quantity = 2
주문 생성 시 Product.salePrice = 1,000원
shippingAddress = 서울
```

### 관계의 개수

- `Order` 수: 1
- 해당 `Order`의 `OrderItem` 수: 1
- 해당 `OrderItem`의 `Product` 수: 1

따라서 다음 다중성을 만족한다.

```text
Order당 OrderItem 수 = 1 >= 1
OrderItem당 Order 수 = 1
OrderItem당 Product 수 = 1
```

### 값의 범위

```text
salePrice = 1,000원 >= 0
unitPrice = 1,000원 >= 0
quantity = 2 >= 1
totalAmount = 2,000원 >= 0
```

모든 금액은 원 단위 정수이고 수량도 정수이므로 범위 조건을 만족한다.

### 생성 시점 조건

```text
unitPrice
= 주문 생성 시 salePrice
= 1,000원
```

```text
totalAmount
= unitPrice × quantity
= 1,000원 × 2
= 2,000원
```

`shippingAddress`는 서울로 존재하므로 배송지 존재 조건도 만족한다.

### 판매가 변경 전후 비교

상품의 현재 판매가가 이후 1,200원이 된 경우:

| 값 | 주문 생성 직후 | 판매가 변경 후 |
|---|---:|---:|
| `Product.salePrice` | 1,000원 | 1,200원 |
| 기존 `OrderItem.unitPrice` | 1,000원 | 1,000원 |
| 기존 `OrderItem.quantity` | 2 | 2 |
| 기존 `Order.totalAmount` | 2,000원 | 2,000원 |
| 기존 `Order.shippingAddress` | 서울 | 서울 |

변경 후에는 다음 등식이 성립할 필요가 없다.

```text
기존 OrderItem.unitPrice = 현재 Product.salePrice
1,000원 ≠ 1,200원
```

반면 주문 자체의 합계 등식은 계속 성립한다.

```text
기존 Order.totalAmount
= 기존 OrderItem.unitPrice × quantity
= 1,000원 × 2
= 2,000원
```

## 7. 수정한 판단과 근거

- `unitPrice = salePrice`를 일반 불변 조건에서 생성 시점 조건으로 옮겼다. 두 값은 주문 생성 순간에만 같으며 이후 판매가 변경을 허용하기 때문이다.
- 합계 등식은 항상 성립하는 불변 조건으로 유지했다. `totalAmount`는 현재 판매가가 아니라 확정된 `unitPrice`로 계산되기 때문이다.
- 가격 고정과 `PENDING_PAYMENT` 주문의 변경 금지는 전후 값을 비교하는 조건으로 분리했다. 한 시점의 값 범위만으로는 “변경되지 않는다”를 표현할 수 없기 때문이다.
- 다이어그램에서는 `Order`, `OrderItem`, `Product`만 개념으로 표현했다. `Money`, `Quantity`, `Address` 등은 속성 타입과 제약 목록으로 충분하다.
- 결제 이력, 회원·비회원, 주소 구조, 식별자 형식, 중복 항목 병합 및 수량 상한은 합의대로 확정하지 않았다.
- 카드 승인, 재고 판단, 배송 요청의 절차와 상태 전이는 정적 모델에 포함하지 않았다.

# “주문한다” 정적 업무 모델

## 1. 용어와 속성

| 개념 | 속성 | 업무 의미 |
|---|---|---|
| 주문 `Order` | `orderNumber: OrderNumber` | 주문을 식별하는 값 |
|  | `totalAmount: Money` | 주문 항목별 확정 단가와 수량으로 계산한 주문 금액 |
|  | `shippingAddress: Address` | 주문 생성 시 확정된 배송지 |
|  | `status: OrderStatus` | 주문의 현재 상태를 나타내는 값 |
| 주문 항목 `OrderItem` | `quantity: Quantity` | 주문한 상품의 수량 |
|  | `unitPrice: Money` | 주문 생성 시점의 `salePrice`로 확정된 단가 |
| 상품 `Product` | `productNumber: ProductNumber` | 상품을 식별하는 값 |
|  | `salePrice: Money` | 상품의 현재 판매가 |

값의 의미는 다음과 같다.

- `Money`: 원 단위의 0 이상 정수
- `Quantity`: 1 이상의 정수
- `Address`: 주문에 확정된 배송지 값
- `OrderNumber`: 주문 식별 값
- `ProductNumber`: 상품 식별 값
- `OrderStatus`: 주문의 현재 상태 값. 현재 확인된 값은 `PENDING_PAYMENT`와 `PAID`이며, 가능한 상태 전체가 확정된 것은 아니다.

## 2. 세 개념의 클래스 도식과 관계 목록

관계선은 업무상 관계와 개수만 나타낸다. 참조 방향, 저장 방식 또는 생명주기 구현을 뜻하지 않는다.

```mermaid
classDiagram
    class Order {
        orderNumber: OrderNumber
        totalAmount: Money
        shippingAddress: Address
        status: OrderStatus
    }

    class OrderItem {
        quantity: Quantity
        unitPrice: Money
    }

    class Product {
        productNumber: ProductNumber
        salePrice: Money
    }

    Order "1" -- "1..*" OrderItem : 주문 항목
    OrderItem "0..*" -- "1" Product : 해당 상품
```

관계와 속성을 목록으로 읽으면 다음과 같다.

1. 하나의 `Order`에는 `OrderItem`이 1개 이상 있다.
2. 하나의 `OrderItem`은 정확히 하나의 `Order`에 속한다.
3. 하나의 `OrderItem`은 정확히 하나의 `Product`에 해당한다.
4. 하나의 `Product`는 0개 이상의 `OrderItem`과 관계를 맺을 수 있다.
5. `Order`는 `orderNumber`, `totalAmount`, `shippingAddress`, `status`를 각각 하나씩 가진다.
6. `OrderItem`은 `quantity`, `unitPrice`를 각각 하나씩 가진다.
7. `Product`는 `productNumber`, `salePrice`를 각각 하나씩 가진다.

같은 주문에서 동일 상품에 해당하는 주문 항목을 병합할지, 중복 항목을 허용할지는 정하지 않았다.

## 3. 조건과 대표 예

### 값 조건

```text
Product.salePrice, OrderItem.unitPrice, Order.totalAmount는
원 단위의 0 이상 정수다.

OrderItem.quantity는 1 이상의 정수다.

Order.shippingAddress는 존재한다.

Order에 속한 OrderItem 수는 1개 이상이다.
```

### 항상 성립하는 계산 조건

유효한 주문에서는 현재 `Product.salePrice`가 아니라 확정된 `OrderItem.unitPrice`를 사용하여 합계를 계산한다.

```text
Order.totalAmount
= Σ(OrderItem.unitPrice × OrderItem.quantity)
```

### 주문 생성 시점 조건

각 주문 항목의 단가는 장바구니에 상품을 넣은 시점이 아니라 주문을 생성하는 시점에 확정된다.

```text
OrderItem.unitPrice
= 해당 Order 생성 시점의 해당 Product.salePrice
```

```text
Order.totalAmount
= 생성된 모든 OrderItem의
  Σ(unitPrice × quantity)
```

`shippingAddress`도 주문 생성 시점에 확정된다.

### 생성 이후 변경 전후 조건

상품의 현재 판매가가 변경되더라도 기존 주문의 확정 단가와 주문 금액은 변하지 않는다.

```text
Product.salePrice(before)와 Product.salePrice(after)는 다를 수 있다.

기존 OrderItem.unitPrice(before)
= 기존 OrderItem.unitPrice(after)

기존 Order.totalAmount(before)
= 기존 Order.totalAmount(after)
```

`PENDING_PAYMENT`인 기존 주문에서는 다음 내용이 변경되지 않는다.

```text
OrderItem 구성(before) = OrderItem 구성(after)

각 OrderItem.quantity(before)
= 각 OrderItem.quantity(after)

각 OrderItem.unitPrice(before)
= 각 OrderItem.unitPrice(after)

shippingAddress(before)
= shippingAddress(after)
```

### 대표 주문 확인

```text
상품: 펜
OrderItem 수: 1
quantity: 2
주문 생성 시 salePrice: 1,000원
unitPrice: 1,000원
totalAmount: 2,000원
shippingAddress: 서울
```

관계와 값 조건을 만족한다.

```text
Order당 OrderItem 수 = 1 >= 1
OrderItem당 Order 수 = 1
OrderItem당 Product 수 = 1

salePrice = 1,000원 >= 0
unitPrice = 1,000원 >= 0
quantity = 2 >= 1
totalAmount = 2,000원 >= 0
```

생성 시점 조건과 합계 등식도 성립한다.

```text
unitPrice
= 주문 생성 시 salePrice
= 1,000원

totalAmount
= unitPrice × quantity
= 1,000원 × 2
= 2,000원
```

이후 현재 판매가가 1,200원으로 변경된 경우:

| 값 | 주문 생성 직후 | 판매가 변경 후 |
|---|---:|---:|
| `Product.salePrice` | 1,000원 | 1,200원 |
| 기존 `OrderItem.unitPrice` | 1,000원 | 1,000원 |
| 기존 `OrderItem.quantity` | 2 | 2 |
| 기존 `Order.totalAmount` | 2,000원 | 2,000원 |
| 기존 `Order.shippingAddress` | 서울 | 서울 |

변경 후 기존 `unitPrice`가 현재 `salePrice`와 같을 필요는 없지만, 주문의 합계 등식은 계속 성립한다.

```text
기존 unitPrice 1,000원 ≠ 현재 salePrice 1,200원

기존 totalAmount
= 기존 unitPrice × quantity
= 1,000원 × 2
= 2,000원
```

## 4. 이번에 정하지 않은 항목과 기존 업무 미정

### 정적 모델에서 구체화하지 않은 항목

- 회원 주문과 비회원 주문의 허용 범위
- 주문 주체와 본인 확인을 표현할 구체 타입 및 식별 정보
- 결제 이력과 승인 결과의 보존 구조
- `OrderNumber`와 `ProductNumber`의 형식 및 생성 규칙
- `Address`의 세부 항목
- 동일 상품 주문 항목의 병합 여부와 중복 허용 여부
- `Quantity`의 구체적인 상한
- 현재 확인된 값 이외의 `OrderStatus`

본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정하고 다른 고객의 주문 요청은 거절해야 한다. 다만 이를 표현할 `Customer`, `Member`, 식별자 등의 구체 개념은 확정하지 않는다.

### 기존 업무 미정

- 결제대기 기한과 만료 정책
- 결제 응답을 확정할 수 없을 때의 처리와 재결제 허용 여부
- 재고 판단 시점
- 승인 전 재고 부족 처리
- 카드 승인 뒤 재고 부족 처리
- 배송 요청 실패 처리와 재요청 기준
- 주문 결과의 별도 통지 여부와 담당 시스템

이 미정 사항으로부터 새로운 개념, 정책 또는 상태를 도출하지 않는다.
