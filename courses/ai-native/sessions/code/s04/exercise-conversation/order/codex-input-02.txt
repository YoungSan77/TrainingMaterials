# “주문한다” 요구사항 정의서

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인할 때까지의 요구사항과 수용 기준을 정의한다.

## 목적과 범위

- 상품 조회와 장바구니 구성은 전제다.
- 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

## 기본 용어집

- **주문(Order):** 배송지가 지정되어 생성된 거래 기록
- **주문 항목(OrderItem):** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가(salePrice):** 상품 시스템이 제공하는 상품 가격
- **주문 금액(totalAmount):** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기(PENDING_PAYMENT):** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료(PAID):** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

## 대표 수용 예

공통 전제는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울인 같은 주문이다.

### 1. 카드 승인

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이고 상태는 `결제완료`다. 승인 결과를 확인할 수 있으며 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X의 승인이 거절된 주문이 `결제대기`이고 배송 요청은 0회다.
- **사건:** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

# “주문한다” 정적 모델 초안

이 모델은 요구사항에 명시된 개념과 제약만 표현한다. 결제·배송·재고 시스템의 내부 모델, 처리 절차, 상태 전이 및 구현 방식은 포함하지 않는다.

## 1. 용어집

| 한글 용어 | 영문 이름 | 정의 |
|---|---|---|
| 주문 | `Order` | 배송지가 지정되어 생성된 거래 기록. 주문 항목, 확정된 주문 금액, 배송지, 주문번호 및 현재 주문 상태를 가진다. |
| 주문 항목 | `OrderItem` | 주문에 포함된 상품, 수량 및 주문 생성 시점에 확정된 단가를 나타낸다. |
| 상품 | `Product` | 상품 시스템이 관리하는 주문 대상 상품. 주문 모델에서는 상품번호와 상품 시스템이 제공한 판매가를 참조한다. |
| 금액 | `Money` | 판매가, 주문 단가 및 주문 금액을 표현하는 값. 통화와 반올림 규칙은 아직 정해지지 않았다. |
| 수량 | `Quantity` | 주문 항목에 포함된 상품의 개수. 허용 범위와 단위는 아직 정해지지 않았다. |
| 배송지 | `Address` | 주문 생성 시 확정되어 배송 요청에 사용되는 주소. 세부 구성은 아직 정해지지 않았다. |
| 주문번호 | `OrderNumber` | 동일 주문을 식별하는 값. 생성 규칙과 형식은 아직 정해지지 않았다. |
| 상품번호 | `ProductNumber` | 상품 시스템의 상품을 식별하는 값. 형식은 상품 시스템의 기준을 따른다. |
| 주문 상태 | `OrderStatus` | 주문의 현재 상태. 현재 확정된 값은 `PENDING_PAYMENT`와 `PAID`다. |
| 판매가 | `salePrice` | 상품 시스템이 제공하는 상품의 현재 판매가. 주문 생성 이후 변경될 수 있다. |
| 주문 단가 | `unitPrice` | 주문 생성 시점의 `salePrice`를 주문 항목에 확정한 금액. 이후 상품의 `salePrice`가 바뀌어도 변하지 않는다. |
| 주문 금액 | `totalAmount` | 모든 주문 항목의 `unitPrice × Quantity`를 합한 금액. |
| 배송지 속성 | `shippingAddress` | 주문에 확정된 배송지. 결제대기 주문에서도 변경할 수 없다. |
| 결제대기 | `PENDING_PAYMENT` | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태. |
| 결제완료 | `PAID` | 카드 승인이 완료되어 주문이 성립한 상태. |

`unitPrice`는 요구사항의 “주문 생성 시점 판매가”와 `salePrice`의 변동 가능성을 구별하기 위한 이름이다. 이 명칭 구분이 업무 용어와 맞는지는 확인이 필요하다.

## 2. 개념과 속성

### Order

- `orderNumber: OrderNumber`
- `items: OrderItem[1..*]`
- `totalAmount: Money`
- `shippingAddress: Address`
- `status: OrderStatus`
- 주문 주체: 본인 주문 여부를 판단할 수 있어야 하지만, 회원·비회원 정책과 식별 개념은 미정이다.

### OrderItem

- `productNumber: ProductNumber`
- `quantity: Quantity`
- `unitPrice: Money`
- 특정 `Product`를 가리킨다.
- `unitPrice`는 주문 생성 시점의 `Product.salePrice`로 확정된다.

### Product

- `productNumber: ProductNumber`
- `salePrice: Money`
- 상품 시스템이 관리하는 외부 개념이다.
- 상품명, 설명, 재고 등의 속성은 현재 주문 정적 모델의 확정 범위가 아니다.

### 값 개념

- `Money`: 금액 값
- `Quantity`: 수량 값
- `Address`: 배송지 값
- `OrderNumber`: 주문 식별 값
- `ProductNumber`: 상품 식별 값
- `OrderStatus`: `PENDING_PAYMENT` 또는 `PAID`

## 3. 관계

- 하나의 `Order`는 하나 이상의 `OrderItem`으로 구성된다.
- 각 `OrderItem`은 정확히 하나의 `Product`를 참조한다.
- 하나의 `Product`가 여러 주문의 `OrderItem`에서 참조될 수 있다.
- 하나의 `Order`에는 정확히 하나의 `shippingAddress`가 확정된다.
- 하나의 `Order`에는 정확히 하나의 `OrderNumber`, `totalAmount`, `OrderStatus`가 존재한다.
- `OrderItem.unitPrice`는 연결된 `Product.salePrice`의 주문 생성 시점 값이다.
- 주문 생성 이후 `Product.salePrice`와 `OrderItem.unitPrice`는 서로 독립적으로 취급된다.

## 5. 다이어그램과 같은 내용을 읽을 수 있는 목록

1. `Order`는 `OrderNumber` 형식의 `orderNumber`를 하나 가진다.
2. `Order`는 하나 이상의 `OrderItem`을 소유한다.
3. `Order`는 `Money` 형식의 `totalAmount`를 하나 가진다.
4. `Order`는 `Address` 형식의 `shippingAddress`를 하나 가진다.
5. `Order`는 `OrderStatus` 형식의 `status`를 하나 가진다.
6. `OrderItem`은 `ProductNumber` 형식의 `productNumber`를 하나 가진다.
7. `OrderItem`은 `Quantity` 형식의 `quantity`를 하나 가진다.
8. `OrderItem`은 `Money` 형식의 `unitPrice`를 하나 가진다.
9. 각 `OrderItem`은 하나의 `Product`를 참조한다.
10. 하나의 `Product`는 여러 `OrderItem`에서 참조될 수 있다.
11. `Product`는 `ProductNumber` 형식의 `productNumber`를 하나 가진다.
12. `Product`는 `Money` 형식의 `salePrice`를 하나 가진다.
13. `OrderStatus`의 현재 확정된 값은 `PENDING_PAYMENT`와 `PAID`다.

## 6. 불변 조건

다음 조건은 객체가 유효한 주문을 표현하는 동안 항상 성립해야 한다.

1. 주문 항목 존재

   ```text
   Order.items의 개수 >= 1
   ```

2. 주문 금액 계산

   ```text
   Order.totalAmount
   = Σ(OrderItem.unitPrice × OrderItem.quantity)
   ```

3. 생성 시점 가격 확정

   ```text
   각 OrderItem.unitPrice
   = 해당 항목이 주문에 포함될 때의 Product.salePrice
   ```

4. 가격 변경과 주문 금액의 독립성

   ```text
   주문 생성 이후 Product.salePrice가 변경되어도
   OrderItem.unitPrice와 Order.totalAmount는 변경되지 않는다.
   ```

5. 카드 승인 요청 금액

   ```text
   카드 승인 요청 금액 = Order.totalAmount
   ```

   이는 금액의 동일성 제약이며 결제 요청 절차를 모델링한 것은 아니다.

6. 주문 항목 식별 일치

   ```text
   OrderItem.productNumber
   = 참조하는 Product.productNumber
   ```

7. 배송지 확정

   ```text
   Order.shippingAddress는 반드시 존재한다.
   ```

8. 변경 금지

   ```text
   Order.status = PENDING_PAYMENT인 기존 Order에서는
   items, 각 항목의 quantity, unitPrice, shippingAddress가 변하지 않는다.
   ```

   이는 새로운 주문 생성 여부나 변경 처리 절차를 정의하지 않는다.

9. 주문 상태 범위

   ```text
   Order.status ∈ {PENDING_PAYMENT, PAID}
   ```

10. 동일 주문 유지

   카드 승인 거절 후 재결제하더라도 주문을 식별하는 `orderNumber`, 주문 항목, `totalAmount`, `shippingAddress`는 동일하다.

11. 주문자와 수령인

   요구사항상 주문자와 수령인은 같은 사람이다. 다만 그 사람을 나타내는 개념과 속성이 정해지지 않았으므로 현재 다이어그램에는 포함하지 않는다.

12. 접근 범위

   주문은 본인 여부를 판단할 수 있는 주문 주체와 연결되어야 한다. 다만 비회원 허용 여부와 본인 확인 방식이 미정이므로 구체적인 클래스와 관계는 확정하지 않는다.

## 7. 확인이 필요한 질문

1. `OrderItem`의 확정 가격 속성명을 `unitPrice`로 사용할 것인가, 요구사항 표현을 그대로 살려 `salePrice`로 사용할 것인가? 이 초안은 상품의 현재 가격을 `Product.salePrice`, 주문 시 확정된 단가를 `OrderItem.unitPrice`로 구분했다.
2. 회원 주문만 허용하는가? 비회원도 허용한다면 주문 주체와 본인 확인 정보를 어떤 개념으로 표현해야 하는가?
3. `Money`는 통화 정보를 포함하는가? 포함한다면 주문 하나에서 단일 통화만 허용하는가?
4. `Money × Quantity` 계산에서 소수점과 반올림 규칙은 무엇인가?
5. `Quantity`는 양의 정수만 허용하는가? 상품별 구매 단위나 최대 수량이 있는가?
6. 같은 `ProductNumber`가 한 주문에 여러 `OrderItem`으로 존재할 수 있는가, 아니면 하나의 항목으로 합쳐져야 하는가?
7. `Address`에 반드시 포함해야 하는 항목은 무엇인가? 예: 수령인명, 연락처, 우편번호, 기본주소, 상세주소.
8. 주문자와 수령인이 같은 사람이라는 규칙에서, `shippingAddress`의 수령인 정보까지 주문자 정보와 동일해야 하는가?
9. `OrderNumber`의 유일성 범위와 형식은 무엇인가?
10. 카드 승인 결과와 승인 요청 금액을 주문 결과에서 확인할 수 있어야 한다. 이를 정적 모델에 보존해야 하는 별도 업무 개념으로 볼 것인가? 현재 요구사항만으로는 결제 시도·승인 결과의 속성과 다중성이 확정되지 않는다.
11. 결제 응답 미확정 상태를 `OrderStatus`에 추가해야 하는가, 아니면 주문은 `PENDING_PAYMENT`로 유지되고 별도의 결제 결과 개념에서만 표현하는가?
12. 승인 뒤 재고 부족이나 배송 요청 실패가 `OrderStatus`의 추가 값을 요구하는가? 현재 정책이 없으므로 `PENDING_PAYMENT`와 `PAID` 외 상태는 추가하지 않았다.

- 상품의 현재 판매가는 salePrice, 주문 생성 시 확정한 단가는 unitPrice로 합의한다. 요구사항 정의서의 "주문 생성 시점 판매가"가 단가의 뜻이다.
- 이 실습의 금액은 원 단위 정수이고 0 이상이다. 수량은 1 이상의 정수이고 생성되는 주문에는 항목이 1개 이상 있어야 한다. 구체적인 상한은 정하지 않는다.
- Address는 배송지 값으로 두고 세부 항목·식별자 형식·중복 상품 항목 병합 규칙은 이번에 정하지 않는다. 본인 주문 확인은 필요한 요구로 유지하되 회원/비회원 여부나 Customer·Member 같은 구체 타입을 확정하지 않는다.
- 결제 이력의 보존 구조와 결제 응답 미확정·승인 뒤 재고 부족·배송 요청 실패 정책은 원래 미정으로 유지한다. 상태 전이는 뒤 실습의 대상이며 현재 상태 목록이 시스템의 가능한 상태 전부라고 단정하지 마라.
