아래 답과 수정 요청을 반영해라. 아키텍처 선택과 필요한 패키지의 책임·의존 방향을 정하고, 패키지 다이어그램을 대화창에 보여줘라. 화살표가 호출 순서인지 코드 의존인지 명확히 하고 불필요한 분리는 피하라.

[앞선 질문에 대한 답과 수정 요청]
- 배치: 기존 쇼핑몰과 한 배포 단위인 정기배송 모듈로 시작한다. 별도 서비스나 새 인프라는 도입하지 않는다. 업무 흐름·규칙과 외부 연계·저장 구현의 경계를 보여주되 필요 이상으로 패키지를 쪼개지 마라.
- 결제 경로: 기존 쇼핑몰의 결제 기능을 거친다. 멱등 키 지원 여부는 확인되지 않았다. 업무에서 필요한 연계 계약은 정하되 제공자의 지원을 가정하지 마라. 타임아웃 값은 정하지 않는다 — 확정할 수 없는 응답은 미확정으로 다룬다.
- 결과 확정 방식: 콜백·폴링·재시도 주기와 운영 복구는 이번 범위 밖이다. 결과 확인을 받을 자리만 두고 그 처리를 누가 언제 시작할지는 미결로 남겨라.
- 신청 식별자: 서버가 발급하고 같은 신청 의사의 재전송에는 같은 식별자를 쓴다. 첫 결제와 계약은 신청 식별자에 연결한다. 키 전달 방식·DB 제약 구현과 신청준비의 유효기간은 지금 정하지 않는다.
- 금액 산정 시점: 고지할 때 한 번 산정하고 그 금액을 계약 기간 동안 유지한다. 재고지 정책을 새로 만들지 마라.
- 첫 회차와 일반 주문의 관계: 이번 범위에서는 정기배송 안에서만 기록한다. 기존 주문 기능에 태울지는 정하지 않고 미결로 남겨라.
- 저장 범위: 신청·고지한 조건·예정 회차·첫 결제 결과·성립한 계약에 필요한 정보만 둔다. 회원·상품·배송지·결제수단은 식별자로 참조하고 개인정보 사본을 만들지 마라.
- 기존 쇼핑몰의 제공 범위: 실제 API 유무와 내부 구조는 제공되지 않았다. 기존 기능은 논리적 연결 대상으로만 표시하고 단일 API나 단일 컴포넌트라고 단정하지 마라.
- 앞 산출물에서 이미 정해진 것은 재질문하거나 바꾸지 마라 — 고지 확인 뒤 결제하는 순서, 고지한 조건·금액 유지, 실패 확정 뒤 별개 신규 신청, 날짜 기준·가격·할인·배송비·배송 가능 여부의 기존 정책 준용. 화면·REST API 분할은 범위 밖이다.
- 대화창 검토를 위해 패키지는 Mermaid flowchart의 노드·그룹으로 보여줘라. 화살표는 내부 코드의 의존만 표현하고 외부 호출 흐름을 섞지 마라. 구현 코드는 제외하고 책임과 의존 판단에 집중해라.
