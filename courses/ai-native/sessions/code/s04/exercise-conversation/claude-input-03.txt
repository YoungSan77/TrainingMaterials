[실습 2 요구사항 정의서]
# 정기배송 최초 신청 요구사항 정의서

## 사용자 이야기

기존 회원으로서 반복 주문의 수고를 줄이기 위해 원하는 상품을 정해진 주기로 배송받는 정기배송을 신청하고 싶다.

## 업무 규칙

1. 정기배송은 자동 갱신하지 않으며 계약기간이 끝나면 종료한다.
2. 계약기간은 3개월 또는 6개월, 배송 주기는 2주 또는 4주로 한다.
3. 첫 배송일은 신청일에 3일을 더한 날짜부터 선택할 수 있으며 해당 날짜를 포함한다. 배송 가능 여부는 기존 쇼핑몰 배송 달력을 따른다.
4. 첫 배송일을 계약 시작일로 한다.
5. 계약 종료일은 첫 배송일에 계약 개월 수를 더한 날짜로 한다. 해당 월에 같은 날짜가 없으면 그달의 말일로 하며, 종료일은 계약기간에 포함하지 않는다.
6. 첫 배송일을 첫 회차로 하고 이후 선택한 배송 주기마다 배송 예정일을 산정한다. 계약 종료일보다 이른 회차만 포함한다.
7. 상품 가격·할인·배송비는 신청 시점의 기존 쇼핑몰 정책으로 산정하며, 산정된 회차별 결제금액은 계약기간 동안 유지한다.
8. 첫 회차는 신청 시 결제하고 이후 회차는 각 배송 예정일 3일 전에 결제한다.
9. 첫 회차 결제 성공이 확인된 경우에만 신청을 완료한다. 결제 실패 시 신청은 완료되지 않으며, 결과를 확인할 수 없으면 완료로 단정하지 않고 결과 확인이 필요함을 안내한다.
10. 동일한 신청의 반복 전송으로 계약이나 첫 회차 결제가 중복되어서는 안 된다. 별개의 신규 신청은 제한하지 않는다.
11. 회원·상품·배송지·결제수단·배송 달력과 일반 주문 정책은 기존 쇼핑몰 기능 및 정책을 연계한다.

## 기능 요구사항

1. 기존 회원은 상품과 수량, 자신이 등록한 배송지와 결제수단을 선택할 수 있어야 한다.
2. 회원은 계약기간, 배송 주기와 첫 배송일을 선택할 수 있어야 한다.
3. 신청 완료 전에 다음 내용을 회원에게 고지해야 한다.

   - 선택한 상품과 수량
   - 배송지와 결제수단
   - 계약기간·계약 시작일·계약 종료일
   - 배송 주기와 첫 배송일
   - 총 배송 횟수와 회차별 예정 배송일
   - 첫 회차 결제금액
   - 계약기간 동안 유지되는 회차별 결제금액
   - 첫 회차와 이후 회차의 결제 시점
   - 자동 갱신 없이 계약기간 종료 시 종료된다는 사실

4. 신청 과정에서 첫 회차 결제를 수행하고 결제 결과에 따라 신청 결과를 안내해야 한다.
5. 동일한 신청이 반복 전송되어도 하나의 계약과 한 번의 첫 회차 결제만 처리해야 한다.

## 품질 요구사항

1. 동시 신청 100건이고 각 외부 연계가 1초 이내에 응답하는 정상 시험 조건에서, 신청 요청부터 결과 수신까지 전체 요청의 95% 이상이 3초 이내여야 한다. 이는 실습 검증 기준이며 실제 운영 보장 수치는 아니다. 이를 초과하는 부하는 기존 쇼핑몰 정책을 따른다.
2. 회원은 자신의 배송지와 결제수단만 선택하고 자신의 정기배송 신청 정보에만 접근할 수 있어야 한다. 다른 회원의 정보는 조회하거나 변경할 수 없어야 한다.
3. 운영시간·가용성·복구·기록 보존·보안·개인정보 보호는 기존 쇼핑몰 정책을 준용한다.

## 대표 수용 기준

- **일정 계산:** 첫 배송일이 2027-11-03이고 계약기간이 3개월, 배송 주기가 2주이면 계약 종료일은 2028-02-03이며 해당 날짜는 제외한다. 배송 예정일은 2027-11-03, 11-17, 12-01, 12-15, 12-29, 2028-01-12, 01-26의 총 7회다.
- **월말 계산:** 첫 배송일이 2027-01-31이고 계약기간이 3개월이면 계약 종료일은 2027-04-30이며 해당 날짜는 제외한다. 시험 날짜는 기존 배송 달력에서 허용된 것으로 본다.
- **금액 유지:** 휴지 1묶음의 신청 시 가격이 10,000원이고 할인과 배송비가 각각 0원이면 회차별 결제금액은 10,000원이다. 이후 상품 가격이 변경되어도 계약기간 동안 같은 금액을 유지한다.
- **신청 결과:** 첫 회차 결제 성공이 확인되면 신청 완료로 안내하고, 실패하면 신청 미완료로 안내한다. 결제 결과를 확인할 수 없으면 결과 확인이 필요함을 안내한다.
- **반복 전송:** 동일한 신청을 반복 전송해도 생성되는 계약과 실행되는 첫 회차 결제는 각각 하나여야 한다.

[실습 3 도메인 모델]
# 실습 3 정기배송 최초 신청 도메인 모델

## 1. 용어와 업무 규칙

### 1.1 용어

- **정기배송 신청:** 고객이 상품 한 종류와 수량, 본인의 등록 배송지·결제수단 및 배송 조건을 선택하여 계약 체결을 요청하는 과정이다.
- **정기배송 계약:** 첫 결제 성공이 확인될 때 정기배송 신청으로부터 성립하는 계약이다.
- **배송회차:** 신청 시 계산하여 고객에게 고지하는 예정 일정이다. 실제 배송 실행이나 운영 상태를 뜻하지 않는다.
- **첫 결제:** 첫 회차 금액을 신청 시 결제하는 행위다.
- **회차 결제금액:** 신청 시 확정하여 모든 배송회차에 동일하게 적용하는 금액이다.
- **동일 신청:** 고객이 한 번의 신청 의사로 시작한 신청이 반복 전달된 경우다. 선택 내용이 같다는 사실만으로 동일 신청이 되지는 않는다.
- **별개 신규 신청:** 고객이 신청 절차를 새로 시작하고 별도로 신청 의사를 확인한 신청이다.

### 1.2 업무 규칙

- 한 신청에서는 상품 한 종류와 수량을 선택한다.
- 기존 회원·상품·등록 배송지·등록 결제수단은 기존 쇼핑몰의 개념을 참조하며 내부 구조를 새로 정의하지 않는다.
- 고객은 본인의 유효한 등록 배송지와 등록 결제수단만 선택할 수 있다.
- 선택 대상이 유효하지 않거나 본인 소유가 아니거나 첫 배송일이 허용되지 않으면 선택 내용 확인을 요청하고 `신청준비` 상태를 유지한다. 이때 첫 결제를 실행하지 않는다.
- 날짜 산정, 배송회차 계산, 월말 처리, 금액 산정·유지 및 검증값은 **실습 2 요구사항 정의서와 대표 수용 기준**을 따른다.
- 신청 완료 전 선택 내용, 계약 조건, 배송 일정과 횟수, 결제금액과 결제 시점, 금액 유지 및 자동 갱신 없음을 고지한다.
- 첫 회차는 신청 시 결제하며 배송일 기준의 결제 예정일을 갖지 않는다. 이후 회차만 실습 2에서 정한 결제 예정일을 갖는다.
- 첫 결제 성공이 확인된 경우에만 신청이 완료되고 신청당 최대 하나의 계약이 성립한다.
- 첫 결제 실패가 확정되면 신청은 미완료되고 계약은 성립하지 않는다. 다시 신청하려면 별개의 신규 신청을 시작해야 한다.
- 결제 결과를 확인할 수 없으면 실패로 취급하지 않고 `결과확인필요` 상태로 둔다. 이후 결제 시스템의 결과 확인을 통해 성공 또는 실패가 확정된다.
- 계약이 성립하면 신청 시 고지한 배송회차와 회차 결제금액이 계약 내용으로 확정된다.
- 동일 신청의 반복 전달은 추가 청구, 추가 계약, 회차 추가 또는 상태 변화를 일으키지 않는다. 결과가 확정되었으면 기존 결과를, 아직 확정되지 않았으면 결과 확인 필요를 안내한다.
- 별개의 신규 신청은 허용한다. 동일 신청을 식별하는 기술적 방식은 설계에서 결정한다.
- 결제 결과를 통지하거나 조회하는 기술적 방식과 고객 알림 수단은 설계에서 결정한다.
- 이후 배송 운영, 후속 결제 실행, 배송 불가일 조정, 계약 변경 및 해지는 이 모델의 범위에서 제외한다.

## 2. 클래스 다이어그램

신청과 계약을 서로 다른 업무 개념으로 표현한다. 상태와 결과 속성에는 타입만 표시하며 값과 전이는 상태 머신에서 정의한다.

```plantuml:class
@startuml
left to right direction
skinparam classAttributeIconSize 0

class 회원 <<기존 개념 참조>>
class 상품 <<기존 개념 참조>>
class 등록배송지 <<기존 개념 참조>>
class 등록결제수단 <<기존 개념 참조>>

class 정기배송신청 {
  신청일: 날짜
  수량: 양의정수
  계약기간: 계약기간
  배송주기: 배송주기
  첫배송일: 날짜
  종료예정일: 날짜
  회차결제금액: 금액

  결제금액: 금액
  결과: 첫결제결과
}

class 정기배송계약 {
  계약시작일: 날짜
  계약종료일: 날짜
  계약기간: 계약기간
  배송주기: 배송주기
  회차결제금액: 금액
  자동갱신여부: 불리언
}

회원 "1" <-- "0..*" 정기배송신청 : 신청자

정기배송신청 "1" *-- "1..*" 배송회차 : 계산·고지
정기배송신청 "1" *-- "0..1" 첫결제 : 신청 시 실행
정기배송신청 "1" --> "0..1" 정기배송계약 : 성공 확인 시 성립
정기배송계약 "0..1" --> "1..*" 배송회차 : 일정·금액 확정
```

`배송회차`는 신청 시점의 예정 정보를 나타내며 실제 배송 상태는 포함하지 않는다.

## 3. 시퀀스 다이어그램

최초 신청 요청부터 첫 결과 안내까지의 업무 상호작용을 표현한다.

```plantuml:sequence
@startuml
actor 고객
participant "정기배송 업무" as 정기업무
participant "기존 쇼핑몰" as 쇼핑몰
participant "결제 시스템" as 결제

고객 -> 정기업무 : 상품·수량, 배송지·결제수단,\n계약기간·배송 주기·첫 배송일 선택
정기업무 -> 쇼핑몰 : 회원·상품·배송지·결제수단의 유효성·소유 관계,\n배송 가능 여부 및 적용 금액 확인
쇼핑몰 --> 정기업무 : 확인 결과와 회차 결제금액

alt 선택 내용이 유효하지 않음
  정기업무 --> 고객 : 선택 내용 확인 요청
else 선택 내용이 유효함
  정기업무 -> 정기업무 : 계약 조건과 배송회차 산정
  정기업무 --> 고객 : 선택 내용, 계약 조건, 배송회차,\n결제금액·결제 시점 및 종료 조건 고지
  고객 -> 정기업무 : 고지 확인 및 신청 의사 확정
  정기업무 -> 결제 : 첫 회차 금액 결제

  alt 첫 결제 성공 확인
    결제 --> 정기업무 : 성공 확정
    정기업무 -> 정기업무 : 고지된 일정과 금액으로 계약 성립
    정기업무 --> 고객 : 신청 완료 및 계약 성립 안내
  else 첫 결제 실패 확정
    결제 --> 정기업무 : 실패 확정
    정기업무 --> 고객 : 신청 미완료 안내
  else 결제 결과 확인 불가
    결제 --> 정기업무 : 결과 미확정
    정기업무 --> 고객 : 결과 확인 필요 안내
  end
end
@enduml
```

결과 미확정 이후 성공 또는 실패가 확인되는 사건은 상태 머신에서 표현한다.

## 4. 상태 머신 다이어그램

상태 머신의 대상은 `정기배송신청`이다. 계약 성립 이후의 배송 진행과 계약 운영 상태는 포함하지 않는다.

```plantuml:state

신청준비 --> 신청준비 : 선택 대상 부적합 또는 첫 배송일 미허용\n/ 선택 내용 확인 요청
신청준비 --> 첫결제결과확인중 : 유효성 확인 및 고지 확인\n/ 첫 결제 실행

```

`결과확인필요`는 실패가 아니라 첫 결제 결과가 아직 확정되지 않은 상태다.

# 정기배송 최초 신청 구조 제안

## 1. 제안 방향

기존 쇼핑몰 안에 **정기배송 신청 모듈**을 별도 업무 경계로 추가한다. 회원·상품·배송지·결제수단·배송 달력·가격 정책·결제 실행은 기존 기능을 재사용하고, 정기배송 모듈은 다음 책임만 가진다.

- 신청 절차와 상태 관리
- 계약 조건 및 배송회차 계산
- 신청 완료 전 고지 내용 생성
- 첫 결제 요청과 결과 판정
- 중복 신청 및 중복 결제 방지
- 결제 성공 시 정기배송 계약 확정

초기에는 별도 서비스보다 기존 쇼핑몰 내부의 독립 모듈로 구현하는 편이 적절하다. 업무 경계와 저장소 인터페이스를 분리해 두면 향후 필요할 때 별도 서비스로 분리할 수 있다.

## 2. 전체 구조

```text
회원 화면/API
    │
    ▼
정기배송 신청 API
    │
    ▼
정기배송 신청 응용 서비스
    ├── 정기배송 도메인
    │   ├── 정기배송신청
    │   ├── 배송회차
    │   ├── 첫결제
    │   ├── 정기배송계약
    │   └── 일정 계산 정책
    │
    ├── 기존 쇼핑몰 연계
    │   ├── 회원 확인
    │   ├── 상품 확인
    │   ├── 배송지·결제수단 소유 확인
    │   ├── 배송 가능일 확인
    │   └── 가격·할인·배송비 산정
    │
    ├── 결제 시스템 연계
    │   ├── 첫 결제 요청
    │   └── 결제 결과 확인
    │
    └── 저장소
        ├── 신청 및 상태
        ├── 고지한 조건·금액·배송회차
        ├── 첫 결제 식별 정보
        └── 성립한 계약
```

## 3. 주요 책임

### 정기배송 신청 API

신청 시작, 고지 내용 조회, 신청 확정 및 결과 조회를 외부에 제공한다.

권장 API 구분은 다음과 같다.

- `신청 시작/변경`: 선택 내용을 받아 검증하고 고지안을 만든다.
- `신청 확정`: 고객의 고지 확인 후 첫 결제를 수행한다.
- `신청 결과 조회`: 완료, 미완료 또는 결과 확인 필요 상태를 반환한다.

신청 확정 요청에는 한 번의 신청 의사를 나타내는 **신청 식별자**를 포함해야 한다. 같은 요청이 재전송되면 기존 처리 결과를 반환한다.

### 정기배송 신청 응용 서비스

신청 절차 전체를 조정한다.

- 현재 로그인한 회원을 기준으로 접근 권한을 검사한다.
- 기존 쇼핑몰 기능을 호출해 선택 대상과 금액을 확인한다.
- 도메인에 계약 조건 및 배송회차 계산을 요청한다.
- 고객이 확인할 고지 내용을 저장한다.
- 고지 확인 후 첫 결제를 한 번만 요청한다.
- 결제 결과에 따라 신청 상태를 변경한다.
- 성공이 확인된 경우에만 계약을 생성한다.
- 반복 요청에는 기존 신청과 결제 결과를 반환한다.

외부 연계 호출과 상태 변경 순서를 통제하되, 날짜나 상태 전이 같은 업무 규칙 자체는 도메인 객체에 둔다.

### 정기배송신청

최초 신청 과정의 중심 객체다.

- 신청자와 선택한 기존 쇼핑몰 자원의 식별자를 보유한다.
- 계약기간, 배송 주기, 첫 배송일, 종료예정일을 관리한다.
- 신청 시 확정한 회차별 결제금액과 배송회차를 보유한다.
- `신청준비`, `첫결제결과확인중`, `결과확인필요`, `신청완료`, `신청미완료` 상태 전이를 통제한다.
- 첫 결제 성공 전에는 계약 생성을 허용하지 않는다.
- 완료된 신청이나 실패가 확정된 신청의 재처리를 막는다.

### 일정 계산 정책

날짜 계산을 다른 기능과 분리하여 명시적으로 담당한다.

- 첫 배송일을 계약 시작일로 지정한다.
- 첫 배송일에 3개월 또는 6개월을 더해 종료일을 계산한다.
- 같은 날짜가 없는 달에는 말일을 적용한다.
- 첫 배송일부터 2주 또는 4주 간격으로 회차를 생성한다.
- 계약 종료일보다 이른 배송일만 포함한다.
- 첫 회차는 `신청 시 결제`, 이후 회차는 `배송 예정일 3일 전 결제 예정`으로 표시한다.

배송 가능일 판정은 하지 않고 기존 배송 달력에 위임한다.

### 고지안

첫 결제 전에 고객이 확인한 내용을 하나의 변경 불가능한 자료로 저장한다.

- 상품과 수량
- 배송지 및 결제수단의 표시용 정보
- 계약 시작일과 종료일
- 계약기간과 배송 주기
- 전체 배송회차와 예정 배송일
- 회차별 결제금액
- 첫 회차와 이후 회차의 결제 시점
- 자동 갱신되지 않는다는 조건

신청 확정 시 화면에서 다시 계산하지 않고, 고객이 확인한 고지안과 현재 신청이 일치하는지 확인해야 한다. 선택 내용이 변경되면 기존 고지안을 폐기하고 다시 검증·산정한다.

### 첫결제

정기배송 신청과 첫 결제 시도 사이의 관계를 관리한다.

- 신청별 결제 요청 식별자를 하나만 발급한다.
- 같은 식별자로 결제 시스템의 멱등 처리를 요청한다.
- 요청 금액과 결제 시스템 거래 식별자를 기록한다.
- 성공, 실패 또는 결과 미확정을 구분한다.
- 응답 유실이나 시간 초과를 실패로 간주하지 않는다.

결제 요청 중 응답을 받지 못했다면 새 결제를 실행하지 않고 기존 거래의 결과를 조회해야 한다.

### 정기배송계약

첫 결제 성공이 확인될 때만 생성한다.

- 한 신청에서 최대 한 건만 생성한다.
- 고객에게 고지한 계약 조건, 배송회차 및 회차별 금액을 그대로 확정한다.
- 기존 상품 가격이 이후 변경되더라도 계약의 금액은 변경하지 않는다.
- 자동 갱신 여부는 항상 `false`로 확정한다.

계약 성립 이후의 배송·후속 결제·변경·해지 상태는 이번 범위에 포함하지 않는다.

## 4. 기존 기능과의 경계

| 영역 | 정기배송 모듈 책임 | 기존 쇼핑몰 책임 |
|---|---|---|
| 회원 | 신청자 식별자 보관 및 접근 통제 요청 | 회원의 존재·유효성 확인 |
| 상품 | 상품 식별자와 신청 당시 표시 정보 보관 | 판매 가능 여부와 상품 정보 제공 |
| 배송지 | 선택한 배송지 식별 및 표시 정보 보관 | 회원 소유·유효성 확인 |
| 결제수단 | 선택한 수단 식별 및 표시 정보 보관 | 회원 소유·사용 가능 여부 확인 |
| 배송 일정 | 계약 종료일과 회차 날짜 계산 | 첫 배송일의 배송 가능 여부 판정 |
| 금액 | 산정 결과를 회차별 고정 금액으로 확정 | 가격·할인·배송비 정책 적용 |
| 일반 주문 | 직접 생성하거나 변경하지 않음 | 기존 주문 정책과 주문 기능 유지 |
| 결제 | 첫 결제 절차 및 결과에 따른 상태 결정 | 실제 승인 처리와 거래 결과 제공 |

정기배송 모듈은 기존 회원·상품·배송지·결제수단 구조를 복제하지 않는다. 다만 계약 당시 무엇에 동의했는지 재현할 수 있도록 상품명, 배송지 요약, 결제수단 마스킹 정보, 금액 구성 같은 표시용 스냅샷은 보관할 수 있다.

## 5. 신청 처리 흐름

1. 고객이 상품·수량·배송지·결제수단·계약기간·배송 주기·첫 배송일을 선택한다.
2. 시스템이 신청 식별자를 발급하고 `신청준비` 상태로 저장한다.
3. 기존 쇼핑몰을 통해 회원, 상품, 소유 관계, 사용 가능 여부와 배송 가능일을 확인한다.
4. 기존 가격 정책으로 가격·할인·배송비를 산정한다.
5. 계약 종료일과 전체 배송회차를 계산한다.
6. 계산 결과와 결제 조건을 고지안으로 저장하고 고객에게 보여준다.
7. 고객이 고지를 확인하고 신청을 확정한다.
8. 시스템이 같은 신청에 첫 결제가 이미 요청되었는지 확인한다.
9. 미요청 상태인 경우에만 신청별 결제 요청 식별자로 첫 결제를 요청한다.
10. 성공이 확인되면 계약을 한 건 생성하고 `신청완료`로 변경한다.
11. 실패가 확정되면 계약 없이 `신청미완료`로 변경한다.
12. 결과를 확인할 수 없으면 계약을 만들지 않고 `결과확인필요`로 변경한다.
13. 동일 신청이 재전송되면 새 결제나 계약을 만들지 않고 저장된 결과를 반환한다.

신청, 첫 결제 기록 및 계약에 각각 고유 제약을 두는 것이 필요하다.

- 신청 식별자: 회원 범위에서 유일
- 첫 결제: 신청당 최대 한 건
- 계약: 신청당 최대 한 건
- 결제 요청 식별자: 전체 시스템에서 유일

## 6. 일관성과 성능 고려

신청 저장과 계약 생성 같은 내부 변경은 데이터베이스 트랜잭션으로 보호한다. 외부 결제 호출을 데이터베이스 트랜잭션에 장시간 포함하지는 않되, 결제 요청 식별자를 먼저 확정하여 재시도 시 같은 거래를 조회하거나 재사용할 수 있게 한다.

3초 성능 기준을 위해 기존 쇼핑몰이 허용한다면 회원·상품·배송지·결제수단 검증과 배송 가능일 확인을 하나의 조회 API로 묶는 것이 유리하다. 가격 산정도 정기배송 모듈이 여러 정책 서비스를 차례로 호출하기보다 기존 쇼핑몰의 최종 견적 기능을 한 번 호출하는 편이 좋다.

첫 결제 응답이 제한 시간 안에 확정되지 않으면 억지로 완료를 기다리지 않고 `결과확인필요`를 반환한다. 이는 실패가 아니며, 같은 신청의 재전송으로 새 결제를 실행해서는 안 된다.

## 7. 범위에서 제외할 사항

- 두 번째 회차 이후의 결제 실행
- 실제 주문 및 배송 작업 생성
- 배송 진행 상태 관리
- 신청 후 배송 불가일 조정
- 계약 변경·해지·환불
- 계약 만료 처리와 갱신
- 운영자용 관리 기능
- 고객 알림 발송 구현
- 구체적인 구현 코드와 배포 구조

## 8. 구조 확정을 위해 결정할 사항

1. **신청 식별자 발급 주체**  
   신청 화면을 시작할 때 서버가 식별자를 발급할지, 클라이언트가 생성한 멱등 키를 서버가 등록할지 결정해야 한다. 서버 발급 방식을 권장한다.

2. **고지와 신청 확정의 분리 여부**  
   고지안 생성과 첫 결제를 별도 요청으로 분리할지 결정해야 한다. 고객의 고지 확인을 명확히 남기려면 `고지안 생성 → 신청 확정`의 2단계 방식을 권장한다.

3. **고지안 유효기간**  
   가격이나 상품 상태가 바뀔 수 있으므로 고지안을 언제까지 확정할 수 있는지 정해야 한다. 유효기간이 지나면 기존 쇼핑몰 정책으로 다시 검증하고 금액을 재산정하는 방식이 필요하다.

4. **가격 확정 시점**  
   고지안을 만든 시점과 고객이 신청을 확정한 시점 중 언제의 가격을 “신청 시점 가격”으로 볼지 결정해야 한다. 첫 결제 직전인 신청 확정 시점에 유효성을 재검증하고 금액을 확정하는 방식을 권장한다.

5. **결제 시스템의 멱등성 지원 여부**  
   결제 시스템이 요청 식별자를 이용한 중복 방지와 거래 결과 조회를 지원하는지 확인해야 한다. 지원하지 않는다면 자체 결제 시도 기록과 별도의 중복 방지 연계 방식이 필요하다.

6. **결제 결과 확인 방식**  
   결과 미확정 거래를 결제사의 콜백으로 확인할지, 정기 조회할지, 두 방식을 함께 사용할지 결정해야 한다. 이번 범위에서는 인터페이스만 정의하더라도 최종 상태를 확정할 책임 주체는 정해야 한다.

7. **첫 배송일 검증 기준 시각**  
   `신청일 + 3일`의 신청일을 회원 현지 날짜, 쇼핑몰 영업 기준 날짜 또는 서버 날짜 중 무엇으로 계산할지 결정해야 한다. 날짜 변경 기준 시각과 시간대도 함께 정해야 한다.

8. **배송 달력의 반환 규칙**  
   기존 배송 달력이 선택한 날짜의 가능 여부만 반환하는지, 불가능할 때 대체 가능일도 반환하는지 확인해야 한다. 이번 최초 신청에서는 자동 대체하지 않고 고객이 다시 선택하게 하는 방식을 권장한다.

9. **가격 산정 범위**  
   정기배송 상품에 일반 주문과 동일한 쿠폰, 회원 등급 할인, 프로모션, 무료배송 조건을 적용할지 결정해야 한다. 기존 가격 산정 기능이 “계약기간 동안 고정할 최종 회차 금액”을 반환할 수 있는지도 확인해야 한다.

10. **저장할 스냅샷 범위**  
    계약 증빙과 고객 고지 재현을 위해 상품명, 옵션, 배송지 요약, 결제수단 마스킹 정보 및 가격 구성 중 무엇을 저장할지 정해야 한다. 원본 개인정보의 불필요한 복제는 피해야 한다.

11. **신청 실패 후 재시도 정책**  
    첫 결제 실패가 확정된 신청을 다시 사용할 수 없게 하고 반드시 새 신청 식별자로 시작하게 할지 확인해야 한다. 제시된 도메인 모델에 따르면 별개의 신규 신청만 허용하는 것이 맞다.

12. **모듈 배치 방식**  
    기존 쇼핑몰 코드베이스 안의 독립 모듈로 시작할지, 처음부터 별도 서비스로 구축할지 결정해야 한다. 현재 요구 범위와 3초 응답 기준만 보면 기존 쇼핑몰 내부의 독립 모듈을 권장한다.
[사용자]
아래 답과 수정 요청을 반영해라. 아키텍처 선택과 필요한 패키지의 책임·의존 방향을 정하고, 패키지 다이어그램을 대화창에 보여줘라. 화살표가 호출 순서인지 코드 의존인지 명확히 하고 불필요한 분리는 피하라.

[앞선 질문에 대한 답과 수정 요청]
- 배치: 기존 쇼핑몰과 한 배포 단위인 정기배송 모듈로 시작한다. 별도 서비스나 새 인프라는 도입하지 않는다. 업무 흐름·규칙과 외부 연계·저장 구현의 경계를 보여주되 필요 이상으로 패키지를 쪼개지 마라.
- 결제 경로: 기존 쇼핑몰의 결제 기능을 거친다. 멱등 키 지원 여부는 확인되지 않았다. 업무에서 필요한 연계 계약은 정하되 제공자의 지원을 가정하지 마라. 타임아웃 값은 정하지 않는다 — 확정할 수 없는 응답은 미확정으로 다룬다.
- 결과 확정 방식: 콜백·폴링·재시도 주기와 운영 복구는 이번 범위 밖이다. 결과 확인을 받을 자리만 두고 그 처리를 누가 언제 시작할지는 미결로 남겨라.
- 신청 식별자: 서버가 발급하고 같은 신청 의사의 재전송에는 같은 식별자를 쓴다. 첫 결제와 계약은 신청 식별자에 연결한다. 키 전달 방식·DB 제약 구현과 신청준비의 유효기간은 지금 정하지 않는다.
- 금액 산정 시점: 고지할 때 한 번 산정하고 그 금액을 계약 기간 동안 유지한다. 재고지 정책을 새로 만들지 마라.
- 첫 회차와 일반 주문의 관계: 이번 범위에서는 정기배송 안에서만 기록한다. 기존 주문 기능에 태울지는 정하지 않고 미결로 남겨라.
- 저장 범위: 신청·고지한 조건·예정 회차·첫 결제 결과·성립한 계약에 필요한 정보만 둔다. 회원·상품·배송지·결제수단은 식별자로 참조하고 개인정보 사본을 만들지 마라.
- 기존 쇼핑몰의 제공 범위: 실제 API 유무와 내부 구조는 제공되지 않았다. 기존 기능은 논리적 연결 대상으로만 표시하고 단일 API나 단일 컴포넌트라고 단정하지 마라.
- 앞 산출물에서 이미 정해진 것은 재질문하거나 바꾸지 마라 — 고지 확인 뒤 결제하는 순서, 고지한 조건·금액 유지, 실패 확정 뒤 별개 신규 신청, 날짜 기준·가격·할인·배송비·배송 가능 여부의 기존 정책 준용. 화면·REST API 분할은 범위 밖이다.
- 대화창 검토를 위해 패키지는 Mermaid flowchart의 노드·그룹으로 보여줘라. 화살표는 내부 코드의 의존만 표현하고 외부 호출 흐름을 섞지 마라. 구현 코드는 제외하고 책임과 의존 판단에 집중해라.

# 정기배송 최초 신청 아키텍처 및 패키지 구조

## 1. 아키텍처 선택

기존 쇼핑몰과 같은 배포 단위에 포함되는 **모듈러 모놀리스의 정기배송 모듈**로 구성한다.

정기배송 모듈 내부에는 다음 세 경계만 둔다.

- `application`: 최초 신청 업무 흐름과 외부 기능 사용 계약
- `domain`: 신청·계약의 업무 규칙과 상태
- `infrastructure`: 저장 및 외부 연계 계약의 구현

화면이나 기존 쇼핑몰의 요청 진입부는 정기배송 `application`을 호출한다. 기존 회원·상품·배송지·결제수단·배송 달력·가격 정책은 복제하지 않고 기존 쇼핑몰 모듈을 사용한다.

별도 서비스, 메시지 브로커, 전용 데이터베이스 같은 새로운 배포 단위나 인프라는 도입하지 않는다.

## 2. 패키지 다이어그램

아래 화살표 `A --> B`는 **A 패키지의 코드가 B 패키지의 타입이나 인터페이스를 참조하는 컴파일 시점 코드 의존**을 뜻한다. 업무 처리 순서나 런타임 외부 호출 순서를 나타내지 않는다.

```mermaid
flowchart LR
    subgraph Existing["기존 쇼핑몰"]
        Entry["기존 요청 진입부<br/>화면·컨트롤러"]
        ExistingDomain["기존 업무 패키지<br/>회원·상품·배송지·결제수단<br/>배송 달력·가격 정책"]
        ExistingInfra["기존 기반 구현<br/>결제 클라이언트·영속성 기술"]
        Bootstrap["기존 구성 패키지<br/>객체 생성·의존성 연결"]
    end

    subgraph Subscription["정기배송 모듈"]
        App["subscription.application<br/>최초 신청 업무 흐름<br/>저장·쇼핑몰·결제 연계 인터페이스"]
        Domain["subscription.domain<br/>신청·회차·첫 결제·계약<br/>일정 계산과 상태 규칙"]
        Infra["subscription.infrastructure<br/>저장소 구현<br/>기존 쇼핑몰·결제 연계 구현"]
    end

    Entry --> App
    App --> Domain
    Infra --> App
    Infra --> Domain
    Infra --> ExistingDomain
    Infra --> ExistingInfra
    Bootstrap --> App
    Bootstrap --> Infra
```

`domain`은 다른 패키지에 의존하지 않는다. `application`은 `domain`에만 의존하며, 저장과 외부 연계에 필요한 인터페이스를 직접 소유한다. `infrastructure`가 이 인터페이스들을 구현하므로 의존 방향이 업무 규칙을 향한다.

`application.port`, `domain.model`, `adapter.payment` 같은 하위 패키지는 현재 구조 결정에 필수적이지 않으므로 별도 패키지로 세분화하지 않는다. 구현 규모가 커질 때 같은 책임 안에서 정리할 수 있다.

## 3. 패키지별 책임

### `subscription.domain`

정기배송 최초 신청에 고유한 업무 개념과 불변 규칙을 담당한다.

포함할 개념은 다음과 같다.

- `정기배송신청`
- `배송회차`
- `첫결제`
- `정기배송계약`
- 계약기간과 배송 주기
- 신청 상태와 첫 결제 결과
- 계약 종료일 및 배송회차 계산 규칙

주요 책임은 다음과 같다.

- 첫 배송일을 계약 시작일로 사용한다.
- 첫 배송일에 계약 개월 수를 더해 계약 종료일을 계산한다.
- 같은 날짜가 없는 달에는 말일을 적용한다.
- 계약 종료일을 제외하고 2주 또는 4주 간격의 배송회차를 계산한다.
- 첫 회차와 이후 회차의 결제 시점을 구분한다.
- 고지한 회차별 결제금액을 계약 성립 시 그대로 확정한다.
- 신청 상태에 허용되는 전이만 수행한다.
- 첫 결제 성공이 확인된 경우에만 계약 성립을 허용한다.
- 한 신청에서 첫 결제와 계약이 각각 하나를 초과하지 않도록 업무 규칙을 표현한다.
- 실패가 확정된 신청은 다시 결제하지 않고 종료한다.
- 결과 미확정을 실패로 취급하지 않는다.

회원, 상품, 배송지, 결제수단의 내부 구조나 기존 가격·배송 정책은 이 패키지에 구현하지 않는다. 해당 결과는 식별자와 판정값 또는 산정값으로 전달받는다.

### `subscription.application`

정기배송 최초 신청의 업무 흐름을 조정한다.

주요 책임은 다음과 같다.

- 서버가 발급한 신청 식별자로 신청 절차를 시작한다.
- 로그인 회원과 신청 식별자의 관계를 확인한다.
- 기존 쇼핑몰에 선택 대상의 유효성과 소유 관계 확인을 요청한다.
- 기존 배송 달력에 첫 배송일의 배송 가능 여부 확인을 요청한다.
- 기존 가격 정책에 회차별 결제금액 산정을 요청한다.
- 도메인을 사용해 계약 조건과 배송회차를 계산한다.
- 고객에게 고지할 조건·금액·예정 회차를 저장한다.
- 고객의 고지 확인 후에만 첫 결제를 요청한다.
- 신청 식별자에 연결된 기존 첫 결제 처리 여부를 확인한다.
- 첫 결제 결과에 따라 신청 상태를 변경한다.
- 성공이 확인된 경우 고지한 내용으로 계약을 성립시킨다.
- 동일 신청 식별자의 반복 요청에는 기존 결과를 반환한다.
- 실패가 확정된 신청에는 별개의 신규 신청이 필요하다는 결과를 반환한다.
- 회원이 자신의 신청 정보에만 접근하도록 사용 사례 수준에서 통제한다.

이 패키지는 다음과 같은 **필요 기능 중심의 연계 인터페이스**를 소유한다.

| 연계 인터페이스 | 필요한 의미 |
|---|---|
| 신청 저장 | 신청, 고지한 조건, 예정 회차 및 현재 상태 저장·조회 |
| 계약 저장 | 신청 식별자에 연결된 계약 저장·조회 |
| 기존 쇼핑몰 확인 | 회원·상품·배송지·결제수단의 유효성과 소유 관계 확인 |
| 배송 가능일 확인 | 기존 배송 달력에 따른 첫 배송일 허용 여부 확인 |
| 금액 산정 | 기존 가격·할인·배송비 정책이 적용된 회차별 최종 금액 산정 |
| 첫 결제 | 신청 식별자와 첫 회차 금액으로 결제를 요청하고 성공·실패·미확정 결과 반환 |
| 결제 결과 확인 | 기존 결제 요청의 결과를 새 청구 없이 확인 |

인터페이스는 업무에 필요한 의미만 규정한다. REST, 내부 메서드 호출, 결제 제공자 API 형태 같은 기술 규격은 포함하지 않는다.

### `subscription.infrastructure`

`application`이 정의한 저장 및 외부 연계 인터페이스를 구현한다.

주요 책임은 다음과 같다.

- 신청과 신청 상태를 저장하고 조회한다.
- 고지한 계약 조건·금액·예정 회차를 저장하고 조회한다.
- 첫 결제 요청 식별 정보와 확인된 결과를 저장한다.
- 신청 식별자에 연결된 성립 계약을 저장하고 조회한다.
- 기존 쇼핑몰의 회원·상품·배송지·결제수단 기능을 호출한다.
- 기존 배송 달력과 가격 산정 기능을 호출한다.
- 기존 결제 클라이언트를 통해 첫 결제를 요청한다.
- 결제 결과 확인 기능이 정해지면 해당 규격을 연계 인터페이스에 맞게 변환한다.
- 외부 시스템의 응답을 도메인이나 응용 계층이 사용하는 성공·실패·미확정 결과로 변환한다.

이 패키지에는 업무 상태 전이, 배송회차 계산 또는 계약 성립 판단을 두지 않는다.

결제 제공자의 중복 방지와 결과 확인 규격이 아직 없으므로 특정 기능을 지원한다고 가정하지 않는다. 다만 구현은 다음 업무 의미를 충족해야 한다.

- 동일 신청 식별자의 반복 전달로 추가 청구하지 않는다.
- 결과를 알 수 없는 기존 요청을 실패로 바꾸지 않는다.
- 결과 확인 과정에서는 새 결제를 요청하지 않는다.

제공자 규격이 확정되면 이 의미를 제공자 기능만으로 보장할 수 있는지, 정기배송 저장 정보와 결합해야 하는지를 `infrastructure` 구현에서 결정한다.

## 4. 기존 쇼핑몰과의 경계

| 관심사 | 정기배송 모듈 | 기존 쇼핑몰 |
|---|---|---|
| 회원 | 신청자 식별과 자신의 신청에 대한 접근 통제 | 회원 존재 및 유효성 판단 |
| 상품 | 선택한 상품 식별자와 수량을 신청에 연결 | 상품 존재와 신청 가능 여부 판단 |
| 배송지 | 선택 배송지를 신청에 연결 | 회원 소유와 유효성 판단 |
| 결제수단 | 선택 결제수단을 신청에 연결 | 회원 소유와 사용 가능 여부 판단 |
| 날짜 정책 | 종료일과 배송회차 계산 | 신청일 기준 및 첫 배송일 가능 여부 판단 |
| 금액 | 산정된 회차별 금액을 고지하고 계약에 고정 | 가격·할인·배송비 정책 적용 및 최종 금액 산정 |
| 첫 결제 | 요청 여부와 결과에 따른 신청 상태 결정 | 실제 결제 실행과 거래 결과 제공 |
| 계약 | 성공 확인 시 고지 내용으로 계약 성립 | 정기배송 계약을 생성하지 않음 |
| 일반 주문 | 생성하거나 변경하지 않음 | 기존 주문 기능과 정책 유지 |

정기배송 모듈은 기존 쇼핑몰 정책의 계산 방식을 재구현하지 않는다. 기존 기능에서 받은 판정과 금액을 정기배송 신청 및 계약의 근거로 사용한다.

## 5. 의존 방향에 대한 판단

핵심 의존 방향은 다음과 같다.

```text
기존 요청 진입부 → application → domain
                            ↑
                    infrastructure
```

- 요청 진입부는 정기배송 사용 사례만 호출한다.
- `application`은 정기배송 업무 규칙을 실행하기 위해 `domain`을 사용한다.
- `application`은 구체적인 저장소, 기존 쇼핑몰 구현 또는 결제 클라이언트를 직접 참조하지 않는다.
- `infrastructure`는 `application`의 연계 인터페이스를 구현하므로 `application`에 의존한다.
- `infrastructure`는 값 변환과 저장을 위해 필요한 경우 `domain` 타입을 참조한다.
- 기존 구성 패키지가 구현 객체를 생성하고 `application`에 연결한다.
- `domain`에서 `application`, `infrastructure`, 기존 쇼핑몰 패키지로 향하는 의존은 허용하지 않는다.

이 구조를 사용하면 기존 쇼핑몰과 한 배포 단위를 유지하면서도 최초 신청의 업무 규칙이 결제사·데이터베이스·기존 쇼핑몰 구현 방식에 종속되지 않는다.

## 6. 신청 처리 책임 배치

업무 처리 순서는 패키지 다이어그램의 화살표와 별개이며 다음과 같다.

1. `application`이 서버 발급 신청 식별자로 신청을 준비한다.
2. 기존 쇼핑몰 연계를 통해 선택 대상, 소유 관계, 배송 가능 여부와 금액을 확인한다.
3. `domain`이 계약 종료일과 배송회차를 계산한다.
4. `application`이 고지한 조건·금액·예정 회차를 저장한다.
5. 고객의 고지 확인을 받는다.
6. `application`이 같은 신청 식별자의 첫 결제 처리 여부를 확인한다.
7. 아직 요청되지 않은 경우에만 첫 결제 연계를 사용한다.
8. 성공이면 `domain`이 계약 성립을 허용하고 고지한 내용으로 계약을 저장한다.
9. 실패가 확정되면 계약 없이 신청을 미완료로 확정한다.
10. 결과가 확인되지 않으면 계약을 만들지 않고 결과 확인 필요 상태로 둔다.
11. 동일 신청 식별자가 다시 전달되면 추가 결제나 계약을 만들지 않고 저장된 상태에 따른 결과를 반환한다.

## 7. 이번 구조의 범위

포함하는 저장 정보는 다음으로 제한한다.

- 정기배송 신청과 상태
- 고객에게 고지한 계약 조건과 회차별 금액
- 계산된 예정 배송회차
- 첫 결제 요청 식별 정보와 확인된 결과
- 성공 시 성립한 정기배송 계약

다음 사항은 이번 구조의 책임에서 제외한다.

- 두 번째 회차 이후 결제 실행
- 실제 주문 및 배송 생성
- 배송 진행과 계약 운영 상태
- 계약 변경·해지·환불·만료 처리
- 배송 불가일의 사후 조정
- 결제 콜백·폴링·재시도 주기
- 장애 복구와 운영자 처리 절차
- 화면 또는 REST API의 세부 분할
- 데이터베이스 제약과 구체적인 키 전달 방식
- 구현 코드와 새로운 인프라 도입

결제 제공자 규격이 확정되기 전까지 남는 설계 과제는 **첫 결제 연계 구현이 신청 식별자를 기준으로 중복 청구 방지와 기존 거래 결과 확인이라는 업무 계약을 어떻게 충족할지** 확인하는 것이다. 이는 패키지 구조를 변경할 사안이 아니라 `subscription.infrastructure` 구현을 확정할 때 해결할 외부 연계 과제다.
[사용자 — 이번 피드백]
아래 답과 수정 요청을 반영해라. 기존 쇼핑몰·결제 및 저장 기능과 연결할 때 필요한 요청·결과와 책임을 정리해라. 제공자의 실제 API 정보는 만들지 말고, 업무에서 필요한 계약과 구현 전에 확인할 규격을 구분해라.

[앞선 응답에 대한 판단과 수정 요청]
- 네 패키지(신청 업무·정기배송 규칙·쇼핑몰 연계·신청 저장)와 포트로 의존을 뒤집는 구조를 채택한다. 실행 중 호출 방향과 코드 의존이 반대라는 설명도 유지한다. 패키지를 더 쪼개지 마라.
- 포트마다 업무에서 필요한 요청과 결과, 그리고 그 결과를 누가 판단하는지를 정리해라. 선택 확인과 금액 산정을 따로 둔 이유가 설명되면 그대로 둔다.
- 동일 신청의 동시 재전송에서 중복 청구를 막는 책임을 분명히 해라. 조회한 뒤 결제한다는 설명만으로는 막을 수 없다. 신청 저장소 포트가 한 신청의 첫 결제 시작을 한 번만 성공시키는 조건부 전이를 제공하고, 신청 업무는 그 결과로만 결제를 요청하게 해라. 이 권한을 새 업무 상태로 추가하지 마라. DBMS·락·SQL 구현은 정하지 않는다.
- 첫 결제 포트는 성공 확정·실패 확정·결과 확인 불가를 구분하고, 결과 확인은 새 청구 없이 기존 요청을 확인한다. 제공자의 멱등 키·조회·오류 규격 지원은 미확인이므로 지원한다고 단정하지 마라. 이 규격을 입증하기 전에는 실제 결제 연동을 완료로 보지 않는다.
- 성공이 확인되면 계약 성립과 신청완료를 한 단위로 반영해라. 결제 결과 기록과 계약 저장을 따로 두어 한쪽만 반영되는 틈을 만들지 마라.
- 날짜·금액·상태 규칙을 다시 나열하지 말고 앞 산출물을 참조해라. 도식에 없는 REST 주소·새 도메인 객체·운영 정책은 추가하지 마라. 바뀐 내용이 있으면 도식을 다시 보여라.
