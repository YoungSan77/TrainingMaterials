# “주문한다” 요구사항 정의서 초안 v0.4

> 사람 검토용 실습 초안이다. 미정 분기는 필요한 정책을 담당자에게 확인해야 하며, 현재 요구사항이 해당 분기까지 완성됐음을 뜻하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 기본 용어

| 용어 | 정의 |
|---|---|
| 주문 | 배송지가 지정되어 생성된 거래 기록 |
| 주문 항목 | 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가 |
| 판매가 | 상품 시스템이 제공하는 상품의 가격 |
| 주문 금액 | 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액 |
| 주문 생성 | 배송지 지정에 따라 주문이 기록되고 상태가 `결제대기`가 되는 것 |
| 주문 성립 | 카드 승인이 완료되어 같은 주문의 상태가 `결제완료`가 되는 것 |
| 주문 결과 확인 | 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것. 별도 통지 여부나 담당 시스템을 뜻하지 않는다. |
| 응답 미확정 | 결제 응답을 승인 또는 거절로 확정할 수 없는 상황 |

## 기능 및 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다. 재고 판단 시점은 확정하지 않는다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다. 구체적인 후속 처리는 `[미정 F]`다.
- 고객은 본인의 주문만 조회하거나 변경 요청할 수 있다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능을 재구현하지 않는다.

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정 — 상세 범위:** 배송지를 지정하면 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제 — 상세 범위:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인 — 상세 범위:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다.

## 범위

- 공통 흐름 3～5단계
- 배송지 지정과 주문 생성
- 주문 생성 시점의 판매가 및 주문 금액 확정
- 상품 시스템의 판매가·재고 판단 연계
- 카드 승인 요청과 응답에 따른 주문 결과 처리
- 승인에 따른 `결제완료` 반영과 배송 요청
- 본인 주문에 대한 조회·변경 접근 제한

상품 조회와 장바구니 구성은 공통 흐름의 전제다.

## 제외 범위

- 화면과 사용자 인터페이스
- 상품·결제·배송 시스템 내부 기능의 재구현
- 주문 성립 이후의 취소·환불·반품·교환 및 배송 진행
- 카드 외 결제 수단
- 배송비
- 쿠폰과 할인

도메인 모델, 아키텍처, 기술 설계 및 구현 코드는 이번 요구사항 명세에 포함하지 않는다. 이는 시스템 기능의 제외 범위가 아니라 작성 산출물의 구분이다.

## 미정 사항과 확인 근거

| 항목 | 담당자 확인이 필요한 내용 | 발견 근거 |
|---|---|---|
| `[H]` | 비회원 주문 허용 여부와 본인 확인 방법 | 비회원의 주문 접근 조건이 제시되지 않았다. |
| 재고 판단 시점 | 상품 시스템에 재고 판단을 요청하는 시점 | 재고 판단을 따르라는 조건만 있고 시점은 제시되지 않았다. |
| 승인 전 재고 부족 | 승인 전에 재고 부족으로 판단된 경우의 처리 | 해당 분기의 처리 정책이 제시되지 않았다. |
| `[B]` | 결제대기 기한과 기한 경과 후 처리 | 기한과 만료 정책이 제시되지 않았다. |
| `[F]` | 결제 응답 미확정 시 후속 처리와 재결제 허용 여부 | 성공 또는 실패로 바꾸지 말라는 조건만 있다. |
| `[E]` | 카드 승인 뒤 재고 부족 시 처리 | 승인 취소나 주문 상태 처리 기준이 제시되지 않았다. |
| `[G]` | 카드 승인 뒤 배송 요청 실패 시 처리 | 주문·승인에 미치는 영향과 재요청 기준이 제시되지 않았다. |
| `[I]` | 별도 주문 확인 통지 여부와 담당 시스템 | 통지 주체가 정해지지 않았다. |

이 항목들은 정책 확인 전까지 완료된 요구사항이나 수용 기준으로 간주하지 않는다. 미정이라는 이유만으로 운영 시 무조건 아무 행동도 하지 않는 정책을 부여하지 않는다.

## 대표 수용 예

모든 예는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울을 사용한다.

### 1. 카드 승인

- **Given(전제):** 서울을 배송지로 지정한 주문이 `결제대기`이고 주문 금액은 2,000원이다.
- **When(사건):** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **Given(전제):** 펜의 판매가가 개당 1,000원일 때 생성된 주문의 금액은 2,000원이고 상태는 `결제대기`다.
- **When(사건):** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이며 상태는 `결제완료`다. 승인 결과를 확인할 수 있고 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **Given(전제):** 주문 금액 2,000원의 주문이 `결제대기`다.
- **When(사건):** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **Then(기대 결과):** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 고객은 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **Given(전제):** 카드 X의 승인이 거절된 같은 주문이 `결제대기`이고 배송 요청은 0회다.
- **When(사건):** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

결제 응답 미확정, 재고 부족 및 배송 요청 실패는 정책이 미정이므로 대표 수용 예의 기대 결과로 확정하지 않는다.

## 품질 및 접근 수용 기준

### 정상 품질 시험

- **Given(전제):** 상품·결제·배송 외부 시스템을 정상 응답을 주는 테스트 대역으로 구성하고, 각 외부 응답은 1초 이내다.
- **When(사건):** 공통 흐름 4의 카드 결제 요청을 동시에 100건 실행한다.
- **Then(기대 결과):** 공통 흐름 5의 결과 수신까지 측정했을 때 100건 중 95건 이상이 각각 3초 이내에 완료된다.

이는 실습 시험 기준이며 실제 운영 환경의 보장 값이 아니다.

### 본인 주문 접근

- **Given(전제):** 고객 본인과 다른 고객의 주문이 존재한다.
- **When(사건):** 고객이 주문 조회 또는 변경을 요청한다.
- **Then(기대 결과):** 본인 주문에 대한 요청은 허용되고 다른 고객의 주문에 대한 요청은 거절된다.

인증 방식, 거절 응답 코드 및 화면 표현은 이번 요구사항에서 설계하지 않는다.
