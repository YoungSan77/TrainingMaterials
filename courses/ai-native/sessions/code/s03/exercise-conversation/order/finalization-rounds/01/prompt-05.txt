합의한 "주문한다" 요구사항 정의서와 수용 기준을 다음 실습에서 읽을 간결한 Markdown 파일로 생성해라. 초안 표기·대화 안내·파일 생성 안내 없이 최종 문서 본문만 출력해라. 새 정책·분석·설계·코드를 추가하지 말고 지금까지의 합의만 정리해라.

마지막 초안의 접근 수용 예에는 '본인의 변경 요청은 허용'이라고 돼 있어 결제대기 중 상품·수량·배송지를 바꿀 수 없다는 합의와 충돌한다. 본인 여부는 접근 권한의 조건일 뿐 업무상 변경을 무조건 허용하는 조건이 아니다. 본인 주문에 대한 권한 확인과 변경 가능 여부를 구분하고, 결제대기 주문의 변경 금지를 그대로 보존해라. 다른 고객의 조회·변경 요청은 거절한다. 인증 방식이나 응답 코드는 설계하지 마라.

문서는 짧은 목적·범위, 사용자 이야기 하나, 핵심 기능·업무 규칙, 기본 용어집, 공통 흐름 1~5와 승인·거절 분기, 네 대표 수용 예, 품질·접근 기준, 제외·미정으로 구성해라. 같은 값을 매번 반복하지 말고 대표 예의 공통 전제를 한 번만 적어라. 용어집은 다음 실습에 필요한 기본 용어와 상태의 뜻만 짧게 적고 클래스·속성·관계·아키텍처는 만들지 마라. 전제·사건·기대 결과는 각 예마다 짧은 항목으로 유지해라. 품질 시험의 측정 구간과 조건을 보존해라. 미정 H·B·F·E·G·I와 재고 판단 시점·승인 전 재고 부족 처리는 짧은 질문과 이유로 남기되 완료 정책으로 확정하지 마라. 새 예외나 폐기한 가정을 되살리지 마라. 긴 표나 도식·반복 설명·부가 체크리스트를 넣지 말고 핵심만 목록으로 정리해라.
