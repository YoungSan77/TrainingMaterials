# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

# “주문한다” 요구사항 정의서 초안 v0.1

> 사람의 검토를 위한 초안이다. `[미정]` 항목은 정책 결정 전까지 요구사항으로 확정하지 않는다.

## 지금 필요한 질문

1. 회원만 주문할 수 있는가? 비회원도 가능하다면 결제대기 주문을 다시 찾을 때 어떻게 본인을 확인하는가? `[미정 H]`
2. 상품 시스템의 재고 판단은 어느 시점에 요청하며, 카드 승인 전에 재고가 없다고 판단되면 어떻게 처리하는가?
3. 결제대기 기한은 얼마이며, 기한이 지나면 주문과 결제를 어떻게 처리하는가? `[미정 B]`
4. 카드 승인 응답을 확정할 수 없을 때 재결제를 허용하는가? 이후 누가 어떤 기준으로 결과를 확정하는가? `[미정 F]`
5. 카드 승인 뒤 재고가 없으면 승인과 주문을 어떻게 처리하는가? `[미정 E]`
6. 카드 승인 뒤 배송 요청이 실패하면 누가, 언제, 어떻게 재요청하는가? 승인이나 주문에는 어떤 영향을 주는가? `[미정 G]`
7. 주문 확인 통지는 이 시스템이 보내는가, 다른 시스템의 통지로 대신하는가? `[미정 I]`
8. 카드 승인 뒤 성립한 주문의 상태명은 무엇인가?
9. 응답시간, 처리량, 가용성 등 품질 목표가 있는가?

예시의 상품·수량·주소는 제공되지 않았으므로 구체적인 값은 넣지 않았다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 확정하고 카드 승인을 받아 주문을 성립시키고 싶다.

## 기능 요구사항

- 고객은 장바구니에서 주문을 시작할 수 있어야 한다.
- 고객이 배송지를 확정하면 주문을 생성해야 한다.
- 생성된 주문은 결제대기 상태여야 한다.
- 주문을 생성할 때 상품 시스템에서 적용되는 판매가와 재고 판단을 사용해야 한다.
- 주문 생성 시점의 판매가를 주문 항목의 단가로 기록하고 주문 금액을 산정해야 한다.
- 결제대기 주문에 대해 카드 결제를 요청할 수 있어야 한다.
- 카드 승인이 완료되면 주문을 성립시켜야 한다.
- 카드 승인 뒤에만 배송 시스템에 배송을 요청해야 한다.
- 카드 승인이 거절되면 주문을 결제대기로 유지하고 다른 카드로 다시 결제할 수 있어야 한다.
- 카드 승인 응답을 확정할 수 없으면 이를 성공 또는 실패로 임의 처리하지 않아야 한다.

## 업무 규칙

- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 다음과 같이 계산한다.  
  `주문 금액 = 각 항목의 주문 생성 시점 판매가 × 수량의 합`
- 주문 생성 뒤 상품 판매가가 변경되어도 주문 금액과 청구 금액은 바뀌지 않는다.
- 결제대기 중에는 상품, 수량 및 배송지를 변경할 수 없다.
- 상품, 수량 또는 배송지를 바꾸려면 새로운 주문을 생성해야 한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 완료된 시점에 주문이 성립한다.
- 주문 시스템은 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 배송 요청은 카드 승인 이전에 보내지 않는다.
- 미정 정책은 구현 과정에서 임의로 보완하지 않는다.

## 용어

| 용어 | 정의 |
|---|---|
| 주문 생성 | 고객이 배송지를 확정하여 주문이 결제대기 상태로 만들어지는 것 |
| 결제대기 | 카드 승인이 아직 완료되지 않은 주문 상태 |
| 주문 항목 | 주문에 포함된 상품, 주문 수량 및 주문 생성 시점의 단가 |
| 주문 금액 | 모든 주문 항목의 단가와 수량을 곱한 결과의 합 |
| 카드 승인 완료 | 결제 시스템에서 카드 승인이 확정된 것 |
| 주문 성립 | 카드 승인이 완료되어 주문의 효력이 발생하는 것 |
| 배송 요청 | 카드 승인 뒤 배송 시스템에 주문 배송을 요청하는 것 |
| 응답 미확정 | 결제 시스템의 응답을 승인 성공이나 거절로 확정할 수 없는 상황 |

## 기본 흐름

1. 고객이 장바구니에서 주문을 시작한다.
2. 고객이 배송지를 확정한다.
3. 시스템이 주문 생성 시점의 판매가를 적용하여 주문 금액을 계산한다.
4. 시스템이 결제대기 상태의 주문을 생성한다.
5. 고객이 카드 결제를 요청한다.
6. 결제 시스템이 카드 승인을 완료한다.
7. 주문이 성립한다.
8. 시스템이 배송 시스템에 배송을 요청한다.
9. 주문 확인 통지는 `[미정 I]`의 결정에 따른다.

## 대안 흐름

### A1. 결제대기 주문의 내용을 변경하려는 경우

1. 고객이 상품, 수량 또는 배송지 변경을 요청한다.
2. 기존 주문의 내용은 변경하지 않는다.
3. 고객은 변경된 내용으로 새로운 주문을 생성한다.

### A2. 카드 승인이 거절된 경우

1. 결제 시스템이 카드 승인을 거절한다.
2. 주문을 취소하지 않고 결제대기로 유지한다.
3. 고객은 다른 카드로 결제를 다시 요청할 수 있다.

## 예외 흐름

### E1. 결제 결과를 확정할 수 없는 경우

1. 결제 시스템의 응답을 승인 성공이나 거절로 확정할 수 없다.
2. 시스템은 이를 성공 또는 실패로 임의 확정하지 않는다.
3. 재결제 허용 여부와 후속 처리는 `[미정 F]`로 남긴다.

### E2. 카드 승인 뒤 재고가 없는 경우

1. 상품 시스템이 재고가 없다고 판단한다.
2. 승인 취소나 주문 상태 변경을 임의로 수행하지 않는다.
3. 후속 처리는 `[미정 E]`로 남긴다.

### E3. 카드 승인 뒤 배송 요청이 실패한 경우

1. 배송 시스템이 요청을 정상적으로 수신하지 못한다.
2. 승인 취소, 주문 상태 변경 또는 재요청 방식을 임의로 결정하지 않는다.
3. 후속 처리는 `[미정 G]`로 남긴다.

### E4. 결제대기 기한이 지난 경우

기한과 만료 후 처리가 정해지지 않았으므로 만료, 취소, 삭제 또는 결제 차단을 수행하는 것으로 요구하지 않는다. `[미정 B]`

# “주문한다” 요구사항 정의서 초안 v0.2

> 사람의 검토을 위한 실습용 초안이다. 미정 정책은 구현 요구사항으로 확정하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 확정하고 카드 승인을 받아 주문을 성립시키고 싶다.

## 기능 요구사항

- 고객이 배송지를 확정하면 주문을 생성한다.
- 생성된 주문의 상태는 `결제대기`로 한다.
- 주문 생성 시점의 상품 판매가를 단가로 확정하고 주문 금액을 계산한다.
- 재고 판단은 상품 시스템의 판단을 따르되, 판단 시점은 아직 정하지 않는다.
- 결제대기 주문에 대해 카드 승인을 요청할 수 있다.
- 카드 승인이 완료되면 주문이 성립하고 상태를 `결제완료`로 변경한다.
- 카드 승인 뒤 배송 시스템에 배송을 요청한다.
- 주문의 조회 및 변경 요청은 본인의 주문만 대상으로 한다.
- 상품·결제·배송 시스템의 기능은 연계하여 사용하며, 그 내부 기능을 이 시스템에서 재구현하지 않는다.

## 업무 규칙

- `주문 생성`은 배송지 확정에 따라 주문이 기록되고 `결제대기` 상태가 되는 것을 뜻한다.
- `주문 성립`은 카드 승인이 완료되어 주문 상태가 `결제완료`가 되는 것을 뜻한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱한 값의 합이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 청구 금액은 바뀌지 않는다.
- 결제대기 중에는 상품, 수량 및 배송지를 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 주문을 취소하지 않고 `결제대기`로 유지한다.
- 카드 승인이 완료되기 전에는 배송을 요청하지 않는다.
- 주문 시스템은 재고를 별도로 확보하지 않으며 상품 시스템의 판단을 따른다.
- 결제 응답이 확정되지 않으면 성공이나 실패로 임의 확정하지 않는다.
- 미정 사항에 관한 상태 변경이나 후속 처리를 임의로 수행하지 않는다.

## 용어

| 용어 | 정의 |
|---|---|
| 주문 생성 | 배송지 확정에 따라 주문이 기록되고 `결제대기` 상태가 되는 것 |
| 결제대기 | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태 |
| 주문 성립 | 카드 승인이 완료되어 주문 상태가 `결제완료`가 되는 것 |
| 결제완료 | 카드 승인이 완료되어 주문이 성립한 상태 |
| 주문 금액 | 각 항목의 주문 생성 시점 단가와 수량을 곱한 값의 합 |
| 응답 미확정 | 결제 응답을 승인 성공이나 거절로 확정할 수 없는 상황 |

## 예시

- 상품: 펜
- 수량: 2개
- 주문 생성 시 판매가: 개당 1,000원
- 주문 금액 및 카드 청구 금액: 2,000원
- 배송지: 서울
- 배송지 확정 뒤 상태: `결제대기`
- 카드 승인 완료 뒤 상태: `결제완료`
- 배송 요청: 카드 승인 완료 뒤 수행

주문 생성 뒤 펜의 판매가가 변경되더라도 이 주문의 금액과 청구 금액은 2,000원으로 유지한다.

## 흐름

### 기본 흐름

1. 고객이 장바구니에서 주문을 시작한다.
2. 고객이 배송지를 확정한다.
3. 시스템이 주문 생성 시점의 판매가로 주문 금액을 계산한다.
4. 시스템이 주문을 생성하고 상태를 `결제대기`로 기록한다.
5. 고객이 카드 결제를 요청한다.
6. 결제 시스템이 카드 승인을 완료한다.
7. 주문이 성립하고 상태가 `결제완료`가 된다.
8. 시스템이 배송 시스템에 배송을 요청한다.

### 대안 흐름: 카드 승인 거절

1. 결제 시스템이 카드 승인을 거절한다.
2. 주문을 `결제대기`로 유지한다.
3. 고객은 다른 카드로 다시 결제할 수 있다.

### 대안 흐름: 주문 내용 변경 요청

1. 고객이 결제대기 주문의 상품, 수량 또는 배송지 변경을 요청한다.
2. 기존 주문은 변경하지 않는다.
3. 변경된 내용으로 새 주문을 생성하도록 한다.

### 대표 미정 분기

- 결제 응답을 확정할 수 없으면 성공이나 실패로 처리하지 않는다. 재결제 허용 여부와 후속 처리는 `[미정 F]`다.
- 승인 뒤 재고가 부족해도 승인 취소나 주문 상태 변경을 임의로 수행하지 않는다. 후속 처리는 `[미정 E]`다.
- 승인 뒤 배송 요청이 실패해도 승인 취소, 상태 변경 또는 재요청 방식을 임의로 결정하지 않는다. 후속 처리는 `[미정 G]`다.

## 기능 및 업무 규칙

- 고객이 배송지를 지정하면 주문을 생성하고 상태를 `결제대기`로 기록한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 생성 시점의 상품 판매가를 단가로 확정하여 주문 금액을 계산한다.
- 주문 생성 뒤 판매가가 바뀌어도 주문 금액과 카드 청구 금액은 바꾸지 않는다.
- `결제대기` 주문의 상품, 수량 및 배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며, 고객은 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태를 `결제완료`로 변경한다.
- 배송 요청은 카드 승인 완료 뒤에만 해당 주문의 확정된 배송지로 보낸다.
- 재고는 별도로 확보하지 않고 상품 시스템의 판단을 따른다. 재고 판단 시점은 정하지 않는다.
- 결제 응답이 미확정이면 승인이나 거절로 임의 확정하지 않는다.
- 고객은 본인의 주문만 조회하거나 변경 요청할 수 있다.
- 상품·결제·배송 시스템을 외부 시스템으로 연계하며, 그 내부 기능은 재구현하지 않는다.

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품 시스템의 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정 — 이번 상세 범위:** 고객이 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제 — 이번 상세 범위:** 고객이 카드 결제를 요청한다.
   - 승인되면 같은 주문이 성립하고 `결제완료`가 된 뒤 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하며 배송을 요청하지 않는다. 고객은 다른 카드로 다시 결제할 수 있다.
5. **주문 결과 확인 — 이번 상세 범위:** 고객이 결제 응답에 따른 주문 결과를 확인한다. 이는 별도의 통지 주체를 확정하지 않는다.

- 주문 생성 시점의 판매가 및 주문 금액 확정
- 상품 시스템의 판매가·재고 판단 연계
- 카드 승인 요청과 응답에 따른 주문 결과 처리

상품 조회와 장바구니 구성은 공통 흐름의 전제이며, 이번 상세 범위는 3～5단계이다.

## 미정 사항

- `[H]` 비회원 주문 허용 여부와 본인 확인 방법
- 재고 판단 시점과 승인 전 재고 부족 시 처리
- `[B]` 결제대기 기한과 기한 경과 후 처리
- `[F]` 결제 응답 미확정 시 후속 처리와 재결제 허용 여부
- `[E]` 승인 뒤 재고 부족 시 처리
- `[G]` 승인 뒤 배송 요청 실패 시 처리
- `[I]` 별도 주문 확인 통지 여부와 담당 시스템

배송 요청 실패를 주문 취소나 자동 재요청으로 처리한다는 기준은 두지 않는다. 중복 요청 등 새로운 예외 정책도 추가하지 않는다.

## 품질 기준

다음은 실습의 정상 시험 기준이며 운영 환경의 보장 수치가 아니다.

- 동시 요청 100건으로 시험한다.
- 상품·결제·배송 시스템의 각 외부 응답이 1초 이내인 조건에서 시험한다.
- 요청부터 결과 수신까지 전체 요청의 95% 이상이 3초 이내여야 한다.
- 고객은 본인의 주문만 조회하거나 변경 요청할 수 있어야 한다.

## 대표 수용 예

모든 예는 펜 2개, 주문 생성 시 개당 판매가 1,000원, 주문 금액과 카드 청구 금액 2,000원, 배송지 서울을 사용한다.

### 1. 카드 승인

- **전제:** 서울을 배송지로 지정하여 주문 금액 2,000원의 주문이 생성됐고 상태가 `결제대기`이다.
- **사건:** 카드 Y가 승인된다.
- **기대 결과:** 같은 주문의 상태가 `결제완료`로 관찰되고 청구 금액은 2,000원이다. 그 주문에 대해 서울로 보내는 배송 요청이 1회 관찰된다.

### 2. 주문 생성 뒤 가격 변경

- **전제:** 펜의 판매가가 개당 1,000원일 때 펜 2개의 주문이 생성됐고 주문 금액은 2,000원이다.
- **사건:** 주문 생성 뒤 상품 시스템의 펜 판매가가 개당 1,200원으로 오른 후 카드 Y가 승인된다.
- **기대 결과:** 같은 주문의 주문 금액과 청구 금액은 모두 2,000원으로 관찰된다. 상태는 `결제완료`이며 서울로 보내는 배송 요청은 1회 관찰된다.

### 3. 카드 승인 거절

- **전제:** 서울을 배송지로 지정하여 주문 금액 2,000원의 주문이 생성됐고 상태가 `결제대기`이다.
- **사건:** 카드 X가 거절된다.
- **기대 결과:** 같은 주문의 상태가 `결제대기`로 유지되고 배송 요청 횟수는 0회이다. 승인이나 청구 완료는 관찰되지 않는다.

### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X가 거절되어 주문 금액 2,000원의 같은 주문이 `결제대기` 상태이며, 배송 요청 횟수는 0회이다.
- **사건:** 고객이 카드 Y로 같은 주문의 결제를 다시 요청하고 카드 Y가 승인된다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문의 상태가 `결제완료`로 바뀐다. 청구 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 해당 주문에 대해 서울로 보내는 배송 요청은 모두 합해 1회이다.

## 대표 수용 예

모든 예는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울을 사용한다.

### 1. 카드 승인

- **Given(전제):** 서울을 배송지로 지정한 주문이 `결제대기`이고 주문 금액은 2,000원이다.
- **When(사건):** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **Given(전제):** 펜의 판매가가 개당 1,000원일 때 생성된 주문의 금액은 2,000원이고 상태는 `결제대기`다.
- **When(사건):** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이며 상태는 `결제완료`다. 승인 결과를 확인할 수 있고 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **Given(전제):** 주문 금액 2,000원의 주문이 `결제대기`다.
- **When(사건):** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **Then(기대 결과):** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 고객은 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **Given(전제):** 카드 X의 승인이 거절된 같은 주문이 `결제대기`이고 배송 요청은 0회다.
- **When(사건):** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **Then(기대 결과):** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

결제 응답 미확정, 재고 부족 및 배송 요청 실패는 정책이 미정이므로 대표 수용 예의 기대 결과로 확정하지 않는다.

# “주문한다” 요구사항 정의서

## 목적과 범위

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 결과를 확인할 때까지의 요구사항을 정의한다.

상품 조회와 장바구니 구성은 전제이며, 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다. 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 확인한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

## 기본 용어집

- **주문:** 배송지가 지정되어 생성된 거래 기록
- **주문 항목:** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가:** 상품 시스템이 제공하는 상품 가격
- **주문 금액:** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기:** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료:** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

## 품질·접근 기준

### 정상 품질 시험

- **전제:** 상품·결제·배송 외부 시스템은 정상 응답을 주는 테스트 대역이며, 각 외부 응답은 1초 이내다.
- **사건:** 공통 흐름 4의 카드 결제 요청을 동시에 100건 실행한다.
- **기대 결과:** 공통 흐름 4의 카드 결제 요청부터 5의 결과 수신까지 측정했을 때 100건 중 95건 이상이 각각 3초 이내에 완료된다.

이 기준은 실습 시험용이며 실제 운영 환경의 보장 값이 아니다.

### 주문 접근

- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.
- 본인 주문이더라도 변경 가능 여부는 업무 규칙에 따른다. 따라서 `결제대기` 주문의 상품·수량·배송지는 변경할 수 없으며, 바꾸려면 새 주문을 생성한다.
- 인증 방식, 거절 응답 코드 및 화면 표현은 정하지 않는다.

## 제외 사항

- 화면과 사용자 인터페이스
- 상품·결제·배송 시스템 내부 기능의 재구현
- 주문 성립 이후의 취소·환불·반품·교환 및 배송 진행
- 카드 외 결제 수단
- 배송비
- 쿠폰과 할인
- 도메인 모델, 아키텍처, 기술 설계 및 구현 코드

## 미정 사항

다음 항목은 담당자 확인이 필요하며 완료된 정책으로 간주하지 않는다.

- **`[H]` 비회원 주문과 본인 확인:** 비회원 주문을 허용하는가? 허용한다면 결제대기 주문의 본인을 어떻게 확인하는가? 비회원의 접근 조건이 제시되지 않았다.
- **`[B]` 결제대기 기한:** 기한은 얼마이며 경과 후 어떻게 처리하는가? 기한과 만료 정책이 제시되지 않았다.
- **`[F]` 결제 응답 미확정:** 이후 어떻게 처리하며 재결제를 허용하는가? 성공이나 실패로 확정하지 않는다는 조건만 제시됐다.
- **`[E]` 승인 뒤 재고 부족:** 카드 승인 뒤 재고가 없으면 어떻게 처리하는가? 승인과 주문의 처리 기준이 제시되지 않았다.
- **`[G]` 배송 요청 실패:** 승인 뒤 배송 요청이 실패하면 어떻게 처리하는가? 주문·승인에 미치는 영향과 재요청 기준이 제시되지 않았다.
- **`[I]` 주문 확인 통지:** 별도 통지가 필요한가? 필요하다면 어느 시스템이 담당하는가? 통지 주체가 정해지지 않았다.
- **재고 판단 시점:** 상품 시스템에 언제 재고 판단을 요청하는가? 상품 시스템의 판단을 따른다는 조건만 있고 시점은 제시되지 않았다.
- **승인 전 재고 부족:** 승인 전에 재고 부족으로 판단되면 어떻게 처리하는가? 해당 분기의 정책이 제시되지 않았다.

최종 MD를 검토하니 앞서 합의한 구분이 누락됐다. 다음 두 곳을 고쳐 합의 결과의 Markdown 문서 본문 전체를 다시 생성해라. 다른 정책이나 모델·설계를 새로 만들지 마라.

1. '제외 사항' 마지막의 '도메인 모델, 아키텍처, 기술 설계 및 구현 코드'는 시스템 기능의 제외가 아니다. 그 항목만 별도 '이번 문서에서 다루지 않는 산출물'로 구분하고, 시스템 기능을 제외한다는 뜻이 아님을 짧게 밝혀라. 취소·환불·배송 진행, 카드 외 수단, 배송비·쿠폰 등 기능 범위의 제외와 섞지 마라. 이 구분은 ②에서 이미 합의했다.
2. 다음 실습의 용어집에 쓸 공통 영문 표기를 기본 용어에만 병기해라. 주문(Order), 주문 항목(OrderItem), 판매가(salePrice), 주문 금액(totalAmount), 결제대기(PENDING_PAYMENT), 결제완료(PAID)가 사람의 지정이다. 코드·클래스·속성 설계를 하라는 뜻이 아니라 같은 뜻을 같은 이름으로 부르기 위한 표기다. 주어진 표기 외의 새 영문 이름은 만들지 마라. 주문 생성과 주문 성립의 차이는 기존 흐름·설명에서 유지한다.

그 외 합의한 범위, 규칙, 흐름 1~5, 네 대표 수용 예, 품질·접근 기준, 미정 질문을 보존해라. 접근 권한이 있어도 결제대기 중 변경할 수 없다는 구분을 유지하고 재고 시점이나 배송 요청 실패의 답을 만들지 마라. 같은 조건을 여러 절에서 되풀이하지 말고 간결하게 정리해라. 서두에는 목적을 요약한 한 문단을 먼저 두어라. 형식은 제목·짧은 항목 목록으로 하고 표·도식·코드는 추가하지 마라. 초안 표기·수정 설명·대화 안내는 빼고 최종 문서 전문만 출력해라.
