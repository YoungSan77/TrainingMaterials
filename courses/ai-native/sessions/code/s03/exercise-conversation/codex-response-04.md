대표 수용 기준을 기준으로 용어와 규칙을 통일하고, 신청과 계약을 분리해 세 다이어그램을 보완했다.

## 용어와 업무 규칙

- **정기배송 신청:** 고객이 상품 한 종류·수량, 본인의 등록 배송지·결제수단, 계약기간, 배송 주기와 첫 배송일을 선택해 계약 체결을 요청하는 과정.
- **정기배송 계약:** 첫 결제 성공이 확인될 때 신청으로부터 성립하는 계약. 신청당 최대 하나만 성립한다.
- **배송회차:** 신청 시 계산하고 고객에게 고지하는 예정 일정. 실제 배송 실행 상태를 뜻하지 않는다.
- **첫 결제:** 첫 회차 금액을 신청 시 결제하는 행위. 이후 회차의 결제 예정일 규칙과 구분한다.
- **동일 회차 결제금액:** 신청 시 기존 쇼핑몰 정책으로 산정하며 모든 회차에 같은 금액을 적용한다.

핵심 규칙은 다음과 같다.

- 선택 대상이 유효하지 않거나 본인 소유가 아니거나 첫 배송일이 허용되지 않으면 신청 준비 상태를 유지하며 첫 결제를 실행하지 않는다.
- 첫 배송일은 `신청일 + 3달력일`부터 선택할 수 있으며 해당 날짜를 포함한다.
- 종료일은 첫 배송일에 계약 개월 수를 더해 계산하고 계약기간에서 제외한다. 대응 날짜가 없으면 해당 월의 말일이다.
- 종료일보다 이른 예정 배송일만 회차에 포함한다.
- 첫 회차는 신청 시 결제한다. 이후 회차에만 예정 배송일 3달력일 전의 결제 예정일을 둔다.
- 첫 결제 성공 확인만 계약을 성립시킨다. 실패 확정은 신청 미완료이고, 결과 확인 불가는 실패가 아니다.
- 계약이 성립하면 신청 시 고지한 일정과 동일 결제금액이 계약 내용으로 확정된다.
- 동일 신청의 반복 전송은 추가 청구, 추가 계약 또는 상태 변화를 발생시키지 않는다. 별개의 신규 신청은 허용한다.

## 클래스 다이어그램

```mermaid
classDiagram
direction LR

class 회원 {
  <<기존 개념 참조>>
}

class 상품 {
  <<기존 개념 참조>>
}

class 등록배송지 {
  <<기존 개념 참조>>
}

class 등록결제수단 {
  <<기존 개념 참조>>
}

class 정기배송신청 {
  신청일: 날짜
  수량: 양의 정수
  계약개월수: 3 | 6
  배송주기주수: 2 | 4
  첫배송일: 날짜
  종료예정일: 날짜
  회차결제금액: 금액
  상태: 신청준비 | 첫결제결과확인중 | 결과확인필요 | 신청완료 | 신청미완료
}

class 배송회차 {
  회차번호: 양의 정수
  예정배송일: 날짜
  결제구분: 신청시결제 | 배송전결제
  결제예정일: 날짜[0..1]
}

class 첫결제 {
  결제금액: 금액
  결제시점: 신청시
  결과: 확인중 | 확인불가 | 성공 | 실패
}

class 정기배송계약 {
  계약시작일: 날짜
  계약종료일: 날짜
  계약개월수: 3 | 6
  배송주기주수: 2 | 4
  회차결제금액: 금액
  자동갱신여부: false
}

회원 "1" <-- "0..*" 정기배송신청 : 신청자
상품 "1" <-- "0..*" 정기배송신청 : 선택 상품
등록배송지 "1" <-- "0..*" 정기배송신청 : 선택 배송지
등록결제수단 "1" <-- "0..*" 정기배송신청 : 선택 결제수단

정기배송신청 "1" *-- "1..*" 배송회차 : 계산·고지
정기배송신청 "1" *-- "0..1" 첫결제 : 유효한 신청 확정 후 실행
정기배송신청 "1" --> "0..1" 정기배송계약 : 성공 확인 시 성립
정기배송계약 "0..1" --> "1..*" 배송회차 : 동일 일정 확정
첫결제 "0..1" --> "1" 배송회차 : 첫 회차 대상
```

정적 제약:

- 첫 회차의 `결제구분`은 `신청시결제`이며 `결제예정일`은 없다.
- 2회차 이후는 `배송전결제`이며 `결제예정일 = 예정배송일 - 3달력일`이다.
- 모든 배송회차에는 신청의 `회차결제금액`과 같은 금액이 적용된다.
- 계약의 일정·금액은 해당 신청에서 계산·고지된 값 및 회차와 동일하다.
- 첫 결제 성공 확인 전에는 계약이 존재하지 않는다.

## 시퀀스 다이어그램

```mermaid
sequenceDiagram
    actor 고객
    participant 업무 as 정기배송 업무
    participant 쇼핑몰 as 기존 쇼핑몰
    participant 결제 as 결제 시스템

    고객->>업무: 상품·수량, 배송지·결제수단,<br/>계약기간·주기·첫 배송일 선택
    업무->>쇼핑몰: 선택 대상의 유효성·본인 소유 및<br/>첫 배송일 허용 여부 확인
    쇼핑몰-->>업무: 확인 결과

    alt 선택 내용이 유효하지 않음
        업무-->>고객: 선택 내용 확인 요청
        Note over 업무: 신청 준비 유지<br/>첫 결제 실행 안 함
    else 선택 내용이 유효함
        업무->>쇼핑몰: 신청 시점 가격·할인·배송비 산정
        쇼핑몰-->>업무: 모든 회차에 적용할 동일 금액

        Note over 업무: 종료 예정일과 배송회차 계산<br/>첫 회차는 신청 시 결제<br/>이후 회차만 배송 3일 전 결제

        업무-->>고객: 선택 내용, 계약기간, 일정·횟수,<br/>동일 금액과 결제 시점 등 고지
        고객->>업무: 고지 확인 및 신청 의사 확정
        업무->>결제: 첫 회차 금액 결제

        alt 성공 확인
            결제-->>업무: 첫 결제 성공 확정
            Note over 업무: 고지된 일정과 금액으로<br/>계약 1건 성립
            업무-->>고객: 신청 완료 및 계약 성립 안내
        else 실패 확정
            결제-->>업무: 첫 결제 실패 확정
            업무-->>고객: 신청 미완료 안내
        else 결과 확인 불가
            결제-->>업무: 결과 미확정
            업무-->>고객: 결과 확인 필요 안내
            결제-->>업무: 이후 성공 또는 실패 확정
            Note over 업무: 확정 결과에 따라<br/>신청 완료 또는 미완료
        end
    end
```

결과 확인 불가 이후의 성공·실패 확정은 결제 시스템의 결과 확인으로 발생하는 업무 사건만 나타낸다. 통지·조회 방식과 고객 알림 수단은 포함하지 않는다.

## 정기배송 신청 상태 머신

```mermaid
stateDiagram-v2
    [*] --> 신청준비 : 새 신청 절차 시작

    신청준비 --> 신청준비 : 선택 변경
    신청준비 --> 신청준비 : 선택 대상 부적합 또는\n첫 배송일 미허용 / 선택 확인 요청
    신청준비 --> 첫결제결과확인중 : 유효성 확인 및 고지 확인\n첫 결제 실행

    첫결제결과확인중 --> 신청완료 : 첫 결제 성공 확인\n계약 1건 성립
    첫결제결과확인중 --> 신청미완료 : 첫 결제 실패 확정\n계약 미성립
    첫결제결과확인중 --> 결과확인필요 : 결제 결과 확인 불가\n계약 미성립

    결과확인필요 --> 신청완료 : 첫 결제 성공 확인\n계약 1건 성립
    결과확인필요 --> 신청미완료 : 첫 결제 실패 확정\n계약 미성립

    신청완료 --> [*]
    신청미완료 --> [*]
```

상태 머신 전체에 적용되는 공통 불변 규칙은 다음과 같다.

> 동일 신청이 반복 전달되어도 상태는 바뀌지 않으며 첫 결제, 계약 또는 배송회차를 추가하지 않는다. 기존에 확정된 결과가 있으면 그 결과를, 아직 확정되지 않았으면 결과 확인 필요를 안내한다.

## 대표 수용 기준 검토

| 검토 항목 | 모델 적용 결과 |
|---|---|
| 일정 | 2027-11-03 시작, 3개월, 2주 주기이면 종료일은 2028-02-03이며 제외된다. 2028-01-26까지 7회다. |
| 월말 | 2027-01-31 시작, 3개월이면 대응 날짜가 없으므로 종료일은 2027-04-30이며 제외된다. |
| 금액 | 회차결제금액은 10,000원이고 7개 회차 모두 10,000원으로 유지된다. |
| 청구 시점 | 신청 시에는 첫 회차 10,000원만 결제한다. 총액 70,000원을 일시불로 청구하지 않는다. |
| 신청 결과 | 성공 확인만 신청 완료와 계약 성립을 발생시킨다. 실패 확정은 신청 미완료, 결과 미확정은 결과 확인 필요다. |
| 선택 오류 | 신청 준비를 유지하고 선택 내용 확인을 요청하며 결제를 실행하지 않는다. |
| 반복 전송 | 추가 청구·계약·회차·상태 변화 없이 기존 결과만 안내한다. |
| 성능·정보 보호 | 모델의 검토 제약으로 유지하며 별도 업무 개념이나 기술 구성요소로 만들지 않았다. |

현재 제공된 답변과 대표 수용 기준 사이에 추가로 확인이 필요한 불명확한 의미는 없다.
