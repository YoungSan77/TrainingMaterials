# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

# 첫 주문 기능 개발 활용 방식

현재는 활용 방식만 선택한다. 요구·모델·설계·코드·검사·완료 조건의 내용은 만들지 않으며, 실습 1의 미정 정책도 확정하지 않는다. 운영 시스템과 실제 고객 데이터는 사용하지 않고 외부 부작용은 없으며, 로컬 변경은 Git으로 되돌릴 수 있다.

1. **업무 조건 결정**
   - **특성:** 업무 규칙—확정 조건과 의도적 미정이 구분됨 / 절차—담당자가 정책과 경계를 확인 / 자동 확인—정책 타당성은 자동 판정 불가 / 되돌림—문서 수정은 쉬우나 정책 결정은 사람의 책임
   - **선택·근거와 사람 확인 시점:** **수작업**. LLM은 질문·정리만 보조하며 담당자가 답마다 확인한다.

2. **요구·모델·설계 초안**
   - **특성:** 업무 규칙—확정 범위만 반영하고 미정 사항을 대신 결정하지 않아야 함 / 절차—아직 마련되지 않음 / 자동 확인—검사와 완료 조건이 없음 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** **대화형 보조**. 담당자가 LLM의 답마다 검토한다.

3. **저장소 골격**
   - **특성:** 업무 규칙—기술과 구성 규칙이 아직 정해지지 않음 / 절차—생성 순서와 명령이 없음 / 자동 확인—빌드·검사 환경이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 확인한다.

4. **확정 범위 코드 구현**
   - **특성:** 업무 규칙—확정 조건만 구현하고 미정 분기를 정책화하지 않아야 함 / 절차—설계와 구현 절차가 없음 / 자동 확인—완료 조건과 자동 검사가 아직 없음 / 되돌림—작은 로컬 변경으로 Git 복구 가능
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 정책 침범과 오류를 확인한다.

5. **검사 작성·실행**
   - **특성:** 업무 규칙—확인 대상과 기대 결과가 아직 정해지지 않음 / 절차—작성·실행 절차가 없음 / 자동 확인—검사를 마련하고 실제 오류를 잡는지 사람의 확인이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재 검사 초안은 **대화형 보조** 대상이다. 담당자가 LLM의 답마다 확인한다.

6. **릴리스 설명**
   - **특성:** 업무 규칙—확정 범위·제외 범위·미정 사항을 구분해야 함 / 절차—작성·승인 절차가 없음 / 자동 확인—실제 변경 내역과 검사 결과가 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**, 최종 확인과 승인은 **수작업**이다. 초안은 답마다, 승인은 공개 전에 확인한다.

## 공통 전환 조건

현재는 담당자의 수작업 결정과 LLM 대화형 보조가 가장 단순하고 충분하다. 비용은 아직 계측하지 않았으며, 별도 실행 체계 구성과 검토 비용을 줄이는 선택이다.

절차를 고정할 수 있으면 일반 자동화 또는 워크플로를 사용한다. 명확한 완료 조건을 자동 검사로 판정할 수 있고, 그 검사가 실제 오류를 잡는다고 사람이 확인한 뒤에도 실행 결과에 따라 다음 행동을 정해야 하여 절차를 사전에 고정하기 어려울 때만 에이전트를 검토한다. 사람은 대화형 보조에서는 답마다, 워크플로에서는 정한 단계마다, 에이전트에서는 종료·중단 시점에 확인한다.

# 주문 기능 요구사항 정의서 초안

## 1. 목적

고객이 장바구니에서 주문을 시작하여 배송지를 확정하고, 카드 결제 승인을 받아 주문이 성립할 때까지의 요구사항을 정의한다.

본 문서는 제공된 업무 조건만 반영한다. 미정 사항은 정책으로 확정하지 않고 질문으로 남긴다.

## 2. 사용자 스토리

> 고객으로서, 장바구니의 상품과 배송지를 기준으로 주문을 생성하고 카드 결제 승인을 받아 주문을 성립시키고 싶다.

## 3. 기능과 흐름

### 3.1 주요 기능

1. 장바구니를 바탕으로 주문을 시작한다.
2. 고객이 배송지를 확정하면 주문을 생성한다.
3. 주문 생성 시 판매가와 수량을 기준으로 주문 금액을 확정한다.
4. 생성된 주문을 `결제대기` 상태로 둔다.
5. 결제대기 주문에 대해 카드 승인을 요청한다.
6. 카드 승인 결과에 따라 다음과 같이 처리한다.
   - 승인 완료: 주문이 성립한다.
   - 승인 거절: 주문을 `결제대기` 상태로 유지한다.
   - 응답 불확정: 성공이나 실패로 임의 확정하지 않는다.
7. 카드 승인 뒤 상품 시스템의 재고 판단을 따른다.
8. 카드 승인 뒤에만 배송 시스템에 배송을 요청한다.

### 3.2 기본 흐름

```mermaid
flowchart TD
    A[고객이 장바구니에서 주문 시작] --> B[배송지 확정]
    B --> C[주문 생성]
    C --> D[생성 시점 판매가로 주문 금액 확정]
    D --> E[주문 상태: 결제대기]
    E --> F[카드 승인 요청]
    F --> G{카드 승인 응답}

    G -->|승인 완료| H[주문 성립]
    G -->|승인 거절| I[결제대기 유지]
    I --> J[다른 카드로 재결제 가능]
    J --> F

    G -->|응답 불확정| K[성공·실패로 임의 확정하지 않음]
    K --> L[이후 처리 미정]

    H --> M[상품 시스템의 재고 판단을 따름]
    M --> N{재고 있음 여부}
    N -->|재고 있음| O[배송 시스템에 배송 요청]
    N -->|재고 없음| P[이후 처리 미정]
    O --> Q{배송 요청 결과}
    Q -->|성공| R[배송 요청 접수]
    Q -->|실패| S[이후 처리 미정]
```

배송 요청과 재고 확인의 정확한 선후관계는 입력에서 확정되지 않았다. 위 도식은 승인 이후 두 연계가 필요함을 표현한 초안이며, 실제 순서는 미정 질문에서 확인해야 한다.

## 4. 업무 규칙

### BR-01 주문 생성

- 고객이 배송지를 확정하면 주문을 생성한다.
- 생성된 주문의 최초 상태는 `결제대기`이다.
- 주문자와 수령인은 같은 사람으로 본다.

### BR-02 주문 금액

- 각 주문 항목의 금액은 다음과 같이 계산한다.
  - `주문 생성 시점의 판매가 × 수량`
- 주문 금액은 모든 주문 항목 금액의 합이다.
- 주문 생성 뒤 상품 판매가가 변해도 주문 금액은 변경하지 않는다.
- 결제 시 주문 생성 때 확정한 금액을 청구한다.
- 배송비, 쿠폰 및 할인은 주문 금액 계산 범위에서 제외한다.

### BR-03 결제대기 주문의 변경 제한

- 결제대기 중에는 다음 정보를 변경할 수 없다.
  - 상품
  - 수량
  - 배송지
- 위 정보를 바꾸려면 기존 주문을 수정하지 않고 새로 주문해야 한다.

### BR-04 결제 수단과 주문 성립

- 결제 수단은 카드만 허용한다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 카드 승인이 거절되어도 주문을 취소하지 않는다.
- 승인 거절 주문은 `결제대기` 상태로 유지한다.
- 고객은 승인 거절 후 다른 카드로 다시 결제할 수 있다.

### BR-05 결제 응답 불확정

- 결제 시스템의 응답을 확정할 수 없으면 이를 결제 실패로 바꾸지 않는다.
- 불확정 응답을 결제 성공으로도 임의 확정하지 않는다.
- 응답 불확정 이후의 처리와 재결제 허용 여부는 미정이다.

### BR-06 재고

- 재고 여부는 상품 시스템의 판단을 그대로 따른다.
- 주문 기능은 재고를 별도로 확보하지 않는다.
- 카드 승인 뒤 재고가 없을 때 승인 취소나 주문 상태 변경을 임의로 수행하지 않는다.

### BR-07 배송 요청

- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- 배송 요청 실패 시 다음 처리를 임의로 수행하지 않는다.
  - 카드 승인 취소
  - 주문 상태 변경
  - 임의의 배송 재요청
- 재요청의 주체와 방식은 미정이다.

## 5. 용어

| 용어 | 정의 |
|---|---|
| 고객 | 장바구니에서 주문을 시작하고 배송지와 카드 결제를 제공하는 사람 |
| 주문자 | 주문하는 고객. 이 범위에서는 수령인과 같은 사람으로 본다. |
| 수령인 | 주문 상품을 받을 사람. 이 범위에서는 주문자와 같은 사람으로 본다. |
| 장바구니 | 고객이 주문하려는 상품과 수량을 담은 주문 시작점 |
| 주문 항목 | 주문에 포함된 개별 상품과 그 수량 및 주문 생성 시점의 판매가 |
| 주문 금액 | 각 주문 항목의 `주문 생성 시점 판매가 × 수량`을 모두 합한 금액 |
| 결제대기 | 주문이 생성되었으나 카드 승인이 완료되지 않은 상태 |
| 카드 승인 완료 | 결제 시스템에서 카드 결제가 승인되어 주문이 성립하는 조건 |
| 카드 승인 거절 | 결제 시스템에서 카드 승인을 거절한 결과. 주문은 결제대기로 유지된다. |
| 응답 불확정 | 결제 시스템의 응답을 성공 또는 실패로 확정할 수 없는 상황 |
| 주문 성립 | 카드 승인이 완료된 상태 |
| 재고 판단 | 상품 시스템이 해당 상품의 재고 여부를 판단하는 것 |
| 배송 요청 | 카드 승인 뒤 배송 시스템에 배송 처리를 요청하는 것 |

`주문 성립`이 별도의 주문 상태를 뜻하는지, 업무상 성립 여부만 뜻하는지는 미정이다.

## 6. 품질 요구사항

입력에서 성능, 보안, 가용성 및 운영 품질의 구체적인 목표치는 제시되지 않았다. 현재 확정할 수 있는 품질 요구사항은 다음과 같다.

### QR-01 금액 일관성

- 주문 생성 시 확정한 단가와 주문 금액은 이후 판매가 변경의 영향을 받지 않아야 한다.
- 카드 승인 요청 금액은 주문 생성 시 확정한 주문 금액과 같아야 한다.

### QR-02 상태 및 결과의 임의 확정 방지

- 카드 승인 거절을 주문 취소로 처리하지 않아야 한다.
- 결제 응답 불확정을 성공이나 실패로 임의 변경하지 않아야 한다.
- 미정 정책에 해당하는 상황에서 승인 취소, 주문 상태 변경, 삭제 또는 결제 차단을 임의로 수행하지 않아야 한다.

### QR-03 외부 시스템 판단 존중

- 판매가는 상품 시스템에서 제공한 주문 생성 시점의 값을 사용해야 한다.
- 재고는 상품 시스템의 판단을 그대로 따라야 한다.
- 카드 승인 완료 여부는 결제 시스템의 결과를 기준으로 해야 한다.
- 카드 승인 전에는 배송 요청이 발생하지 않아야 한다.

### 추가로 정의가 필요한 품질 항목

다음 항목은 목표나 기준이 입력에 없으므로 담당자의 결정이 필요하다.

- 주문 및 결제 처리 응답시간
- 동시 주문 처리량
- 서비스 가용성 및 장애 복구 목표
- 개인정보와 결제 관련 정보의 보호 기준
- 주문·결제·배송 요청 이력의 보존 및 추적 기준
- 외부 시스템 호출의 시간 제한과 장애 판단 기준
- 중복 주문, 중복 결제 및 중복 배송 요청 방지 기준

## 7. 수용 기준

### AC-01 주문 생성

**Given** 고객이 장바구니에서 주문을 시작했고  
**When** 배송지를 확정하면  
**Then** 주문이 생성되고 주문 상태는 `결제대기`여야 한다.

### AC-02 주문 금액 확정

**Given** 주문 항목별 판매가와 수량이 제공되었고  
**When** 주문이 생성되면  
**Then** 주문 금액은 각 항목의 `생성 시점 판매가 × 수량`을 합산한 값이어야 한다.

### AC-03 판매가 변경

**Given** 주문 금액이 확정된 주문이 있고  
**When** 상품 시스템의 판매가가 변경되어도  
**Then** 해당 주문의 단가와 주문 금액은 변경되지 않아야 하며, 확정된 주문 금액을 청구해야 한다.

### AC-04 결제대기 정보 변경 제한

**Given** 주문이 `결제대기` 상태일 때  
**When** 고객이 상품, 수량 또는 배송지를 변경하려 하면  
**Then** 기존 주문에서는 변경할 수 없어야 하며 새 주문이 필요함을 알려야 한다.

알림의 표현 및 전달 방식은 화면 범위에 해당하므로 본 문서에서는 정하지 않는다.

### AC-05 카드 승인 완료

**Given** 주문이 `결제대기` 상태이고  
**When** 카드 승인이 완료되면  
**Then** 주문이 성립해야 한다.

### AC-06 카드 승인 거절

**Given** 주문이 `결제대기` 상태이고  
**When** 카드 승인이 거절되면  
**Then** 주문은 취소되지 않고 `결제대기` 상태로 남아야 하며 다른 카드로 다시 결제할 수 있어야 한다.

### AC-07 결제 응답 불확정

**Given** 결제 시스템에 카드 승인을 요청했고  
**When** 응답을 성공 또는 실패로 확정할 수 없으면  
**Then** 이를 성공이나 실패로 임의 확정하지 않아야 한다.

재결제 허용 여부와 이후 처리에 관한 수용 기준은 정책 확정 전까지 정의하지 않는다.

### AC-08 재고 판단

**Given** 카드 승인이 완료되었고  
**When** 재고 여부를 판단하면  
**Then** 주문 기능이 별도 재고를 확보하지 않고 상품 시스템의 판단을 따라야 한다.

승인 뒤 품절인 경우의 최종 결과는 정책 확정 전까지 정의하지 않는다.

### AC-09 배송 요청 시점

**Given** 주문의 카드 승인 여부가 확인되지 않았거나 승인이 완료되지 않았을 때  
**Then** 배송 시스템에 배송을 요청하지 않아야 한다.

**Given** 카드 승인이 완료되었을 때  
**Then** 배송 시스템에 배송을 요청해야 한다.

배송 요청 실패 이후의 최종 결과는 정책 확정 전까지 정의하지 않는다.

주요 기능 7과 도식·AC-08에서 재고 판단을 승인 뒤에 배치한 것은 입력에 없는 순서 확정이다. 주석으로 미정이라고 쓰는 것만으로 도식의 화살표와 수용 기준의 전제에 있는 확정이 해소되지 않는다. 재고 판단 시점과 승인 전후 품절 처리는 미정으로 분리하고 확정 흐름에 끼워 넣지 마라.
AC-04의 새 주문 필요 알림은 입력에서 합의한 기능이 아니므로 알림 의무를 추가하지 마라. 미정을 구현자가 결정하지 말라는 제약을 운영 중 영구 무동작 정책으로 바꾸지 마라.
데이터 모델·기술 설계·코드는 기능 제외가 아니라 이번 문서에서 작성하지 않는 산출물로 구분해라. 확정 규칙은 보존하고 사용자 스토리 하나, 기능·흐름, 기본 용어, 4가지 대표 상황의 전제·사건·기대 결과, 품질·접근 기준, 제외·미정이 연결되도록 초안을 보완해라. 네 상황 모두 동일 주문 여부·주문 금액·승인 요청 금액·상태·배송 요청 횟수를 관찰할 수 있게 해라. 불필요한 새 정책·모델·설계·코드는 추가하지 마라.

# 주문 기능 요구사항 정의서 초안 — 수정본

## 1. 목적과 작성 원칙

고객이 장바구니에서 주문을 시작해 배송지를 지정하고, 카드 결제 결과를 확인할 때까지의 요구사항을 정의한다.

- 기본 흐름 1~2는 전제, 상세 범위는 3~5이다.
- 제공된 업무 조건과 추가 확정 자료만 반영한다.
- 미정 사항은 확정 흐름이나 수용 기준에 끼워 넣지 않는다.
- 모델, 기술 설계, 코드 및 화면은 이 문서에서 작성하지 않는다.

## 2. 사용자 스토리

> 고객으로서, 장바구니의 상품에 배송지를 지정하고 주문 생성 시 확정된 금액으로 카드 승인을 받아 주문 결과를 확인하고 싶다.

## 3. 기능과 흐름

### 3.1 기본 흐름

1. 상품 조회
2. 장바구니
3. 배송지 지정
4. 결제
5. 주문 결과 확인

상품 조회와 장바구니는 주문 기능을 시작하기 위한 전제이다. 이 문서의 상세 범위는 배송지 지정부터 주문 결과 확인까지다.

```mermaid
flowchart TD
    A[1. 상품 조회<br/>전제] --> B[2. 장바구니<br/>전제]
    B --> C[3. 배송지 지정]
    C --> D[주문 생성<br/>상태: 결제대기]
    D --> E[생성 시점 판매가로<br/>주문 금액 확정]
    E --> F[4. 카드 승인 요청]
    F --> G{카드 승인 결과}

    G -->|승인 완료| H[상태: 결제완료<br/>주문 성립]
    H --> I[배송 요청 1회]
    I --> J[5. 주문 결과 확인]

    G -->|승인 거절| K[상태: 결제대기 유지<br/>청구 완료 아님]
    K --> L[다른 카드로 다시 결제 가능]
    L --> F
    K --> J

    G -->|응답 불확정| M[성공·실패로 확정하지 않음]
    M --> N[이후 처리 미정]
```

재고 판단은 상품 시스템을 따르지만 판단 시점이 정해지지 않았다. 따라서 재고 판단이나 재고 부족 처리를 위 확정 흐름에 배치하지 않는다.

주문 결과 확인은 기본 흐름에 포함되지만, 별도의 주문 확인 통지를 누가 보내는지는 확정하지 않는다.

### 3.2 주요 기능

1. 고객이 배송지를 확정하면 주문을 생성한다.
2. 생성된 주문의 상태를 `결제대기(PENDING_PAYMENT)`로 둔다.
3. 주문 생성 시점의 판매가와 수량으로 주문 금액을 확정한다.
4. 결제대기 주문에 대해 확정된 주문 금액으로 카드 승인을 요청한다.
5. 카드 승인 결과를 처리한다.
   - 승인 완료: 같은 주문이 성립하고 상태는 `결제완료(PAID)`가 된다.
   - 승인 거절: 같은 주문을 `결제대기`로 유지하며 청구 완료로 보지 않는다.
   - 응답 불확정: 성공이나 실패로 임의 확정하지 않는다.
6. 승인 거절 후 같은 주문에 다른 카드로 다시 승인을 요청할 수 있다.
7. 카드 승인 완료 뒤 배송 시스템에 배송을 1회 요청한다.
8. 고객은 자신의 주문 결과를 확인할 수 있다.

## 4. 업무 규칙

### BR-01 주문 생성

- 고객이 배송지를 확정하면 주문을 생성한다.
- 최초 상태는 `결제대기(PENDING_PAYMENT)`이다.
- 주문자와 수령인은 같은 사람으로 본다.

### BR-02 주문 금액

- 주문 항목 금액은 `주문 생성 시점 판매가 × 수량`이다.
- 주문 금액은 모든 주문 항목 금액의 합이다.
- 주문 생성 후 판매가가 변경되어도 같은 주문의 주문 금액은 바뀌지 않는다.
- 카드 승인 요청 금액은 주문 생성 시 확정된 주문 금액이다.

### BR-03 결제대기 주문의 변경 제한

- 결제대기 중에는 상품, 수량 및 배송지를 변경할 수 없다.
- 이를 바꾸려면 새로 주문해야 한다.
- 변경 거절의 응답 코드나 화면 표현은 정하지 않는다.

### BR-04 카드 결제와 주문 성립

- 결제 수단은 카드만 허용한다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태는 `결제완료(PAID)`가 된다.
- 카드 승인이 거절되면 청구 완료가 아니다.
- 승인 거절 시 같은 주문은 취소되지 않고 `결제대기`로 유지된다.
- 고객은 같은 주문에 다른 카드로 다시 결제를 요청할 수 있다.

### BR-05 결제 응답 불확정

- 결제 시스템의 응답을 확정할 수 없으면 실패로 바꾸지 않는다.
- 성공으로도 임의 확정하지 않는다.
- 이후 처리와 재결제 허용 여부는 미정이다.

이 규칙은 불확정 상황을 영구히 아무 처리도 하지 않는다는 정책을 뜻하지 않는다. 미정 정책을 구현자가 임의로 결정하지 말아야 한다는 제약이다.

### BR-06 재고

- 재고는 상품 시스템의 판단을 그대로 따른다.
- 주문 기능은 재고를 별도로 확보하지 않는다.
- 재고 판단 시점과 승인 전후 재고 부족 처리는 미정이다.
- 승인 뒤 재고가 없을 때 승인 취소나 주문 상태 변경 여부도 미정이다.

### BR-07 배송 요청

- 카드 승인 전이나 승인 거절 직후에는 배송을 요청하지 않는다.
- 카드 승인 완료 뒤 배송을 요청한다.
- 정상 승인 및 가격 변경 후 승인 사례에서는 배송 요청이 1회 발생한다.
- 카드 X 거절 후 카드 Y 승인 사례에서는 전체 결제 시도에 걸쳐 배송 요청이 총 1회 발생한다.
- 배송 요청 실패 후 처리는 미정이다.

## 7. 품질 및 접근 기준

### QR-01 실습 정상 품질 시험 기준

- 외부 상품·결제·배송 시스템은 정상 응답하는 테스트 대역을 사용한다.
- 각 외부 시스템의 응답 시간은 1초 이내로 둔다.
- 카드 결제 요청 100건을 동시에 실행한다.
- 기본 흐름 4의 요청부터 흐름 5의 결과 수신까지 측정한다.
- 100건 중 95건 이상이 3초 이내에 완료돼야 한다.

이 기준은 실습의 정상 품질 시험 조건이며 운영 환경의 성능 보장 수치가 아니다.

### QR-02 금액 일관성

- 주문 생성 시 확정한 판매가와 주문 금액은 이후 판매가 변경의 영향을 받지 않아야 한다.
- 각 카드 승인 요청 금액은 같은 주문의 확정된 주문 금액과 같아야 한다.

### QR-03 결제 및 배송 결과의 일관성

- 승인 거절을 청구 완료나 주문 취소로 처리하지 않아야 한다.
- 결제 응답 불확정을 성공이나 실패로 임의 확정하지 않아야 한다.
- 승인 완료 전에는 배송 요청이 발생하지 않아야 한다.
- 대표 정상 승인 사례에서는 배송 요청이 정확히 1회 발생해야 한다.

### QR-04 주문 접근 기준

- 고객은 본인의 주문만 조회하거나 변경을 요청할 권한이 있다.
- 타인의 주문에 대한 조회 및 변경 요청은 거절해야 한다.
- 본인이라도 `결제대기` 주문의 상품, 수량 및 배송지는 변경할 수 없다.
- 인증 방식, 거절 응답 코드 및 화면 표현은 정하지 않는다.

- 카드 승인 요청

- 승인 거절 후 다른 카드로 같은 주문 재결제
- 승인 완료에 따른 주문 성립과 결제완료 상태

## 10. 미정 사항

### H. 비회원 주문

- 비회원 주문 허용 여부
- 허용할 경우 결제대기 주문을 다시 찾을 때의 본인 확인 방법

### B. 결제대기 기한

- 결제대기 기한의 유무와 길이
- 기한 경과 후 취소, 삭제, 보존 또는 상태 처리
- 기한 경과 후 결제 차단 여부

정책이 정해질 때까지 구현자가 만료, 취소, 삭제 또는 결제 차단을 임의로 정하지 않는다.

### F. 결제 응답 불확정

- 결과 확인 방법과 책임 주체
- 재결제 허용 여부
- 중복 승인 가능성에 대한 처리
- 이후 적용할 상태나 표시

정책이 정해질 때까지 성공 또는 실패를 임의로 확정하지 않는다. 이를 영구 무동작 정책으로 해석하지 않는다.

### E. 재고 판단과 재고 부족

- 재고 판단 시점
- 승인 전 재고 부족 시 처리
- 승인 뒤 재고 부족 시 처리
- 일부 주문 항목만 재고가 없을 때의 처리
- 승인 취소나 주문 상태 변경 여부

재고 판단은 확정된 결제 흐름에 선행 또는 후행하는 단계로 배치하지 않는다.

### G. 배송 요청 실패

- 배송 요청 실패 후 주문 및 카드 승인 처리
- 재요청 여부
- 재요청의 주체, 횟수 및 방식
- 중복 배송 요청 방지 방법

### I. 주문 확인 통지

- 주문 확인 통지 여부
- 이 주문 기능과 다른 시스템 중 통지 주체
- 통지 대상, 시점 및 채널
- 통지 실패 후 처리

기본 흐름의 주문 결과 확인만으로 별도의 통지 의무나 주체를 확정하지 않는다.

### 그 밖에 근거가 없어 미정으로 유지할 사항

- 장바구니가 비어 있거나 수량이 유효하지 않을 때의 처리
- 주문 생성 시 판매가를 가져올 수 없을 때의 처리
- 중복 주문·결제·배송 요청의 식별 및 처리
- 외부 시스템의 시간 초과와 장애 판단 기준
- 이력 보존 기간
- 개인정보와 카드 관련 정보의 구체적인 인증·보안·보존 방식
- 실습 시험 기준을 제외한 운영 성능, 처리량, 가용성 및 복구 목표
