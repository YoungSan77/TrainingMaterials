# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

# 첫 주문 기능 개발 활용 방식

현재는 활용 방식만 선택한다. 요구·모델·설계·코드·검사·완료 조건의 내용은 만들지 않으며, 실습 1의 미정 정책도 확정하지 않는다. 운영 시스템과 실제 고객 데이터는 사용하지 않고 외부 부작용은 없으며, 로컬 변경은 Git으로 되돌릴 수 있다.

1. **업무 조건 결정**
   - **특성:** 업무 규칙—확정 조건과 의도적 미정이 구분됨 / 절차—담당자가 정책과 경계를 확인 / 자동 확인—정책 타당성은 자동 판정 불가 / 되돌림—문서 수정은 쉬우나 정책 결정은 사람의 책임
   - **선택·근거와 사람 확인 시점:** **수작업**. LLM은 질문·정리만 보조하며 담당자가 답마다 확인한다.

2. **요구·모델·설계 초안**
   - **특성:** 업무 규칙—확정 범위만 반영하고 미정 사항을 대신 결정하지 않아야 함 / 절차—아직 마련되지 않음 / 자동 확인—검사와 완료 조건이 없음 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** **대화형 보조**. 담당자가 LLM의 답마다 검토한다.

3. **저장소 골격**
   - **특성:** 업무 규칙—기술과 구성 규칙이 아직 정해지지 않음 / 절차—생성 순서와 명령이 없음 / 자동 확인—빌드·검사 환경이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 확인한다.

4. **확정 범위 코드 구현**
   - **특성:** 업무 규칙—확정 조건만 구현하고 미정 분기를 정책화하지 않아야 함 / 절차—설계와 구현 절차가 없음 / 자동 확인—완료 조건과 자동 검사가 아직 없음 / 되돌림—작은 로컬 변경으로 Git 복구 가능
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 정책 침범과 오류를 확인한다.

5. **검사 작성·실행**
   - **특성:** 업무 규칙—확인 대상과 기대 결과가 아직 정해지지 않음 / 절차—작성·실행 절차가 없음 / 자동 확인—검사를 마련하고 실제 오류를 잡는지 사람의 확인이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재 검사 초안은 **대화형 보조** 대상이다. 담당자가 LLM의 답마다 확인한다.

6. **릴리스 설명**
   - **특성:** 업무 규칙—확정 범위·제외 범위·미정 사항을 구분해야 함 / 절차—작성·승인 절차가 없음 / 자동 확인—실제 변경 내역과 검사 결과가 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**, 최종 확인과 승인은 **수작업**이다. 초안은 답마다, 승인은 공개 전에 확인한다.

## 공통 전환 조건

현재는 담당자의 수작업 결정과 LLM 대화형 보조가 가장 단순하고 충분하다. 비용은 아직 계측하지 않았으며, 별도 실행 체계 구성과 검토 비용을 줄이는 선택이다.

절차를 고정할 수 있으면 일반 자동화 또는 워크플로를 사용한다. 명확한 완료 조건을 자동 검사로 판정할 수 있고, 그 검사가 실제 오류를 잡는다고 사람이 확인한 뒤에도 실행 결과에 따라 다음 행동을 정해야 하여 절차를 사전에 고정하기 어려울 때만 에이전트를 검토한다. 사람은 대화형 보조에서는 답마다, 워크플로에서는 정한 단계마다, 에이전트에서는 종료·중단 시점에 확인한다.

# 주문 기능 요구사항 정의서 초안

## 1. 목적

고객이 장바구니에서 주문을 시작하여 배송지를 확정하고, 카드 결제 승인을 받아 주문이 성립하기까지의 요구사항을 정의한다.

이 문서는 제공된 업무 조건만 반영한다. 확정되지 않은 정책은 결정하지 않고 미정 사항과 확인 질문으로 남긴다.

## 2. 사용자 스토리

> 고객으로서 장바구니의 상품과 배송지를 기준으로 주문을 생성하고 카드 결제 승인을 받아 주문을 성립시키고 싶다.

## 3. 기능과 업무 흐름

### 3.1 주요 기능

1. 고객이 장바구니에서 주문을 시작한다.
2. 고객이 배송지를 확정한다.
3. 시스템이 주문을 생성하고 주문 당시 판매가를 기준으로 주문 금액을 확정한다.
4. 생성된 주문을 `결제대기` 상태로 둔다.
5. 고객이 카드 결제를 요청한다.
6. 카드 승인이 완료되면 주문이 성립한다.
7. 카드 승인 뒤 배송 시스템에 배송을 요청한다.

### 3.2 흐름

```mermaid
flowchart TD
    A[고객이 장바구니에서 주문 시작] --> B[배송지 확정]
    B --> C[상품 시스템의 판매가를 기준으로 주문 생성]
    C --> D[주문 상태: 결제대기]
    D --> E[고객이 카드 결제 요청]
    E --> F{카드 승인 결과}

    F -->|승인 완료| G[주문 성립]
    G --> H[배송 시스템에 배송 요청]
    H --> I{배송 요청 결과}
    I -->|성공| J[배송 요청 수신 완료]
    I -->|실패| K[미정 G: 후속 처리 필요]

    F -->|승인 거절| L[결제대기 유지]
    L --> M[다른 카드로 다시 결제 가능]
    M --> E

    F -->|응답을 확정할 수 없음| N[성공 또는 실패로 확정하지 않음]
    N --> O[미정 F: 후속 처리 및 재결제 허용 여부 필요]
```

재고 확인의 시점과 호출 흐름은 입력에서 정해지지 않았으므로 도식에서 특정 단계로 배치하지 않았다.

## 4. 업무 규칙

### 4.1 주문 생성

- 고객이 배송지를 확정한 때 주문을 생성한다.
- 생성된 주문의 상태는 `결제대기`이다.
- 주문자와 수령인은 같은 사람으로 취급한다.
- 비회원 주문 허용 여부는 미정이다.
- 비회원 주문을 허용할 경우 결제대기 주문을 다시 찾을 때의 본인 확인 방법도 미정이다.

### 4.2 주문 금액

- 주문 금액은 각 주문 항목의 `주문 생성 시점 판매가 × 수량`을 모두 합한 값이다.
- 주문 생성 시점의 판매가는 상품 시스템에서 제공하는 판매가를 따른다.
- 주문이 생성된 뒤 판매가가 변경되어도 주문 금액은 변경하지 않는다.
- 카드 결제 시 주문 생성 때 확정된 주문 금액을 청구한다.
- 배송비, 쿠폰 및 할인은 주문 금액 계산 범위에서 제외한다.

### 4.3 결제대기 주문

- 결제대기 중인 주문의 상품, 수량 및 배송지는 변경할 수 없다.
- 상품, 수량 또는 배송지를 바꾸려면 새 주문을 생성해야 한다.
- 카드 결제가 거절되어도 주문을 취소하지 않고 결제대기로 유지한다.
- 승인 거절 뒤 고객은 다른 카드로 다시 결제할 수 있다.
- 결제대기 기한과 기한 경과 후 처리는 미정이다.
- 기한 경과 시 만료, 취소, 삭제 또는 결제 차단 여부를 임의로 결정하지 않는다.

### 4.4 결제와 주문 성립

- 지원하는 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없는 경우 승인 성공이나 실패로 임의 확정하지 않는다.
- 응답을 확정할 수 없을 때의 후속 처리와 재결제 허용 여부는 미정이다.

### 4.5 재고

- 재고에 관한 판단은 상품 시스템의 결과를 그대로 따른다.
- 주문 기능은 재고를 별도로 확보하지 않는다.
- 카드 승인 뒤 재고가 없다고 판단된 경우의 처리는 미정이다.
- 이 경우 카드 승인 취소나 주문 상태 변경을 임의로 수행하지 않는다.

### 4.6 배송 요청

- 배송 시스템에는 카드 승인이 완료된 뒤에만 배송을 요청한다.
- 카드 승인 전에는 배송을 요청하지 않는다.
- 카드 승인 뒤 배송 요청이 실패했을 때의 처리는 미정이다.
- 배송 요청 실패 시 다음 사항을 임의로 결정하지 않는다.

  - 카드 승인 취소 여부
  - 주문 상태 변경 여부
  - 재요청 여부
  - 재요청 주체와 방식

- 주문 확인 통지의 발송 주체는 미정이다.

## 5. 용어

| 용어 | 정의 |
|---|---|
| 고객 | 장바구니에서 주문을 시작하고 배송지를 확정하며 카드 결제를 요청하는 주체 |
| 장바구니 | 고객이 주문하려는 상품과 수량을 담아 두는 대상 |
| 주문 항목 | 주문에 포함된 개별 상품과 수량 및 주문 생성 시점의 단가 |
| 주문 | 배송지가 확정되었을 때 생성되는 주문 대상 |
| 주문 생성 | 고객이 배송지를 확정하여 주문이 생기는 것 |
| 결제대기 | 주문이 생성되었으나 카드 승인이 완료되지 않은 주문 상태 |
| 주문 금액 | 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱한 값을 모두 합한 금액 |
| 카드 승인 | 결제 시스템이 카드 결제를 승인한 결과 |
| 승인 거절 | 결제 시스템이 카드 결제를 거절한 확정 결과 |
| 응답 확정 불가 | 결제 시스템의 응답을 승인 성공 또는 실패로 판단할 수 없는 상황 |
| 주문 성립 | 카드 승인이 완료된 상태 또는 사건 |
| 재고 판단 | 상품 시스템이 해당 상품의 재고 가능 여부를 판단하는 것 |
| 배송 요청 | 카드 승인 뒤 배송 시스템에 배송 처리를 요청하는 것 |

`주문 성립` 이후 주문에 부여할 상태의 명칭은 입력에서 정해지지 않았으므로 별도 상태명을 정의하지 않는다.

## 6. 품질 요구사항

### 6.1 금액 일관성

- 주문 생성 시 확정된 주문 항목의 단가와 주문 금액은 이후 상품 판매가가 변경되어도 바뀌지 않아야 한다.
- 카드 결제 요청 금액은 해당 주문에 확정된 주문 금액과 같아야 한다.

### 6.2 상태 및 결과의 정확성

- 카드 승인 완료 전에는 주문을 성립된 것으로 처리하지 않아야 한다.
- 승인 거절을 받은 주문은 결제대기 상태로 유지되어야 한다.
- 확정할 수 없는 결제 응답을 승인 성공이나 승인 실패로 변환하지 않아야 한다.
- 미정 정책에 해당하는 상황에서 시스템이 만료, 취소, 삭제, 승인 취소 또는 상태 변경을 임의로 수행하지 않아야 한다.

### 6.3 외부 시스템 결과의 보존

- 판매가와 재고 판단은 상품 시스템의 결과를 따라야 한다.
- 카드 승인 결과는 결제 시스템의 확정된 결과를 따라야 한다.
- 배송 요청은 카드 승인 완료 뒤에만 이루어져야 한다.

### 6.4 변경 방지

- 결제대기 주문의 상품, 수량 및 배송지는 변경되지 않아야 한다.
- 변경이 필요한 경우 기존 주문을 수정하는 대신 새 주문을 생성해야 한다.

성능, 가용성, 보안, 개인정보 보호, 감사 기록, 장애 복구 목표 및 외부 시스템 응답시간에 관한 수치는 입력에서 제공되지 않았으므로 미정이다.

## 7. 수용 기준

### AC-01 주문 생성

- Given 고객이 장바구니에서 주문을 시작했고
- When 고객이 배송지를 확정하면
- Then 주문이 생성되고
- And 주문 상태는 결제대기가 된다.

### AC-02 주문 금액 계산

- Given 장바구니에 하나 이상의 주문 항목이 있고
- When 배송지 확정으로 주문이 생성되면
- Then 주문 금액은 각 항목의 주문 생성 시점 판매가에 수량을 곱한 값의 합계가 된다.

장바구니가 비어 있을 수 있는지와 빈 장바구니의 처리 정책은 별도 확인이 필요하다.

### AC-03 판매가 변경

- Given 주문이 생성되어 주문 금액이 확정되었고
- When 상품 시스템의 판매가가 변경되면
- Then 해당 주문의 항목 단가와 주문 금액은 변경되지 않는다.
- And 카드 결제에는 주문 생성 때 확정된 금액을 사용한다.

### AC-04 결제대기 주문 변경 방지

- Given 주문이 결제대기 상태이고
- When 고객이 상품, 수량 또는 배송지를 변경하려 하면
- Then 기존 주문은 변경되지 않는다.
- And 변경된 내용으로 주문하려면 새 주문을 생성해야 한다.

### AC-05 카드 승인 완료

- Given 주문이 결제대기 상태이고
- When 결제 시스템의 카드 승인이 완료되면
- Then 주문이 성립한다.
- And 그 이후에만 배송 시스템에 배송을 요청한다.

### AC-06 카드 승인 거절

- Given 주문이 결제대기 상태이고
- When 카드 승인이 거절되면
- Then 주문을 취소하지 않는다.
- And 주문을 결제대기 상태로 유지한다.
- And 고객은 다른 카드로 다시 결제할 수 있다.

### AC-07 결제 응답 확정 불가

- Given 카드 결제가 요청되었고
- When 결제 시스템의 응답을 성공 또는 실패로 확정할 수 없으면
- Then 시스템은 그 응답을 승인 성공으로 확정하지 않는다.
- And 시스템은 그 응답을 승인 실패로 확정하지 않는다.
- And 미정 정책이 확정될 때까지 후속 처리와 재결제 허용 여부를 임의로 결정하지 않는다.

### AC-08 재고 판단

- Given 주문 처리 중 재고 판단이 필요하고
- When 상품 시스템이 재고 결과를 제공하면
- Then 주문 기능은 그 판단을 그대로 따른다.
- And 주문 기능은 재고를 별도로 확보하지 않는다.

재고 확인 시점과 재고 부족 시 주문 진행 여부가 정해져야 이 기준을 구체적인 시나리오로 확장할 수 있다.

### AC-09 승인 뒤 재고 부족

- Given 카드 승인이 완료되었고
- When 상품 시스템이 재고가 없다고 판단하면
- Then 카드 승인을 임의로 취소하지 않는다.
- And 주문 상태를 임의로 변경하지 않는다.
- And 미정 정책에 따른 후속 처리를 임의로 만들어 내지 않는다.

### AC-10 배송 요청 실패

- Given 카드 승인이 완료되어 배송 시스템에 배송을 요청했고
- When 배송 요청이 실패하면
- Then 카드 승인을 임의로 취소하지 않는다.
- And 주문 상태를 임의로 변경하지 않는다.
- And 재요청 주체와 방식을 임의로 결정하지 않는다.

### AC-11 카드 외 결제 수단

- Given 고객이 주문 결제를 진행하려 할 때
- Then 지원되는 결제 수단은 카드로 한정된다.
- And 카드 외 결제 수단은 이 기능의 범위에 포함되지 않는다.

# 주문 기능 요구사항 정의서 초안

## 1. 목적과 적용 범위

고객이 장바구니에서 주문을 시작하여 배송지를 확정하고, 카드 승인을 받아 주문이 성립한 결과를 확인하기까지의 요구사항을 정의한다.

기본 흐름은 다음과 같다.

1. 상품 조회
2. 장바구니
3. 배송지 지정
4. 결제
5. 주문 결과 확인

상품 조회와 장바구니는 이 문서의 전제이며, 상세 범위는 배송지 지정부터 주문 결과 확인까지다. 결과 확인은 주문 확인 통지의 발송 여부나 주체를 확정하지 않는다.

이 문서는 제공된 업무 조건과 추가로 확인된 자료만 반영한다. 기술 설계·모델·코드는 주문 기능의 제외 범위가 아니라, 이번 문서에서 작성하지 않는 별도 산출물이다.

## 2. 사용자 스토리

> 고객으로서 장바구니의 상품과 수량을 바탕으로 배송지를 확정하고, 확정된 주문 금액으로 카드 승인을 받아 주문 결과를 확인하고 싶다.

## 3. 기능과 흐름

### 3.1 기능

1. 고객이 장바구니에서 주문을 시작한다.
2. 고객이 배송지를 확정한다.
3. 시스템이 주문 생성 시점의 판매가로 주문 금액을 계산하여 주문을 생성한다.
4. 생성된 주문의 상태를 결제대기(`PENDING_PAYMENT`)로 둔다.
5. 고객이 해당 주문의 확정 금액으로 카드 승인을 요청한다.
6. 카드가 거절되면 같은 주문을 결제대기로 유지하고, 다른 카드로 다시 결제할 수 있게 한다.
7. 카드 승인이 완료되면 같은 주문을 결제완료(`PAID`)로 변경하여 주문을 성립시킨다.
8. 카드 승인 완료 뒤 배송 시스템에 배송을 요청한다.
9. 고객이 주문 결과를 확인할 수 있게 한다.

### 3.2 업무 흐름

```mermaid
flowchart TD
    A[1. 상품 조회<br/>상세 범위의 전제] --> B[2. 장바구니<br/>상세 범위의 전제]
    B --> C[3. 배송지 지정]
    C --> D[주문 생성<br/>생성 시점 판매가로 주문 금액 확정]
    D --> E[상태: 결제대기<br/>PENDING_PAYMENT]
    E --> F[4. 카드 승인 요청<br/>확정된 주문 금액 사용]
    F --> G{결제 시스템의 확정 결과}

    G -->|승인 완료| H[같은 주문의 상태: 결제완료<br/>PAID]
    H --> I[배송 요청 1회]
    I --> J[5. 주문 결과 확인]

    G -->|승인 거절| K[같은 주문을 결제대기로 유지<br/>배송 요청 0회]
    K --> L[다른 카드로 재결제 가능]
    L --> F

    G -->|응답 확정 불가| M[성공·실패를 임의로 확정하지 않음]
    M --> N[미정 F<br/>담당자 결정 필요]
```

재고 판단 시점은 확정되지 않았으므로 흐름의 특정 단계에 배치하지 않는다.

## 4. 확정된 업무 규칙

### 4.1 주문 생성과 변경

- 고객이 배송지를 확정하면 주문을 생성한다.
- 주문 생성 직후 상태는 결제대기(`PENDING_PAYMENT`)다.
- 주문자와 수령인은 같은 사람으로 본다.
- 결제대기 주문의 상품, 수량 및 배송지는 변경할 수 없다.
- 상품, 수량 또는 배송지를 바꾸려면 새로 주문해야 한다.

### 4.2 주문 금액

- 주문 금액은 각 주문 항목의 `주문 생성 시점 판매가 × 수량`을 모두 더한 값이다.
- 주문 생성 뒤 상품의 판매가가 바뀌어도 주문 항목의 단가와 주문 금액은 바뀌지 않는다.
- 카드 승인 요청 금액은 주문 생성 때 확정된 주문 금액이다.
- 배송비, 쿠폰 및 할인은 범위에서 제외한다.

### 4.3 결제와 주문 성립

- 결제 수단은 카드로 한정한다.
- 카드 승인이 완료되면 주문이 성립하고, 같은 주문의 상태는 결제완료(`PAID`)가 된다.
- 카드 거절은 청구 완료가 아니다.
- 카드가 거절되면 같은 주문을 취소하지 않고 결제대기로 유지한다.
- 거절 뒤 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.
- 결제 응답을 확정할 수 없으면 성공이나 실패로 임의 확정하지 않는다. 이후 처리는 미정 F에 대한 담당자 결정이 필요하다.

### 4.4 재고와 배송

- 재고 판단은 상품 시스템의 판단을 그대로 따른다.
- 주문 기능은 재고를 별도로 확보하지 않는다.
- 배송 요청은 카드 승인 완료 뒤에만 한다.
- 정상 승인된 주문에는 배송 요청이 1회 발생한다.
- 승인 거절 직후에는 배송 요청이 발생하지 않는다.
- 카드 X 거절 뒤 카드 Y가 승인된 경우, 해당 주문의 배송 요청은 전체 과정에서 총 1회다.
- 승인 뒤 재고 부족과 배송 요청 실패의 최종 처리는 아직 정해지지 않았다.

- 처음 생성된 주문과 결제 결과가 같은 주문에 관한 것인지
- 주문 금액
- 카드 승인 요청 금액
- 최종 주문 상태
- 누적 배송 요청 횟수

## 7. 품질 및 접근 기준

### 7.1 정상 흐름 성능 시험 기준

다음 조건은 실습의 정상 품질 시험 기준이며 운영 환경의 성능 보장 수치가 아니다.

- 외부 상품·결제·배송 시스템은 정상 응답하는 테스트 대역으로 둔다.
- 각 외부 시스템은 1초 이내에 응답한다.
- 카드 결제 요청 100건을 동시에 실행한다.
- 기본 흐름 4의 결제 요청부터 흐름 5의 주문 결과 수신까지 측정한다.
- 100건 중 95건 이상이 3초 이내에 결과를 수신해야 한다.

### 7.2 금액과 상태의 일관성

- 주문 생성 시 확정된 단가와 주문 금액은 이후 판매가 변경으로 바뀌지 않아야 한다.
- 카드 승인 요청 금액은 주문 금액과 같아야 한다.
- 카드 승인 완료 전에는 주문을 결제완료로 처리하지 않아야 한다.
- 승인 거절 주문은 결제대기로 유지되어야 한다.
- 응답 확정 불가를 승인 성공이나 실패로 바꾸지 않아야 한다.

### 7.3 배송 요청 기준

- 카드 승인 전에는 배송을 요청하지 않아야 한다.
- 정상 승인된 같은 주문에는 배송 요청이 1회 발생해야 한다.
- 승인 거절 직후에는 배송 요청이 0회여야 한다.
- 카드 X 거절 뒤 카드 Y가 승인된 같은 주문에는 전체 과정에서 배송 요청이 총 1회여야 한다.

### 7.4 접근 기준

- 고객은 본인의 주문만 조회하거나 변경을 요청할 권한이 있다.
- 타인의 주문에 대한 조회 또는 변경 요청은 거절해야 한다.
- 본인의 주문이라도 결제대기 상태의 상품, 수량 및 배송지는 변경할 수 없다.
- 인증 방식, 거절 응답 코드 및 화면 표현은 정하지 않는다.

### 7.5 미정 분기에 대한 수용 기준의 한계

미정 정책을 구현자가 임의로 결정하지 말라는 제약은 운영 중 해당 분기를 영구적으로 아무 처리도 하지 않는 정책을 의미하지 않는다.

다음 상황은 담당자가 후속 정책을 결정하기 전까지 최종 수용 기준이 완성되지 않은 상태다.

- 결제 응답 확정 불가
- 카드 승인 뒤 재고 부족
- 배송 요청 실패
- 결제대기 기한 경과
- 주문 확인 통지

정책이 확정되기 전에는 성공·실패, 승인 취소, 주문 상태 변경, 재시도 또는 영구 무동작 중 어느 하나를 최종 동작으로 간주해서는 안 된다.

## 8. 범위와 산출물 구분

### 8.1 상세 범위

- 배송지 지정
- 주문 생성
- 주문 생성 시점 판매가와 수량을 이용한 주문 금액 확정
- 결제대기 상태 관리
- 카드 승인 요청과 확정 결과 처리
- 카드 거절 뒤 같은 주문에 대한 다른 카드 재결제
- 카드 승인 완료에 따른 결제완료 처리와 주문 성립
- 카드 승인 뒤 배송 요청
- 주문 결과 확인

### 8.2 전제

- 상품 조회
- 장바구니
- 상품 시스템에서 제공하는 판매가
- 상품 시스템의 재고 판단
- 운영 중인 결제 시스템의 카드 승인
- 운영 중인 배송 시스템의 배송 요청 수신

### 8.3 기능 제외 범위

- 결제 이후의 취소 및 환불
- 반품 및 교환
- 배송 진행
- 카드 외 결제 수단
- 배송비
- 쿠폰 및 할인
- 주문 기능 자체의 재고 확보

### 8.4 이번 문서에서 작성하지 않는 산출물

다음은 주문 기능 자체의 제외 범위가 아니라 이번 요구사항 문서에서 작성하지 않는 산출물이다.

- 화면 및 사용자 인터페이스 설계
- 업무·도메인·데이터 모델
- 기술 및 상세 설계
- 클래스와 속성 정의
- 구현 코드

## 9. 미정 사항

### 미정 H: 비회원 주문

- 비회원 주문을 허용하는가?
- 허용한다면 비회원이 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는가?

### 미정 B: 결제대기 기한

- 결제대기 주문에 기한을 두는가?
- 기한이 있다면 언제부터 얼마 동안인가?
- 기한이 지나면 주문을 어떻게 처리하는가?
- 기한이 지난 주문의 결제를 허용하는가?

### 미정 F: 결제 응답 확정 불가

- 응답을 확정할 수 없는 경우 이후 처리는 무엇인가?
- 결제 결과를 다시 확인하는 주체와 방식은 무엇인가?
- 결과 확정 전에 재결제를 허용하는가?
- 중복 승인이 확인되면 어떻게 처리하는가?

담당자 결정 전에는 이 분기의 최종 수용 기준을 완성할 수 없다.

### 미정 E: 승인 뒤 재고 부족

- 재고를 주문 흐름의 어느 시점에 판단하는가?
- 승인 전에 재고가 부족하면 어떻게 처리하는가?
- 승인 뒤 재고가 부족하면 주문과 카드 승인을 어떻게 처리하는가?
- 고객에게 알리는 주체와 방식은 무엇인가?

재고 판단 시점은 도식에서 고정하지 않는다. 담당자 결정 전에는 승인 뒤 재고 부족 분기의 최종 수용 기준을 완성할 수 없다.

### 미정 G: 배송 요청 실패

- 배송 요청 실패 시 재요청하는가?
- 재요청한다면 주체, 시점 및 횟수는 무엇인가?
- 주문 상태와 카드 승인은 어떻게 처리하는가?
- 고객이나 운영 담당자에게 실패를 알리는가?

담당자 결정 전에는 배송 요청 실패 분기의 최종 수용 기준을 완성할 수 없다.

### 미정 I: 주문 확인 통지

- 주문 확인 통지가 필요한가?
- 필요하다면 이 시스템이 보내는가, 다른 시스템의 통지로 대신하는가?
- 통지 채널, 시점, 내용 및 실패 처리는 무엇인가?

주문 결과 확인 요구는 유지하되, 이를 별도 통지로 제공한다고 확정하지 않는다.

### 그 밖의 미정 사항

다음 항목은 입력에 근거가 없으므로 새 정책으로 확정하지 않는다.

- 빈 장바구니 처리
- 최소·최대 주문 수량
- 판매가를 받지 못했을 때의 처리
- 판매 가능 여부가 바뀌었을 때의 처리
- 통화, 세금 포함 여부 및 반올림 규칙
- 배송지 항목과 유효성 기준
- 반복된 배송지 확정 요청에 대한 중복 주문 처리
- 반복된 결제 요청에 대한 중복 승인 처리
- 배송 시스템에 전달할 정보
- 외부 시스템 장애 및 응답 지연 처리
- 운영 환경의 성능·가용성·복구 목표
- 인증 방식, 응답 코드 및 화면 표현
[사용자 — 이번 피드백]
[앞선 응답의 검토 결과와 수정 요청]
추가 업무 결정은 없다. 확인된 조건으로 다음 불일치만 바로잡아라.
1. 상황 2는 가격 변경 전에 만들어진 같은 주문을 가격 변경 후 결제하는 것이다. '가격 변경 뒤 생성된 주문'이라는 문구는 전제 및 기대 결과와 모순된다. 주문 생성 → 가격 변경 → 같은 주문에 승인 요청의 순서를 명확히 해라.
2. 실습 1의 입력은 화면을 제외했다. '화면 및 사용자 인터페이스'의 기능 제외를 유지하고, 기술 설계·모델·코드 같은 이번 문서 미작성 산출물과 구분해라. 화면 제외를 단순히 화면 설계를 이번 문서에서 작성하지 않는다는 뜻으로 바꾸지 마라.
3. 외부 상품·결제·배송 시스템 내부 기능은 재구현하지 않는다는 범위를 유지해라.
나머지 확정 규칙, 4가지 상황, 시험 조건, 미정 정책은 보존하고 간결한 보완본을 제시해라. 새로운 정책·모델·설계·코드는 만들지 마라.
