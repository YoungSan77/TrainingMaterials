# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

# 첫 주문 기능 개발 활용 방식

현재는 활용 방식만 선택한다. 요구·모델·설계·코드·검사·완료 조건의 내용은 만들지 않으며, 실습 1의 미정 정책도 확정하지 않는다. 운영 시스템과 실제 고객 데이터는 사용하지 않고 외부 부작용은 없으며, 로컬 변경은 Git으로 되돌릴 수 있다.

1. **업무 조건 결정**
   - **특성:** 업무 규칙—확정 조건과 의도적 미정이 구분됨 / 절차—담당자가 정책과 경계를 확인 / 자동 확인—정책 타당성은 자동 판정 불가 / 되돌림—문서 수정은 쉬우나 정책 결정은 사람의 책임
   - **선택·근거와 사람 확인 시점:** **수작업**. LLM은 질문·정리만 보조하며 담당자가 답마다 확인한다.

2. **요구·모델·설계 초안**
   - **특성:** 업무 규칙—확정 범위만 반영하고 미정 사항을 대신 결정하지 않아야 함 / 절차—아직 마련되지 않음 / 자동 확인—검사와 완료 조건이 없음 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** **대화형 보조**. 담당자가 LLM의 답마다 검토한다.

3. **저장소 골격**
   - **특성:** 업무 규칙—기술과 구성 규칙이 아직 정해지지 않음 / 절차—생성 순서와 명령이 없음 / 자동 확인—빌드·검사 환경이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 확인한다.

4. **확정 범위 코드 구현**
   - **특성:** 업무 규칙—확정 조건만 구현하고 미정 분기를 정책화하지 않아야 함 / 절차—설계와 구현 절차가 없음 / 자동 확인—완료 조건과 자동 검사가 아직 없음 / 되돌림—작은 로컬 변경으로 Git 복구 가능
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**. 담당자가 LLM의 답마다 정책 침범과 오류를 확인한다.

5. **검사 작성·실행**
   - **특성:** 업무 규칙—확인 대상과 기대 결과가 아직 정해지지 않음 / 절차—작성·실행 절차가 없음 / 자동 확인—검사를 마련하고 실제 오류를 잡는지 사람의 확인이 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재 검사 초안은 **대화형 보조** 대상이다. 담당자가 LLM의 답마다 확인한다.

6. **릴리스 설명**
   - **특성:** 업무 규칙—확정 범위·제외 범위·미정 사항을 구분해야 함 / 절차—작성·승인 절차가 없음 / 자동 확인—실제 변경 내역과 검사 결과가 필요함 / 되돌림—Git으로 쉬움
   - **선택·근거와 사람 확인 시점:** 현재는 **대화형 보조**, 최종 확인과 승인은 **수작업**이다. 초안은 답마다, 승인은 공개 전에 확인한다.

## 공통 전환 조건

현재는 담당자의 수작업 결정과 LLM 대화형 보조가 가장 단순하고 충분하다. 비용은 아직 계측하지 않았으며, 별도 실행 체계 구성과 검토 비용을 줄이는 선택이다.

절차를 고정할 수 있으면 일반 자동화 또는 워크플로를 사용한다. 명확한 완료 조건을 자동 검사로 판정할 수 있고, 그 검사가 실제 오류를 잡는다고 사람이 확인한 뒤에도 실행 결과에 따라 다음 행동을 정해야 하여 절차를 사전에 고정하기 어려울 때만 에이전트를 검토한다. 사람은 대화형 보조에서는 답마다, 워크플로에서는 정한 단계마다, 에이전트에서는 종료·중단 시점에 확인한다.

# 주문 스토리: 카드 승인으로 주문을 성립한다

## 1. 사용자 스토리

고객으로서 장바구니의 상품을 주문하기 위해 배송지를 확정하고 카드 승인을 받아 주문을 성립시키고 싶다.

## 2. 범위

### 시작 조건

- 고객이 장바구니에서 주문을 시작한다.
- 상품 시스템에서 판매가와 재고 판단을 받을 수 있다.

### 종료 조건

다음 중 하나에 도달할 때까지를 다룬다.

- 카드 승인이 완료되어 주문이 성립하고 배송 시스템에 배송을 요청한다.
- 카드 승인이 거절되어 주문이 결제대기로 남는다.
- 결제 응답을 확정할 수 없어 정책 결정이 필요한 상태가 된다.
- 카드 승인 뒤 재고 부족 또는 배송 요청 실패가 발생해 정책 결정이 필요한 상태가 된다.

### 포함

- 배송지 확정
- 주문 생성
- 주문 금액 확정
- 상품 시스템의 재고 판단 사용
- 카드 승인 요청과 결과 처리
- 카드 승인 후 배송 요청
- 확정된 범위와 미정 정책의 구분

### 제외

- 화면과 사용자 인터페이스
- 기술 설계와 구현 방식
- 카드 외 결제 수단
- 배송비
- 쿠폰과 할인
- 주문 성립 이후의 취소, 환불, 반품, 교환 및 배송 진행
- 외부 시스템 내부 동작
- 운영 시스템과 실제 고객 데이터 사용
- 주문 확인 통지의 구체적 구현(정책 미정)

## 3. 기본 흐름

```mermaid
flowchart TD
    A[고객이 장바구니에서 주문 시작] --> B[상품 시스템의 판매가와 재고 판단 확인]
    B --> C{상품 시스템이 주문 가능하다고 판단하는가}
    C -- 아니요 --> X[주문을 진행하지 않음]
    C -- 예 --> D[고객이 배송지 확정]
    D --> E[주문 생성]
    E --> F[주문 상태를 결제대기로 설정]
    F --> G[생성 시점 단가와 수량으로 주문 금액 확정]
    G --> H[고객이 카드 결제 시도]
    H --> I[결제 시스템에 카드 승인 요청]
    I --> J{승인 응답을 확정할 수 있는가}
    J -- 아니요 --> U1[처리 미정: 성공·실패를 임의로 확정하지 않음]
    J -- 예 --> K{카드가 승인되었는가}
    K -- 아니요 --> L[주문을 결제대기로 유지]
    L --> H
    K -- 예 --> M[주문 성립]
    M --> N{승인 뒤 재고가 있는가}
    N -- 아니요 --> U2[처리 미정: 승인 취소·상태 변경을 임의로 하지 않음]
    N -- 예 --> O[배송 시스템에 배송 요청]
    O --> P{배송 요청이 성공했는가}
    P -- 예 --> Q[확정 범위의 정상 흐름 종료]
    P -- 아니요 --> U3[처리 미정: 승인 취소·상태 변경·재요청을 임의로 하지 않음]
```

재고 확인의 정확한 시점과 호출 횟수는 주어진 조건만으로 확정되지 않았다. 위 흐름의 “승인 뒤 재고” 판단은 미정 E를 드러내기 위한 표현이며, 상세 절차로 확정하면 안 된다.

## 4. 확정된 업무 규칙

### 주문 생성

- 고객이 배송지를 확정한 때 주문을 생성한다.
- 생성된 주문의 최초 상태는 `결제대기`다.
- 주문자와 수령인은 같은 사람으로 취급한다.
- 결제대기 주문의 상품, 수량 및 배송지는 변경할 수 없다.
- 이를 바꾸려는 고객은 새 주문을 만들어야 한다.

### 주문 금액

- 각 주문 항목의 금액은 `주문 생성 시점의 판매 단가 × 수량`이다.
- 주문 금액은 모든 주문 항목 금액의 합계다.
- 주문 생성 후 판매가가 변해도 주문 금액은 바뀌지 않는다.
- 카드 승인 요청에는 확정된 주문 금액을 청구한다.
- 배송비, 쿠폰 및 할인은 계산하지 않는다.

### 결제

- 결제 수단은 카드만 허용한다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 카드 승인이 거절되어도 주문을 취소하지 않는다.
- 승인 거절 후 주문을 결제대기로 유지하여 다른 카드로 다시 결제할 수 있게 한다.
- 결제 시스템의 응답을 확정할 수 없으면 이를 성공 또는 실패로 임의 변환하지 않는다.

### 재고

- 재고 판단은 상품 시스템의 판단을 그대로 따른다.
- 주문 시스템은 재고를 별도로 확보하거나 예약하지 않는다.
- 승인 후 재고 부족에 대한 보상 처리는 아직 정하지 않는다.

### 배송 요청

- 카드 승인이 완료되기 전에는 배송을 요청하지 않는다.
- 카드 승인 완료 후에만 배송 시스템에 배송을 요청한다.
- 배송 요청 실패 시 승인 취소, 주문 상태 변경 및 재요청 방식을 임의로 정하지 않는다.

## 5. 대안·예외 흐름

### 카드 승인 거절

1. 결제 시스템이 카드 승인을 거절한다.
2. 주문은 취소되지 않고 결제대기로 남는다.
3. 고객은 다른 카드로 다시 승인 요청을 할 수 있다.

### 결제 응답 불확정

1. 승인 요청 후 성공인지 실패인지 확정할 수 없다.
2. 시스템은 이를 승인 성공이나 승인 실패로 단정하지 않는다.
3. 재결제 허용 여부를 포함한 이후 처리는 미정으로 남긴다.

### 승인 후 재고 부족

1. 카드 승인은 완료되었지만 상품 시스템이 재고 부족으로 판단한다.
2. 승인 취소나 주문 상태 변경을 임의로 수행하지 않는다.
3. 이후 처리는 미정으로 남긴다.

### 승인 후 배송 요청 실패

1. 카드 승인 완료 후 배송을 요청한다.
2. 배송 시스템이 요청을 받지 못하거나 실패를 반환한다.
3. 승인 취소, 주문 상태 변경 또는 재요청을 임의로 수행하지 않는다.
4. 재요청 주체와 방식은 미정으로 남긴다.

## 6. 용어

| 용어 | 의미 |
|---|---|
| 장바구니 | 고객이 주문하려는 상품과 수량을 모아 둔 주문 시작 자료 |
| 배송지 확정 | 고객이 주문에 사용할 배송지를 최종 선택하는 행위이며 주문 생성 시점 |
| 주문 | 확정된 상품, 수량, 배송지, 생성 시점 단가와 주문 금액을 보유하는 업무 기록 |
| 주문 항목 | 주문에 포함된 개별 상품과 그 수량 및 확정 단가 |
| 결제대기 | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태 |
| 주문 금액 | 각 항목의 생성 시점 단가와 수량을 곱한 뒤 합산한 금액 |
| 카드 승인 | 결제 시스템이 해당 카드와 주문 금액의 결제를 허가한 결과 |
| 승인 거절 | 결제 시스템이 카드 결제를 허가하지 않았다고 확정한 결과 |
| 응답 불확정 | 카드 승인 성공 또는 거절 중 어느 쪽인지 확정할 수 없는 상황 |
| 주문 성립 | 카드 승인이 완료된 시점에 발생하는 업무 결과 |
| 재고 판단 | 상품 시스템이 제공하는 주문 가능 여부에 대한 판단 |
| 배송 요청 | 카드 승인 후 배송 시스템에 전달하는 배송 처리 요청 |
| 미정 정책 | 담당자가 아직 결정하지 않았으며 구현이 임의로 보완해서는 안 되는 규칙 |

`결제대기` 외의 구체적인 주문 상태 이름은 주어진 조건에 없으므로 새로 정의하지 않는다.

## 7. 품질 조건

### 업무 규칙 보존

- 주문 금액은 주문 생성 시점 이후의 판매가 변경에 영향을 받지 않아야 한다.
- 카드 승인 전에는 주문이 성립한 것으로 취급하지 않아야 한다.
- 카드 승인 전에는 배송 요청이 발생하지 않아야 한다.
- 승인 거절만으로 주문을 취소하거나 삭제하지 않아야 한다.
- 결제대기 주문의 상품, 수량 또는 배송지를 수정하지 않아야 한다.
- 주문 시스템이 자체적으로 재고를 확보한 것으로 간주하지 않아야 한다.

### 미정 정책 보호

- 결제대기 기한이나 만료 처리를 임의로 추가하지 않아야 한다.
- 불확정 결제 응답을 성공 또는 실패로 임의 확정하지 않아야 한다.
- 승인 후 재고 부족을 이유로 카드 승인을 임의 취소하지 않아야 한다.
- 배송 요청 실패 시 주문 상태, 승인 취소 및 재시도 방식을 임의로 결정하지 않아야 한다.
- 주문 확인 통지의 발송 주체를 임의로 결정하지 않아야 한다.

### 외부 연계 안전성

- 상품 시스템의 판매가와 재고 판단을 주문 시스템이 자의적으로 대체하지 않아야 한다.
- 결제 시스템에서 승인 완료가 확인된 경우에만 주문 성립으로 처리해야 한다.
- 배송 요청은 승인 완료 이후에만 발생해야 한다.
- 외부 시스템의 응답이 모호하면 확정된 응답으로 변환하지 않아야 한다.

### 개발 활용 방식

- 현재 업무 조건 결정은 수작업으로 수행하고, LLM은 질문과 정리만 보조한다.
- 요구·모델·설계·코드·검사 초안은 담당자가 LLM의 답마다 검토한다.
- 미정 사항은 자동화나 구현 편의를 위해 대신 결정하지 않는다.
- 검사와 완료 조건이 마련되고 실제 오류를 잡는다고 사람이 확인하기 전에는 자율 실행으로 전환하지 않는다.
- 릴리스 설명은 확정 범위, 제외 범위 및 미정 사항을 구분하며 공개 전에 사람이 최종 승인한다.
- 운영 시스템과 실제 고객 데이터는 사용하지 않는다.
- 로컬 변경은 Git으로 되돌릴 수 있는 범위에서 수행한다.

[앞선 질문에 대한 답 — 확인된 후속 조건]
두 첨부 문서에 없던 품질·사례 조건은 이번에 담당자가 제공한다. 다음은 실습 3 강사 노트와 Course Design 및 기존 확정 대화에 근거한 답이며, 새로운 운영 정책이 아니다.
- 사례는 주문 생성 시 판매가 1,000원인 펜 2개와 배송지 서울이다. 주문 금액은 2,000원이다. 가격 변경 상황은 주문 생성 뒤 판매가가 1,200원으로 오른 뒤 같은 주문을 결제하는 것이다.
- 카드 X는 거절되고 카드 Y는 승인된다. 승인 뒤 상태명은 결제완료(PAID), 거절 뒤는 결제대기(PENDING_PAYMENT)다. 같은 주문의 식별자를 보존한다.
- 정상 승인과 가격 변경 후 승인에서는 배송 요청 1회, 카드 거절 직후에는 0회, X 거절 뒤 Y 승인까지 전체 과정에서는 총 1회다. 금액은 카드 승인 요청 금액을 확인하며 카드 거절을 청구 완료로 취급하지 않는다.
- 기본 흐름 1 상품 조회, 2 장바구니는 전제이며 상세 범위는 3 배송지 확정, 4 결제, 5 주문 결과 확인이다. 본인 주문만 조회·변경할 권한이 있고 타인의 주문 조회·변경은 거절한다. 본인이라도 결제대기 주문의 상품·수량·배송지는 바꿀 수 없다. 인증 방법과 오류 코드·화면은 정하지 않는다.
- 정상 품질 시험은 외부 상품·결제·배송 시스템이 정상 응답하는 테스트 대역이고 각 응답이 1초 이내인 조건에서 카드 결제 요청 100건을 동시에 실행한다. 결제 요청부터 주문 결과 수신까지 100건 중 95건 이상이 3초 이내여야 한다. 운영 환경의 보장 수치가 아니다.
- 용어 표기는 주문(Order), 주문 항목(OrderItem), 판매가(salePrice), 주문 금액(totalAmount), 결제대기(PENDING_PAYMENT), 결제완료(PAID)다. 판매가는 상품 시스템의 현재 판매 가격이며 주문 생성 때 기록한 항목 단가와 구분한다. 이는 용어이지 설계가 아니다.
- 질문 1~26과 28~30 가운데 위 답으로 확인되지 않은 사항은 미정이다. H·B·F·E·G·I, 재고 판단 시점·호출 횟수, 승인 전 재고 부족의 처리를 새로 결정하지 않는다. 질문 27의 승인 뒤 상태명만 위에서 확정했다.

[추가 질문·수정 요청 — 첫 응답 검토]
기본 흐름 도식은 배송지 확정 전에 재고를 확인하고 재고가 없으면 주문을 진행하지 않는 것으로 고정했다. 그러나 확인 시점과 승인 전 부족 처리는 주어진 조건에 없다. 이 흐름을 확정 절차로 제시하지 마라. 승인 뒤 재고 확인의 호출 순서도 확정하지 마라.
미정 정책을 구현자가 임의로 채우지 못한다는 제약을 영구적인 무동작 정책으로 바꾸지 마라. 담당자 결정 전에는 해당 분기의 최종 수용 기준이 미완성이라고 구분해라. 입력의 기능 제외와 이번 요구사항 문서에서 작성하지 않을 모델·설계·코드 산출물을 구분해라.
사용자 스토리는 ‘주문한다’ 하나로 유지하고, 정상 승인·가격 변경·거절·재결제의 네 대표 상황마다 전제·사건과 동일 주문 여부·주문 금액·승인 요청 금액·상태·누적 배송 요청 횟수가 확인되도록 초안을 보완해라. 한 상황의 재결제를 새 주문 생성으로 바꾸지 마라. 확인된 조건만 반영하고 남은 미정 질문을 보존해라.
