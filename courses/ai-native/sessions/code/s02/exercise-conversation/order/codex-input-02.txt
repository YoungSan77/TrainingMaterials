[실행 환경] 이 실행기는 응답을 그대로 파일로 저장한다. 도구 호출·파일 탐색·파일 쓰기를 하지 마라. 대화창에서 읽을 답을 그대로 출력하고, 도식은 Mermaid 원본으로 보여라.

다음 실제 대화를 이어서 마지막 사용자 메시지에 답하라.

[사용자]
실습 1에서 합의한 업무 조건으로 쇼핑몰의 첫 주문 기능을 개발한다. 개발에 필요한 일 목록을 만들고 각 일의 업무 규칙 확정·절차 확정·결과의 자동 확인·되돌리기 쉬움을 살펴, 수작업·대화형 보조·워크플로·에이전트 중 충분한 가장 단순한 활용 방식을 제안해라. 아직 정하지 않은 조건은 질문하고 정책을 대신 정하지 마라. 대화창에서 검토할 간결한 초안으로 답해라.

[실습 1의 업무 조건]
# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

## 권장 진행 순서

```mermaid
flowchart TD
    A[장바구니 상품 조회] --> B[배송지 확정]
    B --> H{H: 주문 자격과<br/>본인 확인 정책 확정}
    H --> C[결제대기 주문 생성]
    C --> D[생성 시점 가격과 금액 고정]
    D --> E[카드 승인 요청]
    E -->|거절| C
    E -->|응답 불명| F{F: 후속 처리 정책 필요}
    E -->|승인| G[주문 성립]
    G --> J{상품 시스템 재고 판단}
    J -->|재고 없음| K{E: 처리 정책 필요}
    J -->|재고 있음| L[배송 요청]
    L -->|실패| M{G: 실패 처리 정책 필요}
    L -->|성공| N[주문 처리 완료]
    G --> O{I: 확인 통지 주체}
    C -. 기한 도래 .-> P{B: 기한과 후속 처리 정책 필요}
```

정책이 확정되기 전에도 가격 고정, 금액 계산, 주문 불변 조건, 카드 거절 처리와 해당 자동 시험은 개발할 수 있다. 다만 미정 분기는 임의의 성공·실패·취소 상태로 바꾸지 않고 개발 완료 조건에서도 제외해 두어야 한다.

## 먼저 답이 필요한 질문

1. **H—주문 자격:** 비회원 주문을 허용하는가? 허용한다면 결제대기 주문을 다시 찾을 때 어떤 정보와 인증으로 본인을 확인하는가?
2. **B—결제대기:** 기한은 얼마인가? 기한 후 결제를 막는가? 주문 상태를 바꾸는가, 기록을 유지하거나 삭제하는가?
3. **F—결제 응답 불명:** 주문을 어떤 상태로 표시하는가? 결제 시스템에 누가·언제 승인 결과를 재확인하는가? 확인 전 재결제를 허용하는가?
4. **E—승인 뒤 재고 없음:** 주문을 유지하는가? 카드 승인을 취소하는가? 고객 또는 운영자에게 어떤 후속 조치를 요구하는가?
5. **G—배송 요청 실패:** 주문 상태를 바꾸는가? 자동 재요청, 운영자 재요청, 배송 시스템의 재수신 중 누가 책임지는가?
6. **I—주문 확인 통지:** 이 주문 시스템이 보내는가, 결제·배송 등 다른 시스템의 통지로 대신하는가?
7. **재고 판단 시점:** 상품 시스템에 재고 판단을 요청하는 정확한 시점은 카드 승인 전인가, 승인 후인가?
8. **중복 요청:** 고객의 연속 클릭이나 통신 재시도로 같은 주문·승인·배송 요청이 반복될 때, 업무상 한 건으로 보아야 하는 기준은 무엇인가?

이 질문들이 확정되면 미정 항목을 워크플로와 자동 인수시험으로 전환할 수 있다. 에이전트 적용은 자동 판정과 안전한 복구가 모두 약한 현재 단계에서는 불필요하다.

[앞선 질문에 대한 답]
H·B·F·E·G·I는 실습 1에서 의도적으로 미정으로 남겼으므로 지금 결정하지 않는다. 재고 판단 시점과 중복 처리도 이번 활용 방식 판단에서 새로 정하지 않는다. 개발할 일은 확정된 범위와 미정 분기를 구분하면 된다. 운영 결제·배송 호출과 실제 고객 데이터는 쓰지 않고 인터페이스와 테스트 대역만 쓴다. 실습은 빈 로컬 저장소라 데이터 이관은 없다.
[추가 질문·수정 요청]
목록이 기능 흐름의 분기와 미정 질문 위주다. 업무 규칙의 결정·초안 작성·코드 구현·운영 실행을 구분해 첫 기능 개발에 필요한 일 목록으로 고쳐라. 필요한 일은 업무 조건 확인, 요구와 수용 기준, 모델·설계, 저장소 골격, 코드 구현과 검사, 릴리스 설명의 수준에서 간결하게 묶어라. 업무 담당자의 결정은 수작업이고 LLM은 질문·초안을 돕는다고 구분해라. 미정을 자동화해 워크플로로 전환한다고 쓰지 마라. 아직 없는 테스트를 이미 있다고 판정하지 말고 준비 조건으로 표시해라. 개발 절차와 주문 실행 흐름을 혼동하지 말고 도식은 생략해라.
