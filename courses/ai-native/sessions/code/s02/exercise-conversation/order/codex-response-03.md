# 첫 주문 기능 개발 활용 방식 초안

전제: 지금은 활용 방식만 선택한다. 요구사항·모델·인터페이스·검사·완료 조건은 뒤 실습에서 만든다. 미정 정책과 그 분기의 반환값·상태·실패 처리도 설계하지 않는다. 구현은 로컬의 작은 Git 변경이며 운영 시스템과 실제 고객 데이터는 사용하지 않는다.

| 필요한 일 | 업무 규칙 | 절차 | 자동 확인 | 되돌림 | 현재 선택 | 준비 후 선택 |
|---|---|---|---|---|---|---|
| 업무 조건 결정·경계 확인 | 확정 조건과 의도적 미정이 구분됨. 정책 결정은 담당자 책임 | 검토 절차는 아직 미정 | 담당자 검토가 필요 | 문서 초안은 쉬움 | **수작업 결정**, LLM은 질문·정리 보조 | 동일 |
| 요구·모델·설계 초안 | 확정 범위만 반영해야 함 | 뒤 실습에서 확정 | 검사·완료 조건이 아직 없음 | Git으로 쉬움 | **대화형 보조**, 최종 판단은 수작업 | 기준과 검토 절차가 정해져도 대화형 보조가 기본 |
| 저장소 골격 | 기술·구성 규칙이 아직 미정 | 생성 절차와 명령이 아직 없음 | 빌드·검사 명령 준비 필요 | Git으로 쉬움 | **대화형 보조** | 정해진 코드 경로로 LLM과 도구를 조율해야 하면 **워크플로**, 단순 생성이면 일반 자동화 |
| 확정 범위 코드 구현 | 확정 규칙만 구현하고 미정 분기는 정책화하지 않아야 함 | 설계와 작업 절차가 아직 없음 | 수용 기준과 자동 검사 준비 필요 | 작은 Git 변경으로 쉬움 | **대화형 보조** | 설계·검사·완료 조건이 결정적이면 **에이전트**에 위임 가능 |
| 검사 작성·실행 | 무엇을 확인할지는 뒤 실습에서 정함 | 작성·실행 절차가 아직 없음 | 검사 자체를 새로 준비해야 함 | Git으로 쉬움 | 검사 초안은 **대화형 보조**, 실행 조건은 수작업 확인 | 검사 작성은 조건이 충분하면 **에이전트** 가능. `gradle check` 같은 실행은 **일반 자동화** |
| 릴리스 설명 | 확정 범위, 제외 범위, 미정 사항을 구분해야 함 | 작성·승인 절차가 아직 없음 | 실제 검사 결과와 변경 내역 필요 | 문서 변경은 쉬움 | **대화형 보조**, 승인은 수작업 | 자료 수집 경로가 정형화되면 **워크플로** 가능 |

현재 가장 단순한 선택은 **담당자의 수작업 결정·검토 + LLM 대화형 초안 작성**이다. 아직 결정적인 설계·검사·완료 조건이 없으므로 에이전트에 맡길 일은 고르지 않는다.

준비 후에는 선택이 달라질 수 있다.

- **에이전트:** 명확한 작업 지시, 자동 검사, 완료 조건, Git 되돌림이 갖춰진 코드·검사 작성
- **워크플로:** LLM과 여러 도구를 미리 정한 코드 경로로 조율해야 하는 반복 작업
- **일반 자동화:** 빌드나 `gradle check`처럼 판단 없이 정해진 명령을 실행하는 작업

따라서 에이전트 사용 여부는 작업 크기보다 **규칙·절차·자동 확인·되돌림의 준비 정도**로 판단한다.
