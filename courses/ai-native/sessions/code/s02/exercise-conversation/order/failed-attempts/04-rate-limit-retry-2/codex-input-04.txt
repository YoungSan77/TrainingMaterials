[실습 1의 업무 조건]
# "주문한다" 업무 조건

## 범위
- 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
- 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
- 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

## 주문 생성
- 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
- 주문자와 수령인은 같은 사람으로 본다.
- [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

## 주문 금액
- 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
- 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

## 결제대기
- 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
- 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
- [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

## 결제와 주문 성립
- 결제 수단은 카드뿐이다.
- 카드 승인이 완료된 때 주문이 성립한다.
- 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
- [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

## 재고
- 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
- [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

## 배송 요청
- 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
- [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
- [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

## 권장 진행 순서

```mermaid
flowchart TD
    A[장바구니 상품 조회] --> B[배송지 확정]
    B --> H{H: 주문 자격과<br/>본인 확인 정책 확정}
    H --> C[결제대기 주문 생성]
    C --> D[생성 시점 가격과 금액 고정]
    D --> E[카드 승인 요청]
    E -->|거절| C
    E -->|응답 불명| F{F: 후속 처리 정책 필요}
    E -->|승인| G[주문 성립]
    G --> J{상품 시스템 재고 판단}
    J -->|재고 없음| K{E: 처리 정책 필요}
    J -->|재고 있음| L[배송 요청]
    L -->|실패| M{G: 실패 처리 정책 필요}
    L -->|성공| N[주문 처리 완료]
    G --> O{I: 확인 통지 주체}
    C -. 기한 도래 .-> P{B: 기한과 후속 처리 정책 필요}
```

정책이 확정되기 전에도 가격 고정, 금액 계산, 주문 불변 조건, 카드 거절 처리와 해당 자동 시험은 개발할 수 있다. 다만 미정 분기는 임의의 성공·실패·취소 상태로 바꾸지 않고 개발 완료 조건에서도 제외해 두어야 한다.

## 먼저 답이 필요한 질문

1. **H—주문 자격:** 비회원 주문을 허용하는가? 허용한다면 결제대기 주문을 다시 찾을 때 어떤 정보와 인증으로 본인을 확인하는가?
2. **B—결제대기:** 기한은 얼마인가? 기한 후 결제를 막는가? 주문 상태를 바꾸는가, 기록을 유지하거나 삭제하는가?
3. **F—결제 응답 불명:** 주문을 어떤 상태로 표시하는가? 결제 시스템에 누가·언제 승인 결과를 재확인하는가? 확인 전 재결제를 허용하는가?
4. **E—승인 뒤 재고 없음:** 주문을 유지하는가? 카드 승인을 취소하는가? 고객 또는 운영자에게 어떤 후속 조치를 요구하는가?
5. **G—배송 요청 실패:** 주문 상태를 바꾸는가? 자동 재요청, 운영자 재요청, 배송 시스템의 재수신 중 누가 책임지는가?
6. **I—주문 확인 통지:** 이 주문 시스템이 보내는가, 결제·배송 등 다른 시스템의 통지로 대신하는가?
7. **재고 판단 시점:** 상품 시스템에 재고 판단을 요청하는 정확한 시점은 카드 승인 전인가, 승인 후인가?
8. **중복 요청:** 고객의 연속 클릭이나 통신 재시도로 같은 주문·승인·배송 요청이 반복될 때, 업무상 한 건으로 보아야 하는 기준은 무엇인가?

이 질문들이 확정되면 미정 항목을 워크플로와 자동 인수시험으로 전환할 수 있다. 에이전트 적용은 자동 판정과 안전한 복구가 모두 약한 현재 단계에서는 불필요하다.

[앞선 질문에 대한 답]
H·B·F·E·G·I는 실습 1에서 의도적으로 미정으로 남겼으므로 지금 결정하지 않는다. 재고 판단 시점과 중복 처리도 이번 활용 방식 판단에서 새로 정하지 않는다. 개발할 일은 확정된 범위와 미정 분기를 구분하면 된다. 운영 결제·배송 호출과 실제 고객 데이터는 쓰지 않고 인터페이스와 테스트 대역만 쓴다. 실습은 빈 로컬 저장소라 데이터 이관은 없다.
[추가 질문·수정 요청]
목록이 기능 흐름의 분기와 미정 질문 위주다. 업무 규칙의 결정·초안 작성·코드 구현·운영 실행을 구분해 첫 기능 개발에 필요한 일 목록으로 고쳐라. 필요한 일은 업무 조건 확인, 요구와 수용 기준, 모델·설계, 저장소 골격, 코드 구현과 검사, 릴리스 설명의 수준에서 간결하게 묶어라. 업무 담당자의 결정은 수작업이고 LLM은 질문·초안을 돕는다고 구분해라. 미정을 자동화해 워크플로로 전환한다고 쓰지 마라. 아직 없는 테스트를 이미 있다고 판정하지 말고 준비 조건으로 표시해라. 개발 절차와 주문 실행 흐름을 혼동하지 말고 도식은 생략해라.

# 첫 주문 기능 개발 활용 방식 초안

전제: H·B·F·E·G·I, 재고 판단 시점, 중복 처리는 이번에 결정하지 않는다. 외부 시스템은 인터페이스와 테스트 대역만 사용하며, 실제 고객 데이터와 데이터 이관은 없다.

| 필요한 일 | 규칙·절차 상태 | 자동 확인 준비 조건 | 되돌리기 | 활용 방식 |
|---|---|---|---|---|
| 업무 조건 확인 및 미정 경계 표시 | 업무 담당자가 확정 조건과 의도적 미정을 확인해야 함 | 조건 목록과 미정 분기 검토표 작성 필요 | 쉬움 | **수작업 결정 + 대화형 보조로 질문·정리** |
| 요구사항과 수용 기준 초안 | 확정 조건만 기준화하고 미정 사항은 판정 대상에서 제외 | 정상 승인, 카드 거절, 가격 고정, 주문 변경 금지 등의 수용 기준과 테스트 사례를 새로 작성해야 함 | 쉬움 | **대화형 보조** |
| 주문 모델과 인터페이스 설계 | 상태·금액 규칙은 일부 확정, 미정 분기는 열린 상태로 표현해야 함 | 설계 검토 기준과 외부 시스템 계약 대역 필요 | 쉬움 | **대화형 보조**, 최종 선택은 **수작업** |
| 개발 절차와 작업 순서 확정 | 빈 로컬 저장소 기준으로 정할 수 있음 | 빌드·검사 명령과 완료 기준을 정의해야 함 | 쉬움 | **대화형 보조**, 반복 절차는 이후 **워크플로** |
| 저장소 골격 구성 | 기술 선택 후 절차화 가능 | 실행, 정적 검사, 단위 테스트가 동작하도록 처음 구성해야 함 | 쉬움 | 초기에는 **대화형 보조**, 명령이 고정되면 **워크플로** |
| 확정 범위 코드 구현 | 가격 고정, 금액 계산, 결제대기 생성·변경 금지, 승인·거절 처리, 승인 후 배송 인터페이스 호출까지 구현 | 구현 전 수용 기준과 테스트 대역 필요 | 변경 단위가 작으면 쉬움 | **대화형 보조** |
| 미정 분기 안전하게 표현 | 정책을 대신 결정하지 않고 불명·미처리 결과를 보존해야 함 | 미정 분기에서 임의의 성공·실패·취소가 발생하지 않는 테스트 필요 | 비교적 쉬움 | **대화형 보조**, 판단은 **수작업 검토** |
| 테스트 대역과 자동 검사 작성 | 운영 결제·배송 호출 없이 정해진 반응을 재현 | 테스트 코드와 기대 결과를 새로 작성해야 함. 현재 테스트가 있다고 전제하지 않음 | 쉬움 | 작성은 **대화형 보조**, 실행은 **워크플로** |
| 코드·요구사항 일치 검토 | 확정 조건 준수와 미정 정책의 잠입 여부를 사람이 판단 | 추적표, 테스트 결과, 변경 내역 필요 | 쉬움 | **수작업 검토 + 대화형 보조** |
| 릴리스 설명 작성 | 구현 범위, 제외 범위, 미정 사항, 테스트 대역 사용을 명시 | 빌드·검사 결과와 알려진 제한을 수집해야 함 | 쉬움 | **대화형 보조**, 공개 승인은 **수작업** |

## 방식 구분

- **수작업:** 업무 조건의 결정, 설계안의 최종 선택, 미정 정책이 들어가지 않았는지 검토, 릴리스 승인
- **대화형 보조:** 질문 정리, 요구·수용 기준·설계·코드·테스트·릴리스 설명의 초안 작성
- **워크플로:** 저장소에 실제로 마련된 빌드, 정적 검사, 단위·통합 테스트의 반복 실행
- **에이전트:** 이번 범위에는 불필요하다. 작업 범위가 작고, 정책 판단은 담당자에게 남겨야 하며, 운영 시스템 실행도 하지 않는다.

미정 사항은 향후 자동화 대상으로 간주하지 않고, 이번 구현에서 명시적으로 보존해야 할 경계로 다룬다. 가장 단순한 구성은 **담당자의 수작업 결정·검토 + LLM 대화형 초안 작성 + 준비된 검사만 워크플로로 반복 실행**이다.
[사용자]
[앞선 질문에 대한 답]
검사·설계·완료条件은 뒤 실습에서 만든다. 지금은 활용 방식 선택을 위한 준비 조건만 적는다. 업무 정책은 미정으로 유지하며 미정 분기의 반환값·새 상태·실패 처리도 여기서 설계하지 않는다. 구현은 로컬의 작은 변경이고 Git으로 되돌릴 수 있다.
[추가 질문·수정 요청]
에이전트로 고른 일이 없다면 억지로 추가하지 마라. 다만 '범위가 작아서 에이전트가 불필요'라는 일반화는 고쳐라. 자동 검사와 되돌림이 준비되면 작은 코드 작업도 에이전트에 맡길 수 있다. 현재와 준비 후의 선택을 구분해라. 반대로 gradle check 같은 결정적인 검사 명령 자체는 LLM 워크플로가 아니라 일반 자동화다. 워크플로는 LLM과 도구를 미리 정한 코드 경로로 조율할 때만 쓰는 용어다. 일이 너무 세분됐다. 업무 조건 결정, 요구·모델·설계 초안, 저장소 골격, 확정 범위 코드 구현, 검사 작성·실행, 릴리스 설명 수준으로 묶고 업무 규칙·절차·자동 확인·되돌림 네 특성을 빠뜨리지 마라. 뒤 실습의 요구사항·모델·인터페이스를 지금 만들지는 마라.

# 첫 주문 기능 개발 활용 방식 초안

전제: 지금은 활용 방식만 선택한다. 요구사항·모델·인터페이스·검사·완료 조건은 뒤 실습에서 만든다. 미정 정책과 그 분기의 반환값·상태·실패 처리도 설계하지 않는다. 구현은 로컬의 작은 Git 변경이며 운영 시스템과 실제 고객 데이터는 사용하지 않는다.

| 필요한 일 | 업무 규칙 | 절차 | 자동 확인 | 되돌림 | 현재 선택 | 준비 후 선택 |
|---|---|---|---|---|---|---|
| 업무 조건 결정·경계 확인 | 확정 조건과 의도적 미정이 구분됨. 정책 결정은 담당자 책임 | 검토 절차는 아직 미정 | 담당자 검토가 필요 | 문서 초안은 쉬움 | **수작업 결정**, LLM은 질문·정리 보조 | 동일 |
| 요구·모델·설계 초안 | 확정 범위만 반영해야 함 | 뒤 실습에서 확정 | 검사·완료 조건이 아직 없음 | Git으로 쉬움 | **대화형 보조**, 최종 판단은 수작업 | 기준과 검토 절차가 정해져도 대화형 보조가 기본 |
| 저장소 골격 | 기술·구성 규칙이 아직 미정 | 생성 절차와 명령이 아직 없음 | 빌드·검사 명령 준비 필요 | Git으로 쉬움 | **대화형 보조** | 정해진 코드 경로로 LLM과 도구를 조율해야 하면 **워크플로**, 단순 생성이면 일반 자동화 |
| 확정 범위 코드 구현 | 확정 규칙만 구현하고 미정 분기는 정책화하지 않아야 함 | 설계와 작업 절차가 아직 없음 | 수용 기준과 자동 검사 준비 필요 | 작은 Git 변경으로 쉬움 | **대화형 보조** | 설계·검사·완료 조건이 결정적이면 **에이전트**에 위임 가능 |
| 검사 작성·실행 | 무엇을 확인할지는 뒤 실습에서 정함 | 작성·실행 절차가 아직 없음 | 검사 자체를 새로 준비해야 함 | Git으로 쉬움 | 검사 초안은 **대화형 보조**, 실행 조건은 수작업 확인 | 검사 작성은 조건이 충분하면 **에이전트** 가능. `gradle check` 같은 실행은 **일반 자동화** |
| 릴리스 설명 | 확정 범위, 제외 범위, 미정 사항을 구분해야 함 | 작성·승인 절차가 아직 없음 | 실제 검사 결과와 변경 내역 필요 | 문서 변경은 쉬움 | **대화형 보조**, 승인은 수작업 | 자료 수집 경로가 정형화되면 **워크플로** 가능 |

현재 가장 단순한 선택은 **담당자의 수작업 결정·검토 + LLM 대화형 초안 작성**이다. 아직 결정적인 설계·검사·완료 조건이 없으므로 에이전트에 맡길 일은 고르지 않는다.

준비 후에는 선택이 달라질 수 있다.

- **에이전트:** 명확한 작업 지시, 자동 검사, 완료 조건, Git 되돌림이 갖춰진 코드·검사 작성
- **워크플로:** LLM과 여러 도구를 미리 정한 코드 경로로 조율해야 하는 반복 작업
- **일반 자동화:** 빌드나 `gradle check`처럼 판단 없이 정해진 명령을 실행하는 작업

따라서 에이전트 사용 여부는 작업 크기보다 **규칙·절차·자동 확인·되돌림의 준비 정도**로 판단한다.

[앞선 질문에 대한 답]
현재는 담당자가 결정하고 LLM 초안을 매번 확인하는 방식으로 충분하다. 지금 에이전트를 쓸 필요는 없다. 뒤 실습에서 검사가 생겨도 실제로 오류를 잡는지 사람이 확인한 뒤 전환 여부를 판단한다. 코드 변경은 Git으로 되돌리되 외부 부작용은 이 실습에 없다.
[추가 질문·수정 요청]
표현을 고쳐라. '완료 조건이 결정적' 대신 '완료 조건이 명확하고 자동 검사로 판정 가능'이라고 해라. 에이전트는 절차를 사전에 고정할 수 없어 실행 결과로 다음 행동을 정해야 할 때 검토한다. 절차를 고정할 수 있으면 워크플로 또는 일반 자동화로 충분하다. 자율성이 높다고 좋은 것이 아니다. 현재 선택의 근거에 비용과 사람의 확인 시점을 짧게 더해라. 대화형 보조는 답마다, 워크플로는 정한 단계마다, 에이전트는 종료·중단 시점에 사람이 확인한다. 단가·횟수·시간은 아직 재지 않았으니 수치를 만들지 마라. 최종 문서는 여섯 일만 남기고 준비 후 선택은 조건부로 써라. 표 대신 일별 짧은 목록으로 정리할 수 있다. 요구·모델·코드 내용은 만들지 마라.
