[실행 환경] 이 실행기는 응답을 그대로 파일로 저장한다. 도구 호출·파일 탐색·파일 쓰기를 하지 마라. 대화창에서 읽을 답을 그대로 출력하고, 도식은 Mermaid 원본으로 보여라.

[사용자]
쇼핑몰의 주문 시스템을 빈 저장소에서 새로 만든다. 업무 담당자의 요청은 "장바구니에 담은 상품을 결제하면 주문이 되고 배송이 시작되게 해 주세요" 한 줄이다. 요구사항을 정의하기 전에 내가 정해야 할 업무 조건은 무엇인가?

[실제 응답]
# 주문 시스템 요구사항 정의 전에 정해야 할 업무 조건

"장바구니에 담은 상품을 결제하면 주문이 되고 배송이 시작되게 해 주세요"라는 요청에는 모든 것이 잘 될 때의 흐름 하나만 들어 있습니다. 요구사항을 쓰기 전에 다음 세 가지를 업무 담당자와 합의해야 합니다.

1. 요청에 나온 말이 각각 무엇을 뜻하는지
2. 상태가 바뀌는 시점이 언제인지
3. 일이 잘못됐을 때 어떻게 처리하는지

이 셋을 정하지 않으면 개발자가 코드를 짜면서 업무 정책을 임의로 정하게 됩니다.

---

## 1. 범위: 무엇을 만들고 무엇과 연동하는가

빈 저장소에서 시작하므로 "주문 시스템"이 어디까지인지부터 정해야 합니다.

```mermaid
flowchart LR
    Customer([고객]) --> Cart[장바구니]
    Cart --> Order[주문]
    Order <--> PG[[결제대행사 PG]]
    Order --> Stock[(상품·재고)]
    Order --> Fulfill[출고·배송 관리]
    Fulfill <--> Carrier[[택배사 / 3PL]]
    Admin([운영자]) --> Order
    Admin --> Fulfill

    classDef core fill:#dbeafe,stroke:#2563eb
    classDef unknown fill:#fef3c7,stroke:#d97706,stroke-dasharray:4 3
    classDef external fill:#f3f4f6,stroke:#6b7280
    class Order core
    class Cart,Stock,Fulfill unknown
    class PG,Carrier external
```

파란색은 확실히 만드는 범위, 점선 노란색은 범위가 미정인 부분, 회색은 외부 시스템입니다.

| 정할 것 | 왜 필요한가 |
|---|---|
| 장바구니, 상품, 재고, 회원 관리도 이번에 만드는가, 아니면 이미 있는가 | 이미 있으면 연동 규격이 필요하고, 없으면 해당 기능의 요구사항이 따로 필요합니다. |
| 비회원 주문을 허용하는가 | 주문 조회 방식, 본인 확인, 개인정보 처리가 달라집니다. |
| 판매자가 우리 하나인가, 여러 판매자가 입점하는 마켓인가 | 주문 분리, 정산, 배송 주체가 완전히 달라집니다. |
| 배송은 자체 물류, 3PL(물류 대행), 판매자 직배송 중 무엇인가 | "배송 시작"을 누가 실행하는지가 여기서 결정됩니다. |
| 반품, 교환, 정산도 이번 범위인가 | 보통 2단계로 미루지만, 미룬다는 결정 자체를 명시해야 합니다. |

## 2. 용어 정의: 요청 문장의 단어마다 뜻이 여러 가지다

| 요청의 표현 | 가능한 해석 | 정해야 할 것 |
|---|---|---|
| "장바구니에 담은 상품" | 장바구니 전체 / 고른 상품만 | 일부 상품만 주문할 수 있는가 |
| "결제하면" | 결제 버튼을 누른 때 / PG 승인 / 무통장입금 확인 | 결제 완료의 기준이 되는 사건 |
| "주문이 되고" | 결제 전에 주문서 생성 / 결제 승인 후 주문 확정 | 결제 전 단계의 주문을 "주문"으로 볼 것인가 |
| "배송이 시작" | 출고 지시 / 포장 완료 / 송장 발행 / 택배사 집하 | 고객에게 "배송 중"으로 보여 주는 시점 |
| "~되게 해 주세요" | 자동 처리 / 운영자 확인 후 처리 | 사람이 개입하는 단계가 있는가 |

## 3. 주문 상태와 전이 시점

요청 문장을 상태 흐름으로 그리면 결정되지 않은 곳이 드러납니다. 아래 그림의 Q 표시가 모두 업무 담당자에게 물어야 할 질문입니다.

```mermaid
stateDiagram-v2
    state "주문서 생성" as Created
    state "결제 대기" as PaymentPending
    state "결제 완료" as Paid
    state "출고 준비" as Preparing
    state "배송 중" as Shipping
    state "배송 완료" as Delivered
    state "구매 확정" as Confirmed
    state "취소" as Cancelled

    [*] --> Created: 결제 버튼 클릭 (Q1 이때부터 주문인가)
    Created --> PaymentPending: PG 결제창 진입
    PaymentPending --> Paid: PG 승인 또는 입금 확인
    PaymentPending --> Cancelled: 실패 또는 시간 초과 (Q2 몇 분, 무통장은 며칠)
    Paid --> Preparing: 배송 시작 (Q3 자동인가 사람이 하는가)
    Paid --> Cancelled: 고객 취소 (Q4 즉시 환불인가 승인 후 환불인가)
    Preparing --> Cancelled: 출고 전 취소 (Q5 허용하는가)
    Preparing --> Shipping: 송장 등록 또는 집하 (Q6 어느 사건이 기준인가)
    Shipping --> Delivered: 배송 완료 (Q7 택배사 연동인가 수동인가)
    Delivered --> Confirmed: 구매 확정 (Q8 자동 확정 기간)
    Confirmed --> [*]
    Cancelled --> [*]
```

이 상태 목록과 각 전이를 누가(고객, 운영자, 시스템, 외부 연동) 일으키는지를 확정하면 요구사항의 뼈대가 됩니다.

## 4. 금액과 재고 정책

| 정할 것 | 선택지 예시 |
|---|---|
| 가격 확정 시점 | 장바구니에 담을 때의 가격 / 결제할 때의 가격. 담은 뒤 가격이 바뀌면 고객에게 알리는가 |
| 할인 수단 | 쿠폰, 적립금, 즉시할인을 쓰는가. 같이 쓸 수 있는가. 취소하면 돌려주는가 |
| 배송비 | 무료배송 기준 금액, 도서산간 추가비, 묶음배송 기준 |
| 재고 차감 시점 | 장바구니에 담을 때 / 주문서 생성 때 / 결제 완료 때 |
| 재고 선점 시간 | 결제창에 들어간 뒤 몇 분 동안 재고를 잡아 두는가 |
| 결제 중 품절 | 결제를 막는가 / 결제 후 취소·환불하는가 / 예약 주문으로 받는가 |
| 구매 수량 제한 | 1인당 최대 수량, 최소 주문 금액 |

## 5. 결제 정책과 예외

장애와 민원은 대부분 결제 실패 쪽에서 생깁니다.

| 정할 것 | 왜 필요한가 |
|---|---|
| 결제 수단: 카드, 간편결제, 계좌이체, 무통장입금, 후불 | 무통장입금이 있으면 "입금 대기" 상태와 입금 기한이 생깁니다. |
| 결제는 승인됐는데 주문 저장이 실패하면 | 자동 취소할지 운영자가 수동으로 맞출지 정해야 합니다. 대사(PG 거래 내역과 주문 대조) 주기도 필요합니다. |
| 같은 주문을 두 번 결제하면 (더블클릭, 네트워크 재시도) | 막는 방식과 이미 중복 결제됐을 때 환불 절차를 정해야 합니다. |
| 분할 결제(여러 결제 수단을 섞어 결제)를 허용하는가 | 부분 취소와 환불 금액 계산이 복잡해집니다. |
| 결제 실패 후 다시 시도할 때 | 같은 주문을 쓸지 새 주문을 만들지 정해야 합니다. |

## 6. 주문 단위와 배송

| 정할 것 | 왜 필요한가 |
|---|---|
| 한 주문의 상품이 여러 창고나 판매자에 있으면 | 배송을 나눌지 한 번에 보낼지, 일부만 배송할 수 있는지 정해야 합니다. |
| 출고 마감 시간 (예: 오후 2시 결제분까지 당일 출고) | 고객에게 안내하는 출고 예정일을 계산하는 데 씁니다. |
| 배송 불가 지역, 예약 배송, 희망 배송일 | 주문을 받을 때 검증해야 할 항목이 됩니다. |
| 배송지와 주문 내용을 언제까지 바꿀 수 있는가 | 출고 준비에 들어간 뒤에는 막을지 정해야 합니다. |
| 송장은 누가 만드는가 | 택배사 API 연동인지 운영자가 직접 입력하는지 정해야 합니다. |

## 7. 취소, 환불, 청약철회

| 정할 것 | 비고 |
|---|---|
| 고객이 직접 취소할 수 있는 마지막 상태 | 위 상태도의 Q4, Q5 |
| 부분 취소 허용 여부 | 쿠폰과 배송비를 어떻게 다시 계산할지도 같이 정해야 합니다. |
| 환불 시점 | 취소 즉시 / 반품 상품 회수 확인 후 |
| 청약철회 | 전자상거래법상 원칙적으로 상품을 받은 날부터 7일 이내 철회할 수 있습니다. 예외 상품(신선식품, 주문제작 등)이 있는지 확인해야 합니다. |

## 8. 사람과 알림

- 역할: 고객, CS 상담원, 운영자, 물류 담당자가 각각 무엇을 보고 무엇을 바꿀 수 있는지 정합니다.
- 알림: 어느 상태로 바뀔 때 누구에게 무엇으로 보내는지 정합니다(문자, 알림톡, 이메일).
- 운영자 권한: 운영자가 상태를 강제로 바꿀 수 있는지, 그 이력을 남기는지 정합니다.

## 9. 법규와 비기능 조건

- 기록 보존: 전자상거래법상 계약·청약철회 기록과 대금결제·재화공급 기록은 5년, 소비자 불만·분쟁 처리 기록은 3년 보존해야 합니다. 개인정보는 보존 기간이 지나면 파기해야 합니다.
- 카드 정보: 카드 정보를 직접 저장하지 않고 PG에 위임하는지 확인합니다. 직접 저장하면 보안 요구 수준이 크게 올라갑니다.
- 처리 규모: 평소와 행사 때의 시간당 주문 수, 한정 수량 판매(선착순 등)를 하는지 확인합니다. 재고 동시성 설계가 여기에 따라 달라집니다.
- 장애 허용 범위: PG나 택배사 연동이 멈췄을 때 주문 접수를 계속 받을지 정합니다.

## 먼저 정해야 할 5가지

나머지 항목은 이 다섯 가지 결정에 따라 정해집니다.

1. **범위와 판매 구조**: 우리가 직접 판매하는지 입점 판매자가 있는지, 배송 주체가 누구인지, 이번에 만드는 시스템이 어디까지인지
2. **주문 성립 시점**: 결제 승인 전에 주문을 만드는지, 결제 완료를 판단하는 기준이 무엇인지
3. **배송 시작의 정의와 실행 주체**: 자동인지 사람이 하는지, 어느 사건을 기준으로 하는지
4. **재고 차감 시점과 품절 처리**
5. **취소할 수 있는 마지막 상태와 환불 방식**

업무 담당자와 회의할 때는 각 항목을 "질문 / 선택지 / 결정 / 결정한 사람 / 날짜"가 들어간 표로 기록하세요. 그 표가 그대로 요구사항 문서의 업무 규칙 절이 됩니다.
[사용자]
고객이 배송지를 정하고 카드로 결제까지 마치는 범위만 다루자. 상품·결제·배송은 이미 운영 중인 외부 시스템이며 화면과 기술 설계는 제외해라.

# 배송지 지정부터 카드 결제 완료까지: 요구사항 정의 전에 정할 업무 조건

범위를 다음과 같이 좁혔습니다.

- **다루는 것**: 고객이 장바구니에서 주문을 시작해 배송지를 정하고 카드 결제를 마쳐 주문이 성립할 때까지
- **외부 시스템(이미 운영 중)**: 상품(가격·재고), 결제(카드 승인), 배송
- **제외**: 화면 구성, 기술 설계, 결제 후의 배송 진행, 취소·환불·반품, 카드 외 결제 수단

그래서 이번에 정할 것은 크게 두 가지입니다. 하나는 **이 구간 안의 업무 규칙**이고, 다른 하나는 **외부 시스템과 책임을 어떻게 나누는지**입니다.

## 1. 범위 경계: 무엇을 판단하고 무엇을 외부에 맡기는가


외부 시스템이 이미 있으므로 "어느 시스템의 판단을 최종으로 보는가"를 업무 담당자와 정해야 합니다.

| 정할 것 | 예시 선택지 |
|---|---|
| 판매 가격의 기준 | 상품 시스템이 결제 시점에 알려 주는 가격 / 장바구니에 담을 때의 가격 |
| 재고 판단의 기준 | 상품 시스템의 판단을 그대로 따름 / 주문 쪽에서 별도 기준을 둠 |
| 배송 가능 지역과 배송비를 정하는 쪽 | 배송 시스템 / 주문 쪽 업무 규칙 |
| 결제 성공의 기준 | 결제 시스템의 승인 결과 하나만 인정하는가 |
| 주문 성립 후 배송 시스템에 넘기는 시점과 내용 | 결제 완료 즉시 / 운영자 확인 후. 넘기는 항목(배송지, 상품, 수량, 요청사항) |

## 2. 용어 정의

| 용어 | 정해야 할 것 |
|---|---|
| 주문 시작 | 장바구니 전체를 주문하는가, 고객이 고른 상품만 주문하는가 |
| 주문 성립 | 카드 승인이 완료된 때인가, 승인 후 재고 확정까지 끝난 때인가 |
| 결제 완료 | 카드 승인 시점과 같은가 (매입 시점과는 구분) |
| 주문자와 수령인 | 같은 사람이어야 하는가, 선물 주문처럼 다를 수 있는가 |
| 카드 결제 | 신용·체크카드만인가, 카드 기반 간편결제도 포함하는가. 법인카드와 해외 발급 카드도 받는가 |

## 3. 주문 접수 상태와 전이 시점

Q로 표시한 곳이 업무 담당자에게 확인할 질문입니다.

```mermaid
stateDiagram-v2
    state "주문서 작성 중" as Drafting
    state "배송지 확정" as AddressSet
    state "결제 진행 중" as Paying
    state "주문 성립" as Placed
    state "결제 실패" as Failed
    state "주문 포기" as Abandoned

    [*] --> Drafting: 장바구니에서 주문 시작 (Q1 이때 주문 번호를 주는가)
    Drafting --> AddressSet: 배송 가능 확인 완료 (Q2 배송 불가 시 일부 상품만 진행 가능한가)
    AddressSet --> Drafting: 배송지 변경
    AddressSet --> Paying: 최종 금액 확인 후 결제 요청 (Q3 이 시점에 재고를 잡는가)
    Paying --> Placed: 카드 승인 (Q4 승인 후 재고 부족이면 어떻게 하는가)
    Paying --> Failed: 승인 거절 또는 응답 없음 (Q5 응답이 없으면 실패로 보는가)
    Failed --> Paying: 재시도 (Q6 횟수 제한, 같은 주문으로 재시도하는가)
    Drafting --> Abandoned: 이탈 (Q7 주문서를 얼마 동안 유지하는가)
    Failed --> Abandoned: 이탈
    Placed --> [*]: 배송 시스템에 전달 (Q8 자동인가 확인 후인가)
    Abandoned --> [*]
```

## 4. 배송지 조건

| 정할 것 | 왜 필요한가 |
|---|---|

| 필수 입력 항목 | 수령인 이름, 연락처, 주소, 우편번호, 배송 요청사항 중 무엇이 필수인지 정합니다. |

| 한 주문에 배송지를 여러 개 지정할 수 있는가 | 지정할 수 있으면 주문 하나를 여러 배송 건으로 나눠야 합니다. |

## 8. 주문 성립 직후의 처리

이번 범위의 마지막 단계이므로 다음을 정해야 합니다.

- **주문 확인 통지**: 누구에게, 어떤 수단(문자, 알림톡, 이메일)으로, 어떤 내용을 보내는지 정합니다. 통지가 이번 범위에 들어가는지도 정합니다.
- **배송 시스템에 전달하지 못했을 때**: 주문은 성립했는데 전달이 실패하면 누가 언제 다시 처리하는지 정합니다.
- **운영자 확인 단계**: 고액 주문이나 의심 주문을 운영자가 확인한 뒤 넘기는 절차가 필요한지 정합니다.

## 9. 법규 조건

- **결제 전 고지와 확인**: 전자상거래법에 따라 결제 전에 상품, 가격, 배송비, 청약철회 조건 같은 거래 조건을 알리고, 고객이 주문 내용을 확인하고 정정할 기회를 줘야 합니다. 고지할 항목 목록을 업무 담당자와 확정하세요.
- **주문 확인 통지**: 청약을 받았다는 사실을 고객에게 지체 없이 알려야 합니다(8절과 연결).
- **기록 보존**: 계약·대금결제 기록은 5년 동안 보존해야 합니다. 이 기록을 주문 쪽과 결제 시스템 중 어디서 보존하는지 정합니다.
- **개인정보**: 수령인 정보를 배송 시스템에 넘기는 것이 동의받은 이용 범위에 들어가는지, 비회원 정보는 얼마 동안 보존하는지 정합니다.

## 지금 꼭 정해야 할 조건

### A. "주문이 생기는 때"가 언제인가

- **정할 것**: 주문서에 들어간 때, 배송지를 확정한 때, 처음 결제를 요청한 때 가운데 어느 때를 주문 생성으로 보는지 정합니다.
- **이유**: "주문이 생길 때의 판매가로 청구한다"는 결정은 이 시점이 정해져야 적용할 수 있습니다. 시점에 따라 고정되는 가격이 달라지고, 결제대기 상태가 시작되는 때와 주문 번호를 주는 때도 달라집니다.

### B. 결제대기를 얼마 동안 유지하고, 끝나면 어떻게 하는가

- **정할 것**: 결제대기를 유지하는 기한, 기한이 지났을 때 주문을 처리하는 방법, 고객이 결제대기 주문을 직접 포기할 수 있는지 정합니다.
- **이유**: 거절돼도 주문을 취소하지 않고 결제대기로 남기기로 했으므로, 기한이 없으면 결제대기가 끝나지 않습니다. 그러면 판매가가 올라도 예전 가격으로 언제든 결제할 수 있습니다. 미결제 주문이 계속 쌓이고 재고 판단도 낡은 정보가 됩니다.
- **참고**: 결제하지 않은 주문을 끝내는 일은 환불이 없으므로, 범위에서 뺀 "취소·환불"과 다릅니다. 이번 범위에 넣어야 합니다.

### C. 고정되는 "주문 금액"에 무엇이 들어가는가

- **정할 것**
  - 판매가만 고정하는지, 배송비도 고정하는지 정합니다.
  - 쿠폰이나 할인이 이번 범위에 들어가는지 정합니다.
  - 결제 전에 판매가가 **내려간** 경우를 정합니다.
- **이유**: 지금 결정은 판매가가 오른 경우만 다룹니다. 가격이 내렸는데 주문할 때의 높은 금액을 청구하면 민원이 생기기 쉬우므로, 내렸을 때 어떻게 할지도 명시해야 합니다. 배송비는 배송지에 따라 달라지므로 D와도 이어집니다.

### D. 결제대기 중에 주문 내용을 바꿀 수 있는가

- **정할 것**: 결제대기 중에 배송지, 수량, 상품을 바꿀 수 있는지 정합니다. 선택지는 다음과 같습니다.
  - 아무것도 바꿀 수 없고, 바꾸려면 새 주문을 만든다.
  - 배송지만 바꿀 수 있다.
  - 모두 바꿀 수 있다.
- **이유**: 내용을 바꿀 수 있으면 새로 담은 상품을 어느 시점 가격으로 청구할지, 바뀐 배송지의 배송비를 다시 계산할지를 정해야 합니다. 바꿀 수 없게 하면 A~C의 규칙이 단순해집니다.

### E. 재고는 언제 확인하고, 승인 뒤 재고가 없으면 어떻게 하는가

- **정할 것**
  - 재고를 확인하는 시점(주문 생성 때, 결제 요청 직전, 둘 다)을 정합니다.
  - 카드는 승인됐는데 상품 시스템이 재고 없음이라고 답하면 어떻게 할지 정합니다.
- **이유**: 결제대기가 길어질 수 있으므로 주문 생성 때만 확인하면 결제 시점에는 품절일 수 있습니다. 승인 뒤 재고가 없으면 선택지는 두 가지이고, 어느 쪽이든 지금 결정한 내용을 고쳐야 합니다.
  1. 승인을 취소하고 주문을 성립시키지 않는다. 이 경우 주문 성립의 정의가 "승인 완료"에서 "승인 완료와 재고 확정"으로 바뀝니다.
  2. 주문을 성립시키고 취소 절차로 넘긴다. 이 경우 범위에서 뺀 취소·환불 기능에 기대게 됩니다.
- **확인할 사실**: 상품 시스템이 재고를 잡아 두는(선점) 기능을 제공하는지 먼저 확인하세요. 제공한다면 결제 요청 직전에 선점해서 이 문제를 크게 줄일 수 있습니다.

### F. 결제 결과를 알 수 없을 때와 승인이 두 번 났을 때

- **정할 것**
  - 결제 시스템이 응답하지 않으면 주문을 결제대기로 둘지, "결제 확인 중" 같은 별도 상태로 둘지 정합니다.
  - 결과가 확인될 때까지 재시도를 막을지 정합니다.
  - 결과를 누가, 언제까지 확정하는지 정합니다.
  - 한 주문에 승인이 두 건 생기면 어떻게 처리하는지 정합니다.
- **이유**: 다른 카드로 다시 결제할 수 있게 했으므로, 첫 결제 결과를 모르는 상태에서 고객이 재시도하면 한 주문에 승인이 두 건 생길 수 있습니다. 주문 성립이 "승인 완료"로 정해져 있으니 결과를 모르는 동안 주문이 어느 상태인지도 정해야 합니다. 중복 승인을 취소하는 일을 이번 범위에 넣을지도 정해야 합니다. 고객이 요청한 취소가 아니므로 범위에서 뺀 취소와는 별개입니다.

### G. 배송 요청은 언제, 어떻게 하고, 실패하면 어떻게 하는가

- **정할 것**
  - 승인 직후 자동으로 요청하는지, 운영자 확인을 거치는지 정합니다.
  - 요청이 실패해도 주문 성립 상태를 유지하는지 정합니다.
  - 실패하면 누가 다시 요청하는지 정합니다.
- **이유**: "승인 뒤에만 요청한다"는 결정은 요청 시점의 하한일 뿐, 자동으로 요청하는지는 정하지 않았습니다. 또 주문은 성립했는데 배송이 시작되지 않는 상태를 누가 책임지는지 정하지 않으면, 요구사항에 정상 흐름만 남습니다.

### H. 비회원 주문을 허용하는가

- **정할 것**: 비회원도 주문할 수 있는지 정합니다. 허용한다면 결제대기 주문을 다시 찾을 때 본인 확인을 어떻게 하는지도 정합니다.
- **이유**: 거절 뒤 다른 카드로 다시 결제하려면 고객이 그 주문으로 돌아올 수 있어야 합니다. 회원은 로그인으로 해결되지만, 비회원은 별도의 본인 확인 규칙이 있어야 이 결정을 실현할 수 있습니다.

### I. 주문 확인 통지를 누가 보내는가

- **정할 것**: 이 시스템이 보내는지, 결제나 배송 시스템의 통지로 갈음하는지 정합니다.
- **이유**: 전자상거래법상 청약을 받았다는 사실을 지체 없이 알려야 합니다. 이 시스템이 보낸다면 요구사항이 하나 생기고, 다른 시스템에 맡긴다면 그 사실을 요구사항에 명시해야 합니다. 통지 수단과 문구는 나중에 정해도 됩니다.

## 지금 정하지 않아도 요구사항을 쓸 수 있는 것

이 항목들은 요구사항에 "값은 추후 확정" 또는 "외부 시스템의 판단을 따른다"고 적어 두면 됩니다. 흐름과 상태는 바뀌지 않습니다.

| 항목 | 지금 정하지 않아도 되는 이유 | 요구사항에 적는 방법 |
|---|---|---|
| 결제대기 기한의 정확한 값 (예: 30분, 24시간) | 기한이 있다는 원칙(B)만 정하면 흐름이 정해집니다. | "결제대기는 N시간 뒤 만료된다(N 추후 확정)" |
| 결제 재시도 횟수 제한 | 숫자가 바뀌어도 흐름은 같습니다. | "재시도 횟수 상한을 둔다(값 추후 확정)" |
| 할부 개월 수, 무이자 조건 | 카드 승인 조건이라 결제 시스템이 정합니다. | "할부 조건은 결제 시스템 정책을 따른다" |
| 승인 거절 안내 문구 | 문구일 뿐이고 업무 흐름과 상관없습니다. | "거절 사실과 재시도 방법을 안내한다" |
| 배송지 입력 항목의 세부, 주소록 저장 | 수령인이 주문자와 같으므로 필수 항목은 주소와 연락처로 좁혀졌습니다. 주소록은 회원 기능입니다. | 필수 항목만 적고, 주소록은 범위 밖으로 표시 |
| 배송 가능 지역, 도서산간 추가비 | 배송 시스템의 판단을 따르면 됩니다. 단, 배송비를 금액에 포함하는지는 C에서 정합니다. | "배송 가능 여부와 배송비는 배송 시스템에서 받는다" |
| 최소·최대 주문 금액, 1인당 구매 수량 제한 | 검증 규칙을 하나 더하는 일이라 흐름에 영향이 없습니다. | 검증 규칙 목록에 "추후 확정"으로 자리만 둠 |
| 결제 전 고지 항목의 문구 | 고지하고 확인받는다는 요구는 지금 적을 수 있고, 문구는 법무 검토 사항입니다. | "법정 거래 조건을 고지하고 확인받는다" |
| 기록 5년 보존을 어느 시스템이 하는가 | 보존 의무는 요구사항에 적고, 보존 위치는 설계 단계에서 정해도 됩니다. | "주문·결제 기록을 5년 보존한다" |
| 알림 수단, 운영자 조회 권한, 처리 규모 | 기능을 덧붙이는 것이거나 비기능 조건이라, 핵심 흐름과 따로 정할 수 있습니다. | 별도 절로 분리 |
