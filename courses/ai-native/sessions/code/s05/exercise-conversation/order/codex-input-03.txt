# “주문한다” 요구사항 정의서

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인할 때까지의 요구사항과 수용 기준을 정의한다.

## 목적과 범위

- 상품 조회와 장바구니 구성은 전제다.
- 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

## 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

## 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

## 기본 용어집

- **주문(Order):** 배송지가 지정되어 생성된 거래 기록
- **주문 항목(OrderItem):** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가(salePrice):** 상품 시스템이 제공하는 상품 가격
- **주문 금액(totalAmount):** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기(PENDING_PAYMENT):** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료(PAID):** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

## 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
   - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
   - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

## 대표 수용 예

공통 전제는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울인 같은 주문이다.

### 1. 카드 승인

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

### 2. 주문 생성 뒤 가격 변경

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이고 상태는 `결제완료`다. 승인 결과를 확인할 수 있으며 서울로의 배송 요청은 1회다.

### 3. 카드 승인 거절

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X의 승인이 거절된 주문이 `결제대기`이고 배송 요청은 0회다.
- **사건:** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

## 품질·접근 기준

# “주문한다” 정적 업무 모델

이 정적 모델은 주문·주문 항목·상품의 관계와, 주문 생성 시점의 판매가를 단가로 확정하여 각 항목의 확정 단가에 수량을 곱한 금액의 합계로 주문 금액을 유지하는 조건을 명시한다.

## 1. 용어와 속성

- 주문 `Order`
  - `orderNumber: OrderNumber`: 주문 식별 값
  - `totalAmount: Money`: 주문 항목별 확정 단가와 수량으로 계산한 주문 금액
  - `shippingAddress: Address`: 주문 생성 시 확정된 배송지
  - `status: OrderStatus`: 주문의 현재 상태

- 주문 항목 `OrderItem`
  - `quantity: Quantity`: 주문한 상품의 수량
  - `unitPrice: Money`: 주문 생성 시점의 `salePrice`로 확정된 단가

- 상품 `Product`
  - `productNumber: ProductNumber`: 상품 식별 값
  - `salePrice: Money`: 상품의 현재 판매가

- `Money`: 원 단위의 0 이상 정수
- `Quantity`: 1 이상의 정수
- `Address`: 주문에 확정된 배송지 값
- `OrderNumber`: 주문 식별 값
- `ProductNumber`: 상품 식별 값
- `OrderStatus`: 주문의 현재 상태 값. 현재 확인된 값은 `PENDING_PAYMENT`와 `PAID`이며 가능한 상태 전체가 확정된 것은 아니다.

## 2. 클래스 도식과 관계

관계선은 업무상 관계와 개수만 나타내며 연관 방향이나 저장 방식을 정하지 않는다.

```mermaid
classDiagram
    class Order {
        orderNumber: OrderNumber
        totalAmount: Money
        shippingAddress: Address
        status: OrderStatus
    }

    class OrderItem {
        quantity: Quantity
        unitPrice: Money
    }

    class Product {
        productNumber: ProductNumber
        salePrice: Money
    }

    Order "1" -- "1..*" OrderItem : 주문 항목
    OrderItem "0..*" -- "1" Product : 해당 상품
```

1. 하나의 `Order`에는 `OrderItem`이 1개 이상 있다.
2. 하나의 `OrderItem`은 정확히 하나의 `Order`에 속한다.
3. 하나의 `OrderItem`은 정확히 하나의 `Product`에 해당한다.
4. 하나의 `Product`는 0개 이상의 `OrderItem`과 관계를 맺을 수 있다.

## 3. 조건과 대표 예

- `salePrice`, `unitPrice`, `totalAmount`는 원 단위의 0 이상 정수다.
- `quantity`는 1 이상의 정수다.
- 하나의 `Order`에는 `OrderItem`이 1개 이상 있고 `shippingAddress`가 존재한다.
- 유효한 주문에서는 다음 합계 등식이 항상 성립한다.

  ```text
  Order.totalAmount
  = Σ(OrderItem.unitPrice × OrderItem.quantity)
  ```

- `unitPrice`는 장바구니에 담은 시점이 아니라 `Order` 생성 시점의 해당 `Product.salePrice`로 확정된다.
- 생성 이후 현재 `salePrice`가 변경되어도 기존 `unitPrice`와 `totalAmount`는 변하지 않는다.
- `PENDING_PAYMENT`인 기존 주문에서는 주문 항목의 구성, 각 항목의 `quantity`와 `unitPrice`, `shippingAddress`가 변경되지 않는다.

대표 주문과 판매가 변경 전후는 다음과 같다.

| 값 | 주문 생성 직후 | 판매가 변경 후 |
|---|---:|---:|
| 상품 | 펜 | 펜 |
| `OrderItem` 수 | 1 | 1 |
| `Product.salePrice` | 1,000원 | 1,200원 |
| `OrderItem.unitPrice` | 1,000원 | 1,000원 |
| `OrderItem.quantity` | 2 | 2 |
| `Order.totalAmount` | 2,000원 | 2,000원 |
| `Order.shippingAddress` | 서울 | 서울 |

생성 시점에는 `unitPrice = salePrice = 1,000원`이고, `totalAmount = 1,000원 × 2 = 2,000원`이다. 이후 현재 판매가가 1,200원으로 바뀌어도 기존 주문은 확정 단가 1,000원과 총액 2,000원을 유지한다.

## 4. 정하지 않은 항목과 기존 업무 미정

본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정하며 다른 고객의 주문 요청은 거절한다. 주문자와 수령인은 같은 사람으로 본다. 다만 회원·비회원 여부와 주문 주체, 본인 확인, 주문자 및 수령인을 나타낼 구체 타입이나 식별 정보는 정하지 않는다.

정적 모델에서 다음 사항은 정하지 않는다.

- `OrderNumber`와 `ProductNumber`의 형식 및 생성 규칙
- `Address`의 세부 항목
- `Quantity`의 구체적인 상한
- 동일 상품 주문 항목의 병합 여부와 중복 허용 여부
- 결제 이력과 승인 결과의 보존 구조
- 현재 확인된 값 이외의 `OrderStatus`

기존 업무 미정은 다음과 같다.

- 결제대기 기한과 만료 정책
- 결제 응답을 확정할 수 없을 때의 처리와 재결제 허용 여부
- 재고 판단 시점과 승인 전 재고 부족 처리
- 카드 승인 뒤 재고 부족 처리
- 배송 요청 실패 처리와 재요청 기준
- 주문 결과의 별도 통지 여부와 담당 시스템

이 미정 사항으로부터 허용 또는 금지 정책, 새로운 개념이나 상태를 도출하지 않는다.

# “주문한다” 동적 업무 모델 초안

이 초안은 실습 3의 요구사항과 실습 4의 정적 업무 모델에서 확인된 사건, 상태 변화, 업무 참여자 간 상호작용을 표현한다. 기술 구성요소, 저장 방식, 통신 방식은 다루지 않는다.

## 1. 주요 사건과 결과

1. **배송지를 지정한다**
   - 장바구니의 상품과 수량을 주문 대상으로 삼는다.
   - 상품별 주문 생성 시점의 판매가를 확인한다.
   - 판매가를 주문 항목의 `unitPrice`로 확정한다.
   - `totalAmount = Σ(unitPrice × quantity)`로 주문 금액을 확정한다.
   - 배송지를 확정하고 주문을 생성한다.
   - 생성된 주문의 상태는 `PENDING_PAYMENT`다.

2. **카드 승인을 요청한다**
   - 대상 주문은 고객 본인의 `PENDING_PAYMENT` 주문이어야 한다.
   - 승인 요청 금액은 확정된 `Order.totalAmount`다.
   - 주문 생성 뒤 현재 판매가가 달라져도 승인 요청 금액은 바뀌지 않는다.

3. **카드 승인 응답을 받는다**
   - 승인되면 같은 주문이 `PAID`로 전이한다.
   - 거절되면 주문은 `PENDING_PAYMENT`로 유지된다.
   - 응답을 확정할 수 없으면 승인이나 거절로 해석하지 않는다.

4. **배송을 요청한다**
   - 카드 승인이 완료된 뒤에만 요청한다.
   - 주문에 확정된 `shippingAddress`를 사용한다.
   - 승인 거절 시에는 요청하지 않는다.

5. **주문 결과를 확인한다**
   - 고객은 본인 주문에 한해 현재 상태와 카드 승인 결과를 확인한다.
   - 별도 통지의 필요 여부와 담당 주체는 아직 정하지 않는다.

6. **다른 카드로 재결제를 요청한다**
   - 카드 승인이 명확히 거절된 주문은 `PENDING_PAYMENT`로 유지된다.
   - 고객은 같은 주문에 다른 카드로 다시 승인을 요청할 수 있다.
   - 새 주문을 생성하지 않으며 승인 요청 금액도 변경하지 않는다.

## 2. 주문 상태 기계

현재 근거가 있는 주문 상태는 `PENDING_PAYMENT`와 `PAID`뿐이다. 결제 만료, 취소, 배송 실패 등의 상태는 정책이 정해지지 않았으므로 추가하지 않는다.

```mermaid
stateDiagram-v2
    [*] --> PENDING_PAYMENT: 배송지 지정 및 주문 생성\n단가·주문 금액 확정

    PENDING_PAYMENT --> PAID: 카드 승인 완료\n같은 주문 성립
    PENDING_PAYMENT --> PENDING_PAYMENT: 카드 승인 거절\n다른 카드로 재결제 가능

    note right of PENDING_PAYMENT
        상품·수량·확정 단가·배송지는 변경할 수 없다.
        주문 생성 뒤 판매가가 변해도 주문 금액은 유지된다.
        결제 응답 미확정 시의 후속 처리와
        재결제 허용 여부는 아직 정해지지 않았다.
    end note

    note right of PAID
        카드 승인 완료 뒤
        확정된 배송지로 배송을 요청한다.
        이후 취소·환불·배송 진행은 범위 밖이다.
    end note
```

### 상태와 전이를 목록으로 읽기

- **시작 → `PENDING_PAYMENT`**
  - 사건: 고객이 배송지를 지정한다.
  - 조건: 주문 항목이 하나 이상이고 각 수량이 1 이상이다.
  - 결과: 주문 생성 시점 판매가로 단가와 총액을 확정하여 주문을 생성한다.

- **`PENDING_PAYMENT` → `PAID`**
  - 사건: 카드 승인 완료 응답을 받는다.
  - 조건: 승인 요청 금액이 해당 주문의 확정된 `totalAmount`다.
  - 결과: 같은 주문이 성립하며 배송을 요청한다.

- **`PENDING_PAYMENT` → `PENDING_PAYMENT`**
  - 사건: 카드 승인 거절 응답을 받는다.
  - 결과: 배송을 요청하지 않으며 다른 카드로 같은 주문을 재결제할 수 있다.

- **결제 응답 미확정**
  - 승인이나 거절에 해당하는 전이로 처리하지 않는다.
  - 주문이 `PAID`가 되지 않는다는 점은 분명하다.
  - 이후 확인 방법과 재결제 허용 여부는 미정이므로 새로운 상태나 전이를 확정하지 않는다.

- **`PAID` 이후**
  - 이 범위에서 확인된 업무는 배송 요청까지다.
  - 취소, 환불, 반품, 교환 및 배송 진행 상태는 모델링하지 않는다.

## 3. 분석 수준 업무 상호작용

다이어그램의 `주문`은 실습 4에서 정의한 업무 개념 `Order`다. 별도의 소프트웨어 서비스나 저장소를 뜻하지 않는다.

```mermaid
sequenceDiagram
    actor Customer as 고객
    participant Product as 상품 시스템
    participant Order as 주문
    participant Payment as 결제 시스템
    participant Delivery as 배송 시스템

    Customer->>Order: 장바구니 상품·수량과 배송지로 주문 생성 요청
    Order->>Product: 주문 생성 시점 판매가 확인
    Product-->>Order: 상품별 판매가
    Note over Order: unitPrice를 판매가로 확정하고<br/>totalAmount를 계산한다.
    Order-->>Customer: PENDING_PAYMENT 주문과 확정 금액

    Customer->>Order: 카드 결제 요청
    Note over Order: 확정된 totalAmount를 사용한다.
    Order->>Payment: 카드 승인 요청(확정 주문 금액)

    alt 카드 승인 완료
        Payment-->>Order: 승인 완료
        Order->>Order: 같은 주문을 PAID로 전이
        Order->>Delivery: 확정된 배송지로 배송 요청
        Order-->>Customer: 결제완료 주문 결과
    else 카드 승인 거절
        Payment-->>Order: 승인 거절
        Note over Order: PENDING_PAYMENT 유지<br/>배송 요청 없음
        Order-->>Customer: 승인 거절 및 결제대기 결과
        opt 다른 카드로 재결제
            Customer->>Order: 같은 주문의 카드 결제 재요청
            Order->>Payment: 다른 카드 승인 요청(같은 확정 금액)
        end
    else 응답을 확정할 수 없음
        Payment-->>Order: 확정되지 않은 응답
        Note over Order,Customer: 승인 또는 거절로 간주하지 않는다.<br/>후속 확인과 재결제 정책은 미정이다.
        Order-->>Customer: 확정되지 않은 결제 결과
    end
```

### 상호작용을 목록으로 읽기

#### 주문 생성

1. 고객이 장바구니의 상품·수량과 배송지를 제시한다.
2. 주문 생성 시점의 상품별 판매가를 상품 시스템에서 확인한다.
3. 주문은 각 판매가를 주문 항목의 확정 단가로 기록한다.
4. 확정 단가와 수량으로 주문 금액을 계산한다.
5. 확정 배송지와 함께 `PENDING_PAYMENT` 주문을 생성한다.
6. 이후 현재 판매가가 변해도 기존 주문의 단가와 총액은 바뀌지 않는다.

#### 승인 완료

1. 고객이 `PENDING_PAYMENT` 주문의 카드 결제를 요청한다.
2. 해당 주문의 확정 금액으로 카드 승인을 요청한다.
3. 결제 시스템이 승인 완료를 응답한다.
4. 새 주문을 만들지 않고 같은 주문을 `PAID`로 변경한다.
5. 주문의 확정 배송지로 배송을 요청한다.
6. 고객이 결제완료 결과를 확인한다.

#### 승인 거절과 재결제

1. 결제 시스템이 승인 거절을 응답한다.
2. 주문은 `PENDING_PAYMENT`로 유지된다.
3. 배송은 요청하지 않는다.
4. 고객은 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.
5. 재승인 요청에도 기존 주문의 확정 금액을 사용한다.
6. 재승인이 완료되면 같은 주문이 `PAID`가 되고 배송은 총 1회 요청된다.

#### 응답 미확정

1. 결제 시스템의 응답을 승인 또는 거절로 확정할 수 없다.
2. 이를 승인 완료나 승인 거절로 간주하지 않는다.
3. 따라서 배송을 요청할 근거가 생기지 않는다.
4. 결과 확인 방법, 후속 확인, 재결제 허용 여부는 정책 확인 전까지 확정하지 않는다.

## 4. 대표 업무 규칙

- 주문 생성 시점의 `Product.salePrice`를 `OrderItem.unitPrice`로 확정한다.
- 주문 금액은 `Σ(OrderItem.unitPrice × OrderItem.quantity)`다.
- 주문 생성 이후의 판매가 변경은 기존 주문의 단가, 총액 및 카드 승인 요청 금액에 영향을 주지 않는다.
- `PENDING_PAYMENT` 주문의 상품, 수량, 확정 단가 및 배송지는 변경하지 않는다.
- 이를 바꾸려면 새 주문을 생성해야 한다.
- 카드 결제만 허용한다.
- 승인 거절 후에는 새 주문이 아니라 같은 주문을 재결제한다.
- 승인 완료 전에는 배송을 요청하지 않는다.
- 승인 완료 후에는 주문에 확정된 배송지로 배송을 요청한다.
- 주문이 별도로 재고를 확보한다고 보지 않으며 재고 판단은 상품 시스템에 따른다.
- 고객은 본인 주문만 조회하거나 변경 요청할 수 있다.
- 본인 주문이라도 상태와 업무 규칙상 금지된 변경은 허용되지 않는다.

## 5. 대표 동적 예

### 승인 성공

- 초기 상태: 주문은 `PENDING_PAYMENT`, 금액은 2,000원, 배송지는 서울이다.
- 사건: 카드 Y로 2,000원 승인을 요청하고 승인 완료 응답을 받는다.
- 전이: `PENDING_PAYMENT → PAID`
- 결과: 같은 주문이 성립하고 서울로 배송을 1회 요청한다.

### 가격 변경 뒤 승인

- 초기 상태: 주문의 확정 단가는 1,000원, 수량은 2개, 총액은 2,000원이다.
- 사건: 현재 판매가가 1,200원으로 오른 뒤 카드 승인을 요청한다.
- 전이: 승인 완료 시 `PENDING_PAYMENT → PAID`
- 결과: 승인 요청 금액은 2,000원이며 기존 확정 단가와 총액은 변하지 않는다.

### 승인 거절

- 초기 상태: 주문은 `PENDING_PAYMENT`다.
- 사건: 카드 X의 승인이 거절된다.
- 전이: `PENDING_PAYMENT → PENDING_PAYMENT`
- 결과: 배송 요청은 없고 다른 카드로 재결제할 수 있다.

### 거절 뒤 재승인

- 초기 상태: 카드 X가 거절된 같은 주문이 `PENDING_PAYMENT`다.
- 사건: 카드 Y로 같은 금액을 재승인 요청하고 승인 완료 응답을 받는다.
- 전이: `PENDING_PAYMENT → PAID`
- 결과: 새 주문은 생성되지 않으며 서울로의 배송 요청은 전체 과정에서 1회다.

## 6. 정책 확인이 필요한 질문

다음 질문에 답하기 전에는 관련 상태나 전이를 추가하면 안 된다.

1. 결제 응답을 확정할 수 없을 때 고객의 재결제를 허용하는가? 허용한다면 기존 승인과 중복될 가능성을 어떤 업무 기준으로 판정하는가?
2. `PENDING_PAYMENT` 주문에 유효 기한이 있는가? 기한이 지나면 어떤 업무 상태가 되는가?
3. 재고는 주문 생성 전, 주문 생성 후, 카드 승인 전, 카드 승인 후 중 언제 판단하는가?
4. 승인 전에 재고 부족이 확인되면 주문 생성 또는 결제를 중단하는가? 이미 생성된 주문의 상태는 어떻게 하는가?
5. 카드 승인 완료 뒤 재고 부족이 확인되면 `PAID` 주문과 카드 승인을 어떻게 처리하는가?
6. 카드 승인 뒤 배송 요청이 실패하면 `PAID` 상태를 유지하는가? 배송 재요청은 어떤 조건에서 몇 번까지 허용하는가?
7. 배송 요청의 “1회”는 업무 요청을 한 번만 시도한다는 뜻인가, 중복되지 않은 유효한 배송 접수를 하나만 만든다는 뜻인가?
8. 비회원 주문을 허용하는가? 허용한다면 본인 주문임을 판단하는 업무 조건은 무엇인가?
9. 주문 결과를 고객이 조회하는 것 외에 별도 통지가 필요한가? 필요하다면 어느 업무 주체가 담당하는가?

실습 3·4의 미정 정책은 새로 결정하지 않는다. 본인 확인, 기한, 응답 미확정의 후속 처리, 재고 판단·부족 처리, 배송 요청 실패, 별도 통지 정책은 미정으로 유지해라. 정해진 정상 승인·거절의 대표 예를 모델링할 수 있으므로 이 미정 전체를 해결하려고 범위를 늘리지 마라. 정상 응답의 대표 예에서 배송 요청 1회는 기록한 업무 요청이 1번이라는 뜻이며 운영상 중복 방지·재시도 정책은 아직 정하지 않는다.

[추가 질문·수정 요청]
같은 주문 생애주기의 참고 범위를 확장하겠다. PAID에서 배송 시작 통보를 받으면 IN_DELIVERY, 배송중에 배송 완료 통보를 받으면 DELIVERED다. 이 두 상태와 전이는 주문한다의 요구 범위 밖인 생애주기 맥락으로 표시하고 실습 3 요구 범위 자체를 확대하지 마라. 취소는 범위 밖으로 유지해라.
상태 기계에서 카드 승인 거절은 PENDING_PAYMENT 자기 전이로 유지해라. 배송 요청은 PAID 상태에 진입하는 승인 사건의 반응이며 요청 자체로 IN_DELIVERY가 되지 않는다.
시퀀스는 고객·주문 시스템·결제 시스템·배송 시스템의 분석 수준으로 정상 승인 장면과 거절 뒤 재결제 장면을 나눠 보여라. 업무 사건의 선후 관계를 나타낼 뿐 동기·비동기 전달 방식을 정하지 않는다. 기술 객체·DB·재시도·복구 정책은 추가하지 마라. 펜 2개·확정 단가 1000원·총액 2000원·서울을 유지하고, 같은 주문의 식별·상품·수량·배송지·금액이 거절 뒤에도 유지됨을 명시해라.
이 조건으로 상태 기계·전이 목록·정상 승인 시퀀스·대표 예를 보완하고, 금지된 전이와 미정 정책의 차이를 짚어라. 전체 도메인 사건 목록을 발명하지 말고 범위 안의 대표 사건만 담아라.

# “주문한다” 동적 업무 모델 보완안

이 모델은 실습 3의 요구 범위인 주문 생성, 카드 승인·거절, 재결제와 배송 요청을 중심으로 한다. `IN_DELIVERY`와 `DELIVERED`는 같은 주문 생애주기를 이해하기 위한 범위 밖 참고 상태이며, 실습 3의 요구 범위를 확대하지 않는다.

시퀀스의 참여자는 분석 수준의 업무 주체다. 화살표는 업무 사건의 선후 관계만 나타내며 동기·비동기 전달 방식이나 기술 연동 구조를 정하지 않는다.

## 1. 상태 기계

```mermaid
stateDiagram-v2
    [*] --> PENDING_PAYMENT: 배송지 지정 및 주문 생성\n단가·금액·배송지 확정

    state "실습 3 요구 범위" as InScope {
        PENDING_PAYMENT --> PENDING_PAYMENT: 카드 승인 거절\n같은 주문으로 재결제 가능
        PENDING_PAYMENT --> PAID: 카드 승인 완료\n배송 요청 1회 기록
    }

    state "주문 생애주기 참고 범위\n(실습 3 요구 범위 밖)" as OutOfScope {
        PAID --> IN_DELIVERY: 배송 시작 통보
        IN_DELIVERY --> DELIVERED: 배송 완료 통보
    }

    note right of PENDING_PAYMENT
        상품·수량·확정 단가·금액·배송지는 변경하지 않는다.
        승인 거절 뒤에도 같은 주문을 유지한다.
    end note

    note right of PAID
        배송 요청은 PAID 진입을 일으킨
        카드 승인 완료 사건의 반응이다.
        배송 요청 자체는 상태 전이가 아니다.
    end note

    note right of OutOfScope
        배송 시작·완료는 생애주기 참고 맥락이다.
        배송 진행의 상세 정책과 취소는 모델링하지 않는다.
    end note
```

`PAID → IN_DELIVERY`는 배송 요청을 했을 때가 아니라 배송 시작 통보를 받았을 때 발생한다. 정상 승인 예에서 “배송 요청 1회”는 해당 업무 요청을 한 번 기록한다는 의미다. 운영상의 중복 방지, 전달 실패, 재시도 또는 복구 정책은 포함하지 않는다.

## 2. 전이 목록

| 현재 상태 | 대표 사건 | 다음 상태 | 반응 또는 결과 | 범위 |
|---|---|---|---|---|
| 주문 없음 | 배송지를 지정하여 주문 생성 | `PENDING_PAYMENT` | 주문 생성 시점 단가, 총액, 배송지를 확정한다. | 실습 3 |
| `PENDING_PAYMENT` | 카드 승인 완료 | `PAID` | 같은 주문이 성립하고 확정된 서울 배송지로 배송 요청 1회를 기록한다. | 실습 3 |
| `PENDING_PAYMENT` | 카드 승인 거절 | `PENDING_PAYMENT` | 배송을 요청하지 않으며 같은 주문을 다른 카드로 재결제할 수 있다. | 실습 3 |
| `PAID` | 배송 시작 통보 | `IN_DELIVERY` | 주문이 배송 중임을 나타낸다. | 생애주기 참고 |
| `IN_DELIVERY` | 배송 완료 통보 | `DELIVERED` | 주문의 배송이 완료됐음을 나타낸다. | 생애주기 참고 |

전이별 해석은 다음과 같다.

- 주문 생성 시 펜 2개의 확정 단가는 개당 1,000원, 총액은 2,000원, 배송지는 서울로 확정된다.
- 카드 승인 완료는 `PENDING_PAYMENT → PAID` 전이를 일으킨다.
- 배송 요청은 이 승인 사건에 대한 반응이며 별도의 주문 상태 전이를 일으키지 않는다.
- 카드 승인 거절은 `PENDING_PAYMENT`의 자기 전이다. 주문을 없애거나 새 주문으로 바꾸지 않는다.
- 거절 뒤에도 같은 주문의 식별, 상품인 펜, 수량 2개, 확정 단가 1,000원, 총액 2,000원 및 배송지 서울이 유지된다.
- 배송 요청을 기록했다는 사실만으로 `IN_DELIVERY`가 되지 않는다. 배송 시작 통보가 있어야 전이한다.
- `IN_DELIVERY`와 `DELIVERED`는 주문 생애주기의 참고 상태일 뿐 실습 3의 기능 범위에는 포함되지 않는다.
- 취소 상태와 취소 전이는 계속 범위 밖이다.

## 3. 정상 승인 시퀀스

```mermaid
sequenceDiagram
    actor Customer as 고객
    participant Order as 주문 시스템
    participant Payment as 결제 시스템
    participant Delivery as 배송 시스템

    Note over Customer,Order: 같은 주문: 펜 2개, 확정 단가 1,000원,<br/>총액 2,000원, 배송지 서울, 상태 PENDING_PAYMENT

    Customer->>Order: 같은 주문에 카드 결제 요청
    Order->>Payment: 카드 승인 요청(2,000원)
    Payment-->>Order: 카드 승인 완료

    Note over Order: 같은 주문을 PAID로 전이
    Order->>Delivery: 서울로 배송 요청
    Note over Order,Delivery: 배송 요청 1회를 기록한다.<br/>이 요청 자체로 IN_DELIVERY가 되지는 않는다.

    Order-->>Customer: 결제완료 주문 결과

    rect rgb(245, 245, 245)
        Note over Order,Delivery: 이하 전이는 실습 3 요구 범위 밖의 생애주기 참고
        Delivery-->>Order: 배송 시작 통보
        Note over Order: PAID에서 IN_DELIVERY로 전이
        Delivery-->>Order: 배송 완료 통보
        Note over Order: IN_DELIVERY에서 DELIVERED로 전이
    end
```

이 시퀀스는 정상 승인 장면의 업무 순서를 나타낸다.

1. 고객이 `PENDING_PAYMENT`인 같은 주문의 카드 결제를 요청한다.
2. 주문 시스템이 확정된 주문 금액 2,000원으로 카드 승인을 요청한다.
3. 결제 시스템이 승인 완료를 통보한다.
4. 같은 주문이 `PAID`로 전이한다.
5. 승인 사건의 반응으로 서울에 대한 배송 요청 1회를 기록한다.
6. 고객이 결제완료 결과를 확인한다.
7. 이후 배송 시작 및 완료 통보에 따른 전이는 생애주기 참고 범위다.

## 4. 승인 거절 뒤 재결제 시퀀스

```mermaid
sequenceDiagram
    actor Customer as 고객
    participant Order as 주문 시스템
    participant Payment as 결제 시스템
    participant Delivery as 배송 시스템

    Note over Customer,Order: 주문 A: 펜 2개, 확정 단가 1,000원,<br/>총액 2,000원, 배송지 서울, 상태 PENDING_PAYMENT

    Customer->>Order: 주문 A를 카드 X로 결제 요청
    Order->>Payment: 카드 X 승인 요청(2,000원)
    Payment-->>Order: 카드 승인 거절

    Note over Order: 주문 A는 PENDING_PAYMENT 유지<br/>배송 요청 없음
    Order-->>Customer: 승인 거절 및 결제대기 결과

    Note over Customer,Order: 거절 뒤에도 주문 A의 식별·상품·수량·<br/>확정 단가·총액·배송지가 모두 유지된다.

    Customer->>Order: 같은 주문 A를 카드 Y로 재결제 요청
    Order->>Payment: 카드 Y 승인 요청(2,000원)
    Payment-->>Order: 카드 승인 완료

    Note over Order: 새 주문을 만들지 않고<br/>주문 A를 PAID로 전이
    Order->>Delivery: 서울로 배송 요청
    Note over Order,Delivery: 전체 장면에서 기록된 배송 요청은 1회
    Order-->>Customer: 같은 주문 A의 결제완료 결과
```

이 시퀀스는 거절과 재결제의 업무 순서를 나타낸다.

1. 고객이 주문 A를 카드 X로 결제한다.
2. 카드 X의 승인이 거절된다.
3. 주문 A는 `PENDING_PAYMENT`로 유지되며 배송 요청은 기록되지 않는다.
4. 주문 A의 식별, 상품, 수량, 확정 단가, 총액 및 배송지는 바뀌지 않는다.
5. 고객이 주문 A를 카드 Y로 재결제한다.
6. 승인 요청 금액은 여전히 2,000원이다.
7. 카드 Y가 승인되면 새 주문을 만들지 않고 주문 A를 `PAID`로 전이한다.
8. 서울로의 배송 요청 1회를 기록한다.

## 5. 대표 예

### 정상 승인

- 초기 상태: 주문 A는 `PENDING_PAYMENT`다.
- 확정 내용: 펜 2개, 개당 1,000원, 총액 2,000원, 배송지 서울이다.
- 사건: 카드 Y에 2,000원 승인을 요청하고 승인 완료 통보를 받는다.
- 전이: `PENDING_PAYMENT → PAID`
- 반응: 같은 주문 A에 대해 서울로의 배송 요청 1회를 기록한다.
- 결과: 고객은 주문 A의 결제완료 결과를 확인한다.
- 비전이: 배송 요청 자체는 `PAID → IN_DELIVERY` 전이를 일으키지 않는다.

### 승인 거절

- 초기 상태: 주문 A는 `PENDING_PAYMENT`다.
- 사건: 카드 X의 승인 거절 통보를 받는다.
- 전이: `PENDING_PAYMENT → PENDING_PAYMENT`
- 결과: 배송 요청은 없고 같은 주문을 다른 카드로 재결제할 수 있다.
- 유지되는 값: 주문 A의 식별, 펜 2개, 확정 단가 1,000원, 총액 2,000원 및 배송지 서울이다.

### 거절 뒤 재결제 성공

- 초기 상태: 카드 X가 거절된 주문 A는 `PENDING_PAYMENT`다.
- 사건: 카드 Y로 같은 주문 A의 2,000원 승인을 다시 요청하고 승인 완료 통보를 받는다.
- 전이: `PENDING_PAYMENT → PAID`
- 결과: 새 주문을 만들지 않으며 서울로의 배송 요청은 전체 장면에서 1회 기록된다.

### 범위 밖 생애주기 참고

- 초기 상태: 주문 A는 `PAID`다.
- 사건: 배송 시작 통보를 받는다.
- 전이: `PAID → IN_DELIVERY`
- 후속 사건: 배송 중 배송 완료 통보를 받는다.
- 전이: `IN_DELIVERY → DELIVERED`
- 범위: 두 전이는 같은 주문 생애주기의 참고 맥락이며 실습 3의 요구 범위에 포함되지 않는다.

## 6. 금지된 전이와 미정 정책의 차이

금지된 전이는 이미 정해진 업무 규칙에 어긋나므로 허용하지 않는 변화다.

- 카드 승인 완료 없이 `PENDING_PAYMENT → PAID`로 전이할 수 없다.
- 카드 승인 거절로 `PAID`가 될 수 없다.
- 배송 요청만으로 `PAID → IN_DELIVERY`로 전이할 수 없다.
- 배송 시작 통보 없이 `IN_DELIVERY`가 될 수 없다.
- 배송 완료 통보 없이 `IN_DELIVERY → DELIVERED`로 전이할 수 없다.
- 승인 거절 뒤 재결제를 위해 기존 주문을 변경하거나 새 주문으로 대체할 수 없다.
- `PENDING_PAYMENT` 주문의 상품, 수량, 확정 단가, 총액 및 배송지를 변경할 수 없다.

미정 정책은 허용 또는 금지 여부를 아직 판단할 근거가 없는 사안이다. 임의의 상태나 전이로 보완하지 않는다.

- 비회원 주문과 본인 확인 방법
- `PENDING_PAYMENT`의 기한과 만료 처리
- 결제 응답 미확정 시의 후속 처리와 재결제 허용 여부
- 재고 판단 시점 및 승인 전·후 재고 부족 처리
- 배송 요청 실패와 재요청·복구 기준
- 별도 주문 결과 통지 여부와 담당 주체
- 운영상의 배송 요청 중복 방지 및 재시도 정책

따라서 “카드 승인 없이 `PAID`가 된다”는 확정된 규칙에 반하는 금지 전이지만, “결제 응답 미확정 후 재결제한다”는 금지된 전이가 아니라 아직 결정하지 않은 정책이다. 취소는 미정 정책을 보충해 모델링할 대상이 아니라 이번 모델의 범위 밖으로 유지한다.

상태 기계에서 PAID를 두 composite 안에 중복 선언한 것은 같은 주문 상태를 서로 다른 상태로 오해하게 한다. 복합 상태 컨테이너를 제거하고 PENDING_PAYMENT·PAID·IN_DELIVERY·DELIVERED 네 상태를 한 번씩만 선언해라. 범위 차이는 도식 밖의 설명으로 명시해라. 상태 기계의 긴 노트는 목록에 두고 전이 라벨은 사건과 짧은 반응만 남겨라.

[추가 수정 요청]
최종 문서는 요구와 정적 관점을 반복하지 않고 이번에 보완한 동적 관점의 핵심만 담아라. 도입·상태 기계·전이 목록·정상 승인 시퀀스·규칙의 대표 예 및 금지·미정으로 구성해라. 시퀀스는 정상 승인 한 장면만 도식으로 남기고 거절 뒤 재결제는 대표 예에 넣어라. 상태 기계와 시퀀스 도식의 제목·라벨은 한글을 쓰고 상태 코드 값은 전이 목록에 함께 적어라. 시퀀스에 응답 점선·색 바탕·rect를 넣지 말고 사건의 선후 관계를 나타내는 실선 화살표로 통일해라. 동기·비동기 미정을 본문에 밝혀라.
네 대표 예(승인, 판매가 변경 뒤 승인, 거절, 거절 뒤 재결제)는 전제·사건·결과를 한 줄씩 읽을 수 있는 간결한 목록 또는 표로 담아라. 취소는 범위 밖, 기한·미확정 응답·재고·본인 확인·배송 요청 실패·별도 통지는 미정으로 보존해라. 금지 목록에 배송 요청 전 승인 필요와 요청만으로 배송중 전이 금지를 명시해라. 불필요한 중복 설명을 빼고 이번 합의의 빠짐·모순을 점검해라. 아직 최종 파일 생성 단계는 아니다.
