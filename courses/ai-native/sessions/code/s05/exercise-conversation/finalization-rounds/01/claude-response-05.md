# 정기배송 최초 신청 작업 명세서

업무 규칙·날짜 계산·상태 전이는 앞 산출물을 따릅니다. 이 문서에는 이번 작업에 필요한 결정만 적습니다.

- **실습 2 요구사항 정의서:** 업무 규칙, 고지 항목, 대표 수용 기준
- **실습 3 도메인 모델:** 신청과 계약의 구분, 상태 머신(`신청준비`·`첫결제결과확인중`·`결과확인필요`·`신청완료`·`신청미완료`)
- **실습 4 아키텍처:** 패키지 책임과 의존 규칙, 네 포트(선택 확인·금액 산정·첫 결제·신청 저장), 두 조건부 전이(결제 시작·결과 반영)

## 1. 스토리와 대표 값

기존 회원으로서 반복 주문의 수고를 줄이고 싶다. 그래서 상품과 배송 조건을 고르고, 고지를 확인한 뒤 정기배송을 최초 신청한다. 첫 회차 결제 성공이 확인되어야 계약이 성립한다.

| 상품·수량 | 신청일 | 첫 배송일 | 계약기간·주기 | 계약 종료일 | 예정 회차 | 회차 결제금액 | 신청 시 결제 |
|---|---|---|---|---|---|---|---|
| 휴지 1묶음 1개 | 2027-10-28 | 2027-11-03 | 3개월·2주 | 2028-02-03(제외) | 7개 | 10,000원 | 첫 회차 10,000원만 |

## 2. 이번 작업이 지킬 업무 규칙

- **날짜:** 신청일은 신청 절차를 시작한 날입니다. 첫 배송일 하한은 Asia/Seoul 기준 달력 날짜로 고지를 산출할 때 판정하고, 그 결과를 확정 때까지 유지합니다.
- **고지와 확정:** 두 단계로 나눕니다. 확정할 때는 선택 대상의 유효성·소유 관계만 다시 확인합니다. 금액은 고지한 값을 쓰며 다시 산정하지 않습니다. 금액에 유효기간은 두지 않습니다.
- **결제:** 신청할 때는 첫 회차만 결제합니다. 7회분 일시불은 없습니다. 이후 회차의 결제 예정일은 고지만 하고 결제하지 않습니다.
- **결과:**
  - 성공이 확인되면 고지한 일정·금액으로 계약 1건이 성립합니다.
  - 실패가 확정되면 계약을 만들지 않습니다.
  - 결과를 확인할 수 없거나 저장 전에 중단되면 결과 확인 필요로 안내합니다.
- **동일 신청:** 신청 업무가 신청 식별자를 만들어 신청 저장 포트로 저장합니다. 저장소 일련번호나 DB 키로 발급하지 않습니다. 결제 시작 전이에 성공한 요청 하나만 결제를 부릅니다.
- **접근:** 회원은 본인의 배송지·결제수단·신청만 씁니다. 표시 형식은 기존 쇼핑몰 형식을 따릅니다.

## 3. 범위와 제외

**범위**

- 신청 시작과 선택 검증
- 일정·금액 산정과 고지 정보 산출
- 확정 시 재확인과 첫 회차 결제
- 성공·실패·결과 확인 필요 처리와 저장
- 동일 신청 반복 전달에 대한 응답
- 결과 반영 업무 진입점의 자리

**제외**

- 이후 회차의 실제 결제, 주문 생성·배송 운영, 첫 회차와 일반 주문의 연결
- 계약 변경·해지·자동 갱신, 배송 불가일 조정
- 실패가 확정된 같은 신청의 재결제 경로(재신청은 별개의 신규 신청으로 시작)
- 결과 확인을 시작하는 콜백·폴링·재시도와 복구 운영
- 진입부 요청 형태(화면·REST 분할), 새 보존·마스킹 정책, 별도 서비스·인프라

## 4. 수용 예

각 예는 독립된 신청 절차에서 시작합니다. 횟수는 그 예 안에서 포트 대역으로 센 누적값입니다. 첫 결제 포트 대역은 결제 요청과 결과 확인을 따로 셉니다.

### 예 1. 대표 조건 고지

```gherkin
Given 신청일 2027-10-28에 시작한 신청이 신청준비다
  And 휴지 1묶음 1개, 첫 배송일 2027-11-03, 계약기간 3개월, 배송 주기 2주를 선택했다
  And 선택 대상이 모두 유효하고 본인 소유이며 기존 정책 금액은 10,000원이다
When 회원이 고지 정보를 요청한다
Then 계약 종료일 2028-02-03(제외)과 예정 회차 7개가 고지된다
  And 회차 결제금액 10,000원, 신청 시 결제할 금액은 첫 회차 10,000원으로 고지된다
  And 상태는 신청준비이고 계약 0건, 결제 요청 0회, 금액 산정 1회다
  But 7회분 합계 청구나 고지 단계의 결제·계약이 있어서는 안 된다
```

잡는 오류: 종료일 포함, 회차 누락·추가, 일시불 고지, 고지 단계의 조기 결제

### 예 2. 본인 소유가 아닌 배송지

```gherkin
Given 대표 값으로 시작한 신청이 신청준비다
  And 선택한 등록 배송지가 다른 회원 소유다
When 회원이 고지 정보를 요청한다
Then 선택 내용 확인 요청을 안내하고 상태는 신청준비로 유지된다
  And 계약 0건, 결제 요청 0회, 금액 산정 0회다
  But 고지 정보 산출이나 결제가 진행되어서는 안 된다
```

첫 배송일이 신청일에 3일을 더한 날보다 이른 경우도 결과가 같습니다.

잡는 오류: 부적합한 선택으로 금액을 산정하거나 결제를 시작하는 것

### 예 3. 첫 결제 성공 확정

```gherkin
Given 대표 값으로 고지를 받고 확인한 신청이 신청준비다
  And 확정 시 선택 대상이 유효하고 본인 소유다
  And 첫 결제 결과는 성공 확정이다
When 회원이 신청을 확정한다
Then 신청 완료와 계약 성립을 안내하고 상태는 신청완료다
  And 계약 1건에 종료일 2028-02-03, 예정 회차 7개, 회차 결제금액 10,000원이 확정된다
  And 결제 요청 1회, 청구 금액 10,000원, 금액 산정 1회(고지 단계)다
  But 확정 시 재산정, 계약 2건 이상, 7회분 청구가 있어서는 안 된다
```

잡는 오류: 확정 시 재산정, 고지와 다른 계약 내용, 중복 계약, 일시불 청구

### 예 4. 첫 결제 실패 확정

```gherkin
Given 대표 값으로 고지를 받고 확인한 신청이 신청준비다
  And 확정 시 선택 대상이 유효하고 본인 소유다
  And 첫 결제 결과는 실패 확정이다
When 회원이 신청을 확정한다
Then 신청 미완료를 안내하고 상태는 신청미완료다
  And 계약 0건, 결제 요청 1회, 금액 산정 1회(고지 단계)다
  But 신청 완료나 결과 확인 필요로 안내해서는 안 된다
```

잡는 오류: 실패한 신청의 계약 생성, 실패 결과의 오분류

### 예 5. 결제 결과 확인 불가

```gherkin
Given 대표 값으로 고지를 받고 확인한 신청이 신청준비다
  And 확정 시 선택 대상이 유효하고 본인 소유다
  And 첫 결제 결과를 확인할 수 없다
When 회원이 신청을 확정한다
Then 결과 확인 필요를 안내하고 상태는 결과확인필요다
  And 계약 0건, 결제 요청 1회(결과 확인과 따로 셈), 금액 산정 1회(고지 단계)다
  But 신청완료나 신청미완료로 처리하거나 새 결제를 요청해서는 안 된다
```

잡는 오류: 미확정 결과를 성공·실패로 단정하는 것, 확인을 핑계로 다시 청구하는 것

### 예 6. 동일 신청의 반복 전달

```gherkin
Given 같은 예 안에서 대표 값으로 고지와 확정을 거쳐 첫 결제 성공이 확정되었다
  And 상태는 신청완료다
When 같은 신청 식별자의 확정 요청이 다시 전달된다
Then 저장된 신청 완료와 계약 결과를 안내하고 상태는 신청완료로 유지된다
  And 반복 전달 동안 늘어난 것이 없어 계약·결제 요청·금액 산정의 누적이 각각 1이다
  And 예정 회차는 7개로 유지된다
  But 추가 청구, 추가 계약, 회차 추가, 재산정이 있어서는 안 된다
```

잡는 오류: 반복 전달로 인한 중복 청구·중복 계약·회차 중복

## 5. 작업 단위

| 단위 | 구현할 결과 | 완료 확인 예 | 쓰는 포트·조건부 전이 |
|---|---|---|---|
| 1. 신청 전 고지 | 유효한 선택이면 일정·금액·첫 회차 결제 조건을 고지합니다. 부적합하면 확인 요청만 안내합니다. 신청 식별자는 신청 업무가 만듭니다. | 예 1, 예 2 | 선택 확인, 금액 산정, 신청 저장 |
| 2. 확정과 결과 확정 | 확정하면 유효성·소유 관계만 다시 확인하고 첫 회차만 결제합니다. 성공이면 완료와 계약, 실패면 미완료입니다. 결제 요청 식별 정보는 업무가 정한 값이고, 제공자 형식으로 바꾸는 일은 쇼핑몰 연계가 맡습니다. | 예 3, 예 4 | 선택 확인, 첫 결제, 신청 저장(결제 시작·결과 반영) |
| 3. 결과 미확정 안내 | 결과를 확인할 수 없으면 결과 확인 필요로 안내합니다. 이 결과는 `첫결제결과확인중`에서만 반영하고, `결과확인필요`에서는 성공·실패만 반영합니다. 결과 반영 진입점은 자리까지만 두며, 이 단위는 결과 확인 필요 안내까지로 완료합니다. | 예 5 | 첫 결제, 신청 저장(결제 시작·결과 반영) |
| 4. 반복 전달 응답 | 같은 신청이 다시 오면 저장된 결과만 안내합니다. 결제 시작 전이가 거부되어 결제·금액 산정은 부르지 않습니다. | 예 6 | 신청 저장(조회·결제 시작 거부) |

**의존 순서:** 1 → 2 → 3·4 순서입니다. 3과 4는 서로 의존하지 않습니다. 일정 계산, 상태 전이, 신청 저장 포트, 결제 응답 변환처럼 여러 단위가 함께 쓰는 코드를 바꾸면 앞 단위의 예까지 다시 실행합니다.

## 6. 네 단위 전체에 걸친 별도 검사

- **구조:** 네 단위를 모두 마친 뒤, 정적 의존 검사로 실습 4의 허용·금지 의존과 순환이 없는지 확인합니다.
- **성능:** 실습 2의 품질 요구사항은 연계 환경에서 실측한 결과로만 판정합니다. 대역 검증으로 충족을 선언하지 않습니다.
