# 정기배송 최초 신청 수용 기준

각 예의 호출 횟수와 생성 수는 해당 예의 독립된 신청 절차 안에서 누적 관찰한 값이다.

## 예 1. 대표 조건 고지

**Given**

- 신청 상태는 `신청준비`이다.
- 상품·수량은 휴지 1묶음 1개이다.
- 신청일은 2027-10-28이다.
- 첫 배송일은 2027-11-03이다.
- 계약기간은 3개월, 배송 주기는 2주이다.
- 기존 쇼핑몰이 산정한 회차 결제금액은 10,000원이다.
- 선택 대상은 모두 유효하고 신청자 본인 소유이다.

**When**

- 회원이 신청 확정 전에 고지 정보를 산출한다.

**Then**

- 신청 상태는 `신청준비`이다.
- 계약 종료일은 2028-02-03으로 고지되고 해당 날짜는 배송회차에서 제외된다.
- 예정 배송일은 2027-11-03, 11-17, 12-01, 12-15, 12-29, 2028-01-12, 01-26의 7개로 고지된다.
- 회차 결제금액은 10,000원으로 고지된다.
- 신청 시 결제할 금액은 7회분 합계가 아닌 첫 회차 10,000원으로 고지된다.
- 계약 수는 0건이다.
- 결제 요청 횟수는 0회이다.
- 금액 산정 호출 횟수는 1회이다.
- 안내 결과는 대표 조건의 일정·금액·첫 회차 결제 조건을 포함한 신청 전 고지이다.
- 계약이 미리 성립하거나 첫 결제가 실행되어서는 안 된다.

잡으려는 오류: 종료일 포함, 회차 누락·추가, 7회분 일시불 청구 또는 고지 단계의 조기 결제를 탐지한다.

## 예 2. 본인 소유가 아닌 배송지 선택

**Given**

- 신청 상태는 `신청준비`이다.
- 대표 값으로 신청을 준비한다.
- 선택한 등록 배송지는 유효하지만 신청자 본인 소유가 아니다.

**When**

- 선택 대상의 유효성과 소유 관계를 확인한다.

**Then**

- 신청 상태는 `신청준비`로 유지된다.
- 계약 수는 0건이다.
- 결제 요청 횟수는 0회이다.
- 금액 산정 호출 횟수는 0회이다.
- 안내 결과는 선택 내용 확인 요청이다.
- 고지 정보 산출, 계약 성립 또는 첫 결제가 진행되어서는 안 된다.

첫 배송일이 신청일로부터 3일보다 이른 날인 경우에도 같은 기대 결과를 적용한다.

잡으려는 오류: 부적합한 선택으로 금액을 산정하거나 결제·계약 절차를 시작하는 것을 탐지한다.

## 예 3. 첫 결제 성공 확정

**Given**

- 대표 값으로 산출한 고지 내용을 회원이 확인했다.
- 신청 상태는 `신청준비`이다.
- 신청 확정 시 선택 대상의 유효성이 다시 확인된다.
- 첫 결제 결과는 성공 확정이다.

**When**

- 회원이 신청을 확정하고 첫 회차 결제를 요청한다.

**Then**

- 신청 상태는 `신청완료`이다.
- 계약 수는 1건이다.
- 결제 요청 횟수는 1회이다.
- 금액 산정 호출 횟수는 고지 단계의 1회뿐이다.
- 계약에는 고지한 계약 종료일 2028-02-03, 예정 회차 7개와 회차 결제금액 10,000원이 그대로 확정된다.
- 실제 청구 금액은 첫 회차 10,000원이다.
- 안내 결과는 신청 완료와 계약 성립이다.
- 금액을 다시 산정하거나 계약을 2건 이상 만들거나 7회분을 청구해서는 안 된다.

잡으려는 오류: 결제 성공 전 계약 생성, 확정 시 재산정, 중복 계약 또는 전체 회차 일시불 청구를 탐지한다.

## 예 4. 첫 결제 실패 확정

**Given**

- 대표 값으로 산출한 고지 내용을 회원이 확인했다.
- 신청 상태는 `신청준비`이다.
- 신청 확정 시 선택 대상의 유효성이 다시 확인된다.
- 첫 결제 결과는 실패 확정이다.

**When**

- 회원이 신청을 확정하고 첫 회차 결제를 요청한다.

**Then**

- 신청 상태는 `신청미완료`이다.
- 계약 수는 0건이다.
- 결제 요청 횟수는 1회이다.
- 금액 산정 호출 횟수는 고지 단계의 1회뿐이다.
- 안내 결과는 첫 결제 실패에 따른 신청 미완료이다.
- 성공이나 결과 확인 필요로 안내해서는 안 된다.
- 같은 신청으로 다시 결제할 수 없어야 하며 추가 결제 요청 횟수는 0회이다.
- 재신청하려면 별개의 신규 신청을 시작해야 한다.

잡으려는 오류: 실패한 신청의 계약 생성, 실패 결과의 오분류 또는 동일 신청 재결제를 탐지한다.

## 예 5. 결제 결과 확인 불가

**Given**

- 대표 값으로 산출한 고지 내용을 회원이 확인했다.
- 신청 상태는 `신청준비`이다.
- 신청 확정 시 선택 대상의 유효성이 다시 확인된다.
- 첫 결제 결과를 확인할 수 없다.

**When**

- 회원이 신청을 확정하고 첫 회차 결제를 요청한다.

**Then**

- 신청 상태는 `결과확인필요`이다.
- 계약 수는 0건이다.
- 결제 요청 횟수는 1회이다.
- 금액 산정 호출 횟수는 고지 단계의 1회뿐이다.
- 안내 결과는 결제 결과 확인 필요이다.
- `신청완료`나 `신청미완료`로 처리해서는 안 된다.
- 결과 확인을 위해 새 결제를 요청해서는 안 된다.

잡으려는 오류: 미확정 결과를 성공 또는 실패로 단정하거나 결과 확인 과정에서 다시 청구하는 것을 탐지한다.

## 예 6. 동일 신청의 반복 전달

**Given**

- 대표 값으로 신청한 동일 신청 식별자의 첫 결제가 이미 성공 확정되었다.
- 신청 상태는 `신청완료`이다.
- 계약 수는 1건이다.
- 결제 요청 횟수는 1회이다.
- 금액 산정 호출 횟수는 1회이다.
- 계약에 예정 회차 7개와 회차 결제금액 10,000원이 확정되어 있다.

**When**

- 같은 신청 식별자의 신청 확정 요청이 다시 전달된다.

**Then**

- 신청 상태는 `신청완료`로 유지된다.
- 계약 수는 1건으로 유지된다.
- 결제 요청 횟수는 1회로 유지된다.
- 금액 산정 호출 횟수는 1회로 유지된다.
- 예정 회차는 7개로 유지된다.
- 안내 결과는 저장된 기존 신청 완료 및 계약 결과이다.
- 추가 청구, 추가 계약, 회차 추가 또는 금액 재산정이 발생해서는 안 된다.

잡으려는 오류: 반복 전달로 인한 중복 청구, 중복 계약, 회차 중복 또는 금액 재산정을 탐지한다.
