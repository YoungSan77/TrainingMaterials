# 주문 기능 정의서 — 주문한다

## 1. 목적

고객이 장바구니의 상품에 배송지를 확정하고 카드 승인을 받아 주문 결과를 확인하는 하나의 사용자 스토리인 **‘주문한다’**를 정의한다.

## 2. 사용자 스토리

고객으로서 장바구니에 담은 상품을 배송지로 주문하고 카드로 결제하여 주문 결과를 확인하고 싶다.

## 3. 범위

### 전제

1. 고객이 상품을 조회했다.
2. 고객이 장바구니에 상품과 수량을 담았다.

상품 조회와 장바구니의 상세 동작은 정의하지 않는다.

### 포함 범위

3. 고객이 배송지를 확정한다.
4. 주문을 생성하고 주문 금액을 확정한다.
5. 고객이 카드로 결제한다.
6. 승인 결과에 따라 주문 상태를 결정한다.
7. 카드 승인 후 배송을 요청한다.
8. 고객이 주문 결과를 확인한다.
9. 본인 주문에 대한 조회·변경 권한과 변경 제한을 판단한다.

### 기능 제외

- 카드 외 결제 수단
- 배송비
- 쿠폰과 할인
- 화면 및 오류 화면
- 인증 방법
- 오류 코드
- 주문 성립 이후의 취소, 환불, 반품, 교환
- 배송 진행
- 외부 상품·결제·배송 시스템의 내부 동작

### 이 정의서의 작성 범위에서 제외

다음 산출물은 이 정의서에서 작성하지 않는다.

- 업무 모델 및 데이터 모델
- 기술 설계와 외부 연계 상세 설계
- 코드와 저장소 골격
- 자동화된 검사 코드와 실행 환경
- 릴리스 설명

용어의 영문 표기는 의사소통을 위한 것이며 데이터 구조, 클래스 또는 구현 이름을 결정하지 않는다.

## 4. 확정된 업무 흐름

```mermaid
flowchart TD
    A[전제: 상품 조회 및 장바구니 구성] --> B[고객이 배송지 확정]
    B --> C[주문 생성]
    C --> D[생성 시점 항목 단가와 주문 금액 기록]
    D --> E[결제대기 PENDING_PAYMENT]
    E --> F[확정된 주문 금액으로 카드 승인 요청]
    F --> G{승인 결과가 확정되었는가}

    G -- 아니요 --> U1[미정: 최종 수용 기준 미완성]
    G -- 예 --> H{승인되었는가}

    H -- 거절 --> I[같은 주문을 PENDING_PAYMENT로 유지]
    I --> J{다른 카드로 재결제하는가}
    J -- 예 --> F
    J -- 아니요 --> K[결제대기 결과 확인]

    H -- 승인 --> L[같은 주문을 PAID로 변경]
    L --> M[주문 성립]
    M --> N[배송 요청]
    N --> O{배송 요청 성공 여부}
    O -- 성공 --> P[주문 결과 확인]
    O -- 실패 --> U2[미정: 최종 수용 기준 미완성]
```

이 흐름은 재고 판단의 시점, 횟수 또는 호출 순서를 정하지 않는다.

## 5. 업무 규칙

### 주문 생성과 식별

- 고객이 배송지를 확정하면 `주문(Order)`을 생성한다.
- 최초 주문 상태는 `결제대기(PENDING_PAYMENT)`다.
- 주문자와 수령인은 같은 사람으로 본다.
- 카드 승인 거절 후 재결제할 때 새 주문을 생성하지 않는다.
- 거절과 재결제를 거치는 동안 같은 주문 식별자를 유지한다.

### 주문 금액

- 주문 항목 금액은 `주문 생성 시점에 기록한 항목 단가 × 수량`이다.
- `주문 금액(totalAmount)`은 모든 주문 항목 금액의 합계다.
- 주문 생성 후 `판매가(salePrice)`가 바뀌어도 기록된 항목 단가와 주문 금액은 바뀌지 않는다.
- 카드 승인 요청에는 확정된 주문 금액을 사용한다.
- 승인 거절은 청구 완료로 취급하지 않는다.

### 결제와 상태

- 결제 수단은 카드뿐이다.
- 카드 승인 완료 시 주문이 성립한다.
- 승인 완료 후 상태는 `결제완료(PAID)`다.
- 승인 거절 후에는 같은 주문을 `결제대기(PENDING_PAYMENT)`로 유지한다.
- 고객은 명시적으로 거절된 주문을 다른 카드로 다시 결제할 수 있다.
- 승인 결과가 불확정이면 성공이나 실패로 임의 확정하지 않는다.

### 권한과 변경 제한

- 고객은 본인의 주문만 조회하거나 변경을 요청할 수 있다.
- 타인의 주문 조회 및 변경 요청은 거절한다.
- 인증 방법, 오류 코드 및 화면 표현은 정하지 않는다.
- 본인이라도 결제대기 주문의 상품, 수량 및 배송지를 변경할 수 없다.
- 상품, 수량 또는 배송지를 바꾸려면 새 주문을 생성해야 한다.

### 재고

- 재고는 상품 시스템의 판단을 따른다.
- 주문 시스템은 재고를 별도로 확보하거나 예약하지 않는다.
- 재고 판단 시점, 호출 횟수 및 승인 전후 재고 부족 처리는 미정이다.

### 배송 요청

- 카드 승인 전과 승인 거절 직후에는 배송을 요청하지 않는다.
- 정상 승인 시 배송 요청은 한 번 발생한다.
- 카드 X 거절 후 같은 주문에서 카드 Y가 승인되면 전체 과정의 누적 배송 요청은 한 번이다.
- 배송 요청 실패 후 처리는 미정이다.

## 6. 대표 상황 비교

공통 사례는 다음과 같다.

- 상품: 펜
- 수량: 2개
- 주문 생성 시 판매가: 개당 1,000원
- 배송지: 서울
- 주문 금액: 2,000원
- 카드 X: 승인 거절
- 카드 Y: 승인

| 상황 | 전제 및 사건 | 동일 주문 여부 | 주문 금액 | 카드 승인 요청 금액 | 최종 상태 | 누적 배송 요청 |
|---|---|---|---:|---:|---|---:|
| 정상 승인 | 펜 2개와 서울 배송지로 주문을 생성하고 카드 Y 승인 | 생성된 같은 주문 | 2,000원 | 2,000원 | `결제완료(PAID)` | 1회 |
| 가격 변경 후 승인 | 2,000원으로 주문을 생성한 뒤 현재 판매가가 1,200원으로 상승하고 카드 Y 승인 | 가격 변경 전에 생성된 같은 주문 | 2,000원 | 2,000원 | `결제완료(PAID)` | 1회 |
| 카드 거절 | 2,000원의 결제대기 주문에 카드 X 승인 요청 후 거절 | 생성된 같은 주문 | 2,000원 | 2,000원 | `결제대기(PENDING_PAYMENT)` | 0회 |
| 거절 후 재결제 | 같은 주문에서 카드 X 거절 후 카드 Y로 다시 요청하여 승인 | X 거절 전후와 Y 승인 후 모두 같은 주문 식별자 | 2,000원 | X: 2,000원, Y: 2,000원 | 최종 `결제완료(PAID)` | 전체 과정 총 1회 |

## 7. 품질 및 수용 조건

### 기능 수용 조건

- 배송지 확정 시 주문이 생성되고 `PENDING_PAYMENT`가 되어야 한다.
- 정상 승인 시 승인 요청 금액은 2,000원이고 결과 상태는 `PAID`여야 한다.
- 주문 생성 후 판매가가 1,200원으로 올라도 주문 금액과 승인 요청 금액은 모두 2,000원이어야 한다.
- 카드 X 거절 직후 상태는 `PENDING_PAYMENT`이고 배송 요청은 없어야 한다.
- 승인 거절을 청구 완료로 취급해서는 안 된다.
- 카드 X 거절 후 카드 Y 승인까지 같은 주문 식별자를 유지해야 한다.
- 재결제를 새 주문으로 처리해서는 안 된다.
- 카드 X 거절부터 카드 Y 승인까지 배송 요청은 누적 한 번이어야 한다.
- 승인 완료 전에는 주문을 `PAID`로 처리하거나 배송을 요청해서는 안 된다.
- 타인의 주문 조회 및 변경 요청은 거절해야 한다.
- 본인이라도 결제대기 주문의 상품, 수량 및 배송지를 변경할 수 없어야 한다.

### 성능 시험 조건

다음 조건에서 카드 결제 요청 100건을 동시에 실행한다.

- 외부 상품·결제·배송 시스템은 정상 응답하는 테스트 대역이다.
- 각 외부 시스템은 1초 이내에 응답한다.
- 측정 구간은 카드 결제 요청부터 주문 결과 수신까지다.
- 100건 중 95건 이상이 3초 이내에 주문 결과를 수신해야 한다.

이 수치는 제한된 시험 환경의 수용 조건이며 운영 환경의 성능 보장 수치가 아니다.

## 8. 용어

| 용어 | 표기 | 정의 |
|---|---|---|
| 주문 | `Order` | 배송지 확정 시 생성되는 업무 기록 |
| 주문 항목 | `OrderItem` | 주문에 포함된 상품, 수량 및 주문 생성 시점에 기록한 항목 단가 |
| 판매가 | `salePrice` | 상품 시스템이 제공하는 현재 판매 가격 |
| 주문 금액 | `totalAmount` | 생성 시점의 항목 단가와 수량으로 계산한 주문 항목 금액의 합계 |
| 결제대기 | `PENDING_PAYMENT` | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태 |
| 결제완료 | `PAID` | 카드 승인이 완료되어 주문이 성립한 상태 |
| 승인 거절 | — | 카드 승인이 허용되지 않은 확정 결과이며 청구 완료가 아님 |
| 응답 불확정 | — | 승인과 거절 중 어느 결과인지 확정할 수 없는 상황 |
| 배송 요청 | — | 카드 승인 완료 후 배송 시스템에 전달하는 요청 |

`판매가(salePrice)`와 주문 생성 시점에 주문 항목에 기록된 단가는 서로 구분한다. 기록된 항목 단가의 영문 표기는 아직 정하지 않았다.

## 9. 미정 사항

미정 사항은 영구적으로 아무 처리도 하지 않는다는 정책이 아니라, 담당자가 결정하기 전까지 최종 수용 기준이 미완성이라는 의미다.

- 비회원 주문 허용 여부와 본인 확인 방법
- 결제대기 기한과 기한 경과 후 처리
- 기한 경계에서 진행 중인 승인 요청의 처리
- 결제 응답 불확정 시 상태·표식·대사·재결제·중복 승인 처리
- 재고 판단의 시점과 호출 횟수
- 승인 전후 재고 부족 처리
- 배송 요청 실패 시 상태, 재시도 및 최종 실패 처리
- 중복 배송 요청 식별 방법
- 주문 확인 통지의 담당 시스템과 발송 시점
- 중복 결제 요청 식별 및 방지 책임
- 변경을 위해 새 주문을 생성했을 때 기존 결제대기 주문의 처리
- 외부 시스템의 지연·일시 오류와 명시적 거절의 구분 기준

# 주문 기능 정적 모델 정의서 — 최종안

## 1. 목적과 범위

이 문서는 승인된 S03 최종 정의서의 주문 기능을 수업용 최소 정적 모델로 정리한다.

모델의 핵심 개념은 다음 세 가지로 한정한다.

- 주문(`Order`)
- 주문 항목(`OrderItem`)
- 상품(`Product`)

고객 식별, 결제 이력, 카드 참조, 배송 요청 이력은 업무상 필요하거나 발생하는 정보이지만 구조가 확정되지 않았으므로 별도 모델 개념으로 추가하지 않는다. 관련 요구는 규칙과 미정 질문으로 보존한다.

이 모델은 데이터베이스 구조, 구현 클래스, 외부 시스템 연동 절차, 상태 전이 또는 저장 방향을 결정하지 않는다.

## 2. 구분 기준

- **확정 업무 규칙**: 승인된 S03 최종 정의서에서 확정된 제약과 수용 기준이다.
- **교육 예제 가정**: 과정 설계와 S04에서 모델 검증을 위해 명시적으로 사용하는 가정이다. 업무 정책으로 확정된 것은 아니다.
- **미정 질문**: 추가 결정이 필요하며, 현재 허용 또는 금지로 단정할 수 없는 사항이다.

## 3. 용어와 개념

### 3.1 핵심 개념

| 개념 | 표기 | 정의 | 근거 구분 |
|---|---|---|---|
| 주문 | `Order` | 배송지가 확정될 때 생성되며 주문 항목, 주문 금액, 상태 및 주문 식별 정보를 갖는 업무 기록 | 확정 업무 규칙 |
| 주문 항목 | `OrderItem` | 주문에 포함된 상품, 수량 및 주문 생성 시점에 기록한 단가를 나타내는 항목 | 확정 업무 규칙 |
| 상품 | `Product` | 상품 시스템에서 식별되며 현재 판매가가 제공되는 주문 대상 | 확정 업무 규칙 |

### 3.2 값과 타입

| 용어 | 표기 | 정의 | 근거 구분 |
|---|---|---|---|
| 주문번호 | `OrderNumber` | 같은 주문을 구별하는 값의 타입 | 식별 필요성은 확정, 형식은 미정 |
| 상품번호 | `ProductNumber` | 상품을 구별하는 값의 타입 | 상품 식별 필요성은 확정, 형식은 미정 |
| 금액 | `Money` | 판매가, 기록 단가, 항목 금액 및 주문 금액을 표현하는 값의 타입 | 교육 예제 가정 포함 |
| 수량 | `Quantity` | 주문 항목의 상품 개수를 표현하는 값의 타입 | 교육 예제 가정 포함 |
| 주소 | `Address` | 주문에 확정된 배송지를 표현하는 값의 타입 | 상세 구성은 미정 |
| 주문 상태 | `OrderStatus` | 주문의 현재 상태를 표현하는 값의 타입 | 확인된 값 외 전체 목록은 미정 |
| 판매가 | `salePrice` | 상품 시스템이 제공하는 현재 판매 가격 | 확정 업무 규칙 |
| 기록 단가 | `unitPrice` | 주문 생성 시점의 판매가를 주문 항목에 기록한 단가 | 확정 업무 규칙, 이번 교육 모델의 명칭 |
| 항목 금액 | `lineAmount` | 주문 항목의 `unitPrice × quantity`로 계산되는 금액 | 확정 업무 규칙 |
| 주문 금액 | `totalAmount` | 주문에 속한 모든 주문 항목 금액의 합계 | 확정 업무 규칙 |
| 결제대기 | `PENDING_PAYMENT` | 주문은 생성됐지만 카드 승인이 완료되지 않은 것으로 확인된 상태 값 | 확정 업무 규칙 |
| 결제완료 | `PAID` | 카드 승인이 완료되어 주문이 성립한 것으로 확인된 상태 값 | 확정 업무 규칙 |

`PENDING_PAYMENT`와 `PAID`는 현재 정의서에서 확인된 상태 값이다. 이 둘이 `OrderStatus`의 전체 값이라고 확정하지 않는다. 결제 결과 확정 불가는 새로운 주문 상태로 추가하지 않는다.

## 4. 속성

### 4.1 주문 (`Order`)

| 속성 | 타입 | 의미 | 제약 | 근거 구분 |
|---|---|---|---|---|
| `orderNumber` | `OrderNumber` | 같은 주문을 식별하는 값 | 거절과 재결제를 거쳐도 같은 주문은 같은 값을 유지한다 | 확정 업무 규칙 |
| `status` | `OrderStatus` | 주문의 현재 상태 | 생성 시 확인된 상태는 `PENDING_PAYMENT`, 승인 완료 시 `PAID` | 확정 업무 규칙 |
| `shippingAddress` | `Address` | 주문을 생성하기 전에 확정한 배송지 | `PENDING_PAYMENT`인 같은 주문에서는 변경할 수 없다 | 확정 업무 규칙 |
| `totalAmount` | `Money` | 모든 주문 항목 금액의 합계 | 생성 후 판매가가 변해도 기존 주문의 값은 변하지 않는다 | 확정 업무 규칙 |

주문자 식별 속성은 추가하지 않는다. 본인 주문만 조회하거나 변경 요청할 수 있다는 요구는 유지하지만, 고객 타입과 식별·인증 방식은 미정이다.

### 4.2 주문 항목 (`OrderItem`)

| 속성 | 타입 | 의미 | 제약 | 근거 구분 |
|---|---|---|---|---|
| `quantity` | `Quantity` | 주문한 상품의 수량 | 교육 예제에서는 1 이상의 정수이며, `PENDING_PAYMENT`인 같은 주문에서는 변경할 수 없다 | 규칙·교육 예제 가정 |
| `unitPrice` | `Money` | 주문 생성 시점에 기록한 상품 단가 | 생성 시점의 `Product.salePrice`를 기록하며 이후 판매가가 변해도 변하지 않는다 | 확정 업무 규칙 |
| `lineAmount` | `Money` | 해당 주문 항목의 금액 | `unitPrice × quantity`와 같다 | 확정 업무 규칙 |

주문 항목 자체의 식별자는 정의하지 않는다. 필요 여부는 미정이다.

### 4.3 상품 (`Product`)

| 속성 | 타입 | 의미 | 제약 | 근거 구분 |
|---|---|---|---|---|
| `productNumber` | `ProductNumber` | 상품을 식별하는 값 | 구체적인 형식은 정하지 않는다 | 식별 필요성은 확정, 형식은 미정 |
| `salePrice` | `Money` | 상품 시스템이 제공하는 현재 판매가 | 변경될 수 있으며 기존 주문의 `unitPrice`와 `totalAmount`를 변경하지 않는다 | 확정 업무 규칙 |

## 5. 관계와 양 끝 다중성

| 관계 | `Order` 쪽 다중성 | `OrderItem` 쪽 다중성 | `Product` 쪽 다중성 | 의미 | 근거 구분 |
|---|---:|---:|---:|---|---|
| 주문—주문 항목 | `1` | `1..*` | — | 하나의 주문은 하나 이상의 주문 항목을 가지며, 각 주문 항목은 정확히 하나의 주문에 속한다 | 항목 수 하한은 교육 예제 가정 |
| 주문 항목—상품 | — | `0..*` | `1` | 각 주문 항목은 정확히 하나의 상품을 나타내며, 하나의 상품은 0개 이상의 주문 항목에서 참조될 수 있다 | 확정 업무 관계 |

양 끝을 각각 읽으면 다음과 같다.

- 하나의 `Order`에는 `OrderItem`이 `1..*`개 연결된다.
- 하나의 `OrderItem`에는 `Order`가 정확히 `1`개 연결된다.
- 하나의 `Product`에는 `OrderItem`이 `0..*`개 연결될 수 있다.
- 하나의 `OrderItem`에는 `Product`가 정확히 `1`개 연결된다.

관계는 일반 연관으로 표현한다. 구현 참조 방향, 객체 소유권, 데이터 저장 위치 및 외래 키 구조는 정하지 않는다.

## 6. 불변 조건과 생성 시점 조건

### 6.1 확정 업무 규칙

#### 합계 조건

모든 주문 항목에 대해 항목 금액은 기록 단가와 수량의 곱이다.

```text
OrderItem.lineAmount = OrderItem.unitPrice × OrderItem.quantity
```

주문 금액은 해당 주문에 연결된 모든 주문 항목 금액의 합이다.

```text
Order.totalAmount = Order.items.lineAmount의 합계
```

#### 생성 시점 조건

주문 항목의 `unitPrice`는 주문 생성 시점에 해당 상품의 `salePrice`를 기록한 값이다.

```text
주문 생성 시:
OrderItem.unitPrice = OrderItem.product.salePrice
```

주문의 최초 확인 상태는 `PENDING_PAYMENT`다.

```text
주문 생성 시:
Order.status = PENDING_PAYMENT
```

카드 승인 요청에는 확정된 `Order.totalAmount`를 사용한다.

#### 가격 변경 후 보존 조건

주문 생성 후 상품의 현재 `salePrice`가 변경되더라도 기존 주문의 다음 값은 변경되지 않는다.

- `OrderItem.unitPrice`
- `OrderItem.lineAmount`
- `Order.totalAmount`

```text
Product.salePrice 변경
≠ 기존 OrderItem.unitPrice 변경
≠ 기존 OrderItem.lineAmount 변경
≠ 기존 Order.totalAmount 변경
```

#### 상태와 같은 주문의 식별

- 카드 승인 거절 후 주문 상태는 `PENDING_PAYMENT`로 유지된다.
- 승인 거절은 청구 완료로 취급하지 않는다.
- 다른 카드로 재결제할 때 새 주문을 생성하지 않는다.
- 거절과 재결제를 거치는 동안 같은 `orderNumber`를 유지한다.
- 카드 승인 완료 시 같은 주문의 상태는 `PAID`가 된다.
- 결제 결과가 확정되지 않았을 때 승인이나 거절로 임의 확정하지 않는다.

#### 결제대기 주문의 변경 제한

`PENDING_PAYMENT`인 같은 주문에서는 다음을 변경할 수 없다.

- 상품
- 수량
- 배송지

이를 변경하려면 새 주문을 생성해야 한다. 이 제한을 `PAID` 이후를 포함한 모든 상태의 영구 불변 조건으로 확대하지 않는다.

#### 본인 주문 접근 제한

- 주문 조회나 변경 요청은 본인 주문에 대해서만 허용한다.
- 타인의 주문 조회 및 변경 요청은 거절한다.
- 고객 타입, 주문자 식별 속성, 인증 및 본인 확인 방식은 이 모델에서 확정하지 않는다.

### 6.2 교육 예제 가정

다음은 확정 업무 정책이 아니라 과정 설계와 S04의 모델 검증을 위한 가정이다.

- `Money`는 원 단위 정수로 표현한다.
- `Money` 값은 0 이상이다.
- `Quantity`는 1 이상의 정수다.
- 생성된 주문의 주문 항목 수는 1개 이상이다.
- 금액과 수량의 구체적인 상한은 정하지 않는다.

```text
Money ∈ 정수, Money >= 0
Quantity ∈ 정수, Quantity >= 1
Order.items->size() >= 1
```

## 7. 승인·거절·재결제 및 배송 기대값

다음 네 사례의 수용 기준은 S03 최종 정의서 6~7절에서 가져온다. 결제 이력이나 배송 요청을 별도 정적 개념으로 추가하지 않고, 대표 사례의 기대 결과로 확인한다.

| 사례 | 주요 사건 | 같은 주문 여부 | 주문 금액 | 카드 승인 요청 금액 | 최종 상태 | 누적 배송 요청 |
|---|---|---|---:|---:|---|---:|
| 정상 승인 | 펜 2개와 서울 배송지로 주문 생성 후 카드 Y 승인 | 생성된 같은 주문 | 2,000원 | 2,000원 | `PAID` | 1회 |
| 가격 변경 후 승인 | 2,000원으로 주문 생성 후 현재 판매가가 1,200원으로 상승하고 카드 Y 승인 | 가격 변경 전에 생성된 같은 주문 | 2,000원 | 2,000원 | `PAID` | 1회 |
| 카드 거절 | 카드 X 승인 요청 후 명시적으로 거절 | 생성된 같은 주문 | 2,000원 | 2,000원 | `PENDING_PAYMENT` | 0회 |
| 거절 후 재결제 | 같은 주문에서 카드 X 거절 후 카드 Y 승인 | X 거절 전후와 Y 승인 후 모두 같은 주문 | 2,000원 | X: 2,000원, Y: 2,000원 | 최종 `PAID` | 전체 과정 1회 |

정상 승인과 카드 X 거절 후 카드 Y 승인의 누적 배송 요청 1회는 위 수용 사례의 기대값이다. 이를 배송 실패와 재시도가 포함된 모든 상황에서 주문별 배송 요청이 최대 한 번이라는 전역 불변 조건으로 일반화하지 않는다.

## 8. 대표 주문 검산

### 8.1 주문 생성 시점

대표 주문은 다음과 같다.

| 대상 | 값 |
|---|---:|
| 상품 | 펜 |
| `Product.salePrice` | 1,000원 |
| `OrderItem.quantity` | 2 |
| `OrderItem.unitPrice` | 1,000원 |
| `OrderItem.lineAmount` | 2,000원 |
| `Order.totalAmount` | 2,000원 |
| `Order.shippingAddress` | 서울 |
| `Order.status` | `PENDING_PAYMENT` |

항목 금액을 검산하면 다음과 같다.

```text
lineAmount
= unitPrice × quantity
= 1,000원 × 2
= 2,000원
```

항목이 하나이므로 주문 금액은 다음과 같다.

```text
totalAmount
= 모든 lineAmount의 합계
= 2,000원
```

### 8.2 현재 판매가 변경 전후

주문 생성 후 상품의 현재 판매가가 1,000원에서 1,200원으로 상승한다.

```text
Product.salePrice: 1,000원 → 1,200원
```

| 값 | 가격 변경 전 | 가격 변경 후 |
|---|---:|---:|
| `Product.salePrice` | 1,000원 | 1,200원 |
| `OrderItem.unitPrice` | 1,000원 | 1,000원 |
| `OrderItem.quantity` | 2 | 2 |
| `OrderItem.lineAmount` | 2,000원 | 2,000원 |
| `Order.totalAmount` | 2,000원 | 2,000원 |
| 카드 Y 승인 요청 금액 | — | 2,000원 |

변경 후에도 다음 계산이 유지된다.

```text
기존 주문의 lineAmount
= 기존 unitPrice 1,000원 × quantity 2
= 2,000원

기존 주문의 totalAmount
= 2,000원

카드 승인 요청 금액
= 기존 Order.totalAmount
= 2,000원
```

현재 판매가로 다시 계산한 2,400원을 기존 주문이나 카드 승인 요청에 사용하지 않는다.

### 8.3 거절 후 같은 주문에서 재결제

아래의 `ORD-예시-A`는 같은 주문임을 설명하기 위한 값일 뿐이다. 접두어, 길이, 문자 구성 같은 `OrderNumber` 형식 규칙을 정의하지 않는다.

| 순서 | 사건 | 설명용 `orderNumber` | 요청 금액 | 주문 상태 | 누적 배송 요청 |
|---:|---|---|---:|---|---:|
| 1 | 주문 생성 | `ORD-예시-A` | — | `PENDING_PAYMENT` | 0회 |
| 2 | 카드 X 승인 요청 | `ORD-예시-A` | 2,000원 | `PENDING_PAYMENT` | 0회 |
| 3 | 카드 X 승인 거절 | `ORD-예시-A` | 2,000원 | `PENDING_PAYMENT` | 0회 |
| 4 | 카드 Y 승인 요청 | `ORD-예시-A` | 2,000원 | `PENDING_PAYMENT` | 0회 |
| 5 | 카드 Y 승인 완료 | `ORD-예시-A` | 2,000원 | `PAID` | 1회 |

이 사례에서는 주문번호, 주문 항목의 `unitPrice`, `lineAmount` 및 주문의 `totalAmount`가 재결제 전후에 유지된다.

## 11. 모델 해석의 경계

- `Order`, `OrderItem`, `Product`는 업무 개념이며 구현 클래스나 데이터베이스 테이블을 의미하지 않는다.
- 관계는 업무상 다중성만 나타내며 참조 방향, 객체 소유권 및 저장 구조를 결정하지 않는다.
- `Money`, `Quantity`, `Address`, `OrderNumber`, `ProductNumber`, `OrderStatus`는 속성의 의미를 설명하는 값 타입이다.
- `PENDING_PAYMENT`와 `PAID`는 확인된 상태 값이며 전체 상태 집합을 닫지 않는다.
- 결제 결과 확정 불가는 별도의 주문 상태로 모델링하지 않는다.
- 결제 이력, 카드 참조 및 배송 요청 이력은 구조가 확정되지 않았으므로 클래스로 추가하지 않는다.
- 정상 승인과 거절 후 재결제 사례의 배송 요청 1회는 수용 사례의 기대값이며, 실패와 재시도를 포함한 전역 최대 1회 제약이 아니다.
- 이 문서는 상태 전이, 외부 연동 절차, 트랜잭션, 동시성 제어, 오류 코드 또는 화면 표현을 새로 정의하지 않는다.

# 주문한다 — 동적 모델

## 1. 사건 목록

아래 사건은 요구사항 정의서와 정적 모델에서 직접 확인되는 것만 정리한 것이다.

| 구분 | 사건 | 의미 및 결과 |
|---|---|---|
| 선행 사건 | 상품 조회 | 주문 흐름의 전제이며 상세 동작은 범위 밖이다. |
| 선행 사건 | 장바구니 구성 | 상품과 수량을 장바구니에 담는다. 상세 동작은 범위 밖이다. |
| 입력 사건 | 배송지 확정 | 주문 생성을 시작한다. |
| 업무 사건 | 주문 생성 | 새 주문 식별자를 부여하고 주문 항목과 배송지를 기록한다. 최초 상태는 `PENDING_PAYMENT`다. |
| 업무 사건 | 생성 시점 단가 기록 | 각 주문 항목에 주문 생성 시점의 `Product.salePrice`를 `unitPrice`로 기록한다. |
| 업무 사건 | 주문 금액 확정 | `lineAmount = unitPrice × quantity`, `totalAmount = 모든 lineAmount의 합`으로 금액을 확정한다. |
| 외부 요청 | 카드 승인 요청 | 확정된 `Order.totalAmount`로 카드 승인을 요청한다. |
| 외부 결과 | 카드 승인 완료 | 같은 주문을 `PAID`로 변경하고 주문을 성립시킨다. |
| 외부 결과 | 카드 승인 거절 | 청구 완료로 취급하지 않고 같은 주문을 `PENDING_PAYMENT`로 유지한다. |
| 외부 결과 | 카드 승인 결과 불확정 | 승인 또는 거절로 임의 확정하지 않는다. 이후 상태·표식·대사·재결제 처리는 미정이다. |
| 입력 사건 | 다른 카드로 재결제 요청 | 명시적으로 거절된 주문에 대해 같은 주문 식별자와 같은 주문 금액으로 다시 승인을 요청한다. |
| 외부 요청 | 배송 요청 | 카드 승인 완료 후 발생한다. 정상 승인 경로에서는 한 번 발생한다. |
| 외부 결과 | 배송 요청 성공 | 고객이 주문 결과를 확인할 수 있다. 배송 진행 자체는 범위 밖이다. |
| 외부 결과 | 배송 요청 실패 | 이후 상태, 재시도 및 최종 실패 처리는 미정이다. |
| 입력 사건 | 주문 결과 확인 | 고객이 주문 결과를 확인한다. |
| 입력 사건 | 본인 주문 조회 요청 | 본인 주문인 경우에만 허용한다. 식별·인증 방법은 미정이다. |
| 입력 사건 | 타인 주문 조회 요청 | 거절한다. 오류 코드와 화면 표현은 정하지 않는다. |
| 입력 사건 | 본인 주문 변경 요청 | 본인 여부와 변경 제한을 판단한다. |
| 입력 사건 | 타인 주문 변경 요청 | 거절한다. |
| 입력 사건 | 결제대기 주문의 상품·수량·배송지 변경 요청 | 본인 주문이라도 거절한다. 변경하려면 새 주문을 생성해야 한다. |
| 외부 변화 | 상품 판매가 변경 | 기존 주문의 `unitPrice`, `lineAmount`, `totalAmount`에는 영향을 주지 않는다. |

재고 판단도 과정 중 발생할 수 있지만, 판단 시점·횟수·호출 순서와 승인 전후 부족 처리가 모두 미정이므로 특정 사건 순서에 배치하지 않는다.

## 2. 상태 목록

### 2.1 확인된 주문 상태

| 상태 | 의미 | 진입 또는 유지 조건 |
|---|---|---|
| `PENDING_PAYMENT` | 주문은 생성됐지만 카드 승인이 완료되지 않은 상태 | 주문 생성 시 진입한다. 카드 승인이 명시적으로 거절되면 같은 상태를 유지한다. |
| `PAID` | 카드 승인이 완료되어 주문이 성립한 상태 | 카드 승인 완료 시 같은 주문이 진입한다. |

`PENDING_PAYMENT`와 `PAID`가 전체 주문 상태 목록이라는 뜻은 아니다. 문서에서 확인된 상태 값이 두 개뿐이라는 의미다.

### 2.2 상태로 확정할 수 없는 결과

다음은 주문 상태 값으로 확정되지 않았다.

| 상황 | 현재 확정 가능한 내용 |
|---|---|
| 카드 승인 결과 불확정 | 승인 또는 거절로 임의 확정할 수 없다. 별도 주문 상태를 추가하지 않는다. |
| 배송 요청 성공 | 주문 상태 변경은 정의되지 않았다. |
| 배송 요청 실패 | 주문 상태와 후속 처리가 미정이다. |
| 결제대기 기한 경과 | 기한과 경과 후 상태·처리가 미정이다. |
| 재고 부족 | 판단 시점과 승인 전후 처리가 미정이다. |

## 3. 주문 상태 기계 Mermaid 원본

```mermaid
stateDiagram-v2
    direction LR

    state "결제대기\nPENDING_PAYMENT" as Pending
    state "결제완료\nPAID" as Paid

    [*] --> Pending : 배송지 확정 후 주문 생성\n생성 시점 단가·주문 금액 기록

    Pending --> Pending : 카드 승인 명시적 거절\n청구 완료 아님
    Pending --> Pending : 다른 카드로 재결제 요청\n같은 주문·같은 확정 금액 사용
    Pending --> Paid : 카드 승인 완료\n주문 성립

    note right of Pending
        상품·수량·배송지 변경 불가
        변경하려면 새 주문 생성
        불확정 응답의 상태·표식·후속 처리는 미정
    end note

    note right of Paid
        승인 완료 후 배송 요청
        정상 승인 경로의 배송 요청은 1회
        배송 성공·실패에 따른 상태 전이는 미정
    end note
```

`PAID`를 종료 상태로 연결하지 않았다. 주문 성립 이후의 취소·환불·반품·교환과 배송 진행이 범위 밖이고, 배송 요청 성공 또는 실패에 따른 추가 주문 상태도 정의되지 않았기 때문이다.

## 4. 정상 승인 시퀀스 Mermaid 원본

재고 판단은 시점과 호출 순서가 미정이므로 시퀀스에 넣지 않았다. 상품 시스템 내부 동작과 판매가 조회 호출 순서 역시 확정하지 않는다.

```mermaid
sequenceDiagram
    actor Customer as 고객
    participant Order as 주문 시스템
    participant Payment as 카드 승인 시스템
    participant Delivery as 배송 시스템

    Note over Customer,Order: 전제: 상품 조회 및 장바구니 구성 완료

    Customer->>Order: 배송지 확정 및 주문 요청
    activate Order
    Order->>Order: 주문 생성
    Order->>Order: 생성 시점 unitPrice 기록
    Order->>Order: lineAmount와 totalAmount 확정
    Order->>Order: 상태 = PENDING_PAYMENT
    Order-->>Customer: 결제대기 주문 결과
    deactivate Order

    Customer->>Order: 카드 결제 요청
    activate Order
    Order->>Payment: 확정된 totalAmount로 승인 요청
    activate Payment
    Payment-->>Order: 승인 완료
    deactivate Payment

    Order->>Order: 같은 주문 상태 = PAID
    Order->>Order: 주문 성립
    Order->>Delivery: 배송 요청
    activate Delivery
    Delivery-->>Order: 배송 요청 성공
    deactivate Delivery

    Order-->>Customer: 주문 결과
    deactivate Order
    Customer->>Order: 주문 결과 확인
```

이 시퀀스의 배송 성공은 정상 승인 사례를 나타낸다. 배송 요청 실패 경로와 그 후속 조치는 정의하지 않는다.

| 번호 | 현재 상태 | 사건·조건 | 다음 상태 | 동작 및 불변 조건 |
|---:|---|---|---|---|
| T1 | 주문 없음 | 배송지가 확정되어 주문 생성 | `PENDING_PAYMENT` | 새 `orderNumber`를 가진 주문을 생성한다. 생성 시점의 판매가를 `unitPrice`로 기록하고 `lineAmount`와 `totalAmount`를 확정한다. |
| T2 | `PENDING_PAYMENT` | 카드 승인 요청 | `PENDING_PAYMENT` | 확정된 `totalAmount`로 요청한다. 승인 결과가 나오기 전 `PAID`로 변경하거나 배송을 요청하지 않는다. |
| T3 | `PENDING_PAYMENT` | 카드 승인 명시적 거절 | `PENDING_PAYMENT` | 청구 완료로 취급하지 않는다. 배송을 요청하지 않으며 같은 주문 식별자와 금액을 유지한다. |
| T4 | `PENDING_PAYMENT` | 거절 후 다른 카드로 재결제 요청 | `PENDING_PAYMENT` | 새 주문을 만들지 않는다. 같은 `orderNumber`와 확정된 `totalAmount`로 다시 승인을 요청한다. |
| T5 | `PENDING_PAYMENT` | 카드 승인 완료 | `PAID` | 같은 주문을 결제완료로 변경하고 주문을 성립시킨다. 정상 승인 경로에서 배송 요청을 한 번 발생시킨다. |
| T6 | `PENDING_PAYMENT` | 카드 승인 결과 불확정 | 미정 | 승인 또는 거절로 임의 확정하지 않는다. 상태·표식·대사·재결제·중복 승인 처리는 미정이다. |
| T7 | `PAID` | 배송 요청 성공 | 상태 전이 미정 | 고객의 주문 결과 확인으로 이어진다. 별도 상태 값은 정의되지 않았다. |
| T8 | `PAID` | 배송 요청 실패 | 미정 | 주문 상태, 재시도, 종료 조건 및 최종 실패 처리가 미정이다. |

다음 요청은 상태 전이가 아니라 접근 또는 변경 제한 판단이다.

| 요청 | 판단 결과 |
|---|---|
| 본인 주문 조회 요청 | 허용한다. 본인 확인 방법은 미정이다. |
| 타인 주문 조회 요청 | 거절한다. |
| 타인 주문 변경 요청 | 거절한다. |
| 본인의 `PENDING_PAYMENT` 주문에서 상품·수량·배송지 변경 | 거절한다. 변경하려면 새 주문을 생성해야 한다. |
| 변경을 위한 새 주문 생성 | 가능하다는 원칙만 확인된다. 기존 결제대기 주문의 처리는 미정이다. |

## 6. 대표 사례

공통 조건은 펜 2개, 생성 시 판매가 1,000원, 배송지 서울, 주문 금액 2,000원이다.

### 6.1 정상 승인

1. 배송지를 확정하고 주문을 생성한다.
2. `unitPrice`는 1,000원, `lineAmount`와 `totalAmount`는 2,000원으로 기록된다.
3. 주문 상태는 `PENDING_PAYMENT`다.
4. 카드 Y에 2,000원 승인을 요청한다.
5. 승인 완료 후 같은 주문이 `PAID`가 된다.
6. 배송 요청이 한 번 발생한다.
7. 고객이 주문 결과를 확인한다.

기대 결과:

- 최종 상태: `PAID`
- 승인 요청 금액: 2,000원
- 누적 배송 요청: 1회

### 6.2 주문 생성 후 판매가 변경

1. 판매가 1,000원일 때 펜 2개 주문을 생성한다.
2. 주문 생성 후 현재 판매가가 1,200원으로 오른다.
3. 기존 주문의 `unitPrice`는 1,000원으로 유지된다.
4. 기존 주문의 `lineAmount`와 `totalAmount`도 2,000원으로 유지된다.
5. 카드 Y 승인 요청에는 2,400원이 아니라 2,000원을 사용한다.

기대 결과:

- 최종 상태: `PAID`
- 기존 주문 금액: 2,000원
- 승인 요청 금액: 2,000원
- 누적 배송 요청: 1회

### 6.3 카드 승인 거절

1. `PENDING_PAYMENT` 주문에 대해 카드 X로 2,000원 승인을 요청한다.
2. 카드 X가 승인을 명시적으로 거절한다.
3. 같은 주문을 `PENDING_PAYMENT`로 유지한다.
4. 거절을 청구 완료로 취급하지 않는다.
5. 배송을 요청하지 않는다.

기대 결과:

- 최종 상태: `PENDING_PAYMENT`
- 승인 요청 금액: 2,000원
- 누적 배송 요청: 0회

### 6.4 거절 후 다른 카드로 재결제

1. 카드 X에 2,000원 승인을 요청한다.
2. 카드 X가 거절한다.
3. 새 주문을 생성하지 않고 같은 주문을 유지한다.
4. 카드 Y에 같은 주문 금액 2,000원으로 다시 요청한다.
5. 카드 Y 승인 후 같은 주문이 `PAID`가 된다.
6. 전체 과정에서 배송 요청은 한 번 발생한다.

기대 결과:

- X 거절 전후와 Y 승인 후의 `orderNumber`: 동일
- X 승인 요청 금액: 2,000원
- Y 승인 요청 금액: 2,000원
- 최종 상태: `PAID`
- 누적 배송 요청: 1회

이 1회 기대값을 배송 실패와 재시도가 있는 모든 상황의 전역 최대 1회 제약으로 확대하지 않는다.
