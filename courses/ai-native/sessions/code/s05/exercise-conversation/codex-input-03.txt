[실습 2 요구사항 정의서]
# 정기배송 최초 신청 요구사항 정의서

## 사용자 이야기

기존 회원으로서 반복 주문의 수고를 줄이기 위해 원하는 상품을 정해진 주기로 배송받는 정기배송을 신청하고 싶다.

## 업무 규칙

1. 정기배송은 자동 갱신하지 않으며 계약기간이 끝나면 종료한다.
2. 계약기간은 3개월 또는 6개월, 배송 주기는 2주 또는 4주로 한다.
3. 첫 배송일은 신청일에 3일을 더한 날짜부터 선택할 수 있으며 해당 날짜를 포함한다. 배송 가능 여부는 기존 쇼핑몰 배송 달력을 따른다.
4. 첫 배송일을 계약 시작일로 한다.
5. 계약 종료일은 첫 배송일에 계약 개월 수를 더한 날짜로 한다. 해당 월에 같은 날짜가 없으면 그달의 말일로 하며, 종료일은 계약기간에 포함하지 않는다.
6. 첫 배송일을 첫 회차로 하고 이후 선택한 배송 주기마다 배송 예정일을 산정한다. 계약 종료일보다 이른 회차만 포함한다.
7. 상품 가격·할인·배송비는 신청 시점의 기존 쇼핑몰 정책으로 산정하며, 산정된 회차별 결제금액은 계약기간 동안 유지한다.
8. 첫 회차는 신청 시 결제하고 이후 회차는 각 배송 예정일 3일 전에 결제한다.
9. 첫 회차 결제 성공이 확인된 경우에만 신청을 완료한다. 결제 실패 시 신청은 완료되지 않으며, 결과를 확인할 수 없으면 완료로 단정하지 않고 결과 확인이 필요함을 안내한다.
10. 동일한 신청의 반복 전송으로 계약이나 첫 회차 결제가 중복되어서는 안 된다. 별개의 신규 신청은 제한하지 않는다.
11. 회원·상품·배송지·결제수단·배송 달력과 일반 주문 정책은 기존 쇼핑몰 기능 및 정책을 연계한다.

## 기능 요구사항

1. 기존 회원은 상품과 수량, 자신이 등록한 배송지와 결제수단을 선택할 수 있어야 한다.
2. 회원은 계약기간, 배송 주기와 첫 배송일을 선택할 수 있어야 한다.
3. 신청 완료 전에 다음 내용을 회원에게 고지해야 한다.

   - 선택한 상품과 수량
   - 배송지와 결제수단
   - 계약기간·계약 시작일·계약 종료일
   - 배송 주기와 첫 배송일
   - 총 배송 횟수와 회차별 예정 배송일
   - 첫 회차 결제금액
   - 계약기간 동안 유지되는 회차별 결제금액
   - 첫 회차와 이후 회차의 결제 시점
   - 자동 갱신 없이 계약기간 종료 시 종료된다는 사실

4. 신청 과정에서 첫 회차 결제를 수행하고 결제 결과에 따라 신청 결과를 안내해야 한다.
5. 동일한 신청이 반복 전송되어도 하나의 계약과 한 번의 첫 회차 결제만 처리해야 한다.

## 품질 요구사항

1. 동시 신청 100건이고 각 외부 연계가 1초 이내에 응답하는 정상 시험 조건에서, 신청 요청부터 결과 수신까지 전체 요청의 95% 이상이 3초 이내여야 한다. 이는 실습 검증 기준이며 실제 운영 보장 수치는 아니다. 이를 초과하는 부하는 기존 쇼핑몰 정책을 따른다.
2. 회원은 자신의 배송지와 결제수단만 선택하고 자신의 정기배송 신청 정보에만 접근할 수 있어야 한다. 다른 회원의 정보는 조회하거나 변경할 수 없어야 한다.
3. 운영시간·가용성·복구·기록 보존·보안·개인정보 보호는 기존 쇼핑몰 정책을 준용한다.

## 대표 수용 기준

- **일정 계산:** 첫 배송일이 2027-11-03이고 계약기간이 3개월, 배송 주기가 2주이면 계약 종료일은 2028-02-03이며 해당 날짜는 제외한다. 배송 예정일은 2027-11-03, 11-17, 12-01, 12-15, 12-29, 2028-01-12, 01-26의 총 7회다.
- **월말 계산:** 첫 배송일이 2027-01-31이고 계약기간이 3개월이면 계약 종료일은 2027-04-30이며 해당 날짜는 제외한다. 시험 날짜는 기존 배송 달력에서 허용된 것으로 본다.
- **금액 유지:** 휴지 1묶음의 신청 시 가격이 10,000원이고 할인과 배송비가 각각 0원이면 회차별 결제금액은 10,000원이다. 이후 상품 가격이 변경되어도 계약기간 동안 같은 금액을 유지한다.
- **신청 결과:** 첫 회차 결제 성공이 확인되면 신청 완료로 안내하고, 실패하면 신청 미완료로 안내한다. 결제 결과를 확인할 수 없으면 결과 확인이 필요함을 안내한다.
- **반복 전송:** 동일한 신청을 반복 전송해도 생성되는 계약과 실행되는 첫 회차 결제는 각각 하나여야 한다.

[실습 3 도메인 모델]
# 실습 3 정기배송 최초 신청 도메인 모델

## 1. 용어와 업무 규칙

### 1.1 용어

- **정기배송 신청:** 고객이 상품 한 종류와 수량, 본인의 등록 배송지·결제수단 및 배송 조건을 선택하여 계약 체결을 요청하는 과정이다.
- **정기배송 계약:** 첫 결제 성공이 확인될 때 정기배송 신청으로부터 성립하는 계약이다.
- **배송회차:** 신청 시 계산하여 고객에게 고지하는 예정 일정이다. 실제 배송 실행이나 운영 상태를 뜻하지 않는다.
- **첫 결제:** 첫 회차 금액을 신청 시 결제하는 행위다.
- **회차 결제금액:** 신청 시 확정하여 모든 배송회차에 동일하게 적용하는 금액이다.
- **동일 신청:** 고객이 한 번의 신청 의사로 시작한 신청이 반복 전달된 경우다. 선택 내용이 같다는 사실만으로 동일 신청이 되지는 않는다.
- **별개 신규 신청:** 고객이 신청 절차를 새로 시작하고 별도로 신청 의사를 확인한 신청이다.

### 1.2 업무 규칙

- 한 신청에서는 상품 한 종류와 수량을 선택한다.
- 기존 회원·상품·등록 배송지·등록 결제수단은 기존 쇼핑몰의 개념을 참조하며 내부 구조를 새로 정의하지 않는다.
- 고객은 본인의 유효한 등록 배송지와 등록 결제수단만 선택할 수 있다.
- 선택 대상이 유효하지 않거나 본인 소유가 아니거나 첫 배송일이 허용되지 않으면 선택 내용 확인을 요청하고 `신청준비` 상태를 유지한다. 이때 첫 결제를 실행하지 않는다.
- 날짜 산정, 배송회차 계산, 월말 처리, 금액 산정·유지 및 검증값은 **실습 2 요구사항 정의서와 대표 수용 기준**을 따른다.
- 신청 완료 전 선택 내용, 계약 조건, 배송 일정과 횟수, 결제금액과 결제 시점, 금액 유지 및 자동 갱신 없음을 고지한다.
- 첫 회차는 신청 시 결제하며 배송일 기준의 결제 예정일을 갖지 않는다. 이후 회차만 실습 2에서 정한 결제 예정일을 갖는다.
- 첫 결제 성공이 확인된 경우에만 신청이 완료되고 신청당 최대 하나의 계약이 성립한다.
- 첫 결제 실패가 확정되면 신청은 미완료되고 계약은 성립하지 않는다. 다시 신청하려면 별개의 신규 신청을 시작해야 한다.
- 결제 결과를 확인할 수 없으면 실패로 취급하지 않고 `결과확인필요` 상태로 둔다. 이후 결제 시스템의 결과 확인을 통해 성공 또는 실패가 확정된다.
- 계약이 성립하면 신청 시 고지한 배송회차와 회차 결제금액이 계약 내용으로 확정된다.
- 동일 신청의 반복 전달은 추가 청구, 추가 계약, 회차 추가 또는 상태 변화를 일으키지 않는다. 결과가 확정되었으면 기존 결과를, 아직 확정되지 않았으면 결과 확인 필요를 안내한다.
- 별개의 신규 신청은 허용한다. 동일 신청을 식별하는 기술적 방식은 설계에서 결정한다.
- 결제 결과를 통지하거나 조회하는 기술적 방식과 고객 알림 수단은 설계에서 결정한다.
- 이후 배송 운영, 후속 결제 실행, 배송 불가일 조정, 계약 변경 및 해지는 이 모델의 범위에서 제외한다.

## 2. 클래스 다이어그램

신청과 계약을 서로 다른 업무 개념으로 표현한다. 상태와 결과 속성에는 타입만 표시하며 값과 전이는 상태 머신에서 정의한다.

```plantuml:class
@startuml
left to right direction
skinparam classAttributeIconSize 0

class 회원 <<기존 개념 참조>>
class 상품 <<기존 개념 참조>>
class 등록배송지 <<기존 개념 참조>>
class 등록결제수단 <<기존 개념 참조>>

class 정기배송신청 {
  신청일: 날짜
  수량: 양의정수
  계약기간: 계약기간
  배송주기: 배송주기
  첫배송일: 날짜
  종료예정일: 날짜
  회차결제금액: 금액
  상태: 정기배송신청상태
}

  결제예정일: 날짜 [0..1]
}

class 첫결제 {
  결제금액: 금액
  결과: 첫결제결과
}

class 정기배송계약 {
  계약시작일: 날짜
  계약종료일: 날짜
  계약기간: 계약기간
  배송주기: 배송주기
  회차결제금액: 금액
  자동갱신여부: 불리언
}

회원 "1" <-- "0..*" 정기배송신청 : 신청자
상품 "1" <-- "0..*" 정기배송신청 : 선택 상품
등록배송지 "1" <-- "0..*" 정기배송신청 : 선택 배송지
등록결제수단 "1" <-- "0..*" 정기배송신청 : 선택 결제수단

정기배송신청 "1" *-- "1..*" 배송회차 : 계산·고지
정기배송신청 "1" *-- "0..1" 첫결제 : 신청 시 실행
정기배송신청 "1" --> "0..1" 정기배송계약 : 성공 확인 시 성립
정기배송계약 "0..1" --> "1..*" 배송회차 : 일정·금액 확정
첫결제 "0..1" --> "1" 배송회차 : 첫 회차 대상
```

`배송회차`는 신청 시점의 예정 정보를 나타내며 실제 배송 상태는 포함하지 않는다.

## 3. 시퀀스 다이어그램

최초 신청 요청부터 첫 결과 안내까지의 업무 상호작용을 표현한다.

```plantuml:sequence
@startuml
actor 고객
participant "정기배송 업무" as 정기업무
participant "기존 쇼핑몰" as 쇼핑몰
participant "결제 시스템" as 결제

고객 -> 정기업무 : 상품·수량, 배송지·결제수단,\n계약기간·배송 주기·첫 배송일 선택
정기업무 -> 쇼핑몰 : 회원·상품·배송지·결제수단의 유효성·소유 관계,\n배송 가능 여부 및 적용 금액 확인
쇼핑몰 --> 정기업무 : 확인 결과와 회차 결제금액

alt 선택 내용이 유효하지 않음
  정기업무 --> 고객 : 선택 내용 확인 요청
else 선택 내용이 유효함
  정기업무 -> 정기업무 : 계약 조건과 배송회차 산정
  정기업무 --> 고객 : 선택 내용, 계약 조건, 배송회차,\n결제금액·결제 시점 및 종료 조건 고지
  고객 -> 정기업무 : 고지 확인 및 신청 의사 확정
  정기업무 -> 결제 : 첫 회차 금액 결제

  alt 첫 결제 성공 확인
    결제 --> 정기업무 : 성공 확정
    정기업무 -> 정기업무 : 고지된 일정과 금액으로 계약 성립
    정기업무 --> 고객 : 신청 완료 및 계약 성립 안내
  else 첫 결제 실패 확정
    결제 --> 정기업무 : 실패 확정
    정기업무 --> 고객 : 신청 미완료 안내
  else 결제 결과 확인 불가
    결제 --> 정기업무 : 결과 미확정
    정기업무 --> 고객 : 결과 확인 필요 안내
  end
end
@enduml
```

결과 미확정 이후 성공 또는 실패가 확인되는 사건은 상태 머신에서 표현한다.

## 4. 상태 머신 다이어그램

상태 머신의 대상은 `정기배송신청`이다. 계약 성립 이후의 배송 진행과 계약 운영 상태는 포함하지 않는다.

```plantuml:state
@startuml
[*] --> 신청준비 : 새 신청 절차 시작

신청준비 --> 신청준비 : 선택 내용 변경
신청준비 --> 신청준비 : 선택 대상 부적합 또는 첫 배송일 미허용\n/ 선택 내용 확인 요청
신청준비 --> 첫결제결과확인중 : 유효성 확인 및 고지 확인\n/ 첫 결제 실행

첫결제결과확인중 --> 신청완료 : 첫 결제 성공 확인\n/ 계약 1건 성립
첫결제결과확인중 --> 신청미완료 : 첫 결제 실패 확정
첫결제결과확인중 --> 결과확인필요 : 결제 결과 확인 불가

결과확인필요 --> 신청완료 : 첫 결제 성공 확인\n/ 계약 1건 성립
결과확인필요 --> 신청미완료 : 첫 결제 실패 확정

신청완료 --> [*]
신청미완료 --> [*]
@enduml
```

`결과확인필요`는 실패가 아니라 첫 결제 결과가 아직 확정되지 않은 상태다.

# 실습 4 정기배송 최초 신청 아키텍처

업무 규칙, 날짜·금액 조건, 상태 전이와 수용 기준은 **실습 2 요구사항 정의서**와 **실습 3 도메인 모델**을 따른다. 이 문서는 그 규칙을 어느 패키지가 맡고, 패키지끼리 어떻게 의존하는지만 정한다.

## 1. 아키텍처 선택과 패키지

**선택:** 정기배송 모듈을 기존 쇼핑몰과 같은 배포 단위 안에 두고, 포트로 의존 방향을 뒤집는다.

**이유**

- 범위가 최초 신청 하나다. 별도 서비스나 새 인프라를 둘 근거가 없다.
- 업무 흐름과 규칙이 결제·저장·기존 쇼핑몰의 구현 방식에 묶이지 않는다.
- 포트를 대역으로 바꾸면 실제 외부 시스템 없이도 업무 결과를 확인할 수 있다.

| 패키지 | 책임 | 두지 않는 것 |
|---|---|---|
| 신청 업무 | 최초 신청 흐름을 조정하고 네 포트를 소유한다. 결과 확인을 반영할 자리를 둔다. 본인 신청만 다루도록 접근을 통제한다. | 저장·연계 구현, 기존 정책의 계산 |
| 정기배송 규칙 | 신청·배송회차·첫 결제·계약을 다룬다. 일정 계산, 첫 배송일 하한 판정, 상태 전이 허용을 맡는다. | 다른 패키지에 대한 의존 |
| 쇼핑몰 연계 | 선택 확인·금액 산정·첫 결제 포트를 구현한다. 기존 기능을 조합하고, 그 응답을 업무 결과로 바꾼다. | 상태 전이, 계약 성립 판단 |
| 신청 저장 | 신청 저장 포트를 구현한다. 조건부 전이가 원자적으로 일어나도록 보장하고, 성공을 한 단위로 반영한다. | 전이를 허용할지 판단하는 일 |

## 2. 패키지 다이어그램

`A --> B`는 **A의 코드가 B의 타입이나 인터페이스를 참조한다**는 코드 의존이다. 호출 순서나 외부 호출 흐름은 나타내지 않는다. 실행 중에는 신청 업무가 포트를 거쳐 연계·저장 구현을 호출하지만, 코드 의존은 반대로 구현에서 포트를 향한다.

```mermaid
flowchart LR

        subgraph App["신청 업무"]
            Flow["최초 신청 흐름<br/>결과 확인 반영 자리"]
```

기존 쇼핑몰의 각 상자는 논리적 연결 대상이다. 단일 API나 단일 컴포넌트를 뜻하지 않는다.

## 3. 의존 규칙

**허용**

- 기존 요청 진입부 → 신청 업무
- 신청 업무 → 정기배송 규칙
- 쇼핑몰 연계·신청 저장 → 신청 업무의 포트, 정기배송 규칙, 각자 필요한 기존 기능
- 기존 구성 코드 → 세 패키지(구현 객체를 생성하고 연결할 때만)

**금지**

- 정기배송 규칙에서 다른 패키지로 향하는 의존
- 신청 업무에서 쇼핑몰 연계·신청 저장·기존 쇼핑몰 구현으로 향하는 의존
- 쇼핑몰 연계와 신청 저장 사이의 의존
- 기존 쇼핑몰에서 정기배송 내부로 향하는 의존(진입부와 구성 코드는 예외)
- 모든 순환

## 4. 세 연계 계약

| 연계 계약 | 포트 | 목적 | 담당 경계 |
|---|---|---|---|
| 쇼핑몰 확인 | 선택 확인, 금액 산정 | 선택 대상의 유효성·소유 관계와 배송 달력 허용 여부를 판정한다. 기존 정책으로 회차별 최종 금액을 산정한다. | 판정과 산정은 기존 쇼핑몰이 한다. 3일 하한 판정과 진행 여부는 정기배송 규칙과 신청 업무가 정한다. 금액 산정은 고지할 때 한 번만 부르고, 선택 확인이 부적합이면 부르지 않는다. 두 포트는 결과의 성격(판정과 산정값)이 달라서 나누었다. |
| 첫 결제 | 첫 결제 | 첫 회차 결제를 요청한다. 결과 확인은 새 청구 없이 기존 요청만 확인한다. | 쇼핑몰 연계가 응답을 **성공 확정·실패 확정·결과 확인 불가**로 바꾼다. 확정할 수 없는 응답은 실패로 바꾸지 않는다. |
| 신청 저장 | 신청 저장 | 신청 전체(고지 조건·예정 회차·첫 결제 결과·계약)를 신청 식별자와 신청자 기준으로 저장하고 조회한다. | 두 조건부 전이를 원자적으로 처리하는 것은 저장 구현의 책임이다. 전이를 허용할지는 정기배송 규칙이 판단한다. |

**두 조건부 전이**(새 업무 상태를 추가하지 않는다)

- **결제 시작:** 신청이 `신청준비`일 때만 `첫결제결과확인중`으로 전이하고, 결제 요청 식별 정보를 함께 기록한다. 동시에 들어온 요청 중 이 전이에 성공한 하나만 첫 결제를 요청한다.
- **결과 반영:** 신청이 `첫결제결과확인중`이나 `결과확인필요`일 때만 결과를 반영한다. 성공이면 결제 결과·계약 1건·`신청완료`를 한 단위로 기록한다. 이미 종료된 신청은 바꾸지 않는다.

**반복 전달과 결과 확인은 구분한다.** 같은 신청이 다시 오면 저장된 상태에 따라 안내만 하고, 결제 포트는 부르지 않는다. 상태가 바뀌는 것은 결과 확인 반영을 거칠 때뿐이며, 이는 상태 머신에 정의된 전이다.

**실제로 연결하기 전에 확인할 핵심 규격**

- 쇼핑몰 확인: 기존 기능이 업무상 부적합과 기술 오류를 구분해 주는지 확인한다. 기존 기준의 신청일과 최종 회차 금액을 얻을 수 있는지도 확인한다.
- 첫 결제: 중복 승인을 막는 수단, 새 청구 없이 결과를 조회하는 수단, 세 결과를 구분할 수 있는지를 확인한다. 셋이 입증되기 전에는 결제 연동을 완료로 보지 않는다.
- 신청 저장: 기존 영속성 기반으로 두 조건부 전이와 성공 반영을 원자적으로 처리할 수 있는지 확인한다.

## 5. 외부 시스템 없이 하는 검증

| 방향 | 방법 | 입증하는 것 | 입증하지 못하는 것 |
|---|---|---|---|
| 업무 결과 | 신청 업무와 정기배송 규칙은 실제 코드를 쓰고, 네 포트만 대역으로 바꾼다. 일정·월말 기준은 대역 없이 규칙만으로 확인한다. | 실습 2의 대표 수용 기준과 실습 3의 상태 머신대로 결과가 나오는지. 관찰 대상은 신청 상태, 계약 수와 금액, 결제 요청 횟수, 금액 산정 호출 횟수, 안내 결과다. | 실제 저장소의 원자성, 실제 결제의 중복 승인 방지 |
| 구조 | 정적 의존 검사로 3절의 허용·금지 의존과 순환을 확인한다. | 업무 결과가 맞더라도 의존 규칙이 깨지지 않았는지 | 업무 결과 |
| 성능 | 각 외부 연계가 1초 안에 응답하는 연계 환경에서 동시 100건으로 실측한다. | 실습 2의 품질 요구사항 충족 여부 | 대역 검증으로는 입증할 수 없다. 아직 충족했다고 보지 않는다. |

대표 예: 결제 대역이 결과 확인 불가를 돌려주면 신청은 `결과확인필요`가 되고 계약은 생기지 않는다. 같은 신청을 다시 보내도 결제 요청 횟수는 1회 그대로다.

## 6. 남은 미결 사항

- **결과 확인 반영의 시작 주체와 시점:** 콜백·폴링·재시도와 운영 복구는 이번 범위 밖이다.
- **첫 회차와 일반 주문의 연결:** 이번 범위에서는 정기배송 안에서만 기록한다.
- **신청 식별자 전달 방식과 DB 제약 구현:** 업무 계약만 정했고 기술 구현은 정하지 않았다.
- **신청준비의 유효기간:** 지금 정하지 않기로 했다.
- **결제 제공자의 멱등·조회·오류 규격:** 지원 여부가 확인되지 않아 결제 연동 완료를 판단할 수 없다.
- **의존 검사 도구:** 구조 검증의 방향만 정했다.
- **성능 실측:** 대역으로 입증할 수 없어 연계 환경에서 측정해야 한다.

# 정기배송 최초 신청 작업 명세서 초안

## 1. 작업 목표

기존 회원이 상품 한 종류와 수량, 본인의 등록 배송지·결제수단, 계약기간, 배송 주기, 첫 배송일을 선택하여 정기배송을 신청할 수 있게 한다.

신청 내용을 사전에 고지하고 회원이 최종 확정하면 첫 회차 결제를 한 번만 실행한다. 결제 성공이 확인된 경우에만 계약을 성립시키며, 실패 또는 결과 미확정 상태를 구분하여 안내한다.

정기배송 모듈은 기존 쇼핑몰과 같은 배포 단위에 두고 다음 구조를 따른다.

- `신청 업무`: 최초 신청 흐름 조정 및 포트 소유
- `정기배송 규칙`: 일정, 금액, 상태 전이 및 계약 성립 규칙
- `쇼핑몰 연계`: 기존 쇼핑몰의 선택 확인, 금액 산정, 결제 기능 연결
- `신청 저장`: 신청, 회차, 결제 결과 및 계약 저장

```mermaid
    L -->|결과 확인 불가| O["결과확인필요 기록<br/>계약 생성 안 함"]

    M --> P["신청 완료 및 계약 성립 안내"]
    N --> Q["신청 미완료 안내"]
    O --> R["결과 확인 필요 안내"]
```

## 3. 이번 작업에 포함할 범위

### 3.1 신청 준비와 선택 내용 확인

- 새 신청 절차를 시작하고 신청 식별자를 부여한다.
- 신청자는 기존 쇼핑몰의 인증된 기존 회원을 사용한다.
- 한 신청에서 다음 항목을 입력받는다.
  - 상품 한 종류
  - 양의 정수 수량
  - 회원이 등록한 배송지
  - 회원이 등록한 결제수단
  - 계약기간: 3개월 또는 6개월
  - 배송 주기: 2주 또는 4주
  - 첫 배송일
- 다음 사항은 기존 쇼핑몰 기능을 통해 확인한다.
  - 회원과 상품의 유효성
  - 배송지와 결제수단의 유효성
  - 배송지와 결제수단이 신청자 소유인지
  - 첫 배송일이 기존 배송 달력에서 허용되는지
- 정기배송 규칙에서 첫 배송일이 신청일로부터 3일 이후인지 확인한다.
- 부적합한 선택은 `신청준비` 상태를 유지하고 첫 결제를 실행하지 않는다.
- 다른 회원의 배송지, 결제수단 및 신청 정보에 대한 접근을 차단한다.

### 3.2 계약 조건과 배송회차 계산

- 첫 배송일을 계약 시작일로 정한다.
- 계약 종료일은 첫 배송일에 3개월 또는 6개월을 더해 계산한다.
- 종료 월에 같은 일자가 없으면 그달의 말일을 사용한다.
- 계약 종료일은 계약기간과 배송회차에 포함하지 않는다.
- 첫 배송일을 첫 회차로 한다.
- 이후 2주 또는 4주 간격으로 예정 배송일을 계산한다.
- 계약 종료일보다 이른 예정 배송일만 포함한다.
- 회차번호는 1부터 연속해서 부여한다.
- 첫 회차는 신청 시 결제로 표시하며 결제 예정일을 두지 않는다.
- 두 번째 이후 회차의 결제 예정일은 예정 배송일 3일 전으로 계산한다.

### 3.3 금액 산정 및 고지

- 선택 내용이 유효한 경우에만 기존 쇼핑몰의 금액 산정 기능을 호출한다.
- 신청 시점의 상품 가격, 할인 및 배송비 정책으로 최종 회차 결제금액을 산정한다.
- 금액 산정은 고지 내용을 만들 때 한 번만 실행한다.
- 산정된 회차 결제금액을 모든 배송회차와 계약에 동일하게 확정한다.
- 신청 후 상품 가격이나 일반 주문 정책이 변해도 확정 금액을 다시 계산하지 않는다.
- 회원의 신청 확정 전에 다음 내용을 고지한다.
  - 상품과 수량
  - 배송지와 결제수단
  - 계약기간, 계약 시작일 및 계약 종료일
  - 배송 주기와 첫 배송일
  - 총 배송 횟수와 회차별 예정 배송일
  - 첫 회차 결제금액
  - 모든 회차에 적용되는 결제금액
  - 첫 회차와 이후 회차의 결제 시점
  - 금액이 계약기간 동안 유지된다는 사실
  - 자동 갱신되지 않고 계약기간 종료 시 종료된다는 사실

### 3.4 첫 결제와 신청 결과 처리

- 회원이 고지 내용을 확인하고 신청 의사를 확정한 뒤에만 첫 결제를 시작한다.
- 신청이 `신청준비` 상태일 때만 결제 시작 전이를 허용한다.
- 결제 요청 전에 결제 요청 식별 정보를 신청과 함께 기록한다.
- 조건부 상태 전이에 성공한 요청 하나만 결제 포트를 호출한다.
- 결제 응답은 다음 세 결과로 구분한다.
  - 성공 확정
  - 실패 확정
  - 결과 확인 불가
- 성공 확정 시 다음 내용을 하나의 원자적 저장 단위로 반영한다.
  - 첫 결제 결과
  - 고지된 일정과 금액을 가진 계약 1건
  - `신청완료` 상태
- 실패 확정 시 계약을 생성하지 않고 `신청미완료`로 기록한다.
- 결과 확인 불가 시 계약을 생성하지 않고 `결과확인필요`로 기록한다.
- 결과를 확정할 수 없는 기술 오류나 시간 초과를 임의로 결제 실패로 변환하지 않는다.

### 3.5 동일 신청의 반복 전달 방지

- 동일 신청은 선택 내용의 조합이 아니라 한 번 발급된 신청 식별자로 판별한다.
- 같은 신청 식별자를 사용한 반복 요청은 신규 신청으로 처리하지 않는다.
- 반복 요청 시 새로운 금액 산정, 결제, 계약 생성 또는 배송회차 추가를 실행하지 않는다.
- 이미 결과가 확정된 경우 저장된 기존 결과를 반환한다.
- `첫결제결과확인중` 또는 `결과확인필요`이면 결과 확인이 필요하다고 안내한다.
- 별도로 시작하여 새로운 신청 식별자가 발급된 신청은 입력 내용이 같아도 신규 신청으로 허용한다.

신청 식별자의 실제 전달 방식은 미정이므로, 위 항목은 아래 결정 사항이 확정된 후 구현한다.

### 3.6 저장과 동시성

- 신청자, 입력 선택, 고지 조건, 배송회차, 회차 결제금액, 결제 요청 식별 정보, 결제 결과, 신청 상태 및 성립 계약을 저장한다.
- 신청은 신청 식별자와 신청자 기준으로 조회한다.
- 저장 구현은 다음 조건부 전이를 원자적으로 보장한다.
  - `신청준비 → 첫결제결과확인중`
  - `첫결제결과확인중/결과확인필요 → 신청완료/신청미완료`
- 성공 결과 반영 시 계약 생성과 신청 상태 변경이 일부만 저장되지 않게 한다.
- 종료 상태인 `신청완료`와 `신청미완료`에는 뒤늦은 결과가 상태 변화를 일으키지 않게 한다.
- 신청당 계약은 최대 1건만 존재하도록 저장소 수준의 제약을 둔다.

저장 기술과 구체적인 제약 방식은 기존 영속성 구조를 확인한 후 정한다.

### 3.7 요청 진입부와 결과 표현

다음 업무 동작을 기존 요청 진입부에서 호출할 수 있게 한다.

- 새 신청 절차 시작
- 선택 내용 검증 및 고지 정보 산출
- 고지 확인 후 신청 확정과 첫 결제 실행
- 본인의 신청 결과 조회
- 결제 결과 확인 후 상태를 반영할 수 있는 업무 진입점

마지막 항목은 업무 진입점까지만 이번 구조에 마련한다. 누가 언제 호출할지는 미정으로 남긴다.

## 5. 구현 작업 단위

### 작업 1. 정기배송 규칙 정의

- 계약기간과 배송 주기의 허용값을 표현한다.
- 첫 배송일 하한, 계약 종료일 및 월말 보정 규칙을 구현 대상으로 정의한다.
- 배송회차와 후속 회차 결제 예정일 산정 규칙을 정의한다.
- 상태별 허용 전이와 계약 성립 조건을 정의한다.
- 정기배송 규칙 패키지는 다른 패키지에 의존하지 않게 한다.

### 작업 2. 신청 업무 흐름 구성

- 선택 확인, 금액 산정, 첫 결제 및 신청 저장 포트를 정의한다.
- 신청 준비, 고지, 신청 확정, 기존 결과 반환 흐름을 조정한다.
- 신청자와 저장된 신청 소유자가 일치할 때만 조회·변경을 허용한다.
- 부적합, 기술 오류 및 결제 결과 미확정을 서로 다른 업무 결과로 표현한다.

### 작업 3. 쇼핑몰 확인 연계

- 기존 회원·상품·배송지·결제수단 확인 기능을 조합한다.
- 배송지와 결제수단의 신청자 소유 관계를 확인한다.
- 기존 배송 달력으로 첫 배송일 허용 여부를 확인한다.
- 업무상 부적합과 연계 기술 오류를 구분한다.

### 작업 4. 금액 산정 연계

- 기존 쇼핑몰 정책으로 한 회차의 최종 결제금액을 산정한다.
- 가격, 할인 및 배송비가 모두 반영된 최종 금액을 받는다.
- 신청에 저장된 금액이 이후 가격 조회 결과에 의해 변경되지 않게 한다.

### 작업 5. 첫 결제 연계

- 저장된 결제 요청 식별자를 기존 결제 기능에 전달한다.
- 같은 결제 요청 식별자의 중복 승인을 막는다.
- 결제 응답을 성공 확정, 실패 확정, 결과 확인 불가로 변환한다.
- 결과 조회 시 새 청구를 만들지 않고 기존 결제 요청만 확인한다.

결제 제공자가 멱등 처리와 기존 요청 조회를 지원하는지 확인되기 전에는 이 작업을 완료 처리하지 않는다.

### 작업 6. 신청 저장 구현

- 신청과 배송회차, 결제 정보 및 계약을 저장한다.
- 결제 시작 경쟁에서 한 요청만 성공하게 한다.
- 결제 성공 반영과 계약 생성을 원자적으로 처리한다.
- 신청당 계약 최대 1건과 결제 요청 식별자의 중복 방지를 저장소에서 보장한다.
- 반복 전달 시 기존 신청 상태를 조회하여 반환한다.

### 작업 7. 기존 진입부 및 구성 연결

- 기존 인증 회원 정보를 신청 업무에 전달한다.
- 구체 연계·저장 구현을 신청 업무의 포트에 연결한다.
- 기존 구성 코드를 제외하고 신청 업무가 구체 구현을 참조하지 않게 한다.
- 기존 쇼핑몰 내부가 정기배송 규칙이나 구현에 역으로 의존하지 않게 한다.

## 6. 완료 조건

다음 사항이 모두 충족되어야 최초 신청 기능 구현이 완료된 것으로 본다.

### 업무 결과

- 허용된 계약기간과 배송 주기만 신청할 수 있다.
- 첫 배송일 하한, 월말 보정 및 종료일 제외 규칙이 적용된다.
- 대표 일정 사례에서 총 7개의 배송회차가 계산된다.
- 신청 시 확정된 회차 결제금액이 전체 계약에 유지된다.
- 첫 결제 성공이 확인된 경우에만 계약 1건이 성립한다.
- 결제 실패와 결과 미확정이 서로 다르게 처리된다.
- 동일 신청의 반복 전달로 결제나 계약이 추가되지 않는다.
- 별개의 신규 신청은 제한하지 않는다.
- 회원은 본인의 배송지, 결제수단 및 신청만 사용할 수 있다.

### 구조

- 신청 업무는 네 포트를 통해서만 연계·저장 구현을 사용한다.
- 정기배송 규칙은 다른 패키지에 의존하지 않는다.
- 쇼핑몰 연계와 신청 저장은 서로 의존하지 않는다.
- 패키지 사이에 순환 의존이 없다.

### 동시성 및 성능

- 동시에 같은 신청이 전달되어도 첫 결제 요청과 계약은 각각 최대 1건이다.
- 외부 연계가 각각 1초 안에 응답하는 환경에서 동시 신청 100건을 실행했을 때 전체 요청의 95% 이상이 3초 안에 결과를 받는다.
- 성능 기준은 실제 연계 환경에서 측정한 경우에만 충족으로 판정한다.

## 7. 이번 작업에서 제외할 범위

- 두 번째 이후 회차의 실제 결제 실행
- 배송 주문 생성 및 출고 처리
- 실제 배송 상태와 배송 완료 관리
- 배송 불가일 발생 시 예정일 조정
- 계약 변경, 일시정지, 재개 및 해지
- 계약기간 연장 및 자동 갱신
- 첫 결제 실패 후 같은 신청의 재결제
- 상품 추가·삭제 또는 여러 상품을 묶은 정기배송
- 일반 주문과 첫 배송회차의 연결
- 신청 완료 후 배송지나 결제수단 변경
- 고객에게 보내는 이메일, 문자, 푸시 등 알림

## 9. 명세 확정을 위해 결정이 필요한 사항

1. **신청 식별자는 어떻게 전달합니까?**  
   권장안은 새 신청 시작 시 서버가 신청 식별자를 발급하고, 이후 고지 조회·신청 확정·반복 요청에서 동일 식별자를 사용하도록 하는 방식입니다. HTTP 멱등 키처럼 클라이언트가 생성하는 방식도 가능한지 결정해야 합니다.

2. **고지와 신청 확정을 두 단계 요청으로 분리합니까?**  
   권장안은 `고지 정보 산출`과 `고지 확인 후 신청 확정`을 분리하는 것입니다. 한 요청 안에서 모두 처리하면 회원이 고지 내용을 확인했다는 사실을 어떻게 표현할지 별도 규칙이 필요합니다.

3. **고지 후 신청 확정까지 상품·배송지·정책이 변경되면 어떻게 합니까?**  
   다음 중 하나를 정해야 합니다.
   - 고지 시 계산한 내용을 일정 시간 동안 그대로 사용
   - 확정 시 선택 유효성만 다시 확인하고 금액은 유지
   - 확정 시 선택과 금액을 모두 다시 확인하며 변경 시 재고지

4. **신청일과 ‘3일 후’의 기준은 무엇입니까?**  
   쇼핑몰 영업 시간대 기준의 달력 날짜인지, 요청 시각으로부터 정확히 72시간 이후인지 결정해야 합니다. 요구사항 문맥상 `Asia/Seoul` 기준 달력 날짜 계산이 자연스럽지만 확인이 필요합니다.

5. **금액 산정 결과의 유효기간이 있습니까?**  
   신청준비를 무기한 유지할 수 있으므로 고지 후 며칠 뒤에도 같은 금액으로 결제할 수 있는지, 일정 시간이 지나면 재고지해야 하는지 결정해야 합니다.

6. **첫 결제 요청의 중복 방지는 어디까지 보장됩니까?**  
   기존 결제 기능이 결제 요청 식별자에 대한 멱등 승인과 기존 요청 결과 조회를 지원하는지 확인이 필요합니다. 지원하지 않는다면 이번 구조만으로는 프로세스 중단 상황의 중복 승인을 완전히 방지할 수 없습니다.

7. **`결과확인필요` 이후 결과 반영은 누가 시작합니까?**  
   최초 신청 범위에서는 업무 진입점만 마련할지, 다음 중 하나까지 포함할지 결정해야 합니다.
   - 결제 시스템 콜백
   - 운영자 또는 고객의 명시적 결과 조회
   - 주기적 폴링
   - 별도 복구 작업

8. **결제 호출이 끝났지만 결과 저장 전에 장애가 발생하면 최초 응답을 무엇으로 합니까?**  
   권장안은 성공이나 실패로 추정하지 않고 `결과확인필요`로 안내하는 것입니다. 다만 저장된 상태와 결제 시스템 결과를 복구하는 운영 방식이 함께 결정되어야 합니다.

9. **신청 미완료 데이터는 보존합니까?**  
   첫 결제 실패 후 계약은 만들지 않지만 신청과 결제 시도 기록을 기존 기록 보존 정책에 따라 유지할지 확인해야 합니다.

10. **고객에게 표시할 배송지와 결제수단 정보의 마스킹 기준은 무엇입니까?**  
    기존 쇼핑몰의 표시 형식을 그대로 사용할지 확인이 필요합니다.

11. **첫 회차에 대한 일반 주문 생성은 확실히 후속 작업으로 분리합니까?**  
    현재 초안은 정기배송 계약과 예정 회차만 기록하고 일반 주문은 만들지 않는 것으로 범위를 정했습니다.

12. **성능의 ‘결과 수신’은 어떤 응답까지 측정합니까?**  
    결제 결과 미확정을 즉시 `결과확인필요`로 반환한 시점까지인지, 최종 성공·실패 확정까지인지 결정해야 합니다. 현재 초안은 최초 요청에 대한 세 가지 결과 중 하나를 반환한 시점까지로 해석했습니다.

# 정기배송 최초 신청 작업 명세서

## 1. 스토리

기존 회원으로서 반복 주문의 수고를 줄이기 위해 상품 한 종류와 수량, 본인의 등록 배송지·결제수단, 계약기간, 배송 주기와 첫 배송일을 선택하고 정기배송을 최초 신청한다.

신청자는 고지 정보를 확인한 뒤 신청을 확정한다. 첫 회차만 신청 시 결제하며, 결제 성공이 확인된 경우에만 정기배송 계약이 성립한다.

## 2. 이번 작업이 지킬 업무 규칙과 대표 값

대표 값은 다음 한 벌로 고정한다.

| 항목 | 대표 값 |
|---|---|
| 상품·수량 | 휴지 1묶음 1개 |
| 신청일 | 2027-10-28 |
| 첫 배송일·계약 시작일 | 2027-11-03 |
| 계약기간 | 3개월 |
| 배송 주기 | 2주 |
| 계약 종료일 | 2028-02-03, 계약기간에서 제외 |
| 예정 회차 | 7개 |
| 회차 결제금액 | 10,000원 |
| 신청 시 결제 | 첫 회차 금액 10,000원만 결제 |

이번 작업은 다음 규칙을 지킨다.

- 신청일과 첫 배송일 하한은 `Asia/Seoul` 기준 달력 날짜로 계산한다. 대표 값의 첫 배송일 2027-11-03은 신청일 2027-10-28로부터 선택 가능한 날짜다.
- 계약 종료일은 2028-02-03이며 해당 날짜는 포함하지 않는다. 2주 주기의 예정 배송일은 2027-11-03, 11-17, 12-01, 12-15, 12-29, 2028-01-12, 01-26의 7개다.
- 고지 정보 산출과 고지 확인 후 신청 확정을 분리한다. 확정 시 선택 대상의 유효성만 다시 확인하고, 고지한 회차 결제금액 10,000원은 다시 산정하지 않는다. 금액에는 유효기간을 두지 않는다.
- 신청 확정 시 첫 회차 10,000원만 결제한다. 7회분 일시불 청구는 하지 않는다. 이후 회차의 결제 예정일은 고지하지만 실제 결제하지 않는다.
- 첫 결제의 성공이 확인되면 고지한 일정과 금액으로 계약 한 건을 성립시킨다. 실패가 확정되면 계약을 만들지 않으며, 결과를 확인할 수 없거나 결제 호출 뒤 결과 저장 전에 중단되면 성공·실패로 추정하지 않고 결과 확인 필요로 안내한다.
- 서버가 새 신청 절차를 시작할 때 신청 식별자를 발급한다. 같은 신청은 조건부 전이로 결제 시작을 한 번만 성공시키고, 성공한 요청만 결제를 호출한다. 입력 내용이 같더라도 새 절차에서 발급된 식별자는 별개의 신규 신청이다.
- 회원은 본인의 등록 배송지·결제수단과 신청 정보만 사용할 수 있다. 표시 형식과 마스킹은 기존 쇼핑몰 방식을 그대로 따른다.

## 3. 이번 작업 범위

- 서버가 신청 식별자를 발급하는 새 신청 절차와, 상품 한 종류·수량·본인 배송지·본인 결제수단·계약기간·배송 주기·첫 배송일의 선택 및 검증
- 신청일 기준 첫 배송일 하한, 계약 종료일, 예정 회차와 이후 회차 결제 예정일의 산정
- 기존 쇼핑몰 정책에 따른 회차 결제금액 산정과 신청 내용·계약 조건·예정 일정·결제 조건·금액 유지·비자동 갱신에 대한 고지 정보 산출
- 고지 확인 후 선택 대상 유효성 재확인, 조건부 결제 시작 전이, 첫 회차 결제 요청 및 성공·실패·결과 확인 필요 처리
- 신청·고지 내용·예정 회차·첫 결제 결과·계약의 저장과 본인 신청 조회
- 기존 상태에 따른 동일 신청의 반복 요청 응답과 추가 결제·추가 계약 방지
- 미확정 결제 결과를 성공 또는 실패로 반영할 수 있는 업무 진입점 마련

고지와 확정은 업무상 두 단계로 구분하지만, 화면 구성이나 REST 요청 분할 방식은 정하지 않는다.

## 4. 제외 범위

- 두 번째 이후 회차의 실제 결제, 주문 생성·출고·배송 운영 및 첫 회차와 일반 주문의 연결
- 계약 변경·일시정지·재개·해지·연장·자동 갱신과 배송 불가일에 따른 일정 조정
- 첫 결제 실패가 확정된 동일 신청의 재결제 경로. 재신청은 별개의 신규 신청으로 시작한다.
- 결제 결과 확인을 시작하는 콜백·폴링·재시도와 장애 복구 운영 자동화
- 신청준비 유효기간, 신규 보존·마스킹 정책, 별도 서비스·인프라 및 진입부 표현 방식의 설계

신청 미완료 기록의 보존은 기존 쇼핑몰의 기록 보존 정책을 준용한다.

## 5. 미정 사항과 확인 담당

| 미정 사항 | 이번 작업의 처리 경계 | 확인 담당 |
|---|---|---|
| 결제 제공자의 멱등 처리, 기존 요청 결과 조회 및 오류 구분 규격 | 조건부 전이까지 구현한다. 규격이 확인되기 전에는 실제 결제 연동을 완료로 판정하지 않는다. | 연동 담당 |
| 기존 영속성 기반의 조건부 전이, 성공 결과·계약의 원자적 반영 및 고유 제약 지원 방식 | 지원 방식을 확인한 뒤 저장 구현을 확정한다. | 저장 담당 |
| 신청 식별자의 전달 방식과 DB 제약 구현 | 실습 4의 미결 사항으로 유지한다. 클라이언트 생성 멱등 키는 사용하지 않는다. | 업무 담당·저장 담당 |

결제 호출 뒤 결과 저장 전에 중단된 신청의 복구 운영 방식도 실습 4의 미결 사항으로 유지한다. 이번 작업에서는 결과 확인 필요 안내와 결과 반영 업무 진입점까지만 제공한다.

## 6. 참조할 앞 산출물

- **실습 2 요구사항 정의서:** 최초 신청의 업무·기능·품질 요구사항과 대표 수용 기준을 참조한다. 성능 요구사항은 이번 작업의 수용 기준에 넣지 않으며, 연계 환경에서 실측하기 전에는 충족을 선언하지 않는다.
- **실습 3 도메인 모델:** 신청과 계약의 구분, 배송회차의 의미, 첫 결제 결과와 신청 상태 전이, 동일 신청과 별개 신규 신청의 정의를 참조한다.
- **실습 4 아키텍처:** 패키지 책임과 의존 규칙, 네 포트, 두 조건부 전이, 저장 원자성 경계 및 외부 시스템 없이 검증할 범위를 참조한다. 패키지 구조를 이 명세에서 다시 정의하지 않는다.
[사용자 — 이번 피드백]
아래 답과 수정 요청을 반영해라. 확정한 범위의 수용 기준을 Given–When–Then 예로 써라. 허용되는 결과와 금지되는 결과를 함께 확인하고, 관찰할 상태·계약 수·결제 요청 횟수·안내 결과를 기대값으로 적어라. 근거가 없는 기대값은 지어내지 말고 질문으로 남겨라.

[앞선 응답에 대한 판단과 수정 요청]
- 작업 명세서를 채택한다. 대표 값 한 벌, 첫 회차만 결제, 실패 확정 뒤 재결제 경로 없음, 미정별 확인 담당을 그대로 유지한다. 규칙을 다시 늘리지 마라.
- 예는 **여섯 개**로 하고 각각 한 가지 결정을 확인해라.
  1. 고지 — 대표 값의 예정 회차 7개와 회차 금액, 종료일 제외, 신청 시 결제할 첫 회차 금액
  2. 선택 대상 부적합 — 본인 소유가 아닌 등록 배송지를 선택한 경우. 같은 결과가 되는 경우(첫 배송일이 신청일+3일보다 이른 날)는 한 줄로 덧붙여라
  3. 첫 결제 성공 확정 — 신청 완료와 계약 성립, 고지한 일정·금액의 확정
  4. 첫 결제 실패 확정 — 계약이 생기지 않고 같은 신청으로는 다시 결제하지 않는다
  5. 결제 결과 확인 불가 — 실패로 바꾸지 않고 결과 확인 필요로 안내한다
  6. 동일 신청의 반복 전달 — 추가 청구·추가 계약·회차 추가가 없다
- **금지되는 결과를 Then에 함께 써라.** 상태만 확인하면 잘못 나간 결제나 생겨 버린 계약을 놓친다. 각 예에서 **계약 수·결제 요청 횟수·금액 산정 호출 횟수**를 숫자로 확인해라.
- 상태 값은 실습 3이 정한 이름(`신청준비`·`첫결제결과확인중`·`결과확인필요`·`신청완료`·`신청미완료`)을 그대로 써라. 새 상태를 만들지 마라.
- 날짜·금액은 대표 값만 쓴다. 월말 보정은 일정 규칙의 다른 예이니 이번 수용 예로 만들지 마라. 성능도 수용 예로 만들지 마라.
- 각 예는 독립된 전제에서 시작하고 앞 예의 실행 결과에 기대지 마라. 전제는 재현에 필요한 값만 적어라.
- 구현 코드·테스트 코드·클래스 이름·메서드 이름은 쓰지 마라. 업무가 관찰하는 결과로만 적어라.
- 예는 Given–When–Then 블록으로 보여라. 예마다 한 줄로 그 예가 잡으려는 오류를 덧붙여라.
- 기대값의 근거가 앞 산출물에 없으면 지어내지 말고 그 예 뒤에 질문으로 남겨라.
