## 01. 세션 목표

에이전트가 "다 했다"고 말할 때 그 말을 받칠 것은 **검사가 낸 증거**뿐이다.

- CI/CD 파이프라인의 단계를 짚고, 검사 파이프라인이 그 **어디를 가져오고 무엇을 남기는지** 구분한다.
- 03~07에서 정한 결정마다 그것을 재는 **검사를 하나씩** 붙인다.
- 에이전트가 들어오면서 달라지는 **셋**을 말한다 — 메시지의 독자, 검사의 위치, 도는 빈도.
- 검사를 **명령 하나**로 모으고, 루프 안에서 돌 것과 CI에 남길 것을 구분한다.
- 검사의 실패를 **원인이 된 결정**으로 되돌리고, 녹색이 보장하지 않는 것을 안다.
- 자동 검사가 **놓치는 셋**을 알고 사람의 리뷰가 볼 것을 정한다.

**강사 노트**

- "세션 08. 위임"이 어긋난 실행을 미리 막는 **예방**을 다뤘다. 이 세션은 **탐지**와 결과를 받아들이는 판단이다.
- 기준 원전은 [Böckeler 2026a]이고, 추론적 센서의 실험 기록은 [Böckeler 2026b], 엔지니어의 일은 [Lopopolo 2026], 검사를 흐름에 잇는 것은 [Thoughtworks 2026]으로 받친다.
- 계속 맡길지의 판단과 평가 세트는 "세션 10. 비용과 평가"가 맡는다. 이 세션은 실패가 **어느 결정을 가리키는지**까지다.

## 02. 이미 있는 파이프라인

## CI/CD 파이프라인

CI/CD 파이프라인은 코드가 바뀔 때마다 **사람 손을 거치지 않고 도는 단계의 사슬**이다. 단계마다 통과해야 다음으로 간다.

**표 — 파이프라인의 단계**

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| **소스** | 변경을 받아 브랜치를 만든다 | — |
| **빌드** | 컴파일하고 의존성을 푼다 | 뒤 단계를 돌리지 않는다 |
| **테스트** | 단위·통합 테스트를 돌린다 | 합치지 못한다 |
| **정적 분석** | 형식·버그 패턴·보안을 본다 | 경고나 차단 |
| **패키징** | 실행할 수 있는 산출물을 만든다 | 배포하지 못한다 |
| **배포** | 환경에 올리고 되돌릴 길을 둔다 | 되돌린다 |

- **언제 도는가** — 보통 push와 병합 요청에서 돈다. 사람이 코드를 **올린 뒤**가 기준점이다.
- **도구는 바뀐다** — 어떤 제품으로 구성하든 단계의 성격은 같다. 이 세션은 도구가 아니라 단계를 좌표로 쓴다.

**강사 노트**

- 수강생의 조직에 파이프라인이 없을 수 있다. 먼저 "지금 코드를 합치기 전에 자동으로 도는 것이 있는가?"를 묻고, 없으면 이 표를 **앞으로 갖출 순서**로 읽게 한다.
- 단계 이름은 분야에 통용되는 것이다. 특정 제품의 용어가 아니며, 조직마다 단계를 합치거나 나눈다.
- 파이프라인의 구성과 배포 전략은 범위 밖이다(`course-design.md`의 Non-scope). 여기서는 **어떤 검사가 언제 도는가**만 본다.

## 기존 CI/CD와 검사 파이프라인

검사 파이프라인은 새 도구가 아니다. 위 사슬에서 **빌드·테스트·정적 분석을 떼어 에이전트가 돌리는 자리로 옮긴 것**이다.

**표 — 무엇을 가져오고 무엇을 남기는가**

| 단계 | 검사 파이프라인 | 그대로 CI에 남는 것 |
|---|---|---|
| **빌드** | 가져온다 | — |
| **테스트** | 빠른 것만 가져온다 | 느린 통합·성능 |
| **정적 분석** | 가져온다 | 긴 보안 스캔 |
| **패키징·배포** | 가져오지 않는다 | 전부 |

- **구분하는 기준은 속도와 되돌림이다** — 초 단위로 돌고 되돌리기 쉬운 것만 앞으로 당긴다.
- **둘은 경쟁하지 않는다** — 같은 검사가 루프 안에서 한 번, 병합 전에 다시 돈다. 앞의 것은 에이전트가 고치라고, 뒤의 것은 사람이 합쳐도 되는지 보라고 돈다.

**강사 노트**

- 이 표가 이 세션의 포지셔닝이다. "하네스를 새로 도입한다"가 아니라 **이미 있는 검사를 앞으로 당기고 몇 개를 더한다**로 설명한다.
- 파이프라인이 없는 팀은 당길 것이 없다. 그 경우의 순서는 검사를 먼저 만들고(그것이 실습 9다) 뒤에 CI에 올리는 것이다.
- 배포 전략·환경 구성은 DevOps 과정이 맡는다.

## 결정마다의 검사

03~07에서 내린 결정에는 **그것을 재는 검사가 하나씩** 있다. 왼쪽에서 정하지 않은 것은 오른쪽에 검사가 없다.

**표 — 결정과 그것을 재는 검사**

| 결정 | 정한 곳 | 재는 검사 |
|---|---|---|
| **요구** | 요구사항 정의서, 수용 기준 | 수용 테스트 |
| **정적 모델** | 용어집, 불변 조건 | 불변 조건 테스트, 이름의 일치 |
| **동적 모델** | 상태와 전이 | 전이 테스트, 금지된 순서 |
| **아키텍처** | 의존 규칙, 연동 규격 | 의존 규칙 검사 |
| **설계** | 오퍼레이션 계약 | 사전·사후조건 테스트 |

- **검사가 없는 결정은 맡길 수 없다** — 지켜졌는지 아무도 모르는 채로 코드가 쌓인다.
- **거꾸로도 본다** — 검사가 없는 칸이 있으면 왼쪽에서 정하지 않은 것이 무엇인지 되묻는다.

**강사 노트**

- 이 표는 "세션 01. 사람의 일과 AI의 일"의 「06. 결정과 검사의 짝」이 그린 지도의 오른쪽이다. 거기서 예고한 것을 여기서 실제 명령으로 만든다.
- 5줄이 모두 검사를 갖는 것은 아니다. 「06. 명령 하나로 모으기」의 「주문한다의 검사 5가지」이 실제로 붙인 것을 보인다.

## 03. 하네스라는 이름

## 가이드와 센서

앞으로 당긴 검사의 묶음을 **하네스**(harness)라 부른다. 하네스는 두 방향으로 작동한다.

**인용문**

하네스는 원하지 않는 결과를 **미리 막는 일**과 에이전트가 **스스로 고치도록 센서를 두는 일**을 함께 한다, "To harness a coding agent we both anticipate unwanted outputs and try to prevent them, and we put sensors in place to allow the agent to self-correct", [Böckeler 2026a]

  - 가이드(guide)는 에이전트가 행동하기 전에 방향을 잡아 **첫 시도에서 좋은 결과가 나올 확률**을 높인다, "Guides (feedforward controls) - anticipate the agent's behaviour and aim to steer it before it acts. Guides increase the probability that the agent creates good results in the first attempt", [Böckeler 2026a]

- **가이드** — 작업 지시문, 맥락 문서, 권한 설정. "세션 08. 위임"에서 이미 세웠다.
- **센서** — 컴파일·테스트·의존 규칙 검사. 실행한 **뒤에** 결과를 측정한다.

**인용문**

하나만 두면 같은 실수를 되풀이하는 에이전트(센서만)나 규칙을 적어 두고도 **효과가 있었는지 알지 못하는** 에이전트(가이드만)가 된다, "Separately, you get either an agent that keeps repeating the same mistakes (feedback-only) or an agent that encodes rules but never finds out whether they worked (feed-forward-only)", [Böckeler 2026a]

**강사 노트**

- 인용 근거: [Böckeler 2026a] 원문 확인. feedforward·feedback의 대응을 이 자리에서 한 번만 밝히고 이후 본문은 가이드·센서로만 부른다.
- 이 과정은 "하네스"를 이 한 장에서 이름으로 짚고, 이후 **검사**로 부른다. 새 어휘를 늘리지 않는다.
- 가이드만 둔 상태가 "세션 08. 위임"의 실행에서 드러났다 — 금지로 적은 저장소 밖 쓰기가 통과했다.

---

## 계산적과 추론적

센서는 **무엇이 판정하는가**로 나뉜다. 기계가 판정할 수 있는 것은 기계로 옮긴다.

**인용문**

계산적 — **결정적이고 빠르며** CPU가 돌린다. 테스트·린터·타입 검사·구조 분석, "Computational - deterministic and fast, run by the CPU. Tests, linters, type checkers, structural analysis", [Böckeler 2026a]

**표 — 두 종류의 센서**

| | 계산적 | 추론적 |
|---|---|---|
| **판정하는 것** | CPU | LLM |
| **같은 입력에** | 같은 결과 | 다를 수 있다 |
| **비용** | 초, 거의 공짜 | 분, 호출마다 돈 |
| **주문한다에서** | 컴파일·테스트·의존 규칙·결합도 | 금액 계산의 심사 |

- **옮길 수 있으면 옮긴다** — 사람이 읽어 판정하던 것을 계산적 센서로 내리면 루프 안에서 공짜로 돈다.
- **추론적 센서는 한 번으로 끝내지 않는다**.
  - 중요한 일이라면 LLM으로 하는 분석은 **여러 번 돌려 보는 것**이 낫다, "A useful reminder that when it matters, it's often worth running an LLM-based analysis multiple times, to get a fuller picture.", [Böckeler 2026b]

**강사 노트**

- 인용 근거: [Böckeler 2026a]·[Böckeler 2026b] 원문 확인. 두 분류는 센서와 가이드 모두에 적용되는 실행 방식의 구분이다.
- [Böckeler 2026b]의 모듈성 리뷰는 두 번째 실행에서 첫 실행이 찾지 못한 문제를 찾았고, 그 경험에서 나온 문장이다.
- 비용의 숫자는 교육용 어림이다. 실제 값은 모델과 코드 크기가 정하며, 그 판단은 "세션 10. 비용과 평가"가 다룬다.

## 04. 달라지는 것 3가지

## 독자·위치·빈도

같은 검사라도 **에이전트가 돌리게 되면** 셋이 달라진다.

**표 — 사람이 볼 때와 에이전트가 돌릴 때**

| | 사람이 볼 때 | 에이전트가 돌릴 때 |
|---|---|---|
| **메시지의 독자** | 사람 | 에이전트 |
| **검사의 위치** | 올린 뒤 | 커밋 앞 |
| **도는 빈도** | 변경마다 | 고칠 때마다 |

**인용문**

검사를 에이전트의 흐름에 연결해 두면 사람이 **일일이 조종하는 수고가 줄어든다**, "These checks reduce routine steering work for the human in the loop.", [Thoughtworks 2026]

  - 검사는 운영에 이르는 길의 **가능한 앞쪽**에 둔다 — 문제를 일찍 찾을수록 고치는 비용이 싸다, "You want to have checks as far left in the path to production as possible, since the earlier you find issues, the cheaper they are to fix.", [Böckeler 2026a]

- **독자가 바뀌면 메시지가 바뀐다** — 사람은 규칙 이름만 봐도 알지만, 에이전트에게는 **무엇을 어떻게 고치라**고 적어야 한다.
- **빈도가 바뀌면 속도가 기준이 된다** — 한 번의 작업에서 수십 번 도는 검사는 초 단위여야 한다.

**강사 노트**

- 인용 근거: [Thoughtworks 2026]의 feedback sensors for coding agents(Trial)와 [Böckeler 2026a] 원문 확인. Radar는 같은 검사를 사람이 보는 리포트로만 두면 이 이득이 없다는 점을 짚는다.
- 셋의 묶음은 이 과정의 정리다. 3가지가 각각 뒤 세 topic의 주제가 된다 — 독자는 「고치는 방법을 담은 메시지」, 위치와 빈도는 「루프 안과 CI를 구분하는 기준」이다.

---

## 고치는 방법을 담은 메시지

실패 메시지를 에이전트가 읽는다면, 그 메시지에 **고치는 방법**이 들어 있어야 한다.

**인용문**

고치는 방법을 함께 담은 린터 메시지는 **좋은 쪽으로 쓰는 프롬프트 주입**이다, "custom linter messages that include instructions for the self-correction - a positive kind of prompt injection", [Böckeler 2026a]

**표 — 같은 실패, 두 메시지**

| | 메시지 | 에이전트가 하는 일 |
|---|---|---|
| **규칙 이름만** | 의존 규칙 위반 | 짐작해서 이것저것 고친다 |
| **고치는 방법까지** | 포트를 선언해 그것만 쓰라 | 포트를 만들고 다시 돌린다 |

- **메시지에 담을 셋** — 무엇을 어겼는지, 어떻게 고치는지, 규칙이 어디에 적혀 있는지다.
- **가이드를 가리킨다** — 메시지가 맥락 문서를 가리키면, 에이전트가 그 문서를 읽고 고친다.

**강사 노트**

- 인용 근거: [Böckeler 2026a] 원문 확인. 프롬프트 주입을 좋은 쪽으로 쓴다는 표현이 원문의 것이다. 공격으로서의 프롬프트 주입은 "세션 08. 위임"의 「06. 위험과 피해 범위」에서 다뤘다.
- 실제 메시지는 「07. 의존 규칙 검사가 잡은 것」에서 출력으로 본다.
- 메시지를 길게 쓰는 것이 목적이 아니다. 에이전트가 **다음 행동을 정할 수 있는 만큼**이면 된다.

---

## 루프 안과 CI를 구분하는 기준

모든 검사를 루프 안에 넣으면 루프가 느려져 에이전트가 멈춘다. **속도와 비용**으로 구분한다.

**인용문**

하네스는 **스스로 조절하는 장치**처럼 앞서 주는 방향과 되돌아오는 신호를 합쳐 코드베이스를 원하는 상태로 유지한다, "The agent harness acts like a cybernetic governor, combining feed-forward and feedback to regulate the codebase towards its desired state.", [Böckeler 2026a]

**표 — 어디서 돌릴 것인가**

| 기준 | 루프 안 | CI |
|---|---|---|
| **도는 시간** | 초 단위 | 분을 넘어도 된다 |
| **비용** | 거의 공짜 | 호출마다 들어도 된다 |
| **결과** | 고칠 수 있다 | 사람이 판단한다 |

- **주문한다의 넷**은 루프 안에서 돈다 — 컴파일·수용 테스트·의존 규칙·결합도다.
- **금액 계산의 LLM 심사**는 CI에 남긴다. 느리고 호출마다 돈이 들며 결과가 매번 같지 않다.

**강사 노트**

- 인용 근거: [Böckeler 2026a] 원문 확인. "cybernetic governor"는 출력이 되돌아와 스스로 속도를 유지하는 조절 장치에 하네스를 견준 비유다. 번역에서 기계 이름을 쓰지 않고 그 작동으로 풀었다.
- 경계는 고정이 아니다. 모델이 싸고 빨라지면 추론적 센서도 루프 안으로 내려온다. 그 재점검은 "세션 10. 비용과 평가"가 다룬다.
- 전부 루프 안에 넣는 잘못은 「11. 잘못된 관행」에서 다시 본다.

## 05. 새 단계 — 모델·코드 적합성

기존 CI에 없던 단계가 하나 붙는다. **문서로 정한 모델과 코드가 어긋나지 않았는지** 보는 검사다.

**표 — 무엇을 대조하는가**

| 모델에서 정한 것 | 코드에서 볼 것 | 어긋남의 예 |
|---|---|---|
| **용어집의 이름** | 타입·필드의 이름 | 판매가와 단가가 한 이름이다 |
| **불변 조건** | 생성 시 검사 | 수량 0을 받아들인다 |
| **상태와 전이** | `enum`과 바꾸는 메서드 | 없는 상태가 코드에 있다 |
| **의존 규칙** | 패키지 의존 | 업무가 연동을 import한다 |

- **왜 새로 필요한가** — 사람이 코드를 쓰던 때는 모델을 읽은 사람이 그대로 옮겼다. 에이전트는 **문서를 읽고도 그럴듯한 다른 이름**을 만든다.
- **이름의 어긋남은 테스트가 잡지 못한다** — 동작이 맞으면 녹색이다. 사람이 읽거나 LLM이 심사해야 드러난다.

**강사 노트**

- 이 단계의 이름은 이 과정의 것이다. 적합성 함수(fitness function)라는 업계 용어가 아키텍처 특성을 기계가 재는 검사를 가리키며, 의존 규칙 검사가 그 예다.
- 4줄 중 의존 규칙만 완전히 계산적이다. 이름과 불변 조건은 일부만 기계가 본다 — 나머지가 「10. 사람의 리뷰가 볼 것」으로 간다.
- "세션 04. 정적 모델"의 용어집과 "세션 05. 동적 모델"의 상태 기계가 이 대조의 기준이다.

## 06. 명령 하나로 모으기

## 검사 명령 만들기

검사는 **명령 하나**로 돈다. 에이전트가 외울 것이 하나여야 루프가 단순해진다.

```kotlin
tasks.test {
    useJUnitPlatform()
}

// 업무 패키지는 연동·영속을 의존하지 않고, 업무 사이는 허용 목록만 쓴다.
val business = setOf("order", "payment", "delivery", "product")
val allowed = setOf("order->payment", "order->delivery", "order->product")

// ... dependencyRules·coupling 작업의 본문 생략

tasks.check {
    dependsOn(dependencyRules, coupling)
}
```

- **단계는 넷이다** — 빌드 도구를 고르고, 테스트를 붙이고, 검사 작업을 더하고, `check`에 매단다.
- **수강생이 만든다** — 과정이 구성 파일을 주지 않는다. 빌드 구성도 위임의 대상이다.

**강사 노트**

- 전체 구성은 `code/s09/pipeline/build.gradle.kts`다. 슬라이드는 검사를 매다는 3곳만 발췌했다.
- `gradle check`는 자바 세계의 관례적인 검사 명령이다. 다른 언어라면 그 생태계의 같은 자리를 쓴다 — 중요한 것은 **명령이 하나**라는 것이다.
- 수강생의 빌드 구성은 실습 8에서 에이전트가 만들었다. 여기서는 거기에 검사를 더한다.

## 주문한다의 검사 5가지

다섯 검사가 **세 범주**를 덮는다. 범주마다 센서가 따로 필요하다.

**인용문**

지금 유용해 보이는 범주는 **셋**이다, "The following are three categories that seem useful to me as of now", [Böckeler 2026a]

**표 — 검사 다섯과 범주**

| 검사 | 범주 | 종류 | 어디서 |
|---|---|---|---|
| **컴파일** | — | 계산적 | 루프 안 |
| **수용 테스트** | 행위 | 계산적 | 루프 안 |

- **결합도는 합격선이 아니다** — 클래스가 아는 것의 수를 신호로 볼 뿐 통과·실패를 구분하지 않는다.

**강사 노트**

- 결합도를 합격선으로 쓰지 않는 이유 — [Böckeler 2026b]의 실험에서 결합도 데이터는 사람에게 유용했지만 그 자체로 통과·실패를 구분하는 기준은 되지 못했다.
- 실제 출력에서 `OrderApplicationService`가 13으로 가장 높았다. 작업 단위가 하나 더 붙으면 이 수가 어떻게 되는지 보라고 말한다.

**인용문**

빈 저장소에서 시작하는 팀은 **첫날부터** 하네스를 만들기 쉽게 해 둘 수 있다 — 기술과 아키텍처의 선택이 그 코드베이스를 얼마나 조절할 수 있는지를 정한다, "Greenfield teams can bake harnessability in from day one - technology decisions and architecture choices determine how governable the codebase will be.", [Böckeler 2026a]

- **계약이 있어 테스트를 작성한다** — "세션 07. 설계 — 책임과 협력"의 사전·사후조건이 기대값이 된다.

**인용문**

**강사 노트**

## 07. 의존 규칙 검사가 잡은 것

에이전트가 결제 연동을 **주문 안에서 직접 조립**했다. 동작하고 테스트도 녹색이다.

```java
package order;

import payment.PaymentGateway;
import paymentadapter.CardPaymentAdapter;

// ... 재현 방법을 적은 주석 생략
public final class PaymentAssembly {
    public PaymentGateway paymentGateway() {
        return new CardPaymentAdapter();
    }
}
```

```text
> Task :dependencyRules FAILED        ... 빌드 실패 머리말 생략
> 의존 규칙 위반 1건
  order -> paymentadapter
      업무 패키지는 연동·영속을 알지 못한다. 포트 인터페이스를 선언해 그것만 쓰고,
      구현을 끼우는 일은 업무 밖에서 한다. 규칙은 docs/아키텍처.md에 있다.
```

- **테스트는 잡지 못한다** — 동작이 맞기 때문이다. 구조는 다른 검사가 본다.
- **메시지가 다음 행동을 정해 준다** — 조립을 업무 밖으로 옮기고 다시 돌린다.

**강사 노트**

- 실제 실행이다. 위반 파일은 `code/s09/pipeline/examples/violation/`에 있고, 재현 절차와 전체 출력은 그 폴더의 README와 `check-output-violation.txt`에 있다.
- 판정은 `jdeps`의 패키지 의존으로 한다. 허용 목록은 "세션 06. 아키텍처"의 「05. 의존 규칙」이 정한 것과 같다.
- 수강생에게 먼저 묻는다 — 이 코드는 왜 테스트를 통과하는가? 그다음 어느 검사가 잡아야 하는지 답하게 한다.

## 08. 녹색이 보장하지 않는 것

모든 검사가 녹색이어도 그것은 **쓴 검사만큼만** 보장한다.

**표 — 녹색이 말하지 않는 것**

| 녹색이 말하는 것 | 말하지 않는 것 |
|---|---|
| 작성한 수용 예가 통과했다 | 작성하지 않은 경로는 모른다 |
| 의존 규칙을 어기지 않았다 | 경계가 옳은지는 모른다 |
| 컴파일된다 | 업무 규칙과 맞는지는 모른다 |
| 결합도를 쟀다 | 그 수가 좋은지는 모른다 |

- **기대값이 추측이면 녹색도 추측이다** — "세션 01. 사람의 일과 AI의 일"의 첫 시도가 그랬다.
- **검사를 늘리는 것이 답은 아니다** — 무엇을 보장하고 싶은지 정하고 그만큼 작성한다.

**강사 노트**

- 이 장이 Anchor Message의 뒤쪽이다. 앞쪽("완료는 주장이다")은 「07. 의존 규칙 검사가 잡은 것」이 보였다.
- 실제 LLM 심사도 세 항목을 통과시켰지만 이름 하나를 지적했다 — 녹색과 지적이 함께 나오는 예다(`code/s09/pipeline/examples/amount-review-output.md`).
- 커버리지를 합격선으로 쓰는 잘못은 「11. 잘못된 관행」에서 다룬다.

## 09. 실패가 가리키는 결정

검사가 실패하면 코드를 고치기 전에 **그 실패가 어느 결정에서 왔는지** 본다.

**표 — 실패와 되돌릴 결정**

| 실패한 검사 | 실패의 모습 | 되돌릴 곳 |
|---|---|---|
| **컴파일** | 이름·타입이 맞지 않는다 | 없다 — 에이전트가 고친다 |
| **수용 테스트** | 기대한 금액이 아니다 | 작업 명세서와 수용 기준 |
| **의존 규칙** | 업무가 연동을 import한다 | 맥락의 의존 규칙 |
| **결합도** | 한 클래스가 계속 커진다 | 작업 단위의 분할 |
| **LLM 심사** | 금액을 정하는 곳이 둘이다 | 용어집 |

- **같은 입력으로 다시 돌리는 것은 복구가 아니다** — 명세가 빠뜨린 것은 몇 번을 돌려도 빠져 있다.
- **되돌릴 곳이 가이드라면** 고친 가이드가 다음 과제에서도 같은 실패를 막는다. 코드만 고치면 그 효과가 없다.
- **같은 실패가 세 번** 되풀이되면 멈추고 사람에게 묻는다.

**강사 노트**

- 표의 5줄은 「06. 명령 하나로 모으기」의 「주문한다의 검사 5가지」과 순서가 같다. 검사를 세우는 일과 실패를 읽는 일이 한 줄씩 이어진다.
- 같은 실패 3회의 멈춤은 "세션 08. 위임"의 「07. 종료 조건과 확인 지점」에 적은 멈출 조건이다. 3회는 교육용 값이다.
- 원인을 모른 채 재시도 횟수만 늘리지 않게 한다. 무엇을 바꿨고 결과가 어땠는지 기록이 남아야 판단할 수 있다.

## 10. 사람의 리뷰가 볼 것

검사를 다 세워도 **사람이 볼 것이 남는다**. 그것이 무엇인지 알아야 리뷰가 형식이 되지 않는다.

**인용문**

계산적 센서도 추론적 센서도 **영향이 큰 문제**는 믿을 만하게 잡아내지 못한다 — 문제를 잘못 짚는 것과 과한 설계와 필요 없는 기능과 지시를 잘못 이해한 것이다, "Neither catches reliably some of the higher-impact problems: Misdiagnosis of issues, overengineering and unnecessary features, misunderstood instructions.", [Böckeler 2026a]

**표 — 사람이 보는 셋**

| 놓치는 문제 | 주문한다에서 물을 것 |
|---|---|
| **문제를 잘못 짚음** | 고친 것이 실제 원인인가? |
| **과한 설계와 필요 없는 기능** | 요구에 없는 것이 생기지 않았는가? |
| **지시를 잘못 이해함** | 맡긴 작업 단위가 맞는가? |

- **셋 모두 검사의 녹색과 함께** 일어난다. 녹색이라서 넘어가면 그대로 쌓인다.
- **리뷰의 입력은 증거다** — 검사 출력과 실행 기록을 먼저 보고, 그다음 코드를 본다.

**강사 노트**

- 인용 근거: [Böckeler 2026a] 원문 확인. 3가지 문제의 이름이 원문의 것이고, 오른쪽 열은 이 과정의 적용이다.
- 실제 LLM 심사가 지적한 이름 문제는 셋 중 어디에도 들지 않는다 — 추론적 센서가 잡아 주는 쪽이다. 사람이 볼 것은 더 위의 판단이다.
- 리뷰에서 발견한 것을 모델과 가이드로 되돌리는 일은 「09. 실패가 가리키는 결정」과 같은 원칙을 따른다.

## 11. 잘못된 관행

## 테스트를 끄는 에이전트

실패를 없애는 가장 빠른 길은 **검사를 끄는 것**이다. 에이전트는 그 길을 고른다.

**표 — 끄는 모습과 막는 법**

| 끄는 모습 | 막는 법 |
|---|---|
| 실패한 테스트에 건너뛰기 표시 | 검사 파일의 변경을 승인 대상으로 |
| 기대값을 결과에 맞춰 고침 | 기대값의 출처를 수용 기준으로 고정 |
| 규칙을 허용 목록에 추가 | 규칙 파일을 사람만 고치게 |

- **지시문에 적는 것으로 막히지 않는다** — "검사를 끄지 마라"는 부탁이다. 막으려면 권한이 거절해야 한다.
- **녹색이 늘었는데 검사가 줄었는지** 본다. 수가 줄었으면 끈 것이다.

**강사 노트**

- "세션 08. 위임"의 Anchor Message와 같은 원리다 — 금지는 글로 적는 것으로 막히지 않는다.
- 검사 파일과 규칙 파일을 쓰기 금지로 두는 설정이 가장 단순한 수단이다. 실습 9에서 직접 적는다.

---

## 센서를 모두 루프 안에

검사를 늘리는 것이 좋다고 생각해 **전부 루프 안에** 넣으면 루프가 멈춘다.

**표 — 넣었을 때 생기는 일**

| 넣은 것 | 생기는 일 |
|---|---|
| 긴 통합 테스트 | 한 번 고치는 데 몇 분이 든다 |
| 추론적 심사 | 호출마다 돈이 들고 결과가 흔들린다 |
| 전체 보안 스캔 | 에이전트가 기다리다 멈춘다 |

- **루프 안의 기준은 초 단위**다. 넘는 것은 CI로 보낸다.
- **느린 검사를 빼는 것이 아니다** — 자리를 옮기는 것이다. 병합 전에 반드시 돈다.

**강사 노트**

- 변이 테스트(mutation testing)는 테스트의 질을 재는 센서이지만 느려서 주문한다에 두지 않았다.
- 어디까지 루프 안에 둘지는 한 번의 비용과 도는 횟수가 정한다. 그 계산은 "세션 10. 비용과 평가"가 다룬다.

## 12. 실습 9 — 검사 붙이기

**①로 시작해 답·질문·수정 요청을 주고받는다.** ②~④는 보완 예시다. ⑤로 MD를 만들고 필요하면 보완·재생성한다.

**투입물**

**프롬프트 — 요청사항 포함**

1. 이 저장소의 검사를 **명령 하나**로 모아라. 지금 있는 빌드 구성에 테스트를 붙이고, 그 명령에 매달아라. 아직 검사를 더하지는 마라.
2. [앞선 질문에 대한 답] [추가 질문·수정 요청] 실습 6에서 정한 **의존 규칙을 검사**로 만들어 같은 명령에 매달아라. 실패 메시지에는 무엇을 어겼는지와 **어떻게 고치는지**와 규칙이 적힌 곳을 함께 담아라.
3. [앞선 질문에 대한 답] [추가 질문·수정 요청] 의존 규칙을 **일부러 어긴 파일**을 만들어 검사가 실제로 막는지 확인하고, 출력을 보여라. 확인한 뒤에는 그 파일을 지워라.
4. [앞선 질문에 대한 답] [추가 질문·수정 요청] 루프 안에서 돌 검사와 CI에 남길 검사를 **속도와 비용**으로 나누어 적고, 검사 파일과 규칙 파일을 네가 고치지 못하도록 권한을 설정해라.
5. [앞선 질문에 대한 답] [추가 질문·수정 요청] 이번에 붙인 검사를 MD 하나로 정리해라. 검사 목록과 각 검사가 재는 **결정**, 명령, 실패 메시지의 예, 루프 안과 CI의 구분으로 구성하고 새 결정을 추가하지 마라. 5장을 넘지 않게 핵심만 남겨라.

**점검 항목**

1. **짝** — 검사마다 그것이 재는 **결정**이 무엇인지 적혀 있는가?
2. **메시지** — 실패 메시지에 고치는 방법과 규칙의 위치가 있는가?
3. **실제 확인** — 일부러 어겨서 검사가 막는 것을 **출력으로** 확인했는가?
4. **자리** — 루프 안과 CI의 구분에 속도·비용의 근거가 있는가?
5. **끄기 방지** — 검사와 규칙 파일이 에이전트의 쓰기에서 막혀 있는가?

**결과물**

**강사 노트**

- 수강생의 빌드 도구가 달라도 된다. **명령이 하나인지**와 **실패 메시지가 에이전트에게 쓰였는지**를 본다.
- 네트워크가 막혀 의존성을 받지 못하면 테스트 라이브러리 없이 돌리고 그 사실을 기록에 적게 한다.

## 13. 요약

검사는 결정마다 하나씩 붙고, **명령 하나**로 모이며, 실패는 코드가 아니라 결정을 가리킨다.

### 검사 파이프라인

- **이미 있는 것을 당긴다** — 빌드·테스트·정적 분석을 에이전트가 돌리는 자리로 옮긴다
- **달라지는 셋** — 메시지의 독자, 검사의 위치, 도는 빈도
- **명령 하나** — 루프 안은 초 단위, 느리고 비싼 것은 CI
- **새 단계** — 모델과 코드가 어긋났는지 보는 검사가 더해진다
- **녹색은 작성한 검사만큼만** 보장하고, 실패는 되돌릴 결정을 가리킨다

### 다음 세션

- "**세션 10. 비용과 평가**" — 지금까지 맡긴 것이 값했는지 재고 남은 단위도 맡길지 정한다.

**강사 노트**

- 모델에서 보완된 것 — 검사가 판정하지 않는 산출물이 드러났고, 모델·코드 적합성 검사가 더해졌다.
- 이 세션으로 과정의 오른쪽이 섰다. 다음 둘은 그 위에서 **계속 맡길 것인가**를 판단한다.

## 주문한다 — 검사 기록

**문서 형식 — 10pt**

"주문한다"의 검사 다섯을 명령 하나에 모았다. `./gradlew check`로 넷이 돌고 금액 계산의 심사만 CI에 남겼다. 검사마다 재는 결정과 그 결정을 정한 자리를 함께 적는다.

### 검사 목록과 재는 결정

| 검사 | 재는 결정 | 정한 곳 |
| --- | --- | --- |
| 컴파일 | — | — |
| 수용 테스트 | 요구 — 주문 금액과 사전조건 | 실습 7의 수용 기준 |
| 의존 규칙 | 아키텍처 — 업무와 연동의 경계 | 실습 6의 의존 규칙 |
| 결합도 | 설계 — 작업 단위의 크기 | 실습 7의 작업 단위 |
| 금액 계산의 심사 | 정적 모델 — 판매가와 단가의 구별 | 실습 4의 용어집 |

### 실패 메시지의 예

```text
> 의존 규칙 위반 1건
  order -> paymentadapter
      업무 패키지는 연동·영속을 알지 못한다. 포트 인터페이스를 선언해 그것만 쓰고,
      구현을 끼우는 일은 업무 밖에서 한다. 규칙은 docs/아키텍처.md에 있다.
```

### 자리와 끄기 방지

- **루프 안** — 컴파일·수용 테스트·의존 규칙·결합도. 모두 합쳐 수 초다.
- **CI** — 금액 계산의 LLM 심사. 호출마다 돈이 들고 결과가 매번 같지 않다.
- **끄기 방지** — 빌드 구성과 검사 작업, 규칙 목록은 에이전트의 **쓰기에서 막았다**.
- **확인** — 일부러 어긴 파일로 검사가 막는 것을 보고 지웠다.

**강사 노트**

- 이 별첨은 **강사가 예시 저장소에서 실제로 수행한 결과**를 실습의 결과물 형식으로 정리한 것이다. LLM의 응답을 옮긴 것이 아니다. 출력 원본은 `code/s09/pipeline/check-output.txt`·`check-output-violation.txt`, LLM 심사의 프롬프트와 응답은 `examples/`에 있다.
- **실제로 실행한 프롬프트** — 이 별첨은 LLM에 맡겨 받은 것이 아니라 강사가 저장소에서 직접 만든 결과다. 이 세션에서 LLM을 실제로 돌린 것은 금액 계산의 심사 하나뿐이고, 보낸 프롬프트 전문이 `code/s09/pipeline/examples/amount-review-prompt.txt`, 받은 응답이 같은 폴더의 `amount-review-output.md`다.
- 금액 계산의 심사는 Claude Opus 5.5로 2026-10-27에 1턴 실행했다. 세 항목을 통과시키면서 `PricedOrderItem` 주석이 단가를 "sale price"로 설명한다는 점을 지적했다 — 컴파일과 테스트가 잡지 못하는 종류의 지적이다.
- 수강생의 기록은 자기 빌드 도구와 자기 작업 단위로 쓰인다. 표의 「재는 결정」 열이 비어 있으면 검사와 결정의 짝이 끊어진 것이다.
