## 01. 세션 목표

요구사항은 **검증할 수 있을 때** 요구사항이고, **미정으로 남긴 것은 AI가 대신 결정한다**.

- **요구**와 **요구사항**을 가르고, 요구사항을 기능·업무 규칙·품질로 나눈다.
- **검증 가능함·명확함·단일함**으로 모호한 표현을 관찰할 결과로 바꾼다.
- 작업 단위마다 **사용자 이야기와 수용 기준**을 짝으로 적는다.
- 기대값을 **전제·사건·기대 결과**로 적고 허용과 금지를 함께 확인한다.
- 흐름의 분기에서 **범위·제외·미정**을 가른다.
- **요구사항 정의서와 작업 명세서**를 범위와 수명으로 나누어 AI의 입력으로 둔다.
- LLM 초안이 **근거 없이 확정한 것**을 질문으로 되돌린다.

**강사 노트**

- 1시간 30분 세션이다. "세션 02. LLM이라는 도구"가 맡길 형태를 골랐다면, 이 세션은 무엇을 맡기고 무엇으로 받아들일지 정한다.
- 입력은 업무 담당자의 요청 한 줄과 30분 회의 메모다. 정적·동적 모델과 설계의 상세는 뒤 세션이 맡는다.

## 02. 요청 한 줄에 요구사항은 없다

업무 담당자의 요청 한 줄은 고객이 **원하는 결과**를 말하고 시스템이 **충족할 조건**은 말하지 않는다 — 언제의 가격으로 청구하는지, 언제 배송을 요청하는지, 거절된 주문을 어떻게 둘지가 비어 있다. 확인에 사용할 주문은 **펜 2개**, 판매가 각 1,000원, 배송지 서울이고 금액은 **2,000원**이다.

## 03. 요구사항은 능력과 조건이다

요구는 이해관계자가 원하는 것이고, 요구사항은 **시스템이 충족할 능력과 조건**이다. 고객이 원하는 결과는 결제하고 배송받는 것이고, 시스템이 충족할 조건은 승인 뒤에만 배송을 요청하는 것이다. 요구사항은 **기능·업무 규칙·품질** 3가지로 나뉜다.

**인용문**

요구사항은 시스템이 따라야 할 **능력과 조건**이다, "Requirements are capabilities and conditions to which the system … must conform", [Larman 2004]

## 04. 검증할 수 없으면 요구사항이 아니다

요구사항이 요구사항이 되는 조건은 **검증할 수 있는가**다. "금액이 정확하다"는 읽는 사람마다 다른 금액을 떠올리므로 무엇을 확인해야 통과인지 말하지 않는다. 자격요건 3가지로 판정하고, 어긴 표현은 **관찰할 결과**로 바꿔 적는다.

- **검증 가능함** — 충족 여부를 측정하거나 증명할 수 있는가?
- **명확함** — 읽는 사람이 달라도 같은 뜻으로 읽히는가?
- **단일함** — 한 가지 결과만 적었는가?

**표 — 모호한 표현을 관찰할 결과로**

| 모호한 표현 | 어긴 자격요건 | 관찰할 결과 |
|---|---|---|
| **금액이 정확하다** | 명확함 | 판매가가 1,200원이 되어도 2,000원을 청구한다 |
| **거절을 처리한다** | 검증 가능함 | 결제대기로 남고 배송 요청은 0회다 |
| **거절되면 남기고 다시 결제한다** | 단일함 | 상태와 재결제를 기준 2개로 나눈다 |

- 바꿔 적은 쪽은 **구현 방법이 아니라 받아들일 결과**다. 2,000원을 어떻게 계산하는지는 요구사항이 정하지 않는다.

**강사 노트**

- 자격요건 3가지의 이름은 ISO/IEC/IEEE 29148:2018의 개별 요구사항 특성에서 가져왔다. 열네 특성 전부는 "객체지향 분석과 설계 실무"가 좋은 요구사항의 자격요건으로 다루고, 이 과정은 수용 기준을 판정하는 3가지만 사용한다.
- 표준 본문은 유료라 공식 미리보기의 목차로 절의 구분만 확인했으므로 그 범위의 주장만 한다.
- 왼쪽 표현을 보이고 어느 자격요건을 어겼는지 수강생에게 먼저 묻는다.

## 05. 스토리는 어떻게 자라는가?

## 카드는 대화를 시작할 만큼만 적는다

사용자 이야기는 완성된 명세가 아니라 **대화의 약속**이다. 카드는 누가 무엇을 왜 원하는지만 적고, 규칙은 **대화**에서 합의하며, 합의한 것은 **확인**에서 관찰할 값으로 적는다. 요구를 담는 형식은 여럿이지만 이 과정은 사용자 이야기로 쓰고 **수용 기준과 예**로 확인한다.

**인용문**

사용자 이야기에는 **카드·대화·확인**이라는 3가지 핵심 관점이 있다, "User stories have three critical aspects. We can call these Card, Conversation, and Confirmation.", [Jeffries 2001]

## 작게 나누되 가치는 자르지 않는다

스토리는 **고객이 얻는 가치** 하나를 담는 작은 단위다. 작게 만드는 것은 가치를 자르는 것이 아니라 **범위와 조건**을 줄이는 것이고, 테스트를 작성할 수 있을 만큼 뜻이 분명해야 작다고 할 수 있다.

**인용문**

스토리 카드를 작성한다는 것은 **원하는 것을 충분히 이해해 테스트를 작성할 수 있다**는 암묵적 약속이다, "Writing a story card carries an implicit promise: \"I understand what I want well enough that I could write a test for it.\"", [Wake 2003]

**표 — INVEST로 점검한 주문 스토리**

| 속성 | 뜻 | "주문한다"에서 확인한 것 |
|---|---|---|
| **Independent** | 독립적 | 상품·결제·배송 시스템이 운영 중이라 이 스토리만으로 끝난다 |
| **Negotiable** | 협상 가능 | 가격 확정 시점을 구현이 아니라 업무 담당자와의 대화로 정했다 |
| **Valuable** | 가치 있음 | 고객이 2,000원을 결제하고 서울로 배송받는다 |
| **Estimable** | 추정 가능 | 배송 요청 실패의 처리가 미정이라 그만큼 불확실하다 |
| **Small** | 작음 | 취소·환불·배송지 변경을 빼 범위를 한정했다 |
| **Testable** | 테스트 가능 | 2,000원·결제완료·배송 요청 1회로 확인한다 |

- **기술 층으로 쪼개지 않는다** — 결제 화면·주문 테이블만으로는 고객이 주문을 끝내지 못한다.

**강사 노트**

- Wake, INVEST in Good Stories, and SMART Tasks(2003)에서 6가지 속성과 Testable의 인용을 확인했다. 오른쪽 열은 주문 사례에 적용한 것이다.
- "주문한다"는 과정의 유일한 과제다. 이 장에서 별도 기능이나 추가 스토리를 만들지 않는다.
- 스토리 하나가 구현 작업 하나라는 뜻은 아니다. 작업 단위는 "세션 07. 설계 — 책임과 협력"이 나눈다.

## 06. 무엇을 받아들일 것인가?

## 수용 기준은 허용과 금지를 함께 적는다

수용 기준은 구현 방법이 아니라 **받아들일 결과**를 정한다. 업무 규칙 3가지에 예를 하나씩 두고 기본인 승인을 더해 4가지로 확인하며, 전제의 **카드 X는 거절되고 카드 Y는 승인된다**.

**인용문**

스토리의 행동은 곧 **수용 기준**이며, 시스템이 그 기준을 모두 충족하면 올바르게 행동하는 것이다, "A story’s behaviour is simply its acceptance criteria: if the system fulfils all the acceptance criteria, it’s behaving correctly; if it doesn’t, it isn’t", [North 2006]

**표 — "주문한다"의 수용 예 4가지**

| 예 | 전제·사건 | 기대 결과 |
|---|---|---|
| **승인** | 펜 2개·각 1,000원·카드 Y로 결제 | 2,000원·결제완료·서울 배송 요청 1회 |
| **가격 변경** | 주문 뒤 판매가 1,200원·카드 Y로 결제 | 청구 금액은 2,000원·결제완료 |
| **거절** | 카드 X로 결제·거절 | 결제대기·배송 요청 0회 |
| **재결제** | 카드 X 거절 뒤 같은 주문을 카드 Y로 | 결제완료·배송 요청 총 1회 |

- 거절 예에 **배송 요청 0회**를 함께 적어야 배송까지 요청해 버린 구현이 걸린다.
- **기대값의 근거는 업무 담당자가 정한 규칙**이다. 구현 결과를 복사하면 2,400원이 기준이 된다.

**강사 노트**

- North, Introducing BDD(2006)를 제공받은 원문으로 확인했다. 인용이 말하는 올바름은 주어진 수용 기준의 충족 범위이며 기준 자체의 누락까지 없다는 뜻은 아니다.
- 수용 기준은 조건이고 수용 테스트는 그 조건을 실행해 확인하는 수단이다. 검사 구성은 "세션 09. 검사 파이프라인"이 맡는다.
- 예 4가지는 공통 전제의 업무 규칙 3가지를 관찰하는 대표 예다. 모든 입력·장애 조합을 검증했다는 뜻이 아니다.

## 예는 대화에서 나온다

수용 기준의 예는 **업무 담당자와의 대화**에서 나온다. 구체적인 예로 기대 행동을 합의하는 협업 방식을 **행위 주도 개발**(BDD, Behaviour-Driven Development)이라 하고, 그 대화를 짧게 끝내는 방법이 **예시 매핑**이다.

**인용문**

BDD는 **업무 담당자와 기술 담당자 사이의 간극**을 줄이는 소프트웨어 팀의 협업 방식이다, "BDD is a way for software teams to work that closes the gap between business people and technical people", [Cucumber]

**인용문**

예시 매핑은 이 대화를 **짧고 생산적으로** 만들도록 설계된 방법이다, "Example Mapping is a method designed to make this conversation short and very productive.", [Cucumber: Example Mapping]

**도식 — Mermaid — 주문 스토리의 예시 매핑**

```mermaid
flowchart LR
  S["스토리: 주문하고 배송받는다"] --> R["규칙: 주문 생성 시 가격 확정"]
  R --> E1["예: 펜 2개 × 1,000원"]
  R --> E2["예: 판매가 변경 뒤에도 2,000원"]
  S --> Q["질문: 승인 뒤 배송 요청 실패?"]
  classDef story fill:#fff0ac,stroke:#666;
  classDef rule fill:#dceafa,stroke:#666;
  classDef example fill:#e3f1d7,stroke:#666;
  classDef question fill:#f7dada,stroke:#666;
  class S story;
  class R rule;
  class E1,E2 example;
  class Q question;
```

- **답하지 못한 질문을 새 규칙처럼 만들지 않는다** — 승인 뒤 배송 요청 실패의 처리는 미정으로 남긴다.
- **색은 예시 매핑의 표기다** — 스토리 노랑·규칙 파랑·예 초록·질문 빨강이다.

**강사 노트**

- Cucumber 공식 BDD 문서의 정의와 Example Mapping의 카드 색을 원문 확인했다. 카드 색을 외우는 것이 목표가 아니라 규칙·예·질문의 연결이 목표다.
- 발견·정식화·자동화는 **활동**, 예시 매핑은 발견의 **방법**, 전제·사건·기대 결과는 정식화의 **표기**다. 수강생이 셋을 나란한 선택지로 읽지 않게 이 자리에서 밝힌다.
- 도식은 업무 규칙 3가지 가운데 금액 규칙과 남은 질문을 대표로 보인 것이다. 원문의 this conversation은 수용 기준을 논의하는 대화를 가리킨다.

---

## 전제·사건·기대 결과로 적는다

발견한 예를 같은 뜻으로 읽히게 적는 뼈대가 **전제·사건·기대 결과**다. 준비할 상황, 발생한 사건, 관찰할 금액·상태·외부 요청을 차례로 적으면 그 문장이 그대로 수용 테스트가 된다.

**인용문**

**초기 맥락**이 주어지고 **사건**이 발생하면 **결과**를 확인한다, "Given some initial context (the givens), When an event occurs, Then ensure some outcomes", [North 2006]

```gherkin
Scenario: 거절 뒤 다른 카드로 결제한다
  Given 펜 2개, 주문 시 판매가 1000원, 배송지 서울의 결제대기 주문
    And 카드 X는 거절되고 카드 Y는 승인된다
  When 카드 X로 결제한 뒤 같은 주문을 카드 Y로 다시 결제한다
  Then 같은 주문은 결제완료다
    And 청구 금액은 2000원이다
    And 서울로의 배송 요청은 모두 합해 1회다
```

- **표기이지 활동이 아니다** — 이 형식으로 적었다고 발견의 대화를 한 것은 아니다. 적을 예는 대화에서 나온다.
- **재결제 예가 거절 예를 대신하지 않는다** — 거절 직후의 결제대기와 배송 요청 0회를 따로 확인한다.

**강사 노트**

- North 원문의 상황·사건·결과 문형을 주문 사례에 적용했다. Gherkin은 요구 예의 표현이며 이 세션에서 실행 코드를 만들었다는 뜻이 아니다.
- 도구 설치나 스텝 정의 구현은 다루지 않는다. 업무 수준의 사건을 화면 클릭이나 DB 필드 변경으로 바꾸지 않는다.

## 07. 분기에서 무엇을 약속하는가?

## 분기가 빠진 요구를 드러낸다

기본 흐름만 보면 요구는 다 적힌 것처럼 보인다. 결제 결과가 갈리는 자리에서 분기를 따라가면 **승인 외의 경로**가 드러나고, 거기서 아직 답하지 못한 요구가 나온다. 기본 흐름은 배송지 확정부터 주문 결과 확인까지이고, 카드 거절과 배송 요청 실패가 그 밖의 경로다.

**도식 — Mermaid — 주문 결제의 분기**

```mermaid
flowchart LR
  S["배송지 확정: 주문 생성"] --> P["카드로 결제"]
  P -->|승인| A["결제완료 · 배송 요청"]
  A --> R["주문 결과 확인"]
  P -->|거절| D["결제대기 유지"]
  D -->|다른 카드| P
  A -. 배송 요청 실패 .-> U["처리 정책 미정"]
```

- **거절은 알려진 반응이다** — 주문은 결제대기로 남고 고객은 다른 카드로 다시 결제한다.
- **배송 요청 실패는 아직 모르는 반응이다** — 승인은 끝났는데 다음에 무엇을 할지가 정해지지 않았다.
- **도메인 이벤트는 업무에서 발생한 사건의 이름**이다 — 결제되었다·배송이 시작되었다가 "주문한다"의 사건이다.
- 도메인의 활동에 관한 정보를 **일련의 개별 이벤트**로 모델링한다, "Model information about activity in the domain as a series of discrete events.", [Evans 2015]

**강사 노트**

- Evans, Domain-Driven Design Reference(2015)의 Domain Event 설명에서 인용했다. 도메인 이벤트를 메시지 큐나 비동기 통신으로 한정하지 않는다. "결제되었다"는 공통 용어의 사건이며 새 이벤트 타입이나 코드 이름을 만들지 않는다.
- 흐름은 공통 전제의 기본 흐름 3~5를 분기로 펼친 개념도다. 상태 기계나 통신 프로토콜이 아니며 상태 전이의 상세는 "세션 05. 동적 모델"이 맡는다. 같은 분기를 2곳에 적지 않는다.
- 대안·예외의 명칭보다 각 경우의 결과가 확정됐는지 묻는 것이 중요하다.
- 가격 변경은 별도 고객 행동이 아니라 같은 결제 흐름에서 금액 규칙을 확인하는 전제다.

## 08. 품질 요구는 조건과 수치로 바꾼다

요구사항이 어떤 결과를 제공할지 정한다면, 품질 요구사항은 그 결과를 **어떤 조건에서 어느 수준으로** 제공할지 정한다. 빠르다·안전하다 같은 말은 측정할 수 없으므로 조건과 수치로 바꿔야 검사가 된다. "주문한다"에서 묻는 관점은 **응답 성능·접근 통제·장애 대응** 3가지다.

**표 — 품질 요구를 검증 가능하게 만드는 질문**

| 품질 관점 | 요구 후보 | 검증 가능하게 만드는 질문 |
|---|---|---|
| **응답 성능** | 주문이 빠르게 처리된다 | 부하·측정 구간·허용 지연은? |
| **접근 통제** | 남의 주문을 바꿀 수 없다 | 누가 어떤 주문에 무엇을 하는가? |
| **장애 대응** | 요청 실패에도 주문이 남는다 | 유실의 정의와 후속 정책은? |

- **응답 성능**은 측정의 시작과 끝, 동시 요청 수, 외부 시스템의 응답 조건을 함께 정한다. 목표 시간과 그 안에 끝나야 할 비율을 합의한다.
- **접근 통제**는 누가 어떤 주문에 어떤 행동을 할 수 있는지 정한다. 본인 확인과 결제대기 주문의 변경 허용은 서로 다른 규칙이다.
- **장애 대응**은 실패한 지점과 지켜야 할 결과를 정한다. 배송 요청 실패 뒤 취소·재요청은 업무 담당자의 결정이 필요하다.

**강사 노트**

- 강의 시연의 회의 메모에는 품질 목표가 없다. 동시 100건·외부 응답 1초·95% 이상 3초는 course-design.md의 실습 품질 기준이며 강의 사례의 확정 요구가 아니다. 본문은 목표를 합의할 때 필요한 조건만 설명하고 실습 수치를 가져오지 않는다.
- 품질 관점의 이름과 검증 가능하게 만드는 질문은 "객체지향 분석과 설계 실무"의 품질속성 취급과 같게 적는다. 기준은 ISO/IEC 25010:2023의 품질 모델이며 공식 초록의 범위만 확인했다.
- 그 과정이 함께 다루는 사용 편의·변경 용이성은 "주문한다"의 범위에 없어 제외했다. 근거 없이 측정 수치나 서비스 수준을 확정하지 않는다.

## “주문한다” 요구사항 정의서

요구사항 정의서 한 장은 스토리·흐름·업무 규칙·용어·수용 예·미정을 **절로 나눠** 담는다. 같은 규칙을 절마다 다시 적지 않고, 모델·설계·코드는 이 문서가 정하지 않는다.

**문서 형식 — 10pt**

### 목적과 범위

- 고객이 **배송지를 확정하고 카드로 결제한다**. 상품·결제·배송은 외부 시스템이다.
- **취소·환불·배송 진행**은 제외한다. 화면·기술 설계는 이 문서에서 정하지 않는다.

### 사용자 이야기

- 고객으로서 선택한 상품의 배송지를 정하고 **카드로 결제해 배송받고 싶다**.

### 기능과 흐름

1. 배송지를 확정하면 주문이 결제대기로 생긴다.
2. 카드 승인을 요청한다. 승인되면 결제완료가 되고 배송을 요청한다.
3. 거절되면 결제대기로 남고 같은 주문을 다른 카드로 다시 결제할 수 있다.
4. 고객은 주문 결과를 확인한다.

### 업무 규칙

- **주문 금액**은 주문 생성 시점의 판매가와 수량으로 정하고 이후 판매가가 바뀌어도 유지한다.
- **배송 요청**은 승인 뒤에만 한다. 거절된 주문을 취소하지 않는다.

### 용어집의 시작

- **주문**(Order): 배송지 확정 시 생기는 주문. 승인 전에는 결제대기다.
- **주문 항목**(OrderItem): 주문한 상품과 수량에 관한 항목이다.
- **판매가**(salePrice): 상품 시스템이 제공하는 현재 가격이다.
- **주문 금액**(totalAmount): 주문 생성 시 가격으로 확정한 금액이다.

### 수용 기준의 대표 예

- **승인**: 펜 2개·각 1,000원·서울 → 2,000원 청구·결제완료·배송 요청 1회.
- **가격 변경**: 주문 후 판매가 1,200원 → 청구 금액 2,000원 유지.
- **거절**: 결제대기 유지·배송 요청 0회. 다른 카드 승인 뒤에는 같은 주문이 결제완료다.

### 품질과 미정

- **응답시간**의 측정 조건·목표와 **접근 권한**의 사용자·허용 행동은 업무 담당자에게 확인한다.
- **승인 뒤 배송 요청 실패**의 후속 처리는 미정이다. 취소·재요청을 임의로 정하지 않는다.

**강사 노트**

- 문서 형식의 강의 예다. course-design.md의 공통 전제만 담고 실습 1의 미정 H·B·F·E·G·I를 강의 정책으로 가져오지 않는다.
- 용어집의 영문명은 공통 영한 용어집을 따른다. 가격의 현재 값과 확정 값을 구분하는 상세는 "세션 04. 정적 모델"이 이어 간다.
- 수용 예 4가지 전체는 「06. 무엇을 받아들일 것인가?」의 「수용 기준은 허용과 금지를 함께 적는다」에서 확인한다. 이 문서는 거절과 재결제를 한 항목에 이어 적었다.

## 10. 중간 산출물은 복잡성이 정한다

불변의 뼈대는 **사용자 이야기와 수용 기준에서 코드·테스트까지**다. 도메인 모델과 아키텍처는 언제나 거치는 단계가 아니라, 업무 의미가 복잡하거나 기술 경계가 복잡할 때 더하는 중간 산출물이다. "주문한다"는 복잡성 2가지가 모두 중간이어서 용어집과 정적·동적 모델, 의존 규칙을 가볍게 더한다.

**도식 — Mermaid — 요구에서 구현·검증으로 가는 경로**

```mermaid
flowchart LR
  R["사용자 이야기 · 수용 기준"] --> C["구현 · 테스트"]
  R -. 업무 의미가 복잡하면 .-> M["도메인 모델"]
  R -. 기술 경계가 복잡하면 .-> A["아키텍처 · 설계"]
  M --> C
  A --> C
```

- **가격의 시점과 상태의 뜻이 흔들리면 도메인 모델이 필요하다** — 판매가와 단가를 가르는 일이 그 자리다.
- **넣는 기준은 그 산출물이 결과를 바꾸는가**다. 사람의 확인을 바꾸지 않으면 넣지 않는다.

**강사 노트**

- sw-engineering-principles.md의 도메인·기술 복잡성 두 축을 따른다. 실습의 작은 작업에서도 수용 기준과 검사는 빠지지 않는다.
- 화살표는 입력 관계이며 모든 프로젝트가 같은 문서 순서를 거쳐야 한다는 뜻이 아니다.
- 도메인 모델은 "세션 04. 정적 모델"·"세션 05. 동적 모델", 아키텍처와 설계는 "세션 06. 아키텍처"·"세션 07. 설계 — 책임과 협력"이 상세화한다.

## 미정 질문 15가지에 사람이 답한다

초안의 가치는 빈칸을 그럴듯하게 채우는 대신 **질문을 드러내는 데** 있다. 모르는 것을 질문 15가지로 남겼고, 사람이 답한 것은 요구사항 정의서로 들어가며 답하지 못한 것은 **미정**으로 남는다.

**표 — 초안의 질문과 사람의 결정**

| 초안이 남긴 질문 | 드러난 빈 결정 | 업무 담당자의 결정 |
|---|---|---|
| 주문은 언제 생기나요? | 요청과 회의 메모의 생성 시점 | 배송지를 확정할 때 |
| 승인 뒤의 상태 이름은? | 승인 결과를 표현할 업무 상태 | 결제완료 |
| 취소·환불이 범위인가요? | 이번에 약속할 기능의 경계 | 이번 범위에서 제외 |
| 배송 요청이 실패하면? | 실패 뒤 처리 정책 | 아직 정하지 못함 |

- 요청의 "결제하면 주문이 된다"대로면 거절된 주문은 없는 것이 된다. 업무 담당자는 **배송지를 확정할 때** 주문이 생긴다고 정했다.
- **내린 결정은 그것을 확인하는 예에 함께 적는다** — 판매가가 1,200원이 된 뒤에도 기대값은 2,000원이다.
- **미정이 있으면 그 경우까지 완료했다고 주장하지 않는다**. 배송 요청 실패는 "세션 11. 종합 실행"에서 거두어진다.

**강사 노트**

- 실제 기록: `code/s02/demo-results/`의 `prompt.txt`·`draft.md`·`result.json`·`README.md`. 최초 실행 위치를 보존해 provenance가 바뀌지 않게 했다.
- 본문 시연은 2026-10 기준이다. 실행일 2026-10-18, Claude Code 2.1.302(`claude -p`, 도구 없음), claude-opus-5-5. 46.0초·출력 4,668토큰은 그 실행 한 번의 기록이며 이번 작성일의 재실행이 아니다.
- 질문은 원문을 발췌하되 표에서는 문장을 짧게 적었다. 15가지 전체는 앞 장과 원본에 있다.
- 답은 초안이 스스로 정한 것이 아니다. course-design.md의 공통 전제에 확정된 강의의 업무 결정을 적용했다. 실습 1에는 강의보다 많은 미정 사항이 있으므로 이 답을 실습의 미정 전부에 대한 답으로 복사하지 않는다.

## 13. SDD는 새 단계를 더하지 않는다

명세 주도 개발(SDD, Spec-Driven Development)은 새로운 분석·설계 단계를 더하는 것이 아니라, 이미 하던 요구사항 명세·도메인 분석·설계의 결정을 **AI가 읽을 수 있게 남기는 것**이다. 활동 5가지는 그대로이고, 주문 금액 규칙 같은 결정이 **어디에 어떤 형태로** 적히는가가 달라진다.

**인용문**

명세 주도 개발은 AI로 코드를 작성하기 전에 **명세를 작성하는 것**이며, 명세가 사람과 AI의 **사실의 원천**이 된다, "Spec-driven development means writing a \"spec\" before writing code with AI (\"documentation first\"). The spec becomes the source of truth for the human and the AI", [Böckeler 2025]

**표 — 기존 활동과 AI가 읽는 것**

| 기존 활동 | 사람이 결정하는 것 | AI가 읽는 것 |
|---|---|---|
| **요구 확인** | 원하는 결과와 그 이유 | 업무 조건과 사용자 이야기 |
| **요구사항 명세** | 기능·업무 규칙·품질·기대 결과 | 요구사항 정의서와 작업 명세서 |
| **도메인 분석** | 업무 개념·관계·규칙 | 도메인 모델과 용어집 |
| **설계** | 책임·협력·경계 | 설계와 연동 규격·의존 규칙 |
| **검증** | 무엇이 통과를 뜻하는가? | 수용 기준과 검사 결과 |

- **온톨로지는 네 번째 산출물이 아니다** — 개념과 관계의 뜻을 명시한다는 관점이며 도메인 모델과 관심이 겹친다.
- 온톨로지는 **개념화의 명시적 명세**다, "An ontology is an explicit specification of a conceptualization.", [Gruber 1993]
- **명세의 상세함은 분량이 아니라 빠진 결정이 기준이다**. 항목을 늘려도 가격 확정 시점이 없으면 판매가가 1,200원이 된 뒤의 청구 금액을 판단할 수 없다.
- **미정은 자세히 적는 것으로 채워지지 않는다**. 배송 요청 실패의 처리는 업무 담당자에게 묻고, 답을 받기 전에는 기대값을 만들지 않는다.
- **구현과 검사에서 발견한 것은 원인이 된 결정으로 돌아간다**. 먼저 작성했다는 이유로 명세를 고정하지 않는다.

**강사 노트**

- Böckeler의 SDD 작업상 정의와 Gruber, A Translation Approach to Portable Ontology Specifications(1993)를 원문 확인했다. 온톨로지와 도메인 모델이 모든 분야에서 같은 산출물이라는 주장은 하지 않는다.
- 기존 공학 활동과의 대응은 sw-engineering-principles.md와 과정의 원전 적용 결정이다. 모든 분석·설계 산출물을 하나의 요구사항 명세로 취급하지 않는다.
- specification은 정밀하게 표현했다는 성질이며 대상에 따라 요구사항의 명세·개념화의 명세가 된다. 개념 모델의 상세는 "세션 04. 정적 모델"이 맡고 형식 언어·추론 엔진은 범위 밖이다.
- 문서 과잉은 Böckeler의 SDD 도구 사용 경험에 나온다. 작은 버그 하나가 사용자 이야기 4개·수용 기준 16개가 된 사례인데, 그 버그가 무엇인지 모르면 수만 남으므로 본문에 싣지 않는다. 수강생이 물으면 출처를 들어 말한다.

## 14. 잘못된 관행

잘못된 관행은 모두 같다 — **업무 담당자에게 물어야 할 것을 묻지 않고 문서로 채운다**. 칸을 채우고 테스트를 통과시켜도 빠진 결정은 그대로 남아 구현에서 틀린 값으로 나타난다.

**표 — 요구 명세의 잘못된 관행**

| 관행 | 놓치는 것 | 고치는 법 |
|---|---|---|
| **요청을 그대로 명세로** | 가격·승인·거절의 규칙 | 사건과 기대 결과를 질문한다 |
| **템플릿만 채우기** | 대화와 수용 기준 | 구체적인 예로 뜻을 합의한다 |
| **승인 예만 확인** | 가격 변경·거절·재결제 | 규칙을 가르는 대표 예를 더한다 |
| **미정을 제외로 바꾸기** | 아직 답하지 못한 정책 | 질문과 미확정 사실을 남긴다 |
| **명세에 모두 복제** | 명세·모델·설계의 책임 | 대상과 원천을 가려 참조한다 |

- 첫 시도의 **2,400원**은 가격 확정 시점을 비워 둔 채 코드와 테스트까지 간 결과다. 요청을 되풀이하지 않고 **빠진 결정과 기대값**에 반영한다.

**강사 노트**

- 「13. SDD는 새 단계를 더하지 않는다」의 구분을 적용해 spec이라는 이름만으로 새 문서를 더하거나 모든 모델을 넣지 않게 한다.
- 수용 기준이 정해졌어도 그 기준을 확인하는 테스트가 맞는지는 별도 검증이 필요하다. 검사 구성은 "세션 09. 검사 파이프라인"이 맡는다.

## “주문한다” 요구사항 정의서

**실제 LLM 응답**

**문서 형식 — 10pt**

고객이 장바구니의 상품과 수량을 바탕으로 배송지를 지정하고, 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인할 때까지의 요구사항과 수용 기준을 정의한다.

### 목적과 범위

- 상품 조회와 장바구니 구성은 전제다.
- 상세 범위는 공통 흐름 3~5단계인 배송지 지정, 결제, 주문 결과 확인이다.
- 상품·결제·배송 시스템은 외부 시스템으로 연계하며 내부 기능은 재구현하지 않는다.

### 사용자 이야기

고객으로서 장바구니의 상품과 수량을 기준으로 배송지를 지정하고 카드 승인을 받아 주문을 성립시킨 뒤 그 결과를 확인하고 싶다.

### 핵심 기능과 업무 규칙

- 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
- 주문자와 수령인은 같은 사람으로 본다.
- 주문 금액은 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액이다.
- 주문 생성 뒤 판매가가 변경되어도 주문 금액과 카드 승인 요청 금액은 바뀌지 않는다.
- `결제대기` 주문의 상품·수량·배송지는 변경할 수 없다. 변경하려면 새 주문을 생성한다.
- 결제 수단은 카드만 허용한다.
- 카드 승인이 거절되면 같은 주문을 `결제대기`로 유지하며 다른 카드로 재결제할 수 있다.
- 카드 승인이 완료되면 같은 주문이 성립하고 상태가 `결제완료`가 된다.
- 배송 요청은 카드 승인 완료 뒤 해당 주문의 확정된 배송지로 보낸다.
- 주문 쪽에서 재고를 별도로 확보하지 않고 상품 시스템의 판단을 따른다.
- 결제 응답을 확정할 수 없으면 승인 또는 거절로 간주하지 않는다.
- 본인 주문에 대해서만 조회 또는 변경 요청의 권한을 인정한다. 권한이 있더라도 실제 변경 가능 여부에는 주문 상태와 업무 규칙을 적용한다.
- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.

### 기본 용어집

- **주문(Order):** 배송지가 지정되어 생성된 거래 기록
- **주문 항목(OrderItem):** 주문에 포함된 상품, 수량 및 주문 생성 시점의 판매가
- **판매가(salePrice):** 상품 시스템이 제공하는 상품 가격
- **주문 금액(totalAmount):** 각 주문 항목의 주문 생성 시점 판매가에 수량을 곱하여 합한 금액
- **주문 생성:** 배송지 지정에 따라 주문이 기록되고 `결제대기`가 되는 것
- **결제대기(PENDING_PAYMENT):** 주문은 생성됐지만 카드 승인이 완료되지 않은 상태
- **주문 성립:** 카드 승인이 완료되어 같은 주문이 `결제완료`가 되는 것
- **결제완료(PAID):** 카드 승인이 완료되어 주문이 성립한 상태
- **주문 결과 확인:** 카드 승인 응답에 따른 주문 상태와 결과를 확인하는 것

### 공통 흐름

1. **상품 조회 — 전제:** 고객이 상품을 조회한다.
2. **장바구니 — 전제:** 고객이 상품과 수량을 장바구니에 담는다.
3. **배송지 지정:** 배송지를 지정하면 주문 생성 시점의 판매가로 주문 금액을 확정하고 `결제대기` 주문을 생성한다.
4. **결제:** 고객이 주문 금액으로 카드 승인을 요청한다.
  - 승인되면 같은 주문이 `결제완료`가 되고 배송을 요청한다.
  - 거절되면 같은 주문을 `결제대기`로 유지하고 배송을 요청하지 않는다. 고객은 다른 카드로 재결제할 수 있다.
5. **주문 결과 확인:** 고객이 카드 승인 응답에 따른 주문 결과를 확인한다. 이는 별도 통지 여부나 담당 시스템을 확정하지 않는다.

### 대표 수용 예

공통 전제는 펜 2개, 주문 생성 시 판매가 개당 1,000원, 주문 금액 2,000원, 배송지 서울인 같은 주문이다.

#### 1. 카드 승인

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 Y에 2,000원으로 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제완료`가 되고 승인 결과와 승인 요청 금액 2,000원을 확인할 수 있다. 서울로의 배송 요청은 1회다.

#### 2. 주문 생성 뒤 가격 변경

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 펜 판매가가 개당 1,200원으로 오른 뒤 카드 Y에 승인을 요청하고 승인 응답을 받는다.
- **기대 결과:** 같은 주문의 주문 금액과 승인 요청 금액은 2,000원이고 상태는 `결제완료`다. 승인 결과를 확인할 수 있으며 서울로의 배송 요청은 1회다.

#### 3. 카드 승인 거절

- **전제:** 주문 상태가 `결제대기`다.
- **사건:** 카드 X에 2,000원으로 승인을 요청하고 거절 응답을 받는다.
- **기대 결과:** 같은 주문이 `결제대기`로 유지되고 배송 요청은 0회다. 다른 카드로 같은 주문의 결제를 다시 요청할 수 있다.

#### 4. 거절 뒤 같은 주문의 재결제

- **전제:** 카드 X의 승인이 거절된 주문이 `결제대기`이고 배송 요청은 0회다.
- **사건:** 카드 Y에 같은 주문의 결제를 2,000원으로 다시 요청하고 승인 응답을 받는다.
- **기대 결과:** 새 주문이 생성되지 않고 같은 주문이 `결제완료`가 된다. 카드 Y의 승인 요청 금액은 2,000원이며, 카드 X의 거절부터 카드 Y의 승인까지 서울로의 배송 요청은 총 1회다.

### 품질·접근 기준

#### 정상 품질 시험

- **전제:** 상품·결제·배송 외부 시스템은 정상 응답을 주는 테스트 대역이며, 각 외부 응답은 1초 이내다.
- **사건:** 공통 흐름 4의 카드 결제 요청을 동시에 100건 실행한다.
- **기대 결과:** 공통 흐름 4의 카드 결제 요청부터 5의 결과 수신까지 측정했을 때 100건 중 95건 이상이 각각 3초 이내에 완료된다.

#### 주문 접근

- 다른 고객의 주문에 대한 조회·변경 요청은 거절한다.
- 본인 주문이더라도 변경 가능 여부는 업무 규칙에 따른다. 따라서 `결제대기` 주문의 상품·수량·배송지는 변경할 수 없으며, 바꾸려면 새 주문을 생성한다.

    실습 1의 업무 조건을 읽고 "주문한다"의 요구사항 정의서 초안을 제안해라. 실습 2에서 이 일은 대화형 보조로 하고 사람이 초안마다 검토하기로 했다. 사용자 이야기 하나, 기능·업무 규칙·용어, 기본·대안·예외 흐름, 범위·제외·미정, 수용 기준을 포함해라. 요구사항을 쓰되 도메인 모델·아키텍처·기술 설계·코드는 만들지 마라. 실습 1에 없는 정책을 결정하지 말고 질문으로 남겨라. 조건이 부족하면 지금 필요한 질문을 하고 대화창에서 검토할 간결한 초안으로 답해라. 예시의 상품·수량·주소와 품질 목표는 아직 주어지지 않았다. 임의로 정하지 마라.

    [실습 1의 최종 업무 조건]
    # "주문한다" 업무 조건

    ## 범위
    - 대상: 고객이 장바구니에서 주문을 시작하고, 배송지를 확정한 뒤 카드 결제 승인을 받아 주문이 성립할 때까지다.
    - 연계 대상(이미 운영 중인 외부 시스템): 상품 시스템(판매가, 재고), 결제 시스템(카드 승인), 배송 시스템(배송 요청 수신).
    - 제외: 화면, 기술 설계, 결제 이후 운영(취소, 환불, 반품, 교환, 배송 진행), 카드 외 결제 수단, 배송비, 쿠폰과 할인.

    ## 주문 생성
    - 고객이 배송지를 확정하면 주문이 생기고, 주문 상태는 결제대기가 된다.
    - 주문자와 수령인은 같은 사람으로 본다.
    - [미정 H] 비회원 주문을 허용하는지, 허용한다면 결제대기 주문을 다시 찾을 때 본인을 어떻게 확인하는지 정해지지 않았다.

    ## 주문 금액
    - 주문 금액은 항목마다 주문 생성 시점의 판매가(단가)에 수량을 곱해 모두 더한 값이다.
    - 주문이 생긴 뒤 판매가가 오르거나 내려도 주문 금액은 바뀌지 않으며, 그 금액을 청구한다.

    ## 결제대기
    - 결제대기 중에는 상품, 수량, 배송지를 바꿀 수 없다. 바꾸려면 새로 주문한다.
    - 카드 결제가 거절되면 주문을 취소하지 않고 결제대기로 남겨, 고객이 다른 카드로 다시 결제할 수 있게 한다.
    - [미정 B] 결제대기의 기한과 기한이 지난 뒤의 처리가 정해지지 않았다. 구현에서 만료, 취소, 삭제, 결제 차단을 임의로 정하지 않는다.

    ## 결제와 주문 성립
    - 결제 수단은 카드뿐이다.
    - 카드 승인이 완료된 때 주문이 성립한다.
    - 결제 시스템의 응답을 확정할 수 없으면 그 응답을 실패로 바꾸지 않는다.
    - [미정 F] 응답을 확정할 수 없을 때 이후 처리(재결제 허용 여부 포함)가 정해지지 않았다. 구현에서 성공이나 실패를 임의로 확정하지 않는다.

    ## 재고
    - 재고는 상품 시스템의 판단을 그대로 따르며, 주문 쪽에서 재고를 따로 확보하지 않는다.
    - [미정 E] 승인 뒤 재고가 없을 때의 처리가 정해지지 않았다. 구현에서 승인 취소나 주문 상태 변경을 임의로 하지 않는다.

    ## 배송 요청
    - 배송 시스템에는 카드 승인 뒤에만 배송을 요청한다.
    - [미정 G] 승인 뒤 배송 요청이 실패했을 때의 처리가 정해지지 않았다. 구현에서 승인 취소, 주문 상태 변경, 재요청 주체와 방식을 임의로 정하지 않는다.
    - [미정 I] 주문 확인 통지를 이 시스템이 보내는지, 다른 시스템의 통지로 대신하는지 정해지지 않았다.

    [앞선 질문에 대한 답]
    실습 예는 펜 2개·주문 생성 시 판매가 1,000원·배송지 서울로 하자. 카드 승인 뒤의 상태명은 결제완료다. 실습 품질 기준은 정상 시험에서 동시 요청 100건, 각 외부 응답 1초 이내일 때 요청부터 결과 수신까지 95% 이상 3초 이내이며, 본인의 주문만 조회·변경한다. 실습용 조건이며 운영 보장 수치가 아니다.
    비회원과 본인 확인(H), 결제대기 기한(B), 결제 응답 불명 처리(F), 승인 뒤 재고 부족(E), 승인 뒤 배송 요청 실패(G), 통지 담당(I)는 실습 1처럼 미정으로 남긴다. 재고 판단 시점도 지금 정하지 않는다. 승인 전 재고 부족이나 중복 요청 같은 새 정책을 여기서 더 만들지 않는다.
    [추가 질문·수정 요청]
    기능 요구사항의 '주문을 생성할 때 ... 재고 판단을 사용'은 근거 없는 시점 확정이다. 판매가를 확정하는 시점과 재고 판단 시점을 분리해 고쳐라. 주문 생성과 승인 뒤 주문 성립의 뜻도 구분해라. 외부 시스템은 상품·결제·배송이며 그 내부를 재구현하지 않는다. 요구의 범위에서 '도메인 모델 제외'라고 쓰면 시스템 기능의 제외로 오해한다. 도메인 모델·설계·코드는 이번 작성 산출물에서 다루지 않는다는 뜻으로 분리해라. 주문한다의 사용자 이야기는 하나로 유지하고 수용 기준은 관찰할 금액·상태·배송 요청으로 써라. 모든 오류를 나열하기보다 확정된 기본·대안 흐름과 대표 미정 분기를 간결하게 정리해라.

    [추가 질문·수정 요청]
    네 대표 예를 각각 전제·사건·기대 결과로 간결하게 적고, 미정 분기를 거절 테스트의 기대값으로 확정하지 마라. 배송 요청 실패를 취소나 자동 재요청으로 처리하는 기준도 만들지 마라. 같은 주문인지와 요청 횟수가 관찰 가능하게 써라. 기본 흐름은 공통 흐름 번호 1 상품 조회, 2 장바구니, 3 배송지 지정, 4 결제, 5 주문 결과 확인을 따르되 1~2는 전제이고 이번 상세 범위는 3~5다. 주문 결과 확인은 응답 결과를 확인하는 뜻이며 I의 별도 통지 주체를 확정하는 말이 아니다. 재고 판단 시점을 기능 요구사항으로 고정한 문장은 제거됐는지 확인해라. 반복되는 같은 규칙과 긴 항목은 합치되 정의와 관찰 결과가 없어지지 않게 해라. 문형·흐름·수용 예가 서로 다른 이름과 값을 쓰지 않는지 확인해라.

    [추가 질문·수정 요청]
    네 예의 2,000원은 결제 시스템에 승인을 요청하는 금액이다. 카드 X가 거절되면 실제 청구가 완료됐다고 적지 마라. 승인 예와 가격 변경 예는 승인 결과와 금액을, 거절 예는 결제대기·배송 0회·다른 카드 재결제 가능을, 재결제 예는 같은 주문·승인 요청 금액·배송 총 1회를 확인해라.
    대표 수용 예를 Given/When/Then(전제/사건/기대 결과)로 표현하되 Markdown의 짧은 목록으로 충분하다. 재고 판단 시점 등 원래 조건에 없는 질문은 발견 근거를 한 줄 남기고 미정으로 보존한다. 미정 B·F·E·G·H·I와 재고 판단 시점의 답을 새로 만들지 마라. '미정이니 운영에서도 아무 행동을 하지 않는다'를 정책으로 확정하지 마라. 필요한 정책을 담당자에게 확인해야 하며 그 분기까지 완료했다고 주장하지 않는다는 뜻이다. 조건·정의·흐름을 반복해 길어진 부분을 간결하게 묶고, 용어집에는 주문·주문 항목·판매가·주문 금액처럼 뒤 실습에서 읽을 기본 용어도 짧게 남겨라. 요구 명세에 분석·설계 산출물을 섞지 마라.
