# AI-native SW 공학 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** AI-native SW 공학 (`ai-native`)
- **총 교육시간:** 14시간, 2일(하루 7시간). 1시간은 강의 50분과 휴식 10분이다. **세션 시간은 참고값이다** — 기준은 세션 내용의 완성도이며, 시간은 최종 원고가 완성된 뒤 파일럿에서 확정한다.
- **대상:** SW 아키텍트, Back-End·Front-End 개발자, Cloud 엔지니어, AI 엔지니어
- **선수지식:** LLM 대화 도구나 코딩 에이전트를 업무에 써 본 경험, 자바 코드 독해, Git 사용, **빌드·테스트·정적 분석을 CI로 돌려 본 경험**

이 과정은 **독립된 과정**이다. 관통 사례는 "객체지향 분석과 설계 실무"(`ooad`)와 **같은 시나리오**이며 이름과 값도 같게 맞춘다(연계 조정). 두 과정의 경계는 사례가 아니라 가르치는 것이다 — OOAD는 모델의 상세와 표기법을, 이 과정은 결정과 검사를 가르친다(「3. 범위와 경계」). OOAD는 선수 과정이 아니므로, 이 과정만 듣는 수강생도 이해하도록 필요한 전제를 이 문서와 개요 세션이 직접 소개한다.

### 과정의 맥락

아래 성숙도·운영 조건은 **가정**이다. 사전 설문과 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 | 확인 방법 |
|---|---|---|
| **도메인** | 주문·결제·배송을 사용자로서 안다. 사례의 규칙은 과정이 정해 준다 | 사전 설문 |
| **기술** | LLM으로 코드·문서를 만들어 봤지만, 분석·설계의 결정을 명시하고 그것을 재는 검사를 갖춘 채 작업을 위임해 본 적은 적다. 자바 코드를 읽고 테스트를 실행하며 CI 파이프라인을 써 봤다 | 사전 설문, 실습 2 |
| **팀워크** | 코드 리뷰는 하지만 AI가 만든 결과를 무엇으로 받아들일지(수용 기준·증거) 팀이 합의해 본 경험은 적다 | 사전 설문, 실습 9 |

- **다루는 불확실성** — **기술 불확실성**이 중심이다. LLM의 생성은 비결정적이고 그럴듯한 추측을 섞으며, 모델·도구의 능력이 빠르게 바뀐다. 업무 불확실성은 단순한 주문 사례와 정해 둔 규칙으로 낮춘다.
- **깊이의 결정** — 깊이는 **대상의 성숙도와 과정의 목적**이 정하며 배정된 시간이 정하지 않는다. 이 과정은 AI 도입으로 SW 공학이 어떻게 바뀌는지를 다루므로 **범위를 유지하고 깊이를 낮춘다** — 기법의 숙련이 아니라 활동마다 사람이 내릴 결정과 그 결정을 재는 검사까지다. 성숙도가 낮은 **결정의 명시**(요구·모델·설계), **그 결정을 재는 검사**, **위임의 경계**, **비용 대비 효과의 판단**을 명시하고 먼저 검증한다. 도구별 기능·설정은 예로만 보이고 가르치지 않는다. 내용은 날짜가 있는 1차 원문을 따르며, 원고에는 그 내용을 확인한 **교재 작성 월**을 밝힌다(예: "2026-10 기준"). 과정을 열 때마다 원문을 다시 확인하고 작성 월을 갱신한다.
- **요구에서 코드까지의 경로** — 관통 사례인 주문한다는 **도메인·기술 복잡성 모두 중간**이다. 업무 규칙 3가지와 상태 다섯 개, 외부 시스템 연동(상품·결제·배송)이 있다. 수강생이 빈 저장소에서 끝까지 직접 만들고 검증해야 하므로 **강의와 실습이 같은 주문 시스템을 쓰고 도메인을 하나로 둔다**(2026-10-21). 그래서 불변의 뼈대(요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트)에 용어집과 정적·동적 모델·의존 규칙을 가볍게 더하고, 남기는 것은 요구사항 정의서·용어집·정적 모델·상태 기계·의존 규칙이다. 작업 명세서는 작업용이며 설계 세션에서 작업 단위로 쪼갠다(「4. 과정 전체 판단 원칙」).
- **운영 조건** — 가정: 20명 안팎, 개인 실습과 결과 공유. 실습 환경은 **Windows**를 전제하며(작성 환경만 macOS다), 수강생이 쓰는 **코딩 에이전트**(Claude Code, Claude Team 계정)와 Git, JDK 17 이상, Gradle이 필요하고 인터넷 연결이 있어야 한다. **과정이 제공하는 저장소·빌드 구성·코드는 없다** — 수강생은 **빈 저장소에서 시작해 실습 1~11로 요구부터 검사까지 직접 쌓는다**(「공통 용어와 전제」의 실습 저장소). **수강생은 첫 실습 전에 자기 PC에 저장소 하나를 만들고 끝까지 그 저장소를 쓴다.** 실습 1~7은 대화창에서 검토한 최종 MD를 저장소의 `docs`에 모으고, 실습 8부터는 같은 저장소에서 코딩 에이전트에게 맡겨 실제로 코드와 검사를 돌린다. ①~⑤는 대화 횟수가 아니라 단계이며 보완 대화와 최종 MD 생성은 필요한 만큼 반복한다.
- **환경 설정은 슬라이드가 안내한다** — 수강생이 **Claude Team에 로그인한 뒤 필요한 모든 단계를 과정 슬라이드가 그대로 따라 할 수 있게 안내한다**: 도구 확인(JDK·Gradle·Git·코딩 에이전트), 빈 저장소 초기화, 프로젝트와 빌드 구성 만들기, 에이전트의 권한 설정, 검사 명령 만들기. 별도 사전 설치 안내 문서나 강사 구두 설명에 맡기지 않는다. 안내는 그것이 필요한 세션의 슬라이드에 둔다 — 01(설치와 로그인, 실습 폴더), 08(저장소·빌드·권한), 09(검사 명령). 도구의 기능을 가르치는 것이 아니라 **실습을 진행하는 데 필요한 단계**를 빠짐없이 적는 것이다(2026-10-21).

**원전 적용 결정**

- **모델 용어의 공통 기준(2026-10-23)** — `guides/sw-engineering-principles.md`의 「도메인 모델·설계 모델과 정적·동적 관점」을 따른다. 세션 04와 05는 하나의 도메인 모델의 정적·동적 관점을 발전시킨다. 세션 06의 아키텍처와 07의 객체 책임·협력은 설계 모델의 서로 다른 범위다. 세션을 나눈 것이 독립 모델이나 고정 개발 단계를 뜻하지 않는다. 클래스·시퀀스·상태 기계는 모델의 표현이며, 표기 종류로 분석·설계를 구분하지 않는다. Larman의 정적 개념도 정의를 인용할 때는 그 범위를 밝히고, 정적·동적 관점을 포괄하는 이 과정의 도메인 모델 용례를 저자의 정의로 귀속하지 않는다.

- **SDD와 기존 분석·설계의 관계** — SDD를 별도의 분석·설계 단계나 새로운 산출물 체계로 가르치지 않는다. 기존에 하던 요구사항 명세·도메인 분석·설계의 결정과 산출물에 대응시키고, 이를 AI 구현의 입력과 검증 근거로 사용하는 접근으로 설명한다. 요구사항 명세는 필요한 결과·조건을, 도메인 모델은 업무 개념·관계·규칙을, 설계는 실현할 책임·협력·경계를 정한다. 온톨로지는 개념과 관계의 의미를 명시하는 관점으로 도메인 모델과 연결하며, SDD의 다음 단계나 별도 필수 산출물로 더하지 않는다. 온톨로지와 도메인 모델을 모든 용례에서 동일한 것으로 단정하지 않는다. 관계는 세션 03에서, 모델의 상세는 세션 04에서 설명한다(2026-10-22).

- **개발 방식의 구분** — LLM 이전·AI 지원(AI-assisted)·AI-native의 세 구분과 개발자·LLM의 역할 구분(「4. 과정 전체 판단 원칙」)은 원전의 분류가 아니라 **이 과정의 구분**이다. 원고에서 원전의 정의처럼 제시하지 않고, 각 구분을 받치는 원문(워크플로·에이전트의 정의, 하네스의 정의 등)만 인용한다(2026-10-06).
- **결정과 검사의 짝** — 활동마다의 결정과 그것을 재는 검사를 짝으로 보는 틀은 **V 모델의 대응 관계**를 이 과정에 적용한 것이다. **이름은 쓰고 출처는 달지 않는다** — 분야에 널리 알려진 통용 개념이며, 원문을 확인하지 못한 관점은 출처 없이 이 과정의 설명으로 쓴다는 「인용과 추론」 결정을 따른다. 단계의 순서(폭포수)로 가르치지 않고 **대응 관계로만** 쓰며, 작업 단위마다 한 바퀴 돈다(2026-10-21).
- **모델의 표기는 가르치지 않는다** — OOAD와 **같은 시나리오**를 쓰되, 정적·동적 모델의 상세와 표기법(기호·관계의 종류·상세화 절차)은 OOAD의 몫이다. 이 과정에서 다이어그램은 **LLM이 만들고 사람은 그것이 업무와 맞는지 읽고 판정한다** — 요구하는 수준은 그리는 숙련이 아니라 **읽고 틀린 것을 찾아내는 것**이다. 그래서 04·05의 산출물은 다이어그램과 함께 **용어·관계·규칙·전이의 목록**을 두고, 판정의 근거는 목록이 된다. 표기를 설명해야 할 때는 그 자리에서 읽는 법 한 줄만 붙인다(2026-10-21).
- **가드레일** — 이름 하나에 두 가지가 섞여 있다. 프롬프트에 적는 금지 사항은 **부탁**이며 가드레일이 아니고, 환경·도구가 실행 전에 거절하는 것만 가드레일이다. 그 실체는 **최소 권한**이라는 기존 원칙이다. 과정은 "가드레일"을 08에서 한 번 짚고 이후 **권한과 강제**로 부른다. 가이드(feedforward)·센서(feedback), 계산적(computational)·추론적(inferential) 구분은 [Böckeler 2026a]를 따른다(2026-10-21).
- **하네스는 검사 파이프라인이다** — 하네스를 새 어휘로 가르치지 않고 수강생이 이미 돌리는 CI 파이프라인에서 출발해 **달라지는 것**(실패 메시지의 독자가 에이전트다, 검사가 커밋 앞으로 당겨진다, 루프마다 돌 검사는 초 단위다, 모델–코드 적합성 단계가 새로 붙는다)으로 정의한다. 검사는 실무와 같은 빌드 도구로 묶어 **`gradle check` 하나**로 돌리고, 그 구성 파일도 수강생이 코딩 에이전트에게 맡겨 만든다 — 빌드 구성 역시 위임의 대상이다. CI/CD 도구의 구성과 배포 전략은 범위 밖이다(2026-10-21).
- **비용은 교환이다** — 비용은 토큰 단가가 아니라 **사람이 하던 일을 LLM으로 옮기는 결정**이며, 단기·중기·장기의 기준이 서로 다르다(「4. 과정 전체 판단 원칙」). 02에서 구조를, 10에서 판단을 다루고, 벤더 가격표와 조직의 비용 관리 체계는 넣지 않는다(2026-10-21).
- **위험** — NIST AI RMF는 위험을 식별·측정·관리하는 어휘로만 쓴다. 과정의 뼈대로 쓰지 않으며 조직 거버넌스(GOVERN)의 상세는 다루지 않는다. 생성형 AI의 위험 항목은 [NIST 2024], 실행 시점의 에이전트 보안 위험은 [OWASP 2025]를 참고한다(2026-10-06).
- **활용 방식과 자율성** — 과정의 기준은 수작업·대화형 보조·워크플로·에이전트의 4가지 방식이다. [Blount 외 2026]의 자율성 단계는 02에서 **보완 관점**으로 대응만 보이고, 형태를 대신하지 않는다(2026-10-06).
- **인용과 추론** — 인용은 원문에서 확인한 문장만 쓴다(`tools/verify-quote.js`). 원문으로 확인하지 못한 관점(예: Software 3.0, 부분 자율, 비결정적 추상, AI의 증폭 효과)은 출처를 달지 않고 이 과정의 설명(추론)으로만 쓴다. 그런 자료([Karpathy 2025]·[Fowler 2025]·[DORA 2025])는 참고 자료에 읽을거리로 둔다(2026-10-06).
- **AI 지원과 바이브 코딩** — 바이브 코딩(결과를 보지 않고 받아들이는 방식)은 개발 방식의 한 구분이 아니라 **규율이 없는 사용**이다. AI 지원·AI-native 모두에 생길 수 있으며, 증강 코딩·바이브 엔지니어링과 대비해 보인다(2026-10-06).
- **Technology Radar** — Radar의 링(Adopt·Trial·Assess·Caution)은 기법이 업계에서 어느 단계인지 보여 주는 신호로만 인용한다. 판(Vol. 34, 2026-04)을 밝히고 과정을 열 때마다 최신판으로 다시 확인한다(2026-10-06).
- **본질적 복잡성은 업무 규칙이다** — [Brooks 1986]의 본질적·우연적 복잡성을 이 과정은 이렇게 대응시킨다: 본질적 복잡성은 **업무 규칙**(도메인 지식), 우연적 복잡성은 업무 규칙을 **코드로 옮기는 일**이다. AI는 뒤의 것을 크게 줄였고 앞의 것은 사람이 정한다. 대응은 이 과정의 해석이며 Brooks의 문장이 아니다. 업무 규칙을 명시하는 수단으로 용어집·도메인 모델([Evans 2015]의 보편 언어)과 온톨로지([Gruber 1993])를 함께 다룬다(2026-10-07).
- **용어** — 업무 담당자가 정하는 주문 금액·배송 요청·결제 거절 같은 규칙은 **업무 규칙**으로 부른다. 요구의 작업 단위는 **사용자 이야기**(user story), 그 테스트 기준은 **수용 기준**이라 부른다. 짧게 가리킬 때는 **스토리**로 쓴다("스토리 하나", "스토리를 나눈다")(2026-10-20). 동기·비동기는 설계에서 정할 일이라 이 과정의 시나리오·요구에서 구분하지 않는다. 원고 본문은 코드 식별자(`pay` 등)와 사례 번호(O-1 등) 대신 한글 이름을 쓰고, 영문 이름은 코드 안에만 둔다(2026-10-07).
- **번역** — context는 **맥락**(OOAD·엑셀과 같음)으로 쓴다. workflow·agent·harness·guardrail·sensor는 음차하고 처음 나올 때 원어를 병기한다(워크플로(workflow)). human-in-the-loop는 **사람의 개입**, checkpoint는 **확인 지점**, eval은 **평가**로 쓴다(2026-10-06).
- **받은 원문** — 자동 접근이 막힌 원문은 `references/inputs/`에 두고 그 파일로 인용을 확인한다: [OpenAI 2025]·[DORA 2025]·[Blount 외 2026]은 PDF, [Lopopolo 2026]은 영문판 본문 추출(openai.com이 한국어판으로 자동 전환한다)(2026-10-06).

## 2. 과정 목표

이 과정은 **AI 도입으로 SW 공학이 어떻게 바뀌는가**를 다룬다. 바뀌지 않는 것은 요구·분석·아키텍처·설계에서 사람이 내리는 결정이고, 바뀌는 것은 그 결정을 코드로 만들고 검증하는 실행의 방식이다. 코딩의 자동화만 본다면 SW 공학이라 부를 이유가 없다 — 이 과정은 **공학 활동마다 사람이 무엇을 결정하고, 무엇을 AI에게 맡기며, 그 결과를 무엇으로 받아들이는지**를 하나의 기능으로 끝까지 확인한다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. LLM 이전·AI 지원·AI-native 개발을 구분하고, 공학 활동마다 사람이 결정할 것과 AI가 지원할 것을 나눈다.
2. LLM의 비결정성·추측·맥락 창의 한계와 비용의 구조를 알고, 작업마다 가장 단순한 충분한 활용 방식을 고른다.
3. 요청을 요구사항과 사용자 이야기로 구체화하고, 흐름의 분기에서 범위·제외·미정을 가르며, 받아들일 조건을 기대값으로 쓴다.
4. 용어집·개념·관계·불변 조건으로 정적 모델을, 사건·상태·전이·협력으로 동적 모델을 만들고, AI 초안에서 추측·모순·누락을 걸러낸다.
5. 경계와 의존 규칙으로 아키텍처를 정하고, 분석 모델에서 구현할 객체의 책임과 협력을 설계해 한 번에 검증할 작업 단위로 나눈다.
6. 작업 지시문·맥락·권한·종료 조건으로 위임 계약을 짜 구현을 에이전트에게 맡기고, 돌아온 결과가 설계대로인지 확인한다.
7. 활동마다의 결정을 재는 검사를 파이프라인으로 모아 에이전트가 스스로 돌릴 자리까지 당기고, 실패가 어느 결정을 가리키는지 읽어 모델을 보완한다.
8. 무엇을 맡기고 무엇을 맡기지 않을지 단기·중기·장기의 비용과 효과로 판단하고, 평가 세트로 모델·도구가 바뀐 뒤에도 같은 일을 맡길 수 있는지 확인한다.

## 3. 범위와 경계

**Core:** 개발 방식의 구분과 활동별 사람·AI의 역할, LLM이라는 재료의 성질과 비용의 구조, 작업 특성에 따른 활용 방식, 요구와 사용자 이야기·수용 기준, **정적 모델과 동적 모델**, 아키텍처(경계·의존 규칙·외부 연동), **설계(책임과 협력)와 작업 단위**, 위임 계약(지시문·맥락·권한·종료 조건), **검사 파이프라인과 실패가 가리키는 결정**, 비용 대비 효과의 판단과 평가 세트, 종합 실행과 되돌림.

**Non-scope:** 제품에 LLM 기능을 넣는 설계(이 과정은 SW **개발 작업**에 AI를 쓰는 것을 다룬다), **모델의 표기법과 그리는 숙련**(기호·관계의 종류·상세화 절차 — OOAD의 몫이며 이 과정은 읽고 판정하는 수준만 요구한다), 특정 vendor SDK·도구의 기능 설명, **CI/CD 도구의 구성과 배포 전략**, 모델 학습 이론, **프롬프트 요령 모음**, 벤더 가격표와 조직의 비용 관리 체계, 조직의 AI 전환과 거버넌스.

도구의 **기능을 가르치지 않는 것**과 실습을 진행할 **환경 단계를 안내하는 것**은 다르다. 후자는 슬라이드에 빠짐없이 둔다(「과정의 맥락」의 환경 설정).

**경계를 가르는 기준** — **도구가 바뀌면 달라지는 것은 가르치지 않고, 바뀌어도 남는 판단만 가르친다.**

**다른 과정과의 연계**

| 과정 | 연계 |
|---|---|
| 객체지향 분석과 설계 실무(`ooad`) | **같은 시나리오(주문 시스템의 주문한다)를 쓴다.** 경계는 사례가 아니라 가르치는 것이다 — **OOAD는 정적·동적 모델의 상세와 표기법**(기호, 관계의 종류, 상세화 절차)을, 이 과정은 **활동마다의 결정과 그 결정을 재는 검사, 사람과 AI가 나누는 일**을 가르친다. **이 과정은 표기법을 가르치지 않는다.** OOAD는 선수 과정이 아니므로 필요한 정의는 일부 중복을 감수하고 짧게 둔다. OOAD의 "세션 14. AI-native SW공학"(45분)은 이 과정의 미리 보기다 |
| SWQM | 품질 특성·검증 체계의 전문 판단은 SWQM이 맡는다. 이 과정은 위임 결과를 받아들이는 증거(검사·평가 세트)만 다룬다 |
| DevOps | CI/CD 파이프라인의 구성·배포 전략은 DevOps가 맡는다. 이 과정은 그 파이프라인을 좌표로 쓰고, 에이전트 때문에 달라지는 것만 다룬다 |
| DT→AX | 조직의 AI 도입·운영 모델은 DT→AX로 넘긴다 |

다른 과정의 내용을 이 과정의 완결성을 위해 복제하지 않는다.

## 4. 과정 전체 판단 원칙

- AI-native 개발의 핵심은 모델 호출이 아니라 **불확실한 생성 능력을 책임 있는 실행 경계와 검증 증거 안에 두는 것**이다.
- **결정과 검사는 짝이다.** 활동마다 사람이 내린 결정에는 그것을 재는 검사가 하나씩 있어야 한다. **왼쪽에서 정하지 않은 것은 오른쪽에 검사가 없고, 검사가 없는 것은 에이전트에게 맡길 수 없다.**
- **남는 것은 도메인 모델이다.** AI가 코드를 빠르게 만들수록 코드와 모델이 어긋나는 속도도 빨라진다. 모델을 보완하지 않으면 다음 작업의 입력이 틀린다.
- **모델은 한 번에 완성되지 않는다.** 세션 순서는 학습 순서이며 개발 절차가 아니다. 작업 단위마다 결정과 검사를 한 바퀴 돈다.
- 가장 단순한 형태로 시작하고, 증거가 요구할 때만 자율성을 높인다.
- **미정으로 남긴 것은 AI가 대신 결정한다.** 비워 두면 비는 것이 아니라 그럴듯한 추측으로 채워진다. 사람이 정할 결정은 위임 전에 정하거나, 모르면 멈추고 묻게 한다.
- **금지는 글로 적는 것으로 막히지 않는다.** 환경·도구가 실행 전에 거절해야 막힌다.
- 에이전트의 "완료"는 주장이다. 검사가 낸 증거와 확인 지점의 판단으로 받아들인다. **녹색은 쓴 검사만큼만 보장한다.**
- 실패는 같은 입력의 재시도가 아니라 원인이 된 결정(요구·모델·아키텍처·설계·맥락·경계·검사)으로 되돌려 고친다.
- **비용 대비 효과가 있을 때만 맡긴다.** 맡기는 것은 사람의 일을 LLM으로 옮기는 교환이며, 단기·중기·장기의 기준이 다르다.

**세션이 성립하는 조건** — **세션은 공학 활동 하나이거나, 그 활동을 AI에게 맡기는 결정 하나다. 둘 다 아니면 세션이 아니다.** 맥락·권한·가드레일·실패 대응은 그 자체로 세션이 되지 않고, 필요가 생기는 활동이나 위임의 결정 안에 들어간다(2026-10-21).

**개발 방식의 구분** — 이 과정의 구분이다(「원전 적용 결정」).

| 구분 | 작업의 단위 | 누가 무엇을 하는가 | 검증 |
|---|---|---|---|
| **LLM 이전** | 사람이 쓰는 코드 | 사람이 명세·설계·코드·테스트를 모두 쓴다. 도구(컴파일러·IDE·CI)는 결정적이다 | 사람이 쓴 테스트와 리뷰 |
| **AI 지원**(AI-assisted) | LLM의 제안 하나(코드 완성, 대화의 답) | 사람이 작업 흐름을 그대로 쥐고, LLM이 조각을 제안하면 사람이 읽고 받아들인다 | 사람이 제안마다 읽는다 — 리뷰가 병목 |
| **AI-native** | 맡긴 과제 하나 | 사람이 요구·모델·설계·경계를 정하고, LLM(에이전트)이 과제를 실행하며 검사의 증거로 스스로 고친다 | 파이프라인의 검사가 낸 증거와 확인 지점에서 사람의 판단 |

- AI-native는 "모든 작업을 에이전트에게"가 아니다. 작업마다 수작업·대화형 보조·워크플로·에이전트 중 가장 단순한 충분한 형태를 고른다(세션 02).
- 바뀌는 것은 사람의 일의 **위치**다. 코드를 직접 쓰고 읽던 일이 업무의 개념과 규칙을 정하고, 책임과 경계를 설계하고, 증거를 판단하는 일로 옮겨 간다.

**결정과 그것을 재는 검사** — 과정의 축이다. 왼쪽은 사람이 결정하고 AI가 초안을 내며, 오른쪽은 AI가 실행하고 사람이 증거로 받는다.

| 왼쪽 — 사람이 결정한다 | 산출물 | 오른쪽 — 그 결정을 재는 검사 | 세션 |
|---|---|---|---|
| 요구 | 요구사항 정의서, 사용자 이야기 | 수용 기준 → 수용 테스트 | 03 |
| 정적 모델 | 용어집, 개념·관계·속성, 불변 조건 | 불변 조건 테스트, 용어–코드 적합성 | 04 |
| 동적 모델 | 사건·상태·전이, 협력 | 상태 전이 테스트, 금지된 순서 검사 | 05 |
| 아키텍처 | 경계, 의존 규칙, 연동 규격 | 의존 규칙 검사, 대역을 쓴 통합 테스트 | 06 |
| 설계 | 책임·협력·인터페이스, 작업 단위 | 단위 테스트, 완료 조건 | 07 |
| 구현 | 코드 | 컴파일·린트 | 08 |

**AI-native에서 달라지는 것은 오른쪽의 위치다.** 원래 오른쪽은 사람이 나중에 올라가는 단계였는데, 이제 사람이 보기 전에 에이전트가 루프 안에서 돌린다. 그 오른쪽 전체가 검사 파이프라인이고, 그것이 하네스다(세션 09).

**활동마다 사람과 AI**

| 활동 | 사람이 한다 | LLM(에이전트)이 한다 |
|---|---|---|
| 문제·의도 | 문제와 의도를 정하고, 규칙·정책·위험 수용을 결정한다 | 요청에서 빠진 결정을 **질문으로** 드러낸다(정하지 않는다) |
| 요구 | 요구사항과 사용자 이야기, 범위·제외·미정, 수용 기준을 확정한다 | 초안을 작성하고 애매한 사항을 질문한다. 확정된 기대값을 바꾸지 않는다 |
| 정적 모델 | 업무 개념·관계·불변 조건을 결정한다 | 초안을 작성하고 모순과 누락을 제시한다. 근거 없는 개념을 만들지 않는다 |
| 동적 모델 | 사건과 상태·전이, 금지와 미정을 결정한다 | 초안을 작성하고 빠진 전이를 질문한다 |
| 아키텍처 | 무엇이 무엇을 알아야 하는지 정한다 | 대안을 비교하고 규칙 위반을 검사한다 |
| 설계 | 책임 배치와 협력, 작업 단위를 결정한다 | 설계 대안을 내고 분석 모델과의 불일치를 짚는다 |
| 위임 | 지시문·맥락·권한·종료 조건을 정한다 | 경계 안에서 일하고 벗어나거나 미정에 닿으면 멈춰 묻는다 |
| 구현·검증 | 무엇이 통과를 뜻하는지 정하고 검사를 유지한다 | 코드와 테스트를 만들고, 실패 메시지를 읽어 스스로 고친다. 검사를 끄거나 지우지 않는다 |
| 결과 판단 | 확인 지점에서 증거를 보고 수용하거나 되돌린다. 최종 책임을 진다 | 완료의 증거를 제시한다. 추론적 검사로서 리뷰를 보조한다 |
| 보완·판단 | 발견을 모델에 반영할지, 계속 맡길지 결정한다 | 잘못된 곳과 개선을 제안한다. 상한 안에서 재시도한다 |

**비용은 교환이다** — 맡기는 것은 사람의 일을 LLM으로 옮기는 결정이며, 기간에 따라 답이 달라진다(세션 10).

| | 재는 것 | 흔한 오판 |
|---|---|---|
| **단기** | 토큰 + 사람의 검토·수정 시간 vs 직접 했을 시간 | 생성이 빨라진 것만 보고 검토·수정이 늘어난 것을 빼지 않는다 |
| **중기** | 같은 일이 몇 번 오는가 | 한 번 쓸 일에 검사를 만들고, 열 번 올 일을 매번 손으로 한다 |
| **장기** | 남는 자산(모델·명세·검사)과 남는 부채(이해하지 못하는 코드, 검사 없이 쌓인 양, 도구에 묶인 구성) | 지금 비싼 것이 내년에 싸진다 — 오늘 깊이 투자할지, 내려올 때까지 사람이 할지 |

투자는 **모델 문서와 검사**에 하고 회수는 **반복**에서 한다. 과정은 판단의 틀과 재는 항목만 주고 수치는 주지 않는다.

**요구에서 코드까지의 경로** — `guides/sw-engineering-principles.md` 7절을 이 과정에 적용한다.

- **명세와 산출물** — 요구는 원하는 것, 요구사항은 시스템이 충족할 것이다. 요구사항의 명세는 범위·수명에 따라 **요구사항 정의서**(시스템 전체, 유지 — 용어집 포함)와 **작업 명세서**(스토리 하나, 작업용)로 나눈다. 작업 명세서의 범위·제외·미정·수용 기준은 요구의 결정이고(03), 작업 단위로 쪼개는 것은 설계의 결정이다(07).
- **불변의 뼈대** — 요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트. 사용자 이야기가 AI에게 맡기는 작업 단위이고, 수용 기준이 테스트가 된다. 요구를 담는 형식 중 **사용자 이야기와 수용 기준을 뼈대로 삼고**, 이벤트–반응 목록과 유스케이스는 정의와 쓰임만 소개한다.
- **흐름의 분기는 상태 기계가 맡는다** — 거절·중복·금지된 전이 같은 분기는 유스케이스의 대안 흐름 대신 **상태 기계와 업무 규칙 목록**으로 적는다. 같은 것을 두 곳에 적지 않는다. 03이 분기에서 범위·제외·미정을 가르고, 05가 그 분기를 전이로 닫는다(2026-10-21).
- **중간 산출물은 두 축으로 고른다** — 도메인 복잡성이 크면 작업 명세서와 도메인 모델을, 기술 복잡성이 크면 아키텍처를 더한다. 사다리처럼 차례로 더하지 않는다.

| | 기술 복잡성 낮음 | 기술 복잡성 높음 |
|---|---|---|
| **도메인 복잡성 낮음** | 스토리와 예 → 코드 | + 아키텍처 |
| **도메인 복잡성 높음** | + 작업 명세서 + 도메인 모델 | 모두 |

- **넣는 기준** — 그 산출물이 **에이전트의 결과나 사람의 확인을 바꾸는가?** 바꾸지 않으면 넣지 않는다.
- **오래 남는 것** — 요구사항 정의서(용어집 포함)·정적 모델·상태 기계·의존 규칙과 그것을 재는 검사다. 작업 명세서와 작업 단위만 작업마다 새로 쓴다.

**세 칸이 과정의 형식이다** — 세션마다 어떤 **산출물**이 남고, **사람이 무엇을 결정**하고, **AI가 무엇을 지원**하는지 같은 자리에서 답한다.

| | 세션 | 산출물 | 사람이 하는 일 | AI가 하는 일 |
|---|---|---|---|---|

| 06 | 아키텍처 | 의존 규칙, 외부 연동 규격 | 무엇이 무엇을 알아야 하는지 정한다 | 대안을 비교하고 규칙 위반을 검사한다 |

| 08 | 위임 | 위임 계약, 구현 코드 | 지시문·맥락·권한·종료 조건을 정한다 | 설계대로 구현하고, 경계에 닿으면 멈춘다 |

진행은 `무엇을 맡기는가 → 무엇을 결정하는가(요구·정적·동적·아키텍처·설계) → 어떻게 맡기는가(위임) → 무엇으로 받아들이는가(검사) → 계속 맡길 것인가(비용·평가) → 종합`이다. **이는 학습 순서이지 고정된 개발 절차가 아니다.** 세션마다 요약의 마지막에 **모델에서 보완된 내용**을 한 줄로 밝혀 반복을 보인다.

### S01 — 사람의 일과 AI의 일 (1시간 30분)

- **목표:** AI가 SW 공학에서 바꾼 것(업무 규칙을 코드로 옮기는 일)과 바꾸지 않은 것(업무 규칙)을 구분하고, LLM 이전·AI 지원·AI-native 개발을 구분하며, 공학 활동마다 사람이 결정할 것과 AI가 지원할 것을 나누고, 결정에는 그것을 재는 검사가 짝으로 있다는 과정의 지도를 받는다.
- **Anchor Message:** AI는 실행을 빠르게 하지만, 무엇이 옳은 결과인지의 판단과 책임은 사람에게 남는다.
- **세부 목차:** 세션 목표 / 첫 시도 — 요청 한 줄과 10분, 업무 담당자 리뷰에서 나온 문제 3가지 / 추측으로 채운 코드와 자기 코드를 확인한 테스트 / 본질적 복잡성과 우연적 복잡성 / 업무 규칙은 도메인 지식이다 / 개발 방식의 구분 — LLM 이전·AI 지원·AI-native, 바이브 코딩과 규율 / 활동마다 사람과 AI / 결정과 검사의 짝 — 과정의 지도 / AI에게 맡기지 않는 작업 / **실습 환경 준비 — 설치하고 확인할 다섯 가지**(코딩 에이전트·JDK·Gradle·Git·실습 폴더) / 실습 1 — 업무 조건 확인 / 요약
- **근거 자료:** [Brooks 1986](본질적·우연적 복잡성), [Beck 2025]·[Willison 2025b](규율), [Lopopolo 2026](사람의 역할), [Osmani 2025](AI-native 개발자)
- **사례에서 답하는 결정:** 첫 시도의 코드가 추측으로 채운 업무 규칙 3가지(주문 금액, 배송 요청, 결제 거절)와 업무 담당자가 정한 규칙. 문제 3가지가 정적(단가의 확정 시점)과 동적(순서·전이)으로 갈리는 것을 보여 04·05를 예고한다.
- **다이어그램·코드:** 과정의 지도(결정과 검사의 짝, 도식), 첫 시도의 결제 코드 한 장과 업무 규칙을 기대값으로 쓴 테스트 결과.
- **모델에서 보완되는 내용:** 없다. 업무 규칙 3가지가 리뷰에서 처음 드러난다.

### S02 — LLM이라는 재료 (1시간)

- **목표:** LLM의 비결정성과 그럴듯한 추측, 맥락 창의 한계와 비용의 구조를 알고, 작업 특성에 따라 수작업·대화형 보조·워크플로·에이전트 중 가장 단순한 충분한 형태를 고른다.
- **Anchor Message:** LLM은 빈칸을 추측으로 채우는 비결정적 재료다. 형태는 작업이 고르고, 비용이 그 선택을 제약한다.
- **세부 목차:** 세션 목표 / 그럴듯한 추측과 비결정성 / 맥락 창의 한계 — 길면 묻힌다 / 비용의 구조 — 입력·출력 토큰, 맥락은 호출마다 다시 들어간다, 캐싱, 반복 횟수 / 작업 특성 — 업무 규칙의 확정·절차의 확정·결과의 자동 확인·되돌리기 쉬움 / 증강 LLM과 4가지 활용 방식 / 워크플로와 에이전트 / 선택의 순서 — 가장 단순한 충분한 형태 / 자율성의 계단과 올리는 조건 / 세 방식의 실제 실행 기록 — 개입한 자리·턴·시간·토큰 / 잘못된 관행 / 실습 2 — 활용 방식 고르기 / 요약
- **근거 자료:** [NIST 2024](confabulation), [Anthropic 2025c](맥락의 한계·주의 예산), [Anthropic 2024](워크플로·에이전트, 가장 단순한 해법), [OpenAI 2025](에이전트가 맞는 작업), [Blount 외 2026](자율성 단계), [Anthropic 2025a](여러 에이전트의 비용)
- **사례에서 답하는 결정:** 첫 릴리스의 일 6가지를 작업 특성으로 나누고 활용 방식을 고른다. 같은 과제를 세 방식으로 실제 실행한 기록으로 토큰·시간·개입을 비교한다.
- **다이어그램·코드:** 증강 LLM과 워크플로·에이전트(도식), 세 방식의 실행 기록(표). 새 코드 없음.
- **모델에서 보완되는 내용:** 없다. 활용 방식 판단이 산출물로 남는다.

### S03 — 요구와 수용 기준 (1시간 30분)

- **목표:** 요청을 문제/기회 → 요구 → 요구사항으로 구체화해 사용자 이야기를 포함한 요구사항 정의서로 적고, 흐름의 기본·대안·예외 분기에서 이번 범위·제외·미정을 가르며, 받아들일 조건을 기대값(수용 기준)으로 쓴다.
- **Anchor Message:** 요구는 사람이 정한다. 미정으로 남긴 것은 AI가 대신 결정한다.
- **세부 목차:** 세션 목표 / 문제에서 요구사항으로 / 요구를 담는 형식 — 이벤트–반응 목록·유스케이스·사용자 이야기·도메인 이벤트 / 사용자 이야기 — 카드·대화·확인, 문형, INVEST / 흐름의 분기 — 기본·대안·예외와 범위·제외·미정 / 수용 기준 — 받아들일 조건을 기대값으로 / 예로 명세하기 — 예시 매핑과 전제·사건·기대 결과 / 품질 요구사항 / 요구사항 정의서와 작업 명세서 — 범위와 수명 / 명세 주도 개발 — 기존 요구·명세·분석·설계와의 관계, 온톨로지의 위치, 명세의 적정 수준 / 시연 — LLM이 쓴 초안과 남긴 미정 질문 / 잘못된 관행 / 실습 3 — 요구사항 정의서와 수용 기준 / 요약
- **근거 자료:** [Böckeler 2025](명세 주도 개발), [Gruber 1993](온톨로지의 위치), [Jeffries 2001](카드·대화·확인), [Evans 2015](도메인 이벤트), [Cucumber](예시 매핑·예로 명세하기), [Lopopolo 2026](수용 기준으로 옮긴다)
- **사례에서 답하는 결정:** 요청 한 줄과 회의 메모로 LLM이 초안을 쓰고 미정 질문을 남긴다. 사람이 답해 허용·거절 예 4가지(승인, 가격 변경, 거절, 거절 뒤 재결제)를 기대값으로 확정하고, 승인 뒤 배송 요청 실패는 **미정으로 남긴다**(11에서 거둔다).
- **다이어그램·코드:** 요구에서 코드까지의 경로(도식), 요구사항 정의서와 수용 기준의 예(문서 형식), 전제·사건·기대 결과. 코드 없음.
- **모델에서 보완되는 내용:** 용어집의 첫 항목과 요구사항 정의서가 생긴다. 미정 목록이 시작된다.

### S04 — 정적 모델 (1시간)

- **목표:** 도메인 모델의 정적 관점을 용어집·개념·관계·속성과 불변 조건으로 명시하고, LLM 초안이 만든 근거 없는 개념·속성을 걸러내며, 모델의 요소가 코드(타입·필드·값 객체)와 검사의 어디로 이어지는지 확인한다.
- **Anchor Message:** 같은 것을 같은 이름으로 — 용어집이 코드의 이름을 정한다.
- **세부 목차:** 세션 목표 / 도메인 모델의 목적과 정적·동적 관점 / 개념 모델·다이어그램·온톨로지와의 관계 / ERD와 클래스 다이어그램의 비교 / 분석·설계·구현의 구분 / 용어집 — 이름이 같으면 뜻도 같아야 한다 / 가격을 판매가와 단가로 나누기 / 도메인 모델 만들기 — 요구에서 개념 후보 찾기·초안·관계 / 속성과 불변 조건 / 주문 도메인 모델의 상세화와 구체 예 검증 / 모델을 만들 때 사람과 AI — 근거 없는 개념 지우기 / 코드와 검사로 이어지는 자리 / 잘못된 관행 / 실습 4 — 정적 모델 / 요약
- **근거 자료:** [Evans 2015](보편 언어), [Gruber 1993](온톨로지), [Larman 2004](개념 모델)
- **사례에서 답하는 결정:** "가격"을 판매가와 단가로 나눈다. LLM 초안이 만든 근거 없는 개념을 지운다. 불변 조건(주문 금액은 항목 단가×수량의 합)을 테스트로 재는 자리를 정한다.
- **다이어그램·코드:** 도메인 모델의 정적 구조를 표현한 클래스 다이어그램과 **용어·관계·불변 조건의 목록**(판정의 근거), 그 요소가 드러나는 자바 코드(타입·필드·값 객체)와 불변 조건 테스트. 표기법은 설명하지 않고 읽는 법만 한 줄 붙인다.
- **모델에서 보완되는 내용:** 용어집에 단가가 더해지고, 요구에서 도출한 개념·관계의 초안에 속성과 조건을 더해 주문 도메인 모델의 정적 관점을 명시한다. 동적 관점은 세션 05에서 보완한다. 본인 확인의 식별 의미와 결제 이력 구조는 미정으로 구별한다.

### S05 — 동적 모델 (1시간)

- **목표:** 같은 도메인 모델의 동적 관점으로 사건과 상태·전이, 금지된 전이와 아직 모르는 전이를 명시하고, 업무 규칙을 전이와 묶으며, 호출 순서와 상태 변경이 코드와 검사의 어디로 이어지는지 확인한다.
- **Anchor Message:** 순서와 전이를 그려 두지 않으면 AI가 그럴듯한 순서를 만든다.
- **세부 목차:** 세션 목표 / 도메인 모델의 동적 관점과 다섯 도식 / 사건이 상태를 바꾼다 / 상태와 전이 / 금지된 전이와 아직 모르는 전이 / 업무 규칙과 대표 예 / 업무 상호작용 — 시퀀스와 커뮤니케이션 / 업무 활동과 데이터 흐름 — 액티비티와 DFD / 상태 변경과 외부 요청은 다른 결정이다 / 승인 후 행동을 코드에 연결하기 / 대표 예를 실행해 확인하기 / 잘못된 관행 / 실습 5 — 동적 모델 / 요약
- **근거 자료:** [Larman 2004](상호작용), [Evans 2015](도메인 이벤트)
- **사례에서 답하는 결정:** 주문 상태와 전이를 확정하고 업무 규칙 3가지를 전이와 묶는다. 결제대기의 자기 전이(거절 뒤 재결제)와 금지된 전이(승인 전 배송 요청)를 적는다.
- **다이어그램·코드:** 상태 기계·시퀀스를 주요 다이어그램으로 사용하고 커뮤니케이션·액티비티·DFD의 질문과 차이를 같은 주문 사례로 소개한다. 분석 수준 도식과 **전이·금지된 순서의 목록**(판정의 근거), 상태를 바꾸는 메서드와 전이·순서를 재는 테스트. 표기법은 설명하지 않고 읽는 법만 한 줄 붙인다.
- **모델에서 보완되는 내용:** 결제대기의 자기 전이가 명시되고, 금지된 순서가 검사의 기대값이 된다.

### S06 — 아키텍처 (1시간)

- **목표:** 아키텍처 스타일 중 사례에 맞는 것을 고르고, 응집도·결합도와 의존성 역전에 비추어 업무 패키지와 연동·영속의 경계를 정해 의존 규칙으로 적으며, 외부 연동 규격을 맥락으로 두고 검사로 지켜지게 한다.
- **Anchor Message:** 경계는 글로 적고 검사로 지킨다.
- **세부 목차:** 세션 목표 / 아키텍처 스타일 — 무엇을 정하는가, 계층형·포트와 어댑터·모듈러 모놀리스·마이크로서비스의 비교와 이 과정이 쓰는 것 / 설계 원칙 — 응집도와 결합도, 단일 책임, 의존성 역전 / 업무 패키지와 외부 시스템 — 인터페이스로만 안다 / 의존 규칙 — 허용과 금지를 글로 적기 / 외부 연동 규격 / 검증하기 쉬운 구조 — 대역으로 업무 규칙 확인하기 / 규칙 위반을 검사하기 / 잘못된 관행 / 실습 6 — 아키텍처 / 요약
- **근거 자료:** [Martin 2000](기준 원전 — 의존성 역전, 패키지 의존의 순환 금지), [Cockburn 2005](포트와 어댑터), [Lewis·Fowler 2014]·[Fowler 2015c](마이크로서비스와 모놀리스 먼저), [Martin 2014](단일 책임), [Larman 2004](응집도와 결합도), [Böckeler 2026a](구조를 재는 센서)
- **사례에서 답하는 결정:** 주문 시스템은 포트와 어댑터 스타일을 쓴다. `order`·`payment`·`delivery`·`product`가 연동·영속을 import하지 않고, 결제·배송은 인터페이스로만 안다. 그 짝으로 의존 규칙 검사와 대역을 쓴 통합 테스트를 정한다.
- **다이어그램·코드:** 아키텍처 스타일의 비교(표), 패키지 다이어그램과 인터페이스 선언, 의존 규칙을 판정하는 검사.
- **모델에서 보완되는 내용:** 외부 시스템과 주고받는 이름이 용어집과 맞춰진다.

### S07 — 설계 — 책임과 협력 (1시간 30분)

- **목표:** 분석 모델에서 구현할 객체의 책임과 협력을 정하고, AI가 낸 설계 대안을 업무 의미와 경계에 비추어 판단하며, 한 번에 검증할 수 있는 작업 단위로 나눈다.
- **Anchor Message:** 분석 모델을 그대로 옮기는 것은 설계가 아니다. 책임과 협력은 사람이 정하고 AI가 대안을 낸다.
- **세부 목차:** 세션 목표 / 분석과 설계의 거리 / 책임 배치 — 업무 규칙을 누가 지키는가 / 협력과 인터페이스 — 설계 수준의 상호작용 / 상태 변경과 실패 처리의 자리 / 설계 원칙으로 판단하기 / AI가 낸 설계 대안 검토 — 분석 모델과의 불일치 / 단위 테스트가 설계의 짝이다 / 작업 단위 — 한 번에 검증할 크기 / 완료의 정의와 증거 / 기능 목록과 점진적 진행 / 잘못된 관행 / 실습 7 — 설계와 작업 단위 / 요약
- **근거 자료:** [Martin 2000](의존성 역전), [Martin 2014](단일 책임), [Larman 2004](책임 배치·상호작용), [Anthropic 2025d](기능 목록), [Böckeler 2025](명세와 설계의 경계)
- **사례에서 답하는 결정:** 주문 금액은 누가 계산하고 상태는 누가 바꾸는가. 주문 서비스가 사건을 받아 주문에 맡기고 저장한다. 작업 단위 4가지와 단위마다의 완료 조건을 정한다.
- **다이어그램·코드:** 설계 수준의 시퀀스 다이어그램과 인터페이스, 책임 배치의 두 대안(표), 단위 테스트.
- **모델에서 보완되는 내용:** 설계하며 드러난 규칙의 빈칸이 업무 규칙으로 돌아간다.

### S08 — 위임 (1시간 30분)

- **목표:** 작업 지시문·맥락·권한·종료 조건으로 위임 계약을 짜 실제 코딩 에이전트에게 구현을 맡기고, 돌아온 결과가 설계대로인지 확인한다.
- **Anchor Message:** 금지는 글로 적는 것으로 막히지 않는다 — 막으려면 환경이 거절해야 한다.
- **세부 목차:** 세션 목표 / 위임 계약의 네 가지 / 작업 지시문 — 무엇을 하라, 무엇을 가리킬 것인가 / 맥락 — 미리 넣을 것과 찾아 읽게 할 것, 점진적 공개, 긴 작업의 압축 / 권한 — 최소 권한, 자원과 동작을 좁히기, 강제와 지시 / 도구와 연결의 표준(개념) / 종료 조건 — 언제 멈추나, 미정과 어긋난 입력에 닿으면 묻는다 / 피해 범위와 되돌림 / 위험 — 치명적 삼박자와 프롬프트 주입 / 확인 지점 — 되돌리기 어려운 자리 / **빈 저장소에서 시작하기** — 저장소 초기화, 빌드 구성을 에이전트에게 맡기는 지시문, 권한 설정(따라 할 단계) / 맡긴 결과 보기 / 잘못된 관행 / 실습 8 — 위임과 구현 / 요약
- **근거 자료:** [Anthropic 2025c](맥락 엔지니어링·점진적 공개), [Anthropic 2025b](도구 설계), [MCP 2025](연결 표준), [OWASP 2025]·[Willison 2025a](위험), [NIST 2023](위험 어휘), [Anthropic 2026c](피해 범위·샌드박스·승인 피로), [Blount 외 2026](사람의 개입), [Anthropic 2024](확인 지점)
- **사례에서 답하는 결정:** `order`와 테스트에 쓰기·빌드·테스트 실행·브랜치 커밋은 허용, 실제 결제 호출·비밀 키 읽기·push는 금지. 에이전트가 실제 결제 샌드박스 주소를 설정에 넣으려 하고 환경이 거절한다. 읽힐 범위는 03~07의 산출물이며, 미정인 배송 요청 실패에 닿으면 멈춰 묻게 한다.
- **다이어그램·코드:** 위임 계약의 네 가지와 권한의 배치(도식), 작업 지시문(문서 형식), 거절된 호출의 기록, 돌아온 구현 코드.
- **모델에서 보완되는 내용:** 금지해야 할 외부 호출이 외부 연동 규격에 명시된다.

### S09 — 검사 파이프라인 (1시간 30분)

- **목표:** 03~07에서 정한 결정마다 검사를 붙여 명령 하나로 모으고, 에이전트가 스스로 돌릴 자리까지 당기며, 실패가 어느 결정을 가리키는지 읽고 녹색이 보장하지 않는 것을 안다.

## 6. 사례·실습 방향

이 과정은 AI와 협업하는 개발을 배우는 과정이다. 도메인 때문에 복잡도를 높이지 않는다. **강의와 실습 모두 같은 주문 시스템을 빈 저장소에서 개발한다.** 강의는 요청 한 줄로 시작한 첫 시도가 업무 리뷰에서 무너지는 데서 출발해, 요구·정적 모델·동적 모델·아키텍처·설계를 세우고 그것을 위임해 구현·검사한다. 실습은 같은 길을 수강생이 **처음부터 끝까지 직접** 걷는다.

- **과제는 하나다** — **주문한다**(흐름 3~5). 강의도 실습도 이 한 과제로 01~11을 관통한다. 기능을 여럿 두면 둘 다 얕아진다. 하나를 요구에서 검사까지 제대로 끝내는 것이 14시간의 전부다(2026-10-21).
- **반복은 작업 단위로 한다** — 07에서 과제를 **작업 단위 4개**로 쪼갠다. 08이 첫 단위를 맡겨 구현하고, 09가 검사를 붙여 루프를 돌리고, 10이 계속 맡길지 판단하고, 11이 **남은 단위를 그 환경으로 맡겨 기능을 끝낸다**. 새 기능이 아니라 같은 과제의 남은 부분이므로 환경이 자란 효과가 바로 드러난다.
- **강의** — OOAD와 같은 **주문 시스템**을 빈 저장소에서 개발한다.
- **실습** — **같은 과제**를 수강생이 빈 저장소에서 만든다. 과정이 주는 저장소·코드·빌드 구성은 없다 — 실습 1~7에서 요구·모델·아키텍처·설계를 직접 결정하고, 실습 8에서 저장소와 빌드를 세워 첫 단위를 맡기고, 실습 9에서 검사를 붙이고, 실습 11에서 남은 단위를 끝낸다. **빈 저장소에서 기능 하나가 검사와 함께 돌아가는 상태까지 수강생이 직접 간다**(2026-10-21).
- **도메인을 하나로 둔 이유** — 수강생이 14시간 안에 빈 저장소에서 끝까지 가야 한다. 새 도메인을 두면 업무를 이해하는 데 시간을 쓰고 이 과정이 가르치는 판단을 연습하지 못한다. 그래서 실습은 강의와 같은 주문 시스템을 쓰고, 도메인 이해 비용을 0으로 둔다(2026-10-21).
- **강의와 실습의 차이는 도메인이 아니라 결정이다** — 강의의 업무 규칙 3가지는 **그 회사의 업무 담당자가 정한 것**이고, 실습에서는 **수강생이 LLM과 대화해 자기 판단으로 정한다**(실습 1). 그래서 수강생의 요구·모델·설계·작업 단위는 강의와 다를 수 있고, 다른 결정이 어떤 코드와 검사로 이어지는지가 실습의 학습 내용이다. 별첨의 답은 정답이 아니라 **한 가지 가능한 답**이다.

실습은 수강생이 **LLM과 코딩 에이전트로 초안을 만들고 사람이 점검 항목으로 판단·보완**하는 방식으로 진행한다. ①로 시작하고 ②~④의 예시를 참고해 답변을 검토·보완하며 필요한 만큼 대화한다. ⑤는 최종 MD 생성 단계다. **별첨의 답은 마지막 프롬프트(⑤)로 받은 최종 MD 그대로이거나 그 요약**이며, 그 파일이 다음 실습의 투입물이다. 실습 8 이후의 별첨은 **실행 기록**(지시문, 검사 출력, 바뀐 파일)이다. 앞 산출물로 되돌릴 것이 생기면 해당 실습의 강사 노트에 적는다.

세션의 예시 코드(강의 저장소의 그 시점 상태)는 `sessions/code/sNN/`에 두고 컴파일·실행으로 확인한다.

### 강의 시나리오 — 주문 시스템을 AI와 함께 새로 만든다

수치(시간·개수·횟수)는 교육용 가정이다.

- **배경** — 생활용품 온라인 쇼핑몰이 외부 솔루션으로 받던 주문을 직접 만든 주문 시스템으로 옮긴다. 업무 담당자 1명이 주문 정책을 정하고, 테크 리드 1명과 개발자 2명이 코딩 에이전트를 쓴다. 출발점은 빈 git 저장소(자바)이며 상품·결제·배송 시스템은 이미 운영 중이다.
- **요청** — 업무 담당자의 요청은 한 줄이다: "장바구니에 담은 상품을 결제하면 주문이 되고 배송이 시작되게 해 주세요."
- **첫 기능** — 고객이 펜 2개(개당 1,000원)를 담고, 배송지(서울)를 정하면 주문이 결제대기로 생기며 주문 금액 2,000원이 정해진다. 카드로 결제해 승인되면 결제완료가 되고 배송을 요청한다.
- **업무 규칙** — 주문 금액, 배송 요청, 결제 거절(공통 전제). 처음 요청에는 없었고 업무 담당자가 정한다.

| 세션 | 장면 | 드러난 것과 결정 |
|---|---|---|
| 01 | 테크 리드가 요청 한 줄을 에이전트에게 준다. 10분 만에 자바 파일 15개·테스트 3개, 테스트는 모두 통과하고 카드 승인 데모도 성공한다 | 업무 담당자 리뷰에서 문제 3가지 — 가격이 바뀐 날 주문 금액이 바뀜, 거절된 주문에 배송 요청이 나감, 거절된 주문이 취소되어 다시 결제할 수 없음. 어느 결정이 비어서 그렇게 됐는지 지도에 표시한다 |

| 05 | 사건과 상태를 맞춘다 | 주문 상태와 전이를 확정하고 업무 규칙 3가지를 전이와 묶는다. 결제대기의 자기 전이와 금지된 순서(승인 전 배송 요청)를 적는다 |
| 06 | 결제·배송 연동을 어디에 둘지 정한다 | 업무 패키지는 연동·영속을 모른다. 외부 시스템은 인터페이스로만 안다. 그 짝으로 의존 규칙 검사와 대역 통합 테스트를 정한다 |
| 07 | 금액은 누가 계산하고 상태는 누가 바꾸는가 | 책임과 협력을 정하고 AI가 낸 두 대안을 업무 의미로 가른다. 작업 단위 4개와 단위마다의 완료 조건을 정한다 |
| 08 | 설계·수용 예·연동 규격을 주고 구현을 맡긴다 | 위임 계약 — 쓰기 범위·실행·커밋은 허용, 실제 결제 호출·비밀 키·push는 금지. 에이전트가 결제 샌드박스 주소를 설정에 넣으려 하고 환경이 거절한다. 미정에 닿으면 멈춰 묻는다 |
| 09 | 돌아온 코드 — 수용 테스트는 녹색인데 주문 서비스가 결제 연동을 직접 조립했다 | 의존 규칙 검사가 실패하고 고치는 방법을 담은 메시지로 에이전트가 스스로 고친다. 검사를 명령 하나로 모아 루프 안으로 당기고, 느린 것은 CI에 남긴다 |
| 10 | 첫 단위의 비용을 재고, 더 싼 새 모델로 바꾸려 한다 | 토큰·시간·검토 시간을 보니 남은 단위도 맡길 만하다. 평가 세트를 돌리니 새 모델은 가격 변경 과제에서 실패가 늘었다. 실제 고객 주소는 LLM에 보내지 않는다 |
| 11 | 남은 작업 단위 셋을 같은 패키지로 맡긴다 | 검사가 이미 있어 에이전트가 스스로 고치고 사람이 볼 것이 줄었다. 그런데 검사는 전부 녹색인데 배송 요청 실패 정책이 미정이라 에이전트가 추측으로 채웠다. 사람이 발견해 규칙을 정하고 모델·수용 예·검사에 더한다. 주문한다가 끝난다 |

### 공통 용어와 전제

이름과 값은 OOAD의 「재사용 사례의 공통 용어와 전제」와 같게 맞춘다(연계 조정). 이 과정에서 새로 정한 이름은 OOAD에도 같은 이름으로 반영한다.

| 용어·사례 | 이 과정에서의 의미와 범위 |
|---|---|
| 강의 시스템 — 주문 | 주문 시스템. 고객이 상품을 골라 배송지를 정하고 결제하면 주문이 성립한다. 강의는 빈 저장소에서 첫 기능 주문한다를 개발한다 |
| 외부 시스템(주문) | 상품 시스템 — 상품 정보와 현재 판매가를 조회한다. 결제 시스템 — 결제 승인을 요청하고 승인·거절을 받는다. 배송 시스템 — 배송을 요청하고, 배송 시작·완료를 통보받는다. 동기·비동기는 설계에서 정할 일이라 이 과정에서 구분하지 않는다 |
| 흐름 | 기본 흐름 1 상품을 조회한다 · 2 장바구니에 담는다 · 3 배송지를 지정한다 · 4 결제한다 · 5 주문 결과를 확인한다 |
| 주문 상태 | 결제대기 → 결제완료 → 배송중 → 배송완료. 결제가 거절되면 결제대기에 머문다(자기 전이). 코드 값은 `PENDING_PAYMENT`·`PAID`·`IN_DELIVERY`·`DELIVERED`. **취소는 이번 과제의 범위 밖이므로 취소됨 상태와 전이를 두지 않는다** — 03에서 제외로 적고 05의 상태 기계에 넣지 않는다. OOAD의 취소처리중도 쓰지 않는다(2026-10-21) |
| 판매가 / 단가 | 상품의 판매가(현재 값), 주문 항목의 단가(주문 시점에 확정한 값) |
| 정적 모델 코드 예제의 가정 | 원 단위 정수 금액은 0 이상, 수량은 1 이상의 정수, 생성된 주문은 항목 1개 이상이다. 실제 업무 전반의 보편 규칙이 아닌 강의용 가정이다. 수량 상한·식별자 형식·주소 세부·동일 상품의 항목 병합 정책은 정하지 않는다. 예제 상품 번호 `PEN`은 펜을 가리키는 값이며 형식 규칙이 아니다 |
| 주문 예 | 펜 2개, 판매가 1,000원, 주문 금액 2,000원, 배송지 서울. 강의의 모든 세션이 이 값을 쓴다. 원고 본문에 "O-1" 같은 사례 번호를 붙이지 않는다 |
| 과제 — 주문한다 | 흐름 3~5. 배송지를 정하면 주문이 결제대기로 생기고 그때의 판매가로 주문 금액이 정해진다 → 결제한다(`pay`): 결제 시스템에 승인을 요청한다 → 승인되면 결제완료와 배송 요청, 거절되면 결제대기에 남고 다른 카드로 다시 결제할 수 있다. **과정의 유일한 과제이며 07에서 작업 단위 4개로 나눈다** — 08이 첫 단위, 11이 남은 셋이다 |
| 업무 규칙(강의) | **주문 금액** — 주문이 생길 때의 판매가로 정한다(결제 직전에 펜 값이 1,200원이 되어도 2,000원). **배송 요청** — 결제가 승인된 뒤에만 한다. **결제 거절** — 주문은 결제대기로 남고, 다른 카드로 다시 결제할 수 있다. 업무 담당자가 정한다 |
| 미정(강의) | **승인 뒤 배송 요청 실패**의 처리 정책. 03에서 미정으로 남기고 04~10이 정하지 않으며, 11의 종합 실행에서 드러나 거두어진다. 그 전 세션은 이 경우의 기대값을 만들지 않는다 |
| 실습 시스템 | **강의와 같은 주문 시스템, 같은 과제**다. 수강생이 빈 저장소에서 주문한다를 작업 단위로 나눠 끝까지 만든다. 외부 시스템도 같다(상품·결제·배송) |
| 실습의 결정 | **업무 규칙·모델·설계·작업 단위를 수강생이 정한다** — 강의의 세 규칙을 그대로 쓰지 않아도 되며, 다르게 정하면 그 결정이 모델·설계·검사로 어떻게 퍼지는지 확인한다. 상품·수량·배송지의 값도 수강생이 정한다. 그래서 별첨의 답은 정답이 아니라 한 가지 가능한 답이다 |
| 실습 품질 기준 | 실습용 정상 시험: 동시 100건·각 외부 응답 1초 이내일 때 요청부터 결과 수신까지 95% 이상 3초 이내. 본인의 주문만 조회·변경한다. 실습용 값이며 실제 운영 보장 수치가 아니다 |
| 검사 명령 | 강의·실습 저장소의 검사는 **명령 하나**로 돌린다(`gradle check`) — 컴파일, 수용 테스트, 불변 조건·전이 테스트, 의존 규칙 검사를 묶고 실패에 고치는 방법을 담은 메시지를 낸다. 느린 검사(결합도, 금액 계산의 LLM 심사)는 이 명령에 넣지 않고 CI에 남긴다. 강의는 09에서 이 명령을 만들고, 실습은 수강생이 실습 8~9에서 에이전트의 도움으로 만든다 |
| 실습 저장소 | **수강생이 자기 PC에 만드는 로컬 git 저장소 하나**다(`order-system`). 과정이 주는 저장소·코드·빌드 구성·스텁은 없고, 원격 저장소·push도 쓰지 않는다. **실습 1부터 모든 산출물을 이 저장소에 모은다** — 실습 1~7의 MD는 `docs`에 쌓이고, 실습 8에서 에이전트가 그것을 읽어 같은 저장소에 코드와 빌드 구성을 만들며, 실습 9에서 검사를 붙인다. 외부 시스템(상품·결제·배송)은 인터페이스와 테스트 대역으로만 둔다. 환경은 Windows·코딩 에이전트·Git·JDK 17 이상·Gradle이다(2026-10-22) |
| 모델 패키지 | 에이전트에게 맥락으로 주는 산출물의 묶음 — 요구사항 정의서·용어집·개념 모델·상태 기계·의존 규칙·설계. 강의는 03~07에서, 실습은 실습 3~7에서 만들어 저장소의 `docs/`에 둔다 |
| 위임 패키지 | 위임 계약(지시문·맥락 참조·권한·종료 조건)과 모델 패키지, 검사 명령을 합친 것 |
| OOAD와의 관계 | **두 과정이 같은 시나리오를 쓴다** — 주문 시스템의 주문한다. 이 과정은 그 한 과제만 쓰고(빈 저장소에서 수강생이 끝까지 만들어야 한다), 취소·배송지 변경·정기배송 같은 다른 기능은 OOAD가 상세화에 쓴다. 가르치는 것이 갈린다 — **OOAD는 모델의 상세와 표기법**, 이 과정은 **결정과 검사, 사람과 AI의 역할**이며 표기법을 가르치지 않는다. `pay`·`requestApproval`·`requestDelivery`·`PaymentMethod`는 이 과정에서 정한 이름이며 OOAD에도 같은 이름으로 반영한다(2026-10-21) |
| 아키텍처 사례의 배포 범위 | 첫 기능의 업무 패키지는 하나의 배포 단위로 두고 포트와 어댑터로 연동·영속을 분리한다. 별도 서비스로의 독립 배포는 필요가 확인될 때 판단한다(세션 06의 교육용 설계 선택) |
| 의존 규칙 | 업무 패키지(`order`·`payment`·`delivery`·`product`, 실습은 `subscription` 등)는 연동 패키지(`paymentadapter` 등)와 `persistence`를 import하지 않는다. 패키지 의존에 순환이 없다 |
| 이 과정의 산출물 | 활용 방식 판단, 요구사항 정의서와 수용 기준, 정적 모델, 동적 모델, 의존 규칙과 연동 규격, 설계와 작업 단위, 위임 계약, 검사와 검사 명령, 평가 세트, 실행 기록과 되돌림 결정 |
| 활용 방식 비교의 가정 | 세션 02의 첫 릴리스 여섯 일에서는 저장소 골격의 생성 절차·구조 검사가 있고, 연동 코드의 규격·생성·검사 경로가 정해졌다고 본다. 200쪽 결제 매뉴얼과 맥락 도식의 길이는 개념 설명용 가정이며 계측값이 아니다. 운영 이관은 강의만의 일이고 빈 저장소 실습에는 없다 |
| 2026-10 기준 | 도구·모델의 능력과 비용에 관한 서술은 이 날짜 기준이다. 과정을 열 때마다 원문을 다시 확인한다 |

위 표가 이 과정의 **공통 식별자의 원천**이다. 세션 원고·다이어그램·예시 코드는 이 이름과 값을 그대로 쓴다. 뒤 세션이 새로 발견한 것은 **진화**로서 그 세션이 발견과 되돌림을 보이고 이 표에 반영한다. 같은 대상을 다른 이름·규칙으로 쓴 것은 **오류**이며 이 표에 맞춰 고친다(`sw-engineering-principles.md`의 「교재에 적용하기」).

### 영한 용어집과 명명 규칙

본문은 한글 용어를, 도식의 설계 요소와 코드는 아래 영문명을 쓴다. 한 용어에 영문명은 하나이며, 표에 없는 업무 용어는 코드에서 먼저 만들지 않고 여기에 먼저 더한다. 명명 규칙은 OOAD와 같다.

- **타입**(클래스·인터페이스·enum·record) — 영문 명사, PascalCase(`OrderItem`)
- **필드** — 영문 명사, camelCase(`unitPrice`)
- **메서드** — 업무 동사, camelCase(`pay()`). 외부·다른 객체가 알리는 사건은 `on`으로 시작한다(`onPaid()`)
- **enum 값** — UPPER_SNAKE(`PENDING_PAYMENT`)
- **패키지** — 소문자 단수, 붙여 쓴다(`order`, `paymentadapter`)

| 결제 게이트웨이 / 배송 게이트웨이 / 상품 게이트웨이 | `PaymentGateway` / `DeliveryGateway` / `ProductGateway` | 타입(외부 시스템에 대한 요청 인터페이스) |
| 연동 | `Adapter` | 접미사(`PaymentAdapter`, 패키지 `paymentadapter`) |
| 주문 서비스 | `OrderService` | 타입(시스템 이벤트를 받아 주문을 찾고, 맡기고, 저장한다) |
| 주문 저장소 | `OrderRepository` | 타입 |
| 영속 | `persistence` | 패키지 |

- "이 과정에서 추가"한 이름은 OOAD 영한 용어집에도 같은 이름으로 더한다(연계 조정).
- 수강생이 실습에서 자기 결정으로 더한 업무 용어는 자기 용어집에 더한다. 이 표는 **강의가 쓰는 이름의 원천**이다.
- 이 과정의 산출물 이름(작업 지시문, 위임 계약, 검사 명령 등)은 업무 용어가 아니므로 영문명을 두지 않는다.
