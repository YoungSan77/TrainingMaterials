# AI-native SW 공학 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** AI-native SW 공학 (`ai-native`)
- **총 교육시간:** 14시간, 2일(하루 7시간). 1시간은 강의 50분과 휴식 10분이다. **세션 시간은 참고값이다** — 기준은 세션 내용의 완성도이며, 시간은 최종 원고가 완성된 뒤 파일럿에서 확정한다.
- **대상:** SW 아키텍트, Back-End·Front-End 개발자, Cloud 엔지니어, AI 엔지니어
- **선수지식:** LLM 대화 도구나 코딩 에이전트를 업무에 써 본 경험, 자바 코드 독해, Git 사용

이 과정은 **독립된 과정**이다. 관통 사례와 그 이름은 "객체지향 분석과 설계 실무"(`ooad`)와 같게 맞추며(연계 조정), 이 과정만 듣는 수강생도 이해하도록 필요한 전제를 이 문서와 개요 세션이 직접 소개한다.

### 과정의 맥락

아래 성숙도·운영 조건은 **가정**이다. 사전 설문과 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 | 확인 방법 |
|---|---|---|
| **도메인** | 주문·결제·배송을 사용자로서 안다. 사례의 규칙은 과정이 정해 준다 | 사전 설문 |
| **기술** | LLM으로 코드·문서를 만들어 봤지만, 위임할 작업의 명세·맥락·권한·검증을 설계해 본 적은 적다. 자바 코드를 읽고 테스트를 실행한다 | 사전 설문, 실습 1 |
| **팀워크** | 코드 리뷰는 하지만 AI가 만든 결과를 무엇으로 받아들일지(수용 기준·증거) 팀이 합의해 본 경험은 적다 | 사전 설문, 실습 5 |

- **다루는 불확실성** — **기술 불확실성**이 중심이다. LLM의 생성은 비결정적이고 그럴듯한 추측을 섞으며, 모델·도구의 능력이 빠르게 바뀐다. 업무 불확실성은 단순한 주문 사례와 정해 둔 규칙으로 낮춘다.
- **깊이의 결정** — 깊이는 **대상의 성숙도와 과정의 목적**이 정하며 배정된 시간이 정하지 않는다. 이 과정은 AI 도입으로 SW 공학이 어떻게 바뀌는지를 다루므로 **범위를 유지하고 깊이를 낮춘다** — 기법의 숙련이 아니라 산출물의 정의와 흐름, 사람과 AI의 역할까지다. 성숙도가 낮은 **사람이 정할 결정의 명시**(명세·수용 기준), **맥락의 선별**, **위임 경계**, **센서와 증거**를 명시하고 먼저 검증한다. 도구별 기능·설정은 예로만 보이고 가르치지 않는다. 내용은 날짜가 있는 1차 원문을 따르며, 원고에는 그 내용을 확인한 **교재 작성 월**을 밝힌다(예: "2026-10 기준"). 과정을 열 때마다 원문을 다시 확인하고 작성 월을 갱신한다.
- **요구에서 코드까지의 경로** — 강의의 주문한다와 실습의 정기배송은 **도메인·기술 복잡성 모두 중간**이다. 업무 규칙 3가지와 상태 몇 개, 외부 시스템 연동(결제·배송)이 있다. 그래서 불변의 뼈대(요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트)에 작업 명세서(업무 규칙과 예)·용어집과 상태 기계·의존 규칙을 가볍게 더하고, 남기는 것은 요구사항 정의서·용어집·상태 기계·의존 규칙(맥락 파일)이다. 작업 명세서는 작업용이다(「4. 과정 전체 판단 원칙」).
- **운영 조건** — 가정: 20명 안팎, 개인 실습과 결과 공유. 실습 환경은 수강생이 쓰는 **LLM과 코딩 에이전트**(Codex·ChatGPT·Claude Team 등), Git, JDK다. 초기 분석·모델링 실습은 renderer 없이 대화창에서 검토하고 최종 MD를 다음 실습에 첨부한다. ①~⑤는 대화 횟수가 아니라 단계이며 보완 대화와 최종 MD 생성은 필요한 만큼 반복한다. 슬라이드 제작은 별개다. 결과물은 도구와 무관한 산출물이며 특정 도구·SDK의 사용법은 다루지 않는다.

**원전 적용 결정**

- **개발 방식의 구분** — LLM 이전·AI 지원(AI-assisted)·AI-native의 세 구분과 개발자·LLM의 역할 구분(「4. 과정 전체 판단 원칙」)은 원전의 분류가 아니라 **이 과정의 구분**이다. 원고에서 원전의 정의처럼 제시하지 않고, 각 구분을 받치는 원문(워크플로·에이전트의 정의, 하네스의 정의 등)만 인용한다(2026-10-06).
- **위임 형태** — 워크플로와 에이전트의 정의, 증강 LLM, 다섯 워크플로 패턴(프롬프트 체이닝·라우팅·병렬화·오케스트레이터-워커·평가자-최적화기)은 [Anthropic 2024]를 따른다. 수작업과 대화형 보조는 이 과정이 더한 비교 대상이다(2026-10-06).
- **하네스** — 가이드(feedforward)·센서(feedback), 계산적(computational)·추론적(inferential) 구분은 [Böckeler 2026a]를 따른다. 가드레일은 하네스의 가이드 중 **실행 전에 강제되는 제약**을 가리키는 이 과정의 이름이다(2026-10-06).
- **위험** — NIST AI RMF는 위험을 식별·측정·관리하는 어휘로만 쓴다. 과정의 뼈대로 쓰지 않으며 조직 거버넌스(GOVERN)의 상세는 다루지 않는다. 생성형 AI의 위험 항목은 [NIST 2024], 실행 시점의 에이전트 보안 위험은 [OWASP 2025]를 참고한다(2026-10-06).
- **활용 방식과 자율성** — 과정의 기준은 수작업·대화형 보조·워크플로·에이전트의 4가지 방식이다. [Blount 외 2026]의 자율성 단계는 S01에서 **보완 관점**으로 대응만 보이고, 형태를 대신하지 않는다(2026-10-06).
- **인용과 추론** — 인용은 원문에서 확인한 문장만 쓴다(`tools/verify-quote.js`). 원문으로 확인하지 못한 관점(예: Software 3.0, 부분 자율, 비결정적 추상, AI의 증폭 효과)은 출처를 달지 않고 이 과정의 설명(추론)으로만 쓴다. 그런 자료([Karpathy 2025]·[Fowler 2025]·[DORA 2025])는 참고 자료에 읽을거리로 둔다(2026-10-06).
- **AI 지원과 바이브 코딩** — 바이브 코딩(결과를 보지 않고 받아들이는 방식)은 개발 방식의 한 구분이 아니라 **규율이 없는 사용**이다. AI 지원·AI-native 모두에 생길 수 있으며, 증강 코딩·바이브 엔지니어링과 대비해 보인다(2026-10-06).
- **Technology Radar** — Radar의 링(Adopt·Trial·Assess·Caution)은 기법이 업계에서 어느 단계인지 보여 주는 신호로만 인용한다. 판(Vol. 34, 2026-04)을 밝히고 과정을 열 때마다 최신판으로 다시 확인한다(2026-10-06).
- **본질적 복잡성은 업무 규칙이다** — [Brooks 1986]의 본질적·우연적 복잡성을 이 과정은 이렇게 대응시킨다: 본질적 복잡성은 **업무 규칙**(도메인 지식), 우연적 복잡성은 업무 규칙을 **코드로 옮기는 일**이다. AI는 뒤의 것을 크게 줄였고 앞의 것은 사람이 정한다. 대응은 이 과정의 해석이며 Brooks의 문장이 아니다. 업무 규칙을 명시하는 수단으로 용어집·도메인 모델([Evans 2015]의 보편 언어)과 온톨로지([Gruber 1993])를 함께 다룬다(2026-10-07).
- **용어** — 업무 담당자가 정하는 주문 금액·배송 요청·결제 거절 같은 규칙은 **업무 규칙**으로 부른다. 요구의 작업 단위는 **사용자 이야기**(user story), 그 테스트 기준은 **수용 기준**이라 부른다. 처음에 유저 스토리로 정했다가 번역어로 통일했다. 짧게 가리킬 때는 **스토리**로 쓴다("스토리 하나", "스토리를 나눈다")(2026-10-20). 동기·비동기는 설계에서 정할 일이라 이 과정의 시나리오·요구에서 구분하지 않는다. 원고 본문은 코드 식별자(`pay` 등)와 사례 번호(O-1 등) 대신 한글 이름을 쓰고, 영문 이름은 코드 안에만 둔다(2026-10-07).
- **번역** — context는 **맥락**(OOAD·엑셀과 같음)으로 쓴다. workflow·agent·harness·guardrail·sensor는 음차하고 처음 나올 때 원어를 병기한다(워크플로(workflow)). human-in-the-loop는 **사람의 개입**, checkpoint는 **확인 지점**, eval은 **평가**로 쓴다(2026-10-06).
- **받은 원문** — 자동 접근이 막힌 원문은 `references/inputs/`에 두고 그 파일로 인용을 확인한다: [OpenAI 2025]·[DORA 2025]·[Blount 외 2026]은 PDF, [Lopopolo 2026]은 영문판 본문 추출(openai.com이 한국어판으로 자동 전환한다)(2026-10-06).

## 2. 과정 목표

이 과정은 **AI 도입으로 SW 공학이 어떻게 바뀌는가**를 다룬다. 바뀌지 않는 것은 업무의 개념과 규칙을 정하고 유지하는 일이고, 바뀌는 것은 그것을 코드로 만들고 검증하는 실행의 방식이다. 코딩의 자동화만 본다면 SW 공학이라 부를 이유가 없다 — 이 과정은 **도메인 모델을 정하고 보완하는 일이 AI 도입 뒤에 어떻게 달라지는지**를 활동마다 확인한다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. LLM 이전·AI 지원·AI-native 개발을 구분하고, 활동마다 사람이 결정할 것과 AI가 지원할 것을 나눈다.
2. 요청을 요구사항과 사용자 이야기로 구체화하고, 수용 기준을 기대값으로 작성한다.
3. 용어집·개념과 관계·상태 기계·업무 규칙으로 도메인 모델을 만들고, AI가 제시한 초안에서 추측과 모순을 걸러낸다.
4. 의존 규칙과 외부 연동 규격으로 경계를 정하고, 검사로 지켜지게 한다.
5. 모델을 맥락·명세·센서로 바꿔 에이전트에게 맡기고, 사용할 도구와 권한, 종료 조건을 정한다.
6. 센서의 증거로 결과를 판단하고, 실패와 AI의 변경 제안을 모델의 보완으로 되돌린다.
7. 평가 세트로 모델·도구가 바뀐 뒤에도 같은 규칙이 지켜지는지 확인한다.

## 3. 범위와 경계

**Core:** 개발 방식의 구분과 활동별 사람·AI의 역할, 작업 특성에 따른 활용 방식, 요구와 사용자 이야기, **도메인 모델의 산출물 정의와 그 사이의 흐름**, 아키텍처(경계·의존 규칙·외부 연동), 작업 명세서와 수용 기준, 맥락 구성, 도구·권한·상태의 경계와 가드레일, 실행 흐름과 사람의 확인 지점, 검증 하네스와 결과 점검, **실패와 모델의 보완**, 평가 세트와 운영 점검(보안·비용·모델 변경).

**Non-scope:** 제품에 LLM 기능을 넣는 설계(이 과정은 SW **개발 작업**에 AI를 쓰는 것을 다룬다), 모델링 기법의 표기법과 숙련, 특정 vendor SDK·도구 설정의 사용법, 모델 학습 이론, 프롬프트 요령 모음, 조직의 AI 전환과 거버넌스.

**다른 과정과의 연계**

| 과정 | 연계 |
|---|---|
| 객체지향 분석과 설계 실무(`ooad`) | 관통 사례와 이름을 같게 맞춘다. **표기법·관계의 종류·상세화 절차는 OOAD가 맡고**, 이 과정은 산출물이 무엇인지와 그 사이의 흐름, 각 산출물에서 사람과 AI가 나누는 일을 직접 소개한다. OOAD는 선수 과정이 아니므로 필요한 정의는 **일부 중복을 감수하고 짧게** 둔다. OOAD의 "세션 14. AI-native SW공학"(45분)은 이 과정의 미리 보기다 |
| SWQM | 품질 특성·검증 체계의 전문 판단은 SWQM이 맡는다. 이 과정은 위임 결과를 받아들이는 증거(센서·평가 세트)만 다룬다 |
| DT→AX | 조직의 AI 도입·운영 모델은 DT→AX로 넘긴다 |

다른 과정의 내용을 이 과정의 완결성을 위해 복제하지 않는다. 산출물의 정의와 흐름까지가 이 과정의 몫이다.

## 4. 과정 전체 판단 원칙

- AI-native 개발의 핵심은 모델 호출이 아니라 **불확실한 생성 능력을 책임 있는 실행 경계와 검증 증거 안에 두는 것**이다.
- **남는 것은 도메인 모델이다.** AI가 코드를 빠르게 만들수록 코드와 모델이 어긋나는 속도도 빨라진다. 모델을 보완하지 않으면 다음 작업의 입력이 틀린다.
- **모델은 한 번에 완성되지 않는다.** 요구·명세·검증·실행의 모든 활동에서 모델이 고쳐진다. 세션 순서는 학습 순서이며 개발 절차가 아니다.
- 가장 단순한 형태로 시작하고, 증거가 요구할 때만 자율성을 높인다.
- LLM은 명세의 빈칸을 그럴듯한 추측으로 채운다. 사람이 정할 결정은 위임 전에 정하거나, 모르면 멈추고 묻게 한다.
- 에이전트의 "완료"는 주장이다. 센서가 낸 증거와 확인 지점의 판단으로 받아들인다.
- 실패는 같은 입력의 재시도가 아니라 원인이 된 결정(요구·모델·명세·맥락·경계·하네스)으로 되돌려 고친다.

**개발 방식의 구분** — 이 과정의 구분이다(「원전 적용 결정」).

| 구분 | 작업의 단위 | 누가 무엇을 하는가 | 검증 |
|---|---|---|---|
| **LLM 이전** | 사람이 쓰는 코드 | 사람이 명세·설계·코드·테스트를 모두 쓴다. 도구(컴파일러·IDE·CI)는 결정적이다 | 사람이 쓴 테스트와 리뷰 |
| **AI 지원**(AI-assisted) | LLM의 제안 하나(코드 완성, 대화의 답) | 사람이 작업 흐름을 그대로 쥐고, LLM이 조각을 제안하면 사람이 읽고 받아들인다 | 사람이 제안마다 읽는다 — 리뷰가 병목 |
| **AI-native** | 맡긴 과제 하나 | 사람이 의도·모델·경계·하네스를 정하고, LLM(에이전트)이 과제를 실행하고 센서로 스스로 고친다 | 하네스의 센서가 낸 증거와 확인 지점에서 사람의 판단 |

- AI-native는 "모든 작업을 에이전트에게"가 아니다. 작업마다 수작업·대화형 보조·워크플로·에이전트 중 가장 단순한 충분한 형태를 고른다("세션 01. 사람의 일과 AI의 일").
- 바뀌는 것은 사람의 일의 **위치**다. 코드를 직접 쓰고 읽던 일이 업무의 개념과 규칙을 정하고, 경계를 설계하고, 증거를 판단하는 일로 옮겨 간다.

**활동마다 사람과 AI** — 「5. Session 구조」의 표가 이 구분을 활동별로 펼친 것이다.

| 활동 | 사람이 한다 | LLM(에이전트)이 한다 |
|---|---|---|
| 문제·의도 | 문제와 의도를 정하고, 규칙·정책·위험 수용을 결정한다 | 요청에서 빠진 결정을 **질문으로** 드러낸다(정하지 않는다) |
| 요구·명세 | 요구사항과 작업 명세서, 허용·거절 예시를 확정한다 | 초안을 작성하고 애매한 사항을 질문한다. 확정된 기대값을 바꾸지 않는다 |
| 도메인 모델 | 업무 개념과 규칙을 결정한다 | 초안을 작성하고 모순과 누락을 제시한다 |
| 아키텍처 | 무엇이 무엇을 알아야 하는지 정한다 | 규칙 위반을 검사한다 |
| 맥락 | 무엇에 따라 판단하는지 선택하고 지도를 유지한다 | 필요한 문서를 찾아 읽는다 |
| 경계 | 사용할 도구와 권한, 종료 조건을 정한다 | 경계 안에서 일하고 벗어나면 멈춘다 |
| 실행 | — | 코드와 테스트를 만들고 고친다. 빌드·테스트를 실행하고 진행을 기록한다 |
| 검증 | 무엇을 어떻게 검증할지 정하고 센서를 유지한다 | 센서의 결과를 보고 스스로 수정한다. 센서를 끄거나 지우지 않는다 |
| 결과 판단 | 확인 지점에서 증거를 보고 수용하거나 되돌린다. 최종 책임을 진다 | 완료의 증거를 제시한다. 추론적 센서로서 리뷰를 보조한다 |
| 실패·보완 | 발견을 모델에 반영할지 결정하고 평가 세트를 유지한다 | 잘못된 곳과 개선을 제안한다. 상한 안에서 재시도한다 |

**요구에서 코드까지의 경로** — `guides/sw-engineering-principles.md` 7절을 이 과정에 적용한다.

- **명세와 산출물** — 요구는 원하는 것, 요구사항은 시스템이 충족할 것이다. 요구사항의 명세는 범위·수명에 따라 **요구사항 정의서**(시스템 전체, 유지 — 용어집 포함)와 **작업 명세서**(스토리 하나, 작업용)로 나눈다. **도메인 모델**(개념·관계·상태·규칙)과 **아키텍처**(경계·의존 규칙)는 명세와 별개의 산출물이며, 명세가 가리키고 에이전트에게 맥락으로 준다.
- **불변의 뼈대** — 요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트. 사용자 이야기가 AI에게 맡기는 작업 단위이고, 수용 기준이 테스트가 된다. 요구를 담는 형식 중 **사용자 이야기와 수용 기준을 뼈대로 삼고**, 이벤트–반응 목록과 유스케이스는 정의와 쓰임만 소개한다.
- **흐름의 분기는 상태 기계가 맡는다** — 거절·중복·금지된 전이 같은 분기는 유스케이스의 대안 흐름 대신 **상태 기계와 업무 규칙 목록**으로 적는다. 같은 것을 두 곳에 적지 않는다(2026-10-18).
- **중간 산출물은 두 축으로 고른다** — 도메인 복잡성이 크면 작업 명세서와 도메인 모델을, 기술 복잡성이 크면 아키텍처를 더한다. 사다리처럼 차례로 더하지 않는다.

| | 기술 복잡성 낮음 | 기술 복잡성 높음 |
|---|---|---|
| **도메인 복잡성 낮음** | 스토리와 예 → 코드 | + 아키텍처 |
| **도메인 복잡성 높음** | + 작업 명세서 + 도메인 모델 | 모두 |

- **무엇·언제·얼마나** — 무엇을 넣는가는 복잡성이, 언제 쓰는가는 불확실성이, 얼마나 남기는가는 수명·변경 빈도와 함께 쓰는 사람·에이전트의 수가 정한다.
- **넣는 기준** — 그 산출물이 **에이전트의 결과나 사람의 확인을 바꾸는가?** 바꾸지 않으면 넣지 않는다.
- **오래 남는 것** — 요구사항 정의서(용어집 포함)·도메인 모델·의존 규칙이다. 작업 명세서와 수용 테스트만 작업마다 새로 쓴다.

**세 칸이 과정의 형식이다** — 세션마다 어떤 **산출물**이 남고, **사람이 무엇을 결정**하고, **AI가 무엇을 지원**하는지 같은 자리에서 답한다.

| | 세션 | 산출물 | 사람이 하는 일 | AI가 하는 일 |
|---|---|---|---|---|
| S01 | 사람의 일과 AI의 일 | — | 어떤 작업을 맡길지 결정한다 | 추측으로 채운 부분을 질문으로 제시한다 |
| S02 | 요구와 사용자 이야기 | 요구사항 정의서, 사용자 이야기 | 원하는 결과와 범위를 결정한다 | 초안을 작성하고 애매한 사항을 질문한다 |

| S04 | 아키텍처 | 의존 규칙, 외부 연동 규격 | 무엇이 무엇을 알아야 하는지 정한다 | 규칙 위반을 검사한다 |
| S05 | 작업 명세와 수용 기준 | 작업 명세서, 수용 테스트 | 옳은 결과를 기대값으로 작성한다 | 예를 늘리고 테스트 코드를 작성한다 |
| S06 | 맥락 구성 | 지도 | 무엇에 따라 판단하는지 선택한다 | 필요한 문서를 찾아 읽는다 |
| S07 | 권한과 가드레일 | 권한과 제약 설정 | 사용할 도구와 종료 조건을 정한다 | 경계 안에서 일하고 벗어나면 멈춘다 |
| S08 | 실행 흐름 | 실행 흐름, 확인 지점 | 사람이 확인할 지점을 정한다 | 정해진 흐름에 따라 작업을 수행한다 |
| S09 | 검증 하네스 | 센서 | 무엇을 어떻게 검증할지 정한다 | 센서의 결과를 보고 스스로 수정한다 |
| S10 | 실패와 모델 보완 | 보완된 모델, 작업 상태 기록 | 모델에 반영할지 결정한다 | 잘못된 곳과 개선을 제안한다 |
| S11 | 평가와 운영 | 평가 세트 | 합격 기준을 정한다 | 같은 과제를 반복 실행하고 결과를 기록한다 |
| S12 | 종합 실행 | 실행 기록, 되돌림 결정 | 결과를 수용할지 되돌릴지 판단한다 | 작업을 완료하고 증거를 제시한다 |

진행은 `무엇을 맡기는가 → 무엇을 만드는가(요구·모델·아키텍처) → 어떻게 맡기는가(명세·맥락·경계) → 어떻게 실행하고 확인하는가(흐름·하네스) → 어긋나면 어떻게 고치는가(보완·평가) → 종합`이다. **이는 학습 순서이지 고정된 개발 절차가 아니다.** 실제 개발에서 모델의 개발과 보완은 동시에 일어나며, 뒤 세션의 활동이 앞 세션의 산출물을 고친다. 세션마다 요약의 마지막에 **모델에서 보완된 내용**을 한 줄로 밝혀 이를 보인다.

### S01 — 사람의 일과 AI의 일 (1시간 30분)

- **목표:** AI가 SW 공학에서 바꾼 것(업무 규칙을 코드로 옮기는 일)과 바꾸지 않은 것(업무 규칙)을 구분하고, LLM 이전·AI 지원·AI-native 개발과 활동마다 사람이 결정할 것과 AI가 지원할 것을 나누며, 작업 특성으로 활용 방식을 고른다.
- **Anchor Message:** AI는 실행을 빠르게 하지만, 무엇이 옳은 결과인지의 판단과 책임은 사람에게 남는다.
- **세부 목차:** 세션 목표 / 첫 시도 — 요청 한 줄로 10분 만에 만든 주문 기능과 업무 담당자 리뷰에서 나온 문제 3가지 / 본질적 복잡성과 우연적 복잡성 — 본질은 업무 규칙(도메인 지식)이고 우연은 그것을 코드로 옮기는 일이다 / 업무 규칙은 도메인 지식이다 — 회사의 정책·운영 방식·고객과의 약속이 정한다 / LLM이라는 새 재료 — 그럴듯한 추측(confabulation), 비결정성, 맥락의 한계 / 개발 방식의 구분 — LLM 이전·AI 지원·AI-native, 바이브 코딩 대 증강 코딩·바이브 엔지니어링 / 사람의 일과 AI의 일 — 활동마다의 구분과 남는 산출물 / 작업 특성 — 업무 규칙의 확정·절차의 확정·결과의 자동 확인·되돌리기 쉬움 / AI 활용 방식 — 수작업·대화형 보조·워크플로·에이전트와 가장 단순한 충분한 형태 / 자율성을 높이는 조건 / 관통 사례 — 주문 시스템 시나리오 / 과정의 지도 — 열두 활동에서 남는 산출물 / 실습 1 — 업무 조건 확인 / 요약
- **근거 자료:** [Brooks 1986](본질적·우연적 복잡성), [NIST 2024](confabulation), [Anthropic 2025c](맥락의 한계), [Anthropic 2024](워크플로·에이전트, 가장 단순한 해법), [OpenAI 2025](에이전트가 맞는 작업), [Beck 2025]·[Willison 2025b](규율), [Lopopolo 2026](사람의 역할)
- **사례에서 답하는 결정:** 첫 시도의 코드가 추측으로 채운 업무 규칙 3가지(주문 금액, 배송 요청, 결제 거절)과 업무 담당자가 정한 규칙. 첫 릴리스의 일 6가지와 그 활용 방식.
- **다이어그램·코드:** 과정의 지도(도식), 첫 시도의 결제 코드 한 장과 업무 규칙을 기대값으로 쓴 테스트 결과.
- **모델에서 보완되는 내용:** 없다. 업무 규칙 3가지가 리뷰에서 처음 드러난다.

### S02 — 요구와 사용자 이야기 (1시간)

- **목표:** 요청을 문제/기회 → 요구 → 요구사항으로 구체화해 하나의 사용자 이야기를 포함한 요구사항 정의서로 적고, 필요한 품질 속성을 확인 가능한 조건으로 정하며, 요구를 담는 형식 넷을 구분하고, LLM이 쓴 초안에서 사람이 확정할 것을 가른다.
- **Anchor Message:** 요구는 사람이 정한다. LLM은 초안을 작성하고 애매한 사항을 질문한다.
- **세부 목차:** 세션 목표 / 문제에서 요구사항으로 — 요구와 요구사항의 구분 / 요구를 담는 형식 — 이벤트–반응 목록·유스케이스·사용자 이야기·도메인 이벤트(각 정의와 쓰임) / 사용자 이야기 — 카드·대화·확인 / 요구사항 정의서와 작업 명세서 — 사용자 이야기와 문서의 관계, 범위와 수명 / 품질 요구사항 — 기능과 품질, 시험 조건과 합격 기준 / 요구사항 정의서를 쓴다 — LLM이 초안을 작성하고 사람이 확정한다 / 명세 주도 개발 — 개념과 얼마나 남기는가 / 시연 — LLM이 쓴 초안과 남긴 미정 질문 / 잘못된 관행 / 실습 2 — 요구사항 정의서와 사용자 이야기 / 요약
- **근거 자료:** [Böckeler 2025](명세 주도 개발), [Jeffries 2001](카드·대화·확인), [Evans 2015](도메인 이벤트), [Cucumber](예로 명세하기)
- **사례에서 답하는 결정:** 업무 담당자의 요청 한 줄과 회의 메모를 LLM에 주어 요구사항 정의서 초안을 쓰게 하고, 초안이 남긴 미정 질문에 사람이 답해 요구사항과 사용자 이야기를 확정한다.
- **다이어그램·코드:** 요구에서 코드까지의 경로(도식), 요구사항 정의서(문서 형식)와 사용자 이야기의 예. 코드 없음.
- **모델에서 보완되는 내용:** 용어집의 첫 항목과 요구사항 정의서가 생긴다.

### S03 — 도메인 모델 (1시간 30분)

- **목표:** 용어집·개념과 관계·상태 기계·업무 규칙으로 도메인 모델을 만들고, LLM이 낸 초안에서 추측·모순·누락을 걸러내며, 모델의 요소가 코드와 테스트의 어디로 이어지는지 확인한다.
- **Anchor Message:** 도메인 모델은 AI에게 주는 자료가 아니라 사람이 정한 업무의 의미다.
- **세부 목차:** 세션 목표 / 도메인 모델이 명시하는 것 — 개념·관계·상태·규칙, 개념 모델과 온톨로지의 뜻 한 줄씩 / 분석과 설계와 구현의 구분 / 용어집 — 같은 것을 같은 이름으로 / 정적 모델 — 개념과 관계, 속성의 의미 / 동적 모델 — 상태와 전이, 금지된 전이와 미정의 구분 / 업무 규칙 — 규칙과 그 대표 예 / 모델을 만들 때 사람과 AI — 초안·모순 지적·확정 / 모델이 코드로 이어지는 자리 / 잘못된 관행 / 실습 3 — 도메인 모델 / 요약
- **근거 자료:** [Evans 2015](보편 언어·도메인 이벤트), [Gruber 1993](온톨로지), [Larman 2004](개념 모델)
- **사례에서 답하는 결정:** "가격"을 판매가와 단가로 나누고, 주문 상태와 전이를 확정하며, 업무 규칙 3가지를 상태 전이와 묶는다.
- **다이어그램·코드:** 개념 모델(클래스 다이어그램)과 상태 기계, 그 요소가 드러나는 자바 코드(필드·`enum`·상태를 바꾸는 메서드).
- **모델에서 보완되는 내용:** 용어집에 단가가 더해지고, 결제대기의 자기 전이가 드러난다.

### S04 — 아키텍처 (1시간)

- **목표:** 아키텍처 스타일 중 사례에 맞는 것을 고르고, 응집도·결합도와 의존성 역전에 비추어 업무 패키지와 연동·영속의 경계를 정해 의존 규칙으로 적으며, 외부 연동 규격을 맥락으로 둔다.
- **Anchor Message:** 경계는 글로 적고 검사로 지킨다.
- **세부 목차:** 세션 목표 / 아키텍처 스타일 — 무엇을 정하는가, 계층형·포트와 어댑터·모듈러 모놀리스·마이크로서비스의 비교와 이 과정이 쓰는 것 / 설계 원칙 — 응집도와 결합도, 단일 책임, 의존성 역전 / 업무 패키지와 외부 시스템 — 인터페이스로만 안다 / 의존 규칙 — 무엇이 무엇을 알아야 하는가 / 외부 연동 규격 — 필요할 때 읽는 문서 / 검증하기 쉬운 구조 — 센서를 만들기 쉬운 코드 / 잘못된 관행 / 실습 4 — 아키텍처 / 요약
- **근거 자료:** [Martin 2000](기준 원전 — 의존성 역전, 패키지 의존의 순환 금지), [Cockburn 2005](포트와 어댑터), [Lewis·Fowler 2014]·[Fowler 2015c](마이크로서비스와 모놀리스 먼저), [Martin 2014](단일 책임), [Larman 2004](응집도와 결합도), [Böckeler 2026a](구조를 재는 센서)
- **사례에서 답하는 결정:** 주문 시스템은 포트와 어댑터 스타일을 쓴다. `order`·`payment`·`delivery`·`product`가 연동·영속을 import하지 않고, 결제·배송은 인터페이스로만 안다.
- **다이어그램·코드:** 아키텍처 스타일의 비교(표), 패키지 다이어그램과 인터페이스 선언, 의존 규칙을 판정하는 검사.
- **모델에서 보완되는 내용:** 외부 시스템과 주고받는 이름이 용어집과 맞춰진다.

### S05 — 작업 명세와 수용 기준 (1시간 30분)

- **목표:** 사용자 이야기에 업무 규칙·범위·제외·미정을 붙여 작업 명세서로 만들고, 허용·거절 예시를 수용 기준과 테스트로 바꾸며, 한 번에 검증할 수 있는 작업 단위로 나눈다.
- **Anchor Message:** 수용 기준이 곧 테스트이며, 검증할 수 없는 작업은 맡길 수 없다.
- **세부 목차:** 세션 목표 / 작업 명세서 — 스토리 하나의 범위·제외·미정 / 수용 기준 — 무엇을 받아들일 것인가 / BDD — 예로 명세하기 / 예시에서 테스트로 / 작업 단위 — 한 번에 검증할 크기 / 기능 목록과 점진적 진행 / 완료의 정의와 증거 / 시연 — 테스트는 누가 쓰는가? / 잘못된 관행 / 실습 5 — 작업 명세와 수용 기준 / 요약
- **근거 자료:** [Cucumber](BDD·예시 매핑), [Lopopolo 2026](수용 기준으로 옮긴다), [Willison 2025b](테스트가 있으면), [Anthropic 2025d](기능 목록)
- **사례에서 답하는 결정:** 허용·거절 예시 4가지(승인, 가격 변경, 거절, 거절 뒤 재결제)와 작업 단위 4가지. 결제 승인 뒤 배송 요청 실패는 미정으로 남긴다.
- **다이어그램·코드:** 작업 명세서(문서 형식), Given-When-Then과 그에 대응하는 수용 테스트, 기능 목록.
- **모델에서 보완되는 내용:** 예를 만들다 드러난 규칙의 빈칸이 업무 규칙으로 돌아간다.

### S06 — 맥락 구성 (1시간)

- **목표:** 과제의 판단을 바꾸는 지식을 골라 맥락으로 구성하고, 지도와 점진적 공개로 맥락의 한계를 관리한다.
- **Anchor Message:** 좋은 맥락은 많은 맥락이 아니라 판단을 바꾸는 최소의 정보다.
- **세부 목차:** 세션 목표 / 맥락 엔지니어링 — 무엇을 읽히는가 / 맥락의 한계 — 주의 예산과 맥락 부패(개념) / 저장소가 기록의 원천 / 지도 — 먼저 읽을 것과 필요할 때 볼 것 / 맥락의 적정량 / 긴 작업의 맥락(개념) / 잘못된 관행 / 실습 6 — 맥락 패키지 / 요약
- **근거 자료:** [Anthropic 2025c](맥락 엔지니어링·점진적 공개), [Lopopolo 2026](지도와 노후화), [AGENTS.md](공개 형식)
- **사례에서 답하는 결정:** 지도 약 30줄과 `docs/`가 가리키는 문서들. 결제 연동 매뉴얼 200쪽을 통째로 주자 옛 API를 썼다.
- **다이어그램·코드:** 맥락의 구성(도식), 지도(문서 형식).
- **모델에서 보완되는 내용:** 지도가 가리키지 않아 쓰이지 않던 문서가 드러난다.

### S07 — 권한과 가드레일 (1시간)

- **목표:** 맡긴 작업이 쓸 도구와 가질 권한, 바꿀 수 있는 상태와 종료 조건을 정하고, 어긋난 실행을 실행 전에 막는 가드레일을 위험에 따라 배치한다.
- **Anchor Message:** 가드레일은 프롬프트의 부탁이 아니라 실행 전에 강제되는 제약이다.
- **세부 목차:** 세션 목표 / 위임의 경계 — 도구·권한·상태·종료 조건 / 도구와 연결의 표준(개념) / 최소 권한 / 상태와 되돌림 / 위험의 식별 / 가드레일의 자리와 방식 — 입력·도구 호출·출력·환경, 강제와 지시 / 치명적 삼박자 / 잘못된 관행 / 실습 7 — 권한과 가드레일 / 요약
- **근거 자료:** [Anthropic 2025b](도구 설계), [MCP 2025](연결 표준), [OWASP 2025]·[Willison 2025a](위험), [NIST 2023](위험 어휘), [Anthropic 2026c](피해 범위와 샌드박스)
- **사례에서 답하는 결정:** `order`와 테스트에 쓰기·빌드·테스트 실행·브랜치 커밋은 허용, 실제 결제 호출·비밀 키 읽기·push는 금지. 설정 파일 쓰기와 외부 네트워크를 막고, 테스트 비활성화는 실패로 처리한다.
- **다이어그램·코드:** 가드레일의 배치(도식), 권한 설정과 거절된 호출의 기록.
- **모델에서 보완되는 내용:** 금지해야 할 외부 호출이 외부 연동 규격에 명시된다.

### S08 — 실행 흐름 (1시간)

- **목표:** 고른 활용 방식을 워크플로 패턴과 에이전트 루프로 구성하고, 되돌리기 어렵고 판단이 필요한 지점에 사람의 확인을 둔다.
- **Anchor Message:** 사람의 확인은 모든 단계가 아니라 되돌리기 어렵고 판단이 필요한 지점에 둔다.
- **세부 목차:** 세션 목표 / 실행 구조 — 워크플로와 에이전트 / 워크플로 패턴(개념) / 에이전트 루프 / 단일과 여러 에이전트(개념) / 사람의 확인 지점 — 어디에 두는가 / 주문한다의 실행 흐름 / 잘못된 관행 / 실습 8 — 실행 흐름 / 요약
- **근거 자료:** [Anthropic 2024](워크플로 패턴·에이전트), [OpenAI 2025](에이전트 설계), [Blount 외 2026](사람의 개입), [Anthropic 2026c](승인 피로)
- **사례에서 답하는 결정:** 계획 → 사람 확인 → 구현·테스트 → 센서 → 결제 관련 변경은 사람 리뷰 → 병합. 모든 단계의 승인은 형식이 된다.
- **다이어그램·코드:** 활동 다이어그램(실행 흐름과 확인 지점). 코드 없음.
- **모델에서 보완되는 내용:** 확인이 필요한 변경의 종류가 업무 규칙의 위험과 맞춰진다.

### S09 — 검증 하네스 (1시간 30분)

- **목표:** 가이드와 센서를 짝지어 하네스를 구성하고, 계산적·추론적 센서와 사람의 리뷰를 배치하며, 모델과 코드가 어긋난 곳까지 센서가 보게 한다.
- **Anchor Message:** 에이전트의 "완료"는 주장이고, 센서가 낸 증거만이 완료를 보인다.
- **세부 목차:** 세션 목표 / 하네스란? / 가이드와 센서 / 조종 루프 / 센서의 세 범주 — 계산적·추론적·사람(개념과 사례 하나) / 주문한다의 하네스 / 고치는 방법을 담은 메시지 / 모델과 코드의 불일치를 보는 센서 / 사람의 리뷰가 볼 것 / 잘못된 관행 / 실습 9 — 하네스 배치 / 요약
- **근거 자료:** [Böckeler 2026a](가이드·센서·조종 루프), [Böckeler 2026b](유지보수성 센서), [Lopopolo 2026](저장소가 기록의 원천)
- **사례에서 답하는 결정:** 센서는 컴파일·수용 테스트·의존 규칙·금액 계산의 LLM 리뷰다. 주문 서비스가 결제 연동을 직접 부르자 의존 규칙 센서가 실패하고, 메시지를 보고 에이전트가 스스로 고친다.
- **다이어그램·코드:** 조종 루프와 하네스 구성(도식), 의존 규칙 센서의 코드와 실패→통과 출력.
- **모델에서 보완되는 내용:** 센서가 판정하지 않는 산출물(기능 목록 등)이 드러난다.

### S10 — 실패와 모델 보완 (1시간)

- **목표:** 작업 실패를 유형으로 진단해 원인이 된 결정으로 되돌리고, AI가 제시한 변경 제안을 모델에 반영할지 판단하며, 모델이 바뀌면 무엇이 따라 바뀌는지 정한다.
- **Anchor Message:** 같은 입력의 재시도는 복구가 아니며, 발견은 모델의 보완으로 되돌린다.
- **세부 목차:** 세션 목표 / 재시도는 복구가 아니다 / 실패의 유형 — 명세 결함·모델 누락·환경 오류·모델 한계 / 되돌릴 자리 찾기 / 작업 상태와 표류 / AI의 변경 제안을 다루는 법 — 근거·범위·결정 / 모델이 바뀌면 따라 바뀌는 것 — 용어·상태·규칙의 전파 / 잘못된 관행 / 실습 10 — 실패와 모델 보완 / 요약
- **근거 자료:** [Lopopolo 2026](표류와 정리), [Anthropic 2026b](진단과 체계적 수정), [Böckeler 2026a](피드백 루프)
- **사례에서 답하는 결정:** "거절 뒤 재결제" 테스트가 되풀이 실패한다. 상한에서 멈추고 보니 상태 기계에 결제대기의 자기 전이가 없었다 — 모델을 고치고 같은 테스트로 검증한다.
- **다이어그램·코드:** 실패에서 결정으로 되돌리는 길과 전파 범위(도식), 보완 전후의 상태 기계.
- **모델에서 보완되는 내용:** 상태 기계에 자기 전이가 더해지고, 수용 테스트가 그것을 지킨다.

### S11 — 평가와 운영 (1시간)

- **목표:** 위임 구성의 품질을 평가 세트로 측정하고, 보안·비용·모델 변경이 생길 때 다시 점검할 기준을 정한다.
- **Anchor Message:** 데모의 성공은 증거가 아니며, 모델·맥락이 바뀌면 같은 평가 세트로 다시 확인한다.
- **세부 목차:** 세션 목표 / 데모는 증거가 아니다 / 평가의 구조 — 과제·시행·채점기·결과 / 능력 평가와 회귀 평가 / 주문한다의 평가 세트 / 함께 재는 값(개념) / 다시 점검하는 때 / 운영의 위험 — 데이터 반출·개인정보·도구 교체 / 잘못된 관행 / 실습 11 — 평가 세트 / 요약
- **근거 자료:** [Anthropic 2026a](평가의 구조), [METR 2025](체감과 측정), [NIST 2024](위험 항목), [Thoughtworks 2026](처리량 지표)
- **사례에서 답하는 결정:** 더 싼 새 모델로 바꾸려 한다. 평가 세트로 통과율·비용·시간을 보니 가격 변경 과제에서 실패가 늘었다.
- **다이어그램·코드:** 평가 세트와 재평가 조건(표). 코드 없음.
- **모델에서 보완되는 내용:** 반복 실패한 과제의 규칙이 업무 규칙의 대표 예로 올라간다.

### S12 — 종합 실행 (1시간)

- **목표:** 실습 1~11의 산출물을 위임 패키지로 모아 실제 코딩 에이전트에게 작업을 맡기고, 결과를 증거로 검토해 원인이 된 결정으로 되돌린다.
- **Anchor Message:** 위임 결과의 문제는 프롬프트가 아니라 원인이 된 결정에서 고친다.
- **세부 목차:** 세션 목표 / 위임 패키지 — 저장소가 자란 순서, 패키지를 이루는 문서 / 종합 실행 — 실행의 조건, 과제와 프롬프트, 에이전트가 한 일 / 결과 검토 — 센서가 준 증거, 사람이 보는 것 / 미정과 질문 / 원인 결정으로 되돌리기 — 되돌리는 길, 이번 실행의 되돌림 / 자율성의 다음 단계 / 사람이 남긴 결정 / 실습 12 — 종합 실행 / 요약
- **근거 자료:** [Lopopolo 2026](자율성의 단계), [Willison 2025b](전문성의 증폭)
- **사례에서 답하는 결정:** 빈 저장소가 어디까지 왔는지 되짚고, 그 패키지로 **주문을 취소한다**를 실제 코딩 에이전트에게 맡긴다. 취소는 앞 세션이 다루지 않은 기능이라 패키지가 스스로 작동하는지 드러난다(상태 기계의 결제완료 → 취소됨은 공통 전제에 이미 있다).
- **다이어그램·코드:** 저장소가 자란 순서와 결과에서 결정으로 되돌리는 길(도식), 주문 상태 기계와 취소 구현(코드), 에이전트의 실행 결과(테스트 출력).
- **실행 기록:** 강의 사례의 실제 실행은 `sessions/code/s12/demo-results/`에 둔다 — 과제, 출발과 끝의 센서 출력, 바뀐 파일의 diff, 에이전트가 남긴 질문.
- **모델에서 보완되는 내용:** 에이전트가 넓히자고 제안한 업무 규칙과, 센서가 보지 않아 낡은 기록이 드러난다.

## 6. 사례·실습 방향

이 과정은 AI와 협업하는 개발을 배우는 과정이다. 도메인 때문에 복잡도를 높이지 않는다. **강의는 빈 저장소에서 시작하는 신규 개발**이고, **실습은 운영 중인 쇼핑몰에 기능 하나를 더하는 개발**이다. 강의는 요청 한 줄로 시작한 첫 시도가 업무 리뷰에서 무너지는 데서 출발해, 요구·도메인 모델·아키텍처·명세·맥락·하네스를 세운다. 실습은 이미 있는 회원·상품·배송지·결제수단·배송 달력을 연계 대상으로 두고 정기배송 신청을 더한다 — 기존 코드를 고치는 유지보수가 아니라 **연계하며 새 기능을 더하는 개발**이다. 두 경우 모두 모델의 개발과 보완은 함께 일어나므로, 이 과정이 다루는 판단은 그대로 적용된다(2026-10-20).

- **강의** — OOAD와 같은 **주문 시스템**을 빈 저장소에서 개발한다. 첫 기능 **주문한다**(흐름 3~5) 한 과제로 S01~S11을 관통하고, S12에서 그 산출물로 **주문을 취소한다**를 실제 에이전트에게 맡긴다. 강의가 실습의 답을 미리 보이지 않는다. 시나리오는 아래 「강의 시나리오」다.
- **실습** — 운영 중인 쇼핑몰에 **정기배송 신청**을 더한다. 기존 회원·상품·배송지·결제수단·배송 달력은 **연계 대상**이며 다시 만들지 않는다. 모델 패키지를 받아서 시작하지 않고 **실습 1~3에서 업무 조건·요구사항·도메인 모델을 직접 만든다**. 실습마다 대화창에서 검토해 최종 MD를 만들고 그 파일이 다음 실습의 투입물이다. **실습 6 이후의 범위와 두 번째 기능은 해당 세션을 보완할 때 확정한다** — 아래 실습 표와 공통 전제의 실습 기능 2는 그때 갱신한다(2026-10-20).

실습 1은 기존 쇼핑몰과 연계하는 최초 정기배송 신청만 다룬다. ①로 시작하고 ②~④의 예시를 참고해 답변을 검토·보완하며 필요한 만큼 대화한다. ⑤는 최종 MD 생성 단계이며 파일을 검토한 뒤 보완·재생성할 수 있다. 화면·기술 설계와 기존 기능 재구현, 신청 이후 운영 정책은 제외한다. 요구사항을 작성할 만큼 핵심 조건을 정했으면 탐색을 끝낸다. 결과는 간결한 업무 조건 MD이며, 실습 2에서 요구사항으로 구체화한다. 실습 1의 답을 확정된 요구사항으로 취급하지 않고, 실습 2에서 남은 필수 결정을 검토한다.

실습은 수강생이 **LLM과 코딩 에이전트로 초안을 만들고 사람이 점검 항목으로 판단·보완**하는 방식으로 진행한다. **별첨의 답은 마지막 프롬프트(⑤)로 받은 최종 MD 그대로이거나 그 요약**이며, 그 파일이 다음 실습의 투입물이다. 앞 산출물로 되돌릴 것이 생기면 해당 실습의 강사 노트에 적는다(2026-10-20).

세션의 예시 코드(강의 저장소의 그 시점 상태)는 `sessions/code/sNN/`에 두고 컴파일·실행으로 확인한다.

### 강의 시나리오 — 주문 시스템을 AI와 함께 새로 만든다

수치(시간·개수·횟수)는 교육용 가정이다.

- **배경** — 생활용품 온라인 쇼핑몰이 외부 솔루션으로 받던 주문을 직접 만든 주문 시스템으로 옮긴다. 업무 담당자 1명이 주문 정책을 정하고, 테크 리드 1명과 개발자 2명이 코딩 에이전트를 쓴다. 출발점은 빈 git 저장소(자바)이며 상품·결제·배송 시스템은 이미 운영 중이다.
- **요청** — 업무 담당자의 요청은 한 줄이다: "장바구니에 담은 상품을 결제하면 주문이 되고 배송이 시작되게 해 주세요."
- **첫 기능** — 고객이 펜 2개(개당 1,000원)를 담고, 배송지(서울)를 정하면 주문이 결제대기로 생기며 주문 금액 2,000원이 정해진다. 카드로 결제해 승인되면 결제완료가 되고 배송을 요청한다. 고객은 주문 결과를 확인한다.
- **업무 규칙** — 주문 금액, 배송 요청, 결제 거절(공통 전제). 처음 요청에는 없었고 업무 담당자가 정한다.

| 세션 | 장면 | 드러난 것과 결정 |

| 01 | 테크 리드가 요청 한 줄을 에이전트에게 준다. 10분 만에 자바 파일 15개·테스트 3개, 테스트는 모두 통과하고 카드 승인 데모도 성공한다 | 업무 담당자 리뷰에서 문제 3가지 — 가격이 바뀐 날 주문 금액이 바뀜, 거절된 주문에 배송 요청이 나감, 거절된 주문이 취소되어 다시 결제할 수 없음. 첫 릴리스의 일 6가지를 작업 특성으로 나눈다 |

### 공통 용어와 전제

이름과 값은 OOAD의 「재사용 사례의 공통 용어와 전제」와 같게 맞춘다(연계 조정). 이 과정에서 새로 정한 이름은 OOAD에도 같은 이름으로 반영한다.

| 용어·사례 | 이 과정에서의 의미와 범위 |
|---|---|
| 강의 시스템 — 주문 | 주문 시스템. 고객이 상품을 골라 배송지를 정하고 결제하면 주문이 성립한다. 강의는 빈 저장소에서 첫 기능 주문한다를 개발한다 |
| 외부 시스템(주문) | 상품 시스템 — 상품 정보와 현재 판매가를 조회한다. 결제 시스템 — 결제 승인을 요청하고 승인·거절을 받는다. 배송 시스템 — 배송을 요청하고, 배송 시작·완료를 통보받는다. 동기·비동기는 설계에서 정할 일이라 이 과정에서 구분하지 않는다 |
| 흐름 | 기본 흐름 1 상품을 조회한다 · 2 장바구니에 담는다 · 3 배송지를 지정한다 · 4 결제한다 · 5 주문 결과를 확인한다 |
| 주문 상태 | 결제대기 → 결제완료 → 배송중 → 배송완료, 결제완료 → 취소됨. 결제가 거절되면 결제대기에 머문다(자기 전이). 코드 값은 `PENDING_PAYMENT`·`PAID`·`IN_DELIVERY`·`DELIVERED`·`CANCELLED`. OOAD의 취소처리중은 이 과정에서 쓰지 않는다 |
| 판매가 / 단가 | 상품의 판매가(현재 값), 주문 항목의 단가(주문 시점에 확정한 값) |
| 주문 예 | 펜 2개, 판매가 1,000원, 주문 금액 2,000원, 배송지 서울. 강의의 모든 세션이 이 값을 쓴다. 원고 본문에 "O-1" 같은 사례 번호를 붙이지 않는다 |
| 강의 과제 — 주문한다 | 흐름 3~5. 배송지를 정하면 주문이 결제대기로 생기고 그때의 판매가로 주문 금액이 정해진다 → 결제한다(`pay`): 결제 시스템에 승인을 요청한다 → 승인되면 결제완료와 배송 요청, 거절되면 결제대기에 남고 다른 카드로 다시 결제할 수 있다 |
| 업무 규칙(강의) | **주문 금액** — 주문이 생길 때의 판매가로 정한다(결제 직전에 펜 값이 1,200원이 되어도 2,000원). **배송 요청** — 결제가 승인된 뒤에만 한다. **결제 거절** — 주문은 결제대기로 남고, 다른 카드로 다시 결제할 수 있다. 업무 담당자가 정한다 |
| 실습 시스템 — 정기배송 | 기존 쇼핑몰에 추가하는 정기배송 기능. 기존 회원·상품·배송지·결제수단·배송 달력과 일반 정책은 연계 대상으로 사용하며 재구현하지 않는다 |
| 실습 기능 1 — 정기배송을 신청한다 | 기존 회원이 기존 상품·수량·본인 배송지·결제수단을 선택해 신청한다. 계약기간은 3개월·6개월, 주기는 2주·4주이며 첫 배송일부터 시작한다. 종료일은 개월 수를 더한 날짜(없는 날짜는 말일)이며 종료일 전 회차만 포함한다. 첫 배송일은 신청일+3일부터 기존 배송 달력에서 선택한다. 신청 시 상품 가격·할인·배송비로 회차 금액을 정해 계약 중 유지한다. 첫 회차는 신청 시 결제하며 성공 확인 시에만 신청 완료다. 실패 시 미완료, 결과 확인 불가 시 확인 필요를 안내하고 동일 신청의 반복 전송으로 중복 계약·청구를 만들지 않는다. 이후 회차의 배송 3일 전 결제는 고지할 조건이며 실제 실행·운영은 범위 밖이다. 내부 상태명은 뒤 모델링에서 정한다. 실습 1의 메모를 실습 2에서 구체화한 값이다 |
| 최초 신청의 분석 모델 | 정기배송신청과 정기배송계약을 구분한다. 배송회차는 신청 시 고지하는 예정 일정이다. 신청 상태는 신청준비·첫결제결과확인중·결과확인필요·신청완료·신청미완료이며 첫 결제 성공 확인 시에만 계약이 성립한다. 계약 운영 상태와 신청 상태를 혼용하지 않는다. 실습 3에서 요구사항을 모델링하며 명확해진 용어와 상태이며 이후 설계의 입력이다 |
| 실습 품질 기준 | 실습용 정상 시험: 동시 100건·각 외부 응답 1초 이내일 때 요청부터 결과 수신까지 95% 이상 3초 이내. 본인의 정보만 선택·조회·변경한다. 그 밖의 운영·복구·보안 정책은 기존 쇼핑몰 정책을 준용한다. 실습용 값이며 실제 운영 보장 수치가 아니다 |
| 실습 기능 2 — 배송지를 변경한다 | 확정된 정기배송은 **언제든** 배송지를 바꿀 수 있다(`changeShippingAddress`). 적용은 회차 상태로 가른다 — 예정 회차는 배송 요청 때 바뀐 배송지를 쓰고, 배송 요청됨(배송 준비 중) 회차는 배송 시스템에 바뀐 배송지를 알려(`requestAddressChange`) 이번 회차부터 적용하며, 배송중·배송됨 회차는 그대로 두고 다음 회차부터 적용한다. 해지됨·만료됨이면 바꿀 회차가 없다 |
| 정기배송 상태 | 결제 대기 → 확정 → 해지됨·만료됨. 코드 값은 `PENDING_PAYMENT`·`CONFIRMED`·`TERMINATED`·`EXPIRED`. OOAD의 신청 실패는 쓰지 않는다 |
| 정기배송 예(실습 답) | 휴지 1묶음 10,000원, 첫 배송일 2027-11-03, 2주 주기, 기간 3개월 → 종료일 2028-02-03(제외), 예정 회차 7개(11/03·11/17·12/01·12/15·12/29·2028/01/12·01/26). 신청 시 할인·배송비 0원이면 회차 금액 10,000원을 계약 중 유지한다. 첫 회차만 신청 시 결제하고 이후 회차의 실제 결제 실행은 범위 밖이다. 신청일은 2027-10-28이며 첫 배송일 하한을 판정할 기준으로 "세션 05. 작업 명세와 수용 기준"의 실습 대화에서 더했다. "세션 02. 요구와 사용자 이야기"의 실제 실습 대화에서 정한 교육용 값 |
| 회차 상태 | 예정 → 배송 요청됨(배송 24시간 전에 배송 시스템에 요청) → 배송중(배송 시작 통보) → 배송됨(배송 완료 통보). 코드 값은 `SCHEDULED`·`DELIVERY_REQUESTED`·`IN_DELIVERY`·`DELIVERED`. 배송중은 배송지 변경의 적용을 가르려고 이 과정에서 더한 값이다. OOAD의 청구됨·환불 대기·취소됨은 쓰지 않는다 |
| 모델 패키지 | 에이전트에게 맥락으로 주는 모델의 묶음. 강의(주문) — 용어집·개념 모델·주문 상태 기계·업무 규칙. 첫 시도에는 없고 "세션 03. 도메인 모델"에서 만든다. 실습(정기배송) — 최초 신청의 요구사항 MD와 용어·업무 규칙·클래스·시퀀스·신청 상태 머신을 담은 도메인 모델 MD를 실습 2·3에서 직접 만든다. 후속 기능의 모델은 해당 실습에서 발전시킨다. 원천은 이 표이며, 저장소의 `docs/`에 둔다 |
| OOAD와의 차이(연계 조정) | ① 주문의 배송지 변경은 이 과정의 강의에서 다루지 않는다. ② 정기배송의 배송지 변경은 OOAD 상태 기계의 조건 [다음 배송 24시간 전]과 달리 언제든 가능하고, 회차 상태로 적용을 가른다. ③ 회차 상태 배송중(`IN_DELIVERY`), 정기배송 상태 값 `TERMINATED`·`EXPIRED`, `subscribe`는 이 과정에서 정한 이름이며 OOAD에도 같은 이름으로 반영한다(2026-10-06) |
| 아키텍처 사례의 배포 범위 | 첫 기능의 업무 패키지는 하나의 배포 단위로 두고 포트와 어댑터로 연동·영속을 분리한다. 별도 서비스로의 독립 배포는 필요가 확인될 때 판단한다(세션 04의 교육용 설계 선택) |
| 의존 규칙 | 업무 패키지(`order`·`payment`·`delivery`·`product`, 실습은 `subscription` 등)는 연동 패키지(`paymentadapter` 등)와 `persistence`를 import하지 않는다. 패키지 의존에 순환이 없다 |
| 이 과정의 산출물 | 활용 방식 판단, 작업 명세서, 수용 기준, 맥락 패키지(맥락 파일 포함), 위임 계약, 실행 흐름, 가드레일 배치, 하네스 배치, 작업 상태 기계, 평가 세트. 모두 합친 것을 **위임 패키지**라 부른다 |
| 2026-10 기준 | 도구·모델의 능력에 관한 서술은 이 날짜 기준이다. 과정을 열 때마다 원문을 다시 확인한다 |

위 표가 이 과정의 **공통 식별자의 원천**이다. 세션 원고·다이어그램·예시 코드는 이 이름과 값을 그대로 쓴다. 뒤 세션이 새로 발견한 것은 **진화**로서 그 세션이 발견과 되돌림을 보이고 이 표에 반영한다. 같은 대상을 다른 이름·규칙으로 쓴 것은 **오류**이며 이 표에 맞춰 고친다(`sw-engineering-principles.md`의 「교재에 적용하기」).

### AI 용어의 한국어 표기

분야의 1차 자료가 모두 영어이고 정착된 한국어 교육 용어가 없다. 세션을 쓰기 전에 **이 표에서 말을 고르고**, 원고를 쓰며 새 번역어를 만들지 않는다(「검토 절차」 3). 표에 없는 용어를 쓸 때는 먼저 여기에 한 줄을 더한다.

### 영한 용어집과 명명 규칙

본문은 한글 용어를, 도식의 설계 요소와 코드는 아래 영문명을 쓴다. 한 용어에 영문명은 하나이며, 표에 없는 업무 용어는 코드에서 먼저 만들지 않고 여기에 먼저 더한다. 명명 규칙은 OOAD와 같다.

- **타입**(클래스·인터페이스·enum·record) — 영문 명사, PascalCase(`OrderItem`)
- **필드** — 영문 명사, camelCase(`unitPrice`)
- **메서드** — 업무 동사, camelCase(`pay()`). 외부·다른 객체가 알리는 사건은 `on`으로 시작한다(`onPaid()`)
- **enum 값** — UPPER_SNAKE(`PENDING_PAYMENT`)
- **패키지** — 소문자 단수, 붙여 쓴다(`order`, `paymentadapter`)

| 한글 | 영문 | 종류 |
|---|---|---|
| 주문 | `Order` | 타입 |
| 주문 항목 | `OrderItem` | 타입 |
| 주문 번호 | `OrderNumber` | 타입 |
| 주문 상태 | `OrderStatus` | 타입 |
| 결제대기 / 결제완료 / 배송중 / 배송완료 / 취소됨 | `PENDING_PAYMENT` / `PAID` / `IN_DELIVERY` / `DELIVERED` / `CANCELLED` | 주문 상태 값 |
| 상품 / 상품 번호 | `Product` / `ProductNumber` | 타입 |
| 결제 | `Payment` | 타입 |
| 결제 수단 | `PaymentMethod` | 타입(이 과정에서 추가) |
| 배송 | `Delivery` | 타입 |
| 금액 / 수량 / 주소 | `Money` / `Quantity` / `Address` | 타입 |
| 단가 / 판매가 | `unitPrice` / `salePrice` | 필드 |
| 주문 총액 | `totalAmount` | 필드·메서드 |
| 배송지 | `shippingAddress` | 필드 |
| 확정한다 | `confirm` | 메서드(주문 항목의 단가 확정) |
| 결제한다 | `pay` | 시스템 오퍼레이션(이 과정에서 추가) |
| 결제되었다 | `onPaid` | 메서드 |
| 결제 승인을 요청한다 | `requestApproval` | 메서드(결제 시스템에 대한 요청, 이 과정에서 추가) |
| 배송을 요청한다 | `requestDelivery` | 메서드(배송 시스템에 대한 요청, 이 과정에서 추가) |

| 연동 | `Adapter` | 접미사(`PaymentAdapter`, 패키지 `paymentadapter`) |
| 주문 서비스 | `OrderService` | 타입(시스템 이벤트를 받아 주문을 찾고, 맡기고, 저장한다) |

| 영속 | `persistence` | 패키지 |

| 한글 | 영문 | 종류 |
