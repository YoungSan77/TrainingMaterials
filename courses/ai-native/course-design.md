# AI-native SW 공학 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** AI-native SW 공학 (`ai-native`)
- **총 교육시간:** 14시간, 2일(하루 7시간). 1시간은 강의 50분과 휴식 10분이다. 세션 시간은 계획값이며 최종 SA 완성 후 운영 적합성을 평가한다.
- **대상:** SW 아키텍트, Back-End·Front-End 개발자, Cloud 엔지니어, AI 엔지니어
- **선수지식:** LLM 대화 도구나 코딩 에이전트를 업무에 써 본 경험, 자바 코드 독해, Git 사용

이 과정은 **독립된 과정**이다. 관통 사례와 그 이름은 "객체지향 분석과 설계 실무"(`ooad`)와 같게 맞추며(연계 조정), 이 과정만 듣는 수강생도 이해하도록 필요한 전제를 이 문서와 개요 세션이 직접 소개한다.

### 과정의 맥락

아래 성숙도·운영 조건은 **가정**이다. 사전 설문과 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 | 확인 방법 |
|---|---|---|
| **도메인** | 주문·결제·배송을 사용자로서 안다. 사례의 규칙은 과정이 정해 준다 | 사전 설문 |
| **기술** | LLM으로 코드·문서를 만들어 봤지만, 위임할 작업의 명세·맥락·권한·검증을 설계해 본 적은 적다. 자바 코드를 읽고 테스트를 실행한다 | 사전 설문, 실습 1 |
| **팀워크** | 코드 리뷰는 하지만 AI가 만든 결과를 무엇으로 받아들일지(수용 기준·증거) 팀이 합의해 본 경험은 적다 | 사전 설문, 실습 4 |

- **다루는 불확실성** — **기술 불확실성**이 중심이다. LLM의 생성은 비결정적이고 그럴듯한 추측을 섞으며, 모델·도구의 능력이 빠르게 바뀐다. 업무 불확실성은 단순한 주문 사례와 정해 둔 규칙으로 낮춘다.
- **깊이의 결정** — 성숙도가 낮은 **사람이 정할 결정의 명시**(명세·수용 기준), **맥락의 선별**, **위임 경계**, **센서와 증거**를 명시하고 먼저 검증한다. 도구별 기능·설정은 예로만 보이고 가르치지 않는다. 내용은 날짜가 있는 1차 원문을 따르며 원고에 "2026-10 기준"을 밝힌다.
- **요구에서 코드까지의 경로** — 강의의 주문한다와 실습의 정기배송은 **도메인·기술 복잡성 모두 중간**이다. 업무 규칙 3가지와 상태 몇 개, 외부 시스템 연동(결제·배송)이 있다. 그래서 불변의 뼈대(요구 → 유저 스토리(수용 기준 포함) → 코드·테스트)에 작업 명세서(업무 규칙과 예)·용어집과 상태 기계·의존 규칙을 가볍게 더하고, 남기는 것은 요구사항 정의서·용어집·상태 기계·의존 규칙(맥락 파일)이다. 작업 명세서는 작업용이다(「4. 과정 전체 판단 원칙」).
- **운영 조건** — 가정: 20명 안팎, 개인 실습과 결과 공유. 실습 환경은 수강생이 쓰는 **LLM과 코딩 에이전트**(엑셀 초안 기준 Claude Code(Team)), Git, JDK다. 결과물은 도구와 무관한 산출물이며 특정 도구·SDK의 사용법은 다루지 않는다.

참고 자료는 별도 문서인 별첨 `sessions/references.md` 하나에 레이블의 알파벳 순서로 둔다. 본문은 레이블로 인용·참조한다. 분야가 빠르게 바뀌고 주목받는 1차 자료가 많아, 이 과정은 다른 과정의 "10개 이내"를 적용하지 않는다(2026-10-06). 세션은 topic의 핵심 메시지를 받칠 때만 인용한다.

**원전 적용 결정**

- **개발 방식의 구분** — LLM 이전·AI 지원(AI-assisted)·AI-native의 세 구분과 개발자·LLM의 역할 구분(「4. 과정 전체 판단 원칙」)은 원전의 분류가 아니라 **이 과정의 구분**이다. 원고에서 원전의 정의처럼 제시하지 않고, 각 구분을 받치는 원문(워크플로·에이전트의 정의, 하네스의 정의 등)만 인용한다(2026-10-06).
- **위임 형태** — 워크플로와 에이전트의 정의, 증강 LLM, 다섯 워크플로 패턴(프롬프트 체이닝·라우팅·병렬화·오케스트레이터-워커·평가자-최적화기)은 [Anthropic 2024]를 따른다. 수작업과 대화형 보조는 이 과정이 더한 비교 대상이다(2026-10-06).
- **하네스** — 가이드(feedforward)·센서(feedback), 계산적(computational)·추론적(inferential) 구분은 [Böckeler 2026a]를 따른다. 가드레일은 하네스의 가이드 중 **실행 전에 강제되는 제약**을 가리키는 이 과정의 이름이다(2026-10-06).
- **위험** — NIST AI RMF는 위험을 식별·측정·관리하는 어휘로만 쓴다. 과정의 뼈대로 쓰지 않으며 조직 거버넌스(GOVERN)의 상세는 다루지 않는다. 생성형 AI의 위험 항목은 [NIST 2024], 실행 시점의 에이전트 보안 위험은 [OWASP 2025]를 참고한다(2026-10-06).
- **활용 방식과 자율성** — 과정의 기준은 수작업·대화형 보조·워크플로·에이전트의 4가지 방식이다. [Blount 외 2026]의 자율성 단계는 S02에서 **보완 관점**으로 대응만 보이고, 형태를 대신하지 않는다(2026-10-06).
- **인용과 추론** — 인용은 원문에서 확인한 문장만 쓴다(`tools/verify-quote.js`). 원문으로 확인하지 못한 관점(예: Software 3.0, 부분 자율, 비결정적 추상, AI의 증폭 효과)은 출처를 달지 않고 이 과정의 설명(추론)으로만 쓴다. 그런 자료([Karpathy 2025]·[Fowler 2025]·[DORA 2025])는 참고 자료에 읽을거리로 둔다(2026-10-06).
- **AI 지원과 바이브 코딩** — 바이브 코딩(결과를 보지 않고 받아들이는 방식)은 개발 방식의 한 구분이 아니라 **규율이 없는 사용**이다. AI 지원·AI-native 모두에 생길 수 있으며, 증강 코딩·바이브 엔지니어링과 대비해 보인다(2026-10-06).
- **Technology Radar** — Radar의 링(Adopt·Trial·Assess·Caution)은 기법이 업계에서 어느 단계인지 보여 주는 신호로만 인용한다. 판(Vol. 34, 2026-04)을 밝히고 과정을 열 때마다 최신판으로 다시 확인한다(2026-10-06).
- **본질적 복잡성은 업무 규칙이다** — [Brooks 1986]의 본질적·우연적 복잡성을 이 과정은 이렇게 대응시킨다: 본질적 복잡성은 **업무 규칙**(도메인 지식), 우연적 복잡성은 업무 규칙을 **코드로 옮기는 일**이다. AI는 뒤의 것을 크게 줄였고 앞의 것은 사람이 정한다. 대응은 이 과정의 해석이며 Brooks의 문장이 아니다. 업무 규칙을 명시하는 수단으로 용어집·도메인 모델([Evans 2015]의 보편 언어)과 온톨로지([Gruber 1993])를 함께 다룬다(2026-10-07).
- **용어** — 업무 담당자가 정하는 주문 금액·배송 요청·결제 거절 같은 규칙은 **업무 규칙**으로 부른다. 요구의 작업 단위는 **유저 스토리**, 그 테스트 기준은 **수용 기준**이라 부른다(2026-10-08). 동기·비동기는 설계에서 정할 일이라 이 과정의 시나리오·요구에서 구분하지 않는다. 원고 본문은 코드 식별자(`pay` 등)와 사례 번호(O-1 등) 대신 한글 이름을 쓰고, 영문 이름은 코드 안에만 둔다(2026-10-07).
- **번역** — context는 **맥락**(OOAD·엑셀과 같음)으로 쓴다. workflow·agent·harness·guardrail·sensor는 음차하고 처음 나올 때 원어를 병기한다(워크플로(workflow)). human-in-the-loop는 **사람의 개입**, checkpoint는 **확인 지점**, eval은 **평가**로 쓴다(2026-10-06).
- **받은 원문** — 자동 접근이 막힌 원문은 `references/inputs/`에 두고 그 파일로 인용을 확인한다: [OpenAI 2025]·[DORA 2025]·[Blount 외 2026]은 PDF, [Lopopolo 2026]은 영문판 본문 추출(openai.com이 한국어판으로 자동 전환한다)(2026-10-06).

## 2. 과정 목표

AI와 협업하는 SW 개발에서 명세·맥락·작업 위임·검증의 역할과 사람의 판단 책임을 이해하고, 워크플로·에이전트의 적용 조건과 가드레일·검증 하네스를 위험에 맞게 배치하는 능력을 기른다. 목차마다 LLM 실습으로 AI와 협업하는 개발 역량을 기른다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. LLM 이전·AI 지원·AI-native 개발을 구분하고, AI-native에서 개발자가 할 일과 LLM이 할 일을 나눈다.
2. 작업의 특성으로 수작업·대화형 보조·워크플로·에이전트 중 가장 단순한 충분한 형태를 고른다.
3. 요청을 작업 명세서와 수용 기준으로 구체화하고, 검증할 수 있는 작업 단위로 나눈다.
4. 도메인·설계 지식(용어집, 도메인 모델, 상태 기계, 의존 규칙)을 맥락으로 구성하고, 도구·권한·상태의 경계를 정한다.
5. 사람의 개입·가드레일·하네스를 위험에 맞게 배치하고, 센서의 증거로 결과를 받아들인다.
6. 실패를 원인이 된 결정으로 되돌리고, 평가 세트로 보안·비용·모델 변경을 점검한다.

## 3. 범위와 경계

**Core:** 개발 방식의 구분과 개발자·LLM의 역할, 활용 방식의 선택, 작업 명세서와 수용 기준, 맥락 구성(도메인 모델·온톨로지·OOAD·DDD와의 관계 포함), 도구·권한·상태의 경계, 워크플로·에이전트와 사람의 개입, 가드레일, 검증 하네스와 결과 점검, 실패 대응·복구, 평가 세트와 운영 점검(보안·비용·모델 변경).

**Non-scope:** 제품에 LLM 기능을 넣는 설계(이 과정은 SW **개발 작업**에 AI를 쓰는 것을 다룬다), 특정 vendor SDK·도구 설정의 사용법, 모델 학습 이론, 프롬프트 요령 모음, 조직의 AI 전환과 거버넌스.

**다른 과정과의 연계**

| 과정 | 연계 |
|---|---|
| 객체지향 분석과 설계 실무(`ooad`) | 관통 사례와 이름을 같게 맞춘다. OOAD의 "14. AI-native SW공학"(45분)은 이 과정의 **미리 보기와 연결**이며 깊이는 이 과정이 맡는다. 같은 내용을 두 곳에 쓰지 않는다. 유스케이스·도메인 모델·상태 기계의 작성법은 OOAD가 맡고, 이 과정은 그 산출물을 **맥락과 명세의 입력**으로 쓴다 |
| SWQM | 품질 특성·검증 체계의 전문 판단은 SWQM이 맡는다. 이 과정은 위임 결과를 받아들이는 증거(센서·평가 세트)만 다룬다 |
| DT→AX | 조직의 AI 도입·운영 모델은 DT→AX로 넘긴다 |

다른 과정의 내용을 이 과정의 완결성을 위해 복제하지 않는다. 필요한 최소 맥락만 짧게 소개한다.

## 4. 과정 전체 판단 원칙

- AI-native 개발의 핵심은 모델 호출이 아니라 **불확실한 생성 능력을 책임 있는 실행 경계와 검증 증거 안에 두는 것**이다.
- 가장 단순한 형태로 시작하고, 증거가 요구할 때만 자율성을 높인다.
- LLM은 명세의 빈칸을 그럴듯한 추측으로 채운다. 사람이 정할 결정은 위임 전에 정하거나, 모르면 멈추고 묻게 한다.
- 에이전트의 "완료"는 주장이다. 센서가 낸 증거와 확인 지점의 판단으로 받아들인다.
- 실패는 같은 입력의 재시도가 아니라 원인이 된 결정(명세·맥락·경계·하네스)으로 되돌려 고친다.

**개발 방식의 구분** — 이 과정의 구분이다(「원전 적용 결정」).

| 구분 | 작업의 단위 | 누가 무엇을 하는가 | 검증 |
|---|---|---|---|
| **LLM 이전** | 사람이 쓰는 코드 | 사람이 명세·설계·코드·테스트를 모두 쓴다. 도구(컴파일러·IDE·CI)는 결정적이다 | 사람이 쓴 테스트와 리뷰 |
| **AI 지원**(AI-assisted) | LLM의 제안 하나(코드 완성, 대화의 답) | 사람이 작업 흐름을 그대로 쥐고, LLM이 조각을 제안하면 사람이 읽고 받아들인다 | 사람이 제안마다 읽는다 — 리뷰가 병목 |
| **AI-native** | 맡긴 과제 하나 | 사람이 의도·맥락·경계·하네스를 설계하고, LLM(에이전트)이 과제를 실행하고 센서로 스스로 고친다 | 하네스의 센서가 낸 증거와 확인 지점에서 사람의 판단 |

- AI-native는 "모든 작업을 에이전트에게"가 아니다. AI-native 개발에서도 작업마다 수작업·대화형 보조·워크플로·에이전트 중 가장 단순한 충분한 형태를 고른다("02. 작업 특성에 따른 AI 활용 방식").
- 바뀌는 것은 사람의 일의 **위치**다. 코드를 직접 쓰고 읽던 일이 의도를 명세하고, 맥락과 경계를 설계하고, 증거를 판단하는 일로 옮겨 간다.

**AI-native에서 개발자의 일과 LLM의 일**

| 활동 | 개발자가 한다 | LLM(에이전트)이 한다 |
|---|---|---|
| 문제·의도 | 문제와 의도를 정하고, 규칙·정책·위험 수용을 결정한다 | 요청에서 빠진 결정을 **질문으로** 드러낸다(정하지 않는다) |
| 명세·수용 기준 | 작업 명세서와 허용·거절 예시를 확정한다 | 명세·예시의 초안을 만든다. 확정된 기대값을 바꾸지 않는다 |
| 맥락 | 과제의 판단을 바꾸는 지식을 고르고 맥락 파일을 유지한다 | 맥락 안에서 필요한 파일·정보를 찾아 읽는다 |
| 위임 경계 | 도구·권한·상태·멈출 조건을 정한다 | 경계 안에서 도구를 호출하고, 경계에 닿으면 멈추고 묻는다 |
| 실행 | — | 코드와 테스트를 만들고 고친다. 빌드·테스트를 실행하고 진행을 기록한다 |
| 가드레일·하네스 | 가드레일과 센서를 설계하고 유지한다 | 센서의 결과로 스스로 고친다. 센서(테스트·검사)를 끄거나 지우지 않는다 |
| 결과 판단 | 확인 지점에서 증거를 보고 받아들이거나 되돌린다. 최종 책임을 진다 | 완료의 증거(테스트 출력)를 보인다. 추론적 센서로서 리뷰를 보조한다 |
| 실패·변경 | 실패를 원인이 된 결정으로 되돌리고, 평가 세트를 유지한다 | 정해진 상한 안에서 재시도하고, 같은 실패가 반복되면 멈춘다 |

이 구분은 OOAD "01. OOAD 개요"의 Human·AI 책임(사람이 최종 책임지는 판단 / 사람과 AI의 협업 / AI가 주도할 수 있는 실행)과 같은 방향이다. 협업 영역은 위 표에서 "LLM이 초안을 만들고 개발자가 확정한다"로 나눈다.

**요구에서 코드까지의 경로** — `guides/sw-engineering-principles.md` 7절을 이 과정에 적용한다.

- **명세와 산출물** — 요구는 원하는 것, 요구사항은 시스템이 충족할 것이다. SDD의 명세는 새 산출물이 아니라 **요구사항 정의**를 다시 부르는 이름이다. 요구사항의 명세는 범위·수명에 따라 **요구사항 정의서**(시스템 전체, 유지 — 용어집 포함)와 **작업 명세서**(스토리 하나, 작업용)로 나눈다. 도메인 모델(분석 — 개념·관계·상태 기계)과 아키텍처(설계)는 명세가 아니며, 명세가 가리키고 에이전트에게 맥락으로 준다. 경로는 명세 → (도메인 모델·아키텍처) → 코드다. OOAD와 같은 이름을 쓴다(OOAD의 실습 1 결과물도 요구사항 정의서다).
- **불변의 뼈대** — 요구 → 유저 스토리(수용 기준 포함) → 코드·테스트. 유저 스토리가 AI에게 맡기는 작업 단위이고, 수용 기준(업무 규칙의 대표 예로 쓴 테스트 기준)이 테스트가 된다. 수용 기준이 없는 스토리 카드만으로는 명세가 아니다.
- **중간 산출물은 두 축으로 고른다** — 도메인 복잡성이 크면 작업 명세서(업무 규칙과 예)와 도메인 모델(용어집·상태 기계)을, 기술 복잡성이 크면 아키텍처(경계·의존 규칙·외부 연동)를 더한다. 사다리처럼 차례로 더하지 않는다.

| | 기술 복잡성 낮음 | 기술 복잡성 높음 |
|---|---|---|
| **도메인 복잡성 낮음** | 스토리와 예 → 코드 | + 아키텍처 |
| **도메인 복잡성 높음** | + 작업 명세서 + 도메인 모델 | 모두 |

- **무엇·언제·얼마나** — 무엇을 넣는가는 복잡성이, 언제 쓰는가는 불확실성이, 얼마나 남기는가는 수명·변경 빈도와 함께 쓰는 사람·에이전트의 수가 정한다. 명세 주도 개발(SDD)의 3가지 수준은 "얼마나 남기는가"의 답이며 별도의 단계가 아니다.
- **넣는 기준** — 그 산출물이 **에이전트의 결과나 사람의 확인을 바꾸는가?** LLM이 문서를 싸게 만들어도 검토 비용과 맥락의 한계는 그대로이므로, 바꾸지 않으면 넣지 않는다.
- **오래 남는 것** — 요구사항 정의서(업무 규칙 목록 포함)·도메인 모델·의존 규칙이다. 작업 명세서는 그것을 가리키고 다시 쓰지 않는다. 명세 고정은 작업 명세서를 정의서처럼 유지하는 것이다.
- **세션 배치** — S01은 경로를 미리 보이고, S03은 SDD를 앞에서 방식으로 소개하고, 명세와 산출물의 관계와 명세의 알맞은 수준에서 두 축을 다루며, S04는 뼈대의 수용 기준과 테스트를, S05는 도메인 모델·아키텍처를 맥락으로 넣는 조건을 다룬다.

### S01 — AI 협업의 특성과 사람의 판단 책임 (1시간)

- **목표:** AI가 SW 공학에서 바꾼 것(업무 규칙을 코드로 옮기는 일)과 바꾸지 않은 것(업무 규칙)을 구분하고, LLM 이전·AI 지원·AI-native 개발과 그 안에서 개발자의 일과 LLM의 일을 나누며, 과정 전체의 결정 지도를 확인한다.
- **Anchor Message:** AI는 실행을 빠르게 하지만, 무엇이 옳은 결과인지의 판단과 책임은 사람에게 남는다.
- **세부 목차:** 세션 목표 / 첫 시도 — 요청 한 줄로 10분 만에 만든 주문 기능과 업무 담당자 리뷰에서 나온 문제 3가지 / 본질적 복잡성과 우연적 복잡성 — 본질적 복잡성은 업무 규칙(도메인 지식)이고 우연적 복잡성은 업무 규칙을 코드로 옮기는 일이다, AI가 줄인 것과 줄이지 못한 것 / 업무 규칙은 도메인 지식이다 — 회사의 정책·운영 방식·고객과의 약속이 정하며 회사마다 다르다 / LLM이라는 새 재료 — 그럴듯한 추측(confabulation), 비결정성, 맥락의 한계 / 업무 규칙의 명시 — 용어집·도메인 모델(DDD 보편 언어)과 온톨로지 / 개발 방식의 구분 — LLM 이전·AI 지원·AI-native(작업의 단위·역할·검증), 바이브 코딩 대 증강 코딩·바이브 엔지니어링 / 개발자의 일과 LLM의 일 — "사람이 조종하고 에이전트가 실행한다", 사람은 업무 규칙을 정하고 명시하고 검증한다 / 관통 사례 — 주문 시스템 시나리오(배경, 첫 기능, 업무 규칙, 주문 상태) / 요구에서 코드까지의 경로 — 불변의 뼈대(요구 → 유저 스토리(수용 기준 포함) → 코드·테스트)와 복잡성에 따라 고르는 중간 산출물(미리 보기) / 결정 지도 — 활용 방식 → 명세·수용 기준 → 맥락 → 위임 경계 → 개입·가드레일·하네스 → 실패·평가 / 실습 1 — 추측 찾기 / 요약
- **근거 자료:** [Brooks 1986](본질적·우연적 복잡성), [NIST 2024](confabulation), [Anthropic 2025c](맥락의 한계), [Evans 2015](보편 언어), [Gruber 1993](온톨로지), [Anthropic 2024](워크플로·에이전트), [Beck 2025]·[Willison 2025b](규율), [Lopopolo 2026](사람의 역할), [Böckeler 2026a](하네스). 비결정성·습관의 증폭·"LLM은 흔히 보이는 답을 고른다"는 이 과정의 설명이다
- **사례에서 답하는 결정:** 첫 시도의 코드가 추측으로 채운 업무 규칙 3가지(주문 금액, 배송 요청, 결제 거절)과 업무 담당자가 정한 규칙.
- **다이어그램·코드:** 주문 상태 기계, 첫 시도의 결제 코드 한 장과 업무 규칙을 기대값으로 쓴 테스트 결과.

### S02 — 작업 특성에 따른 AI 활용 방식 (1시간)

- **목표:** 작업 특성 4가지와 AI 활용 방식 4가지를 설명하고, 작업 특성에 따라 가장 단순하면서 충분한 방식을 고르며, 자율성의 대가와 AI가 할 수 없는 일, 방식을 한 단계 올리는 조건을 설명한다.
- **Anchor Message:** 가장 단순한 방식으로 시작하고, 맡겨도 된다는 증거가 분명할 때만 자율성을 높인다.
- **세부 목차:** 세션 목표 / 작업 특성 — 작업 특성 4가지(업무 규칙의 확정, 절차의 확정, 결과의 자동 확인, 되돌리기 쉬움), 주문 기능의 작업 특성 / AI 활용 방식 — 증강 LLM, 4가지 활용 방식(수작업·대화형 보조·워크플로·에이전트)과 자율성 / 작업 특성에 따른 선택 — 선택의 흐름, 자율성의 대가(시간·비용·오류의 누적), AI가 할 수 없는 일(업무 규칙, 되돌리기 어려운 결정)과 필요 없는 일(결정적인 도구), 에이전트가 맞는 일 / 주문 기능의 활용 방식 / 시연 — 같은 일, 3가지 방식 / 판단이 갈리는 경우 — 외부 문서가 다를 때, 업무 규칙 전과 후 / 잘못된 관행 / 자율성을 높이는 조건 / 실습 2 — 활용 방식 판단 / 요약
- **근거 자료:** [Anthropic 2024](기준 원전 — 증강 LLM, 단순한 해법, 대가, 코딩 에이전트가 효과적인 경우), [OpenAI 2025](에이전트가 맞는 작업, 결정적인 해법). 작업 특성 4가지로 묶은 것과 방식별 대가의 비교는 이 과정의 정리다
- **사례에서 답하는 결정:** 주문한다의 일 6가지 — 업무 규칙 정하기는 수작업(업무 담당자)과 대화형 보조, 저장소 골격은 수작업(템플릿), 주문 금액·상태 구현은 에이전트, 결제·배송 연동 코드는 워크플로, 주문 데이터 이관은 수작업, 릴리스 노트는 대화형 보조.
- **다이어그램·코드:** 증강 LLM, 선택의 흐름, 방식의 변화, 자율성의 계단(도식), 활용 방식 판단표. 코드 없음 — 이 세션의 결정은 코드가 아니라 일과 방식이다.

### S03 — 요구의 구체화와 명세 (1시간 30분)

- **목표:** 요청을 문제/기회 → 요구 → 요구사항으로 구체화하고, 유저 스토리를 바탕으로 업무 규칙·범위·제외·미정을 붙인 작업 명세서로 만든다.
- **Anchor Message:** LLM은 명세의 빈칸을 그럴듯한 추측으로 채우므로, 사람이 정할 것은 먼저 정해 작업 명세서에 쓴다.
- **세부 목차:** 세션 목표 / 명세 주도 개발 — 명세 주도 개발이란?(방식 — 언제 쓰고 얼마나 남기는가, 명세는 요구사항 정의를 다시 부르는 이름), 명세에 무엇을 쓰는가?(스토리·수용 기준·업무 규칙과 예·범위는 쓰고, 도메인 모델·아키텍처는 가리킨다), 명세에서 코드까지(경로 4가지), Kiro의 요구 문서(주문한다를 Kiro 형식으로), 명세를 쓰는 순서(세션 지도) / 문제에서 요구사항으로 — 문제·요구·요구사항·해결책, 업무 규칙 찾기 / 요구를 담는 형식 — 이벤트로 보는 형식(이벤트–반응 목록·유스케이스·도메인 이벤트는 소개) / 유저 스토리 — 카드·대화·확인, 문형과 가치, INVEST, 세로로 나누기, 잘못된 유저 스토리 / BDD — 예로 명세하기: 발견·정형화·자동화, Given-When-Then, Example Mapping(스토리·규칙·예·질문), BDD와 AI / 명세와 산출물 — 요구·요구사항·유저 스토리·요구사항 정의서·작업 명세서·도메인 모델·아키텍처, 산출물의 관계 / 작업 명세서 — 작업 명세서란?(스토리 하나의 작업용 요구사항 명세 — 유저 스토리 + 업무 규칙과 예 + 범위·제외·미정·참조), 주문한다의 작업 명세서 / SDD의 수준과 한계 — 명세와 메모리 뱅크, 3가지 수준(명세 먼저·명세 고정·명세가 원천), 도구 3가지(Kiro·spec-kit·Tessl), 한계(크기와 리뷰·통제의 착각·무엇을 누가 쓰는가?), 모델 주도 개발의 교훈, 지침 / 명세의 알맞은 수준과 경로 — 알맞은 높이(과소·알맞음·과잉), 요구에서 코드까지(불변의 뼈대, 도메인·기술 복잡성의 두 축), 무엇·언제·얼마나, 주문한다의 경로 / 시연 — LLM이 쓴 작업 명세서(실제 실행) / 잘못된 관행 / 실습 3 — 작업 명세서 / 요약
- **근거 자료:** [Böckeler 2025](기준 원전 — 명세의 정의, 3가지 수준, 요구 → 설계 → 작업, 한계), [Anthropic 2025c](알맞은 높이). ### S04 — 수용 기준과 검증 가능한 작업 단위 (1시간)

- **목표:** 작업 명세서를 허용·거절 예시로 된 수용 기준으로 바꾸고, 한 번에 검증할 수 있는 크기의 작업 단위로 나눈다.

### S05 — 도메인·설계 지식과 맥락 구성 (1시간 30분)

- **목표:** 과제의 판단을 바꾸는 도메인·설계 지식을 골라 맥락 패키지로 구성하고, 맥락의 한계(주의 예산)를 관리한다.
- **Anchor Message:** 좋은 맥락은 많은 맥락이 아니라 판단을 바꾸는 최소의 고신호 정보다.
- **세부 목차:** 맥락 엔지니어링의 정의와 프롬프트 엔지니어링과의 차이 / 주의 예산과 맥락 부패(context rot) / 맥락의 구성 — 시스템 지시의 고도, 도구, 예시, 필요할 때 가져오기(에이전트 검색) / 저장소가 기록의 원천(system of record) — 에이전트가 맥락에서 볼 수 없는 지식은 없는 것이다 / 맥락 파일 — 백과사전이 아니라 지도(목차), 점진적 공개(progressive disclosure), 공개 형식 AGENTS.md / 도메인 지식 — 용어집·도메인 모델·상태 기계, 온톨로지 / 설계 지식 — 패키지 경계와 의존 규칙 / 무엇을 맥락으로 넣는가 — 도메인·기술 복잡성에 따라, 오래 남길 것(맥락 파일)과 작업용(작업 명세서) / OOAD·DDD(보편 언어)와의 관계 / 긴 작업의 맥락 — 압축·구조화한 노트·하위 에이전트 / 잘못된 관행 — 맥락 쏟아붓기, 지시 비대(agent instruction bloat) / 실습 5 — 맥락 패키지 / 요약

### S06 — 작업 위임과 도구·권한·상태의 경계 (1시간)

- **목표:** 맡긴 작업이 쓸 도구, 가질 권한, 바꿀 수 있는 상태, 멈출 조건을 위임 계약으로 정한다.

### S07 — 워크플로·에이전트와 사람의 개입 (1시간 30분)

- **목표:** 고른 활용 방식를 워크플로 패턴과 에이전트 루프로 구성하고, 위험에 따라 사람의 확인 지점을 둔다.
- **Anchor Message:** 사람의 개입은 모든 단계가 아니라 되돌리기 어렵고 판단이 필요한 지점에 둔다.
- **세부 목차:** 다섯 워크플로 패턴(프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-워커, 평가자-최적화기) / 에이전트 루프와 종료 조건 — 반복 실행(Ralph loop)의 조건 / 단일 에이전트와 여러 에이전트 — 관리자형·분산형, 계획자·생성자·평가자의 분리 / 여러 에이전트의 비용 — 토큰, 오류의 누적, 조정 / 사람의 개입 — 확인 지점, 개입의 계기(실패 한도 초과, 위험이 큰 행동), "판단이 필요할 때만 사람에게" / 위험에 따른 개입의 배치 / 잘못된 관행 — 모든 단계의 형식적 승인, 코딩 에이전트 떼(coding agent swarms) / 실습 7 — 실행 흐름 / 요약

### S08 — 실행 제약과 가드레일의 역할 (1시간)

- **목표:** 위험을 식별하고, 어긋난 실행을 미리 막는 가드레일을 입력·도구 호출·출력·환경 중 어디에 어떤 방식(강제·지시)으로 둘지 정한다.

### S09 — 검증 하네스·결과 점검·피드백 (1시간 30분)

- **목표:** 가이드와 센서를 짝지어 하네스를 구성하고, 계산적·추론적 센서와 사람의 리뷰를 결과 점검에 배치하며, 센서의 실패에서 원인이 된 판단을 찾는다.
- **Anchor Message:** 에이전트의 "완료"는 주장이고, 센서가 낸 증거만이 완료를 보인다.
- **세부 목차:** 하네스의 정의(에이전트 = 모델 + 하네스) / 가이드와 센서, 계산적·추론적 / 조종 루프(steering loop)와 품질을 왼쪽에(keep quality left) / 하네스의 세 범주 — 유지보수성·아키텍처 적합성·행위 / 센서 — 컴파일, 수용 테스트, 의존 규칙 검사, 결합도, LLM 심사 / 불변 조건을 기계로 강제하기 — 검사의 오류 메시지가 고칠 방법을 맥락에 넣는다 / 엔지니어의 일 — 환경·의도·피드백 루프, 하네스를 만들기 쉬운 코드(harnessability) / 센서의 실패가 가리키는 판단 / 사람의 리뷰가 볼 것 — 자동 검사가 놓치는 것 / 잘못된 관행 — 테스트를 끄는 에이전트 / 실습 9 — 하네스 배치 / 요약
- **근거 자료:** [Böckeler 2026a](기준 원전), [Böckeler 2026b](유지보수성 센서), [Lopopolo 2026](기계적 강제), [Beck 2025](경고 신호), [Anthropic 2025a](LLM 심사·사람의 평가), [Thoughtworks 2026](feedback sensors for coding agents·mutation testing — Trial)
- **사례에서 답하는 결정:** 주문한다의 센서 — 수용 테스트, 의존 규칙(`order`는 연동·`persistence`를 import하지 않음), 단가 확정의 LLM 심사.
- **다이어그램·코드:** 하네스 구성(도식), 의존 규칙 테스트와 수용 테스트(자바).

### S10 — 실패 대응·재시도·복구 (1시간)

- **목표:** 작업 실패를 유형(명세 결함·맥락 누락·환경 오류·모델 한계)으로 진단하고, 재시도·중단·되돌림·상위 결정 재검토 중 대응을 정한다.
- **Anchor Message:** 같은 입력의 재시도는 복구가 아니며, 실패는 원인이 된 결정으로 되돌린다.
- **세부 목차:** 실패의 유형 — 명세 결함·맥락 누락·환경 오류·모델 한계 / "더 열심히"가 아니라 "무엇이 빠졌나" / 에이전트는 상태를 가지고 오류가 누적된다 / 재시도의 조건과 상한 / 체크포인트와 되돌림 — 커밋 단위의 진행, 진행 기록으로 이어 받기 / 추적(trace)과 관찰 / 엔트로피 — 에이전트는 있는 패턴을 복제한다, 정리 작업을 계속 돌린다 / 작업 상태 기계 / 잘못된 관행 — 무한 재시도, 실패 숨기기, 내구성 없는 에이전트 작업 / 실습 10 — 실패·복구 / 요약
- **근거 자료:** [Lopopolo 2026](빠진 능력·엔트로피), [Anthropic 2025a](상태와 오류 누적), [Anthropic 2025d](진행 기록·점진적 진행), [OpenAI 2025](실패 한도), [Blount 외 2026](추적), [Thoughtworks 2026](ignoring durability in agent workflows·codebase cognitive debt — Caution)
- **사례에서 답하는 결정:** 결제 거절 테스트가 실패하면 재시도하지 않고 명세의 거절 규칙 누락으로 되돌린다.
- **다이어그램·코드:** 작업 상태 기계(진행·검증 실패·재시도·사람 확인·중단·완료).

### S11 — 평가 세트와 운영 점검 — 보안·비용·모델 변경 (1시간)

- **목표:** 위임 구성의 품질을 평가 세트로 측정하고, 보안·비용·모델 변경이 생길 때 다시 점검할 기준을 정한다.
- **Anchor Message:** 데모의 성공은 증거가 아니며, 모델·맥락이 바뀌면 같은 평가 세트로 다시 확인한다.
- **세부 목차:** 평가의 구조 — 과제·시행·채점기·결과 / 채점기의 세 종류 — 코드·모델·사람 / 능력 평가와 회귀 평가 / 코딩 에이전트의 평가 / 체감과 측정 — 숙련 개발자 연구의 결과, 처리량은 생산성이 아니다 / 단일 점수의 함정 — 품질·안전·비용·지연 / 모델 변경 — 모델이 좋아지면 하네스를 다시 단순하게, 같은 평가 세트로 다시 확인 / 생성형 AI의 위험 항목 — 데이터 반출·개인정보·정보 보안 / vendor 독립성 — 공개 형식(AGENTS.md·MCP) / 위험 관리의 주기 / 실습 11 — 평가 세트 / 요약
- **근거 자료:** [Anthropic 2026a](기준 원전), [Blount 외 2026](지표 주도 개발·LM 심사), [METR 2025](체감과 측정), [Anthropic 2026b](하네스의 단순화), [NIST 2024], [Thoughtworks 2026](coding throughput as a measure of productivity — Caution)
- **사례에서 답하는 결정:** 주문한다 과제의 변형(승인·거절·판매가 변경)과 기대 결과로 평가 세트를 만들고, 모델·맥락 파일이 바뀌면 다시 실행한다.
- **다이어그램·코드:** 평가 세트 표.

### S12 — 명세·맥락·작업 지시의 종합 검토 (1시간)

- **목표:** 실습 1~11의 위임 패키지로 실제 코딩 에이전트에게 작업을 맡기고, 결과를 하네스의 증거로 검토해 원인이 된 결정으로 되돌린다.
- **Anchor Message:** 위임 결과의 문제는 프롬프트가 아니라 원인이 된 결정에서 고친다.
- **세부 목차:** 위임 패키지의 구성 / 종합 실행 / 결과 검토 — 증거와 확인 지점 / 원인 결정으로 되돌리기 / 자율성을 높이는 조건 — 시험·검증·리뷰·복구가 시스템에 담긴 만큼 / 과정 정리 — 개발자의 일과 LLM의 일 / 실습 12 — 종합 실행 / 요약
- **근거 자료:** [Lopopolo 2026](자율성의 단계), [Willison 2025b](규율의 목록)
- **사례에서 답하는 결정:** 강의는 주문 시스템의 저장소가 빈 저장소에서 어디까지 왔는지(모델 패키지 → 맥락 파일 → 하네스 → 주문한다)를 되짚는다. 실습은 정기배송의 두 기능(신청한다, 배송지를 변경한다)을 실제 에이전트로 실행하고, 드러난 문제를 명세·맥락·경계·하네스 중 어디에서 고칠지 정한다.
- **다이어그램·코드:** 위임 패키지 전체(도식), 에이전트의 실행 결과(테스트 출력).

## 6. 사례·실습 방향

이 과정은 AI와 협업하는 개발을 배우는 과정이다. 도메인 때문에 복잡도를 높이지 않는다. 강의와 실습 모두 **빈 저장소에서 시작하는 신규 개발**이다. 강의는 요청 한 줄로 시작한 첫 시도가 업무 리뷰에서 무너지는 데서 출발해, 업무 규칙·명세·**모델 패키지**(요구·용어집·도메인 모델·상태 기계)·맥락 파일·하네스를 세운다. 실습은 모델 패키지를 받아 시작한다. 유지보수(이미 있는 코드의 수정)를 전제로 하지 않는다.

- **강의** — OOAD와 같은 **주문 시스템**을 빈 저장소에서 개발한다. 첫 기능 **주문한다**(흐름 3~5) 한 과제로 S01~S11을 관통하고, 강의가 실습의 답을 미리 보이지 않는다. 시나리오는 아래 「강의 시나리오」다.
- **실습** — **정기배송 시스템**을 빈 저장소에서 개발한다. 첫 기능 **정기배송을 신청한다**(실습 1~9)에서 명세·맥락·위임 계약·가드레일·하네스를 세우고, 두 번째 기능 **배송지를 변경한다**(실습 10~12)를 같은 맥락·하네스로 진행한다. 정기배송의 이름과 규칙은 OOAD 실습 답(요구사항 정의서·용어집)과 같게 맞추고, 두 기능에 필요한 것만 쓴다.

실습은 수강생이 **LLM과 코딩 에이전트로 초안을 만들고 사람이 점검 항목으로 판단·보완**하는 방식으로 진행한다. 각 실습의 답 `(안)`이 다음 실습의 입력이다. 실제 수업에서는 수강생이 만든 결과물을 이어 쓴다. 새 사례를 더하거나 교육용 가정의 사슬을 만들지 않으며, 실습의 답이 발견해 더한 것은 진화로 이어 간다.

세션의 예시 코드(강의 저장소의 그 시점 상태)는 `sessions/code/sNN/`에 두고 컴파일·실행으로 확인한다. 실습 저장소의 출발점(모델 패키지만 있는 빈 저장소)도 같은 곳에 둔다.

### 강의 시나리오 — 주문 시스템을 AI와 함께 새로 만든다

수치(시간·개수·횟수)는 교육용 가정이다.

- **배경** — 생활용품 온라인 쇼핑몰이 외부 솔루션으로 받던 주문을 직접 만든 주문 시스템으로 옮긴다. 업무 담당자 1명이 주문 정책을 정하고, 테크 리드 1명과 개발자 2명이 코딩 에이전트를 쓴다. 출발점은 빈 git 저장소(자바)이며 상품·결제·배송 시스템은 이미 운영 중이다.
- **요청** — 업무 담당자의 요청은 한 줄이다: "장바구니에 담은 상품을 결제하면 주문이 되고 배송이 시작되게 해 주세요."
- **첫 기능** — 고객이 펜 2개(개당 1,000원)를 담고, 배송지(서울)를 정하면 주문이 결제대기로 생기며 주문 금액 2,000원이 정해진다. 카드로 결제해 승인되면 결제완료가 되고 배송을 요청한다. 고객은 주문 결과를 확인한다.
- **업무 규칙** — 주문 금액, 배송 요청, 결제 거절(공통 전제). 처음 요청에는 없었고 업무 담당자가 정한다. 업무 규칙은 업무 담당자가 아는 도메인 지식이며, 회사의 정책·운영 방식·고객과의 약속이 정하므로 회사마다 다르다.

| 세션 | 장면 | 드러난 것과 결정 |
|---|---|---|
| 01 | 테크 리드가 요청 한 줄을 에이전트에게 준다. 10분 만에 자바 파일 15개·테스트 3개, 테스트는 모두 통과하고 카드 승인 데모도 성공한다 | 업무 담당자 리뷰에서 문제 3가지 — 가격이 바뀐 날 주문 금액이 바뀜, 거절된 주문에 배송 요청이 나감, 거절된 주문이 취소되어 다시 결제할 수 없음. 에이전트의 테스트는 업무 규칙이 아니라 자기 코드를 확인했다 |
| 02 | 첫 릴리스의 일 6가지를 작업 특성으로 나눈다 | 저장소 골격은 수작업(템플릿), 주문 금액·상태 구현은 에이전트, 연동 코드는 워크플로, 주문 데이터 이관은 수작업, 릴리스 노트는 대화형 보조. 업무 규칙과 되돌리기 어려운 일은 사람이 한다 |
| 03 | 업무 담당자와 30분 동안 업무 규칙을 정하고, LLM에게 요청과 회의 메모로 작업 명세서 초안을 쓰게 한다 | 초안은 회의 메모에 없는 업무 규칙을 만들지 않고 모르는 것 8가지를 미정 질문으로 남겼다(실제 시연). 사람은 질문에 답하고(주문은 배송지를 정할 때 생긴다 등), 이번 범위가 아닌 것은 제외로 옮기며, 결제 승인 뒤 배송 요청 실패만 미정으로 남긴다 |
| 04 | 업무 규칙을 받아들일 기준을 만든다 | 허용·거절 예시 4가지(승인, 가격 변경, 거절, 거절 뒤 재결제)이 수용 테스트다. 작업 단위 4가지(금액 확정, 승인, 거절, 배송 요청)은 각각 테스트로 끝난다 |
| 05 | 에이전트에게 알려 줄 것을 정한다 | 지도 역할의 맥락 파일(약 30줄)과 `docs/`의 용어집·도메인 모델·상태 기계. 결제 연동 매뉴얼 200쪽을 통째로 주자 옛 API를 썼다. "가격"을 판매가와 단가로 나눠 용어집에 두자 금액을 추측하지 않는다 |
| 06 | 어디까지 맡길지 정한다 | 위임 계약 — `order`와 테스트에 쓰기, 빌드·테스트 실행, 브랜치 커밋은 허용. 실제 결제 호출·비밀 키 읽기·push는 금지. 기대값·의존 규칙을 바꿔야 하거나 같은 실패가 3회면 멈춘다 |
| 07 | 흐름과 확인 지점을 정한다 | 계획 → 사람 확인 → 구현·테스트 → 센서 → 결제 관련 변경은 사람 리뷰 → 병합. 모든 단계의 승인은 형식이 된다 |
| 08 | 에이전트가 실제 결제 샌드박스 주소를 설정에 넣고, 실패하는 테스트를 건너뛰려 한다 | 부탁이 아니라 강제 — 설정 파일 쓰기와 외부 네트워크 차단, 테스트 비활성화는 실패로 처리 |
| 09 | 결과를 받아들일 기준을 세운다 | 하네스 — 가이드(맥락 파일, 명세), 센서(컴파일, 수용 테스트, 의존 규칙, 금액 계산의 LLM 리뷰). 주문 서비스가 결제 연동을 직접 부르자 의존 규칙 센서가 실패하고, 오류 메시지를 보고 에이전트가 스스로 고친다 |
| 10 | "거절 뒤 재결제" 테스트가 계속 실패하고 에이전트가 같은 수정을 되풀이한다 | 상한 3회에서 멈춘다. 상태 기계에 결제대기의 자기 전이가 없었다 — 명세 결함이므로 재시도가 아니라 상태 기계와 명세를 고친다 |
| 11 | 더 싼 새 모델로 바꾸려 한다 | 평가 세트(주문 과제 변형 10개 × 3회)로 통과율·비용·시간을 본다. 새 모델은 가격 변경 과제에서 실패가 늘었다. 실제 고객 주소는 LLM에 보내지 않는다. "두 배 빨라졌다"는 체감을 리뷰·재작업 시간으로 다시 잰다 |
| 12 | 첫 릴리스 뒤 다음 기능(결제완료 주문의 취소)을 앞둔다 | 빈 저장소가 어디까지 왔는지(맥락 파일·문서·테스트·센서) 되짚고, 다음 기능을 위임 패키지로 맡긴다 |

### 공통 용어와 전제

이름과 값은 OOAD의 「재사용 사례의 공통 용어와 전제」와 같게 맞춘다(연계 조정). 이 과정에서 새로 정한 이름은 OOAD에도 같은 이름으로 반영한다.

| 용어·사례 | 이 과정에서의 의미와 범위 |
|---|---|
| 강의 시스템 — 주문 | 주문 시스템. 고객이 상품을 골라 배송지를 정하고 결제하면 주문이 성립한다. 강의는 빈 저장소에서 첫 기능 주문한다를 개발한다 |
| 외부 시스템(주문) | 상품 시스템 — 상품 정보와 현재 판매가를 조회한다. 결제 시스템 — 결제 승인을 요청하고 승인·거절을 받는다. 배송 시스템 — 배송을 요청하고, 배송 시작·완료를 통보받는다. 동기·비동기는 설계에서 정할 일이라 이 과정에서 구분하지 않는다 |
| 흐름 | 기본 흐름 1 상품을 조회한다 · 2 장바구니에 담는다 · 3 배송지를 지정한다 · 4 결제한다 · 5 주문 결과를 확인한다 |
| 주문 상태 | 결제대기 → 결제완료 → 배송중 → 배송완료, 결제완료 → 취소됨. 결제가 거절되면 결제대기에 머문다(자기 전이). 코드 값은 `PENDING_PAYMENT`·`PAID`·`IN_DELIVERY`·`DELIVERED`·`CANCELLED`. OOAD의 취소처리중은 이 과정에서 쓰지 않는다 |
| 판매가 / 단가 | 상품의 판매가(현재 값), 주문 항목의 단가(주문 시점에 확정한 값) |
| 주문 예 | 펜 2개, 판매가 1,000원, 주문 금액 2,000원, 배송지 서울. 강의의 모든 세션이 이 값을 쓴다. 원고 본문에 "O-1" 같은 사례 번호를 붙이지 않는다 |
| 강의 과제 — 주문한다 | 흐름 3~5. 배송지를 정하면 주문이 결제대기로 생기고 그때의 판매가로 주문 금액이 정해진다 → 결제한다(`pay`): 결제 시스템에 승인을 요청한다 → 승인되면 결제완료와 배송 요청, 거절되면 결제대기에 남고 다른 카드로 다시 결제할 수 있다 |
| 업무 규칙(강의) | **주문 금액** — 주문이 생길 때의 판매가로 정한다(결제 직전에 펜 값이 1,200원이 되어도 2,000원). **배송 요청** — 결제가 승인된 뒤에만 한다. **결제 거절** — 주문은 결제대기로 남고, 다른 카드로 다시 결제할 수 있다. 업무 담당자가 정한다 |
| 실습 시스템 — 정기배송 | 생필품을 고객이 정한 주기로 배송하는 정기배송 시스템. 실습은 빈 저장소에서 두 기능을 개발한다. 외부 시스템 — 상품(상품 정보·가격), 결제(결제 승인), 배송(배송 요청, 배송 시작·완료 통보, 배송지 변경 알림) |
| 실습 기능 1 — 정기배송을 신청한다 | 고객이 상품·수량·배송 주기·첫 배송일·기간·배송지를 정해 신청하고 결제한다(`subscribe`). 회차 금액은 신청 때의 가격 × 수량으로 정해 기간 끝까지 쓴다. 결제가 승인되면 정기배송은 확정되고 배송 회차들이 예정으로 생기며, 거절되면 결제 대기를 유지한다. 청구는 일시불만 다룬다(월별 청구·청구 실패·신청 실패·취소·반품·해지는 이 과정에서 개발하지 않는다) |
| 실습 기능 2 — 배송지를 변경한다 | 확정된 정기배송은 **언제든** 배송지를 바꿀 수 있다(`changeShippingAddress`). 적용은 회차 상태로 가른다 — 예정 회차는 배송 요청 때 바뀐 배송지를 쓰고, 배송 요청됨(배송 준비 중) 회차는 배송 시스템에 바뀐 배송지를 알려(`requestAddressChange`) 이번 회차부터 적용하며, 배송중·배송됨 회차는 그대로 두고 다음 회차부터 적용한다. 해지됨·만료됨이면 바꿀 회차가 없다 |
| 정기배송 상태 | 결제 대기 → 확정 → 해지됨·만료됨. 코드 값은 `PENDING_PAYMENT`·`CONFIRMED`·`TERMINATED`·`EXPIRED`. OOAD의 신청 실패는 쓰지 않는다 |
| 정기배송 예(실습 답) | 휴지 1묶음 10,000원, 첫 배송일 11월 3일, 2주 주기, 기간 3개월 → 만료일 2월 2일, 예정 회차 7개(11/3·11/17·12/1·12/15·12/29·1/12·1/26), 회차 금액 10,000원, 일시불 70,000원. "03. 요구의 구체화와 명세"의 실습 답에서 정한 교육용 값 |
| 회차 상태 | 예정 → 배송 요청됨(배송 24시간 전에 배송 시스템에 요청) → 배송중(배송 시작 통보) → 배송됨(배송 완료 통보). 코드 값은 `SCHEDULED`·`DELIVERY_REQUESTED`·`IN_DELIVERY`·`DELIVERED`. 배송중은 배송지 변경의 적용을 가르려고 이 과정에서 더한 값이다. OOAD의 청구됨·환불 대기·취소됨은 쓰지 않는다 |
| 모델 패키지 | 개발의 출발점으로 LLM에 주는 모델. 강의(주문) — 흐름·용어집·도메인 모델·주문 상태 기계. 첫 시도에는 없고 "05. 도메인·설계 지식과 맥락 구성"에서 만든다. 실습(정기배송) — 요구사항 정의서(두 기능)·용어집·유스케이스·도메인 모델·정기배송 상태 기계·회차 상태 기계. 원천은 이 표이며, 저장소의 `docs/`에 둔다 |
| OOAD와의 차이(연계 조정) | ① 주문의 배송지 변경은 이 과정의 강의에서 다루지 않는다. ② 정기배송의 배송지 변경은 OOAD 상태 기계의 조건 [다음 배송 24시간 전]과 달리 언제든 가능하고, 회차 상태로 적용을 가른다. ③ 회차 상태 배송중(`IN_DELIVERY`), 정기배송 상태 값 `TERMINATED`·`EXPIRED`, `subscribe`는 이 과정에서 정한 이름이며 OOAD에도 같은 이름으로 반영한다(2026-10-06) |
| 의존 규칙 | 업무 패키지(`order`·`payment`·`delivery`·`product`, 실습은 `subscription` 등)는 연동 패키지(`paymentadapter` 등)와 `persistence`를 import하지 않는다. 패키지 의존에 순환이 없다 |
| 이 과정의 산출물 | 활용 방식 판단, 작업 명세서, 수용 기준, 맥락 패키지(맥락 파일 포함), 위임 계약, 실행 흐름, 가드레일 배치, 하네스 배치, 작업 상태 기계, 평가 세트. 모두 합친 것을 **위임 패키지**라 부른다 |
| 2026-10 기준 | 도구·모델의 능력에 관한 서술은 이 날짜 기준이다. 과정을 열 때마다 원문을 다시 확인한다 |

위 표가 이 과정의 **공통 식별자의 원천**이다. 세션 원고·다이어그램·예시 코드는 이 이름과 값을 그대로 쓴다. 뒤 세션이 새로 발견한 것은 **진화**로서 그 세션이 발견과 되돌림을 보이고 이 표에 반영한다. 같은 대상을 다른 이름·규칙으로 쓴 것은 **오류**이며 이 표에 맞춰 고친다(`sw-engineering-principles.md`의 「교재에 적용하기」).

### 영한 용어집과 명명 규칙

본문은 한글 용어를, 도식의 설계 요소와 코드는 아래 영문명을 쓴다. 한 용어에 영문명은 하나이며, 표에 없는 업무 용어는 코드에서 먼저 만들지 않고 여기에 먼저 더한다. 명명 규칙은 OOAD와 같다.

- **타입**(클래스·인터페이스·enum·record) — 영문 명사, PascalCase(`OrderItem`)
- **필드** — 영문 명사, camelCase(`unitPrice`)
- **메서드** — 업무 동사, camelCase(`pay()`). 외부·다른 객체가 알리는 사건은 `on`으로 시작한다(`onPaid()`)
- **enum 값** — UPPER_SNAKE(`PENDING_PAYMENT`)
- **패키지** — 소문자 단수, 붙여 쓴다(`order`, `paymentadapter`)

|---|---|---|
