# AI-native SW Engineering — Course Design

- **과정명:** AI-native SW Engineering (`ai-native`)

이 문서는 과정의 **정체성·교육 목적·목표·대상·범위·공통 판단 원칙·교육 접근법과 시간 제약**을 소유한다. 세션 구성·시간 배분·세션별 목표·Anchor Message·실습 편성과 연결은 [Curriculum](curriculum.md), 세션의 교수 전개와 실습 계약은 Session DD가 소유한다(`guides/governance.md`). **세션별 상세 시간은 이 문서가 정의하지 않는다.**

이 설계는 2026-11-26에 **원점 재검토**로 다시 세운 것이다. 이전 설계는 Git 커밋 `764ac26`에 있으며 비교 자료다. 이전 설계의 목표·성과(O01~O12)·목차·세션 구성·시나리오는 이 설계의 전제나 제약으로 쓰지 않았다. 진행 상태는 [STATUS](checks/STATUS.md)가 가리킨다.

## 1. 과정의 정체성

> **AI-native SW Engineering은 SW 공학의 보편적 원칙을 기반으로 인간과 AI의 능력 및 제약을 고려하여 소프트웨어 개발·딜리버리·운영·진화의 수행 방식을 재구성하는 공학적 접근이다.**

판단·협업·실행·위임·검증·통제·경제성은 이 과정에서 검토할 요소이며, 어느 하나를 과정 전체의 본질로 선언하지 않는다. Prompt Engineering·SDD·온톨로지·Context Engineering·Agentic AI·Guardrails·Harness Engineering·Evals·FinOps는 공학 활동을 수행하기 위한 **수단과 기법**이며 과정의 중심이 아니다.

이 과정은 AI 도구 활용 교육, 위임·검증 중심 교육, 조직 전환 교육으로 한정하지 않는다.

## 2. 교육 목적

> SW 공학의 목적과 본질적 원칙은 AI가 등장해도 유지되지만, 그 원칙을 수행하는 방식은 달라진다. 이 과정은 그 변화를 보편적 SW 공학 원칙 위에서 설명하고, 인간과 AI의 능력과 제약을 고려해 소프트웨어 개발·딜리버리·운영·진화의 수행 방식을 다시 구성하는 관점과 판단 기준을 갖추게 하며, **AI를 활용해 공학 활동을 수행하는 방법을 배우고 하나의 사례에서 직접 경험하게 한다.** 수강생은 자신의 직무와 역량에 적합한 적용 방안을 도출할 수 있게 된다.

**핵심 교육 메시지** — SW 공학의 목적과 본질적 원칙은 유지된다. 그러나 AI의 등장으로 SW 공학을 수행하는 방식은 달라진다.

## 3. 교육 목표

목표마다 **이해 / 경험 / 수행** 중 어느 수준까지인지 밝힌다. 목표는 전원 공통이고, 수준이 14시간의 현실을 반영한다. 목표의 수는 이후 설계의 제약이 아니다.

| | 목표 | 수준 |
|---|---|---|
| **1** | **유지되는 원칙을 안다** — SW 공학의 목적과 본질적 난점(복잡성·불확실성·변경·협업), 품질·비용·위험·시간의 교환이 AI 환경에서도 그대로임을 설명한다 | 이해 |
| **2** | **활동별로 달라지는 수행 방식을 안다** — 각 공학 활동에서 수행 방식·산출물의 역할·작업의 분해와 할당이 어떻게 달라지는지 짚는다 | 이해 |
| **3** | **인간과 AI의 능력과 제약을 식별한다** — AI가 잘하는 일, 어려워하는 일, 그 결과가 어떤 모습으로 나타나는지를 사례에서 가려낸다 | 이해 + 경험 |
| **4** | **인간과 AI가 함께 공학 활동을 수행한다** — 하나의 사례에서 탐색·분석·모델링·설계·구현·검증 등의 활동을 AI와 함께 수행하며, 공동 작업·분업·검토·위임 가운데 상황에 맞는 협업 방식을 골라 적용한다 | 수행 |
| **5** | **결과를 받아들이거나 되돌릴 근거를 세운다** — 결과를 무엇으로 신뢰할지 정하고, 문제가 생겼을 때 적합한 수정과 재시도를 고르는 길을 설명하고 일부를 실행한다 | 이해 + 경험 |
| **6** | **교환으로 판단한다** — AI를 어떤 활동에 어떤 형태로 활용할지를 품질·비용·위험·시간의 교환으로 판단한다 | 이해 |
| **7** | **자기 직무의 적용 방안을 도출한다** — 자신의 직무와 역량에 적합한 AI-native SW Engineering 적용 방안을 도출한다 | 수행 |

## 4. 교육 대상과 선수지식

AI-native SW Engineering에 관심이 있는 **SW 산업 종사자**를 대상으로 한다. 신입 사원부터 숙련 실무자와 전문가, 개발자와 비개발자, 요구사항·분석·설계·아키텍처·구현·테스트·품질·운영 담당자, 프로젝트 관리자와 기술 리더·관리자를 포함한다. SW 공학 지식과 경험이 부족한 사람부터 전문 역량을 갖춘 사람까지, LLM을 처음 쓰는 사람부터 Agentic AI 활용 경험이 있는 사람까지 포함한다.

특정 직무·직급·경력·공학적 성숙도·의사결정 권한으로 대상을 제한하지 않는다. **수강생의 다양성은 제거하거나 제한할 문제가 아니라 설계에서 고려할 주어진 조건이다.**

**필수 선수조건은 두지 않는다.** SW 공학 전문 지식, 코드 작성·독해 능력, Git·CI/CD 경험, LLM 활용 경험을 요구하지 않는다.

**있으면 교육 효과를 높이는 것** — SW 개발 활동에 대한 기본적인 이해, 요구공학·모델링·아키텍처·설계·구현·검증에 대한 지식, 프로그래밍 및 개발 환경 사용 경험, 프로젝트 수행 및 협업 경험, LLM과 Agentic AI 활용 경험.

선수지식이 부족한 수강생도 핵심 공학 원리와 사례를 이해하고 AI 활용을 경험할 수 있어야 한다. 전문가는 자신의 기존 지식과 경험을 기반으로 더 깊은 판단과 적용 기회를 얻을 수 있어야 한다. 선수지식의 차이를 이유로 과정을 분리하거나 참여를 제한하지 않으며, 필요한 경우 사례·기준 산출물·실습 안내·실행 환경 등의 교육적 지원으로 보완한다.

AI는 기존 역량의 **증폭기**라는 관점은 유지하되 **수강 자격이나 대상 제한의 근거로 쓰지 않는다.**

## 5. 과정의 맥락

**[가정]** 아래 성숙도와 운영 조건은 가정이며 사전 안내와 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 |
|---|---|
| **도메인** | 사례의 업무는 과정이 제공한다. 수강생의 도메인 지식에 의존하지 않는다 |
| **기술** | 코드 독해 수준이 신입부터 전문가까지 넓다. 코드 작성 능력을 전제하지 않는다 |
| **팀워크** | 팀의 작업 분해·리뷰 기준을 정해 본 경험이 있는 수강생과 없는 수강생이 섞인다 |

- **다루는 불확실성** — **기술 불확실성**이 중심이다. AI의 생성 결과는 상황에 따라 달라지고 도구·모델의 능력이 빠르게 바뀐다. 업무 불확실성은 과정이 제공하는 사례와 규칙으로 낮춘다.
- **깊이의 결정** — 범위는 공학 활동의 흐름 전체를 유지하고, 깊이는 **각 활동의 원리와 협업·분업의 판단까지**로 둔다. 기법의 체계적 숙련은 목표가 아니다. 다만 공학 원리와 AI 활용을 이해하는 데 필요한 **기법·표기법·사례는 포함한다.**
- **수준 차이의 처리** — 공통 교육 목적과 목표를 유지하되, **수강생의 기존 역량에 따라 학습의 깊이와 적용 수준이 달라질 수 있음을 인정한다.** 별도의 수준별 목표나 교육 트랙을 만들지 않는다.
- **운영 조건** — **[가정]** 20명 안팎, 개인 실습과 결과 비교. 기본 실습 환경은 Claude Team이고 필요한 실습에서 Claude Code CLI를 쓴다. 별도의 API 호출과 API Key 사용은 제외한다. 실습 환경은 첫 세션에서 설정한다.

## 6. 범위와 경계

### 주축 — 핵심 SW 공학 활동

다음 활동을 과정의 주축으로 삼고 **순수 교육시간의 2/3 이상**을 배정한다. 활동별·세션별 배정은 [Curriculum](curriculum.md)이 정한다.

- 요구사항
- 도메인 분석 및 모델링 — 정적 관점
- 도메인 분석 및 모델링 — 동적 관점
- 아키텍처
- 설계
- 설계를 기반으로 한 AI 코드 생성
- 자동 테스트와 CI를 통한 구현 결과 확인

아키텍처와 설계는 **각각의 목적·결정 수준·본질적 원리·산출물과 인간·AI의 역할을 구분해** 다룬다. 각 활동에서 보편적 SW 공학 원칙을 교육하고, AI의 등장으로 수행 방식과 산출물의 역할이 어떻게 달라지며 인간과 AI가 어떻게 협업하고 분업하는지를 설명한다. **기존 SW 공학 강의에 AI 실습만 추가하는 형태로 구성하지 않는다.** 공학 활동마다 동일한 설명 구조를 기계적으로 반복하지 않는다.

**SW 설계의 책임 분해와 AI에 위임할 작업의 분해를 동일시하지 않는다.** 설계의 책임 분해는 소프트웨어 구조의 결정이고, 위임 단위의 분해는 수행 방식의 결정이다. 둘은 관련되지만 같지 않다.

### AI 관련 개념의 위치와 내용

각 개념은 **그 문제가 실제로 생기는 활동에서 처음 설명하고**, 이후 활동에서 필요한 범위로 적용한다. **최초 설명 위치와 적용 범위를 구분한다** — 최초 설명 위치에서만 쓰이는 것이 아니다. 각 개념은 무엇을 해결하려는 것인지, 언제 필요하고 어떻게 적용하며 언제 불필요한지를 중심으로 다룬다.

| 개념 | 내용 | 최초 설명 위치 |
|---|---|---|
| **Prompt Engineering** | 목적·입력·제약·기대 결과와 피드백을 포함하는 AI 상호작용의 구성 | 도입 |
| **SDD** | 명세를 중심으로 설계·구현·검증을 연결하는 접근 | 요구사항 |
| **온톨로지** | 개념·관계·의미의 명시적 표현. 도메인 모델과의 관계 및 차이 | 도메인 모델(정적 관점) |
| **Context Engineering** | 업무 지식·요구사항·모델·설계·코드·실행 환경 등 필요한 맥락의 구성 및 관리 | 설계에서 코드로 |
| **Agentic AI** | 작업 분해, 위임, 도구 활용, 자율성 및 실행 조정 | **도입**에서 대화형 LLM과의 기본적인 차이를 소개하고, **설계에서 코드로·자동 테스트와 CI**에서 실제 공학 활동으로 활용하며, **AI 활용 및 통제 기법**에서 구성과 적용 방법을 종합·확장한다 |
| **Guardrails** | AI의 행동·권한·입력·출력·실행 범위 등에 대한 제약 | 자동 테스트와 CI |
| **Harness Engineering** | 에이전트의 맥락·도구·실행·검증·피드백을 지원하는 실행 체계 | 자동 테스트와 CI |
| **Evals** | AI의 응답·행동·수행 결과를 목적과 기준에 따라 평가하는 접근 | AI 활용 및 통제 기법 |
| **FinOps** | 비용·사용량·품질·비즈니스 가치의 종합적 관리 및 최적화 | AI 활용 및 통제 기법 |

후반부의 「AI 활용 및 통제 기법」은 앞서 경험한 개념을 **종합하고 추가적인 AI 관련 주제를 교육하는** 세션이다.

### 변경·딜리버리·운영

- **변경**은 과정 후반부에서 **통합 실습**으로 다룬다. 변경 영향 분석, 필요한 산출물의 수정, 기존 결정과 업무 규칙의 보존, 회귀 검증을 다루며, 앞서 학습한 공학 원리와 산출물이 변경에서 어떻게 활용되는지를 경험하는 것이 목적이다. 변경 관리나 유지보수 방법의 전문 교육은 하지 않는다.
- **딜리버리·운영과 장기적인 진화**는 변화의 방향과 사례 중심으로 간결하게 다룬다.
- **로컬 테스트 실행과 실제 CI 파이프라인 실행을 구분한다.**

### 제외 범위

| 제외 | 근거 |
|---|---|
| SW 공학 개론 — 요구공학·모델링·설계 기법의 체계적 교육 | 14시간에 불가하고 정체성이 아니다. 원리와 필요한 기법·표기법은 다루되 기법 체계의 숙련은 목표로 삼지 않는다 |
| 특정 도구·제품의 기능 숙련 | 환경 안내와 도구 사용 시연은 실습을 수행하기 위한 수단으로 두고, 숙련 자체를 목적으로 삼지 않는다 |
| 프롬프트 작성 요령 모음 | Prompt Engineering은 AI 상호작용의 구성으로 다루며 요령 목록으로 다루지 않는다 |
| 모델의 내부 원리·학습·미세조정 | 수강생이 내릴 결정이 아니다. AI의 능력과 제약을 설명할 만큼만 다룬다 |
| 조직의 AI 전환 거버넌스·투자 모델 | 전환 교육으로 한정하지 않는다 |
| 벤더 가격표·조직 비용 관리 체계 | FinOps는 무엇을 재고 어떻게 판단하는가까지 다룬다 |
| 품질 보증 체계·테스트 설계 전문 | 별도 전문 영역이다 |

**경계를 가르는 기준** — 도구와 제품의 구체적 기능보다 **공학 활동의 원리와 그것을 수행하는 판단**에 무게를 둔다. 도구에 관한 설명은 실습을 수행하고 변화를 이해하는 데 필요한 범위로 한다.

### 다른 과정과의 연계

**[미정]** 다른 과정(`ooad` 등)과의 사례 공유와 경계는 그 과정의 재설계와 함께 정한다. 현재 이 설계는 다른 과정의 결정에 의존하지 않는다.

## 7. 과정 공통 판단 원칙

**보편적 공학 원칙**과 **상황에 따라 달라지는 경험적 판단**을 구분한다. 전자는 과정이 가르치는 원칙이고, 후자는 수강생이 자기 맥락에서 판단할 사항이다.

### 보편적 공학 원칙

- SW 공학의 목적은 **제약 안에서 문제를 해결해 가치를 지속적으로 전달하는 것**이다. 본질적 난점은 **복잡성·불확실성·변경·협업**이고, 판단은 **품질·비용·위험·시간**의 교환 공간에서 이루어진다. AI는 이 목적과 난점을 바꾸지 않는다.
- 요구·분석·설계·구현은 **서로 다른 결정**을 내린다. 어느 결정이 틀렸는지 가릴 수 있어야 고칠 수 있다.
- **명시된 지식과 공학적 결정이 협업·변경·검증의 기반이다.** 산출물은 의사결정, 협업, 지식 보존, 변경, 검증, 추적성, 그리고 인간과 AI의 공유 맥락 등 **공학적 목적에 따라 선택한다.**
- **검사 통과는 검사한 조건에 관한 증거이며 전체 품질을 보장하지 않는다.**
- **공학적 판단과 책임은 사람에게 남는다.** AI의 활용 범위가 넓어져도 결과를 수용할 책임의 소재는 옮겨지지 않는다.
- 보편 원칙은 `guides/sw-engineering-principles.md`를 따른다.

### AI 활용에서 달라지는 것과 그 판단

- **AI는 새로운 수행 수단이다.** 공학 판단은 사라지지 않고 대상이 늘었다 — "어떻게 만들 것인가"에 **"어떤 방식으로 수행할 것인가, 그 결과를 무엇으로 신뢰할 것인가"**가 더해졌다.
- **모든 공학 활동에서 인간과 AI가 협업하고 분업한다.** 고려할 요소는 능력, 지식, 맥락, 권한, 책임, 검증 가능성, 위험, 복구 가능성, 비용이다. 활동과 상황에 따라 어떤 요소가 결정적인지 달라진다. **AI는 실행만 하고 인간은 결정과 검증만 한다는 식으로 역할을 고정하지 않는다.** 협업의 형태는 공동 작업·분업·검토·위임 등 여러 가지이며 상황에 맞게 고른다.
- **비용의 구조가 재편된다.** 어떤 일은 싸지고 어떤 일은 비싸지며, 무엇이 어떻게 달라지는지는 작업의 성격·관례의 존재·검토의 깊이에 따라 다르다. **일반화된 결론을 과정이 제시하지 않고 판단의 틀과 재는 항목을 제시한다.**
- **AI를 활용하지 않는 선택도 공학적 판단이다.** 판단의 근거는 위 요소들이며, 어떤 작업에 쓰지 말라는 규칙을 과정이 정하지 않는다.
- **같은 입력에 대한 결과가 달라질 수 있다.** 그래서 **재실행 가능성과 재현 가능성을 구분한다.**
- **실패의 원인은 결정·입력·구현·도구·실행 환경 등 다양하다.** 원인에 따라 적합한 수정과 재시도를 선택한다.
- **산출물의 독자가 사람에 더해 AI로 넓어졌다.** 무엇을 어떤 형태로 남길지는 위의 공학적 목적과 맥락 비용을 함께 보고 정한다.

## 8. 교육 접근법

### 교육 덩어리의 구성

각 세션은 **그 활동을 받치는 본질적 원리**와 **AI로 달라지는 수행 방식·산출물의 역할·인간과 AI의 협업과 분업**을 강의하고, 같은 사례에서 실습으로 수행한다. 강의·토의·시연·실습의 배치는 활동의 성격에 따라 정하며 **하나의 순서를 모든 세션에 강제하지 않는다.** 공통 판단 요소를 활동마다 동일한 위치에서 기계적으로 반복하도록 강제하지 않는다.

**대표 실습 답변은 수강생이 먼저 실습을 수행한 뒤 보여준다.** 다만 **실습을 수행하기 위해 필요한 도구 사용 시연이나 안내는 가능하다.**

### 실습의 기본 구성

모든 수강생에게 **동일한 실습 문제**를 제공한다. 역량에 따라 별도의 실습 문제나 트랙을 구성하지 않는다. 각 실습은 다섯 요소로 구성한다.

1. **투입물**
2. **첫 프롬프트** — 제공
3. **중간 프롬프트** — 수강생이 LLM 응답을 검토하고 피드백하는 과정의 반복
4. **최종 프롬프트** — 제공
5. **점검항목**

- 초보자는 제공된 프롬프트를 그대로 실행하고 점검항목으로 결과를 확인할 수 있어야 한다.
- 숙련자와 전문가는 자신의 지식·경험·공학적 판단을 추가하고 LLM과 자유롭게 논의하며 결과를 발전시킬 수 있어야 한다.
- 첫·최종 프롬프트는 공통으로 제공하되 **중간 과정에서 수강생의 사고와 AI 협업을 제한하지 않는다.**
- 필요한 경우 초보자의 피드백을 돕는 질문이나 안내를 제공한다.
- **점검항목은 최종 결과의 확인뿐 아니라 중간 응답의 검토와 피드백에도 쓸 수 있도록 한다.** 점검항목은 학습 도구이며 수강생 평가나 합격 판정에 쓰지 않는다.
- 실습 문제·투입물·프롬프트·점검항목의 구체적 설계는 Session DD가 소유한다.

### 실습 환경

- 기본 환경은 **Claude Team**이고, 필요한 실습에서 **Claude Code CLI**를 쓴다. 별도의 API 호출과 API Key 사용은 제외한다. 대화형 LLM에 한정하지 않고 **Agentic AI를 활용한 공학 활동도 실제로 경험**하도록 한다.
- **첫 세션에서 환경을 설정한다.** 설정에 실패하거나 사용이 어려운 수강생은 **대화형 Claude로 실습을 진행한다** — 공식 경로이며 예외 처리가 아니다.
- **[확인 필요]** Claude Team의 좌석 발급 주체와 동시 사용 가능 여부, 동시 사용 시의 사용량 한도, 교육장 PC의 설치 권한과 사내 네트워크, 실습에 투입할 자료의 데이터 정책. 대표 실행과 파일럿 전에 확인한다. **[판단]** 실습 자료는 과정이 제공하는 사례로 한정하고 수강생의 회사 자료를 쓰지 않는다.

### 실습 간 연결과 복구

공학 활동과 산출물의 **논리적 연속성은 유지하되 실습 간 실행 의존성은 제거한다.** 수강생은 다음 둘 중 하나를 자유롭게 고른다.

- 자신의 실습 산출물을 지정된 본인 저장소에 저장하고 다음 실습에 활용한다.
- **제공된 기준 산출물**을 다음 실습의 투입물로 활용한다.

Claude Code로 생성하고 검토한 기준 산출물을 전원에게 제공한다. CLI 실습에서 필요한 경우 **파일·폴더·코드·빌드 상태를 포함한 기준 저장소 상태**도 제공한다. 앞 실습을 완료하지 못했거나 결과가 적합하지 않은 수강생도 제공된 산출물로 이후 실습을 계속할 수 있어야 한다. 대화형과 CLI의 산출물은 가능한 한 후속 실습에 쓸 수 있는 형태로 제공하되, **실제 코드·명령 실행과 대화형 결과 검토의 차이를 혼동하지 않는다.**

**투입물은 실습 목적에 필요한 맥락을 선택해 제공한다.** 모든 선행 문서를 매번 전문으로 제공하는 것이 아니다.

### 실습 답변과 실제 실행 프롬프트

**대표 실행 결과와 별도의 인간 작성 모범 답안을 제작하지 않는다.** Claude Code가 교재용 MD·PPTX를 제작하는 과정에서 실습을 실제로 실행하고, 실행 결과를 검토하고 필요하면 추가 프롬프트로 개선한 뒤, **검토된 실제 실행 결과를 교재의 실습 답변으로 사용한다.**

**실제 실행 프롬프트**란 Claude Code가 교재를 제작하는 과정에서 실습 답변을 얻기 위해 실제 실행한 **모든 회차의 프롬프트**다. 수강생에게 제공하는 첫·최종 프롬프트와 구분한다. 별도의 모범 프롬프트를 작성하거나 사후에 재구성하는 것이 아니다.

보존 원칙 — 실제 사용한 모든 회차를 별도 파일로 저장한다. 첫 프롬프트, 중간 피드백, 추가 질문, 오류 수정 지시, 재실행, 최종 프롬프트를 모두 포함한다. **성공한 회차뿐 아니라 실패하거나 수정이 필요했던 회차도 보존한다.** 실제 실행 순서와 원문을 유지하고, 사후에 요약·정리·재구성하거나 불필요하다고 판단해 생략하지 않는다. 각 프롬프트와 실제 응답·산출물의 대응 관계를 확인할 수 있어야 한다. 보존된 프롬프트는 강사가 교육 중 실행하거나, 실습 답변의 생성 과정과 인간·AI의 협업 방식을 설명하거나, 이후 교재를 보완할 때 활용한다.

교재에는 검토된 실제 실행 결과를 그대로 또는 필요한 부분을 발췌해 제시한다. **실행하지 않은 가상의 응답을 실제 실행 결과로 제시하지 않는다.** 결과가 적합하면 불필요하게 수정하거나 **인위적인 결함을 만들지 않는다.** 실행 과정에서 발견된 교육적으로 의미 있는 오류·누락·반례·개선 사항은 필요한 경우 교재 또는 강사 노트에서 설명한다. **동일 프롬프트의 재실행 가능성과 동일 결과의 재현 가능성을 구분한다.** API를 직접 쓰지 않는 것과 CLI를 통한 실행·기록 수집 자동화는 구분하며, 교재 제작 과정의 CLI 자동화는 금지하지 않는다.

파일명·저장 경로·실행 증거의 관리 형식은 저장소의 단계별 계약과 제작 지침을 따른다. 별도의 관리 체계를 만들지 않는다.

**[판단] 제작 순서** — 실습 답변은 대표 실행 **뒤에** 정리한다. 프롬프트가 의도한 결과를 내는지는 실행 전에 알 수 없으므로 작성 → 실행 → 검토 → 수정 → 재실행의 루프가 선행한다.

### 실습 후반부 운영

수강생이 먼저 실습을 수행한다. 후반부에 강사는 **교재 제작 과정에서 Claude Code가 실제 사용한 프롬프트와 그 실행 결과를 보여주고, 실습 답변 슬라이드를 간단히 설명한다.** 필요한 경우 **보존된 실제 프롬프트를 직접 실행한다.** 매 실습에서 모든 회차를 다시 실행하도록 강제하지 않는다 — 어느 회차를 보이거나 실행할지는 실습의 성격에 따라 정한다.

필요한 범위에서 실습 답변의 의미, 적용된 공학 원리, 주요 공학적 판단, 인간과 AI의 협업·분업 방식, 결과에서 주목할 사항, 오류·누락·위험과 개선 가능성을 코멘트한다. **교육적으로 의미 있는 결함이나 개선 사항이 있을 때 설명하되, 반드시 결함을 찾아야 하는 것은 아니다.**

**후반부에서 상세한 SW 공학 기법을 반복 교육하지 않는다. 본질적인 SW 공학 원칙과 원리는 강의에 포함한다.**

수강생은 자신의 결과와 실제 실행 결과를 비교하며 **공학적 전문성, 맥락의 품질, AI와의 협업 방식이 결과에 미치는 영향**을 이해한다.

실습당 설명 시간·직접 수행 시간·토의 시간은 실습의 특성에 따라 정한다. **일률적인 비율이나 최소 시간 규칙을 강제하지 않는다.** 전체 실습시간과 수강생의 직접 수행 시간을 구분해 산정하고, 직접 수행 시간이 충분히 확보되도록 한다.

## 9. 시간 제약

- **총 교육시간 2일 14시간.** 50분 교육 + 10분 휴식을 적용하므로 **순수 교육시간 700분 = 50분 블록 14개**, 휴식 140분, 편성 경과시간 840분이다.
- 1일 7블록 350분.
- **블록마다 실습은 최대 25분**(교육 시간의 절반)이다.
- 핵심 SW 공학 활동에 **순수 교육시간의 2/3 이상**을 배정한다.
- 전체 실습 비중 **30~40%**.
- 실습은 핵심 활동에 우선 배정한다.
- 첫 세션에 **환경 설정 25분**을 배정한다.
- 세션은 시간 단위에 기계적으로 맞추지 않고 교육 주제와 학습 흐름에 따라 구성한다. **일자 구분은 교육 주제와 시간 편성에 따른 것이며 인간과 AI의 역할을 구분하는 경계가 아니다.**

**세션 수·세션별 배정·실습 편성은 [Curriculum](curriculum.md)이 소유한다.** 이 문서는 그 수치를 중복 정의하지 않는다.

## 10. 교육 성과에 관한 처리

**수강생의 교육 성과를 측정하거나 평가하지 않는다.** 수강생 평가를 위한 별도의 성과 목록, 최소 달성선, 역량 입증 기준, 평가표와 합격 기준을 설계하지 않는다. 점검항목은 학습 도구다. 목표 7의 적용 방안 도출은 교육 목표로 유지하되 별도의 평가나 산출물 제출을 요구하지 않는다.

**과정 자체의 품질 검증과 수강생 성과 측정을 구분한다.** 과정의 품질과 실습의 실행 가능성은 다음 관점에서 확인한다.

- 교육 목적·목표·교육 내용의 정합성
- 공학적 설명과 사례의 타당성
- 실습의 실행 가능성
- 선행·후속 산출물의 정합성
- 교육시간 내 수행 가능성
- Claude Code 실제 실행 결과의 적합성
- 다양한 수강생의 실습 참여 가능성

이 확인은 Course Design 종합 검토와 이후 교재 제작·실제 실행 검증에서 수행한다. 별도의 복잡한 성과 관리나 검증 체계를 만들지 않는다.

**단계 계약과의 관계** — `guides/course-design-guide.md`의 「필수 항목」은 과정 목적·교육 목표·목표 역량·핵심 주장을 필수로 두고, **별도의 학습 성과 정의와 관찰 가능한 실패 조건은 과정의 목적과 교육 방식에 따라 선택**하도록 한다(2026-11-26 보완). 이 과정은 **교육 목표가 기대 학습 성과를 충분히 나타내므로 별도 성과 목록을 중복 작성하지 않으며**, 자격 인증이나 역량 판정이 목적이 아니므로 수강생 개인의 성과 측정·평가도 두지 않는다. 과정 자체의 품질 검증은 위 관점으로 수행한다.
