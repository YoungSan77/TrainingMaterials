# 정적 모델 강의 소스 (OOA · 정적 모델 · 약 2.5시간 · 6차 · 나선형 재구성)

> 정적 모델(개념 모델) 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 6차: 5차 나선형 구조 유지 + quick-scan 피드백 반영(연관 이름 방침, 다대다, 다이어그램 크게, 물음표 전수).
> 구성 원리 = Larman i&i(반복·점진): 각 개념을 여러 주기에 걸쳐 다시 방문하며 심화. 깊이 = Larman 책 수준(축약본).
> 층 경계: OOA. 책임 배치(RDD·GRASP)는 OOD — 안 넣는다. 설명·워크스루=NewPOS, 실습=Order. 한글(영어). 의문형 물음표. 원작자(Larman) 하단.

## 원작자·출전
- 도메인 모델(Domain Model): Craig Larman (Applying UML and Patterns, 3rd ed.)
- UML 표기: OMG UML 표준

## 1주기 — 무엇을 그리나 (개념 먼저)
### 1-1. 정적 모델·개념 모델이란
- OOA는 도메인을 두 그림으로 본다 — 정적 모델(무엇이 존재하는가: 개념·구조), 동적 모델(무엇이 일어나는가: 행위·시간). 이 강의는 정적.
- 산물 = 개념 모델(Domain Model): 문제 영역에 무엇이 존재하고 어떻게 관계 맺는지 그린 그림.
- 개념 모델은 소프트웨어 설계가 아니라 현실의 개념을 그린다. 연산(메서드)이 없다 — 그러나 속성(자료)은 있다. 가시성·타입 세부는 "없다"가 아니라 "아직 정하지 않는다"(설계의 몫).
- 왜 개념부터인가? 구현을 먼저 생각하면 편의가 도메인 이해를 오염시킨다.
### 1-2. 개념 클래스란 무엇인가 (정의 — 표기보다 먼저)
- 개념 클래스(Conceptual Class): 도메인에 실재하는 개념 — 사물·역할·사건·명세. 소프트웨어 객체가 아니라 현실의 명사.
- 유형: 물리적 사물(상품), 역할(고객·계산원), 사건(판매·지불), 명세(상품 명세), 목록/장부(상품 목록).
### 1-3. 개념 모델의 큰 그림 (미리보기)
- [uml] NewPOS 개념 모델 완성본을 크게 보여준다(미리보기) — "이 강의가 끝나면 이걸 스스로 그린다". 나침반.

## 2주기 — 어떻게 표기하나 (표기법 + 개념 재방문)
### 2-1. 클래스 박스 (기본)
- 세 칸 박스: 맨 위=이름, 가운데=속성(이름과 데이터 타입, 예 price: Money, quantity: int), 맨 아래=연산(메서드).
- 분석(OOA)에서는 연산 칸을 정의하지 않는다 — 연산은 설계(OOD)의 몫. 개념 모델 박스는 이름+속성만.
- 속성 데이터 타입: 분석 단계엔 개념적 타입(금액·수량·날짜)까지. 구현 타입은 설계에서.
- [uml] Sale(이름 / dateTime: Date / 연산 비움), SalesLineItem(이름 / quantity: int / 비움) — 세 칸 크게, 각 칸 라벨.
- 훈련: "총액을 계산한다"는 어느 칸? (연산 — 개념 모델엔 아직 없음)
### 2-2. 연관 (Association)
- 두 개념을 선으로 잇고 관계 이름을 붙인다. 선 = "의미 있게 관계 맺는다".
- 종류 예: 포함(Sale가 SalesLineItem을 포함), 참조(SalesLineItem이 ProductDescription을 참조).
- [uml] Sale -- SalesLineItem : 포함 / SalesLineItem -- ProductDescription : 참조 (포함·참조 둘 다 — 말과 그림 일치)
- 연관 이름 표시 방침: 연관은 본래 양방향 관계다. 이름을 한 방향만 붙이면 어정쩡하다. 연관을 설명하는 슬라이드에서만 이름(과 필요시 읽기 방향)을 명시하고, 완성 다이어그램에서는 연관 이름을 생략한다(선과 다중도만). 이것이 도메인 모델 관행이다.
- 훈련: "계산원이 판매를 기록한다"의 연관은? (Register -- Sale : 기록)
### 2-3. 다중도 (Multiplicity) — 표로
- 연관선 양 끝에 개수 규칙: 1=정확히 하나, 0..1=없거나 하나(선택적), 1..*=하나 이상(상한 없음), *(=0..*)=0개 이상(없어도 됨), 2..5=범위.
- 핵심: *(="0개 이상", 없어도 됨) vs 1..*(="하나 이상", 최소 하나). 이 차이가 규칙을 가른다.
- 읽는 법(양 끝 함께): Sale "1" -- "1..*" SalesLineItem → "판매 하나에 항목 하나 이상, 항목 하나는 판매 하나에".
- [uml] Sale "1" -- "1..*" SalesLineItem : 포함
- 다대다(*--*): 양쪽 다 여럿인 관계도 도메인 모델에 흔하다. 예: 상품 명세와 판촉 — 한 판촉이 여러 상품에, 한 상품이 여러 판촉에 걸린다 → ProductDescription "*" -- "*" Promotion : 적용. 다대다는 설계에서 연관 클래스·중간 테이블로 풀리지만, 개념 모델에선 다대다 그대로 표기한다.
- [uml] ProductDescription "*" -- "*" Promotion : 적용
### 2-4. 다중도가 규칙을 드러낸다
- "1..*"는 곧 도메인 규칙 "판매는 최소 한 항목을 가져야 한다". 다중도가 불변식을 미리 드러낸다.
- 훈련: "*"(0개 이상)로 바꾸면 빈 판매를 허용한다. 도메인이 빈 판매를 원하는가? 다중도를 정하는 것이 규칙을 정하는 것.
### 2-5. 속성 (Attribute) — 개념 클래스 재방문
- 속성: 개념이 갖는 단순 값. Sale.dateTime, SalesLineItem.quantity.
- 속성인가, 별도 개념 클래스인가? 단순 값은 속성, 자기 속성·관계를 갖는 독립 개념은 별도 클래스+연관.
- price를 SalesLineItem 속성으로? 아니다 — 가격은 "상품이 무엇인가"에 속하므로 ProductDescription으로.
- 고객 주소는? 단일 문자열이면 속성, 나뉘고 이력 가지면 개념 — 도메인이 정한다.
- 판단 신호: "자기만의 속성·관계를 갖는가?" Yes=개념, No=속성.
### 2-6. 누락하기 쉬운 개념 클래스 — 명세 개념
- 명세 개념은 함정이 아니라 초보가 빠뜨리기 쉬운 전형적 개념 클래스다.
- 물리적 상품과 "그 상품이 무엇인가"(명세: 이름·가격·바코드)는 다르다. 재고 0이어도 명세·가격은 존재 → 상품 명세(ProductDescription)를 별도 개념으로.
- 놓치면 "재고 0이면 가격도 사라지는" 잘못된 모델. 물리적 사물만 보고 명세를 빠뜨리는 게 흔한 누락.
- 훈련: "메뉴판의 김치찌개"와 "나온 김치찌개 한 그릇"은 같은 개념인가? (명세 vs 물리적 인스턴스 — 다른 개념)

## 3주기 — 어떻게 그리나 (작성법 + 실전 심화)
### 3-1. 클래스 다이어그램 작성 절차 (비약 제거)
- 개별 표기를 배웠으니 하나의 다이어그램으로 조립하는 절차:
  1. 개념 클래스 찾기 — 명사구 추출 → 거르기(속성일 뿐인 것·중복·시스템/UI 용어 제거, 애매하면 다음 반복으로)
  2. 박스로 놓기 (이름 + 속성)
  3. 연관 긋기 (관계 이름)
  4. 다중도 정하기 (규칙 결정)
  5. 속성 채우기 (타입 포함)
### 3-2. 워크스루 — NewPOS Process Sale
- 출발 유스케이스: "고객이 상품들을 계산대로 가져온다. 계산원이 각 상품의 항목을 입력한다. 시스템이 항목별 소계와 판매 총액을 계산한다. 고객이 지불한다."
- 단계 1 — 명사구 추출: 고객·상품·계산대·계산원·항목·소계·판매·총액·지불. [원문 밑줄]
- 단계 2 — 거르기: 소계·총액=계산된 값(개념 아님). 상품→물리적 vs 명세→ProductDescription. 남는 개념: Sale·SalesLineItem·ProductDescription·Payment. [uml: 박스만]
- 단계 3 — 연관: Sale--SalesLineItem:포함, SalesLineItem--ProductDescription:참조, Sale--Payment:지불됨. [uml: 연관]
- 단계 4 — 다중도: Sale"1"-"1..*"SalesLineItem, SalesLineItem"*"-"1"ProductDescription, Sale"1"-"1"Payment. [uml: 다중도]
- 단계 5 — 속성: Sale(dateTime), SalesLineItem(quantity), ProductDescription(itemID·price·description), Payment(amount). [uml: 완성본, 크게, 연관 이름 생략]
- 완성본을 1-3 미리보기와 나란히: "한 문단에서 여기까지."

## 4주기 — 왜 중요한가 (개념 모델 → 코드)
### 4-1. 세 단계 진화
- 개념 모델(OOA) → 설계 클래스 모델(OOD): 연산·가시성·타입 붙임 → 코드. 이 강의는 첫 단계까지.
### 4-2. 구조는 코드로 곧장 매핑 (codepair)
- 개념 클래스→클래스, 속성→필드, "1"→참조, "1..*"→컬렉션.
- [codepair] 왼쪽=완성 개념 모델, 오른쪽=코드 골격: class Sale { Date dateTime; List<SalesLineItem> lines; /*연산 없음 — OOD*/ } / class SalesLineItem { int quantity; ProductDescription description; } / class ProductDescription { String itemID; Money price; String description; }
- 구조는 개념 모델에서 왔고 곧 코드다. 연산은 비어 있다 — OOA/OOD 경계가 코드에서도 보인다.
### 4-3. 그래서 개념 모델이 중요하다
- 정확한 개념 모델 → 정확한 코드 골격. 명세 개념 놓치면 코드도 틀림. "이 다이어그램이 코드의 뼈대다."

## 5주기 — 닫기 (복선)
- 정적 모델은 "무엇이 있나". "어떤 순서로 협력하는가?"는 동적 모델(유스케이스·시퀀스·협업·상태). 책임 배치는 OOD 몫.

## 슬라이드 변환 지침
- 순서 엄수(나선형): 1주기(개념 클래스 정의를 표기보다 먼저)→2주기(표기, 개념 재방문)→3주기(작성 절차 먼저, 워크스루)→4주기(코드)→5주기.
- 비약 제거: 3-1 작성 절차를 워크스루 앞에 반드시.
- 클래스 박스 세 칸(이름/속성/연산, 분석선 연산 비움, 속성 타입) 반드시 설명(2-1).
- 말과 그림 일치: 연관 포함·참조 둘 다 다이어그램에(2-2).
- 연관 이름: 설명 슬라이드에서만 표시, 완성 다이어그램에선 생략(선·다중도만) — 2-2 방침.
- 다대다(*--*) 관계 포함(2-3, 도메인 모델 수준).
- 다이어그램은 크게: 슬라이드 공간을 충분히 써서 크게 그린다(작게 그려 확대하면 테두리가 씻긴다). 하단 잘림 없이.
- 의문형 전수 물음표: 제목·본문·boxes 시각 안 문장까지 의문형이면 모두 물음표.
- 반복은 심화로(i&i): 개념 클래스가 1-2, 2-5, 2-6, 3-2에서 매번 깊어진다. 중복 아님.
- RDD·GRASP 금지(OOA). 깊이는 Larman 책 수준. 실습=Order(별도).
