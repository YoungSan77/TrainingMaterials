# 요구사항 → 유스케이스 강의 소스 (부 01 · 세션 2 · 약 65분 · 1차)

> 세션 2 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 층: OOA 진입(요구 표현). 설명=NewPOS(Process Sale), 실습=Order(PlaceOrder). 한글(영어). 의문형 물음표. 원작자 하단.
> 깊이 = 라만 책 수준(축약본), ~18장. 구성 = 선형(문제→정의→상세도→driven→스토리→실습).
> 층 경계: 요구사항 *품질·정의 표준*(ISO 29148 등)은 QM 과정 소유 — 여기선 "입력으로 받는다"만, 표준 나열 안 함. UML 유스케이스 다이어그램 *배경*은 4교시(표기 첫 사용)로 미룬다.

## 원작자·출전
- 유스케이스: Craig Larman (Applying UML and Patterns, 3rd ed., Ch.6) · Ivar Jacobson(창시)
- 유저 스토리: 애자일(Cohn, User Stories Applied) — INVEST
- 편재 언어(Ubiquitous Language): Eric Evans (DDD)

## 1. 기능 목록의 한계 (문제)
### 1-1. 요구를 기능 목록으로 적으면
- 정의: 흔한 방식 — "시스템은 X를 한다"의 목록(명세서 스타일).
- 현상: 개별 기능은 있으나 사용자가 *무엇을 이루려는지·어떤 순서로·무슨 맥락인지*가 사라진다.
- 예시: "항목 입력·소계 계산·결제 처리" 목록 vs "고객이 상품을 사서 나간다"는 목표.
- 훈련: 기능 목록만 보고 "왜 이 시스템이 필요한가"에 답할 수 있나?

## 2. 유스케이스란 (정의)
### 2-1. 목표를 이루는 텍스트 이야기
- 정의: 유스케이스 = 액터가 목표를 이루려 시스템을 사용하는 과정을 적은 텍스트 이야기(Larman).
- 예시: Process Sale — "고객이 상품을 계산대로 가져오고, 계산원이 항목을 입력하고, 시스템이 소계·총액을 계산하고, 고객이 지불한다."
### 2-2. 텍스트가 본체, 다이어그램은 2차
- 값은 텍스트(시나리오)에 있다. UML 유스케이스 다이어그램은 액터-유스케이스 관계의 개요일 뿐 — 다이어그램만 그리고 텍스트를 안 쓰면 알맹이가 없다(Larman 경고).
### 2-3. 블랙박스로 본다
- 시스템 내부를 그리지 않는다 — 시스템을 한 덩어리(책임)로 보고 액터와의 상호작용만 적는다. "어떻게"가 아니라 "무엇을".
### 2-4. 액터
- 액터 = 시스템과 상호작용하는 역할. 주액터(목표 주체, 계산원)·지원액터(외부 서비스, 결제 대행)·오프스테이지(관심 있으나 직접 안 씀, 세무).
### 2-5. 주 성공 시나리오 + 확장
- 주 성공 시나리오: 문제 없는 정상 흐름(happy path), 번호 매긴 단계.
- 확장: 대안·예외 흐름. "단계 N에서 X면 …"(신용 거부·재고 부족).
- [uml/텍스트] Process Sale 주 시나리오(1~5단계) + 확장(3a. 신용 거부).
- 훈련: PlaceOrder의 확장 하나를 떠올려라 — 재고 부족이면?

## 3. 얼마나 상세히 (상세도 · Just Enough)
### 3-1. 세 단계
- brief(한 문단 요약) · casual(비형식 여러 문단) · fully-dressed(전 항목).
### 3-2. fully-dressed의 구성
- 전제조건(시작 전 참) · 성공 보장(끝나면 참) · 주 시나리오 · 확장 · 특별 요구.
### 3-3. Just Enough — 소수만 상세히
- 모든 유스케이스를 fully-dressed로 쓰지 않는다. 고가치·고위험 소수만 상세, 나머지는 brief/casual. 반복·점진으로 필요할 때 상세화(1교시 Just Enough의 유스케이스판).
- 훈련: NewPOS에서 어느 유스케이스를 fully-dressed로? (Process Sale — 핵심·고빈도)

## 4. 유스케이스가 분석을 이끈다 (use-case driven)
### 4-1. 후속 산출물의 원천
- 유스케이스에서 개념 모델(명사)·동적 모델(SSD·상태)이 파생한다 — 유스케이스가 분석·설계·테스트를 이끈다.
- 예시: Process Sale 명사 → 개념 클래스(Sale·SalesLineItem·Payment), 시나리오 → SSD(세션 6).

## 5. 유저 스토리와 편재 언어
### 5-1. 유스케이스는 사용자 언어로
- 유스케이스는 도메인·사용자 어휘로 쓴다(기술 용어 아님). 편재 언어(UL)가 여기서 시작 — 이후 개념 모델·코드가 같은 어휘를 쓴다.
### 5-2. 유저 스토리
- 유저 스토리 = "As a <역할>, I want <기능> so that <가치>"의 경량 카드 — 대화를 위한 약속. INVEST(독립·협상가능·가치·추정가능·작음·검증가능).
### 5-3. 두 해상도 — 언제 무엇
- 유저 스토리=대화용 경량(상세는 대화에서), 유스케이스=시나리오 흐름(상세는 텍스트에). 스토리는 백로그·계획에, 유스케이스는 흐름·확장이 중요할 때.
- 훈련: "고객이 주문을 취소한다" — 스토리로 충분한가, 유스케이스가 필요한가? (확장·예외가 많으면 유스케이스)

## 6. 실습 — Order PlaceOrder fully-dressed
- 목표: Order의 PlaceOrder 유스케이스를 fully-dressed로 작성한다.
- 준비: Order 도메인 서술.
- 진행: 액터 식별 → 주 성공 시나리오(번호 단계) → 확장 2~3 → 전제조건·성공 보장.
- 산출: PlaceOrder fully-dressed 유스케이스.
- 디브리프: 텍스트가 본체인가(다이어그램 아님)? 확장을 빠뜨리지 않았나? 사용자 언어로 썼나?

- 순서: 문제 → 정의(2) → 상세도(3) → driven(4) → 스토리·UL(5) → 실습(6).
- 설명=NewPOS Process Sale, 실습=Order PlaceOrder. 예시 일관.
- UC 다이어그램은 "2차"로만 언급 — **UML 등장 배경은 여기서 안 함**(4교시 정적 모델, 표기 첫 사용).
- 요구 품질·정의 표준(ISO 29148)은 QM 소유 — "입력으로 받는다"까지만, 표준 나열 금지.
- 의문형 물음표, 원작자(Larman·Jacobson·Cohn·Evans) 하단.
- 목표 장수 ~18장(65분): 학습목표1 + 본문 ~16 + 요약1.
- 역반영 후보: 없음 — 전제조건·성공 보장은 fully-dressed의 전개(C7)이지 새 주장 아님(DbC는 이 세션서 안 가르침).
