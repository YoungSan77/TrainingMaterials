# BDD 강의 소스 (부 01 · 세션 3 · 약 35분 · 1차)

> 세션 3 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 층: 유스케이스(세션 2)의 확장 — 시나리오를 실행가능 명세로. 설명=일반/NewPOS, 실습=Order. 한글(영어). 의문형. 원작자 하단.
> 깊이 = 가벼움(35분, ~10장). 구성 = 선형(문제→BDD→실행가능 명세→UL→스토리+GWT→실습).
> 층 경계: BDD *도구*(Cucumber·Gherkin 런타임)는 여기서 안 다룬다 — 접근·명세 사고까지. 단위 테스트 기법(TDD)은 세션 13.

## 원작자·출전
- BDD: Dan North (2006) — TDD의 오해에서 출발한 재구성
- Given-When-Then: Gherkin 문법
- 편재 언어: Eric Evans (DDD)
- 유스케이스 연결: Larman (세션 2)

## 1. 문제 — 요구·테스트·코드가 따로 논다
- 현상: 요구 문서·테스트·코드가 별개로 관리되어 명세가 낡고 셋의 해석이 갈린다.
- 예시: "취소는 배송 전만" 규칙이 문서엔 있고, 테스트엔 없고, 코드는 다르게 구현된다.
- 훈련: 이 셋이 어긋났을 때 무엇이 진실인가? (아무도 모른다 — 그게 문제)

## 2. BDD — 예시로 명세한다
- 정의: BDD = 구체 시나리오(예시)로 행위를 명세하는 접근(Dan North). 추상 규칙이 아니라 실제 예로 합의한다.
- GWT: Given(전제 상태) · When(사건) · Then(기대 결과).
- [예시] Given 배송 전 주문, When 취소 요청, Then 주문이 취소된다 / Given 배송된 주문, When 취소 요청, Then 거부된다.
- 훈련: "총액은 항목 합" 규칙을 GWT로 써보라.

## 3. 실행가능 명세
- 시나리오가 곧 수용 테스트다 — 명세와 검증이 한 문서라 문서가 낡지 않는다.
- 유스케이스와의 관계: 유스케이스(세션 2)가 흐름이라면, BDD는 그 시나리오·확장을 검증 가능한 예시로 구체화한다. UC=흐름, BDD=예시.

## 4. 편재 언어로 쓴다
- GWT를 도메인·사용자 어휘로 쓴다(UL — 세션 2에서 시작). 업무 담당자와 개발자가 같은 문장을 읽고 합의한다(번역 손실 제거).

## 5. 유저 스토리 + GWT
- 유저 스토리의 수용 기준을 GWT로 쓴다 — 스토리(무엇을·왜) + GWT(어떻게 검증)가 한 쌍이다.
- [예시] 스토리 "고객으로서 주문을 취소하고 싶다" + 수용 기준 GWT(배송 전 취소 / 배송 후 거부).

## 6. 실습 — Order 규칙 하나를 GWT로
- 목표: Order 상태 전이 규칙 하나를 GWT 시나리오로 쓴다.
- 준비: Order 규칙군(order-domain-definition.md) 중 하나.
- 진행: 규칙 선택 → Given-When-Then → 확장(거부 케이스) 추가.
- 산출: GWT 시나리오 1~2개.
- 디브리프: 이 상태 전이가 동적 모델(세션 6·7 상태 머신)로 이어진다 — 같은 규칙, 다른 표기.

## 슬라이드 변환 지침
- 순서: 문제 → BDD·GWT → 실행가능 명세 → UL → 스토리+GWT → 실습.
- 설명=일반/NewPOS, 실습=Order. 예시는 취소·전이로 일관(세션 6과 이음).
- BDD는 도구가 아니라 접근이다 — Cucumber 등 런타임은 언급만, 가르치지 않음(반론 슬라이드).
- 의문형 물음표, 원작자(North·Evans) 하단.
- 목표 장수 ~10장(35분): 학습목표1 + 본문 ~8 + 요약1.
- 역반영 후보: 없음(노드 C1~C6로 충분).
