# GRASP·RDD 강의 소스 (교시 9 정본 · 개정판)

> 교시 9(책임 주도 설계 강의)의 **내용 정본**. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 개정 사유: 초판이 RDD·정의를 얇게 적어 슬라이드가 "이름만" 남고 걷돌았다. 이번엔 **RDD 본체·각 원칙 정의를 슬라이드로 펼 만큼 두껍게**, 원작자·출전 명시, 의문형은 물음표.
> 서술 원칙: RDD가 주, GRASP·SOLID는 도구. 각 원칙 = 개념→문제→정보 소재 추론(설명 본체)→한계→다음 원칙 연결. 설명 예제 = NewPOS(Larman), 실습만 Order.

## 원작자·출전 표시 규약 (Code에게)
- 개념 수준(RDD·GRASP·SOLID)에만 원작자·출전 표시. 개별 원칙엔 안 붙인다.
- 표시 위치: 슬라이드 하단, **페이지 번호 2줄 위, 9pt, 슬라이드 가로 가운데 맞춤.**
- RDD: Rebecca Wirfs-Brock (Object Design: Roles, Responsibilities, and Collaborations, 2003)
- GRASP: Craig Larman (Applying UML and Patterns, 3rd ed.)
- SOLID: Robert C. Martin

## A. 책임 주도 설계 (RDD) — 본체 (2~3장 분량)

### A-1. RDD란 무엇인가 (정의)
- **책임 주도 설계(Responsibility-Driven Design, RDD)**: 객체를 "데이터 + 알고리즘"이 아니라 **"역할(role) + 책임(responsibility)"**으로 보고, 책임을 객체에 할당하며 협력을 설계하는 기법. Rebecca Wirfs-Brock이 1990년에 창시한, 객체 설계에 대한 최초의 **행위 기반(behavioral)** 접근.
- **데이터 주도 설계와의 대비(핵심)**: 데이터 주도 설계는 클래스의 행위를 그 클래스가 가진 데이터와 함께 정의한다. RDD는 그 반대다 — **무엇을 아는가(데이터)가 아니라 무엇을 책임지는가(행위)로 객체를 정의한다.** 이 대비가 뒤에 나올 빈혈 도메인(데이터+외부 로직) vs 리치 도메인(책임 가진 객체)의 뿌리.

### A-2. 왜 책임이 설계의 단위인가
- 설계 질문은 "무슨 클래스가 있나"가 아니라 **"이 책임은 누가 지는가?"**이다.
- 책임 두 종류(Wirfs-Brock):
  - **아는 책임(knowing)**: 자기 데이터·파생값·관련 객체를 안다.
  - **하는 책임(doing)**: 스스로 무언가를 하거나, 다른 객체에게 시키거나, 활동을 조정한다.
- 객체는 단순한 데이터 묶음이 아니라 **역할**을 맡는다 — 정보 보유자·서비스 제공자·조정자·제어자·구조화자·외부 인터페이스. 각자 자기 몫을 알고 해야 한다.

### A-3. 책임 할당은 판단이다 — 그래서 도구가 필요하다
- 같은 요구도 책임을 어디 두느냐로 설계가 갈린다 — 총액 계산을 바깥 서비스에 두면 절차적, Sale에 두면 객체적.
- 책임 배치엔 정답표가 없다. 이 **판단을 돕는 도구**가 필요하다:
  - **GRASP** (Craig Larman): 책임 할당을 사고하는 9개 패턴.
  - **SOLID** (Robert C. Martin): 그 배치가 변화에 견디는지 보는 5개 원칙.
  - 둘 다 유일 정답이 아니라 **정돈된 틀**이다. 이름이 원칙이든 패턴이든 중요치 않다 — 책임을 명료하게 사고하는 렌즈다.
  - **DbC (operation contracts)**: 책임에는 계약이 따른다(사전·사후조건). Larman은 유스케이스 연산 계약에서 이를 다룬다. 책임 배치(GRASP)와 책임의 계약(DbC)이 한 쌍.

## B. GRASP 핵심 6 (상세 — 각 원칙: 정의·문제·정보 소재 추론·한계·연결)

### B-1. 정보 전문가 (Information Expert)
- **정의**: 어떤 책임을, 그 책임을 수행하는 데 필요한 **정보를 가진 객체**에 할당하는 원칙. "정보가 있는 곳에 행위를 둔다."
- **문제(NewPOS)**: 판매의 총액(grand total)은 누가 계산하는가?
- **정보 소재 추론(설명 본체)**: 필요한 정보를 나열하고, 그 정보를 가진 자를 찾는다 —
  - 모든 판매 항목(SalesLineItem)을 아는 자는? → **Sale**. 따라서 총액 계산은 Sale의 책임.
  - 항목 소계(수량×단가)를 계산할 정보를 가진 자는? → **SalesLineItem**(수량을 안다). 따라서 소계는 SalesLineItem의 책임.
  - 단가를 아는 자는? → **ProductDescription**. 따라서 가격 제공은 그 책임.
  - → 세 객체가 각자 아는 만큼만 계산하고 서로에게 물어 합친다. **코드는 이 추론의 결론일 뿐이다.**
```java
class Sale {
    private List<SalesLineItem> lineItems;
    public Money getTotal() {
        Money total = Money.ZERO;
        for (SalesLineItem li : lineItems)
            total = total.add(li.getSubtotal());   // 각 항목에게 물어본다
        return total;
    }
}
class SalesLineItem {
    private int quantity;
    private ProductDescription description;
    public Money getSubtotal() {
        return description.getPrice().times(quantity);
    }
}
```
- **한계**: 정보를 가졌다고 항상 책임을 주면 안 된다. 예를 들어 데이터베이스 저장 책임을 "저장할 데이터를 가진" Sale에 주면, Sale이 SQL·트랜잭션·연결을 알게 되어 **응집이 무너지고 도메인이 인프라에 결합**된다.
- **다음**: 이 한계가 **순수 창작물(Pure Fabrication)**을 부른다 — 저장 책임을 도메인 객체가 아닌 인공 객체에 위임한다.

### B-2. 창조자 (Creator)
- **정의**: 객체 B를 생성할 책임을, B를 담거나·집약하거나·긴밀히 사용하거나·초기화 정보를 가진 객체 A에 할당한다.
- **문제(NewPOS)**: 판매 항목(SalesLineItem)은 누가 생성하는가?
- **추론**: Sale이 SalesLineItem을 집약하고(포함하고) 생성에 필요한 정보를 안다 → **Sale이 생성 책임(makeLineItem)**. 바깥에서 조립하면 Sale 내부 구성 규칙이 밖으로 샌다.
- **한계**: 생성 로직이 복잡하거나(조건에 따른 타입 선택) 재료가 여러 곳에 흩어지면 창조자가 억지가 된다.
- **다음**: 복잡한 생성 → 팩토리(Factory, 디자인 패턴). GRASP가 패턴을 부르는 첫 지점.

### B-3. 제어자 (Controller)
- **정의**: 시스템 이벤트(사용자 인터페이스가 던지는 요청)를 받을 첫 객체를, 인터페이스가 아니라 **도메인 경계의 제어자**(전체 시스템을 대표하는 객체 또는 유스케이스 처리자)에 할당한다.
- **문제(NewPOS)**: enterItem, endSale 같은 시스템 연산은 누가 받는가?
- **추론**: 인터페이스가 도메인을 직접 헤집으면 업무 로직이 UI로 샌다. Register(또는 유스케이스 처리자)가 이벤트를 받아 도메인에 위임하면 UI와 도메인이 분리된다.
```java
class Register {                       // 제어자
    private Sale currentSale;
    public void enterItem(ItemID id, int qty) {
        ProductDescription d = catalog.find(id);
        currentSale.makeLineItem(d, qty);   // 도메인에 위임
    }
}
```
- **한계**: 한 제어자가 모든 연산을 받으면 비대해진다(bloated controller) — 응집이 낮아진다.
- **다음**: 유스케이스별 분리 → 애플리케이션 서비스 층. **아키텍처 과정의 Use Case Interactor가 여기서 재정박된다.**

### B-4. 낮은 결합도 (Low Coupling)
- **정의**: 요소 사이의 의존을 낮게 유지해, 한 곳의 변화가 다른 곳으로 번지지 않게 한다.
- **문제**: 결제 처리를 Sale이 특정 결제 구현에 직접 의존하면, 결제가 바뀔 때 Sale이 흔들린다.
- **추론**: Sale은 결제의 **역할(인터페이스)**만 알고 구현을 모른다 → 결제 구현을 바꿔도 Sale은 무영향.
- **한계**: 결합을 0으로 추구하면 오히려 인공적 중개가 늘어 이해가 어려워진다 — 낮은 결합도 역시 **정도의 판단**이다.
- **다음**: 변화 지점 격리 → 보호된 변화(Protected Variations)·의존성 역전(아키텍처 의존성 규칙).

### B-5. 높은 응집도 (High Cohesion)
- **정의**: 한 요소는 밀접하게 관련된 책임만 갖게 해, 한 가지를 잘하도록 한다.
- **문제**: 한 클래스가 주문·결제·배송·저장을 모두 하면(낮은 응집) 이해·변경·재사용이 다 어렵다.
- **추론**: 책임을 응집 단위로 나눈다 — Sale(주문), Payment(결제), Shipment(배송). 낮은 결합도와 짝을 이뤄 보통 함께 개선하고 함께 판단한다.
- **한계**: 지나치게 잘게 나누면 협력 비용(객체 수·간접 호출)이 커진다 — 응집도도 정도의 판단.
- **다음**: 도메인에 맞지 않는 응집 덩어리(예: 저장) → 순수 창작물(Pure Fabrication).

### B-6. 다형성 (Polymorphism)
- **정의**: 타입에 따라 동작이 달라질 때, 조건 분기 대신 **다형성**으로 처리한다 — 타입별 변형을 인터페이스와 재정의에 맡긴다.
- **문제(NewPOS)**: 결제 수단(현금·카드·수표)마다 처리가 다르다. `if (현금) … else if (카드) …` 분기가 코드 곳곳에 번진다면?
- **추론**: 결제를 다형 타입으로 만든다 — 현금결제·카드결제가 각자 authorize()를 구현한다. 새 결제 수단이 생겨도 분기문을 고치지 않고 타입만 추가한다.
```java
interface Payment { AuthResult authorize(Money amount); }
class CashPayment   implements Payment { /* ... */ }
class CreditPayment implements Payment { /* ... */ }
// 호출부: payment.authorize(total) — 분기 없음
```
- **한계**: 변형이 하나뿐이거나 늘지 않으면 다형성은 과잉(불필요한 계층)이 된다.
- **다음**: 변형을 인터페이스 뒤로 감추는 일반화 → 보호된 변화(Protected Variations), 그리고 전략(Strategy) 패턴.

## C. GRASP 개념 3 (간단 — 의도적 조작 부류: 원칙을 일부러 거스른다)
> 이 셋은 정보에 충실한 자연스러운 배치가 아니라, 그 배치가 결합·응집을 해칠 때 **일부러 도메인에 없는 인공물이나 간접층을 만드는** 의도적 조작이다(의존성 역전과 같은 성격).

### C-1. 순수 창작물 (Pure Fabrication)
- **정의**: 도메인 개념이 아닌 **인공 클래스**를 지어 책임을 맡긴다 — 응집·재사용·낮은 결합을 얻기 위해.
- **예(NewPOS)**: 영속성. Sale에 저장을 두면 응집이 깨지니, 저장 책임을 도메인 밖 인공물(예: 영속성 저장소/Repository)에 위임한다. (정보 전문가의 한계가 부른 해법)

### C-2. 간접화 (Indirection)
- **정의**: 두 요소의 **직접 결합을 피하려 중개자**를 둔다.
- **예**: 제어자가 UI와 도메인 사이에 서는 것, 어댑터가 도메인과 외부 API 사이에 서는 것.

### C-3. 보호된 변화 (Protected Variations)
- **정의**: 변화가 예상되는 지점을 **안정된 인터페이스로 감싸**, 그 변화가 밖으로 번지지 않게 한다.
- **예**: 결제 구현의 변화를 결제 인터페이스로, 외부 세금 계산의 변화를 어댑터로 감싼다.
- **핵심**: 낮은 결합도·다형성·간접화의 상위 동기 — 의존성 역전(DIP)·개방-폐쇄(OCP)와 같은 뿌리. 아키텍처의 의존성 규칙이 이 원칙의 구조 수준 실현이다.

## D. 원칙에서 패턴으로 (강의 닫기 — 다음 단계 복선)
- 원칙은 **단일 관점**의 판단이다. 현실 문제는 여러 관점이 얽혀 원칙 하나로 풀리지 않는다.
- 원칙들의 긴장을 상황에 맞게 조합한 정형 해법이 **디자인 패턴**(복잡한 창조자→팩토리, 다형성+보호된 변화→전략, 간접화→어댑터), 더 큰 조합이 **아키텍처 패턴**이다.
- 그래서 순서: GRASP(원칙) → 디자인 패턴 → 아키텍처 패턴. **원칙을 알면 패턴을 유도하고, 모르면 암기한다.**
- **DDD를 부르는 복선**: RDD·GRASP는 "책임을 어디 둘까"까지 준다. 그러나 "무엇을 하나의 모델 단위(경계)로 볼까" — VO·Aggregate의 경계 — 는 안 준다. 이 공백이 다음 층(DDD)을 부른다. 개발자들은 이 문제를 이미 풀어왔지만 이름·일관성이 없었고, 에반스가 명명·패턴화했다.

## 슬라이드 변환 지침 (Code에게)
- **A(RDD)를 강의 앞머리 2~3장으로 세운다** — RDD 정의(Wirfs-Brock·역할+책임·데이터주도와 대비), 아는/하는 책임, 책임 할당은 판단이라 도구가 필요하다(GRASP·SOLID). RDD 없이 원칙부터 던지지 않는다.
- 각 원칙 슬라이드는 **정의(온전한 문장, full words)를 먼저**, 그다음 정보 소재 추론(설명 본문), 그다음 코드(예시로 종속), 한계. **코드만 있고 설명 없는 장 금지.**
- 용어는 "한글역(영문)" 완전 표기. 축약·조어 금지. 의문형 문장엔 물음표.
- 원작자·출전은 위 표시 규약대로(RDD·GRASP·SOLID 개념 장 하단, 9pt 가운데).
- 핵심 6은 각 1~2장, 개념 3은 묶어 1~2장, D(원칙→패턴·DDD 복선)로 닫기.
- 분량이 1교시를 넘으면 2교시로 나눈다 — 시수는 소스 분량이 정한다(번호 정리는 OOAD 완성 후 일괄).
