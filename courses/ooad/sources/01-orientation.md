> 오리엔테이션 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 층: 과정 전체의 프레임(왜·자세·지향·예제). 자세=canon-stance.md 축자. 설명=일반/NewPOS, 예제 도메인=Order 소개.
> 깊이 = 오리엔테이션(개념 도입 수준, ~14장). 한글(영어). 의문형 물음표. 원작자 하단.
> 구성 = 선형(계보→문제→해결 씨앗→자세→지향→예제). 나선형 아님.
> 층 경계: anemic·책임 배치·RDD 용어는 여기서 쓰지 않는다(설계 세션). 여기선 "절차적·흩어진" 수준까지.
> 계보 규약: 두 축(조직·상태)으로 그린다(단선 금지). 동기·지도이지 원칙 아님. 함수형은 이름·기여(불변·순수)까지, 깊이는 과정 밖. 각 기법의 깊이는 소유 세션.

## 1. 왜 이 과정인가 (문제)
### 1-0. 패러다임 계보 (동기·지도 — 원칙 아님)
- [조직 축] 코드를 어떻게 조직하나의 계보: 스파게티(GOTO·흐름 통제 불능) → 구조적/절차적(순차·분기·반복으로 흐름을 길들임, Dijkstra) → 모듈화(변경될 결정을 모듈에 숨김, Parnas) → 객체지향(데이터+행위를 한 경계로). 각 세대는 앞 세대의 무엇을 고쳤나 — 흐름, 그다음 지식의 위치, 그다음 데이터·행위의 분리.
- [상태 축] 함수형은 다른 축이다 — "상태를 어떻게 다루나". 명령형(위 계보 전체)의 가변 상태·부작용 문제에 불변 값·순수 함수로 답한다(람다 대수·Lisp). 객체의 다음 단계가 아니라 나란히 자란 계보.
- [수렴] 현대 OO = 두 계보의 수렴이다 — 객체가 조직을, 함수형이 상태 규율을 준다. 이 과정 뒤에서 배울 불변 값 객체·부작용 없는 계산·다형성으로 분기 제거가 그 증거. **동기를 알아야 뒤의 효용이 보인다.**
- [경계·원칙 아님] "옛날엔 이랬다"가 "그래서 이게 맞다"로 미끄러지면 안 된다. 계보는 맥락이고, 각 기법은 그 자체 근거(변경 국소화·결합 감소)로 선다. 깊이는 소유 세션(모듈화=8).
### 1-1. 절차지향의 한계
- 정의: 절차지향 = 데이터(자료구조)와 그것을 다루는 함수를 분리하고, 문제를 함수 분해로 푼다.
- 현상: 규모가 커지면 데이터와 함수가 따로 자란다 — 한 데이터를 여러 함수가 만지고, 한 함수가 여러 데이터를 만진다.
- [codepair] 절차적 Order: `OrderData`(게터·세터만) + `OrderService.calcTotal()/validate()/cancel()` — 로직이 전부 서비스에 몰린다.
- 무너지는 순간: 취소 규칙 하나가 바뀌면 서비스·검증·상태 코드가 여러 곳에서 동시에 바뀐다(산탄총 수정).
### 1-2. 왜 파급이 넓은가 (원인)
- 지식이 전역 상태·공유 자료구조에 새어 있다 — "무엇을 아는가"가 여러 모듈에 흩어져 경계가 없다.
- 그래서 변경 파급을 예측할 수 없다: 어디를 고치면 어디가 깨질지 모른다.

## 2. 객체라는 답 (해결의 씨앗)
### 2-1. 객체 = 경계
- 객체는 데이터와 그 데이터를 다루는 행위를 한 경계로 묶는다.
- [codepair] 그 반대: `order.cancel()` — 취소 규칙이 Order 안에서 지켜진다. 규칙이 바뀌어도 Order 안만 바뀐다(변경 국소화).
- 훈련: 방금 두 버전에서 "취소 조건 추가"를 하면 각각 몇 곳을 고치나? (절차적=흩어진 여러 곳 / 객체=한 곳)
### 2-2. 경계가 책임을 만든다
- 경계는 "이건 누구 일인가"에 답을 준다 — 책임 소재가 생긴다.
- OOAD가 가르치는 것 = 그 경계를 어디에 긋는가. 분석=무엇이 있나(개념), 설계=누가 무엇을 하나(책임). 이 과정의 두 축.

## 3. 어떤 자세로 (프로그램 자세 — canon-stance 정본)
### 3-1. 필요악
- 완벽한 코드를 처음부터 쓸 수 있다면 분석·설계·테스트는 불필요하다.
- 불가능하기에 도입된 보정이다 — 아는 채로 하면 도움, 모르거나 지나치면 필요악(오용).
### 3-2. Just Enough
- 사전 활동은 코드가 요구하는 만큼만 — 모자라면 무지의 부채, 넘치면 과잉의 부채.
- BDUF(전부 미리)가 아니다. 반복·점진으로 나머지는 코드로 배운다.
### 3-3. 예방과 상환
- 정의: 사전 활동(분석·설계·테스트) = 부채 예방 / 사후(리팩토링) = 이미 진 부채의 상환.
- 이 과정에서의 위치: 서론(오늘)의 자세는 예방이다. 상환(리팩토링)은 세션 13에서 다룬다 — 예방과 상환은 한 쌍.
### 3-4. LLM 시대의 명제
- LLM은 우발 복잡도(문법·보일러플레이트)를 걷어낸다. 본질 복잡도(도메인·규칙·불변식)는 암묵지라 인간이 명세한다.
- 그 명세 기술이 이 과정의 내용이다 — 명세 노동은 사라지지 않고 프런티어로 이동한다.

## 4. 어디를 향하나 (지향점)
### 4-1. UC·UL이 나침반
- 우리는 유스케이스(사용자 목표)를 이루려 설계한다 — 기능 목록이 아니라 목표.
- 편재 언어(UL)로 도메인을 한 어휘로 말한다. UL은 다음 세션(유스케이스)부터 실제로 적용된다.
### 4-2. 과정 지도
- 여정: 요구 → 분석(rich 개념 모델) → OO 설계(모듈화·SOLID·책임 배치·패턴) → 코드 → 진화(DDD·MSA 이음). 2일에 이 순서로 간다.
- 오늘의 자리: 출발점 — 자세와 지향을 세운다. 다음(세션 2)은 요구를 유스케이스로 옮긴다.

## 5. 예제 도메인 — Order (소개)
- 과정 내내 하나의 도메인을 쓴다: Order(주문). 설명은 NewPOS(판매), 실습은 Order.
- Order는 규칙(불변식)을 가진 도메인 — 합계·수량·상태 전이 등. 세부는 실습에서 다룬다(정본 order-domain-definition.md).
- 훈련(가벼운): "주문에 항목이 0개일 수 있나?" — 도메인 규칙을 미리 감각한다.

## 슬라이드 변환 지침
- 순서 엄수: 문제(절차지향 한계) → 해결 씨앗(객체) → 자세 → 지향 → 예제.
- 자세(3장)는 canon-stance 축자 — necessary-evil·just-enough·prevent-repay 문구 유지.
- [codepair] 두 곳(절차적 vs 객체 Order) 대비를 코드 골격으로 — 단 **anemic 용어 금지**(설계 세션서 도입). 여기선 "절차적/로직이 흩어진" 수준.
- Order는 소개만 — 규칙 상세는 실습(5)로 미룬다.
- 의문형 물음표, 원작자(Brooks·canon-stance) 하단.
- 계보(1-0)는 두 축(조직·상태)으로 — 단선 금지, functional은 나란한 축. 동기용이라 이름·기여까지만.
- 목표 장수 ~18장(50분): 학습목표1 + 본문 ~16(계보 3 포함) + 요약1.
