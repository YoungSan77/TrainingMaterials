# 객체지향 분석과 설계 실무 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** 객체지향 분석과 설계 실무 (`ooad`)
- **총 교육시간:** 16시간(기존 계획값; 최종 SA 완성 후 운영 적합성 평가)
- **대상:** 개발자·설계자·분석가
- **선수지식:** 절차적·서비스 중심 코드에서 변경 파급과 책임 분산을 경험

### 과정의 맥락

아래 성숙도·운영 조건은 s01~s05 원고가 전제한 수준에서 정리한 **가정**이다. 사전 설문과 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 | 확인 방법 |
|---|---|---|
| **도메인** | 주문·결제·배송을 사용자로서 안다. 규칙·상태·외부 시스템 조정은 모른다 | 사전 설문 |
| **기술** | 자바 코드를 읽고 실행한다(`record`·`enum` 포함). 모델링은 UML을 본 적이 있는 정도다 | 사전 설문, S01 코드 예측 |
| **팀워크** | 요구를 문서로 받아 구현한다. 요구 합의·설계 리뷰 경험은 적다 | 사전 설문, S02 실습 |

- **다루는 불확실성** — 업무 불확실성이 중심이다. 관통 사례는 규칙과 상태 경계가 **처음부터 확정되지 않은** 주문을 다룬다(결제 전 취소, 출고와 배송 시작). 기술 불확실성은 외부 시스템의 **동기·비동기**와 기술 제약(S10)으로 한정한다.
- **깊이의 결정** — 성숙도가 낮은 **요구 합의와 모델링**을 명시하고 먼저 검증한다: 판단의 수준 구분, 공통 식별자, 확정·가정·미정의 구분, 모델과 코드·테스트의 연결. 표기는 판단에 필요한 만큼만 다루고, 자바 문법과 프레임워크는 설명하지 않는다.
- **요구에서 코드까지의 경로** — 관통 사례인 주문은 **도메인 복잡성이 높고**(규칙과 상태 경계가 처음부터 확정되지 않음) 기술 복잡성은 중간이다(외부 시스템 4개와의 조정). 그래서 불변의 뼈대(요구 → 유저 스토리(수용 기준 포함) → 코드·테스트) 사이에 유스케이스·정적·동적 모델을 두고, 경계·설계는 외부 시스템과 변경이 요구하는 만큼만 더한다. 멈추는 기준은 S11의 적정 모델링이다(`guides/sw-engineering-principles.md` 7절).
- **운영 조건** — 가정: 20명 안팎, 개인 실습과 소그룹 비교를 섞는다, 실습 환경은 JDK로 예제를 컴파일·실행할 수 있고 수강생마다 **LLM**(생성형 AI 대화 도구)을 쓸 수 있다.

### 기준 원전과 참고 자료

**기준 원전:** Craig Larman, *Applying UML and Patterns*, 3rd ed., 2004. 요구·유스케이스·도메인 모델·SSD·계약·GRASP·설계 모델의 정의·템플릿·표기·절차는 이 책을 따른다. 2판의 문구는 쓰지 않는다.

참고 자료는 별도 문서인 별첨 `sessions/references.md` 하나에 레이블의 알파벳 순서로 둔다. 본문은 레이블(`[Larman 2004]`)로 인용·참조한다.

- Evans 인용은 *Domain-Driven Design Reference*(2015) 원문을 우선한다.
- AI 에이전트 관련 인용(S14)은 날짜가 있는 1차 원문(공식 엔지니어링 글·저자 글)을 우선하고, 오래된 문헌이나 재인용으로 간접 연결하지 않는다.
- SWEBOK과 실무 서적의 관점이 충돌하면 사용자가 조정하고 아래 결정에 기록한다.

**원전 적용 결정**

- **「주문을 관리한다」는 Larman의 `Manage <X>`(CRUD 목표를 묶은 유스케이스)다** — 주문(생성), 배송지 변경(수정), 배송 전 취소(삭제)를 한 유스케이스로 두고, 배송지 변경·취소는 그 대안 흐름이다. 배송 후 반품은 Larman의 Process Sale·Handle Returns처럼 별도 유스케이스다(2026-10-02).
- **유스케이스 수준의 규칙은 명세서에 포함한다.** 여러 유스케이스에 공통인 도메인 규칙만 별도 규칙 목록에 둔다(2026-10-02).
- Larman의 Extensions와 RUP의 대안 흐름은 같은 것이다. 과정에서는 **대안 흐름** 하나로 쓴다(성공·실패 모두; 대안/예외 흐름을 나누지 않는다, 2026-10-02).
- 유스케이스 명세서는 Larman의 **정식 형식**(fully dressed) 템플릿 전체를 따른다 — 이해관계자와 관심사, 기타(미결 사항)를 포함한다. 이 유스케이스에만 적용되는 **업무 규칙**을 명세서에 더한다. "예외 정책" 항목은 두지 않는다(2026-10-02).
- 오퍼레이션 계약의 사후조건은 Larman대로 **도메인 객체의 생성·삭제, 연관 형성·해제, 속성 변경**으로 쓴다. "관찰 가능한 결과" 항목은 두지 않는다. 외부 시스템에 보내는 요청은 사후조건이 아니라 정제된 SSD의 시스템 사이 이벤트다(2026-10-02).
- **흐름 번호** — 대안 흐름은 갈라지는 기본 흐름 단계 뒤에 붙이고(`1a`, `3a`), 대안 흐름의 단계는 `1a.1`, `1a.2`로 쓴다. 대안 흐름의 단계에서 다시 갈라지면 `1a.2a`다(2026-10-02).
- **유스케이스 명세 형식** — Larman의 간략·약식·정식 세 형식을 소개하고, 가치와 위험이 큰 유스케이스만 정식으로 쓴다. 주문 사례는 「주문을 관리한다」만 정식, 「배송 현황을 조회한다」는 간략 형식이다(2026-10-02).
- **시스템 경계** — 업무 배경도(컨텍스트 다이어그램)를 쓰지 않고 유스케이스 다이어그램의 시스템 경계로 대신한다(2026-10-02).
- **SSD** — 외부 시스템에 보내는 메시지는 모두 "요청"(실선 화살표)으로 그리고 동기·비동기를 구분하지 않는다. 응답(return)은 그리지 않는다(2026-10-02).
- **단계별 구성** — 과정은 Larman의 반복(착수·정련 반복 1~3) 구성을 따르지 않고 단계별로 구성한다. 반복적으로 작업한다는 점은 필요한 슬라이드에서 언급한다. 아키텍처는 설계 뒤에 다룬다(Larman은 아키텍처 뒤에 설계)(2026-10-02).
- **S03 도메인 모델** — 개념 범주와 연관은 Larman의 개념 클래스 범주 목록·일반적인 연관 목록으로 점검한다(다른 원형 분류는 쓰지 않는다). 개념 클래스를 찾는 첫 전략인 기존 모델 재사용의 출발점은 **논리 데이터 모델**이다. Description class는 **설명 클래스**로 쓴다. 집합은 쓰지 않고 필요할 때 합성을 쓴다. 원표가 개념 후보로 두는 협력 시스템은 지원 액터로 두고 도메인 모델에 그리지 않는다. 상태는 하위 클래스가 아니라 열거형 상태 값과 상태 기계로 보인다(2026-10-03).
- **S03 용어와 위치** — Larman의 symbol·intension·extension은 **표기·정의·인스턴스**로 쓴다. 도메인은 **문제영역**(문제·기회, IIBA의 Need)과 **해결영역**으로 나눠 보고, 둘 다 붙여 쓴다. 구체화는 **객체 쪽**(도메인 모델 → 설계 모델 → 코드)과 **데이터 쪽**(개념·논리 → 물리 데이터 모델)으로 나눠 보이며, "물리 모델"은 데이터 쪽에만 쓴다(S10의 `OrderRow`는 물리 모델을 객체로 표현한 저장용 클래스). 원전에 없는 "평면 모델" 같은 조어 대신 "반복되는 속성 묶음"을 쓴다(2026-10-03).
- **S04 분석의 동적 모델** — Larman은 상호작용 다이어그램을 객체 설계에서 쓴다. 이 과정은 단계별 구성이므로, 도메인 모델 전에 시스템 수준의 SSD가 있듯이 도메인 모델 뒤에는 **도메인 객체 수준**의 상호작용(분석 시퀀스·커뮤니케이션)을 그린다. 반복·점진적으로 분석과 설계를 함께 하면 이 수준을 간단히 하고 설계 시퀀스로 간다. 시퀀스의 조건·반복 표기는 Larman대로 **프레임**(frame)이라 부르고 "조각"으로 옮기지 않는다. 정보공학의 DFD는 활동 다이어그램(객체 노드)과 비교해 보인다. 상태 폭증은 표기의 문제로 다루지 않고 **추상화 수준**(사건에 다르게 반응하는 상황만 상태)의 적정 모델링으로 다룬다(2026-10-03).
- **원전과 다르게 유지하는 선택** — S05의 구조적 경계는 업무 경계를 먼저 세우는 현행을 유지하고 Larman의 계층 우선 접근은 쓰지 않는다(계층 아키텍처는 필요할 때 소개만 한다). S05 패키지 원칙(Martin), S09 결정 기록(ADR), S10 매핑, 원전 밖에서 개발한 내용(의미 보존, SOLID·객체 계약, 평가 흐름, 통합, DevOps, DDD·MSA)은 현행을 유지한다. S13 이후는 현행을 유지하고 원전에서 도움이 되는 내용만 더한다(2026-10-02).

## 2. 과정 목표

문제영역의 의미를 해결책과 구분해 이해하고, 이를 정적·동적 모델로 명시한 뒤 구조적 경계와
객체의 책임·협력·계약으로 구체화하며, 구현과 검증 evidence로 필요한 상위 판단을 다시 여는
능력을 기른다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. 문제·요구·분석·설계·구현의 서로 다른 판단을 구분한다.
2. 정적·동적 모델로 문제영역의 의미와 행위를 검토한다.
3. 구조적 경계, 책임, 협력, 계약과 의존성 방향을 설계한다.
4. 변경 압력과 기술 제약 아래 대안을 비교하고 도메인 의미를 보존한다.
5. 코드·테스트·통합 evidence로 다시 열 판단 수준을 진단한다.
6. OOAD에서 SW Architecture·DDD·MSA·도메인 모델·온톨로지를 활용하는 AI-native SW공학으로 확장되는 질문을 구분한다.

## 3. 범위와 경계

**Core:** 요구 분석과 유스케이스, 개념적 도메인 모델과 동적 모델, 구조적 경계와 의존성,
분석에서 설계로의 비기계적 전환, 책임·협력·계약, 변화 대응과 변이 설계, 설계 대안 평가,
기술 제약 아래의 의미 보존, 적정 분석·설계와 그 안의 적정 모델링(Modeling Economics), 구현·테스트·DevOps가 만드는
SW공학 feedback.

**Extension:** SW Architecture·DDD·MSA가 OOAD 위에서 추가하는 독립적 판단, 도메인 모델·온톨로지의 의미 공유와 AI 맥락 활용, Human/Agent
R&R 및 맥락을 담은 Guardrail·Agent·Harness의 역할과 피드백을 다루는 AI-native SW공학. 이 구성을 고정된 단계 순서로 보지 않는다.

**Non-scope:** UML 표기 암기, GoF 카탈로그 완주, 특정 framework·ORM·DB·CI·AI 도구 튜토리얼,
그리고 후속 전문영역을 각 전용 과정 수준으로 완결하는 것.

## 4. 과정 전체 판단 원칙

- 개발 절차에서는 통합할 수 있지만 사고에서는 문제와 해결책을 구분한다.
- 모델은 필요한 질문에 답할 만큼만 만들며 분석 개념을 설계·코드로 기계 변환하지 않는다.
- 책임과 추상화는 실제 변경 evidence, 응집도·결합도, 비용과 trade-off로 판단한다.
- 기술적 실현은 구조를 바꿀 수 있지만 도메인 의미를 조용히 재정의해서는 안 된다.
- evidence가 나타난 위치와 결함이 생긴 판단 수준은 다를 수 있다.

### S01 — OOAD 개요 (45분)

- **목표:** OOAD가 어떤 판단을 다루는지 전체 지도를 만들고 문제와 해결책을 구분하는 사고를 정립하며, 요구·분석·설계가 코드·테스트로 어떻게 이어지는지 확인한다.
- **Anchor Message:** 개발 절차에서는 통합할 수 있지만, 사고에서는 문제와 해결책을 구분한다.
- **세부 목차:** 세션 목표 / 개발의 비용과 가치(재작업·미사용 기능·범위) / 문제와 요구사항(문제·요구·해결책, 이벤트) / 소프트웨어의 복잡성 / 분석과 설계(결정 경계) / 맥락과 접근법(맥락의 정의, 성숙도·불확실성·운영 조건) / OOAD와 UML / 모델에서 코드로(클래스·SSD·시퀀스·커뮤니케이션·상태 기계) / 요구에서 테스트로 / 책임과 경계(아키텍처·협력·분석에서 설계로의 전환) / 적정 분석·설계(북·스트리트 스마트, KISS·DRY·YAGNI) / 피드백과 잘못된 관행 / 전문영역으로의 확장(Architecture·DDD·MSA·DevOps·온톨로지·AI-native) / 실습 — 요구사항 정의서(정기배송) / 요약

### S02 — 요구 분석과 유스케이스 (1시간 15분)

- **목표:** 요청에서 본질적 요구를 분리하고 액터 목표·이벤트 흐름·시스템 오퍼레이션으로 검토 가능한 요구 모델을 만들며, 품질 요구·검증·추적을 연결해 누락과 가정을 검토한다.
- **Anchor Message:** 유스케이스는 액터의 목표와 가치 있는 결과를 중심으로 시스템의 행위와 책임을 드러낸다.
- **세부 목차:** 문제·요구·요구사항·해결책 구분 / 명세의 한계와 이벤트 중심 요구 정의·반복적 접근·AI 시대의 요구 / 고객·개발자의 업무 지식과 업무·기술 불확실성에 따른 요구 접근법 / 요구 발견·FURPS+ 분류·명세 품질과 반복 검증 / 용어집 정의(용어·정의·영문명)와 과정 전체의 이름 원천 / 유스케이스의 정의·작성 절차(경계 → 주 액터 → 목표 → 유스케이스)·액터 세 종류·후보 시험(상사·EBP·크기)·수준 / 유스케이스 다이어그램의 시스템 경계와 경계 판단(외부 시스템을 지원 액터로) / 유스케이스 명세 형식(간략·약식·정식)과 정식 형식 템플릿 / 기본 흐름과 대안 흐름(성공·실패 모두), 업무 규칙·특별 요구사항 / UML 유스케이스 관계와 유스케이스 잘못된 관행(기능 분할·CRUD·화면·기술 요소·시스템 관점·명세 과잉) / 시스템 시퀀스 다이어그램 초안(주 액터·시스템)과 정제된 SSD(외부 시스템에 보내는 요청, 응답은 그리지 않음)·시스템 오퍼레이션과 계약(도메인 객체의 상태 변화)·자바 코드와 테스트로의 연결 / 품질 요구·프로토타입 / 유저 스토리(카드·대화·확인, 문형과 가치, INVEST, 흐름으로 세로로 나누기, 잘못된 스토리)·BDD(발견·정형화·자동화, Given-When-Then, Example Mapping)와 유스케이스의 관계 / 명세 주도 개발(SDD) 개요 — 3가지 수준과 한계(명세 과잉, MDD의 교훈) / 요구 관리·추적·사용 증거 / 유스케이스 다이어그램·명세서 실습(정기배송)

### S03 — 정적 모델 — 도메인 개념과 관계 (1시간 30분)

- **목표:** 문제영역의 핵심 개념·속성·관계와 용어의 의미를 정적 모델로 명시한다.
- **Anchor Message:** 정적 모델은 구현과 분리해 문제영역의 개념과 관계를 이해하고 검토하는 모델이다.
- **세부 목차:** 유스케이스 명세서·정제된 SSD·계약을 입력으로 한 개념 추출과 피드백 / 개념 클래스(기호·내포·외연)와 기술 요소 없는 도메인 모델의 위치, 정보공학 데이터 모델(ERD)과의 연계 / 작성 절차(찾기 → 그리기 → 연관·속성)와 개념 클래스를 찾는 세 전략(기존 모델 재사용·범주 목록·명사구) / Attribute·데이터 타입·Association(need-to-remember, 일반적인 연관 목록)·다중성 식별 / 속성 도메인과 속성 수준 업무 규칙 / 연관 클래스·설명 클래스·일반화(100%·Is-a 규칙, 상태는 하위 클래스가 아님)·합성 / 용어와 의미 정렬, 요구 분석에서 정의한 용어집의 정제 / 정적 모델과 네 동적 다이어그램(상태 기계 중심)의 관계 / 클래스 유형과 관계 유형(연관·집합·합성·일반화·의존·실현) / Conceptual Domain Model 초안·상세 작성과 자바 코드·테스트로의 연결 / 정적 모델링의 잘못된 관행 / 시나리오와의 교차검토를 통한 누락·모순 확인 / 도메인 모델 초안·상세 실습(정기배송)

### S04 — 동적 모델 — 상호작용과 상태 (1시간 30분)

- **목표:** 시나리오의 System Operation·상호작용·상태 변화를 동적 모델로 확인하고 정적 모델과 교차검토한다.
- **Anchor Message:** 정적 모델은 무엇이 존재하는지, 동적 모델은 무엇이 일어나는지를 보여주며 서로를 검증한다.
- **세부 목차:** 요구 분석의 정제된 System Sequence·계약을 입력으로, 활동(유스케이스·시스템 간 업무 흐름, 정보공학 DFD와의 비교)과 도메인 객체의 interaction 모델링(시퀀스·커뮤니케이션을 같은 장면·같은 번호로) / 사건에 따른 state transition 확인 / 정적 모델과 동적 모델의 누락·모순 교차검토(상태·사건 이름은 용어집) / 추상화 수준과 필요한 질문에 답할 만큼만 만드는 적정 모델링 / 활동·시퀀스·커뮤니케이션·상태 기계 다이어그램의 자바 코드 매핑과 금지된 전이 테스트 / 시퀀스·상태 기계 실습(정기배송)

### S05 — 구조적 경계와 의존성 (1시간 15분)

- **목표:** 분석 결과를 바탕으로 책임이 놓일 구조적 경계와 의존성 방향을 판단한다.
- **Anchor Message:** 구조적 경계와 의존성은 책임이 놓일 범위와 변화가 전파되는 방향을 정한다.
- **세부 목차:** 클래스를 패키지로 나누는 기준(합성·소유·변경 이유·함께 쓰임·외부 통제)으로 주문 시스템 내부의 경계 후보 도출(시스템 컨텍스트는 S02에서 결정) / 외부 시스템에 대한 의존 방향 / 설계의 이름 — 분석은 한글, 설계는 용어집의 영문명과 명명 규칙 / 패키지 다이어그램으로 경계와 의존성 표현 / 경계 간 책임과 의존성 방향 설정 / 패키지(컴포넌트) 원칙 — 응집 REP·CCP·CRP, 결합 ADP·SDP·SAP — 과 반복·점진적으로 진화하는 구조 / 결합도와 변경 파급의 초기 검토 / 객체 설계 전에 필요한 구조적 제약 명시 / 패키지 다이어그램 초안·상세 실습(정기배송)

### S06 — 분석 모델에서 설계 모델로 (1시간)

- **목표:** 분석 개념을 기계적으로 변환하지 않고 의미를 보존하며 설계 모델로 전환한다.
- **Anchor Message:** 분석 모델의 의미는 보존하고, 설계 요소의 형태는 책임·경계·협력으로 다시 결정한다 — 전환은 판단이지 변환이 아니다.
- **세부 목차:** 분석 개념(개념·속성·관계·상태·계약·통보)과 설계 요소의 대응 유형(1:1·1:N·N:1·설계에만) / 비기계적 전환에서 지켜야 할 의미 보존 기준(용어집의 영한 대응 포함)과 조용한 의미 변경 / 시스템 이벤트를 받는 객체(주문 서비스)와 메시지에서 책임으로 — initial design / 주문 취소의 설계 시퀀스·설계 클래스 다이어그램과 자바 코드·의미 보존 테스트 / 잘못된 관행(기계적 변환·데이터만 옮기기·분석과 단절·기술 먼저) / 실습: 결제한다의 설계 시퀀스(정기배송, 대응표는 만들지 않는다)

### S07 — 책임·협력·계약 (1시간 30분)

- **목표:** 객체의 책임과 협력을 정제하고 계약으로 행위의 조건과 보장을 검증한다.
- **Anchor Message:** 객체 설계의 핵심은 데이터를 나누는 것이 아니라, 데이터와 규칙을 아는 객체에 책임을 두고 메시지와 계약으로 협력을 만드는 것이다.
- **세부 목차:** Responsibility-Driven Design과 GRASP 기본 다섯으로 책임 후보 도출·배치 / **CRC 카드** — 카드 형태로 보이고, 주문 취소를 카드로 따라가며 메시지가 옮겨 가고 책임이 넘치는 카드가 드러나는 진행 / 메시지 기반 협력·묻기와 시키기·정보 은닉·결합도 / **응집도와 SRP는 한 흐름**으로 — 정의는 Larman "cohesion … is a measure of how strongly related and focused the responsibilities of an element are"(2004, §17.14), 기준은 Martin "A module should be responsible to one, and only one, actor."(2018, *Clean Architecture* 7장)·"Gather together the things that change for the same reasons. Separate those things that change for different reasons."(2014, The Clean Code Blog), 예는 `Order`의 영수증 형식을 `AccountingAdapter`로 옮기는 전·후 클래스 다이어그램(액터: 주문 운영 담당·회계 담당, 교육용 가정) / 클래스 설계 원칙 ISP·DIP·LSP(사용자 SOLID 교재의 배치, 약어 원어는 주석) / precondition·postcondition·invariant로 객체 계약 명시, 시스템 계약과 구분 / 정제된 협력·설계 클래스 다이어그램과 계약 코드·테스트 / 실습: CRC 카드 → 정제된 설계 클래스(계약은 노트)

### S08 — 변화 대응과 변이 설계 (1시간 15분)

- **목표:** 실제 변경 압력이 기존 책임·계약·협력에 주는 영향을 관찰하고 변화를 국소화하는 설계를 만든다.
- **Anchor Message:** 변화 대응은 예상 가능한 모든 변이를 추상화하는 것이 아니라, 실제 변경 압력(change pressure)을 국소화하는 판단이다.
- **세부 목차:** 변경 요청 둘로 변경 파급 관찰 — ① 결제 전 취소(규칙·상태의 변경), ② 간편결제 추가(외부 시스템의 변이, `EasyPayAdapter` — S07 LSP 반례와 쓰임을 맞춘다) / variation point와 stable responsibility 식별 / OCP로 변이 국소화의 목표 정의 / GRASP의 변화 대응 원칙(Protected Variations, Indirection, Polymorphism)을 실제 압력에 선택적으로 적용 / composition·interface·dependency를 이용한 변이 국소화와 Pattern vocabulary(어댑터·전략) / 변경 후 설계 클래스 다이어그램과 자바 코드·변경 테스트 / 실습: 배송 주기 "매월 ○일"을 반영한 설계 클래스

### S09 — 설계 대안 평가 (1시간 15분)

- **목표:** 동일한 문제에 대한 여러 설계 대안을 change impact·품질·비용·trade-off 관점에서 비교하고 선택한다.
- **Anchor Message:** 좋은 설계는 원칙을 많이 적용한 설계가 아니라, 현재의 변화와 품질 요구에 가장 적절한 절충(trade-off)을 선택한 설계다.
- **세부 목차:** 결제 전 취소 규칙의 위치를 대안 셋(A `OrderService`의 분기, B `Order.cancel`의 상태별 검사, C 상태 패턴)으로 평가 / Change Impact → Cohesion/Coupling → Dependency → Abstraction Cost → SOLID/Pattern → Trade-off의 평가 흐름 / 선택(B)과 포기한 대안·다시 열 조건, 결정 기록 / 대안별 클래스 다이어그램과 선택 코드·테스트 / 실습: 대안 둘의 클래스 다이어그램과 고른 이유 한 줄

### S10 — 기술 제약과 도메인 의미 보존 (1시간)

- **목표:** 영속성·프레임워크·외부 시스템 같은 기술 제약에 적응하면서 도메인 의미를 보존한다.
- **Anchor Message:** 기술적 실현은 구조와 표현을 바꿀 수 있어도 도메인 의미를 조용히 바꿔서는 안 된다.
- **세부 목차:** persistence·framework·external API가 설계에 주는 압력 / 도메인 모델과 연동·인프라·물리 모델의 분리("모델"은 도메인·물리 모델에만 쓴다) / mapping과 변환에서 발생하는 의미 손실 — 상태는 이름으로, 단가는 확정 값 그대로, 복원은 규칙 재검사, 결제 금액·배송 번호 저장 / 물리 모델 코드·매퍼·라운드트립 테스트 / 실습: 도메인 클래스와 물리 모델(테이블)

### S11 — 통합 설계와 적정 모델링 (1시간)

- **목표:** 요구부터 기술 실현까지의 판단을 하나의 사례로 통합하고, 추가 모델링의 가치와 비용을 판단한다.
- **Anchor Message:** 모델은 질문에 답하고 위험을 줄일 때 가치가 있으며, 더 이상 판단을 개선하지 못하면 멈춘다.
- **세부 목차:** 주문 O-1의 생애(결제 → 배송지 변경 → 취소)를 요구→정적·동적 모델→경계→객체 설계→기술 실현으로 통합 / 통합이 드러낸 빈틈 — "출고 전"은 배송 시스템만 안다, 배송지 변경 계약을 "배송 시스템이 수락한다"로 되돌린다 / 모델별 질문과 증거 / 위험 주도의 적정 모델링 — 멈추는 기준, 남길 모델의 유지 비용, 추상화의 비용 / 통합 시퀀스와 통합 테스트 / 실습: 결제한다를 끝까지 이어 고친 상태 기계·시퀀스와 더 그리지 않을 다이어그램

### S12 — 구현·검증·DevOps와 SW공학 피드백 (1시간)

- **목표:** 코드·테스트·통합·배포 과정에서 얻은 evidence를 보고 어느 상위 판단을 다시 열어야 하는지 진단한다.
- **Anchor Message:** 문제가 발견된 위치와 그 문제를 만든 판단 수준은 다를 수 있으며, DevOps는 그 feedback을 빠르게 되돌리는 실행 체계다.
- **세부 목차:** Coding·Debugging·Developer Test·TDD(빨강·초록·리팩터링)·Refactoring의 피드백 / IDE·pre-commit·CI·CD·운영 신호가 가리키는 판단 / **역추적은 모델을 거슬러 오른다** — 실패한 테스트 → 계약 → 상태 기계·시퀀스 → 유스케이스(다섯 번의 왜처럼 과정 밖 기법은 쓰지 않는다) / 사례: 환불 완료 통보 중복 — 고친 상태 기계와 재현 테스트 / 원인 수준에서 위에서 아래로 고치기 / 실습: 배송 요청 실패인데 결제가 취소되지 않은 실패 테스트(7a)에서 모델을 거슬러 고친 상태 기계·계약 노트

### S13 — OOAD에서 전문영역으로 — Architecture · DDD · MSA (1시간)

- **목표:** OOAD에서 다룬 판단과 Architecture·DDD·MSA가 추가로 소유하는 판단을 구분한다.
- **Anchor Message:** OOAD는 전문영역을 대체하지 않으며, 문제 이해와 설계 판단을 제공하는 공통 기반이다.
- **세부 목차:** Architecture·DDD·MSA가 더 소유하는 판단을 소개한다(전문영역의 산출물 — 맥락 지도·품질 속성 시나리오 등 — 은 실습하지 않는다) / 구조적 품질속성·trade-off, 지속적 정제·Ubiquitous Language·Bounded Context, 분산 경계·원격 호출·운영 실패 / DDD의 포지셔닝은 Evans(2004) Part II 서두 인용을 다시 쓸 수 있다("01. OOAD 개요"의 「도메인 주도 설계」와 같음) / **간소화한 포트와 어댑터** — 이 과정의 패키지 구조(업무 경계가 출력 포트를 소유, 연동·`persistence`가 어댑터)에 이름을 붙이는 패키지 다이어그램과 코드(입력 포트·유스케이스 인터페이스 없음) / 실습: LLM이 생성한 포트와 어댑터 샘플 코드와 그 코드에서 거꾸로 그린 패키지 다이어그램(실습 5와 비교)

### S14 — AI-native SW공학 (45분)

- **목표:** OOAD의 판단을 Human과 Agent가 어떻게 나누고 검증하는지 AI-native 개발 관점에서 연결한다.
- **Anchor Message:** AI-native 개발에서도 자동화의 품질은 Problem·Model·Boundary·Responsibility에 대한 판단 품질을 넘어서기 어렵다.
- **세부 목차:** 실습 없음 — 실습 1~13의 방식(투입물·프롬프트·점검 항목·보완 (안))을 사람과 에이전트의 역할·맥락·검증으로 되짚어 상세화한다 / OOAD의 Problem·Model·Boundary·Responsibility 및 도메인 모델·온톨로지를 AI context로 전달 / Human·Agent R&R과 확인 지점 / 맥락·제약을 담은 Guardrail, Agent, Harness의 역할과 가이드·센서의 feedback / 에이전트 과제 예: 배송 시작 통보의 중복(S12에서 남긴 질문) / AI-native SW 공학 과정으로 연결(이 세션은 미리 보기이며 깊이는 그 과정이 맡는다)

### 이번 원고와 직접 연결되는 주요 세션 경계

| 세션 | 직접 다루는 판단 | 다음 단계와의 연결 |
|---|---|---|
| S01 | 문제·해결책 구분과 OOAD 전체 지도 | 전문영역은 관계와 질문을 소개하고 S13·S14에서 확장한다 |
| S02 | 액터 목표, 시스템 경계, 이벤트 흐름, 규칙, SSD 초안과 정제된 SSD, 시스템 오퍼레이션과 계약 | 명세서·정제된 SSD·계약이 S03·S04의 입력이 된다. 내부 객체 책임은 결정하지 않는다 |
| S03 | 도메인 개념·속성·관계·제약 | S02 산출물에서 개념을 추출하고, 발견한 것을 명세서·SSD·계약에 되돌린다 |
| S04 | S02의 정제된 SSD·계약에서 출발한 도메인 객체의 상호작용·상태 변화 | S03 개념과 교차검토하고, 발견한 것을 명세서·SSD·계약과 정적 모델에 되돌린다 |
| S06 | 분석 의미를 보존하는 비기계적 설계 전환 | S01 미리보기의 설계 대안을 책임·경계·의존성 관점에서 구체화한다 |
| S07 | 설계 객체의 책임·메시지·협력·계약 | 시스템 수준의 보장을 어떤 객체들이 어떻게 충족할지 설계한다 |
| S12 | 구현·통합·운영 증거로 상위 판단 재검토 | S02의 요구 검증과 추적을 실제 실행 증거에 연결한다 |
| S13 | Architecture·DDD·MSA가 추가로 다루는 전문 판단 | S01의 연결 지도를 품질·도메인 경계·분산 실패의 질문으로 확장한다 |
| S14 | Human·Agent 책임과 실행·검증 구성 | S01의 도메인 의미·온톨로지·역할 구분을 맥락 전달과 피드백에 연결한다 |

S01의 Human·AI 책임 세 영역은 **주도권·최종 책임**의 구분이며, S14의 Guardrail·Agent·Harness는 **실행을 지탱하는 구성과 검증 역할**이다. 같은 분류의 세 항목으로 대응시키지 않는다. 온톨로지는 맥락의 의미를 명시하는 한 수단이며 모든 작업의 필수 기술은 아니다.

같은 계약이라는 용어를 쓰더라도 S02·S04의 시스템 오퍼레이션 계약(오퍼레이션 뒤 도메인 객체의 상태 변화)과 S07의 내부 객체 계약은 구분한다. 학습 순서는 고정 개발 순서를 뜻하지 않으며 새로운 증거가 생기면 앞선 모델도 수정한다.

## 6. 사례·실습 방향

이 과정은 OOAD를 배우는 과정이다. 도메인 때문에 복잡도를 높이지 않는다. 강의의 관통 사례는 주문 시스템이며, S02에서 정한 **세 장면 — 결제한다, 주문을 취소한다, 배송지를 변경한다** — 만 쓴다. 쿠폰·부분 취소·배송 대행사처럼 새 사례를 더하거나, 앞 세션의 교육용 가정에 기대는 가정의 사슬을 만들지 않는다. 필요하면 더 단순하게 한다.
같은 장면을 재사용할 때도 요구·정적 의미·동적 행위·구조적 경계·객체 책임·변경·기술 제약·검증 증거 중
해당 Session이 소유하는 새로운 판단이 분명해야 한다.

실습은 산출물을 완성하면서 그 판단을 드러낸다. 점검 항목은 LLM이 놓친 선택 이유·대안·실패 조건을 질문으로 되돌리고, 보완 (안)은 발견한 것의 변경 영향과 이전 산출물을 다시 열어야 할지를 정한다.

모든 실습은 수강생이 **LLM으로 초안을 만들고 사람이 판단·검증**하는 방식으로 진행한다. 수강생은 실습 슬라이드의 투입물과 프롬프트를 LLM에 주어 초안을 받고, 점검 항목으로 피드백해 산출물을 완성한다. 판단의 기준은 이 과정의 모델링 원칙이며, LLM의 초안이 옳다는 것을 전제하지 않는다(S01의 Human·AI 책임, S14의 AI-native SW공학과 연결).

실습은 강의의 주문 사례와 별개인 **정기배송** 시스템의 신규 개발을 하나의 시나리오로 이어 간다. 장면은 **"정기배송을 신청한다"(결제 포함)** 하나이며, 각 실습의 답 `(안)`이 다음 실습의 입력이다. 실제 수업에서는 수강생이 만든 결과물을 이어 쓴다. 정기배송의 이름과 규칙은 S01 「요구사항 정의서 (안)」이 원천이며, 강의 사례의 공통 식별자와 섞지 않는다.

실습의 결과물은 강의 본문이 형식과 예를 보인 산출물이며 대부분 **다이어그램**이다. 투입물은 필요한 앞 산출물만 가리키고, 새 업무 개념이나 규모를 더하지 않는다.

| 실습 | 세션 | 실습 제목 | 결과물 |
|---|---|---|---|
| 1 | 01. OOAD 개요 | 실습 — 요구사항 정의서 | 요구사항 정의서 |
| 2 | 02. 요구 분석과 유스케이스 | 실습 — 유스케이스 | 유스케이스 다이어그램·명세서, 용어집 |
| 3 | 03. 정적 모델 — 도메인 개념과 관계 | 실습 — 도메인 모델 | 도메인 모델 초안·상세 |
| 4 | 04. 동적 모델 — 상호작용과 상태 | 실습 — 동적 모델 | 시퀀스, 상태 기계 |
| 5 | 05. 구조적 경계와 의존성 | 실습 — 패키지 다이어그램 | 패키지 다이어그램 초안·상세 |
| 6 | 06. 분석 모델에서 설계 모델로 | 실습 — 설계 시퀀스 다이어그램 | 결제한다의 설계 시퀀스 |
| 7 | 07. 책임·협력·계약 | 실습 — CRC와 설계 클래스 다이어그램 | CRC 카드 → 정제된 설계 클래스(계약은 노트) |
| 8 | 08. 변화 대응과 변이 설계 | 실습 — 변경 설계 | 배송 주기 "매월 ○일"을 반영한 설계 클래스 |
| 9 | 09. 설계 대안 평가 | 실습 — 설계 대안 | 대안 둘의 클래스 다이어그램과 고른 이유 한 줄 |
| 10 | 10. 기술 제약과 도메인 의미 보존 | 실습 — 물리 모델 | 도메인 클래스와 물리 모델(테이블) |
| 11 | 11. 통합 설계와 적정 모델링 | 실습 — 통합 | 결제한다를 끝까지 이어 어긋난 곳을 고친 상태 기계·시퀀스, 더 그리지 않을 다이어그램과 이유 |
| 12 | 12. 구현·검증·DevOps와 SW공학 피드백 | 실습 — 피드백 | 실패한 테스트(배송 요청 실패인데 결제가 취소되지 않음, 7a)에서 모델을 거슬러 찾은 뒤 고친 상태 기계·계약 노트 |
| 13 | 13. OOAD에서 전문영역으로 — Architecture · DDD · MSA | 실습 — 아키텍처 스타일 구현 | 간소화한 포트와 어댑터(출력 포트만 — 외부 시스템 약속 둘·저장소 하나, 입력 포트 없음)로 LLM이 생성한 결제한다 샘플 코드, 그 코드에서 거꾸로 그린 패키지 다이어그램(실습 5와 비교) |
| 14 | 14. AI-native SW공학 | — | 실습 없음. 실습 1~13이 이미 LLM 초안 + 사람의 판단·검증이었으므로, 강의에서 그 방식을 AI-native 관점으로 상세화한다 |

사례에서 주어진 사실, 설명을 위한 가정, 아직 확인되지 않은 사항을 구분한다.
같은 사례를 이어 사용할 때는 대상 시스템과 업무 상태·정책의 의미를 유지한다.
전제가 달라지면 해당 예시에서 변경된 전제를 밝힌다. 사례의 정책을 모든 시스템에 적용되는 규칙으로 일반화하지 않는다.

### 재사용 사례의 공통 용어와 전제

| 용어·사례 | S01~S05에서의 의미와 범위 |
|---|---|
| 대상 시스템 | 주문 시스템. 책임은 장바구니, 주문 성립(단가 확정), 주문 상태, 배송지 변경·취소, 외부 시스템과의 조정. 다른 도메인 사례를 사용하는 세션은 그 시스템 경계를 별도로 명시 |
| 지원 액터(외부 시스템) | 결제 시스템 — 결제 승인(동기), 환불(비동기, 완료 통보). 상품 시스템 — 상품 정보·재고 차감(동기). 회계 시스템 — 입금 처리·영수증 발행(비동기). 배송 시스템 — 배송 요청(비동기), 배송지 변경·출고 중단(동기), 배송 시작·완료 통보(비동기) |
| 다른 시스템의 목표 | 배송을 처리한다(배송 시스템), 상품 정보를 관리한다(상품 시스템)는 주문 시스템의 분석 대상이 아니므로 유스케이스로 그리지 않는다. 주문 시스템은 자기 유스케이스 안에서 그 시스템들을 지원 액터로 두고 요청한다 |
| 요구 산출물의 흐름 | S02의 유스케이스 명세서·정제된 SSD·오퍼레이션 계약은 S03·S04의 입력이다. 분석에서 발견한 것은 해당 산출물에 되돌려 보완하며, 보완을 위한 별도 topic·산출물은 만들지 않는다 |
| 개요의 구체 사례(S01) | 주문 O-1 — 펜 2개, 단가 1,000원, 총액 2,000원, 배송지 서울. 시스템 경계 예시는 카드 결제를 쓴다. 외부 연동·저장·비동기 환불은 코드에서 생략하고 업무 규칙을 실행 검증한다 |
| 주문 전체 취소 | 결제 완료·배송 시작 전 주문의 전체 취소 성공 경로. 전액 환불을 교육용 가정으로 명시한 예에 적용 |
| 배송지 변경 | 출고 전 주문의 배송지 변경. 추가 요금·세금·배송 방식 변경이 없는 지역이라는 계약 예시의 가정은 "02. 요구 분석과 유스케이스"의 「45. 시스템 오퍼레이션과 계약」에 한정 |
| 배송 시작 전 / 출고 전 | 각각 취소·배송지 변경의 업무 조건. 두 상태 경계를 자동으로 동의어로 취급하지 않는다. 출고는 배송 시스템이 판단하고, 배송 시작은 배송 시스템의 통보로 주문 시스템이 안다. 실제 사건·상태 관계는 S03·S04에서 확인할 질문 |
| 주문을 관리한다 | 고객의 주문 자료 유지 유스케이스. 배송 현황 조회는 독립 유스케이스(배송 현황을 조회한다). 배송지 변경·주문 취소는 시스템 오퍼레이션과 계약으로 상세화. 배송 완료 후의 반품은 별도 유스케이스(주문을 반품한다)이며 이 과정에서 상세화하지 않음 |
| 흐름과 번호 | 기본 흐름 1 상품을 조회한다 · 2 장바구니에 담는다(1~2 반복) · 3 배송지를 지정한다 · 4 결제한다 · 5 주문 결과를 확인한다. 대안 흐름 1a 주문 취소, 3a 배송지 변경, 5a 주문 내역 확인, 1a.2a 환불 미완료(1a의 2단계에서 갈라짐). 대안 흐름의 단계는 1a.1·1a.2로 쓴다. 성공·실패 모두 대안 흐름이며 예외 흐름을 따로 두지 않는다. 번호는 기본 흐름에서 파생 |
| 시스템 이벤트 | 상품을 조회한다(검색 조건), 장바구니에 담는다(상품, 수량), 배송지를 지정한다(주소), 결제한다(결제 수단), 주문을 취소한다(주문), 배송지를 변경한다(주문, 새 주소). 개요(S01)도 같은 이름을 쓴다 |
| 주문 상태 | 결제 대기 → 결제 완료 → 배송 중 → 배송 완료, 결제 완료 → 취소됨. 결제 전 취소는 확정된 요구가 아니다. S04가 비동기 환불에서 **취소 처리 중**을 발견해 더한다(진화). 코드 값은 결제대기·결제완료·배송중·배송완료·(취소처리중)·취소됨 |
| 판매가 / 단가 | 상품의 판매가(현재 값), 주문 항목의 단가(주문 시점에 확정한 값). 코드 식별자도 같은 이름을 쓴다 |
| 구조적 경계(S05) | 업무 경계 — 고객·장바구니·주문·상품·결제·배송(분석 패키지와 같은 이름). 연동 경계 — 결제 연동·상품 연동·배송 연동·회계 연동(코드 패키지는 결제연동 등 붙여 씀). 요청 인터페이스(게이트웨이 — `PaymentGateway`·`DeliveryGateway` 등)는 업무 패키지에 두고 연동이 구현하며, 연동은 외부 통보를 주문의 사건으로 변환한다. 업무 경계는 연동에 의존하지 않고, 패키지 의존에 순환이 없다 |
| 설계 요소(S05~S07) | 설계 도식과 코드는 영한 용어집의 영문명을 쓴다. `OrderService` — 시스템 이벤트를 받아 주문을 찾고, 맡기고, 저장한다(업무 규칙은 `Order`). `OrderRepository` — 주문을 찾고 저장하는 약속(인터페이스, 저장 기술은 S10). 모두 `order` 패키지에 둔다. 경계를 넘는 연관은 식별자로 잇는다(`OrderItem` → `ProductNumber`, `unitPrice`는 확정 값). 연동은 외부 통보를 주문 번호로 통보 약속 `OrderNotice`(S07, `OrderService`가 실현)에 알린다. 설계 요소는 분석 모델에 역수입하지 않음 |
| 변경 요청(S08) | 교육용 변경 요청 둘 — ① 결제 전 취소 허용(결제대기 → 취소됨, 외부 요청 없음 — 공통 전제에서 "확정되지 않은 요구"였던 것), ② 간편결제 추가(결제 시스템이 둘, `EasyPayAdapter`). ①은 규칙·상태의 변경, ②는 외부 시스템의 변이다. S08 코드에 반영하며 S09 이후의 입력이다 |
| 대안 평가(S09) | 결제 전 취소 규칙의 위치를 평가한다 — 대안 A `OrderService`의 분기, B `Order.cancel`의 상태별 검사, C 상태 패턴. 교육용 결정: B(상태가 여섯이고 전이 규칙이 `Order` 한 곳에 있다). 다시 열 조건: 상태별 규칙이 늘어 `Order`의 분기가 커질 때 C |
| 영속 매핑(S10) | 물리 모델(`OrderRow`·`ItemRow`)은 `persistence`에 두고 도메인은 모른다. 상태는 enum의 **이름**으로, 단가는 **확정 값 그대로** 저장하며, 복원은 생성자를 거쳐 불변 조건을 다시 검사한다. 결제 금액·배송 번호도 주문 행에 저장한다 |
| 통합(S11) | 주문 O-1의 생애 — 결제 → 배송지 변경 → 취소 — 를 전 모델로 추적하고 조립한다. 빈틈: 배송지 변경의 조건 "출고 전"은 배송 시스템만 안다(공통 전제 "배송 시작 전 / 출고 전"에 남긴 질문). 주문 시스템은 출고를 상태로 갖지 않으므로, 계약의 사전조건을 "배송 시스템이 배송지 변경을 수락한다"는 결과로 되돌린다(취소의 출고 중단과 같은 모양) |
| 피드백(S12) | 교육용 가정: 결제 시스템은 환불 완료 통보를 **다시 보낼 수 있다**. 운영의 중복 통보 예외를 요구(외부 시스템 약속)까지 역추적하고, 상태 기계에 취소됨의 자기 전이(환불 완료 통보 → 그대로)를, `Order.onRefundCompleted`의 사전조건에 이미 취소됨을 더한다(멱등). `OrderService`는 찾고·맡기고·저장하는 순서를 `apply` 하나로 리팩터링한다 |
| 전문영역(S13) | 판단의 경계를 다룬다. 실습(아키텍처 스타일 구현)을 위해 간소화한 포트와 어댑터를 이 과정의 패키지로 보인다 — 업무 경계가 약속(출력 포트)을 소유하고 연동·`persistence`가 실현한다(어댑터). 교육용 가정: 가용성 시나리오(결제 시스템 장애 중 취소 접수 99.9%), 맥락(주문·결제·배송·회계 — 연동이 ACL), 서비스로 나누면 출고 중단 요청에 "모른다"가 생겨 예시 상태 "출고 중단 확인 중"이 필요하다(분리 결정 전에는 도입하지 않음) |
| AI-native(S14) | 실습 없음. 강의의 에이전트 과제 예: 배송 시작 통보의 중복(S12에서 남긴 질문). 사람이 요구·상태 기계(배송중에서 배송 시작 통보 → 그대로)·계약을 정하고, 에이전트가 `Order.onDeliveryStarted`와 재현 테스트를 만든다. 하네스의 센서: 회귀 테스트, 의존 규칙 검사(`order`는 `persistence`·연동을 import하지 않음), 과제 테스트. 가드레일·에이전트·하네스는 S01 「AI-native SW공학」의 구분을 따른다. 실습 1~13의 LLM 초안 + 사람 검증을 AI-native 관점으로 되짚는다 |
| 정기배송(실습 사례) | 실습 전용 관통 사례. 이름과 규칙은 S01 「요구사항 정의서 (안)」이 원천이고, 각 실습의 보완 (안)이 진화를 더한다. 다음 배송 취소는 독립 유스케이스(다음 배송을 취소한다). 강의의 주문 사례 식별자와 섞지 않음. AI-native SW 공학 과정이 이 사례를 실습에 다시 쓴다(연계 조정) — 그 과정은 배송지 변경을 언제든 허용하고 회차 상태로 적용을 가르며(이 과정의 조건 [다음 배송 24시간 전]과 다름), 회차 상태 배송중 `IN_DELIVERY`, 정기배송 상태 값 `TERMINATED`·`EXPIRED`, 신청한다 `subscribe`를 더했다 |
| 적정 분석·설계 / 적정 모델링 | 전자는 필요한 분석·설계 판단 전체, 후자는 그 안에서 모델의 추가 가치·비용을 판단하는 활동 |

사례의 성공 계약이 실패·동시성·복구까지 보장한다고 추정하지 않는다. 개별 예시에서 추가한 교육용 가정은 해당 범위에만 적용한다.

위 표가 이 과정의 **공통 식별자의 원천**이다. 세션 원고·다이어그램·예시 코드는 이 이름과 값을 그대로 쓴다. 뒤 세션이 새로 발견한 것(예: 취소 처리 중)은 **진화**로서 그 세션이 발견과 되돌림을 보이고, 되돌린 결과를 이 표에 반영한다. 같은 대상을 다른 이름·규칙으로 쓴 것은 **오류**이며 원천에 맞춰 고친다(`sw-engineering-principles.md`의 「교재에 적용하기」).

### 영한 용어집과 명명 규칙

용어집(Glossary)은 "02. 요구 분석과 유스케이스"에서 정의하고 뒤 세션이 정제한다. **분석**(도메인 모델·분석 시퀀스·상태 기계, S01~S04의 예시 코드)은 한글 용어를, **설계**(S05부터의 패키지·설계 클래스·설계 시퀀스와 코드)는 아래의 영문명을 쓴다. 한 용어에 영문명은 하나이며, 표에 없는 **업무 용어**는 코드에서 먼저 만들지 않고 여기에 먼저 더한다. 업무 의미가 없는 기술 이름(`request`, `api`, 테스트 보조 이름)은 명명 규칙만 따른다.

- **타입**(클래스·인터페이스·enum·record) — 영문 명사, PascalCase(`OrderItem`)
- **필드** — 영문 명사, camelCase(`unitPrice`)
- **메서드** — 업무 동사, camelCase(`cancel()`). 외부·다른 객체가 알리는 사건은 `on`으로 시작한다(`onDeliveryStarted()`)
- **enum 값** — UPPER_SNAKE(`PENDING_PAYMENT`)
- **패키지** — 소문자 단수, 붙여 쓴다(`order`, `paymentadapter`)
