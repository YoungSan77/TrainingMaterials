# 객체지향 분석과 설계 실무 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** 객체지향 분석과 설계 실무 (`ooad`)
- **총 교육시간:** 16시간(기존 계획값; 최종 SA 완성 후 운영 적합성 평가)
- **대상:** 개발자·설계자·분석가
- **선수지식:** 절차적·서비스 중심 코드에서 변경 파급과 책임 분산을 경험

### 과정의 맥락

아래 성숙도·운영 조건은 s01~s05 원고가 전제한 수준에서 정리한 **가정**이다. 사전 설문과 첫 교육 후 피드백으로 확인한다.

| 관점 | 대상의 성숙도 | 확인 방법 |
|---|---|---|
| **도메인** | 주문·결제·배송을 사용자로서 안다. 규칙·상태·외부 시스템 조정은 모른다 | 사전 설문 |
| **기술** | 자바 코드를 읽고 실행한다(`record`·`enum` 포함). 모델링은 UML을 본 적이 있는 정도다 | 사전 설문, S01 코드 예측 |
| **팀워크** | 요구를 문서로 받아 구현한다. 요구 합의·설계 리뷰 경험은 적다 | 사전 설문, S02 실습 |

- **다루는 불확실성** — 업무 불확실성이 중심이다. 관통 사례는 규칙과 상태 경계가 **처음부터 확정되지 않은** 주문을 다룬다(결제 전 취소, 출고와 배송 시작). 기술 불확실성은 외부 시스템의 **동기·비동기**와 기술 제약(S10)으로 한정한다.
- **깊이의 결정** — 성숙도가 낮은 **요구 합의와 모델링**을 명시하고 먼저 검증한다: 판단의 수준 구분, 공통 식별자, 확정·가정·미정의 구분, 모델과 코드·테스트의 연결. 표기는 판단에 필요한 만큼만 다루고, 자바 문법과 프레임워크는 설명하지 않는다.
- **운영 조건** — 가정: 20명 안팎, 개인 실습과 소그룹 비교를 섞는다, 실습 환경은 JDK로 예제를 컴파일·실행할 수 있고 수강생마다 **LLM**(생성형 AI 대화 도구)을 쓸 수 있다.

## 2. 과정 목표

문제영역의 의미를 해결책과 구분해 이해하고, 이를 정적·동적 모델로 명시한 뒤 구조적 경계와
객체의 책임·협력·계약으로 구체화하며, 구현과 검증 evidence로 필요한 상위 판단을 다시 여는
능력을 기른다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. 문제·요구·분석·설계·구현의 서로 다른 판단을 구분한다.
2. 정적·동적 모델로 문제영역의 의미와 행위를 검토한다.
3. 구조적 경계, 책임, 협력, 계약과 의존성 방향을 설계한다.
4. 변경 압력과 기술 제약 아래 대안을 비교하고 도메인 의미를 보존한다.
5. 코드·테스트·통합 evidence로 다시 열 판단 수준을 진단한다.
6. OOAD에서 SW Architecture·DDD·MSA·도메인 모델·온톨로지를 활용하는 AI-native SW공학으로 확장되는 질문을 구분한다.

## 3. 범위와 경계

**Core:** 요구 분석과 유스케이스, 개념적 도메인 모델과 동적 모델, 구조적 경계와 의존성,
분석에서 설계로의 비기계적 전환, 책임·협력·계약, 변화 대응과 변이 설계, 설계 대안 평가,
기술 제약 아래의 의미 보존, 적정 분석·설계와 그 안의 적정 모델링(Modeling Economics), 구현·테스트·DevOps가 만드는
SW공학 feedback.

**Extension:** SW Architecture·DDD·MSA가 OOAD 위에서 추가하는 독립적 판단, 도메인 모델·온톨로지의 의미 공유와 AI 맥락 활용, Human/Agent
R&R 및 맥락을 담은 Guardrail·Agent·Harness의 역할과 피드백을 다루는 AI-native SW공학. 이 구성을 고정된 단계 순서로 보지 않는다.

**Non-scope:** UML 표기 암기, GoF 카탈로그 완주, 특정 framework·ORM·DB·CI·AI 도구 튜토리얼,
그리고 후속 전문영역을 각 전용 과정 수준으로 완결하는 것.

## 4. 과정 전체 판단 원칙

- 개발 절차에서는 통합할 수 있지만 사고에서는 문제와 해결책을 구분한다.
- 모델은 필요한 질문에 답할 만큼만 만들며 분석 개념을 설계·코드로 기계 변환하지 않는다.
- 책임과 추상화는 실제 변경 evidence, 응집도·결합도, 비용과 trade-off로 판단한다.
- 기술적 실현은 구조를 바꿀 수 있지만 도메인 의미를 조용히 재정의해서는 안 된다.
- evidence가 나타난 위치와 결함이 생긴 판단 수준은 다를 수 있다.

세션 시간 합계: 16시간(960분) — 기존 총 교육시간 계획과 일치. 시간 적합성·휴식·실습 운영은 최종 원고 완성 후 평가한다. 작성 중에는 계획 시간이나 topic 수를 근거로 필요한 설명·사례·실습을 축소하지 않는다.

진행은 `문제 이해 → 모델링 → 구조와 객체 설계 → 실현과 feedback → 전문영역과 AI-native 확장`이다.
이는 학습 순서이지 고정된 개발 lifecycle이 아니다.

- **문제 이해:** S01~S02
- **모델링:** S03~S04
- **구조와 객체 설계:** S05~S09
- **실현과 feedback:** S10~S12
- **전문영역과 AI-native 확장:** S13~S14

### S01 — OOAD 개요 (45분)

- **목표:** OOAD가 어떤 판단을 다루는지 전체 지도를 만들고 문제와 해결책을 구분하는 사고를 정립하며, 요구·분석·설계가 코드·테스트로 어떻게 이어지는지 확인한다.
- **Anchor Message:** 개발 절차에서는 통합할 수 있지만, 사고에서는 문제와 해결책을 구분한다.
- **세부 목차:** 재작업·기능 사용률과 범위·가치 판단 / Problem·Requirements·Solution 구분과 이벤트 관점 / 본질적·우연적 어려움 / Analysis와 Design의 역할·진화와 요구·분석·설계·코드의 결정 경계 / 성숙도·불확실성에 따른 접근 / OOAD·UML·Architecture의 구분 / 클래스·SSD·시퀀스·커뮤니케이션·상태 기계 다이어그램과 코드, 요구 예시에서 테스트로 / Responsibility·Boundary·Collaboration 개관과 설계 대안 미리보기 / 분석에서 설계로의 비기계적 전환 / 적정 분석·설계, 북·스트리트 스마트와 KISS·DRY·YAGNI, 피드백과 검증의 배치 / Architecture·DDD·MSA·DevOps·AI로의 확장, DDD·온톨로지·AI-native SW공학의 관계 / 요구사항 명세서 실습(정기배송)

### S02 — 요구 분석과 유스케이스 (1시간 15분)

- **목표:** 요청에서 본질적 요구를 분리하고 액터 목표·이벤트 흐름·시스템 오퍼레이션으로 검토 가능한 요구 모델을 만들며, 품질 요구·검증·추적을 연결해 누락과 가정을 검토한다.
- **Anchor Message:** 유스케이스는 액터의 목표와 가치 있는 결과를 중심으로 시스템의 행위와 책임을 드러낸다.
- **세부 목차:** 문제·요구·요구사항·해결책 구분 / 명세의 한계와 이벤트 중심 요구 정의·반복적 접근·AI 시대의 요구 / 고객·개발자의 업무 지식과 업무·기술 불확실성에 따른 요구 접근법 / 요구 발견·분류·명세 품질과 반복 검증 / 용어집 정의(용어·정의·영문명)와 과정 전체의 이름 원천 / 유스케이스의 위치·수준·작성 절차·목표·액터 / 시스템 컨텍스트와 경계 판단(외부 시스템을 지원 액터로) / 기본·대안·예외 이벤트 흐름과 규칙·정책 / UML 유스케이스 관계와 유스케이스 잘못된 관행(기능 분할·CRUD·화면·기술 요소·시스템 관점·명세 과잉) / 시스템 시퀀스 다이어그램 초안(주 액터·시스템)과 정제된 SSD(외부 시스템·동기·비동기)·시스템 오퍼레이션과 외부 결과 계약·자바 코드와 테스트로의 연결 / 품질 요구·프로토타입 / 사용자 스토리·BDD의 역할 / 요구 관리·추적·사용 증거 / 유스케이스 다이어그램·명세서 실습(정기배송)

### S03 — 정적 모델 — 도메인 개념과 관계 (1시간 30분)

- **목표:** 문제영역의 핵심 개념·속성·관계와 용어의 의미를 정적 모델로 명시한다.
- **Anchor Message:** 정적 모델은 구현과 분리해 문제영역의 개념과 관계를 이해하고 검토하는 모델이다.
- **세부 목차:** 유스케이스 명세서·정제된 SSD·계약을 입력으로 한 개념 추출과 피드백 / 기술 요소 없는 도메인 모델의 위치와 정보공학 데이터 모델(ERD)과의 연계 / Domain Concept·Attribute·Association 식별 / 속성 도메인과 속성 수준 업무 규칙 / 용어와 의미 정렬, 요구 분석에서 정의한 용어집의 정제 / 정적 모델과 네 동적 다이어그램(상태 기계 중심)의 관계 / 클래스 유형과 관계 유형(연관·집합·합성·일반화·의존·실현) / Conceptual Domain Model 초안·상세 작성과 자바 코드·테스트로의 연결 / 정적 모델링의 잘못된 관행 / 시나리오와의 교차검토를 통한 누락·모순 확인 / 도메인 모델 초안·상세 실습(정기배송)

### S04 — 동적 모델 — 상호작용과 상태 (1시간 30분)

- **목표:** 시나리오의 System Operation·상호작용·상태 변화를 동적 모델로 확인하고 정적 모델과 교차검토한다.
- **Anchor Message:** 정적 모델은 무엇이 존재하는지, 동적 모델은 무엇이 일어나는지를 보여주며 서로를 검증한다.
- **세부 목차:** 요구 분석의 정제된 System Sequence·계약을 입력으로, 활동(유스케이스·시스템 간 업무 흐름)과 도메인 객체의 interaction 모델링(시퀀스 중심, 커뮤니케이션 보완) / 사건에 따른 state transition 확인 / 정적 모델과 동적 모델의 누락·모순 교차검토(상태·사건 이름은 용어집) / 필요한 질문에 답할 만큼만 만드는 적정 모델링 / 활동·시퀀스·커뮤니케이션·상태 기계 다이어그램의 자바 코드 매핑과 금지된 전이 테스트 / 시퀀스·상태 기계 실습(정기배송)

### S05 — 구조적 경계와 의존성 (1시간 15분)

- **목표:** 분석 결과를 바탕으로 책임이 놓일 구조적 경계와 의존성 방향을 판단한다.
- **Anchor Message:** 구조적 경계와 의존성은 책임이 놓일 범위와 변화가 전파되는 방향을 정한다.
- **세부 목차:** 클래스를 패키지로 묶는 기준(합성·소유·변경 이유·함께 쓰임·외부 통제)으로 주문 시스템 내부의 경계 후보 도출(시스템 컨텍스트는 S02에서 결정) / 외부 시스템에 대한 의존 방향 / 설계의 이름 — 분석은 한글, 설계는 용어집의 영문명과 명명 규칙 / 패키지 다이어그램으로 경계와 의존성 표현 / 경계 간 책임과 의존성 방향 설정 / 패키지(컴포넌트) 원칙 — 응집 REP·CCP·CRP, 결합 ADP·SDP·SAP — 과 반복·점진적으로 진화하는 구조 / 결합도와 변경 파급의 초기 검토 / 객체 설계 전에 필요한 구조적 제약 명시 / 패키지 다이어그램 초안·상세 실습(정기배송)

### S06 — 분석 모델에서 설계 모델로 (1시간)

- **목표:** 분석 개념을 기계적으로 변환하지 않고 의미를 보존하며 설계 모델로 전환한다.
- **Anchor Message:** 분석 모델의 의미는 보존하고, 설계 요소의 형태는 책임·경계·협력으로 다시 결정한다 — 전환은 판단이지 변환이 아니다.
- **세부 목차:** 분석 개념(개념·속성·관계)과 설계 요소(클래스·상태·메서드)의 대응 관계 확인 / 비기계적 전환에서 지켜야 할 의미 보존 기준(용어집의 영한 대응 포함) / 객체 경계·책임·메시지 관점의 initial design 착수

### S07 — 책임·협력·계약 (1시간 30분)

- **목표:** 객체의 책임과 협력을 정제하고 계약으로 행위의 조건과 보장을 검증한다.
- **Anchor Message:** 객체 설계의 핵심은 데이터를 나누는 것이 아니라 책임을 배치하고 메시지와 계약으로 협력을 만드는 것이다.
- **세부 목차:** Responsibility-Driven Design을 중심으로 책임 후보 도출·배치 / 메시지 기반 협력과 응집도·결합도·정보 은닉 / 클래스 설계 원칙 — SRP(변경 이유 하나), ISP(쓰는 것에만 의존), DIP(추상에 의존), LSP(하위 타입의 계약 준수) / precondition·postcondition·invariant로 계약 명시 / initial design 정제

### S08 — 변화 대응과 변이 설계 (1시간 15분)

- **목표:** 실제 변경 압력이 기존 책임·계약·협력에 주는 영향을 관찰하고 변화를 국소화하는 설계를 만든다.
- **Anchor Message:** 변화 대응은 예상 가능한 모든 변이를 추상화하는 것이 아니라 실제 change pressure를 국소화하는 판단이다.
- **세부 목차:** Change Request로 변경 파급 관찰 / variation point와 stable responsibility 식별 / OCP(확장에 열리고 변경에 닫힌다)로 변이 국소화의 목표 정의 / GRASP의 변화 대응 원칙(Protected Variations, Indirection, Polymorphism 등)을 실제 압력에 선택적으로 적용 / composition·interface·dependency를 이용한 변이 국소화 / 설계 문제와 해결 구조를 Pattern vocabulary와 연결

### S09 — 설계 대안 평가 (1시간 15분)

- **목표:** 동일한 문제에 대한 여러 설계 대안을 change impact·품질·비용·trade-off 관점에서 비교하고 선택한다.
- **Anchor Message:** 좋은 설계는 원칙을 많이 적용한 설계가 아니라 현재의 변화와 품질 요구에 가장 적절한 trade-off를 선택한 설계다.
- **세부 목차:** Change Impact → Cohesion/Coupling → Dependency → Abstraction Cost → SOLID/Pattern → Trade-off의 평가 흐름 / 설계 대안별 장단점 비교 / 선택 근거와 포기한 대안 명시

### S10 — 기술 제약과 도메인 의미 보존 (1시간)

- **목표:** 영속성·프레임워크·외부 시스템 같은 기술 제약에 적응하면서 도메인 의미를 보존한다.
- **Anchor Message:** 기술적 실현은 구조와 표현을 바꿀 수 있어도 도메인 의미를 조용히 바꿔서는 안 된다.
- **세부 목차:** persistence·framework·external API가 설계에 주는 압력 / Domain Model과 Adapter·Infrastructure·Physical Model의 분리 / mapping과 변환에서 발생하는 의미 손실 검토

### S11 — 통합 설계와 적정 모델링 (1시간)

- **목표:** 요구부터 기술 실현까지의 판단을 하나의 사례로 통합하고, 추가 모델링의 가치와 비용을 판단한다.
- **Anchor Message:** 모델은 질문에 답하고 위험을 줄일 때 가치가 있으며, 더 이상 판단을 개선하지 못하면 멈춘다.
- **세부 목차:** 요구→정적·동적 모델→경계→객체 설계→기술 실현의 통합 / 모델별 질문과 evidence 확인 / 모델링·추상화의 추가 비용 대비 위험 감소 판단

### S12 — 구현·검증·DevOps와 SW공학 피드백 (1시간)

- **목표:** 코드·테스트·통합·배포 과정에서 얻은 evidence를 보고 어느 상위 판단을 다시 열어야 하는지 진단한다.
- **Anchor Message:** 문제가 발견된 위치와 그 문제를 만든 판단 수준은 다를 수 있으며, DevOps는 그 feedback을 빠르게 되돌리는 실행 체계다.
- **세부 목차:** Coding·Debugging·Developer Test·TDD·Refactoring의 feedback / IDE·pre-commit·CI의 품질 확인과 통합 evidence / CD·운영 feedback이 설계 판단에 주는 신호 / symptom에서 Requirement·Analysis·Architecture·Design의 원인 수준으로 역추적

### S13 — OOAD에서 전문영역으로 — Architecture · DDD · MSA (1시간)

- **목표:** OOAD에서 다룬 판단과 Architecture·DDD·MSA가 추가로 소유하는 판단을 구분한다.
- **Anchor Message:** OOAD는 전문영역을 대체하지 않으며, 문제 이해와 설계 판단을 제공하는 공통 기반이다.
- **세부 목차:** 구조적 품질속성·trade-off는 SW Architecture로 확장 / Domain Model의 지속적 정제·Ubiquitous Language·Bounded Context는 DDD로 확장 / 분산 경계·통신·운영 실패는 MSA로 확장

### S14 — AI-native SW공학 (45분)

- **목표:** OOAD의 판단을 Human과 Agent가 어떻게 나누고 검증하는지 AI-native 개발 관점에서 연결한다.
- **Anchor Message:** AI-native 개발에서도 자동화의 품질은 Problem·Model·Boundary·Responsibility에 대한 판단 품질을 넘어서기 어렵다.
- **세부 목차:** OOAD의 Problem·Model·Boundary·Responsibility 및 도메인 모델·온톨로지를 AI context로 전달 / Human·Agent R&R / 맥락·제약을 담은 Guardrail, Agent, Harness의 역할과 feedback / 후속 AI-native SW공학으로 handoff

|---|---|---|
| S01 | 문제·해결책 구분과 OOAD 전체 지도 | 전문영역은 관계와 질문을 소개하고 S13·S14에서 확장한다 |
| S02 | 액터 목표, 시스템 컨텍스트와 경계, 이벤트 흐름, 규칙, SSD 초안과 정제된 SSD, 시스템 오퍼레이션의 외부 결과 | 명세서·정제된 SSD·계약이 S03·S04의 입력이 된다. 내부 객체 책임은 결정하지 않는다 |
| S03 | 도메인 개념·속성·관계·제약 | S02 산출물에서 개념을 추출하고, 발견한 것을 명세서·SSD·계약에 되돌린다 |
| S04 | S02의 정제된 SSD·계약에서 출발한 도메인 객체의 상호작용·상태 변화 | S03 개념과 교차검토하고, 발견한 것을 명세서·SSD·계약과 정적 모델에 되돌린다 |
| S06 | 분석 의미를 보존하는 비기계적 설계 전환 | S01 미리보기의 설계 대안을 책임·경계·의존성 관점에서 구체화한다 |
| S07 | 설계 객체의 책임·메시지·협력·계약 | 시스템 수준의 보장을 어떤 객체들이 어떻게 충족할지 설계한다 |
| S12 | 구현·통합·운영 증거로 상위 판단 재검토 | S02의 요구 검증과 추적을 실제 실행 증거에 연결한다 |
| S13 | Architecture·DDD·MSA가 추가로 다루는 전문 판단 | S01의 연결 지도를 품질·도메인 경계·분산 실패의 질문으로 확장한다 |
| S14 | Human·Agent 책임과 실행·검증 구성 | S01의 도메인 의미·온톨로지·역할 구분을 맥락 전달과 피드백에 연결한다 |

S01의 Human·AI 책임 세 영역은 **주도권·최종 책임**의 구분이며, S14의 Guardrail·Agent·Harness는 **실행을 지탱하는 구성과 검증 역할**이다. 같은 분류의 세 항목으로 대응시키지 않는다. 온톨로지는 맥락의 의미를 명시하는 한 수단이며 모든 작업의 필수 기술은 아니다.

같은 계약이라는 용어를 쓰더라도 S02·S04의 시스템 외부 보장과 S07의 내부 객체 계약은 구분한다. 학습 순서는 고정 개발 순서를 뜻하지 않으며 새로운 증거가 생기면 앞선 모델도 수정한다.

## 6. 사례·실습 방향

주문 영역을 기본 관통 사례로 사용하되, 모든 Session에 억지로 동일 사례를 적용하지 않는다.
세션의 판단을 더 분명하게 보여줄 수 있다면 예약·정산·배송·인증·콘텐츠·IoT 등 다른 도메인 사례를 사용할 수 있다.
같은 사례를 재사용할 때도 요구·정적 의미·동적 행위·구조적 경계·객체 책임·변경·기술 제약·검증 evidence 중
해당 Session이 소유하는 새로운 판단이 분명해야 한다.

실습은 산출물을 완성하면서 그 판단을 드러낸다. 점검 항목은 LLM이 놓친 선택 이유·대안·실패 조건을 질문으로 되돌리고, 보완 (안)은 발견한 것의 변경 영향과 이전 산출물을 다시 열어야 할지를 정한다.

모든 실습은 수강생이 **LLM으로 초안을 만들고 사람이 판단·검증**하는 방식으로 진행한다. 수강생은 실습 슬라이드의 투입물과 프롬프트를 LLM에 주어 초안을 받고, 점검 항목으로 피드백해 산출물을 완성한다. 판단의 기준은 이 과정의 모델링 원칙이며, LLM의 초안이 옳다는 것을 전제하지 않는다(S01의 Human·AI 책임, S14의 AI-native SW공학과 연결).

실습은 강의의 주문 사례와 별개인 **정기배송** 시스템의 신규 개발을 하나의 시나리오로 이어 간다. S01 실습의 서비스 개요에서 출발해 요구사항 명세서 → 유스케이스 → 클래스 → 동적 모델 → 패키지로 진행하며, 각 실습의 답 `(안)`이 다음 실습의 입력이다. 실제 수업에서는 수강생이 만든 결과물을 이어 쓴다. 정기배송의 이름과 규칙은 S01 「34. 요구사항 명세서 (안)」이 원천이며, 강의 사례의 공통 식별자와 섞지 않는다.

사례에서 주어진 사실, 설명을 위한 가정, 아직 확인되지 않은 사항을 구분한다.
같은 사례를 이어 사용할 때는 대상 시스템과 업무 상태·정책의 의미를 유지한다.
전제가 달라지면 해당 예시에서 변경된 전제를 밝힌다. 사례의 정책을 모든 시스템에 적용되는 규칙으로 일반화하지 않는다.

### 재사용 사례의 공통 용어와 전제

| 용어·사례 | S01~S05에서의 의미와 범위 |
|---|---|
| 대상 시스템 | 주문 시스템. 책임은 장바구니, 주문 성립(단가 확정), 주문 상태, 배송지 변경·취소, 외부 시스템과의 조정. 다른 도메인 사례를 사용하는 세션은 그 시스템 경계를 별도로 명시 |
| 지원 액터(외부 시스템) | 결제 시스템 — 결제 승인(동기), 환불(비동기, 완료 통보). 상품 시스템 — 상품 정보·재고 차감(동기). 회계 시스템 — 입금 처리·영수증 발행(비동기). 배송 시스템 — 배송 요청(비동기), 배송지 변경·출고 중단(동기), 배송 시작·완료 통보(비동기) |
| 경계 밖 유스케이스 | 배송을 처리한다(배송 시스템, 배송 담당자), 상품 정보를 관리한다(상품 시스템, 관리자). 주문 시스템의 범위가 아니며 다른 시스템의 유스케이스로 표시 |
| 요구 산출물의 흐름 | S02의 유스케이스 명세서·정제된 SSD·오퍼레이션 계약은 S03·S04의 입력이다. 분석에서 발견한 것은 해당 산출물에 되돌려 보완하며, 보완을 위한 별도 topic·산출물은 만들지 않는다 |
| 주문 전체 취소 | 결제 완료·배송 시작 전 주문의 전체 취소 성공 경로. 전액 환불을 교육용 가정으로 명시한 예에 적용 |
| 배송지 변경 | 출고 전 주문의 배송지 변경. 추가 요금·세금·배송 방식 변경이 없는 지역이라는 계약 예시의 가정은 S02 44에 한정 |
| 배송 시작 전 / 출고 전 | 각각 취소·배송지 변경의 업무 조건. 두 상태 경계를 자동으로 동의어로 취급하지 않는다. 출고는 배송 시스템이 판단하고, 배송 시작은 배송 시스템의 통보로 주문 시스템이 안다. 실제 사건·상태 관계는 S03·S04에서 확인할 질문 |
| 주문을 관리한다 | 고객의 주문 자료 유지 유스케이스. 배송 현황 조회는 독립 유스케이스(배송 현황을 조회한다). 배송지 변경·주문 취소는 시스템 오퍼레이션과 계약으로 상세화. 배송 완료 후의 반품은 별도 유스케이스(주문을 반품한다)이며 이 과정에서 상세화하지 않음 |
| 흐름과 번호 | 기본 흐름 1 상품을 조회한다 · 2 장바구니에 담는다(1~2 반복) · 3 배송지를 지정한다 · 4 결제한다 · 5 주문 결과를 확인한다. 대안 흐름 1a 주문 취소, 3a 배송지 변경, 5a 주문 내역 확인. 예외 흐름 1a2a 환불 미완료. 번호는 기본 흐름에서 파생 |
| 시스템 이벤트 | 상품을 조회한다(검색 조건), 장바구니에 담는다(상품, 수량), 배송지를 지정한다(주소), 결제한다(결제 수단), 주문을 취소한다(주문), 배송지를 변경한다(주문, 새 주소). 개요(S01)도 같은 이름을 쓴다 |
| 주문 상태 | 결제 대기 → 결제 완료 → 배송 중 → 배송 완료, 결제 완료 → 취소됨. 결제 전 취소는 확정된 요구가 아니다. S04가 비동기 환불에서 **취소 처리 중**을 발견해 더한다(진화). 코드 값은 결제대기·결제완료·배송중·배송완료·(취소처리중)·취소됨 |
| 판매가 / 단가 | 상품의 판매가(현재 값), 주문 항목의 단가(주문 시점에 확정한 값). 코드 식별자도 같은 이름을 쓴다 |
| 구조적 경계(S05) | 업무 경계 — 고객·장바구니·주문·상품·결제·배송(분석 패키지와 같은 이름). 연동 경계 — 결제 연동·상품 연동·배송 연동·회계 연동(코드 패키지는 결제연동 등 붙여 씀). 요청의 약속(결제 시스템·배송 시스템 등 인터페이스)은 업무 경계가 소유하고 연동이 실현하며, 연동은 외부 통보를 주문의 사건으로 옮긴다. 업무 경계는 연동에 의존하지 않고, 패키지 의존에 순환이 없다 |
| 설계 요소(S05~S06) | 설계 도식과 코드는 영한 용어집의 영문명을 쓴다. `OrderService` — 시스템 이벤트를 받아 주문을 찾고, 맡기고, 저장한다(업무 규칙은 `Order`). `OrderRepository` — 주문을 찾고 저장하는 약속(인터페이스, 저장 기술은 S10). 모두 `order` 패키지에 둔다. 경계를 넘는 연관은 식별자로 잇는다(`OrderItem` → `ProductNumber`, `unitPrice`는 확정 값). 연동은 외부 통보를 주문 번호로 `OrderService`에 알린다. 설계 요소는 분석 모델에 역수입하지 않음 |
| 정기배송(실습 사례) | 실습 전용 관통 사례. 이름과 규칙은 S01 「34. 요구사항 명세서 (안)」이 원천이고, 각 실습의 보완 (안)이 진화를 더한다. 다음 배송 취소는 독립 유스케이스(다음 배송을 취소한다). 강의의 주문 사례 식별자와 섞지 않음 |
| 적정 분석·설계 / 적정 모델링 | 전자는 필요한 분석·설계 판단 전체, 후자는 그 안에서 모델의 추가 가치·비용을 판단하는 활동 |

사례의 성공 계약이 실패·동시성·복구까지 보장한다고 추정하지 않는다. 개별 예시에서 추가한 교육용 가정은 해당 범위에만 적용한다.

위 표가 이 과정의 **공통 식별자의 원천**이다. 세션 원고·다이어그램·예시 코드는 이 이름과 값을 그대로 쓴다. 뒤 세션이 새로 발견한 것(예: 취소 처리 중)은 **진화**로서 그 세션이 발견과 되돌림을 보이고, 되돌린 결과를 이 표에 반영한다. 같은 대상을 다른 이름·규칙으로 쓴 것은 **오류**이며 원천에 맞춰 고친다(`sw-engineering-principles.md`의 「교재에 적용하기」).

### 영한 용어집과 명명 규칙

용어집(Glossary)은 "02. 요구 분석과 유스케이스"에서 정의하고 뒤 세션이 정제한다. **분석**(도메인 모델·분석 시퀀스·상태 기계, S01~S04의 예시 코드)은 한글 용어를, **설계**(S05부터의 패키지·설계 클래스·설계 시퀀스와 코드)는 아래의 영문명을 쓴다. 한 용어에 영문명은 하나이며, 표에 없는 **업무 용어**는 코드에서 먼저 만들지 않고 여기에 먼저 더한다. 업무 의미가 없는 기술 이름(`request`, `api`, 테스트 보조 이름)은 명명 규칙만 따른다.

- **타입**(클래스·인터페이스·enum·record) — 영문 명사, PascalCase(`OrderItem`)
- **필드** — 영문 명사, camelCase(`unitPrice`)
- **메서드** — 업무 동사, camelCase(`cancel()`). 외부·다른 객체가 알리는 사건은 `on`으로 시작한다(`onDeliveryStarted()`)
- **enum 값** — UPPER_SNAKE(`PENDING_PAYMENT`)
- **패키지** — 소문자 단수, 붙여 쓴다(`order`, `paymentadapter`)
