# 객체지향 분석과 설계 실무 — Course Design

이 문서는 과정 수준의 목표, 세션 구조, 시간 배분과 Anchor Message를 정의한다.

## 1. 과정 정보

- **과정명:** 객체지향 분석과 설계 실무 (`ooad`)
- **총 교육시간:** 16시간
- **대상:** 개발자·설계자·분석가
- **선수지식:** 절차적·서비스 중심 코드에서 변경 파급과 책임 분산을 경험

## 2. 과정 목표

문제영역의 의미를 해결책과 구분해 이해하고, 이를 구조적 경계·객체의 책임·협력·계약으로
구체화하며, 구현과 검증 evidence로 필요한 상위 판단을 다시 여는 능력을 기른다.

과정 종료 시 학습자는 다음을 할 수 있어야 한다.

1. 문제·요구·분석·설계·구현의 서로 다른 판단을 구분한다.
2. 정적·동적 모델로 문제영역의 의미와 행위를 검토한다.
3. 구조적 경계, 책임, 협력, 계약과 의존성 방향을 설계한다.
4. 변경 압력과 기술 제약 아래 대안을 비교하고 도메인 의미를 보존한다.
5. 코드·테스트·통합 evidence로 다시 열 판단 수준을 진단한다.
6. OOAD에서 SW Architecture·DDD·MSA·AI-native SW공학으로 확장되는 질문을 구분한다.

## 3. 범위와 경계

**Core:** 요구 발견과 유스케이스, 개념적 도메인 모델과 동적 모델, 구조적 경계와 의존성 방향,
분석에서 설계로의 비기계적 전환, 책임·협력·계약, 변화·변이 대응, 설계 대안 평가, 기술적
실현과 의미 보존, Modeling Economics, 개발·테스트·CI/CD가 만드는 SW공학 feedback.

**Extension:** SW Architecture·DDD·MSA가 OOAD 위에서 추가하는 독립적 판단과, Human/Agent
R&R 및 Context·Guardrail·Agent·Harness로 이어지는 AI-native SW공학.

**Non-scope:** UML 표기 암기, GoF 카탈로그 완주, 특정 framework·ORM·DB·CI·AI 도구 튜토리얼,
그리고 후속 전문영역을 각 전용 과정 수준으로 완결하는 것.

## 4. 과정 전체 판단 원칙

- 개발 절차에서는 통합할 수 있지만 사고에서는 문제와 해결책을 구분한다.
- 모델은 필요한 질문에 답할 만큼만 만들며 분석 개념을 설계·코드로 기계 변환하지 않는다.
- 책임과 추상화는 실제 변경 evidence, 응집도·결합도, 비용과 trade-off로 판단한다.
- 기술적 실현은 구조를 바꿀 수 있지만 도메인 의미를 조용히 재정의해서는 안 된다.
- evidence가 나타난 위치와 결함이 생긴 판단 수준은 다를 수 있다.

## 5. Session 구조 (14개, 총 16시간)

| S03 | 개념적 도메인 모델 — 정적 의미 | 1시간 30분 |
| S04 | 동적 모델 — 행동·상호작용·상태 | 1시간 30분 |
| S05 | 구조적 경계와 의존성 방향 | 1시간 15분 |
| S06 | 분석 모델에서 설계 모델로 | 1시간 |
| S07 | 책임·협력·계약 | 1시간 30분 |
| S08 | 변화와 변이 대응 | 1시간 15분 |
| S09 | 설계 대안 평가 | 1시간 15분 |
| S10 | 기술적 실현과 의미 보존 | 1시간 |

세션 시간 합계: 16시간(960분) — 총 교육시간과 일치.

진행은 `문제 이해 → 모델링 → 구조와 객체 설계 → 실현과 feedback → 전문영역과 AI-native 확장`이다.
이는 학습 순서이지 고정된 개발 lifecycle이 아니다.

### S01 — OOAD와 설계 판단 (45분)

- **목표:** 판단 프레임을 세우고 문제와 해결책을 구분하는 사고를 정립한다.
- **Anchor Message:** 개발 절차에서는 통합할 수 있지만, 사고에서는 문제와 해결책을 구분한다.
- **세부 목차:** 절차적 변경 파급 사례로 본 책임 분산 문제 / Analysis를 phase가 아닌 사고 활동으로 재정의 / 과정 전체 판단 원칙 개관

### S02 — 요구 발견과 유스케이스 (1시간 15분)

- **목표:** 요구를 분석 가능한 행위와 시나리오로 구조화한다.
- **Anchor Message:** 유스케이스는 액터에게 관찰 가능한 가치를 만드는 행위 시퀀스를 기술한다.
- **세부 목차:** 요구에서 essential problem과 premature solution detail 분리 / 액터·시나리오·System Operation 관점의 유스케이스 구조화 / Problem Understanding을 검토 가능한 형태로 명시

### S03 — 개념적 도메인 모델 — 정적 의미 (1시간 30분)

- **목표:** 문제영역의 개념·속성·관계를 정적 모델로 명시한다.
- **Anchor Message:** 정적 모델은 문제영역의 개념과 관계를 코드보다 먼저 이해하기 위한 도구다.
- **세부 목차:** 도메인 개념·속성·관계 식별 / 용어집과 Conceptual Domain Model 작성 / 정적 모델이 이후 구조 설계에 주는 제약 확인

### S04 — 동적 모델 — 행동·상호작용·상태 (1시간 30분)

- **목표:** 사건·협력·상태 변화를 동적 모델로 확인하고 정적 모델과 교차검토한다.
- **Anchor Message:** 정적 모델과 동적 모델은 같은 문제 이해를 보완하는 두 관점이다.
- **세부 목차:** 시나리오별 interaction과 state change 추출 / 정적 모델 대비 누락·모순 검토 / just-enough 모델링 기준(필요한 질문에 답할 만큼만)

### S05 — 구조적 경계와 의존성 방향 (1시간 15분)

- **목표:** 책임이 놓일 구조적 경계와 의존성 방향을 판단한다.
- **Anchor Message:** 구조 경계는 책임이 어디 있어야 하는지를 먼저 정하는 판단이다.
- **세부 목차:** 분석 결과에서 구조적 경계 후보 도출 / 의존성 방향과 결합도 초기 판단 / 경계 판단이 이후 설계 전환에 미치는 영향

### S06 — 분석 모델에서 설계 모델로 (1시간)

- **목표:** 분석 개념을 기계적으로 변환하지 않고 의미를 보존하며 설계 모델로 전환한다.
- **Anchor Message:** 분석 모델을 설계로 그대로 옮기지 않는다 — 전환은 판단이지 변환이 아니다.
- **세부 목차:** 분석 개념(개념·속성·관계)과 설계 요소(클래스·상태·메서드)의 대응 관계 확인 / 비기계적 전환에서 지켜야 할 의미 보존 기준 / 객체 경계·책임·메시지 관점의 initial design 착수

### S07 — 책임·협력·계약 (1시간 30분)

- **목표:** 객체 책임과 협력을 정제하고 계약으로 검증한다.
- **Anchor Message:** 메시지를 보내기 전에 무엇이 참이어야 하고 무엇을 보장하는지 계약으로 먼저 정한다.
- **세부 목차:** precondition·postcondition·invariant로 객체 계약 명시 / information expert·응집도·결합도·정보 은닉으로 책임 배치 정제 / Responsibility-Driven Design 관점에서 initial design을 refined design으로 검증

### S08 — 변화와 변이 대응 (1시간 15분)

- **목표:** 실제 변경 압력이 기존 계약과 협력에 주는 영향을 관찰하고 국소화한다.
- **Anchor Message:** 변화 대응 원칙은 실제 change pressure가 있을 때만 적용한다.
- **세부 목차:** 신규 change request가 기존 계약에 주는 압력 관찰 / composition·interface·dependency 등 변이 대응 원칙의 압력 기반 적용 / 설계 문제와 해결 구조를 먼저 이해한 뒤 Pattern vocabulary와 연결

### S09 — 설계 대안 평가 (1시간 15분)

- **목표:** 여러 설계 대안을 change impact와 trade-off 관점에서 비교하고 선택한다.
- **Anchor Message:** 대안은 원칙 이름이 아니라 change impact·비용·trade-off로 비교한다.
- **세부 목차:** Change Impact → Cohesion/Coupling → Dependency → Abstraction Cost → SOLID/Pattern → Trade-off 순서의 판단 흐름 / 설계 대안별 비용·효과 비교 / 선택 근거를 명시하는 평가 기준

### S10 — 기술적 실현과 의미 보존 (1시간)

- **목표:** 기술 제약에 적응하면서 도메인 의미를 조용히 재정의하지 않는다.
- **Anchor Message:** 기술적 실현은 구조를 바꿀 수 있어도 도메인 의미를 바꿔서는 안 된다.
- **세부 목차:** 영속성·프레임워크 등 기술 제약이 설계에 주는 압력 / 기술 구현 결정과 도메인 의미 결정의 분리 / 의미 손실 여부를 판단하는 기준

### S11 — 통합 설계와 Modeling Economics (1시간)

- **목표:** 지금까지의 판단을 통합하고, 어디서 모델링을 멈출지 판단한다.
- **Anchor Message:** 모든 것을 모델링하는 것 자체가 목적이 되면 그 모델은 실질적 가치가 없다.
- **세부 목차:** 요구부터 설계까지의 판단을 하나의 사례로 통합 / 필요한 질문에 필요한 모델만 남기는 기준 / 과도한 표기·추상화의 비용 대비 효과 판단

### S12 — 개발·테스트·CI/CD와 SW공학 피드백 (1시간)

- **목표:** 실행 evidence를 보고 어느 판단 수준을 다시 열지 구분한다.
- **Anchor Message:** 문제가 나타난 위치와 그 문제를 일으킨 판단 수준은 다를 수 있다.
- **세부 목차:** 개발 중 Debugging·Developer Test·TDD·Refactoring과 Commit 이후 통합 검증의 구분 / CI/CD가 반복 확인하는 품질 관점 / evidence 기반으로 Requirement·Analysis·Architecture·Design 재검토 여부 판단

### S13 — SW Architecture · DDD · MSA로의 확장 (1시간)

- **목표:** 세 전문영역이 OOAD 위에서 추가로 소유하는 독립적 판단을 구분한다.
- **Anchor Message:** OOAD는 세 전문영역의 대체물이 아니라 그 위에서 시작하는 출발점이다.
- **세부 목차:** 구조적 품질·trade-off 판단은 SW Architecture로 이어짐 / 도메인 모델의 지속적 정제·Ubiquitous Language·경계는 DDD로 이어짐 / 분산 경계와 운영 실패는 MSA로 이어짐

### S14 — AI-native SW공학 (45분)

- **목표:** Human과 Agent의 역할 분담을 포함한 다음 단계 개발 방식을 확인한다.
- **Anchor Message:** AI-native 개발도 OOAD가 만든 문제 이해와 책임 판단 위에서 시작한다.
- **세부 목차:** OOAD 판단(문제/모델/경계/책임)이 AI-native 맥락에서도 전제가 됨 / Human·Agent 역할 분담 개관 / Context·Guardrail·Harness 등 다음 수준 개발 방식으로의 handoff

## 6. 사례·실습 방향

주문 영역을 관통 사례로 사용한다. 같은 문제를 요구·정적 의미·동적 행위·구조적 경계·객체
책임·변경·기술 제약·검증 evidence 관점에서 다시 보되, 각 Session은 새 판단을 소유해야 한다.
실습은 산출물 작성보다 선택 이유, 실패 조건, 다시 열 판단 수준을 드러내야 한다.
