# DDD 실습 설계

## 위상
- 형식 복제, 그러나 **코드 대면 대신 모델 대면**이 (a)의 기본. 이 과정의 값은 코드가 아니라 손으로 하는 경계 판단이라서다.
- 코드는 최소(경계 판단을 코드로 확인할 때만).

## 렌즈 차이
- OOAD·아키텍처: 코드가 중심 대상.
- DDD: **모델(도표·스토밍 결과·경계선)이 중심 대상.** 코드는 판단의 결과 확인용.

## 부 1 · 이벤트 스토밍
- (a) 모델 대면 = **좋은 스토밍 벽 vs 나쁜 스토밍 벽** 비교. 이벤트가 빠지거나 순서가 꼬인 벽 vs 흐름이 드러난 벽. "무엇이 빠졌나".
- 통짜(b) = Order 전체 흐름(주문→결제→배송→취소)을 팀이 벽에 세운다. 핫스팟(모호·충돌) 표시.

## 부 2 · 애그리거트 경계 설계 — 핵심 실습

### (a) 모델 대조 · 경계가 맞나

**쌍 D-1 · 경계 너무 큼 vs 맞음**
- 대조: `Order`가 결제·재고·배송을 다 품은 거대 애그리거트 vs `Order`(주문 라인만) + 협력자.
- 물음: 큰 쪽에서 두 사용자가 동시에 다른 라인을 바꾸면? (경합) 작은 쪽에서 "재고 차감"은 누가? (교차 규칙 비용)

**쌍 D-2 · 불변식이 경계를 정한다**
- 대조: R1·R4(주문 내부 불변식)는 Order 안에 → Order 애그리거트. "재고 ≥ 주문량"은 Order·Inventory에 걸침 → 애그리거트 밖(최종 일관성).
- 물음: 이 불변식이 **한 트랜잭션에 즉시** 지켜져야 하나, **결과적으로** 지켜지면 되나. 그 답이 경계다.

### (b) 통짜 · 트레이드오프 판단
- 하나의 경계안을 놓고 **큰 애그리거트/작은 애그리거트** 두 설계를 나란히. 각각의 얻음/잃음을 표로.
- 코드 확인(최소): 작은 애그리거트에서 교차 규칙이 Domain Service로 빠지는 한 조각만.

## 부 3 · 컨텍스트 매핑
- (a) = 컨텍스트 경계가 뭉개진 지도 vs 관계(고객-공급자·ACL)가 명시된 지도. 
- **매핑만. 서비스로 자르지 않는다(MSA 소유).**

## 코더 층 (얕게)
- 경계 판단을 코드로 확인할 때만. 예 — 결정한 애그리거트 루트에 불변식 메서드 하나 짜보기.
- 이 과정은 코더도 **모델 판단**이 주. 코드는 판단의 사후 확인.

## 겹침 방지
- 전술 문법(OOAD)·서비스 분해(MSA)는 실습에서도 안 건드린다. 여기 실습의 산출 = **경계 판단 근거**.
