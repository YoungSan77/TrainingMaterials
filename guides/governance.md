# 교재 제작 Governance

이 문서는 단계별 소유권, 승인, 변경과 이관을 정한다. 교육 원칙은 `guides/sw-engineering-principles.md`, 저장소의 실제 센서와 훅은 `guides/agentic-repository-guide.md`가 관리한다.

## 단계와 정본

| 단계 | 승인 입력 | 정본과 소유권 | 단계 계약 |
|---|---|---|---|
| Course Design | 사용자 의도, 과정 맥락, 공통 원칙과 출처 | `courses/<course>/course-design.md`의 목적·역량·범위·핵심 주장·필수 성과와 실패 조건, 과정 공통 용어·사례 전제, 총시간과 운영 제약 | `guides/course-design-guide.md` |
| Curriculum / Session Architecture | 승인 Course Design | `courses/<course>/curriculum.md`의 세션 ID·이름·순서·시간·역할·선수 관계·연결, 과정 전체 중복·누락 검토 | `guides/curriculum-dd-guide.md` |
| Session DD | 승인 Session Architecture, 해당 Course Design, 출처와 확정된 사례 입력 | `courses/<course>/sessions/sNN-detailed-design.md`의 세션 거버닝 메시지·판단 질문·핵심 주장·교수 순서·정의·근거·사례·실습 설계 | `guides/curriculum-dd-guide.md` |
| Deck Authoring | 승인 DD, 통합 승인 Curriculum과 연결된 자료 | `courses/<course>/sessions/sNN.md`의 슬라이드 문구·표현·학습자 자료·강사 노트 | `guides/session-authoring-guide.md` |
| Production | 승인 Deck, 필요한 자산과 제작 계약 | PPTX와 QA 증거. Renderer·템플릿·테스트가 변환과 측정을 소유 | `guides/production-guide.md` |

경로는 신규·전환 작업의 기본 위치다. 승인된 과정에서 다른 경로가 필요하면 기존 과정 기록에 실제 위치를 남긴다. 한 결정은 표의 소유자가 한 곳에서 관리한다. 소비 산출물은 식별자나 문서·절로 원천을 가리키고 필요한 적용만 적는다. 강의에 필요한 정의의 표시와 실제 응답의 검증된 발췌는 원천의 사용이다. 별도 storyboard·slide-plan·IR·승인 등록부는 필수 산출물이 아니다.

## 책임과 승인

- 실행 에이전트는 저장소의 지침과 승인 입력을 읽고, 위임된 범위에서 해당 단계의 산출물을 생성·수정하고 검증 증거를 남긴다. 이 역할은 특정 제품에 종속되지 않는다 — 현재 주 실행 도구는 Claude Code이고 Codex는 선택적으로 쓴다. 단계·승인·검사 체계는 어느 도구가 실행해도 같다. 작성 권한은 승인 권한과 구분한다. Human은 목적·의미·주요 선택, 단계별 승인과 최종 PPTX 수락을 담당한다. ChatGPT의 자유 대화는 설계 토의·대안 검토·독립 평가에 활용한다. 토의 결과는 검토 자료이며 승인된 저장소 기준의 직접 변경 권한을 부여하지 않는다.
- Course Design 승인 → Session Architecture 승인 → 세션 DD 순차 승인 → 전체 Curriculum 통합 승인 → 대상 Deck 승인 → 제작 검증과 Human의 PPTX 수락 순이다. Architecture 승인 후 첫 DD를 작성하고, 해당 DD 승인 후 다음 DD로 진행한다. 통합 검토를 시작할 때 DD를 모아 중복·연결·시간을 점검한다. 승인된 DD의 의미가 바뀌면 영향을 받는 DD만 재승인한다. Deck은 통합 승인된 Curriculum과 대상 DD를 입력으로 사용한다.
- 리뷰용 초안·검사본은 상태와 목적을 표시한다. 승인 전의 임시 확인은 단계 진입이나 배포 승인이 아니다. 필수 가드레일이 없거나 충돌하면 해당 항목과 필요한 결정을 남긴다.

## 단계 시작 계약

1. 실행자는 Governance와 해당 단계 지침, 적용되는 과정별 규칙을 읽고 대상 단계·산출물 경로를 확인한다.
2. 해당 단계의 승인된 상위 산출물을 직접 읽고 경로·승인 근거·버전을 대조한다. 커밋이나 파일 SHA-256으로 버전을 식별한다. Course Design을 새로 시작할 때는 사용자 의도와 적용 공통 원칙을 기준 입력으로 삼고, 기존 과정 개정은 현재 승인 Course Design도 확인한다.
3. 사용자가 허용한 변경의 파일·필드·의미 범위와 보존 대상을 확인한다. 시작 근거와 필요한 검사 범위를 기존 작업 기록에 연결한다. 필수 입력이나 승인 근거가 없거나 허용 범위와 충돌하면 영향받는 변경을 보류하고 필요한 판단을 보고한다.

## 변경 통제와 기준선

1. 변경 전 대상, 승인 입력 버전, 부모 단계와 승인된 범위를 확인한다. 서술이나 표시 수정과 목적·관계·순서·판정 조건 변경을 구별한다.
2. 부분 피드백은 해당 결함과 같은 유형을 확인하는 근거로 삼는다. 미지적 부분을 다시 설계할 권한으로 확대하지 않는다. 같은 결함이 승인 범위 밖에서도 발견되면 별도 영향으로 기록한다.
3. 결함의 소유 단계, 근거, 최소 변경안, 영향을 받는 하위 산출물과 검사를 보고한다. 상위 의미나 승인 범위가 바뀌면 해당 소유자의 Human 재승인을 받은 뒤 하위 변경을 진행한다. 배치 문제는 Production, 표현 문제는 Deck, 교수 의미는 DD, 세션 간 순서·시간은 Curriculum, 과정 범위·공통 값은 Course Design으로 환류한다.
4. 기존 Git 이력과 과정의 `checks/` 기록에 기준선 경로와 버전(커밋 또는 변경 중인 파일의 SHA-256), 승인 범위·근거, 변경 사유와 영향, 검사 결과를 남긴다. 기존 기준선은 보존하고 이번 수정에서 재검증한 산출물을 구분한다. 커밋되지 않은 승인본도 승인 증거와 파일 해시로 식별할 수 있다. 승인 여부를 경로나 파일 존재만으로 추정하지 않는다.

## 검사 및 전환

- 검사마다 **필수 여부**, **자동 구현 및 적용 범위**, **실행 증거와 판정**을 구분한다. 필수 여부는 단계 지침과 승인된 과정별 계약이 정한다. 자동화 후보 목록이 구현 목록을 대신하지 않는다. 자동 검사가 미구현·미실행이거나 증거가 부족하면 자동 판정은 `NOT VERIFIED`로 남긴다. 확인된 위반은 `FAIL`, 실행 증거로 충족한 범위만 `PASS`다.
- 하네스는 차이·실패 위치·근거를 보고하며 교육 내용을 생성·수정하거나 승인 범위를 넓히지 않는다. 자동화가 없는 필수 항목의 동등한 수동 대조는 별도 증거와 판정으로 기록한다. 수동 판정으로 자동 검사 상태를 바꾸지 않는다. 필수 자동 검사를 계약이 명시한 경우 그 검사 자체를 수행해야 게이트를 충족한다. 자동 결과, 의미 검토, Human 승인과 제작 검증은 각각 기록한다.
- 기존 과정은 승인된 산출물을 기준선으로 보존한다. 과거 작업은 소급 재승인 대상으로 삼지 않는다. 전환과 신규 의미 변경은 해당 소유 단계의 승인부터 진행한다. 전환 목록은 교육 내용이나 승인 상태를 대신하지 않는다.
