# SW Engineering Principles

## 목적

모든 과정의 Course Design과 Session Authoring이 따르는 **SW 공학의 기본 원칙**이다. 교재는 요구사항에서 코드·테스트까지 SW 공학이 어떻게 적용되어야 하는지를 이 원칙으로 설명하고 스스로도 이 원칙을 지킨다.

- 이 문서는 "왜"를 정한다. "어떻게"는 `course-design-guide.md`, `session-authoring-guide.md`, `production-guide.md`가 정한다. 같은 원칙을 세 지침에 되풀이해 쓰지 않고 이 문서를 참조한다.
- 원칙의 설명·사례·다이어그램·코드는 참조 자료 `references/sw-engineering-approach/sw-engineering-approach.md`(슬라이드 `sw-engineering-approach.pptx`)에 있다. 참조 자료는 규칙이 아니며, 규칙은 이 문서가 정한다.

## 1. 결정과 검증

- SW 공학은 산출물과 절차가 아니라 **무엇을 언제 결정하고 어떻게 검증하는가**를 다룬다.
- 요구·분석·설계·코드는 서로 다른 결정을 내린다.

| 관점 | 질문 | 결정 | 가까운 검증 |
|---|---|---|---|
| 요구 | 누가 어떤 결과를 왜 원하는가? | 의도, 범위, 외부 결과 | 수용·거절 예시 |
| 분석 | 그 결과가 업무에서 무엇을 뜻하는가? | 개념·관계·규칙·사건·상태·업무 상호작용 | 시나리오와 모델의 교차검토 |
| 설계 | 어떤 소프트웨어 구조와 협력으로 실현하는가? | 아키텍처·책임·협력·계약·기술적 결정 | 대안·실패 경로·변경 영향 |
| 코드 | 어떻게 실행하는가? | 실행 로직, 기술 구체화 | 정적 검사, 실행 테스트 |

- 단계를 나누는 것이 문제가 아니라 **앞 결정을 닫아 두고 되돌아가지 못하는 것**이 문제다. 증거가 나오면 원인이 된 결정으로 되돌린다. 발견한 위치와 원인이 된 결정의 수준은 다를 수 있다.
- "분석이 끝났다"는 다음 작업자가 중요한 의미를 **추측하지 않아도 되는** 상태다.

### 도메인 모델·설계 모델과 정적·동적 관점

다음은 이 저장소가 일관되게 사용하는 용례다. **분석·설계는 결정의 대상**, **정적·동적은 모델을 보는 관점**이다. 두 구분을 한 줄의 단계 목록으로 섞지 않는다.

- **도메인 모델**은 문제영역의 업무 의미를 설명하는 분석 모델이다. 개념·관계·속성·규칙뿐 아니라 사건·상태·전이·업무 상호작용을 포함한다. **정적 관점과 동적 관점이 함께 하나의 도메인 모델을 이루고 서로를 검증한다.** 도메인 모델을 클래스 그림 하나와 동일시하지 않는다.
- **설계 모델**은 요구사항과 도메인 모델의 의미를 소프트웨어로 실현할 결정을 담는다. 책임·협력·인터페이스와 함께 아키텍처, 외부 연동, 영속, 동시성·트랜잭션 등 필요한 기술적 결정을 더한다. 업무 개념의 이름이나 정책을 조용히 바꾸지 않으며, 분석 그림에 기술 박스만 덧붙이는 기계적 변환으로 설명하지 않는다.
- **아키텍처**는 설계에 포함된다. 시스템의 주요 구조·경계·의존성과 실행·배포 방식 등 품질과 변경에 큰 영향을 주는 결정을 다룬다. 정적인 패키지 그림에만 한정하지 않으며, 아키텍처와 객체 설계를 각각 가르치는 세션도 모두 설계의 서로 다른 범위다.

| 결정의 대상 | 정적 관점 — 무엇이 어떤 관계로 존재하는가 | 동적 관점 — 무엇이 일어날 때 어떻게 변하는가 |
|---|---|---|
| **분석: 도메인 모델** | 업무 개념·관계·속성·불변 조건 | 업무 사건·상태·전이·업무 상호작용 |
| **설계: 설계 모델** | 소프트웨어 클래스·인터페이스·구성요소·의존 구조 | 소프트웨어 객체의 협력·호출·제어·연동·실패 처리 |

- **정적 모델·동적 모델**은 문맥의 모델이 가진 두 관점을 짧게 부르는 말이다. 처음에는 무엇의 관점인지 밝힌다. 「도메인 모델의 정적 관점」·「도메인 모델의 동적 관점」·「설계 모델의 정적 관점」·「설계 모델의 동적 관점」으로 구별한다. 정적은 분석, 동적은 설계라는 대응을 만들지 않는다.
- **개념 모델**은 업무를 구현 기술과 분리해 개념 수준에서 설명한다는 문맥에서 쓴다. 도메인 모델과 나란히 새로 만드는 단계·필수 산출물이 아니다. 원전이 도메인 모델의 정적 개념 구조를 가리킬 때는 「도메인 모델의 정적 구조를 표현한 개념 모델」로 범위를 밝힌다. 개념 모델이라는 일반 용어의 모든 용례를 도메인 모델과 동일시하지 않는다.
- **다이어그램**은 모델을 표현하는 표기다. 클래스 다이어그램은 도메인 개념의 정적 구조와 소프트웨어 클래스의 설계 구조에 모두 쓸 수 있다. 시퀀스·상태 기계도 어떤 대상을 어떤 수준에서 설명하는지에 따라 분석 또는 설계를 표현한다. 도식의 종류만으로 결정 수준을 판정하지 않는다.
- **온톨로지**는 개념과 관계의 의미를 명시한다는 관심사에서 도메인 모델과 연결해 설명한다. 도메인 모델의 다음 단계, 모든 도메인 모델과 같은 것, 별도 필수 파일로 일반화하지 않는다.
- **모델·관점·다이어그램·문서**를 구별한다. 하나의 모델을 여러 관점과 그림으로 표현할 수 있고, 그것을 한 문서나 여러 파일에 둘 수 있다. 개념 수나 그림 수만큼 모델·산출물을 늘리지 않는다.
- **요구사항은 필요한 결과와 조건을 정하고, 도메인 모델은 그 업무 의미를 밝히고, 설계 모델은 실현 방법을 결정한다.** 소스 코드와 테스트로 이 의미와 실현을 확인하고, 모순이 나오면 원인이 된 결정으로 되돌린다. 작은 작업에서는 모델을 별도 문서로 남기지 않을 수 있어도 이러한 판단이 사라지는 것은 아니다(7절).
- **원전과 공통 용례를 구분한다.** 원전이 `Domain Model`을 정적 개념도라는 좁은 뜻으로 쓰면 그 인용·정의의 범위를 그대로 밝힌다. 이 저장소가 정적·동적 관점을 포함해 쓰기로 한 용례를 원전 저자의 정의인 것처럼 귀속하지 않는다. 원전 문장을 넓은 뜻에 맞춰 고쳐 쓰지 않는다.

## 2. 이벤트 관점

- 고객 관점의 요구는 **이벤트 관점으로 수렴**한다. 이벤트 반응 목록, 유스케이스, 사용자 이야기, 도메인 이벤트는 모두 "무엇이 일어나면 어떤 결과가 필요한가"를 본다.
- 많은 문제의 본질은 **관점의 혼합**이다. 화면·데이터·기술·해결책을 요구와 한 문장에 섞지 않는다. 먼저 이벤트 하나로 합의하고, 화면·데이터·기술은 그 뒤에 각자의 결정으로 다룬다.

## 3. 성숙도와 불확실성

- 접근법은 **고객·개발자의 도메인 지식, 기술 숙련, 팀워크의 성숙도**에 따라 달라진다. 성숙도가 낮은 관점일수록 더 명시하고 먼저 검증한다.
- 업무·기술의 **불확실성**이 반복의 주기와 검증 대상을 정한다. 폭포수, 반복·점진(I&I), 애자일, 디자인 씽킹, Lean Startup, Lean UX는 이름이 아니라 불확실성을 줄이는 방식으로 고른다.
- 모든 프로세스는 **결정–검증–되돌림**을 서로 다른 주기로 운영한다. 이름을 따르는 것보다 이 흐름이 살아 있는지가 중요하다.

## 4. 작게 끝까지

- 작은 범위를 **요구부터 코드·테스트까지 끝까지** 관통하고, 반복하며 관계·예외·협력·기술 제약·변경을 하나씩 더한다.
- 다이어그램은 **질문에 답할 때만** 그린다. 같은 정보를 반복하는 다이어그램은 생략한다.
- 다이어그램은 코드로 옮겨 적는 설계도가 아니다. 분석은 의미를 밝히고, 설계는 그 의미를 지킬 책임과 협력을 새로 판단한다.
- 요구의 **수용·거절 예시가 곧 테스트**다. 코드의 예외나 반환값이 미확정 정책을 대신 정하지 않는다.

## 5. 북 스마트와 스트리트 스마트

- **북 스마트**는 표준·모델·프로세스·원칙을 아는 것이고, **스트리트 스마트**는 그중 무엇을 언제 얼마나 쓸지 맥락에서 판단하고 증거로 되돌리는 것이다. 둘 다 필요하다.
- 북 스마트만 있으면 템플릿·도식·절차는 많지만 판단이 없다(분석 과잉). 스트리트 스마트만 있으면 기록·예시·모델 없이 같은 실수를 반복한다.

## 6. KISS · DRY · YAGNI

원칙은 규칙이 아니라 판단의 도구다. 우리 흐름 안에서의 의미로 적용한다.

- **KISS** — 코드를 짧게 쓰는 것이 아니라 **우연적 복잡성을 만들지 않는 것**이다. 업무의 본질적 복잡성은 숨기지 않고 드러낸다. 규칙을 모델에서 빼고 "코드에서 처리"하는 것은 복잡성을 옮긴 것일 뿐이다.
- **DRY** — 코드 중복 제거가 아니라 **하나의 지식에 하나의 원천**을 두는 것이다. 요구는 이벤트 하나로 한 번, 용어·규칙은 모델 한 곳, 규칙을 지키는 책임은 한 객체, 검사·계산은 코드 한 곳, 요구 예시는 곧 테스트다. 모양이 같아도 의미가 다르면 합치지 않는다.
- **YAGNI** — 결정을 미루는 것이 아니라 **추측으로 결정하지 않는 것**이다. 확정되지 않은 기능은 만들지 않되, 핵심 규칙·경계·되돌리기 어려운 기술 선택은 지금 확인한다. 핵심 규칙을 빈칸으로 두는 것은 숨은 위험이다.
- 원칙이 부딪히면 **위험과 비용, 되돌리기 쉬운 정도**로 고른다. 이것이 스트리트 스마트다.

## 7. 적정 수준과 검증

- **다음 결정이 중요한 것을 추측하지 않아도 될 만큼** 명시하고 검증한다. 더 그려도 판단이 바뀌지 않으면 멈추고 구현·테스트로 넘어간다.
- 테스트는 앞 활동을 생략해도 된다는 허가가 아니다. 오류가 생기는 곳 가까이에서 검증을 앞당긴다. 규칙이 모호하면 자동화보다 허용·거절 예시의 합의가 먼저다.
- 모델의 개수가 품질의 척도는 아니다. 성숙도가 높고 영향이 작으면 대화·스케치·코드·테스트로 가볍게 간다.

### 요구에서 코드까지의 경로

- **명세와 산출물** — 명세는 단계나 문서의 이름이 아니라 **확인할 수 있을 만큼 정밀하게 적었다**는 성질이다. SDD가 말하는 명세(spec)는 새 산출물이 아니라 오래 써 온 **요구사항 정의**를 다시 부르는 이름이다. 새 이름으로 같은 것을 따로 만들지 않는다.
- **명세에 쓰는 것과 가리키는 것** — 명세에는 요구사항(사용자 이야기, 수용 기준, 업무 규칙과 예, 범위·제외·미정, 정의서 수준의 용어집·품질 요구)을 쓴다. 도메인 모델(분석)·아키텍처(설계)·작업 계획은 명세가 아니며, 명세는 그것을 가리킨다.

| 산출물 | 무엇인가 | 범위·수명 |
|---|---|---|
| **요구** | 이해관계자가 원하는 것 | — |
| **요구사항** | 시스템이 충족할 능력과 조건 — 명세의 대상 | — |
| **사용자 이야기** | 요구를 담는 작은 가치 단위. **수용 기준**(업무 규칙의 대표 예로 쓴 테스트 기준)이 붙어야 명세가 된다 | 스토리 하나 |
| **요구사항 정의서** | 시스템 전체의 요구사항 명세(기능·업무 규칙·품질속성·용어집) | 시스템 전체, 유지 |
| **작업 명세서** | 스토리 하나의 요구사항 명세(스토리 + 업무 규칙과 예 + 범위·제외·미정). 정의서와 모델을 가리킨다 | 스토리 하나, 작업용 |
| **도메인 모델** | 분석 산출물 — 업무의 정적 구조와 동적 행위(개념·관계·규칙·사건·상태·전이·상호작용). 요구사항 명세가 가리킨다 | 도메인, 유지 |
| **설계 모델** | 해결 공간의 실현 결정 — 아키텍처와 객체 책임·협력·인터페이스·기술적 결정. 정적·동적 관점을 갖는다 | 필요한 범위, 수명에 따라 유지 |
| **아키텍처** | 설계 모델 중 시스템의 주요 구조·실행·품질·변경에 큰 영향을 주는 결정. 요구사항 명세가 가리킨다 | 시스템, 유지 |

- **불변의 뼈대** — **요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트**는 어떤 경우에도 거친다. 가장 작은 명세는 사용자 이야기와 수용 기준이다. 경로는 명세 → 코드, 명세 → 도메인 모델 → 코드, 명세 → 아키텍처 → 코드, 명세 → 도메인 모델·아키텍처 → 코드 가운데 복잡성이 고른다. 수용 기준이 뼈대에 들어 있으므로 작은 작업도 수용 기준과 테스트는 빠지지 않는다.
- **중간 산출물은 고른다** — 작업 명세서(업무 규칙과 예), 도메인 모델(정적 구조·동적 행위), 아키텍처(경계·의존 규칙·외부 연동), 작업 계획은 차례로 더하는 사다리가 아니다. **도메인 복잡성**과 **기술 복잡성**의 두 축으로 따로 고른다.

| | 기술 복잡성 낮음 | 기술 복잡성 높음 |
|---|---|---|
| **도메인 복잡성 낮음** | 스토리와 예 → 코드 | + 아키텍처 |
| **도메인 복잡성 높음** | + 작업 명세서 + 도메인 모델 | 모두 |

- **판단은 셋으로 나눈다** — 같은 산출물이라도 무엇·언제·얼마나를 섞지 않는다.

| 판단 | 기준 | 답 |
|---|---|---|
| **무엇을** 넣는가? | 도메인·기술 복잡성 | 작업 명세서, 도메인 모델, 아키텍처, 작업 계획 |
| **언제** 쓰는가? | 불확실성(3절) | 먼저 정한다, 또는 만들면서 발견해 되돌린다 |
| **얼마나** 남기는가? | 수명·변경 빈도, 함께 쓰는 사람·에이전트의 수 | 작업에 쓰고 버린다, 또는 유지한다 |

- **오래 남는 것** — 작업 명세서가 아니라 요구사항 정의서(업무 규칙 목록 포함)·도메인 모델·의존 규칙이다. 작업 명세서는 그것을 가리키고 다시 쓰지 않는다(6절 DRY).
- **SDD는 단계가 아니다** — 명세 주도 개발은 명세를 코드보다 먼저 쓰고 얼마나 오래 원천으로 두는가의 문제다. 요구와 코드 사이에 단계 하나를 더하는 것으로 다루지 않는다. 명세 고정은 작업 명세서를 요구사항 정의서처럼 유지하는 것이다. "spec" 한 단어로 요구사항·설계·작업 계획을 함께 부르지 않는다.
- **AI 시대에도 같다** — LLM으로 산출물을 만드는 비용은 줄었지만 검토하는 비용은 그대로이고, 산출물은 에이전트의 맥락(유한한 자원)이 된다. 넣는 기준은 하나다: **그 산출물이 에이전트의 결과나 사람의 확인을 바꾸는가?** 바꾸지 않으면 넣지 않는다.
- 이 기준이 없으면 같은 일을 도구·팀마다 다른 단계로 부르는 혼선이 생긴다. 과정은 관통 사례가 두 축의 어디에 있고 어떤 경로를 쓰는지 정한다(`course-design-guide.md`의 「과정의 맥락」).

## 교재에 적용하기

교재는 이 원칙을 **설명하는 대상**이면서 **지켜야 하는 대상**이다.

- **맥락과 사례** — 과정 설계는 과정의 맥락(대상의 성숙도, 다루는 불확실성)과 하나의 **관통 사례**를 정하고, 세션마다 그 사례에서 새로 답하는 결정을 분명히 한다(`course-design-guide.md`).
- **작게 끝까지** — 세션 원고는 요구를 이벤트 관점에서 시작하고, 다이어그램은 코드와, 코드는 테스트와 이어서 보인다. 과정 전체로는 요구 → 분석 → 설계 → 코드 → 테스트를 한 사례로 잇는다(`session-authoring-guide.md`).
- **DRY — 식별자의 원천은 하나** — 관통 사례의 이름과 값(상태 값, 흐름 번호, 이벤트·오퍼레이션 이름, 외부 시스템, 용어)은 과정 설계의 공통 전제 한 곳에 두고, 원고·다이어그램·예시 코드가 그대로 쓴다. 설계·코드의 영문 이름도 같은 곳의 **영한 용어집**에서 가져오며, 한 용어에 영문 이름은 하나다. 같은 사건을 여러 다이어그램으로 보일 때도 **하나의 모델과 하나의 코드**로 모인다.
- **진화와 오류를 구분한다** — 뒤 세션이 분석으로 새로 발견한 것(누락된 상태, 새 예외)은 **진화**다. 앞 세션은 그 시점의 모델로 두고, 뒤 세션이 발견과 되돌림을 보이며, 되돌린 결과를 공통 전제에 반영한다. 같은 대상을 다른 이름·다른 규칙으로 쓴 것은 **오류**다. 발견 즉시 원천에 맞춰 앞 세션까지 고친다. 개요 세션의 단순화도 이름과 규칙은 바꾸지 않는다.
- **KISS·YAGNI** — 교재 자체도 필요 없는 슬라이드·도식·반복을 만들지 않고, 확인하지 않은 사실·정책을 추측으로 채우지 않는다.
- **참조 자료** — 참조 자료의 문장·표를 원고에 그대로 복사하지 않는다. 원칙을 세션의 사례와 결정에 맞게 적용한다.
