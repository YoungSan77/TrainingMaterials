# 과정 설계 지침 (Course Design · 3단계 파이프라인의 1단계)

> 이 문서는 **과정(Course) 설계를 저작하는 절차와 판단 근거**다.
> 파이프라인의 자리: `Portfolio Design(portfolio/) + 과정 설계 지침(이 문서) + References + Human↔LLM → Course Design(courses/<slug>/design/)`.
> 다음 단계는 `커리큘럼_작성_지침.md`(Stage 2 — Curriculum Generation)다. 이 문서는 **무엇을 가르칠지의 뼈대**(Course Context)와 **LLM 실습 설계**(Practice Design)만 정한다 — 세션·시간표·명제는 커리큘럼 지침의 몫이다.
> Portfolio-wide 원칙·용어·개념 소유는 이 문서가 아니라 `portfolio/`(reference-frame·principles·terminology·concept-ownership·cross-course-framework·evidence-policy·governance)가 소유한다. 이 문서는 그 정본들을 어떻게 `courses/<slug>/design/`의 세 파일로 구체화하는지만 정한다.

---

## 0. 저작 R&R (파이프라인 전체에 적용)

3단계 파이프라인 전체를 관통하는 역할 경계다 — Course Design에서 시작해 Curriculum·Deck까지 이어진다.

**3자 역할**
- **Youngon**: 판단·정본의 원천. 교과 내용의 깊이·범위·계보·서술 방식 결정, 원전 해석 최종 판정, 최종 승인권.
- **Claude(대화)**: 밀도 필요 교과의 소스 저작, 구조·규약 설계, 판단 보조. 결정은 사용자, 근거는 Claude.
- **Claude Code**: 소스→슬라이드 변환(소스의 설명을 슬라이드 본문으로 펴는 것까지 책임), 엔진·회귀 수호, 저장소 관리.

**경계원칙**
1. **내용 판단은 대화에서, 구현은 Code** — Code 즉석 생성 금지(소스 없이 밀도 있는 내용을 만들지 말 것).
2. **Code 산출이 얕으면 소스를 의심한다** — Code는 있는 걸 펴는 것까지, 없는 걸 채우는 건 소스(Claude) 몫이다.
3. **정본은 저장소, 판단은 대화, 반영은 Code.** 확정된 규칙·계보·결정은 반드시 저장소 md에 박는다.

## 1. Course Design이 정하는 것

Course Design은 **우리가 가르치고 싶은 지식이 아니라 Learner Capability Gap과 Required Decision에서 시작한다.** `Customer-centered ≠ Customer-request-driven`이다 — 고객이 요청한 과정명이나 기술을 그대로 Curriculum Spine으로 쓰지 않는다.

```text
Learner / Customer Context
→ Desired Outcome
→ Capability Gap
→ Required Decisions
→ Foundational Decision Lenses
→ Course-owned Principles / Content
→ Practice
→ Evidence
→ Transfer to Work
```

이 순서를 건너뛰고 Content부터 쓰면, 나중에 "이게 왜 필요한가"를 사후 합리화하게 된다 — `portfolio/governance.md`(Part B, Change & Extension Protocol)가 이 순서를 강제하는 이유다.

## 2. 세 파일의 소유

```text
courses/<slug>/design/
├── course-context.md     Course Design의 뼈대(왜·누구·무엇·경계)
├── practice-design.md    LLM-integrated Practice(실습 시나리오)
└── references/
    └── verified-sources.md   근거·출처·최신성
```

### 2-a. `course-context.md`가 소유

- Course Purpose / Target Learner / Capability Gap / Typical Failure / Target Capability
- Course Thesis / Narrative
- Decisions Learner Must Make
- OWNER / APPLY / RECAP / FORWARD / NON-SCOPE (해당 과정의 concept-ownership.md 구체화)
- Key Distinctions (terminology.md의 "반드시 구분할 쌍" 중 이 과정에 해당하는 것)
- Course-specific principles (portfolio/principles.md의 Parent Lens를 이 과정에서 구체화한 Child)
- Trade-offs / Failure Conditions
- Cross-course Interfaces (Bridges Forward / Uses / Related Courses)

**커리큘럼 백본을 그대로 복제하지 않는다.** 이미 실제 Curriculum이 있는 과정(OOAD·DDD·SW Architecture·MSA·Modern SWQM)은 `context/course-portfolio-unified-v2.6/courses/`의 해당 baseline 문서에서 다음만 추출한다:

- intended progression (의도된 진행 순서)
- topic priority (무엇이 무거운가)
- sequencing rationale (왜 이 순서인가)
- coverage intent (무엇을 다뤄야 하는가)

세션 번호·시간표·구체적 커리큘럼 구조는 옮기지 않는다 — 그건 실제 `curriculum.md`가 이미 갖고 있고, Course Design과 Curriculum이 같은 정보를 두 벌로 갖으면(이중 SSOT) 하나가 바뀔 때 다른 하나가 조용히 낡는다.

### 2-b. `practice-design.md`가 소유

- 실제 실습 시나리오 목록(Practice ID·제목)
- Course Ownership(OWNER/RECAP/APPLY/FORWARD 경계)
- Work Context / Decision Practiced
- Preconditions / Inputs / Deliverable / Timebox
- Initial Instruction(Recommended Prompt 없이 주는 문제 설명)
- Intervention(5~10분 후 공개)
- Evidence of Learning
- Recommended Prompt + Prompt Design Intent(종료 시 공개)
- Trade-off / Failure Condition / Transfer

필드 상세와 운영 규칙(분량·타이밍·공개 시점·금지 사항)은 `portfolio/practice-standard.md`가 정본이다 — 여기서 다시 정의하지 않는다.

**기존 `lab-design.md`가 있는 과정(ooad·ddd·sw-architecture·msa)은 병합이 아니라 상호보완이다:**
- Practice Pack(`practice-design.md`) = LLM 운영 흐름·개입·평가 — "학습자가 AI와 어떻게 상호작용하는가"
- `lab-design.md` = 실습 대상·대조쌍·모델·코드·상황 구성 — "무엇을 실습 소재로 쓰는가"

어느 한쪽도 다른 쪽을 대체하지 않는다. `lab-design.md`가 없는 과정(swqm 포함 7개)은 Practice Pack을 실습 설계의 기준선으로 삼는다.

### 2-c. `references/verified-sources.md`가 소유

- source/evidence 원문(요약본으로 다시 쓰지 않는다 — 원형 보존)
- claim / quote / locator
- Verification Status / Evidence Role / Source Provenance / Evidence Strength / Transferability / Curriculum Use (`portfolio/evidence-policy.md` 스키마)
- BP Classification(기본값 Not classified, 필요할 때만)

legacy 자료(옛 slide placement·font·display 권고 등)는 삭제하지 않되, 지금은 normative instruction이 아님을 문서 상단 또는 해당 위치에 명시한다.

## 3. Learner & Context Fit — 채우는 법

과정을 새로 설계하거나 크게 바꿀 때만 전체를 다시 채운다. 기존 과정을 흡수할 때는 `context/.../courses/<번호>_<slug>.md` baseline이 이미 이 절을 채워 뒀으므로, 그 내용을 course-context.md로 그대로 가져온다(요약하거나 다시 짓지 않는다).

- **Audience:** 실제 어떤 역할/책임을 가진 학습자인가?
- **Current Capability:** 현재 무엇을 할 수 있고 무엇을 못하는가?
- **Work Context:** 어떤 업무·결정 상황에서 사용할 것인가?
- **Pain / Failure Mode:** 현재 어떤 잘못된 판단·실패·비용이 발생하는가?
- **Target Capability:** 교육 후 무엇을 더 잘 판단하거나 수행해야 하는가?
- **Required Decisions:** 실제 업무에서 어떤 결정을 내릴 수 있어야 하는가?
- **Decision Level:** Recognize / Apply / Decide / Govern 중 어디인가?
- **Constraints / Transfer Context**

## 4. Foundational Decision Lens Fit — 채우는 법

`portfolio/principles.md` §A의 5개 Lens(Systems / Lean / ToC / Design / Empiricism) 중 **이 과정의 실제 판단을 강화하는 것만** 고른다. 모든 과정에 5개를 다 넣지 않는다 — `context/.../support/04_audit/01_portfolio-integrity-audit-v2.6.md` §4의 "Strong APPLY Lenses" 표가 11개 과정 각각에 대해 이미 이 판단을 내려 뒀으므로, 그 판정을 그대로 course-context.md에 옮긴다.

## 5. Course Admission Gate

새 과정(11개 밖)을 추가할 때만 적용한다 — 지금 11개를 course design으로 흡수하는 작업에는 적용 대상이 아니다. Gate 항목은 `portfolio/governance.md` Part B7·`context/.../support/01_governance/06_course-spec-template.md` §17을 그대로 따른다.

## 6. Curriculum Authoring Gate — Course Design에서 Curriculum으로

Course Design(course-context.md·practice-design.md)이 승인되기 전에는:
- curriculum/session 재작성 금지
- source/deck 생성 금지
- renderer/course-specific logic 변경 금지

Course Design이 이미 실제 Curriculum과 공존하는 과정(위 5개)에서는 이 게이트가 "새 Curriculum을 만들지 않는다"는 뜻이지 "Course Design을 만들지 않는다"는 뜻이 아니다 — Course Design은 기존 Curriculum을 설명하는 상위 문서로 병행 작성한다.
