# Course Design Guide

## 목적

Course Design은 과정 목적·목표 역량·범위·핵심 주장·필수 학습 성과와 실패 조건을 소유한다. 과정 간 책임 범위를 정하고 세션 편성에 필요한 제약을 제공한다. 승인·변경 통제의 정본은 `governance.md`다.

모든 과정은 `sw-engineering-principles.md`의 기본 원칙을 따른다.

## 입력과 출력

**시작 확인** — `governance.md`의 「단계 시작 계약」에 따라 이 지침과 적용 공통 원칙을 읽고 사용자 의도, 기존 승인 설계의 버전(개정 시), 변경 허용 범위를 확인한다.

사용자 의도, 대상 학습자와 업무 문제·역량 격차의 근거, 운영 조건, 과정 간 책임 경계, 검증된 출처를 입력으로 받는다. 과정별 `course-design.md`를 출력한다. 가정과 확정 사실을 표시하고 필수 입력의 누락이나 범위 충돌은 해당 부분의 판단을 보류한다.

## 필수 항목

- 총 교육시간
- 대상 / 선수지식
- 과정 목적·목표 역량·핵심 주장, 필수 학습 성과와 관찰 가능한 실패 조건
- 범위·제외 범위와 과정 간 판단 경계
- 과정 공통 판단 원칙
- 재사용하는 사례·실습 방향과 **공통 전제** — 관통 사례의 공통 식별자(용어, 상태 값, 흐름 번호, 이벤트·오퍼레이션 이름, 외부 시스템)를 표 하나에 둔다. 이 표가 원고·다이어그램·예시 코드가 쓰는 이름과 값의 **유일한 원천**이다. 설계와 코드가 있는 과정은 **영한 용어집과 명명 규칙**(한글 용어 ↔ 설계·코드의 영문 이름)을 함께 둔다
- **용어의 한국어 표기** — 1차 자료가 영어이고 정착된 한국어 교육 용어가 없는 분야는 `영어 / 이 과정의 표기 / 뜻 한 줄`을 정한다. 세션에서의 최초 사용 위치는 DD가 가리킨다.
- 기준 원전과 참고 자료 — 분야의 기준 원전, 참고 자료는 별첨 하나로(「기준 원전과 참고 자료」)
- 과정의 맥락 — 대상의 성숙도와 과정이 다루는 불확실성, 그에 따른 깊이의 결정(「과정의 맥락」)
- 관통 사례 — 요구에서 코드·테스트까지 이어 쓰는 사례와 과정 전체에서 다룰 판단
- 실습 방향과 관통 사례 — 실습으로 입증할 역량·필수 성과·실패 조건과 공통 업무 규칙의 원천을 정한다. 실습 편성과 산출물의 세션 간 순서는 Curriculum, 실행 계약은 DD를 따른다.

## 모델 용어와 세션 경계

- 모델의 공통 용례는 `sw-engineering-principles.md`의 「도메인 모델·설계 모델과 정적·동적 관점」을 따른다. 과정 설계에서 다른 분류를 즉석에서 만들지 않는다.
- 정적·동적 모델을 다른 세션에서 가르쳐도 같은 도메인 모델의 두 관점인지 명시한다. 아키텍처와 객체 설계를 나눠 가르치면 둘 다 설계에 속하며 질문의 범위가 다름을 밝힌다.
- 각 모델 관점의 책임과 과정 범위를 정한다. 세션마다 모델을 보완하거나 앞 관점으로 되돌아갈 위치는 Curriculum과 DD가 정한다.
- 기준 원전이 모델 이름을 더 좁게 쓰는 경우 「원전 적용 결정」에 그 범위와 공통 용례의 대응을 기록한다. 원전 인용의 의미를 변경하지 않는다.

## 기준 원전과 참고 자료

과정은 분야별로 검증된 모범 서적·문서를 토대로 강의하고, 수강생이 그 자료를 구해 공부·참고하게 한다. 여러 자료를 섞거나 작성자의 관점을 더하지 않는다(작성 방식은 `session-authoring-guide.md`의 「원전 기반 작성」).

- **기준 원전** — 과정 내용의 정의·템플릿·표기·절차를 정하는 서적·문서와 그 판본. 주제별로 다르면 주제마다 하나씩 정한다.
- **참고 자료** — 기준 원전, 수강생이 구해 공부할 책, 세션이 인용·참조한 자료(영문 위키백과 포함, 한글 사이트 제외)를 과정의 **별도 문서** 별첨 `sessions/references.md` 하나에 레이블의 알파벳 순서로 둔다. 주요·인용을 나누지 않는다. `course-design.md`에는 목록을 다시 쓰지 않는다.
- **SWEBOK v4.0**은 과정의 범위와 과정 사이의 경계를 정하는 참고 틀이다. 실무 서적과 관점이 충돌하면 사용자가 조정하고, 그 결과를 결정으로 기록한다.
- 원전마다 같은 개념을 다른 이름으로 부르면 과정에서 쓸 이름 하나를 정해 기록한다.
- 사례에 원전의 기법을 적용한 방식(예: 어떤 목표를 한 유스케이스로 묶는지)은 결정으로 기록한다. 세션 원고와 지침은 이 기록을 따른다.

## 과정의 맥락

과정의 맥락은 이 과정이 **누구에게, 어떤 불확실성을, 어느 깊이로** 다루는지 정한다. 세션의 깊이·사례의 난이도·실습 방식·시간 평가의 근거가 되며, 대상 정보(직무·선수지식)와 구분한다(`sw-engineering-principles.md` 3절).

- **대상의 성숙도** — 도메인 지식, 기술 숙련(이 과정이 요구하는 언어 독해·모델링·도구 경험 등), 팀워크(요구 합의·리뷰·협업 방식)를 관점마다 한 줄로 적는다. 확인한 사실과 가정을 구분하고, 가정이면 확인 방법(사전 설문·과제 등)을 적는다.
- **다루는 불확실성** — 과정의 사례와 판단이 다루는 업무 불확실성(규칙·범위가 불분명한 정도)과 기술 불확실성(새 기술·제약)을 적는다.
- **깊이의 결정** — 위 두 항목에서 나온 결정이다. 무엇을 명시하고 먼저 검증할지(성숙도가 낮거나 불확실성이 큰 관점), 무엇을 가볍게 다룰지(성숙도가 높고 영향이 작은 관점)를 과정 수준으로 정한다.
- **요구에서 코드까지의 경로** — 관통 사례가 도메인·기술 복잡성의 어디에 있는지, 그래서 요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트 사이에 어떤 중간 산출물을 넣고 얼마나 남기는지 정한다(`sw-engineering-principles.md` 7절 「요구에서 코드까지의 경로」).
- **운영 조건** — 수강 인원, 개인·소그룹 운영, 실습 환경처럼 과정 규모와 난이도를 제한하는 조건을 확인한다. LLM 사용을 전제로 하는 과정은 필요한 운영 환경을 명시한다. DD는 각 실습의 도구 사용과 검토 절차를 정한다.

강의·실습 검토나 교육 후 피드백에서 과정 맥락이 달라지면 깊이와 총시간 제약을 재검토한다. 세션 시간 변경은 Curriculum에 환류한다.

## 좋은 Course Design의 판단 기준

- 과정의 맥락, 역량 격차, 핵심 주장, 필수 성과와 실패 조건이 연결된다.
- 범위와 제외 범위가 선명하고, 실습 성과와 검증된 근거로 교육 효과를 관찰할 수 있다.
- 총 교육시간의 포함 범위와 운영 제약이 분명하다. 세션 배분과 실제 교육량은 Curriculum에서 검토한다.

## 내용 완성과 시간 평가

- 시간 제약과 필수 성과가 충돌하면 과정 책임자에게 대안과 영향을 제시한다. 승인된 성과·실습 범위를 조용히 축소하지 않는다.

## 세션 간 경계와 지침 변경

- 여러 세션에 재사용하는 용어·사례의 공통 전제는 이 Course Design에 둔다. 개별 예시의 추가 가정은 해당 DD에 표시한다.
- 공통 식별자는 `sw-engineering-principles.md`의 **진화와 오류**를 따른다. 공통 전제 변경은 이 단계에서 영향 분석과 재승인을 받고 관련 DD·Deck과 검사에 연결한다.
- 산출물 결함을 수정할 때 공통 지침의 누락·모호함도 점검한다. 재사용 가능한 작성 원칙은 해당 지침에, 과정 고유의 정책·사례·결정은 과정 문서에 반영한다.
- 출처를 필요로 하는 사실·통계·표준 주장을 Course Design에 넣으면 Session Authoring Guide와 동일한 검증 원칙을 적용한다. 학습 순서를 보편적 개발 절차나 필수 기술 의존관계로 단정하지 않는다.

## 하지 말아야 할 것

- Session 상세 설명 작성
- slide 설계, visual 배치
- 코드 상세 작성
- renderer 제약 반영
- Curriculum/DD 생성

Course Design은 downstream Production의 형식이나 제약에 끌려가지 않는다. Production이 무엇을
할 수 있는지는 Course Design의 판단 기준이 아니다.

## 이전 형식의 과정 설계

기존 승인 산출물의 상태는 `governance.md`의 전환 규칙을 따른다. 한 문서에 섞인 세션 결정은 전환 검토에서 원천과 아직 승인되지 않은 조정을 구별한다.

## Downstream handoff

- **승인과 진입** — Human이 목적·역량·범위·핵심 주장·성과와 실패 조건, 공통 전제 및 시간 제약을 승인하면 Curriculum에 넘긴다.
- **필수 검사** — 필수 정보·경로·식별자·출처 기록의 존재와 일관성을 확인한다. 개별 출처 확인 도구는 적용 범위에서 사용한다. 과정 설계 전체의 자동 게이트는 미구현 요구로 구분하고, 수동 대조 증거를 별도로 남긴다. 과정의 업무 가치, 역량과 증거의 관계, 범위와 시간의 현실성은 의미 검토한다.
- **실패와 기준선** — 누락·충돌 항목, 출처와 해결 대안을 과정 기록에 남긴다. 사용자 의도나 공통 원칙의 변경은 해당 소유자에게 돌린다. 승인 설계의 경로·버전, 변경 근거와 하위 영향을 Governance에 따라 기록한다.
- 다음 단계는 `curriculum-dd-guide.md`를 따른다.
