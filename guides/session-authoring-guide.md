# Session Authoring Guide

## 1. 목적과 범위

Session Authoring(SA)은 `course-design.md`의 세션 정의를 입력으로 받아, 실제 강의와 Production에 사용할 최종 Session Source Markdown을 작성한다.

- SA는 별도 Curriculum/DD artifact를 만들지 않는다. Human+LLM이 내용을 논의하고, 최종 결과를 하나의 Session Source에 통합한다.
- 모든 세션은 `sw-engineering-principles.md`의 기본 원칙을 따른다. 원고에서는 특히 요구를 **이벤트 관점**에서 시작하고, **다이어그램은 코드와, 코드는 테스트와** 이어서 보이며, 교재 자체도 **KISS·DRY·YAGNI**를 지킨다.
- 이 지침은 **저자가 결정하는 것**을 정한다. 글꼴 크기·배치·분할·자동 검사처럼 Production이 결정하고 검사하는 것은 `production-guide.md`가 정하며, 이 지침은 그 항목을 가리키기만 한다.
- Session Authoring은 Content authority다. renderer의 현재 한계는 원고의 판단 기준이 아니다. 필요한 문법이나 visual 유형이 없으면 Production을 확장한다(「13. Production과의 관계」).

### 입력

- 해당 과정의 `course-design.md` — 세션 목표·Anchor Message·세부 목차와 **공통 전제**(관통 사례의 공통 식별자)
- 상세화할 세션 번호와 세션명(예: `S01을 상세화하라.`)

## 2. 원고 형식

### 세션명 헤더

모든 Session Source는 파일 최상단에 세션명 헤더를 둔다.

```text
--------------------
Session 명: 01. OOAD 개요
--------------------

## 목차

01. 세션 목표
02. ...

## 01. 세션 목표
...
```

- `Session 명`은 `course-design.md`의 세션명과 번호까지 일치한다. 이 헤더는 topic이 아니며 Production이 슬라이드 우측 상단의 세션명으로 쓴다.
- Session Source 하나가 Production의 입력 authority다. Production 실행 시 metadata를 다시 입력하지 않는다.

### 목차와 topic 번호

- `## 목차` 자체에는 번호를 붙이지 않는다. 목차 항목은 `01.`, `02.` 형식이며 bullet을 붙이지 않는다.
- 첫 항목은 `01. 세션 목표`, 마지막 항목은 `요약`이다. `정리`, `정리와 다음 단계` 같은 변형을 쓰지 않는다.
- 본문 topic은 `## NN. 제목`으로 정의한다. 목차와 본문의 번호·제목·순서는 1:1로 같고, 번호는 빠짐없이 연속되며 중복되지 않는다. 축약 제목을 따로 쓰지 않는다.
- topic을 추가·삭제·이동하면 목차·본문 번호와 그 topic을 가리키는 모든 참조를 함께 고친다(Production이 참조를 검증한다).

### 의미 표식과 블록 경계

- `**인용문**`은 독립된 한 줄에 둔다. 바로 다음의 비어 있지 않은 한 문단만 인용문 그룹이며 다음 빈 줄에서 끝난다. 여러 인용문은 각각 표식을 붙인다. 인용문 안의 bold는 강조만 뜻한다.
- 고객 발언·과제·템플릿의 Markdown `>` 블록은 인용문 그룹이 아니다. 학술 인용으로 렌더할 문장만 `**인용문**`을 쓴다.
- `**강사 노트**`는 독립된 한 줄에 둔다. 이후 내용은 코드 블록 밖의 다음 수평 구분선 또는 다음 `## NN. 제목` 전까지 강사 노트다. 노트 안의 `###`는 본문 복귀 신호가 아니다.
- 본문 `###` 이하 heading은 topic 내부 소제목이다. 별도 topic이나 자동 분할 명령이 아니다.
- `**페이지 분할**`은 독립된 한 줄의 명시적 페이지 분할이다. 분량이 아니라 **의미상 구분**(기본 예와 반례, 서로 다른 소주제)이 있을 때만 쓴다. 범례와 그 표, 짧은 표 두 개, 표와 짧은 후속 설명처럼 한 장에 들어갈 수 있는 내용 사이에는 두지 않는다.
- `**다이어그램 — 시퀀스 다이어그램**`은 topic 제목에 다이어그램 이름이 없는데 그 topic이 특정 다이어그램을 설명하거나 예로 보일 때 제목 바로 아래 한 줄에 둔다. 슬라이드 제목의 둘째 줄로만 표시된다.
- `**도식 — Mermaid**`, `**도식 — PlantUML**`, `**도식 — SVG**`는 뒤 visual의 유형 표식이다. 렌더할 원본은 `mermaid`, `plantuml:<kind>`(`usecase`, `class`, `package`, `sequence`, `communication`, `state`, `activity`), `svg`, `svg:uml` fenced block이다. `svg:uml`은 SVG로 직접 그린 UML·업무 배경도처럼 넓은 도식이다. `java`, `gherkin`, 일반 text block은 학습자에게 보이는 코드·예시다.
- 새 visual 유형이나 표식을 도입할 때는 SA·Production 지침과 파서를 함께 정의한다. 지침 수정만으로 구현이 끝났다고 보지 않는다.

### 참조 형식

- **세션**은 정확한 세션명을 큰따옴표로 쓴다: `"03. 정적 모델 — 도메인 개념과 관계"`. `S03`, `s03.md` 같은 표기를 쓰지 않는다.
- **같은 세션의 topic**은 번호와 제목을 겹낫표로 쓴다: `「26. 주문 취소 시퀀스」`.
- **다른 세션의 topic**은 세션명 바로 뒤에 쓴다: `"02. 요구 분석과 유스케이스"의 「44. 시스템 오퍼레이션과 계약」`. 여러 topic은 `·`, `,`, `과/와`로 잇는다. "같은 세션의" 같은 지시어로 대신하지 않는다.
- 도식의 라벨에는 topic 번호를 쓰지 않는다. 도식은 개념을 가리키고, 번호는 topic이 옮겨지면 틀린다.

## 3. 세션 구성

### 세션 목표와 요약

세션의 처음과 끝은 세션 전체를 한 장으로 보여 준다(Production이 검사한다).

- `01. 세션 목표`는 한 슬라이드, 목표 bullet **7개 이하**다. 목표가 늘어나면 관련 목표를 한 문장으로 합친다.
- 마지막 topic `요약`은 한 슬라이드이며 `### {세션 핵심}`과 `### 다음 세션`으로 구성한다. 다음 세션은 참조 형식의 세션명과 그 세션이 새로 답하는 결정 한 문장이다. 과정의 마지막 세션만 생략한다. 한 장을 넘으면 핵심 bullet을 줄이지 다음 세션을 빼지 않는다.
- 세션 목표·요약을 바꾸면 `course-design.md`의 세션 목표·세부 목차와 대조한다.

### topic 구성

- `course-design.md`의 세션 목표와 Anchor Message를 벗어나지 않는다. Anchor Message는 별도 블록으로 반복 표기하지 않고 학습자가 읽는 본문에 반영한다.
- 각 topic은 제목에 직접 답하는 **핵심 설명 또는 정의**로 시작하고 세부 설명·사례·비교·visual이 뒤따른다. 인용문이 가장 적절한 출발점이면 인용문을 먼저 두고 바로 뒤에서 의미를 설명한다.
- 하나의 topic은 하나의 핵심 메시지를 우선한다. topic 수와 분량은 주제에 따라 정하며 균등 분할하지 않는다.
- 같은 질문에 답하는 topic이 둘 이상이면 하나로 **병합**한다(세션 안의 DRY). 병합은 heading을 이어 붙이지 않고 한 흐름으로 다시 쓴다.
- 슬라이드 본문에는 학습자가 이해·판단하는 데 필요한 내용만 둔다. 출처 검증 과정·저자별 차이·작성 이유는 강사 노트에 둔다.
- 모델링을 다루는 세션에는 해당 기법의 **잘못된 관행** topic을 둔다. 잘못된 예와 바른 예는 표준·원전과 업무 의미에 비추어 정확해야 한다.
- 원칙·프로세스·접근법은 이름을 **명시**한다(예: 폭포수, 반복·점진(I&I), 애자일, 디자인 씽킹(DT), Lean Startup, Lean UX).

### 개요 세션과 상세 세션

- 개요 세션은 전체 흐름과 "왜"를 보이고, 다이어그램마다 **한 장의 미리보기**(다이어그램과 짧은 코드)를 둘 수 있다. 표기·작성법·코드 매핑의 상세는 해당 상세 세션이 맡는다.
- 개요의 단순화는 범위를 줄이는 것이지 **이름과 규칙을 바꾸는 것이 아니다**. 개요의 상태 값·이벤트 이름·업무 규칙은 상세 세션과 같다(「관통 사례와 식별자」).

### 관통 사례와 식별자

- 관통 사례의 **공통 식별자**(용어, 상태 값, 흐름 번호, 이벤트·오퍼레이션 이름, 외부 시스템)는 `course-design.md`의 공통 전제가 원천이다. 원고·다이어그램·예시 코드는 그 이름과 값을 그대로 쓴다.
- 앞 세션의 산출물(명세서·SSD·계약·정적 모델 등)을 뒤 세션의 **입력**으로 명시한다.
- 뒤 세션이 분석으로 새로 발견한 것은 **진화**다. 앞 세션은 그 시점의 모델로 두고, 뒤 세션이 발견과 원래 산출물로의 되돌림을 **언급**하며, 공통 전제를 갱신한다. 보완을 위한 별도 topic이나 산출물을 만들지 않는다.
- 같은 대상을 다른 이름·다른 규칙으로 쓴 것은 **오류**다. 공통 전제에 맞춰 앞 세션까지 고친다(Production이 세션 간 코드의 `enum` 값을 대조한다).

### 사례·가정·실습

- 사례의 주어진 사실, 교육용 가정, 추가 확인할 사항을 구분한다. 새 가정은 해당 예시 범위에서 명시하며 실제 정책이나 표준 요건처럼 제시하지 않는다.
- 사례를 다른 topic에서 재사용할 때 전제·용어·성공 조건을 유지한다. 성공 경로만 다루는 예시는 그 범위를 밝힌다.
- 실습은 목표, 주어진 조건, 수행 과제, 기대 결과물, 검토 기준을 포함한다. 검토 예는 강사 노트나 별도 topic에 두며, 미확인 정책을 임의로 채운 답을 정답으로 취급하지 않는다.
- 필요한 학습 내용과 품질을 먼저 완성한다. 정해진 시간이나 topic 수를 이유로 필요한 설명·사례·실습을 줄이지 않는다. 시간의 적합성은 최종 SA 완성 후 판단한다.

### 원고 수준 유지

- 새 topic은 기존 topic과 같은 구조(제목에 답하는 첫 문장, 필요한 만큼의 bullet·표·visual, 강사 노트)와 같은 수준으로 쓴다.
- 개편 후에는 전·후 topic 목록을 비교해 **사라진 개념**이 없는지 확인한다. 의도적으로 뺀 개념만 빠져야 한다.

## 4. 문장과 강조

### 문체와 용어

- topic 제목은 **한글 중심의 짧은 키워드**다. 두 줄로 넘어가거나 우측 상단 세션명과 겹치지 않게 하고, 설명은 본문 첫 문장에 둔다.
- 일반 기술 용어는 한국어를 우선한다. 영어가 필요하면 본문 최초 등장 시 `한글(English full term, 약어)`로 쓰고 이후에는 한국어나 약어만 쓴다. 표준명·고유명사·약어·코드 식별자는 원문을 유지한다.
- 도식 안의 텍스트도 불가피한 표준명·고유명사·약어가 아니면 한국어를 우선한다. 한 라벨에 `제목 - 설명`을 담을 때는 `-`로 구분한다.
- 질문 문장은 `?`로 끝낸다. 문장을 단순 정의로 끝내기보다 앞뒤 학습 흐름이 이어지게 쓴다.
- 용어는 과정 전체에서 같은 뜻으로 쓴다(예: 유스케이스에서 `이벤트 흐름`이 기본 용어이고 `시나리오`는 특정 경로다).
- 한 bullet에 `라벨 — 설명`을 담을 수 있다. 두 부분이 같은 비중으로 강조돼야 하면 별도 줄과 하위 bullet으로 나눈다.

### 강조(bold)

- bold는 **판단에 필요한 핵심 키워드와 대비되는 개념**에만 쓴다. 한 문장 전체를 bold로 하지 않는다.
- 본문의 lead 문장과 bullet에는 핵심어를 **1~3개** bold로 둔다. 학습자가 bold만 읽어도 요지를 따라갈 수 있어야 한다. 대비는 양쪽을 모두 bold로 한다.
- 질문 목록은 질문마다 **초점어**를, 절차 목록은 단계마다 **산출물·대상**을 bold로 한다.
- 표의 첫 열이 짧은 **항목명**이면 첫 열을 bold로 한다. 문장·예시·질문으로 된 열은 bold를 두지 않는다.
- 예외 — 유스케이스 흐름의 단계(명세 원문), 인용된 요청(`>`), 명사만 나열한 짧은 bullet, 강사 노트, 코드·도식 안의 텍스트. 코드의 선언된 이름은 Production이 bold로 표시하므로 코드 블록에는 `**`를 쓰지 않는다.

## 5. 인용과 출처

저자·책·논문·표준·공식 문서에 귀속되는 문장이나 수치는 **인용문 그룹**이다. 영어 원문이 없는 통계·정의·주장도 출처가 있으면 같은 형식을 쓴다.

- 형식: `"한글 번역", "English original", 저자, 년도` — 영어 원문이 없으면 `"한글 문장 또는 통계", 저자, 년도`. 원전을 직접 확인하지 못했지만 여러 독립 출처가 일관되게 인용하면 끝에 `www`를 붙인다.
- 한글과 영어 원문은 각각 `"..."`로 감싸고 한 문단 안에서 구분한다. `참고:`, `출처:` 같은 별도 줄을 두지 않는다.
- 저자명과 확인된 발행년도만 적는다. 책·논문 제목, 게재지, 페이지, URL은 슬라이드 본문에 넣지 않고 강사 노트에 둔다. 확인하지 못한 년도는 생략한다.
- 영어 원문은 재작성하지 않는다. 직접 인용은 확인한 문구를 정확히 옮기며, 요약은 따옴표로 원문처럼 제시하지 않고 `요약`으로 식별한다.
- 원전을 우선 확인한다. 원전을 확보하지 못하면 실제 본문을 읽은 추적 가능한 2차 인용처를 쓰며, 재인용임을 밝힌다. **검색 결과 요약이나 LLM의 기억은 검증 근거가 아니다.** 2차 인용의 반복 횟수를 독립 검증 횟수로 세지 않는다.
- 통계는 원래의 시점·대상·범위를 보존하고 일반화하지 않는다. 공식 초록·목차만 확인했다면 그 범위의 주장만 한다.
- 근거를 확인하지 못한 귀속·수치는 사실이나 인용으로 남기지 않는다. 학습에 필요한 설명은 확인한 근거로 다시 쓴다. 교육용 가정은 출처를 대신하지 않는다.
- 표준명은 공식 표기 그대로 쓰고(예: `ISO/IEC/IEEE 29148:2018`), 표준에 없는 판본·분류를 만들지 않는다.
- 출처 검증 과정이나 번역 메모는 본문에 넣지 않고 강사 노트에 둔다.

예: `"프로젝트 노력의 약 40~50%를 회피 가능한 재작업에 사용한다", "Current software projects spend about 40 to 50 percent of their effort on avoidable rework.", Barry Boehm·Victor R. Basili, 2001`

## 6. 표와 목록

- 표나 목록으로 충분한 내용은 박스나 다이어그램으로 만들지 않는다. 목록은 구조를 보일 때 쓰고, 불필요한 계층을 만들지 않는다.
- 짧은 항목이 많으면 의미가 유지되는 범위에서 5~6개 그룹으로 묶는다. 병렬 항목은 `A, B, C`처럼 한 문장으로 쓸 수 있다.
- 두 개 이상의 대비 개념에 각각 세부 항목이 있으면 하위 bullet으로 나눈다(예: 본질적 어려움/우연적 어려움).
- 번호가 의미를 갖는 절차는 numbered list, 순서가 없는 항목은 bullet을 쓴다. 목차에는 bullet을 쓰지 않는다.
- 표의 셀은 **한 줄**에 들어가게 핵심 구로 쓴다. 셀 안의 topic 참조는 강사 노트로 옮긴다. 계약의 사후조건처럼 여러 사실을 담은 셀은 **사실마다 행**을 나누고, 이어지는 행의 첫 칸은 비운다(행 높이는 Production이 정한다).

## 7. 강사 노트

강사 노트는 학습자가 읽는 본문을 **보조**한다. 본문과 모순되는 내용이나 본문에 없는 새 주장을 두지 않는다.

- **모든 topic**에 `**강사 노트**`를 둔다(Production이 검사한다).
- 노트는 **bullet**로 쓰고, bullet 하나는 한 가지 일을 한다.
  - **강의 포인트** — 강조할 판단, 던질 질문, 흔한 오해
  - **근거·출처** — 인용·표준의 서지와 링크, 확인 범위, 재인용 여부
  - **가정·범위** — 교육용 가정, 성공 경로만 다룬다는 등의 범위
  - **연결** — 앞뒤 topic이나 다른 세션과의 관계(참조 형식을 따른다)
- 코드 topic의 노트는 코드가 **보장하는 것과 보장하지 않는 것**, 코드의 요소를 분석 모델에 역수입하지 않는다는 점을 밝힌다.
- Anchor Message는 노트에만 두지 않는다. 노트에만 있는 메시지는 본문 반영으로 보지 않는다.

## 8. Visual

### 쓰는 이유와 도구

- Visual은 **관계·구조·흐름·공간적 의미**를 텍스트보다 명확히 보여줄 때만 쓴다. 해당 개념이 등장하는 바로 그 topic에 두고, 종합 visual 페이지를 따로 만들지 않는다.
- 콘텐츠를 먼저 확정한 뒤 도구를 고른다. UML은 PlantUML(또는 `svg:uml`), 일반 흐름·관계는 Mermaid, 정량 데이터는 chart를 쓴다. 실제 수치 없이 chart를 만들지 않는다. 개념 도식은 개념도임이 드러나게 하고 측정된 관계처럼 보이지 않게 한다. 와이어프레임은 편집 가능한 SVG 등으로 둔다.
- 도구 때문에 내용을 바꾸지 않는다. 필요한 표현이 지원되지 않으면 Production을 확장한다.
- Markdown 하나로 의미와 visual 원본이 전달되도록 원본(PlantUML·Mermaid·SVG 등)을 본문에 둔다. ASCII 테두리를 최종 visual로 취급하지 않는다.
- 정보가 적으면 단순하게 그린다. 서로 다른 개념을 한 도식에 억지로 합치지 않는다.

### 그리는 방법

- 도식 안의 흐름은 **왼쪽 → 오른쪽**이 기본이다. 가로로 길면 2~3행으로 나누어 상하로 잇고, 의미 없이 세로로 긴 도식은 피한다.
- 화살표가 학습 순서·시간 순서·인과·메시지·분류·의미 연결 중 무엇인지 분명히 한다. 개념의 연관을 필수 개발 순서로 그리지 않는다.
- 선이 행동·상자·레인 경계를 **가로지르지 않게** 배치한다. 자동 배치로 겹침이 풀리지 않으면 `svg:uml`로 직접 배치한다.
- 같은 상호작용을 두 다이어그램으로 비교할 때는 **같은 메시지·같은 번호**로 **한 슬라이드**에 보인다.
- 표기 그림과 그 「표기와 사용법」 표는 한 슬라이드에 둔다.
- 도식의 글자 크기는 Production이 모든 도식에 같게 맞춘다(`production-guide.md`의 「Visual layout 및 가독성」). 요소가 적은 도식을 키워 그리지 않고, SVG는 도식 안 글자 크기를 한두 가지로 맞춘다.
- 협력 예시는 책임 소유자와 조정 책임을 구분하고, 하나의 설계 대안을 보편적인 책임 배치로 단정하지 않는다.
- Production 가독성 문제를 해결하려고 의미를 훼손하거나 노드·관계를 삭제하지 않는다.

## 9. UML

### 공통

- UML을 설명하는 topic에는 **해당 notation 자체**를 함께 보인다. 다이어그램을 처음 쓰는 topic에서는 표기 요소를 나란히 보이고 요소마다 **이름·의미·사용법**을 표로 설명한다. 문법이 있는 표기(조각·가드·다중성·전이 라벨)는 쓰는 법을 예와 함께 보인다.
- 다이어그램을 소개하는 topic의 제목은 **다이어그램 이름**, 예제 topic은 **대상 + 다이어그램 약칭**(예: `결제 시퀀스`)으로 쓴다.
- 여러 다이어그램을 다루는 세션은 먼저 다이어그램들의 **정의와 정적 모델(또는 요구)과의 관계**를 한 곳에서 보인다.
- 모델을 만드는 다이어그램은 **초안 → 상세화**로 발전시킨다(유스케이스 다이어그램, SSD 초안 → 정제된 SSD, 클래스 다이어그램). 초안은 구조의 합의, 상세화는 규칙의 명시가 목적이다.
- 하나의 개념을 설명할 때 관련 없는 UML 요소를 함께 넣지 않는다(예: `유스케이스란 무엇인가?`에는 타원만).
- 다이어그램마다 같은 의미의 표현이 다르면 그 차이를 밝힌다(예: 시퀀스의 조각 ↔ 커뮤니케이션의 `[조건]`·`*`).
- UML 표기에는 **바탕색을 쓰지 않는다**. 스테레오타입은 `«enumeration»`, `«interface»`, 유스케이스 다이어그램의 외부 시스템 `«actor»`, 관계의 `«include»`·`«extend»`만 쓴다. 데이터 타입·도메인 유형 같은 분류는 도식에 표시하지 않고 본문에서 대응시킨다. 원형 표시·footbox처럼 표기 규칙을 지키는 렌더 설정은 Production이 넣으므로 원고에 쓰지 않는다.

### 유스케이스 다이어그램

- 시스템 경계를 크게, 액터는 작게 그린다. **초안**은 주 액터(왼쪽), 유스케이스, 시스템 경계, 연관만 쓴다. **상세화**에서 외부 시스템 지원 액터를 오른쪽에 `«actor»` 상자로 더하고, 확인된 관계만 더한다.
- `«include»`는 기본 → 포함 유스케이스, `«extend»`는 확장 → 기본 유스케이스, 일반화는 특수 → 일반(실선·속 빈 삼각형)이다. 포함은 코드 공통화가 아니고, 확장은 기본 유스케이스가 독립적으로 의미를 갖는 전제에서 쓴다.
- 관계를 가르칠 때는 그 관계를 성립시키는 사례 전제를 같은 topic에 둔다. 유스케이스 사이의 일반 화살표로 순서나 흐름을 표현하지 않는다.

### 시퀀스 다이어그램·SSD

- 분석 단계의 호출은 **동기**가 기본이며 응답을 그리지 않는다. 결과를 기다리지 않는 요청·통보만 비동기(열린 화살촉)로 구분한다.
- SSD 초안은 주 액터와 대상 시스템만, 정제된 SSD는 외부 시스템(지원 액터)까지 그린다. 시스템 안의 객체는 넣지 않는다.
- 분석 시퀀스의 생명선은 **도메인 개념의 인스턴스**(`:주문`)다. 컨트롤러·서비스·저장소 같은 설계 객체는 넣지 않는다.

## 10. 코드 매핑

- 요구·분석의 결정이 **코드와 실행 결과에 어떻게 이어지는지** 보인다. 코드는 연결을 확인하는 예이지 최종 구현이나 모델의 자동 변환이 아니다.
- 코드는 **자기 topic**에 두고, 바로 앞에 **그 코드가 표현하는 도식**을 둔다. 도식 없이 코드만 제시하지 않는다.
- 코드는 **컴파일하고 실행해 확인한 것**만 싣는다. 전체 코드는 `courses/<course>/sessions/code/sNN/`에 두고, 슬라이드에는 도식이 표현하는 부분만 **발췌**할 수 있다. 생략은 `// ... <설명> 생략` 줄로 표시한다(Production이 발췌와 원본을 대조한다).
- 식별자는 한글이며 **공통 전제·용어집의 이름**과 같다.
- **개념 클래스**는 필드와 생성자를 가진 `class`로 쓴다. 필드가 모델의 속성·연관을 드러낸다. `record`는 **데이터 타입**(금액·수량·주소)처럼 값으로 같은지 판단하는 것에만 쓴다.
- 코드가 **보장하는 것과 보장하지 않는 것**을 구분한다. 미확정 정책을 분기·예외·테스트 기대값으로 대신 결정하지 않는다. 코드의 요소(필드·보조 호출·설계 객체)를 분석 모델에 역수입하지 않는다.
- 학습자가 결과를 먼저 예측한 뒤 실행해 대조하게 한다.

다이어그램마다 코드로 이어지는 요소를 한 가지 이상 보인다. 아래 대응은 설계의 결정이 섞인 "이렇게 이어진다"의 예이지 변환 규칙이 아니다.

| 다이어그램 | 모델 요소 | 코드에서 |
|---|---|---|
| **SSD** | 시스템 이벤트 / 외부 시스템 | 시스템 경계의 인터페이스 메서드 / 호출하는 인터페이스(동기는 반환값, 비동기는 결과 없음) |
| **오퍼레이션 계약** | 사전·사후조건 | 호출 전 검사 / 호출 후 상태와 보낸 요청, 계약의 예는 테스트 |
| **클래스** | 개념 / 속성·연관 / 속성 도메인 | 필드와 생성자를 가진 `class` / 필드(연관의 방향은 설계) / 값의 종류(`record`)와 생성 시 규칙 검사 |
| **클래스** | 다중성 `1..*` / 합성 / 파생 속성 / 확정 값 | 빈 값 거절 / 전체가 부분을 만든다 / 저장하지 않는 계산 / 시점의 값을 옮겨 적기 |
| **활동** | 행동 / 결정 / 분기·합류 | 메서드 호출 / `if` / 기다리지 않는 요청 |
| **시퀀스** | 메시지 / 생성 / 비동기 / `alt`·`loop` | 받는 객체의 메서드 / `new` / 결과 없는 호출 / `if`·`for` |
| **커뮤니케이션** | 링크 / 번호 `1.1` | 참조 필드 / 호출 안의 호출 |
| **상태 기계** | 상태 / 전이 / 가드 / 없는 전이 | `enum` 값 / 상태를 바꾸는 메서드 / 전이 전 검사 / 거절과 그 테스트 |

## 11. 기법별 작성 원칙

여러 과정에서 재사용하는 기법 규칙이다. 모든 세션에 적용하라는 뜻은 아니다. 과정 고유의 전제·용어·사례는 `course-design.md`에 한 번만 둔다.

### 유스케이스

- **시스템 경계는 소유로 판단한다.** 책임과 데이터를 다른 조직·시스템이 소유하면 외부 시스템(지원 액터)으로 둔다. 경계를 비대하게 만드는 것과 기능마다 떼어 액터로 만드는 것을 모두 잘못된 관행으로 다룬다. 경계 밖 유스케이스는 그 시스템의 경계 안에 따로 그린다.
- 유스케이스 모델링의 핵심은 **업무 배경도 → 유스케이스 다이어그램 → 명세서 기본 흐름 → SSD**의 연결이다. 기본 흐름과 SSD는 나란히 대응시킨 슬라이드로 보인다.
- 유스케이스는 기능 목록이 아니라 **액터의 목표와 가치 있는 결과**로 식별한다. 목표를 먼저 찾고 그 목표를 원하는 액터를 찾는다. CRUD 목록을 유스케이스로 만들지 않는다.
- 유스케이스는 글로 쓰는 명세이고 다이어그램과 관계는 부수적이다. 명세는 필요한 항목만 쓰며, 가능한 모든 상황을 열거하는 문서가 아니다.

**이벤트 흐름**

- 목표 달성에 필요한 **본질적인 행위만** 쓴다. 액터의 의도와 외부에서 의미 있는 결과가 중심이다. 의미 없는 `요청한다 → 시스템이 처리한다` 반복, UI 클릭 순서, 내부 구현의 확인·계산·저장·호출, 설계 내용을 넣지 않는다.
- 기본 흐름의 **액터 단계 하나가 SSD의 시스템 이벤트 하나**에 대응하도록 쓴다. 한 단계에 두 이벤트가 숨어 있으면 단계를 나누고, 반복은 "1~2단계를 반복한다"처럼 적는다.
- 대안·예외 흐름은 목표 달성 경로가 의미 있게 달라질 때만 쓴다. 번호는 **기본 흐름에서 파생**한다(`3a`는 기본 흐름 3단계의 첫 번째 대안, `1a2a`는 대안 `1a`의 2단계의 첫 번째 예외). 기본 흐름을 고치면 번호와 그 번호의 모든 참조를 함께 고친다.
- 규칙·제약·예외 정책·품질속성은 흐름과 섞지 않고 따로 기술한다(예: `배송 시작 이후에는 주문을 취소할 수 없다`는 규칙이다).

```text
유스케이스: 주문을 취소한다
전제: 결제 완료·배송 시작 전 주문의 전체 취소 성공 경로다.
교육용 가정: 전체 취소 시 결제 금액 전액이 환불된다.

1. 고객이 주문을 취소한다.
2. 환불이 처리된다.
3. 고객은 주문 취소 결과를 확인한다.
```

### 시스템 오퍼레이션과 계약

- 시스템 오퍼레이션은 시스템 경계를 넘는 **업무 의미의 시스템 이벤트**에 응답하는 시스템의 책임이다. 구현 함수명이나 객체 메서드를 먼저 정하는 작업이 아니며, 이벤트와 오퍼레이션은 다른 개념이다. 이름은 한글 업무 의미로 쓴다.
- 계약은 **어렵고 복잡한 이벤트**에만 쓴다 — 여러 외부 시스템을 조정하거나, 조건을 외부가 판단하거나, 상태와 결과가 얽힌 이벤트다. 시스템 이벤트 목록에서 어느 오퍼레이션에 계약을 쓰는지와 그 이유를 보인다.
- 관련 유스케이스, 입력의 의미, 책임 범위, 사전조건, 성공 사후조건을 함께 제시한다. 사후조건은 처리 절차가 아니라 **수행 후 참인 상태와 유지할 조건**이다. 외부 시스템이 소유한 결과는 "했다"가 아니라 "**요청했다**"로 쓴다.
- 성공 계약은 사전조건 불충족·실패를 보장하지 않는다. 필요한 실패 요구는 따로 정의한다. 시스템 수준 계약과 내부 객체 계약을 구분하며, 어느 세션에서 정제하는지는 Course Design의 세션 경계로 정한다.

### 요구사항 표현

- 특정 한 종류의 요구사항을 요구사항 전체처럼 표현하지 않는다(예: "요구사항은 이해관계자 요구사항에만 머물지 않는다. 사업 목적에서 해결책, 전환까지 연결해서 본다.").
- 서로 다른 표준의 분류를 임의로 일대일 대응시키지 않고, 원문이 말하는 범위를 넘어 새 분류를 만들지 않는다.

## 12. 검토 절차와 완료 기준

### 검토 절차

1. Course Design의 세션 목표·Anchor Message·**공통 전제**를 확인한다.
2. 전체 topic 순서와 학습 흐름을 먼저 합의한다.
3. topic별 텍스트와 visual을 같은 위치에서 검토한다.
4. 불필요한 topic·중복·과도한 상세를 제거하고, 병합·압축 후 사라진 개념이 없는지 전·후 topic 목록을 비교한다.
5. 기본 원칙에 비추어 점검한다 — 이벤트 관점인가, 관점을 섞지 않았는가, 다이어그램이 답하는 질문이 있는가, 코드·테스트와 이어지는가, 같은 지식을 두 곳에 쓰지 않았는가, 추측으로 만든 내용이 없는가, **공통 식별자가 원천과 같은가**.
6. 용어·문체·강조·질문 표현·인용 형식과 강사 노트를 통일한다.
7. visual의 의미·전제·표기·원본 구조를 검토한다. 실제 글꼴·배치·분할·가독성의 판정은 Production이 한다.
8. 표준·인용·통계·기술적 주장의 원전 또는 실제 읽은 재인용처와 확인 범위를 검증한다.
9. 최종 Session Source로 변환하고 Production을 실행한다. **오류는 0개, 경고도 0개**가 되도록 원고를 고친다(`production-guide.md`의 「자동 검사」). 실제 실행한 검사와 하지 않은 검사를 구분해 기록한다.
10. 문제의 원인이 공통 지침의 누락·모호함이면 지침을 함께 보완하고, 과정 고유 판단은 과정 문서에 반영한다.

검토 중에는 사용자가 요청하지 않는 한 임의의 PPT 시안이나 Production과 다른 이미지를 만들지 않는다.

### 완료 기준

- 세션명 헤더가 있고, 목차와 본문 topic이 1:1로 일치한다.
- 세션 목표(한 장·7개 이하)와 요약(한 장·다음 세션 포함)이 규칙을 따른다.
- Course Design의 세션 목표와 Anchor Message를 학습자가 읽는 본문에서 충족한다.
- 강의에 필요한 설명·사례·비교·코드·visual·실습이 충분하고 순서가 자연스럽다.
- 공통 식별자가 `course-design.md`의 공통 전제와 같고, 진화는 발견과 되돌림이 보인다.
- 인용·통계·표준이 확인한 근거에 기반하며, 직접 인용·요약·교육용 가정이 구분된다.
- 코드는 컴파일·실행으로 확인되었고 도식과 짝을 이룬다.
- 모든 topic에 규칙에 맞는 강사 노트가 있다.
- Production 검사의 오류·경고가 0개다.
- renderer의 현재 지원 여부와 관계없이 최종 원고로 사용할 수 있다.

## 13. Production과의 관계

- 정상 Production 입력은 최종 Session Source 하나다. 실행 명령·출력·검증 산출물은 `production-guide.md`가 관리하며 이 지침에 중복하지 않는다.
- Session Source를 renderer 한계에 맞추기 위해 수정하지 않는다. renderer 편의를 위한 내용 삭제, 임의의 문법 치환, slide별 수작업 배치 지시를 하지 않는다.
- Production이 원고의 내용·도식 구조·표기 문제를 발견하면 피드백 문서를 사용자와 함께 검토해 학습 목적을 기준으로 수정 여부를 정한다. Production의 렌더링·배치·글꼴 문제는 원고 수정으로 해결하지 않는다.

### 하지 말아야 할 것

- 별도 Curriculum artifact·Session DD 생성
- 사용자가 요청하지 않은 요약 slide·notation 종합 slide 추가
- 개념 설명보다 visual을 먼저 만들고 그 visual에 맞춰 내용을 왜곡
- 표준이나 원전에 없는 용어·판본·분류의 창작
- 이벤트 흐름에 내부 처리 단계와 가능한 모든 예외 삽입
- 개요 세션에서 공통 식별자(상태 값·이벤트 이름·규칙)를 다르게 단순화
