# Deck Authoring Guide

## 1. 목적과 범위

Deck Authoring은 승인된 Session DD와 통합 승인 Curriculum을 실제 강의용 Deck으로 구현한다. 기존 문서와 도구의 **Session Authoring**, **SA**, **Session Source**는 이 단계와 현재 Markdown 입력 형식을 가리킨다. 단계별 소유권과 승인 기준선은 `governance.md`가 정한다.
- 모든 세션은 `sw-engineering-principles.md`의 기본 원칙을 따른다. 원고에서는 특히 요구를 **이벤트 관점**에서 시작하고, **다이어그램은 코드와, 코드는 테스트와** 이어서 보이며, 교재 자체도 **KISS·DRY·YAGNI**를 지킨다.
- 이 지침은 **저자가 결정하는 것**을 정한다. 글꼴 크기·배치·분할·자동 검사처럼 Production이 결정하고 검사하는 것은 `production-guide.md`가 정하며, 이 지침은 그 항목을 가리키기만 한다.
- Deck은 슬라이드의 문구, 표·도식·코드의 표현, 학습자용 실습과 강사 노트를 소유한다. DD가 승인한 거버닝 메시지, 설명 순서, 정의·근거, 도식 관계와 코드 동작, 실습 계약의 의미를 보존한다. 미지원 표현은 Production에 필요한 기능으로 전달한다(「13. Production과의 관계」).
- 원고를 쓰는 동안 hook이 작업 순서를 들이밀고 턴 끝에 자동 검사가 도는 것은 저장소의 하네스다. 그 요소와 규칙은 `agentic-repository-guide.md`가 정한다.

### 규칙의 순서

규칙이 서로 부딪칠 때는 **아래 순서로** 판단한다. 지침이 길어질수록 형식 규칙이 내용 규칙을 밀어내기 쉬우므로, 어느 쪽을 접을지 먼저 정해 둔다.

1. **내용** — 배울 것이 본문에 있고, 문장이 가르치고, 근거가 확인된 것(「3. 세션 구성」, 「4. 문장과 강조」, 「5. 인용과 출처」, 「11. 원전 기반 작성」). 아래 둘을 위해 **줄이지 않는다**.
2. **형식** — 표식·참조·제목·강조·표와 목록의 규칙(「2. 원고 형식」, 「6. 표와 목록」). 내용을 해치지 않는 선에서 지킨다.
3. **지면** — 페이지 분할이 허용된 콘텐츠는 의미를 보존해 조판한다(「의미 표식과 블록 경계」의 「넘칠 때는 순서가 있다」). 실습 안내처럼 승인된 장수나 배치를 충족하지 못하면 Deck·Production의 결함을 구분해 처리한다.

### 입력

**시작 확인** — Governance의 「단계 시작 계약」에 따라 이 지침과 적용 제작 계약, 통합 승인 Curriculum·승인 DD의 버전, 편집 허용 범위를 확인한다.

- 대상 세션 ID·이름, 승인된 DD와 통합 Curriculum의 버전, 연결된 Course Design의 공통 전제, 검증된 출처·도식·코드 원본·실습 증거.
- **출력**은 편집 가능한 Deck 원고다. Markdown을 우선 사용한다. 현재 문법으로 승인된 교육 내용을 표현하기 어렵다면 필요한 문법·자산·검사 계약을 Production과 합의한다.
- **영역 분리** — 배울 내용과 출처 표기는 학습자 본문, 세부 시간 배분·강사 개입·운영 방법은 강사 노트에 둔다. 내부 ID·제작 표식은 메타데이터로, 승인·검사 증거는 기존 과정 기록 및 QA로 분리한다. 제작 지시를 학습자 화면이나 강사 노트에 노출하지 않는다.

## 2. 원고 형식

### 세션명 헤더

모든 Session Source는 파일 최상단에 세션명 헤더를 둔다.

```text
--------------------
Session 명: 01. OOAD 개요
--------------------

## 목차

01. 세션 목표
02. ...

## 01. 세션 목표
...
```

- `Session 명`은 승인 Curriculum의 세션명과 번호를 사용한다. 기존 과정의 호환 입력은 Production Guide의 「정본 이관과 현재 구현」을 따른다. 헤더는 슬라이드 우측 상단 표기에 쓰인다.
- Session Source 하나가 Production의 입력 authority다. Production 실행 시 metadata를 다시 입력하지 않는다.

### 목차와 topic 번호

- `## 목차` 자체에는 번호를 붙이지 않는다. 목차 항목은 `01.`, `02.` 형식이며 bullet을 붙이지 않는다.
- 첫 항목은 `01. 세션 목표`, 마지막 항목은 `요약`이다. `정리`, `정리와 다음 단계` 같은 변형을 쓰지 않는다.
- 요약 뒤의 **별첨**(`## 별첨. 실습 답`)은 목차에 넣지 않는다(「사례·가정·실습」).
- 본문 topic은 `## NN. 제목`으로 정의한다. 목차와 본문의 번호·제목·순서는 1:1로 같고, 번호는 빠짐없이 연속되며 중복되지 않는다. 축약 제목을 따로 쓰지 않는다.
- **목차는 그룹이다.** 목차가 길어지면 관련 topic을 그룹으로 묶는다. 그룹은 `## NN. 그룹명`(목차 항목)이고, 그 아래 번호 없는 `## 제목`이 **서브 항목**이다. 서브 항목은 자기 제목의 슬라이드가 되고, 제목 둘째 줄(11pt)에 그룹(`05. 연관`)이 표시된다. 목차에는 그룹만 나온다. 그룹 바로 아래 본문이 없으면 그룹만의 슬라이드는 만들지 않는다. 서브 항목이 하나뿐인 그룹은 서브 항목 없이 그룹 자체로 쓴다(제목이 목차 항목 그대로 보인다).
- 서브 항목을 가리킬 때는 번호 없이 「서브 항목 제목」이나 「NN. 그룹명」의 「서브 항목 제목」으로 쓴다.
- **그룹명과 서브 항목 제목을 같게 쓰지 않는다.** 슬라이드 제목 아래 둘째 줄에 그룹명이 찍히므로 같은 말이 두 줄에 연달아 나오고, 그 장이 그룹에 무엇을 더하는지 알 수 없다. 그룹명은 묶음이 답하는 질문(`05. 사람과 AI가 하는 일`), 서브 항목은 그 장이 답하는 질문(`활동마다 사람과 AI`)으로 가른다.
- topic을 추가·삭제·이동하면 목차·본문 번호와 그 topic을 가리키는 모든 참조를 함께 고친다(Production이 참조를 검증한다).
- topic의 **제목·첫 문장·목록·표·도식·코드**는 같은 질문에 답한다. 첫 문장은 제목의 개념이나 주장을 직접 설명하고, 제목과 다른 설명이 필요하면 알맞은 topic으로 옮기거나 독립 topic으로 분리한다.
- 개념은 먼저 직접 정의하고 사례는 그 정의를 구체화할 때만 쓴다. 사례가 정의를 대신하거나, 관통 사례·식별자를 관련 없는 topic까지 반복해서는 안 된다. 사례를 빼도 설명의 의미가 성립해야 한다.
- 본문은 개념·모델·판단을 주어로 직접 설명한다. `이 세션은`, `이 장에서는`, `여기서는`, `다음 장에서`처럼 발표 순서를 설명하는 문장으로 학습 내용을 대신하지 않는다. 범위를 연결할 때는 정확한 세션명·topic 참조와 그 관계를 함께 쓴다.

### 의미 표식과 블록 경계

- `**인용문**`은 독립된 한 줄에 둔다. 바로 다음의 비어 있지 않은 한 문단만 인용문 그룹이며 다음 빈 줄에서 끝난다. 여러 인용문은 각각 표식을 붙인다. 인용문 안의 bold는 강조만 뜻한다.
- 고객 발언·과제·템플릿의 Markdown `>` 블록은 인용문 그룹이 아니다. 학술 인용으로 렌더할 문장만 `**인용문**`을 쓴다.
- **묶음은 상위 bullet, 소속은 들여쓴 bullet이다.** 원문이 `**범위**`·`**US-1. …**`·`**주문과 금액**`처럼 굵은 머리말로 묶은 줄은 그 머리말을 **상위 bullet**(`- **범위**`)으로 두고 속한 줄을 두 칸 들여쓴다. 머리말을 글머리표 없는 글로 두면 묶음과 소속이 같은 단에 나란히 서서 어디까지가 한 묶음인지 보이지 않는다. 번호가 붙은 줄도 같다(`  1. `).
- 문장이 목록의 머리말이면 `- `를 붙이고 소속 항목을 두 칸 들여쓴다. 실제 응답의 문구와 강조는 유지한다. 원본과 동일한 목록 형태에 적용하는 기존 검사 예외는 Production Guide를 따른다.
- **표에 딸린 주석은 표와 같은 장에 둔다.** 표 바로 뒤의 한두 줄이 다음 장 맨 위로 넘어가면 가리킬 표가 없어 뜬금없이 읽힌다. 원문의 순서는 그대로 두고 **topic을 절 경계에서 나눠** 표와 주석을 한 장에 담는다.
- **받은 말은 따옴표만 두른 한 줄로 둔다.** 고객의 요청·업무 담당자의 말처럼 그대로 보일 문장은 `"장바구니에 담은 상품을 결제하면 …"`처럼 **문장 전체를 따옴표 안에** 넣어 제 줄에 두고, 글머리표를 붙이지 않는다. Production이 이 한 줄만 **글머리표 없이** 본문 크기로 그린다(`>` 블록은 글머리표가 붙어 저자의 주장처럼 읽힌다). 따옴표 밖에 다른 말이 붙은 줄은 보통 본문이다.
- `**강사 노트**`는 독립된 한 줄에 둔다. 이후 내용은 코드 블록 밖의 다음 수평 구분선 또는 다음 `## NN. 제목` 전까지 강사 노트다. 노트 안의 `###`는 본문 복귀 신호가 아니다.
- 본문 `###` 이하 heading은 topic 내부 소제목이다. 별도 topic이나 자동 분할 명령이 아니다. 글머리표 없이 **굵게**, 첫 bullet 단계로 들여 그려지며 아래 내용의 단계를 바꾸지 않는다.
- `**기록 그대로**`는 독립된 한 줄이며, 그 topic의 본문이 **실제로 주고받은 기록**(프롬프트·첨부 문서·LLM이 생성한 산출물)임을 뜻한다. 저자가 쓴 글이 아니므로 **핵심어 강조 검사에서 빠진다** — 강조를 더하는 것 자체가 기록을 고치는 일이다. 원본의 경로와 발췌 범위는 강사 노트에 적는다. 별첨의 실습 답에는 `**실제 LLM 응답**`을 그대로 쓴다.
- **기록을 옮길 때는 표시 구조만 바꾼다.** 제목 단계와 목록 들여쓰기를 Deck 문법과 맞춘다. 코드의 표시 줄바꿈은 원본 fence의 내용과 공백을 보존한 채 조판으로 처리한다. 문구·절 번호·강조는 원본과 대조한다.
- **실제 LLM 응답의 생략은 빠진 자리에 `.....` 한 줄로 표시한다.** 반복 목록을 줄일 때는 원문의 앞 2개 항목을 순서대로 보여 준 뒤 `.....`를 적는다. 서로 다른 수용 상황과 시험 조건은 판단과 재현에 필요한 범위를 유지한다. 문장과 항목은 완결된 단위로 옮긴다. 응답 본문에는 발췌 안내, 요약, 저자 설명을 넣지 않는다. 원본 경로와 발췌 범위는 강사 노트에 기록한다. 생략 표시의 설명이 필요한 경우 발췌 마지막 장 하단에 8pt 주석으로 한 번만 둔다.
- `**문서 형식**`은 독립된 한 줄이며, 그 topic을 한 장의 **문서**(예: 유스케이스 명세서)로 그린다 — 실습 답처럼 좌우 두 단, 14/12/11pt. `**문서 형식 — 10pt**`는 문서 본문 전체를 10pt 두 단으로 표시한다. 명세서·템플릿 같은 문서는 표로 쪼개지 않고 항목과 번호를 붙인 이벤트 흐름을 그대로 쓴다. **일반 10pt 문서의 좁은 단에는 읽기 어려운 표를 넣지 않는다.** 실제 응답의 표가 판단에 필요하면 원문 그대로 유지하고, 제작 지침의 좌우형 표 배치와 가독성 기준을 적용한다. 원본의 표를 발췌에서 제외하면 그 자리에 `…..`를 적고 발췌 범위는 강사 노트에 남긴다. 문서에 대한 설명은 문서 뒤 bullet이나 다음 topic에 둔다.
- 문장으로 작성한 수업용 검토 예는 일반 문단이나 목록으로 구성한다. 문단 서식은 Production의 「목록 본문 정렬」을 따른다.
- 템플릿(예: Given-When-Then)은 bullet으로 쪼개지 않고 `text`·`gherkin` 블록으로 원래 모양대로 보인 뒤, 설명을 bullet으로 붙인다.
- `**주석**`은 독립된 한 줄에 두며, 바로 다음 한 문단이 그 topic의 각 슬라이드 아래쪽에 **8pt 주석**으로 표시된다. 본문 흐름에는 들어가지 않는다. 약어의 원어 같은 참고 정보에 쓴다(예: `REP — Release Reuse Equivalency Principle · CCP — Common Closure Principle`).
- `**페이지 분할**`은 독립된 한 줄의 명시적 페이지 분할이다. 분량이 아니라 **의미상 구분**(기본 예와 반례, 서로 다른 소주제)이 있을 때만 쓴다. 성격이 다른 내용이면 여러 장도 좋지만, 한두 줄이나 작은 표 하나를 더하려고 나누지 않는다 — 그 내용을 축약하거나, 맞는 topic으로 옮긴다(학습에 필요한 설명을 노트로 보내 자리를 만들지 않는다. 아래 「넘칠 때는 순서가 있다」). 범례와 그 표, 짧은 표 두 개, 표와 짧은 후속 설명처럼 한 장에 들어갈 수 있는 내용 사이에는 두지 않는다.
- 한 topic이 두 장 이상이면 각 장이 서로 다른 질문에 답하는지 먼저 확인한다. 같은 질문의 설명이 반복되거나 한 장에 들어갈 수 있으면 중복 문장을 줄이고 표·도식을 좌우 또는 상하로 배치해 한 장으로 합친다.
- **넘칠 때는 순서가 있다.** ① 같은 뜻을 지키며 **축약**한다 ② 도식·표의 **모양을 바꿔 조정**한다(가로로 눕히기, 라벨·열 줄이기, 좌우 배치) ③ 둘로 되지 않으면 **그대로 둔다**(두 장이 되어도 좋다). **생각을 덜어내지 않는다** — 설명·근거·사례를 지워 자리를 만들거나, 문장을 `라벨 — 설명` 틀로 접어 추론을 없애지 않는다. 확인한 인용문도 공간 때문에 축약·교체하지 않는다.
- `**다이어그램 — 시퀀스 다이어그램**`은 제목 둘째 줄에 다이어그램 이름을 보이던 이전 표식이다. 새 원고는 쓰지 않는다 — 제목 둘째 줄은 서브 항목의 그룹을 보이는 자리이고, 다이어그램 이름은 도식 제목(`**도식 — … — 이름**`)이 보인다. 이전 원고는 보완할 때 바꾼다.
- `**배치 — 좌우**`는 독립된 한 줄이며, 그 topic의 도식 하나를 오른쪽 반에 두고 본문을 왼쪽에 둔다. 본문이 도식을 항목별로 짚을 때(예: 유형 목록과 그 예의 도식) 쓴다. 표식이 없으면 도식은 본문 아래에 놓인다. **세로로 긴 도식**에만 쓴다 — 넓은 도식은 오른쪽 반에서 7pt 아래로 줄어, Production이 표식을 무시하고 상하로 배치한 뒤 경고한다.
- `**도식 — Mermaid**`, `**도식 — PlantUML**`, `**도식 — SVG**`는 뒤 visual의 유형 표식이다. 표식 끝에 `— 제목`을 붙이면 도식 바로 위의 제목이 된다(`**도식 — PlantUML — 주문 시스템 패키지(상세화)**`). 표는 바로 앞 줄에 `**표 — 제목**`을 둔다. 표와 도식에는 제목을 단다(「6. 표와 목록」). 렌더할 원본은 `mermaid`, `plantuml:<kind>`(`usecase`, `class`, `package`, `sequence`, `communication`, `state`, `activity`), `svg`, `svg:uml` fenced block이다. `svg:uml`은 SVG로 직접 그린 UML(유스케이스 다이어그램·SSD 등)처럼 넓은 도식이다. `java`, `gherkin`, 일반 text block은 학습자에게 보이는 코드·예시다.
- 새 visual 유형이나 표식을 도입할 때는 SA·Production 지침과 파서를 함께 정의한다. 지침 수정만으로 구현이 끝났다고 보지 않는다.

### 참조 형식

이 형식은 Deck의 본문과 검토 의견에 적용한다. Curriculum의 세션 목록·경계 표와 DD의 내부 연결에는 안정된 세션 ID를 사용할 수 있다.

- **세션**은 큰따옴표 안에 `세션`과 정확한 세션명을 함께 쓴다: `"세션 03. 정적 모델 — 도메인 개념과 관계"`. 번호와 제목만 쓰면 이 세션의 목차 항목과 구별되지 않으므로 `세션`을 반드시 붙인다(Production이 오류로 막는다). `S03`, `s03.md`, `"세션 03."`처럼 번호만 쓴 표기도 쓰지 않는다. 본문에서는 세션명만 쓰고, `("세션 01. …"의 첫 시도)`처럼 괄호 안에 세션명과 장면을 덧붙이지 않는다 — 장면은 문장으로 말한다("세션 01. …"에서 보았듯이 …).
- **같은 세션의 topic**은 번호와 제목을 겹낫표로 쓴다: `「26. 주문 취소 시퀀스」`. 번호만 쓴 `「26」`은 참조가 아니다(Production이 오류로 막는다).
- **다른 세션의 topic**은 세션명 바로 뒤에 쓴다: `"세션 02. 요구 분석과 유스케이스"의 「44. 시스템 오퍼레이션과 계약」`. 여러 topic은 `·`, `,`, `과/와`로 잇는다. 그룹의 서브 항목은 그룹 뒤에 붙인다: `"세션 04. 동적 모델 — 상호작용과 상태"의 「06. 시퀀스 다이어그램」의 「주문 취소 시퀀스」·「08. 상태 기계 다이어그램」`. "같은 세션의" 같은 지시어로 대신하지 않는다.
- 세션의 topic 번호를 바꾸면 그 세션을 참조하는 다른 세션을 `node src/cli.js --check <원고…>`로 함께 검사한다(덱은 만들지 않는다).
- 도식의 라벨에는 topic 번호를 쓰지 않는다. 도식은 개념을 가리키고, 번호는 topic이 옮겨지면 틀린다.
- **과제·기능의 이름은 큰따옴표로 쓴다**: `"주문한다"는 두 패턴만 쓴다`, `"신청한다"의 실행 흐름`. 따옴표가 없으면 동사로 읽혀 문장이 흐려진다. 본문·표(제목·열 이름·셀)·강사 노트에 적용하고, **슬라이드 제목과 목차, 「」 안의 topic 참조, 도식·코드 안의 라벨은 제외**한다(제목은 이름표이고, 참조는 가리키는 제목과 한 글자도 달라지면 안 된다).

## 3. 세션 구성

### 세션 목표와 요약

세션의 처음과 끝은 학습자가 승인된 목표와 판단을 한눈에 확인하는 자리다. 현재 목표·요약의 장수와 항목 수 게이트는 Production Guide에 기록한다. 지면이 부족하면 승인 의미를 보존할 표현을 검토하고, 그것으로 해결할 수 없는 경우 제작 결함을 보고한다.

- 목표는 학습자가 확인할 수 있는 성과로 표현한다. 본문 전개를 반복하지 않고 세션 성격에 맞는 동사를 쓴다.

| 세션의 성격 | 형식 | 쓰는 동사 |
|---|---|---|
| **산출물 세션** — 수강생이 실습으로 무엇을 만들어 남긴다 | `…을 작성하고 …을 정의할 수 있다` | 작성한다 · 정의한다 · 정한다 · 고친다 · 판정한다 · 맡긴다 |
| **개요·지도 세션** — 어휘와 판단의 틀을 준다 | `…을 구분하고 …을 이해한다` | 구분한다 · 이해한다 · 설명한다 · 찾아낸다 · 선택한다 |

- 목표는 DD에서 가져온다. 목표가 과정의 학습 성과와 연결되지 않으면 DD와 Curriculum에 환류한다.
- **확인할 수 없는 동사를 쓰지 않는다** — `배운다`·`역량을 확보한다`·`알아본다`·`지양한다`는 모든 목표에 붙어 무엇을 확인할지 가르지 못한다. `이해한다`는 **목적어가 개념의 이름일 때만** 쓴다(`변하지 않는 5가지 원칙을 이해한다`는 되고, `…성립하는 것을 안다`는 안 된다).
- **목표마다 그 세션에서 배울 개념의 이름을 핵심어로 굵게 둔다.** 굵은 말만 이어 읽으면 배울 것의 목록이 되고, 그 이름은 목차 항목·본문 제목의 말과 같아야 한다. 목표 한 장이 지도 노릇을 하므로 목차를 목표 장에 다시 보이지 않는다.
- **목표는 본문의 장과 대응된다.** 어느 목표도 가리키지 않는 내용 장이나, 본문에 없는 목표가 있으면 둘 중 하나가 틀린 것이다.
- 개수를 센 말(넷·여섯·셋)은 **목표·본문·요약·별첨에서 같아야 한다**. 본문에서 개수를 바꾸면 나머지 셋을 함께 고친다.
- 마지막 topic `요약`에는 세션의 핵심 판단과 승인 Curriculum의 다음 세션 연결(`### 다음 세션`)을 둔다. 마지막 세션은 다음 연결을 생략한다.

### topic 구성

- 승인 DD의 목표와 거버닝 메시지를 학습자 본문에 구현한다. 원천 문서의 라벨을 슬라이드에 반복할 필요는 없다.
- 한 topic은 그 주제를 **대화로 설명하듯 충실히** 채운다. 정의·사례·도식·코드를 한 흐름으로 쓰고, 넘치면 줄이거나 자연스럽게 다음 장으로 잇는다. 정의와 적용, 문제·개념·한계 같은 요소별 틀로 topic을 쪼개거나 늘리지 않는다.
- **한 장에서 판단할 질문을 분명히 한다.** 제목은 그 질문이나 주장을 드러내고, lead는 독자가 따라갈 핵심과 필요한 근거를 제시한다. 정의·관계·사례가 그 판단을 설명하는 데 필요한 만큼 쓴다. 실제 제목 크기와 읽기 순서는 Production에서 확인한다.
- **장마다 모양을 바꾼다.** `lead 한 줄 + 표 + bullet 3줄`이 모든 장에 반복되면 세션 전체가 한 틀로 읽힌다. 도식이 끄는 장, 두 축을 맞대는 장, 코드와 테스트가 끄는 장, 기록을 그대로 보이는 장으로 **그 장이 답하는 질문에 맞는 모양**을 고른다.
- 시작은 주제에 맞게 고른다 — 출처 있는 정의 인용, 질문, 사례의 상황. 출처 없는 정의 문장을 지어 인용 앞에 두지 않는다.
- topic 수와 분량은 주제가 정하며 균등 분할하지 않는다. 같은 질문에 답하는 topic이 둘 이상이면 하나로 **병합**한다(세션 안의 DRY). 병합은 heading을 이어 붙이지 않고 한 흐름으로 다시 쓴다.
- **lead는 목록이 아니라 공통점을 말한다.** 뒤따르는 표의 행 몇 개를 골라 `A하고, B하고, C하는 것이 …이다`로 늘어놓으면 왜 그것들이 한 장에 있는지가 빠지고, 고르지 않은 행은 설명되지 않는다. 행들이 **공유하는 원인**을 한 문장으로 말한다(`잘못된 관행은 모두 빈 결정을 보완하지 않고 입력과 실행만 늘린다`).
- **센 수는 그 문장 안에서 호명한다.** `6가지 가운데 하나뿐이다`처럼 수만 말하면 어느 것인지 표에서 다시 찾게 한다. 센 것이 무엇이고 나머지가 무엇인지 같은 문장에서 밝힌다(`에이전트에게 맡긴 것은 주문 금액 구현 하나이고, 나머지 5가지는 수작업·워크플로·대화형 보조로 한다`).
- **대비는 한쪽만 세지 않는다.** 한 축의 몫을 `n가지`로 세어 나열했으면(`사람이 결정하는 것은 5가지다 — …`) 대응하는 축의 몫도 같은 장에서 같은 형식으로 나열한다(`에이전트가 하는 일은 4가지다 — …`). 한쪽만 나열하면 나머지가 비어 보이고, 학습자가 "그럼 저쪽은?"을 스스로 채운다. 자리가 모자라면 덜 중요한 bullet을 빼고 그 내용은 강사 노트로 옮긴다 — 나열을 줄여 균형을 깨지 않는다.
- **사례를 걸어 놓은 표는 모든 칸이 사례여야 한다.** 제목이 `INVEST로 주문 스토리 점검하기`인데 칸이 `다른 스토리와의 의존을 줄임`처럼 속성을 되풀이하면, 사례를 건 제목만 남고 점검한 내용은 없다. 한 칸이라도 일반론이면 그 행은 이 사례에서 무엇을 확인했는지 적는다(`상품·결제·배송 시스템이 운영 중이라 이 스토리만으로 끝남`).
- **잘못된 결과를 말할 때 주어를 밝힌다.** `배송 요청을 보낸 구현도 통과한다`처럼 주어 없이 적으면 그 일이 규칙상 **일어나는** 것으로 읽힌다. 규칙이 금지한 일은 **잘못 만든 구현**이 한다고 적어, 규칙과 구현의 잘못을 가른다(`배송까지 요청해 버린 잘못된 구현도 그 기준을 통과한다`).
- **사례는 쓰기 전에 세운다.** 값(2,000원)·상태 이름(결제대기·결제완료)·단위(배송 요청 1회)·식별자(카드 X·Y)는 **처음 나오는 자리보다 앞에서** 무엇인지 밝힌다. 세션 하나에 **한 번**, 사례를 처음 쓰는 topic에서 한 줄로 세운다(`확인에 사용할 주문은 펜 2개, 판매가 각 1,000원, 배송지 서울이다. 금액은 2,000원이다`). 근거 없이 먼저 나온 값은 학습자가 어디서 왔는지 되짚게 하고, 글쓴이가 지어낸 값과 구별되지 않는다. 뒤 세션이 이미 쓰는 식별자는 **이름을 바꾸지 말고** 그 자리에서 소개한다 — 이름을 바꾸면 세션 사이가 어긋난다.
- **수는 그 수가 센 것을 알 때만 적는다.** `사용자 이야기 4개와 수용 기준 16개`처럼 **무엇을 센 것인지 본문에 없는 수**는 인용이라도 본문에 싣지 않는다. 센 대상(어떤 버그인지)이 없으면 수만 남아 판단의 근거가 되지 못한다. 출처와 수치는 강사 노트에 둔다.
- **시연은 입력 → 실제 응답 → 사람의 판단 순서로 구성한다.** 입력 장에는 실제 프롬프트와 근거 자료를, 응답 장에는 원문이나 원문 발췌를, 판단 장에는 무엇을 채택·확정·보류했는지 적는다. 입력·응답의 절 번호·문구·강조를 보존한다. 응답 발췌는 여러 장에 걸쳐 제시할 수 있다.
- **실제 응답의 분량을 조절할 때는** 원문의 섹션 제목과 순서를 유지하고, 생략한 위치에 `…..`를 표시한다. 응답에 원래 없는 거버닝 메시지나 발췌 설명은 판단 장 또는 강사 노트에 둔다. 시연 입력과 응답이 같은 실행에서 나온 자료인지 확인한다.
- **응답에 포함된 도식은 학습 판단에 필요한 것만 발췌한다.** 원본의 제목·유형과 도식 내용을 확인한다. 제목이 없거나 내용이 중복되는 복잡한 도식은 발췌에서 생략할 수 있다. 필요한 제목이나 단순화한 도식을 저자가 작성하는 경우 원문 응답 밖에서 교재 설명으로 구분한다.
- **시연과 실습 답의 응답은 문서 첫 제목과 첫 문단부터 실어야 한다.** 모델이 생성한 도입 문구는 기록에서 그대로 확인한 뒤 사용한다. 발췌는 그 뒤의 완결된 문장·항목부터 적용하고, 빠진 위치에 `…..`를 표시한다. 첫 절을 건너뛰거나 도입 문구를 대신 작성하지 않는다. 응답 확보를 위해 실행이 요청된 경우, 실제 사용한 프롬프트와 입력·후속 대화, 응답 전문을 먼저 저장하고 결과를 대조한 뒤 교재에 반영한다. 시연의 판단표는 같은 실행의 규칙·질문과 대응시킨다.
- **관계를 말하면 양쪽을 적는다.** `A와 B를 구분한다`·`A는 B가 아니다`로 끝나는 문장은 둘이 무엇인지 말하지 않는다. 양쪽이 답하는 질문이나 양쪽의 값을 같은 문장 안에 적는다(`원하는 결과는 결제하고 배송받는 것이고, 요구사항은 승인 뒤에만 배송을 요청하는 것이다`). 하나가 나머지와 성격이 다르면(산출물 셋 옆의 온톨로지) 같은 목록에 끼워 넣지 않고 그것이 **무엇이 아닌지**를 먼저 말한 뒤 겹치는 관심을 밝힌다.
- **여러 개를 다루는 topic은 묶는 질문으로 순서를 세운다.** 산출물·형식·관점을 여럿 늘어놓기만 하면 읽는 순서가 생기지 않는다. 그것들이 **차례로 답하는 질문**을 lead에 적고 표의 열도 그 질문으로 둔다(`요구사항은 어떤 결과가 필요한가, 도메인 모델은 그 결과가 업무에서 무슨 뜻인가, 설계는 누가 어떻게 실현하는가`).
- **고르는 자리는 과정이 고른 것으로 닫는다.** 형식이나 방법을 여러 가지 보인 topic은 `상황에 따라 고른다`로 끝내지 않는다. 전부를 작성할 필요가 없다는 말 뒤에, 이 과정이 무엇을 **사용하는지** 한 줄로 적어(`사용자 이야기로 쓰고, 흐름의 분기로 빠진 경로를 찾고, 수용 기준과 예로 확인한다`) 뒤 세션에서 볼 것과 잇는다.
- **하나의 사례를 여러 장에서 이어갈 때** 각 장에서 무엇을 새로 판단하거나 기록하는지 드러낸다. 수용 기준 표의 기대 결과, 예시 매핑의 규칙·사례·미정 질문, 합의한 사례의 실행 가능한 테스트를 역할에 맞춰 연결한다.
- **특성이나 기준을 표로 설명할 때** 표 아래 예의 이름과 순서를 표의 항목에 맞춘다. 시연 판단표의 근거 열에는 실제로 보여 준 응답에서 확인할 수 있는 문구만 적고, 사람이 결정한 정책은 판단 및 반영 열에 적는다.
- **인접 항목의 차별성** — 이어지는 항목은 앞 항목에서 이미 설명한 정의·분류를 반복하지 않고, 새로 답하는 질문을 분명히 한다. 비교 다음에는 적용 조건·실행 차이·예외처럼 설명을 진전시킨다.
- 학습자가 이해·판단하는 데 필요한 내용은 **모두 본문**에 둔다. 강사 노트에는 출처 검증과 강의 진행 메모만 둔다(「7. 강사 노트」).
- 과정 밖의 기법(예: 생산 관리의 원인 분석 기법)을 끌어오지 않는다. 과정의 판단은 과정의 모델로 설명한다(예: 역추적은 테스트 → 계약 → 상태 기계·시퀀스 → 유스케이스를 거슬러 오른다).
- 모델링을 다루는 세션에는 해당 기법의 **잘못된 관행** topic을 둔다. 잘못된 예와 바른 예는 표준·원전과 업무 의미에 비추어 정확해야 한다.
- 원칙·프로세스·접근법은 이름을 **명시**한다(예: 폭포수, 반복·점진(I&I), 애자일, 디자인 씽킹(DT), Lean Startup, Lean UX). 설계 원칙의 약어(SRP, CCP 등)는 그 약어가 나오는 topic에 원어를 `**주석**`으로 단다.

### 모델 용어의 설명 순서

- `sw-engineering-principles.md`의 「도메인 모델·설계 모델과 정적·동적 관점」을 따른다. **도메인 모델의 목적과 범위부터** 설명한 뒤 정적·동적 관점, 개념 모델이라는 표현, 다이어그램의 역할을 그 관계 안에서 설명한다.
- 도메인 모델을 클래스 다이어그램 하나로 한정하거나, 도메인 모델·개념 모델·정적 모델·동적 모델을 서로 독립된 산출물처럼 나열하지 않는다. 정적·동적은 분석과 설계 양쪽에 적용되는 관점임을 밝힌다.
- 도식을 소개할 때 무엇의 어떤 관점을 표현하는지 먼저 정한다. 같은 클래스·시퀀스 표기라도 분석의 업무 개념과 설계의 소프트웨어 객체를 구별한다.
- 정적 개념도를 정의하는 원전 인용에는 그 범위를 밝힌다. 넓은 도메인 모델 전체에 해당하는 정의처럼 제시하지 않는다. 실제 LLM 응답의 다른 용어는 원문을 편집하지 않고 본문의 공통 용례와 관계를 설명한다.
- 이 절은 내용 검토의 기준이다. 단어가 등장했는지만 검사해서 모델의 의미·수준·일관성이 검증됐다고 판정하지 않는다. Production은 그림·문장·구조를 보존하고, 의미의 판정은 저자가 맡는다(`production-guide.md`).

### 개요 세션과 상세 세션

- 개요 세션은 전체 흐름과 "왜"를 보이고, 다이어그램마다 **한 장의 미리보기**(다이어그램과 짧은 코드)를 둘 수 있다. 표기·작성법·코드 매핑의 상세는 해당 상세 세션이 맡는다.
- 개요의 단순화는 범위를 줄이는 것이지 **이름과 규칙을 바꾸는 것이 아니다**. 개요의 상태 값·이벤트 이름·업무 규칙은 상세 세션과 같다(「관통 사례와 식별자」).

### 관통 사례와 식별자

- 관통 사례의 **공통 식별자**(용어, 상태 값, 흐름 번호, 이벤트·오퍼레이션 이름, 외부 시스템)는 `course-design.md`의 공통 전제가 원천이다. 원고·다이어그램·예시 코드는 그 이름과 값을 그대로 쓴다.
- 앞 세션의 산출물(명세서·SSD·계약·정적 모델 등)을 뒤 세션의 **입력**으로 명시한다.
- 같은 사례를 표·도식·코드·테스트에서 설명할 때 승인된 값을 유지한다. 추가 교육용 가정은 DD에서 범위를 밝히며, 공통 전제로 승격할 필요가 있으면 Course Design에 환류한다.
- 과정은 **기법을 배우는 것**이 목적이다. 도메인 때문에 복잡도를 높이지 않는다. 관통 사례는 요구 분석에서 정한 장면만 쓰고, 세션마다 새 사례를 더하거나 앞 세션의 가정에 기대는 교육용 가정의 사슬을 만들지 않는다. 필요하면 더 단순하게 한다.
- 뒤 세션이 분석으로 새로 발견한 것은 **진화**다. 앞 세션은 그 시점의 모델로 두고, 뒤 세션이 발견과 원래 산출물로의 되돌림을 해당 topic이나 실습 topic의 강사 노트에 함께 적으며, 공통 전제를 갱신한다. 되돌림만을 위한 별도 중간 산출물은 만들지 않는다.
- 뒤 세션의 답에 앞 산출물에 없던 기능·액터·개념이 있으면 먼저 발견 근거와 되돌림 기록을 확인한다. 분석 과정에서 근거를 갖고 발견한 항목은 앞 산출물에 없다는 이유만으로 삭제하지 않고 진화로 유지한다.
- 같은 대상을 다른 이름·다른 규칙으로 쓴 것은 **오류**다. 공통 전제에 맞춰 앞 세션까지 고친다(Production이 세션 간 코드의 `enum` 값을 대조한다).
- 세션이 다루는 산출물이 **요구에서 코드까지의 경로**에서 어디에 있는지 밝힌다. 불변의 뼈대(요구 → 사용자 이야기(수용 기준 포함) → 코드·테스트)인지, 어느 축(도메인·기술 복잡성) 때문에 넣는 중간 산출물인지를 쓴다. 산출물의 이름(요구사항 정의서·작업 명세서·도메인 모델·아키텍처)은 `sw-engineering-principles.md` 7절의 정의를 따른다. 사례에 필요 없는 산출물을 만들지 않으며, 오래 남는 산출물(요구사항 정의서·도메인 모델·의존 규칙)은 가리키고 다시 쓰지 않는다.
- **용어집**(Glossary)은 요구 분석 세션에서 정의하고(용어·정의·영문명), 뒤 세션은 모델마다 그 이름을 쓰는지 **환기**하고 발견한 용어를 되돌린다. 용어집을 세션마다 새로 정의하지 않는다.
- **분석은 한글, 설계는 영문**이다. 분석 모델(도메인 모델·분석 시퀀스·상태 기계)과 분석 예시 코드는 한글 용어를, 설계 모델(패키지·설계 클래스·설계 시퀀스)과 설계 코드는 **용어집의 영문명**과 과정의 **명명 규칙**을 쓴다. 본문 문장은 한국어로 쓰고, 설계 이름을 가리킬 때는 코드 표기(`Order`)를 쓴다. 전환이 처음 일어나는 세션에서 용어집 → 설계 이름의 대응을 보인다.

### 사례·가정·실습

- 사례의 주어진 사실, 교육용 가정, 추가 확인할 사항을 구분한다. 새 가정은 해당 예시 범위에서 명시하며 실제 정책이나 표준 요건처럼 제시하지 않는다.
- 사례를 다른 topic에서 재사용할 때 전제·용어·성공 조건을 유지한다. 성공 경로만 다루는 예시는 그 범위를 밝힌다.
- 실습은 DD에서 승인한 판단과 LLM 사용 방식을 구현한다. 실제 불일치가 있으면 근거와 필요한 수정을 평가하고, 기준을 충족하면 확인 근거를 남겨 승인하는 것도 평가한다.
- 과정이 승인한 시나리오와 실습 인계를 구현한다. 강의와 실습에서 같은 사례를 사용하면 확정 규칙과 실습에서 추가한 조건의 출처를 구분한다. 선행 실습 결과가 입력이면 실제 수업에서는 학습자가 만든 결과를 이어 사용한다.
- 실습의 결과물 종류·범위와 필요한 투입물은 승인 DD, 세션 간 인계는 Curriculum에 맞춘다. 본문에서 결과물의 형식을 확인할 수 있게 한다. 승인된 투입물의 전문이 필요한 경우 전문을 사용한다.
- **실습 답은 별첨이다.** 과제는 본문, 답은 요약 뒤 `## 별첨. 실습 답` 아래에 산출물 이름을 제목으로 둔다. 답의 공개 순서와 선정 자료는 DD를 따른다. 실제 응답과 저자의 해설을 구분한다. 별첨은 목차에 넣지 않는다.
- 실습 사례도 도메인 복잡도를 높이지 않는다. 새 업무 개념이나 규모를 들이는 변경을 만들지 않는다. 가능한 모든 경우를 열거하게 하지 말고, 다음 작업에 필요한 핵심 결정에 집중한다. 다음 단계로 진행할 수 있으면 탐색을 끝낸다.
- 짧은 업무 조건 확인 실습은 다음 작업에 필요한 핵심 조건만 담은 간결한 Markdown 메모를 요청한다. 실습의 출력은 업무 산출물이며 PPT 분량·폰트·배치·renderer 조건은 프롬프트에 넣지 않는다. 범위·문서 구조·출력 형식은 마지막 프롬프트에 포함한다. 답이 업무 범위를 벗어나 과도하면 저자가 줄이지 않고 피드백으로 보완·재생성한다. 슬라이드의 지면 부족과 업무 산출물의 범위 초과를 구분한다. 질문 개수를 임의로 제한하는 대신 다룰 업무와 제외 범위를 명확히 한다.
- 실습 편성과 시간은 승인 Curriculum을 따르고 과제별 조건은 DD를 따른다. 실제 수행 시간의 차이는 Curriculum/DD로 환류한다.

#### 실습 검증과 Production 연결

- Human이 실습 목적·문제·조건·검증 기준을 DD에서 승인한 뒤, 실행 담당은 동일한 초기 입력·파일·환경 조건에서 필요한 만큼 독립적으로 반복 실행해 실행 가능성을 확인한다. 실행 안의 보완 대화와 초기화 후 새 실행을 구분한다. 실행 조건·도구와 모델·실제 프롬프트·AI 응답·코드와 테스트 결과를 기존 `code/sNN/exercise-conversation/` 기록에 연결한다. 대표 실행의 선택 이유를 남기고 결과를 재작성·미화하지 않는다. 학습상 의미 있는 실패도 보존하고 강사 설명과 구분한다. 선정한 결과가 다음 실습·세션의 투입물과 일치하는지 확인한다.
- 실습 과제(`NN. 실습 M — …`)는 승인된 DD의 과제 단위를 보존한다. `NN`은 세션 안의 topic 번호, `M`은 과정의 실습 번호다. 안내의 현재 장수·좌우 게이트와 이어지는 실습의 적용 조건은 Production Guide에서 확인한다. 학습자 화면에는 다음 정보를 둔다.
  - 안내 문장 한 줄 — 무엇을 LLM에 제공해 무엇을 만들고, 점검 항목으로 피드백해 완성하는지
  - `**서비스 개요**`(첫 실습) 또는 `**투입물**`: 본문은 `+ ` 줄로 쓴다. 투입물은 topic 번호가 아니라 **실습 단위**로 가리킨다(예: "실습 3의 도메인 모델 상세"). 앞 실습의 산출물을 읽는 실습은 **빠짐없이 투입물을 적는다** — 강사 노트에만 적지 않는다.
  - `**결과물**`: 수강생이 만들 **파일 이름**(`주문한다-정적모델.md`)과 그것이 **몇 번 실습의 투입물**인지를 적는다. 다음 실습이 그 이름으로 가리키므로 이름 없이 "최종 MD"로만 두지 않는다.
  - 요청 배경까지 프롬프트에 담은 실습은 표식을 `**프롬프트 — 요청사항 포함**`으로 쓴다. 그래도 **투입물 항목은 둔다** — 무엇을 들고 와야 하는지는 프롬프트 문장 안이 아니라 한 줄로 보여야 한다. 앞 실습의 산출물이 없는 첫 실습만 `**서비스 개요**`를 두거나 둘 다 두지 않는다.
  - `**프롬프트**`: 본문은 두 칸 들여쓴 `+ ` 줄로 쓴다. 점검 항목 번호 목록과 결과물 본문도 해당 소제목 아래에서 두 칸 들여쓴다. 수강생이 LLM에 그대로 입력하는 문장이며 필요한 만큼만 둔다. 보통 한두 개이며, 복잡성을 단계적으로 다루는 실습은 간단한 시작 요청 → 범위 제한 → 누락 보완 → 표현 구체화 → 최종 파일 요청처럼 ①~⑤로 나눌 수 있다. 각 프롬프트는 한 가지 역할을 맡는다. ①~⑤는 고정된 대화 횟수가 아니라 진행 단계다. ②~④는 수업 시간 내 보완 대화의 예시이며 실제 답변에 따라 통합·변경·추가·반복한다. 두 번이나 열 번의 보완도 가능하며 정해진 횟수를 채우지 않는다.
  - **대화창에서 검토하고 파일로 이어 간다.** Codex·ChatGPT·Claude Team 등 특정 제품에 종속시키지 않고 수강생은 renderer 없이 실습한다. 모델링 실습은 필요한 다이어그램을 대화창에서 보고 판단하도록 요청한다. 환경별 표시 지원은 사전에 확인하고 코드만 표시되는 경우를 시각 검토 완료로 보지 않는다. 도구별 실행 방법은 별도로 안내한다. 최종 MD에는 도식 원본과 이해에 필요한 설명을 보존한다.
  - **실제 응답과 관련 프롬프트를 연결한다.** 실제 실행을 재현하는 고정 문구는 해당 입력 그대로 사용한다. 수강생이 채울 피드백과 실행 기록의 실제 답을 구분한다.
  - **후속 프롬프트에는 답과 피드백을 함께 입력한다.** ①~⑤ 흐름에서는 ②~④에 앞선 LLM 질문에 대한 수강생의 답과 필요한 추가 질문·수정 요청을 붙이도록 학습자 본문에 안내한다. 기본 문구만 차례로 입력하게 하지 않는다. `[앞선 질문에 대한 답]`과 `[추가 질문·수정 요청]` 두 칸으로 안내할 수 있다. 질문이 없으면 검토 결과나 필요한 수정 요청만 적는다.
  - **기본 조건과 실제 입력을 구분한다.** 가상 사업의 정책을 모두 창작하는 것이 목적이 아니므로 기본 업무·품질 조건을 제공할 수 있다. 수강생은 실제 받은 질문에 맞춰 답을 작성한다. 강사 예시는 각 응답을 검토한 뒤 후속 답을 작성하고, 그 내용까지 포함한 실제 입력 전체를 보존한다. 질문 개수를 채우거나 모든 경우에 답하도록 요구하지 않는다.
  - 범위와 출력 조건을 프롬프트에 구체적으로 포함해도 답을 검토할 `**점검 항목**`을 함께 둘 수 있다. 순서 안내만 필요하면 `**진행 방법**`을 둔다. 각 답을 읽고 다음 프롬프트로 범위·내용을 다듬은 뒤 마지막 요청으로 파일을 받는 순서를 짧게 안내한다. 프롬프트에 없는 요구를 숨은 점검 기준으로 추가하지 않는다.
  - `**점검 항목**`: 승인 DD의 판정 기준을 확인 가능한 질문이나 기대 결과로 적는다. 업무상 미정은 무리하게 결정하지 않고 근거·확인 질문을 드러낸다.
  - `**결과물**`: 다음 실습에 명시적으로 첨부할 최종 MD 파일을 적는다. 제출 여부와 무관하게 다음 실습의 투입물로 사용한다. 다른 대화나 공유 프로젝트의 기억만으로 전달됐다고 가정하지 않는다.
  - **⑤의 범위는 실습 목적과 다음 입력이 정한다.** 최종 MD는 수강생이 검토하고 다음 실습에 사용할 업무 산출물이다. PPT 장수 제한을 프롬프트에 넣지 않는다. 선정한 실제 응답의 분량 때문에 조판 문제가 생기면 의미·문구를 바꾸지 않고 Production의 기존 배치·분할 규칙을 사용한다.
  - **⑤는 합의 결과의 파일화다.** 새 분석·정책·결정을 추가하지 않고 마지막 합의를 Markdown 파일로 생성한다. 수강생은 누락·불일치·폐기한 안의 재등장을 확인하고 필요하면 보완 대화와 ⑤를 반복한다. 점검항목을 충족하고 다음 실습을 시작할 수 있으면 탐색을 끝낸다.
  - 저장소·파일 경로(`code/…`)는 학습자 본문에 쓰지 않고 강사 노트에 둔다.
  - 승인된 **입력·과제·추천 프롬프트·결과물·검토 기준**을 학습자에게 표시한다. 검토 기준의 세부 해설, 단계별 시간 배분, 강사 개입과 운영 지시는 강사 노트에 둔다. 실제 실행을 검증할 때는 승인 DD의 기준·시간, 선행 확정 산출물, 실제 입력·최종 응답을 대조한다. 제작까지 요청받으면 코드 발췌와 원본도 대조한다.
- 답은 별첨(`## 별첨. 실습 답`)의 번호 없는 서브 항목이며 제목은 산출물의 이름이다. 앞 실습의 결과물을 그대로 이어 받는 **하나의 시나리오**로 쓴다. 요구사항 정의 이전의 업무 조건 확인 실습은 합의한 조건과 필수 미정 사항을 함께 남길 수 있다. 이를 확정된 요구사항으로 설명하지 않는다.
  - 텍스트 답은 산출물 전체를 요약하는 **거버닝 메시지**(글머리표 없는 문단, 예: 명세서의 서비스 개요)로 시작한다. 거버닝 메시지는 두 단 위 전체 폭에 놓이고, 나머지는 한 장에 좌우 두 단으로 배치된다. 저자가 작성한 설명용 답도 생략 위치를 `…..`로 표시할 수 있다. 선정한 실제 LLM 응답은 아래의 원문 보존 규칙을 따르며, 원본에 없는 거버닝 메시지를 덧붙이지 않는다.
  - 도식 답은 도식과 글을 상하로 배치한다.
  - 산출물이 여럿이면 topic을 나눈다(예: `유스케이스 다이어그램`, `유스케이스 명세서`). 실습하지 않는 설명용 답도 둘 수 있다.
- **실습 답의 역할과 시점** — 실습 문제·검토 기준·프롬프트는 DD가 소유한다. 실제 실행, 원본 보관, 검증, 대표 답안 선정 근거와 별첨 반영은 위임받은 실행 담당이 수행한다. 개정된 프롬프트로 아직 실행하지 않았다면 기존 실행의 최종 응답을 새 프롬프트의 정답으로 간주하지 않는다. 이전 응답은 실행 기록에 보존하고, 새 원고의 별첨은 실행·선정 후 삽입한다. 원고에 선정된 답이 없는 상태로 최종 Production을 진행하지 않는다.
- **실습·초안검토의 구현** — 승인된 좌우형 안내는 왼쪽에 입력·과제·결과물, 오른쪽에 추천 프롬프트·검토 기준을 둔다. 비교를 승인한 DD가 있을 때만 같은 대상·범위로 초안과 최종안을 대응시킨다. 실습 1장·좌우 영역·별첨 흐름·가독성의 출력 판정은 `production-guide.md`와 승인된 과정별 제작 계약이 정한다.
- **노테이션 도식 동반 게이트(강제)** — 상태 기계·시퀀스의 구성 요소를 소개하는 장에는 실제 UML 도식과 해당 표기 이름·의미가 **같은 슬라이드에** 존재해야 한다. 텍스트만 있는 노테이션 슬라이드는 FAIL. 최소한 상태 기계의 초기점·상태·전이·자기 전이·가드/반응, 시퀀스의 참여자/생명선·메시지 화살표·응답·세로 순서가 도식에서 식별되어야 한다. 그림을 단순한 장식으로 보지 말고 설명과 위치가 대응하는지 검사한다.
- **실습 답의 표현** — 승인 DD가 정한 공개 순서와 출처·발췌 범위를 보존한다. 원문 셀 값을 화면에 맞추려고 바꾸지 않는다. 폭·분할·가독성 예외는 `production-guide.md`와 적용 과정의 승인된 제작 계약에서 확인한다.
- **실제 LLM 응답을 별첨으로 제시할 때** — 입력·중간 응답·최종 Markdown 전문을 보존하고 같은 실행에 연결한다. 전체 또는 DD가 허용한 발췌 범위를 원문으로 싣고 생략과 원천을 노트에 표시한다. 저자의 설명은 응답 밖에 둔다. `**실제 LLM 응답**`의 검증 범위와 생략 표식은 Production Guide를 따른다. 조판 때문에 응답·업무 조건·프롬프트를 바꾸지 않는다.
- 앞 산출물에 환류할 새 요구·규칙·개념이나 관계는 근거와 영향 범위를 기존 기록에 남긴다. 학습 진행에 필요한 환류 안내는 노트에 두고 실제 답안에는 최종 응답과 구분한다.
  - 거버닝 메시지: 새로 발견한 것은 **후속 작업에 영향을 미치는 경우에만** 이전 산출물에 반영한다.
  - `**※ 현행화 기준**`에 **반영**(다음 실습의 입력이 되는 것)과 **기록만**(지나간 산출물이라 비용 대비 가치가 있을 때만 현행화하는 것)을 나눈다.
  - 앞 실습의 판단을 뒤 실습이 고치는 것은 **진화**다(예: 정적 모델에서 배송 회차에 둔 상태를 동적 모델이 정기배송 상태로 되돌림). 앞 답은 고치지 않고 그 사실을 강사 노트에 적는다.
- 필요한 학습 내용과 품질을 먼저 완성한다. 정해진 시간이나 topic 수를 이유로 필요한 설명·사례·실습을 줄이지 않는다. 시간의 적합성은 최종 SA 완성 후 판단한다.

### 원고 수준 유지

- 새 topic도 「topic 구성」의 기준(충실함, 2줄 이내의 문장, 도식과 맞물린 bullet)으로 쓴다. 기존 topic의 형식을 그대로 복제하지 않는다.
- 개편 후에는 전·후 topic 목록을 비교해 **사라진 개념**이 없는지 확인한다. 의도적으로 뺀 개념만 빠져야 한다.

## 4. 문장과 강조

### 문체와 용어

- topic 제목은 **한글 중심의 짧은 키워드**다. 두 줄로 넘어가거나 우측 상단 세션명과 겹치지 않게 하고, 설명은 본문 첫 문장에 둔다. 제목에 **따옴표를 쓰지 않는다** — 잘못된 믿음이나 발언을 다루는 topic도 명사구로 쓴다(`"가드레일이 막아 줄 것"` → `가드레일 과신`). 그 믿음은 본문 첫 문장이 말한다.
- 일반 기술 용어는 한국어를 우선한다. 영어가 필요하면 본문 최초 등장 시 `한글(English full term, 약어)`로 쓰고 이후에는 한국어나 약어만 쓴다. 표준명·고유명사·약어·코드 식별자는 원문을 유지한다.
- 도식 안의 텍스트도 불가피한 표준명·고유명사·약어가 아니면 한국어를 우선한다. 한 라벨에 `제목 - 설명`을 담을 때는 `-`로 구분한다.
- **본문은 슬라이드 자신을 가리키지 않는다.** "표는 넷을 나란히 둔 것이다", "표의 오른쪽 열이 …이다", "지금까지 넷이 나왔다", "셋째 줄이 이 세션이다"는 내용이 아니라 슬라이드의 가구를 설명하는 말이다. 표·도식 앞뒤의 문장은 **무엇을 가려내고 무엇을 판단할지**를 말한다 — "표는 네 수단을 나란히 둔 것이다"가 아니라 "사람에게는 규칙이지만 에이전트에게는 **지켜질 확률**이다". 고치는 방법은 「6. 표와 목록」에 있다. Production이 본문을 검사해 경고한다(강사 노트는 진행 메모이므로 "표의 마지막 행이 핵심이다"처럼 표를 가리켜도 된다).
- 본문에 **사족**을 쓰지 않는다 — "이 과정의 …", "이 과정은 …", "이 과정에서"처럼 과정 자신을 가리키는 말 없이 내용만 쓴다(예: "이 과정의 SDD 지침" → "SDD 지침"). 원고 작업의 내부 용어(group, topic 등)도 본문에 쓰지 않는다(→ "목차"). 출처와 해석을 가르는 말("…는 원전의 분류가 아니다")은 강사 노트에 둔다.
- 명세에 관한 이름은 `sw-engineering-principles.md` 7절을 기본으로 한다 — **사용자 스토리**(User Story. 과정의 `course-design.md`가 다른 표기를 명시하면 그 표기를 따른다. 짧게 가리킬 때는 **스토리**), **수용 기준**(테스트 기준. "확인(예)"라고 쓰지 않는다. OOAD는 "인수 조건"), **요구사항 정의서**(시스템 전체·유지), **작업 명세서**(스토리 하나·작업용). 용어를 한 과정 안에서 일관되게 사용하고, 다른 과정의 승인된 원고는 이 문장 변경만을 이유로 일괄 수정하지 않는다.
- 구체적인 값이나 사건 순서가 있는 예는 **사례**, 그 사례에서 충족할 결과나 판단 조건은 **수용 기준**이라 한다. 예를 들어 ‘결제 거절 뒤 재결제’는 사례이고 ‘승인 전에 배송을 요청하지 않는다’는 수용 기준이다.
- LLM과 주고받는 내용은 **응답**이라 한다. 필요하면 ‘첫 응답’, ‘수정 요청에 대한 응답’으로 구별한다. 산출물을 검토할 때는 ‘응답에 포함된 모델’처럼 그 이름을 쓴다. **초안**은 검토 전 상태의 모델·문서를 가리킨다. 수업용으로 작성한 예는 ‘검토할 모델’처럼 표시한다.
- **수는 숫자로 적는다.** 2 이상은 숫자에 세는 말을 붙여 쓰고(`3가지`·`5단계`·`11세션`·`4개`·`6원칙`), 한 눈에 세어지게 한다. 다만 **'하나'를 뜻하는 관형어**는 한글로 둔다(`한 번`·`한 줄`·`한 장`·`한 가지`) — `1번`·`1줄`은 번호로 읽힌다. **횟수의 '번'**도 한글이다(`두 번`·`세 번`). 숫자를 붙이면 어색한 말(방식·상태·조건·전이·자리·단위·항목)은 세는 말을 바꿔 쓴다 — "세 방식" → `3가지 방식`, "작업 단위 넷" → `작업 단위 4개`. 세는 말 없이 홀로 쓴 수(`달라지는 것 셋`)도 세는 말을 붙여 숫자로 쓴다(`달라지는 것 3가지`). 일괄 확인·변환은 `node tools/normalize-numbers.js [--apply] <원고…>`로 한다.
- **널리 쓰는 말로 쓴다.** 드문 말·은유·구어는 표준적인 말로 바꾼다 — 쪼개다→**나누다**, 내내→**계속**, 끌어내다→**만들다**, (활동을) 돌다→**수행한다**, 쪽→**영역**. **'쓰다'는 자리마다 갈라 적는다** — 글·코드·테스트·문서는 **작성한다**, 도구·방식·값·이름은 **사용한다**. "테스트를 쓴다"가 아니라 "테스트를 **작성한다**", "도구를 쓴다"가 아니라 "도구를 **사용한다**"다. 읽기·쓰기 권한의 **쓰기**는 그대로 둔다. 개념·속성·규칙의 의미를 정하면 **정의한다**, 값·사례·결정·미정 질문을 문서나 모델에 남기면 **기록한다**로 쓴다. 점검 문장은 **무엇을 대조하거나 확인하는지**를 명시한다. **AI가 코드·테스트·문서를 내놓는 것은 생성한다**로 쓰고 사람이 작성하는 것과 가른다 — "에이전트가 만든 테스트" → "에이전트가 **생성한** 테스트". 모호한 동사는 구체적으로 쓴다("묻지 않고 골랐다" → "묻지 않고 **임의로 선택했다**"). **사역·피동을 줄인다**("적용하게 만든다" → "적용한다", "정해진다" → "결정된다"). 일반적인 사실은 **현재형**으로 쓴다("비용을 크게 줄였다" → "줄인다"). 과정이 쓰는 은유(결정의 왼쪽·오른쪽, 한 바퀴 돈다)는 그 자리에서만 쓰고 다른 문장에서 되풀이하지 않는다.
- **짧은 토박이 동사를 기술 용어 자리에 쓰지 않는다.** 아래 왼쪽은 일상 대화에서도 잘 쓰지 않는 말이거나, 교재의 문맥에서 뜻이 흐려지는 말이다. 오른쪽으로 적는다(2026-11-06, `node tools/check-wording.js <원고…>`가 검사한다).

| 쓰지 않는다 | 쓴다 |
|---|---|
| 가르다·갈리다 | **구분한다 · 나뉜다 · 결정한다** |
| 고르다 | **선택한다** |
| 재다 | **측정한다** |
| 쌓다(산출물·층을) | **완성한다 · 갖춘다** |
| 남다(원칙·결론이) | **있다 · 유지된다** |
| 알다(목표 문장에서) | **이해한다 · 설명한다** |
| 듣다(방식이 잘 듣지 않는다) | **적합하지 않다** |
| 돌리다·돌려 보다(검사를) | **실행한다** |
| 커지다(중요성이) | **중요해진다** |
| 적다(점검 항목을) | **확인한다** |
| 되돌림·되돌린다(실패를) | **롤백**(원인이 된 결정으로 거슬러 오르는 뜻이면 **되짚는다**) |

- **은유로 만든 말을 쓰지 않는다.** 뜻이 통할 것 같아 지어낸 말은 읽는 사람에게 한 번 더 번역을 시킨다 — `목록에서 걸린다`(→ 목록으로 하나씩 확인한다), `읽고 가리는 일`(→ 읽고 판단하는 일), `초안이 값싸졌다`(→ 초안을 생성하는 비용이 거의 들지 않는다), `죽은 문서`(→ 더 이상 사용되지 않는 문서). 표준 용어가 있으면 그것을 쓰고(`시맨틱 갭`, `집약`, `다중성`), 과정 설계의 용어집이 정한 이름을 세션이 바꾸지 않는다.
- **추상적인 말 대신 그 자리의 이름을 적는다.** `이름`·`값`·`것`처럼 무엇이든 가리킬 수 있는 말은 무엇을 맞추라는 것인지 말하지 않는다. 그 자리의 이름으로 적는다 — `용어집에 없는 이름` → **속성명**, `선 위의 이름` → **연관명**, `용어집의 이름과 코드의 이름` → **속성명과 필드명**. 세션 목표도 같다(`업무의 뜻을 객체·속성·관계·조건으로 정의한다`, 2026-11-04).
- **반례는 무엇이 통과해 버리는지로 적는다.** `…만 맞아도 통과한다`처럼 조건절에 넣으면 무엇이 잘못됐는지 보이지 않는다. 빠뜨린 확인과 그 때문에 통과하는 결과를 나란히 적고, 더할 확인을 하위 bullet에 둔다(`거절 뒤 상태가 결제대기인 것만 보면, 배송 요청이 나갔더라도 통과한다` → `배송 요청 0회도 함께 확인한다`).
- 질문 문장은 `?`로 끝낸다. topic 제목도 의문문이면(`사용자 이야기란?`, `무엇을 누가 쓰는가?`) `?`를 붙인다(Production이 경고한다). 문장을 단순 정의로 끝내기보다 앞뒤 학습 흐름이 이어지게 쓴다.
- **지어낸 번역어를 쓰지 않는다.** 영어 용어를 뜻으로 풀어 새 한국어 낱말을 만들면 교재에만 있는 말이 되고, 읽는 사람은 그 말을 한 번 더 번역해야 한다 — `되돌림`·`되돌린다`(→ **롤백**), `되먹임`(→ **피드백**)이 그런 예다. 업계가 그대로 부르는 말이면 **그 말을 쓴다**. `node tools/check-wording.js <원고…>`가 함께 본다.
- 억지 번역보다 **통용되는 발음 표기**를 쓴다(예: round-trip test → 라운드트립 테스트, "왕복 테스트"가 아니다; UML frame → 프레임, "조각"이 아니다). 처음 등장할 때 원어를 병기하고(`프레임(frame)`) 뜻을 한 문장으로 정의한다. 이후에는 음차만 쓴다.
- **아직 가르치지 않은 수단은 짧은 이름으로 부르지 않는다.** "네트워크가 닫혀 있으면"처럼 설정의 이름만 던지면 무슨 뜻인지 추정해야 한다. 그 수단을 정의하는 topic 전에는 **무엇을 하는 것인지 구로 풀어 쓰고**("환경이 밖으로 나가는 통신을 막으면"), 정의한 뒤부터 짧은 이름(네트워크 차단)을 쓴다.
- **과정이 정한 이름은 규칙처럼 제시하지 않는다.** 저장소의 폴더·파일 경로(`docs/`, `AGENTS.md`)는 이 과정이 그렇게 두기로 한 것이지 도구가 아는 이름이 아니다. 본문은 **누가 무엇을 하는지**로 쓰고("사람이 저장소에 넣어 둔 규격 문서만 읽는다"), 경로와 그것이 예시라는 사실은 강사 노트에 둔다("예를 들면 `docs/`다").
- **업계 표준 용어**를 쓴다. 표준 용어를 은유적 조어로 바꾸지 않는다(예: 인터페이스를 "약속", 변환을 "옮기기", 패키지 나누기를 "묶기"로 부르지 않는다). 처음 쓰는 설계 요소는 무엇인지 한 줄로 밝힌다(예: 연동 — 외부 시스템과 통신하는 클래스).
- 도식에 나온 이름(참여자·클래스·패키지)을 본문에서도 **그대로** 쓴다. 도식에 없는 이름으로 설명하지 않는다.
- 용어는 과정 전체에서 같은 뜻으로 쓴다(예: 유스케이스에서 `이벤트 흐름`이 기본 용어이고 `시나리오`는 특정 경로다).
- 한 bullet에 `라벨 — 설명`을 담을 수 있다. 두 부분이 같은 비중으로 강조돼야 하면 별도 줄과 하위 bullet으로 나눈다.
- **라벨은 주어와 술어를 갖춘 평서문으로 쓴다.** 주제만 적은 명사 라벨(`결과 —`, `병목의 이동 —`, `예 —`, `다른 이름 —`)은 술어를 생략해 읽는 사람이 뜻을 추정하게 한다. 라벨 하나가 그 장에서 주장하는 바를 그대로 말하게 한다(`AI는 우연적 복잡성을 줄인다`, `병목은 본질적 복잡성에 있다`). 라벨과 설명은 **문법으로 호응**하고(`방식을 … 부른다`), 같은 말을 되풀이하지 않는다(`책임은 그대로다 — 옳은 결과의 판단과 책임은 사람에게 있다` → `책임은 세 방식에서 같다 — …`). 설명이 라벨을 되받아 쓰지 못할 만큼 한 문장으로 충분하면 라벨을 없애고 **한 문장**으로 쓴다(`숙련자가 규율을 지키며 LLM을 사용하는 방식을 바이브 엔지니어링(vibe engineering)이라고 부른다`). **행위에는 주체를 적는다** — 결과만 적거나(`결과는 자바 파일 15개와 테스트 3개다`) 피동으로 쓰면(`검사는 사람이 보기 전에 실행된다`) 누가 하는 일인지 사라진다(`에이전트가 자바 파일 15개와 테스트 3개를 생성했다`, `에이전트가 사람에게 보이기 전에 검사를 실행한다`). 용어를 소개하는 자리의 용어 라벨(`AI 지원 — …`)과 요약의 항목 라벨은 예외다.
- **설명에는 관통 사례의 값을 적는다.** 라벨을 지우고 설명만 읽어도 무엇을 말하는지 알 수 있어야 한다. 추상 명사로 일반화한 설명(`업무 규칙을 찾고, 정하고, 검증하는 것이다`)은 그 세션의 사례 값으로 바꾼다(`주문 금액·배송 요청·결제 거절을 결정하고 검증하는 일이다`). 사례 값이 표와 강사 노트에만 있고 본문이 일반론이면 본문이 겉돈다 — topic마다 본문에 값이 **하나 이상** 있게 한다(세션 목표와 요약은 예외다).
- **문장은 기계적으로 검사되지 않는다.** 위의 두 규칙과 「널리 쓰는 말로 쓴다」는 Production이 보지 못한다. 「12. 검토 절차」 8에서 사람이 읽어 확인한다.

### 강조(bold)

- bold는 **판단에 필요한 핵심 키워드와 대비되는 개념**에만 쓴다. 한 문장 전체를 bold로 하지 않는다.
- 본문의 lead 문장과 bullet에는 핵심어를 **1~3개** bold로 둔다. 문장은 먼저 문장으로 읽혀야 하며, bold는 핵심어를 보조한다(핵심어만 늘어놓은 문장을 쓰지 않는다). 대비는 양쪽을 모두 bold로 한다.
- 질문 목록은 질문마다 **초점어**를, 절차 목록은 단계마다 **산출물·대상**을 bold로 한다.
- 표의 첫 열이 짧은 **항목명**이면 첫 열을 bold로 한다. 문장·예시·질문으로 된 열은 bold를 두지 않는다.
- 예외 — 유스케이스 흐름의 단계(명세 원문), 인용된 요청(`>`), 명사만 나열한 짧은 bullet, 강사 노트, 코드·도식 안의 텍스트. 코드의 선언된 이름은 Production이 bold로 표시하므로 코드 블록에는 `**`를 쓰지 않는다.
  - 실습 번호와 파일명만 나열한 투입물 목록, 파일명에서 다음 실습 입력으로 잇는 경로 표기는 명사 목록이다. 뒤에 수행 지시나 설명 문장이 붙으면 일반 문장으로 검사한다. 실제 실행 프롬프트는 원문 보존과 강조 규칙의 충돌을 별도 기록한다. 저장 실행과 일치를 확인한 개별 블록에 한해 해당 검사만 제외하는 방식은 `production-guide.md`의 「과정별 제작 기준」을 따른다. 실습 topic 전체를 검사에서 제외하지 않는다.

## 5. 인용과 출처

저자·책·논문·표준·공식 문서에 귀속되는 문장이나 수치는 **인용문 그룹**이다. 영어 원문이 없는 통계·정의·주장도 출처가 있으면 같은 형식을 쓴다.

- 인용은 그 topic의 **핵심 메시지를 받칠 때**만 쓴다. 같은 주장을 되풀이하거나 본문이 이미 설명한 것을 장식하는 인용은 두지 않는다.
- **인용의 재선정** — 중복 설명을 제거할 때는 그 설명을 받치던 인용도 함께 재검토한다. 필요한 인용을 공간 때문에 줄이지는 않되, 중복된 주장을 보존하려고 인용을 남기지도 않는다.
- 인용문은 길이와 관계없이 **한 문단 하나의 인용**이다. 2줄 규칙을 적용하지 않는다.
- **한글 쪽은 따옴표 없이 한 문장**으로 쓴다: `한글 한 문장, "English original", [저자 연도]`. 한글은 18pt, 원문과 출처는 10pt로 렌더된다.
  - 한글은 원문을 **옮긴 문장**이므로 따옴표로 감싸지 않는다. 문맥에 필요한 쉼표는 자연스럽게 쓴다. 한글 내부의 쉼표는 크기 변경의 경계가 아니며, renderer는 따옴표로 감싼 영문 원문과 마지막 출처 레이블을 구분해 한글 전체를 18pt로 유지한다. 영어 원문이 없을 때도 출처 레이블 앞까지가 한글 영역이다.
  - 영어 원문이 길면 전문을 옮기지 않고 **핵심만** 옮기되, 원문에 없는 말을 더하지 않는다. 글쓴이가 **한 일을 보고**하는 문장은 과거형으로, **해야 할 일을 말하는** 문장은 현재형으로 옮긴다.
- topic을 여는 인용은 그 topic의 lead 메시지가 된다(예: 저자의 포지셔닝 문장).
- 정의 인용 아래에서 그 정의의 기준을 주는 인용은 **들여쓴 bullet**로 둘 수 있다. bullet 한 줄이 아래 형식이고 영어 원문과 레이블을 갖추면 `**인용문**` 표식 없이 인용으로 렌더된다(`paragraphs.js`의 `bulletCitation`).

```text
**인용문**

응집도는 한 요소의 책임들이 **얼마나 강하게 관련되고 집중되어 있는가**의 척도다, "cohesion … is a measure of how strongly related and focused the responsibilities of an element are.", [Larman 2004]

  - 모듈은 **오직 하나의 액터**에 대해서만 책임져야 한다, "A module should be responsible to one, and only one, actor.", [Martin 2018]
```

- 형식: `한글 한 문장, "English original", [저자 연도]` — 영어 원문이 없으면 `한글 한 문장, [저자 연도]`. 원전을 직접 확인하지 못하고 재인용처로 확인했으면 `[저자 연도, 재인용]`으로 쓰고, 강사 노트에 **실제로 읽은 재인용처**(문헌명·링크)와 확인 범위를 적는다. "여러 출처가 인용한다"만으로는 근거가 되지 않는다.
- 영어 원문만 `"..."`로 감싸고 한글과 한 문단 안에서 쉼표로 가른다. `참고:`, `출처:` 같은 별도 줄을 두지 않는다. 원문 안의 따옴표는 `\"`로 쓴다(Production이 `"`로 출력한다).
- **출처는 레이블로 쓴다.** 인용·참조 모두 `[Larman 2004]` 형식이다. 저자는 성만 쓰고(둘이면 `[Beck·Cunningham 1989]`, 셋 이상이면 `[Gamma 외 1994]`), 단체는 약칭(`[OMG 2017]`), 같은 저자·같은 해가 둘 이상이면 `[Martin 2014a]`·`[Martin 2014b]`로 구분한다. 영문 위키백과는 `[Wikipedia: Use case]`로 쓴다. 한글 사이트는 출처로 쓰지 않는다.
- 레이블의 서지(서명·문서명, 판, 저자 전체 이름, 출판사, 연도, URL)는 과정의 별첨 `sessions/references.md`에 한 번만 둔다(「별첨 — 참고 자료」). 장·절·쪽 번호는 어디에도 적지 않는다. 확인하지 못한 연도는 레이블에 넣지 않고 별첨에서 그 사실을 밝힌다.
- 영어 원문은 재작성하지 않는다. 확인한 문구를 그대로 옮기며, 한글 쪽은 그 문구가 말한 것만 옮기고 원문에 없는 주장을 더하지 않는다.
- 인용·참고 자료는 **적어도 인터넷에서 찾을 수 있어야** 한다. 확인되지 않은 서지 요소(출판사·URL·제목)는 채워 넣지 않고 지운다.
- 원전을 우선 확인한다. 원전을 확보하지 못하면 실제 본문을 읽은 추적 가능한 2차 인용처를 쓰며, 재인용임을 밝힌다. **검색 결과 요약이나 LLM의 기억은 검증 근거가 아니다.** 2차 인용의 반복 횟수를 독립 검증 횟수로 세지 않는다.
- 통계는 원래의 시점·대상·범위를 보존하고 일반화하지 않는다. 공식 초록·목차만 확인했다면 그 범위의 주장만 한다.
- 근거를 확인하지 못한 귀속·수치는 사실이나 인용으로 남기지 않는다. 학습에 필요한 설명은 확인한 근거로 다시 쓴다. 교육용 가정은 출처를 대신하지 않는다.
- 표준명은 공식 표기 그대로 쓰고(예: `ISO/IEC/IEEE 29148:2018`), 표준에 없는 판본·분류를 만들지 않는다.
- 출처 검증 과정이나 번역 메모는 본문에 넣지 않고 강사 노트에 둔다.

예: `"프로젝트 노력의 약 40~50%를 회피 가능한 재작업에 사용한다", "Current software projects spend about 40 to 50 percent of their effort on avoidable rework.", [Boehm·Basili 2001]`

### 별첨 — 참고 자료

과정마다 교재 맨 끝에 별첨 `courses/<course>/sessions/references.md`를 둔다. 세션 원고가 쓰는 모든 레이블이 여기에 있어야 한다(Production이 검사).

```text
--------------------
Session 명: 별첨. 참고 자료
--------------------

## 참고 자료

**참고 자료 목록**

1. **[Brooks 1986]**  No Silver Bullet, Frederick P. Brooks Jr., 1986
2. **[Larman 2004]**  Applying UML and Patterns, 3rd ed., Craig Larman, Prentice Hall, 2004
3. **[Wikipedia: Use case]**  Use case, Wikipedia, https://en.wikipedia.org/wiki/Use_case
```

- 별첨은 세션과 별도의 문서다(각 세션 끝에 붙이지 않는다). 기준 원전, 수강생이 공부할 책, 세션이 레이블로 인용·참조한 자료를 **하나의 목록**으로 둔다. 주요·인용으로 나누지 않는다. 영문 위키백과는 포함하고 한글 사이트는 쓰지 않는다.
- 항목은 `N. **[레이블]**  서명(문서명), 판, 저자, 출판사(게재지), 연도, URL` 한 줄이다. 없는 요소는 생략한다. 레이블의 알파벳 순서로 처음부터 끝까지 번호를 매긴다.
- 별첨은 목차·세션 목표·요약을 두지 않는다. 강사 노트는 둔다.
- **세션이 인용하지 않는 자료는 항목 끝에 `(읽을거리)`를 붙인다.** 목록에만 있고 본문이 쓰지 않는 자료는 그 표식이 없으면 빠뜨린 것인지 둔 것인지 알 수 없다. Production은 표식이 없으면서 어느 세션도 쓰지 않는 레이블을 경고한다.

## 6. 표와 목록

- 한 세션 안에서 표·도식의 **제목이 겹치지 않게** 한다. 같은 대상을 다루면 무엇이 다른지가 제목에 드러나야 한다(도식 `주문한다의 가드레일 배치` ↔ 표 `주문한다의 위험별 가드레일`).
- 표와 도식에는 **제목**을 단다(`**표 — 제목**`, `**도식 — PlantUML — 제목**`). 표·도식은 본문 문장이 직접 설명하거나 제목만으로도 무엇인지 바로 연결되어야 한다. 연결되지 않는 표·도식은 두지 않는다.
- 표나 목록으로 충분한 내용은 박스나 다이어그램으로 만들지 않는다. 반대로 **관계·흐름·상태·경계**를 표로 나열하면 그 관계가 사라진다 — 그런 내용은 도식으로 보인다(「8. Visual」). 목록은 구조를 보일 때 쓰고, 불필요한 계층을 만들지 않는다.
- 표와 도식은 앞 문장이나 뒤의 bullet이 **무엇을 보여 주는지** 직접 설명한다(예: "위가 도메인 모델, 아래가 물리 모델이다", "왼쪽 `Order`는 두 액터의 요청으로 바뀐다"). "표의 오른쪽 열이 …다" 같은 읽는 법만 말하는 정형 문장으로 대신하지 않는다.
- 읽는 법을 쓰게 되거든 **표에만 있던 구체 값을 문장으로 끌어올린다** — "표의 오른쪽 열이 각 층이 알려 주는 것이다" 대신 "IDE는 컴파일 오류를, 운영은 **실제 외부 시스템의 행동**을 알려 준다". 표를 보기 전에도 요점이 전달되고, 표는 나머지 행을 채운다. 열이 많아 한 문장으로 안 되면 **가르는 기준**을 쓴다(예: "영향 범위가 설계와 아키텍처를 가른다").
- **설명을 위한 설명을 두지 않는다.** "표는 교육용 가정이다", "뒤 세션은 이 topic을 가리킨다", "자세한 것은 「NN」에서" 같은 범위·출처·참조 문장, 도식 제목과 같은 말을 되풀이하는 문장은 본문이 아니라 강사 노트에 둔다. 같은 내용의 표를 이웃 topic에 두 번 두지 않는다.
- 도식이나 코드로 이미 보이는 것을 표로 다시 만들지 않는다. 표는 비교할 값이 실제로 있을 때만 쓴다.
- 모델·패키지·계층처럼 **분류**하는 표에는 도식이나 코드와 맞춰 읽을 **대응 열**(예: 패키지)을 둔다.
- 짧은 항목이 많으면 의미가 유지되는 범위에서 5~6개 그룹으로 묶는다. 병렬 항목은 `A, B, C`처럼 한 문장으로 쓸 수 있다.
- 두 개 이상의 대비 개념에 각각 세부 항목이 있으면 하위 bullet으로 나눈다(예: 본질적 어려움/우연적 어려움).
- 라벨 아래에 항목을 나열할 때는 **들여쓰기 단계마다 bullet**을 둔다 — 라벨은 상위 bullet, 항목은 하위 bullet이다. 글머리표 없는 들여쓰기(`+ `)로 목록을 만들지 않는다.
- **주장은 상위 bullet에 두고 근거·예·수치는 하위 bullet로 내린다.** 한 줄에 `주장. 사례.` 두 문장을 붙이면 어느 쪽이 그 장의 주장인지 보이지 않는다(`정하지 않은 업무 규칙은 LLM이 추측으로 채운다. 첫 시도는 … 2,400원을 청구했다.`). 주장만 남기고 사례는 하위 bullet로 내린다. 하위 bullet에도 굵게 표시한 핵심어를 둔다 — 없으면 Production이 경고한다.
- **같은 성격의 문장은 같은 수준에 둔다.** 한 쌍으로 읽어야 하는 값(틀린 값과 맞는 값, 두 가지 한계, 한 번의 위임에서 잰 두 수치)은 들여쓰기가 같아야 짝으로 읽힌다. 하나를 상위 bullet에, 짝을 하위 bullet에 두면 둘째가 첫째의 부연으로 보인다.
- **인용 bullet의 수준은 그 인용이 받치는 문장이 정한다.** 바로 위 인용에 기준을 더하는 인용만 들여쓴다(「인용 형식」). topic의 본문 주장을 받치는 인용은 다른 본문 bullet과 **같은 수준**의 상위 bullet으로 두고, 그 인용이 설명하는 bullet 옆에 놓는다. 위에 인용이 없는데 들여쓴 인용은 비어 있는 상위 항목을 가리킨다.
- 순서가 있는 단계는 번호 목록(`1. `)으로 쓰고, 그것을 소개하는 문장 아래 **들여 쓴다**. bullet 안에 ①·② 같은 번호를 다시 붙여 글머리표와 번호가 겹치게 하지 않는다. Production이 경고한다.
- 괄호는 **바깥이 주어, 안이 예**다: `개념 클래스(주문)`처럼 유형·개념을 밖에, 사례를 괄호 안에 쓴다. 괄호 안은 작게 렌더되므로 거꾸로 쓰면 핵심이 작아진다.
- 한 흐름의 이벤트를 표로 나열할 때는 행 순서가 이벤트 순서다. "기본 1·기본 2"처럼 번호를 붙여 별개의 흐름처럼 보이게 하지 않고 **기본 흐름 / 대안 흐름**으로 표시한다. 흐름 번호(1a, 3a)는 유스케이스 명세서 안에서 쓴다.
- 번호가 의미를 갖는 절차는 numbered list, 순서가 없는 항목은 bullet을 쓴다. 목차에는 bullet을 쓰지 않는다.
- 표의 **열 이름**은 무엇을 담는지 바로 알게 쓴다(예: "명세 여부", "주문한다(예)"). 목차 번호만 담는 "다루는 곳" 같은 모호한 열을 두지 않는다 — 필요하면 "비고"에 뜻을 쓴다. 질문형 열 이름·셀은 `?`로 끝낸다(Production이 경고한다).
- 표의 셀은 **한 줄**에 들어가게 핵심 구로 쓴다. 근거가 필요해 한 줄을 넘으면 판정만 남기지 말고(예: "높다") 표 대신 bullet로 쓴다. 셀 안의 topic 참조는 강사 노트로 옮긴다. 계약의 사후조건처럼 여러 사실을 담은 셀은 **사실마다 행**을 나누고, 이어지는 행의 첫 칸은 비운다(행 높이는 Production이 정한다).

## 7. 강사 노트

강사 노트는 학습자가 읽는 본문을 **보조**한다. 본문과 모순되는 내용이나 본문에 없는 새 주장을 두지 않는다. 학습자가 알아야 할 설명·통찰은 본문에 둔다. **초안 단계에서는 슬라이드 본문·표·도식·실습을 먼저 검토·승인하고, 그 뒤에 Deck 작성자가 강사 노트를 작성한다.** 최종 Session Source에는 기존 규칙대로 모든 topic의 강사 노트를 포함한다. 노트가 없는 초안은 SA 완료로 판정하지 않는다.

- **모든 topic**에 `**강사 노트**`를 둔다(Production이 검사한다).
- 노트는 **bullet**로 쓰고, bullet 하나는 한 가지 일을 한다.
  - **강의 포인트** — 강조할 판단, 던질 질문, 흔한 오해
  - **근거·출처** — 인용·표준의 서지와 링크, 확인 범위, 재인용 여부
  - **가정·범위** — 교육용 가정, 성공 경로만 다룬다는 등의 범위
  - **연결** — 앞뒤 topic이나 다른 세션과의 관계(참조 형식을 따른다)
- 시연 topic의 노트는 본문이 가리키는 **기록 파일의 경로**를 적는다(`초안 전문은 code/s02/demo-results/draft.md에 있다`). 본문이 "초안"·"실행 기록"을 말하는데 어디에 있는지 없으면 수업에서 열 수 없다.
- 코드 topic의 노트는 코드가 **보장하는 것과 보장하지 않는 것**, 코드의 요소를 분석 모델에 역수입하지 않는다는 점을 밝힌다.
- Anchor Message는 노트에만 두지 않는다. 노트에만 있는 메시지는 본문 반영으로 보지 않는다.

## 8. Visual

### 쓰는 이유와 도구

- Visual은 **관계·구조·흐름·공간적 의미**를 텍스트보다 명확히 보여줄 때만 쓴다. 해당 개념이 등장하는 바로 그 topic에 두고, 종합 visual 페이지를 따로 만들지 않는다.
- 콘텐츠를 먼저 확정한 뒤 도구를 고른다. UML은 PlantUML(또는 `svg:uml`), 일반 흐름·관계는 Mermaid, 정량 데이터는 chart를 쓴다. 실제 수치 없이 chart를 만들지 않는다. 개념 도식은 개념도임이 드러나게 하고 측정된 관계처럼 보이지 않게 한다. 와이어프레임은 편집 가능한 SVG 등으로 둔다.
- 도구 때문에 내용을 바꾸지 않는다. 필요한 표현이 지원되지 않으면 Production을 확장한다.
- Markdown 하나로 의미와 visual 원본이 전달되도록 원본(PlantUML·Mermaid·SVG 등)을 본문에 둔다. ASCII 테두리를 최종 visual로 취급하지 않는다.
- 정보가 적으면 단순하게 그린다. 서로 다른 개념을 한 도식에 억지로 합치지 않는다.
- 세션의 visual은 **구성안에서 topic마다** 정한다(「12. 검토 절차와 완료 기준」). 표가 여러 topic 이어지면 그중 구조·흐름·상태를 보이는 것이 없는지 다시 본다. 표만 이어지는 세션을 만들지 않는다.
- **도식과 글은 서로 다른 것을 담는다.** 도식이 보인 것(개념·속성·관계·다중성)을 글로 다시 적은 "목록"을 따로 만들지 않는다 — 같은 내용이 두 군데면 둘이 어긋나는 순간이 온다. 산출물은 **문서 하나**이고 도식은 그 문서의 한 절이며, 글은 **도식에 적을 자리가 없는 것**(값의 뜻, 언제나 참이어야 하는 조건, 정하지 않은 것과 그 이유)을 적는다. 산출물이 몇 개이고 무엇이 어디에 들어가는지는 그 세션이 한 장으로 밝힌다.

### 그리는 방법

- 배치는 **의미 순서**를 따른다(예: 도메인 모델이 위, 물리 모델이 아래, 업무 경계가 가운데, 연동이 바깥).
- 도식 안의 흐름은 **왼쪽 → 오른쪽**이 기본이다. 가로로 길면 2~3행으로 나누어 상하로 잇고, 의미 없이 세로로 긴 도식은 피한다.
- 화살표가 학습 순서·시간 순서·인과·메시지·분류·의미 연결 중 무엇인지 분명히 한다. 개념의 연관을 필수 개발 순서로 그리지 않는다.
- 선이 행동·상자·레인 경계를 **가로지르지 않게** 배치한다. 자동 배치로 겹침이 풀리지 않으면 `svg:uml`로 직접 배치한다.
- 같은 상호작용을 두 다이어그램으로 비교할 때는 **같은 메시지·같은 번호**로 **한 슬라이드**에 보인다.
- 표기 그림과 그 「표기와 사용법」 표는 한 슬라이드에 둔다.
- 도식의 글자 크기는 Production이 모든 도식에 같게 맞춘다(`production-guide.md`의 「Visual layout 및 가독성」 — 도식 안 글자 10pt). 요소가 적은 도식을 키워 그리지 않고, SVG는 도식 안 글자 크기를 한두 가지로 맞춘다.
- **도식 안의 글도 관통 사례의 값으로 쓴다.** `문서 · 이력 · 문서 · 이력`처럼 자리를 채우는 라벨은 그림만 그럴듯하게 만들고 읽는 사람에게 아무것도 주지 않는다. 그 장의 본문이 말한 구체 값을 그대로 쓴다(`결제 매뉴얼 1~120쪽` · `승인 뒤에만 배송을 요청한다` · `결제 매뉴얼 122~200쪽`).
- **도식과 제목을 분리한다.** 제목은 도식 밖에 두고 **다이어그램 이름만** 쓴다(예: `활동 다이어그램`). "— 상태를 바꾸는 단계" 같은 설명은 제목·도식 안에 넣지 않고, 필요하면 슬라이드 본문에서 설명한다.
  - 도식 하나는 `**도식 — … — 이름**` 제목(14pt)을 단다.
  - 여러 부분을 한 SVG에 담으면 부분마다 이름을 그 부분의 상자 **밖**(위)에 둔다. 이름은 기본 **14pt**(도식 안 글자의 1.4배로 그린다), 부분이 많아 14pt가 어려우면 **12pt**(1.2배)로 줄인다. Production은 SVG의 가장 작은 글자를 10pt로 맞추기 때문이다.
- **도식 안의 글은 상자 폭을 채운다.** 한 문장을 여러 줄로 쪼개 상자의 왼쪽 3분의 1만 쓰면, 칸은 크고 글은 작아 읽기 어렵다. 칸이 좁아 쪼개야 한다면 세로 칸을 **가로 띠**로 바꿔 한 문장을 한 줄에 둔다(네 칸을 나란히 세우는 대신 네 줄로 쌓는다, 2026-11-04).
- **SVG의 크기는 실제 표시로 검증한다.** 내용이 라벨·관계·설명으로 구분되도록 간격과 위계를 조정한다. 기존 띠 도식의 고정 좌표·문자 수를 새 도식에 강제하지 않는다. Production의 표시 글자 하한을 만족할 공간이 없으면 의미 단위의 분할이나 배치 조정을 검토한다.
- **순수한 글은 도식이 아니라 표로 둔다.** 도식 안의 글은 이미지라 검색·편집·확대가 되지 않는다. 선·마름모·화살표처럼 **그려야 뜻이 서는 것만** 도식에 두고, 설명은 바로 아래 표에 둔다(연관 선 그림 + 「선 하나에 적힌 3가지」 표). 색은 뜻을 나를 때만 쓴다.
- **SVG의 내용은 viewBox 안에 들어가야 한다.** 밖으로 나간 상자·선·글은 그려지지 않는다 — 슬라이드 배치는 맞는데 도식 자신의 아래 테두리가 사라진다. Production이 넘친 양을 경고한다(`production-guide.md`의 「Visual layout 및 가독성」, 2026-11-04).
- 협력 예시는 책임 소유자와 조정 책임을 구분하고, 하나의 설계 대안을 보편적인 책임 배치로 단정하지 않는다.
- Production 가독성 문제를 해결하려고 의미를 훼손하거나 노드·관계를 삭제하지 않는다.

## 9. UML

### 공통

- UML을 설명하는 topic에는 **해당 notation 자체**를 함께 보인다. 다이어그램을 처음 쓰는 topic에서는 표기 요소를 나란히 보이고 요소마다 **이름·의미·사용법**을 표로 설명한다. 문법이 있는 표기(조각·가드·다중성·전이 라벨)는 쓰는 법을 예와 함께 보인다.
- 다이어그램을 소개하는 topic의 제목은 **다이어그램 이름**, 예제 topic은 **대상 + 다이어그램 약칭**(예: `결제 시퀀스`)으로 쓴다.
- 여러 다이어그램을 다루는 세션은 먼저 다이어그램들의 **정의와 정적 모델(또는 요구)과의 관계**를 한 곳에서 보인다.
- 모델을 만드는 다이어그램은 **초안 → 상세화**로 발전시킨다(유스케이스 다이어그램, SSD 초안 → 정제된 SSD, 클래스 다이어그램). 초안은 구조의 합의, 상세화는 규칙의 명시가 목적이다.
- **추상화 수준** — 분석 다이어그램은 업무 의미의 수준에서 그린다. 화면 조작·메서드 시그니처·DB 저장·플래그 조합 같은 구현의 세부를 넣지 않는다. 상태는 **같은 사건에 다르게 반응하는 상황**만 나눈다(상태 의존 객체). 상태·흐름이 늘어나는 문제는 표기법이 아니라 이 수준과 적정 모델링의 문제로 다룬다.
- **표기 기호는 쓰기 전에 유형을 먼저 보인다.** 채운 마름모·빈 마름모·빈 삼각형 같은 기호를 설명 없이 먼저 쓰면, 학습자는 그 기호가 무엇인지 모른 채 그 장의 판단을 따라가야 한다. 연관·합성·집약·일반화처럼 **선 모양이 여럿인 표기**는 유형을 한 장에 나란히 보인 뒤(선 모양 · 이름 · 읽는 법 · 이 모델에서) 개별 판단으로 들어간다. 이 모델에 없는 유형도 **가르는 기준**으로 함께 보이고, 없는 것을 그리지는 않는다.
- **도메인 모델의 연관에는 화살표를 그리지 않는다.** 연관은 방향이 없는 양방향이며, 어느 쪽에서 탐색할지는 설계의 결정이다. `A --> B`로 그리면 분석 단계에서 참조 방향을 확정한 것이 된다. 방향이 있는 것은 일반화(빈 삼각형)와 의존뿐이다.
- 하나의 개념을 설명할 때 관련 없는 UML 요소를 함께 넣지 않는다(예: `유스케이스란 무엇인가?`에는 타원만).
- 다이어그램마다 같은 의미의 표현이 다르면 그 차이를 밝힌다(예: 시퀀스의 조각 ↔ 커뮤니케이션의 `[조건]`·`*`).
- UML 표기에는 **바탕색을 쓰지 않는다**. 스테레오타입은 `«enumeration»`, `«interface»`, 유스케이스 다이어그램의 외부 시스템 `«actor»`, 관계의 `«include»`·`«extend»`만 쓴다. 데이터 타입·도메인 유형 같은 분류는 도식에 표시하지 않고 본문에서 대응시킨다. 원형 표시·footbox처럼 표기 규칙을 지키는 렌더 설정은 Production이 넣으므로 원고에 쓰지 않는다.
- **패키지 다이어그램**은 무엇이 어느 패키지에 속하는지를 보인다. 클래스는 **이름만** 보이며 속성·오퍼레이션은 감춘다(Production이 감춘다). 속성과 규칙은 클래스 다이어그램이 보인다. 그리는 법은 아래 「패키지 다이어그램」이 정한다.

### 패키지 다이어그램

- **패키지를 패키지로 그린다** — 탭 달린 사각형으로 그리고 이름을 탭에 둔다. 패키지를 상자 하나로 그리고 이름만 적으면 패키지 다이어그램이 아니라 클래스 그림이다. 한 그림 안의 패키지는 업무·연동·영속을 가리지 않고 **모두 같은 방식**으로 그린다.
- **도메인 모델을 중심으로 그린다** — 패키지 안에 그 경계가 소유한 **대표 도메인 클래스**를 둔다. 포트와 인터페이스만 그리면 무엇의 경계인지 알 수 없다. 모든 클래스를 나열하지 않고 경계의 의미가 드러나는 만큼만 둔다.
- **포트는 소유한 패키지 안에** 두고 `«port»`로 표시한다. 포트를 쓰는 쪽이 아니라 **소유하는 쪽**에 두는 것이 의존 방향의 근거다.
- **관계의 종류를 표기로 구분한다** — 분석에서 확인한 **업무 연관**은 화살촉 없는 실선, **패키지 의존**은 점선 화살표다. 둘을 같은 선으로 그리면 업무가 정한 것과 설계가 정한 것이 섞인다.
- **외부 시스템·저장소는 패키지가 아니다.** 패키지 **바깥**에 `«system»`·`«store»`로 두고, 연동이 그것과 통신하는 관계로 잇는다.
- **관계 없이 떠 있는 패키지를 두지 않는다.** 그릴 관계가 없으면 그 패키지는 이 그림의 대상이 아니다.
- **한 그림이 가로로 길어지면 관점을 나눈다** — 패키지가 다섯을 넘으면 업무 경계(무엇이 어느 패키지에 사는가)와 포트의 구현(어느 연동이 어느 포트를 구현하는가)처럼 **두 그림**으로 가른다. 노드나 관계를 지워 한 장에 우겨넣지 않는다(「의미 표식과 블록 경계」의 「넘칠 때는 순서가 있다」).
- **표기는 `svg:uml`이나 `plantuml:package`로 쓴다.** Mermaid의 `flowchart`는 `subgraph`를 한 랭크에 늘어놓아 패키지가 넷만 되어도 가로로 길어지고, 슬라이드 폭에 맞추면 글자가 7pt 아래로 내려간다(`production-guide.md`의 「Visual layout 및 가독성」).

### 유스케이스 다이어그램

- 시스템 경계를 크게, 액터는 작게 그린다. **초안**은 주 액터(왼쪽), 유스케이스, 시스템 경계, 연관만 쓴다. **상세화**에서 외부 시스템 지원 액터를 오른쪽에 `«actor»` 상자로 더하고, 확인된 관계만 더한다.
- `«include»`는 기본 → 포함 유스케이스, `«extend»`는 확장 → 기본 유스케이스, 일반화는 특수 → 일반(실선·속 빈 삼각형)이다. 포함은 코드 공통화가 아니고, 확장은 기본 유스케이스가 독립적으로 의미를 갖는 전제에서 쓴다.
- 관계를 가르칠 때는 그 관계를 성립시키는 사례 전제를 같은 topic에 둔다. 유스케이스 사이의 일반 화살표로 순서나 흐름을 표현하지 않는다.

### 시퀀스 다이어그램·SSD

- **SSD**는 응답을 그리지 않는다. 외부 시스템에 보내는 메시지는 모두 **요청**(실선 화살표)이며 동기·비동기를 구분하지 않는다. 전달 방식은 설계에서 정한다.
- 메시지를 보내는 객체는 그 시점에 **다른 메시지를 처리하는 중**이어야 한다(처리 안의 호출). 아무 메시지도 처리하지 않는 객체가 요청을 보내게 그리지 않는다 — 커뮤니케이션 다이어그램의 중첩 번호(`1.1`)와 코드의 호출 안의 호출로 옮길 수 없다.
- 분석 시퀀스의 호출은 **동기**가 기본이며 응답을 그리지 않는다. 결과를 기다리지 않는 요청·통보만 비동기(열린 화살촉)로 구분한다.
- SSD 초안은 주 액터와 대상 시스템만, 정제된 SSD는 외부 시스템(지원 액터)까지 그린다. 시스템 안의 객체는 넣지 않는다.
- 분석 시퀀스의 생명선은 **도메인 개념의 인스턴스**(`:주문`)다. 컨트롤러·서비스·저장소 같은 설계 객체는 넣지 않는다. 설계 시퀀스는 설계 객체를 포함하며 용어집의 영문명(`:OrderService`)으로 그린다.

## 10. 코드 매핑

- 요구·분석의 결정이 **코드와 실행 결과에 어떻게 이어지는지** 보인다. 코드는 연결을 확인하는 예이지 최종 구현이나 모델의 자동 변환이 아니다.
- 코드는 **자기 topic**에 두고, 바로 앞에 **그 코드가 표현하는 도식**을 둔다. 도식 없이 코드만 제시하지 않는다.
- 코드는 **컴파일하고 실행해 확인한 것**만 싣는다. 전체 코드는 `courses/<course>/sessions/code/sNN/`에 두고, 슬라이드에는 도식이 표현하는 부분만 **발췌**할 수 있다. 생략은 `// ... <설명> 생략` 줄로 표시한다(Production이 발췌와 원본을 대조한다).
- 식별자는 **공통 전제·용어집의 이름**과 같다. 분석 예시 코드는 한글 용어, 설계 코드는 용어집의 영문명과 명명 규칙을 쓴다(「관통 사례와 식별자」). 용어집에 없는 업무 용어를 코드에서 먼저 만들지 않는다.
- **개념 클래스**는 필드와 생성자를 가진 `class`로 쓴다. 필드가 모델의 속성·연관을 드러낸다. `record`는 **데이터 타입**(금액·수량·주소)처럼 값으로 같은지 판단하는 것에만 쓴다.
- 코드가 **보장하는 것과 보장하지 않는 것**을 구분한다. 미확정 정책을 분기·예외·테스트 기대값으로 대신 결정하지 않는다. 코드의 요소(필드·보조 호출·설계 객체)를 분석 모델에 역수입하지 않는다.
- 학습자가 결과를 먼저 예측한 뒤 실행해 대조하게 한다.

다이어그램마다 코드로 이어지는 요소를 한 가지 이상 보인다. 아래 대응은 설계의 결정이 섞인 "이렇게 이어진다"의 예이지 변환 규칙이 아니다.

- **비동기**의 기준은 반환값이 아니라 호출자가 **완료를 기다리는가**다. **병행**(흐름의 순서)과 비동기를 섞지 않는다. 예제가 전달 방식(큐·이벤트)을 생략하면 그 사실을 밝힌다.
- 상태 기계의 화살표가 없는 이유는 **금지**(확인된 규칙)와 **미정**(요구 질문)으로 구분한다. 금지된 전이만 거절 테스트가 되며, 미정인 전이를 테스트 기대값으로 정하지 않는다.

| 다이어그램 | 모델 요소 | 코드에서 |
|---|---|---|
| **SSD** | 시스템 이벤트 / 외부 시스템에 보내는 요청 | 시스템 경계의 인터페이스 메서드 / 외부 시스템 인터페이스의 메서드(요청 하나가 메서드 하나) |
| **오퍼레이션 계약** | 사전·사후조건 | 호출 전 검사 / 호출 후 도메인 객체의 상태(생성·연관·속성), 계약의 예는 테스트 |
| **클래스** | 개념 / 속성·연관 / 속성 도메인 | 필드와 생성자를 가진 `class` / 필드(연관의 방향은 설계) / 값의 종류(`record`)와 생성 시 규칙 검사 |
| **클래스** | 다중성 `1..*` / 합성 / 파생 속성 / 확정 값 | 빈 값 거절 / 전체가 부분을 만든다 / 저장하지 않는 계산 / 시점의 값을 옮겨 적기 |
| **활동** | 행동 / 결정 / 분기·합류 | 메서드 호출 / `if` / 순서에 의존하지 않는 호출과 모두 끝난 뒤의 진행 |
| **시퀀스** | 메시지 / 생성 / 비동기 / `alt`·`loop` | 받는 객체의 메서드 / `new` / 완료를 기다리지 않는 요청 / `if`·`for` |
| **커뮤니케이션** | 링크 / 번호 `1.1` | 참조 필드 / 호출 안의 호출 |
| **상태 기계** | 상태 / 전이 / 가드 / 금지된 전이 | `enum` 값 / 상태를 바꾸는 메서드 / 전이 전 검사 / 거절과 그 테스트 |

## 11. 원전 기반 작성

교재는 분야별로 검증된 **기준 원전**(모범 서적·문서)을 토대로 강의하고, 수강생이 그 원전을 구해 공부·참고하게 하는 것을 목표로 한다. 여러 원전을 섞거나 작성자(LLM·강사)의 관점을 덧붙이면 초보자가 그 주제를 배우는 데 방해가 된다. 기준 원전과 주요 참고 자료는 `course-design.md`가 정한다(`course-design-guide.md`의 「기준 원전과 참고 자료」).

- 기법의 **정의·템플릿·표기·절차**는 기준 원전대로 쓴다. 원전에 없는 규칙·분류·틀을 만들지 않는다.
- 정의·템플릿 항목·표기·인용 문장은 **확인한 원문**으로 쓴다. LLM의 기억만으로 확정하지 않는다.
- 출처는 **저자·서명(문서명)·연도**로 밝힌다. 장·절·쪽 번호는 어디에도 적지 않는다.
- 원전마다 같은 개념을 다른 이름으로 부르면(예: Extensions·대안 흐름) 같은 것으로 다루고, `course-design.md`가 정한 이름 하나로 쓴다.
- 기준 원전에 없는 관점·비교·주제는 원고에 섞지 않는다. **제안**으로 따로 보이고 승인받은 뒤 넣으며, 넣을 때는 그 출처를 밝힌다.
- **그림은 모두 다시 그린다.** 원전의 사례 대신 관통 사례나 다른·유사한 시나리오를 쓴다.
- 원전의 **표를 가져오면** 표 제목에 출처를 적는다: `**표 — 도메인 규칙 (Larman, 2004)**`.
- 원전 문장은 핵심만 인용한다(「5. 인용과 출처」).
- 과정 전체에서 적용하는 원전 선택과 공통 해석은 Course Design을 따른다. 개별 세션에서 적용할 정의와 예의 의미는 승인 DD에서 확인한다.

## 12. 검토 절차와 완료 기준

### 검토 절차

1. 승인 Curriculum의 세션 역할과 DD의 세션 목표·Anchor Message(거버닝 메시지)·논리 전개, Course Design의 공통 전제를 확인한다.
2. **인용문을 먼저 정리한다.** 세션이 쓸 인용을 원문으로 확인하고(`tools/verify-quote.js`), 한글·영문 원문·레이블·배치할 topic과 확인 범위를 채팅 text로 보여 확정한다. 필요한 인용이 비어 있으면 1차 자료를 더 찾고, 핵심 메시지를 받치지 않는 인용은 뺀다.
3. **용어를 먼저 확인한다.** 공통 용어와 정의는 Course Design, 최초 설명 위치와 세션별 적용은 DD를 따른다. 새 용어나 정의가 필요하면 소유 단계로 환류한다.
4. 승인 DD를 바탕으로 **표현 구성**을 검토한다. topic별 핵심 문장·사례 값·visual 종류·인용 위치를 대조한다. 검토 메모는 별도 정본으로 두지 않는다.
   - 핵심 메시지는 **청중이 따라 말할 한 문장**으로, 원고에 그대로 쓸 문장을 적는다. 그 문장이 슬라이드의 표·열·순서를 가리키지 않고 **내용만으로** 성립해야 한다. 성립하지 않으면 그 topic은 아직 생각이 끝나지 않은 것이다.
   - 구성안의 **목차 항목은 원고에 그대로 들어갈 제목**이다. 주제의 이름이 아니라 그 장이 주장하는 바를 평서문으로 적는다(「3. 세션 구성」의 topic 구성). 목차를 이름으로 적어 승인받으면 원고도 그 수준에서 멈춘다.
   - **도식은 종류만 적지 않고 무엇을 그릴지 적는다**(`연관의 4가지 유형 — 선 모양·이름·읽는 법·이 모델에서`). 표로 충분한 것과 그려야 뜻이 서는 것을 여기서 가른다(「8. Visual」).
5. topic별 텍스트와 visual을 같은 위치에서 검토한다.
6. 먼저 충실히 쓰고, 넘치거나 같은 질문에 답하는 topic만 줄이거나 합친다. 병합·압축 후 사라진 개념이 없는지 전·후 topic 목록을 비교한다. 넘칠 때는 「의미 표식과 블록 경계」의 순서(축약 → 도식·표의 모양 조정 → 그대로 둠)를 따르며, 자리를 만들려고 설명·근거·사례를 덜어내지 않는다. 중복 설명과 불필요한 사례만 줄인다.
7. 기본 원칙에 비추어 점검한다 — 이벤트 관점인가, 관점을 섞지 않았는가, 다이어그램이 답하는 질문이 있는가, 코드·테스트와 이어지는가, 같은 지식을 두 곳에 쓰지 않았는가, 추측으로 만든 내용이 없는가, **공통 식별자가 원천과 같은가**.
8. **lead 문장만 모아 읽는다**(`node tools/read-leads.js <원고>`). 제목과 첫 문장만 차례로 읽어 **세션의 논지가 이어지면** 통과다. 슬라이드를 설명하는 문장, 제목과 어긋난 문장, lead 없이 bullet으로 시작하는 topic이 여기서 한눈에 드러난다.
   - 이어서 **본문 bullet의 라벨을 지우고 설명만 읽는다**. 설명이 혼자 문장으로 읽히지 않거나, 라벨을 되풀이하거나, 그 세션의 사례 값이 하나도 없으면 그 bullet은 아직 전보문이다(「4. 문장과 강조」의 라벨 규칙). 표와 강사 노트는 덮어 두고 본문만 읽는다 — 사례를 아는 사람에게는 추상 문장도 읽히기 때문에, 본문만 남겨야 빈 문장이 드러난다.
   - **문장 단위로 다시 검토한다.** 제목·문단·목록·표 셀·도식 라벨·예제 설명을 빠짐없이 읽고, 첫 등장 전에 소개하지 않은 사례·비표준 조어·번역투·주어 또는 판단 근거가 빠진 문장을 찾는다. 정상 문장은 유지하고 불명확한 문장만 고친다. 수강생이 뜻을 추측해야 하는 문장은 통과시키지 않는다. 검토 대상 본문에서 슬라이드 번호를 이용한 위치 설명과 `두 가지`처럼 글자로 쓴 수량 표현은 피하고, 필요한 경우 `2가지`처럼 아라비아 숫자를 사용한다. 다만 인용 원문·실제 LLM 응답·코드·도식의 고유 식별자·정식 표기는 변경하지 않는다.
   - 각 장의 문장에서 필요한 주체·대상·시점·기대 결과가 분명한지 확인한다. “어떤 시점의 값을 읽느냐에 따라 달라진다”는 “카드 승인 요청에는 주문 생성 당시 기록한 단가를 사용한다”로 고친다. 본문·표·도식이 같은 정의·수치·결론만 반복하면 설명을 한 곳에 둔다. 표나 도식에 사례가 있다면 본문에서 독자가 무엇을 확인할지 밝힌다.
   - 편집한 교정본은 기준본과 대조해 표시한 의견과 삭제, 별도 표시 없이 추가한 문구를 함께 찾는다. 같은 규칙이나 이름을 사용하는 본문·표·도식·접근성 설명·실습·요약을 함께 확인한다. 인용 번역의 주어와 동작을 영어 원문과 대조하고, 코드 설명의 이름과 동작을 실제 코드와 대조한다.
9. 용어·문체·강조·질문 표현·인용 형식을 통일한다. 본문 승인 후 강사 노트를 보완한다. **고정한 용어표와 다른 말이 원고에 들어왔는지** 함께 본다.
10. visual의 의미·전제·표기·원본 구조를 검토한다. 실제 글꼴·배치·분할·가독성의 판정은 Production이 한다.
11. 표준·인용·통계·기술적 주장의 원전 또는 실제 읽은 재인용처와 확인 범위를 검증한다.
12. Deck을 사전 검사하고 증거를 남긴다. 오류·경고의 현재 완료 기준과 의미·제작 결함의 처리 경계는 Production Guide를 따른다.
13. 문제의 원인이 공통 지침의 누락·모호함이면 지침을 함께 보완하고, 과정 고유 판단은 과정 문서에 반영한다.
14. 검토 의견을 표현 교정과 승인 의미 변경으로 구분한다. 충돌·불명확한 요청에는 근거와 대안을 제시하고, 상위 정본 또는 다른 승인 원고에 영향이 있으면 Governance의 변경 통제를 따른다.

검토 중에는 사용자가 요청하지 않는 한 임의의 PPT 시안이나 Production과 다른 이미지를 만들지 않는다.

### 완료 기준

- 세션명 헤더가 있고, 목차와 본문 topic이 1:1로 일치한다.
- 각 topic의 제목·첫 문장·본문·visual·코드가 같은 질문에 답하고, 사례 없이도 핵심 설명이 성립한다.
- 세션 목표·요약은 승인 DD의 의미와 Curriculum의 다음 연결을 보존한다. 승인된 제작 계약 및 현재 검사와의 차이는 Production Guide에 따른다.
- DD의 세션 목표와 거버닝 메시지를 학습자 본문에서 충족한다. 제목이나 슬라이드 수가 바뀌어도 승인된 정의·관계·판단 기준과 전개를 추적할 수 있어야 한다.
- 강의에 필요한 설명·사례·비교·코드·visual·실습이 충분하고 순서가 자연스럽다.
- 공통 식별자가 `course-design.md`의 공통 전제와 같고, 진화는 발견과 되돌림이 보인다.
- 인용·통계·표준이 확인한 근거에 기반하며, 직접 인용·요약·교육용 가정이 구분된다.
- 코드는 컴파일·실행으로 확인되었고 도식과 짝을 이룬다.
- 모든 topic에 규칙에 맞는 강사 노트가 있다.
- 적용되는 사전 검사와 미확인 사항은 Production Guide의 판정 절차를 따른다.
- **경고 0은 형식의 통과이지 글의 품질이 아니다.** 자동 검사가 보는 것은 참조·구조·인용 기록·배치이며, 문장이 가르치는지는 보지 못한다. 「검토 절차」 8의 **lead 훑기와 본문 훑기**를 거쳐야 완료다.
- 본문의 모든 bullet이 라벨을 지워도 완결된 문장으로 읽히고, topic마다 사례 값이 하나 이상 본문에 있다.
- **분량과 도식 수는 진단 지표다.** 기존 `tools/slide-density.js`와 승인된 과정별 기준을 참고한다. 공통 장수·글자 수·도식 비율을 맞추기 위해 DD의 필수 설명을 축소하지 않는다.
- renderer의 현재 지원 여부와 관계없이 최종 원고로 사용할 수 있다.

## 13. Production과의 관계

- **Human 승인·진입** — 승인 DD 대비 의미·순서·자료·학습자와 강사 영역을 대조하고, 규정된 사전 검사 결과와 함께 Human에게 Deck의 정확한 버전을 승인받는다. 임시 검사본과 최종 제작을 구분한다. 승인 버전과 변경 이력은 Governance에 따라 기록한다.
- **필수 검사** — 필수 블록, 노트와 본문 분리, 출처, 적용 대상의 실제 응답 일치, 승인 DD 연결을 확인한다. 자동 검사는 Production Guide에 명시된 적용 범위에서 수행한다. DD–Deck 연결과 영역 분리의 전수 자동 게이트는 미구현 요구이며, 자동 판정과 수동 대조를 따로 기록한다. 정의·관계·주장의 의미 보존과 학습 흐름은 의미 검토한다.
- **실패와 환류** — 표현의 결함은 Deck에서 수정한다. 메시지·학습 흐름·실습의 입력이나 승인 기준이 바뀌면 DD에 돌려보내고 재승인 전 의미 변경은 반영하지 않는다.

- 정상 Production 입력은 최종 Session Source 하나다. 실행 명령·출력·검증 산출물은 `production-guide.md`가 관리하며 이 지침에 중복하지 않는다.
- Session Source를 renderer 한계에 맞추기 위해 수정하지 않는다. renderer 편의를 위한 내용 삭제, 임의의 문법 치환, slide별 수작업 배치 지시를 하지 않는다.
- Production이 원고의 내용·도식 구조·표기 문제를 발견하면 피드백 문서를 사용자와 함께 검토해 학습 목적을 기준으로 수정 여부를 정한다. Production의 렌더링·배치·글꼴 문제는 원고 수정으로 해결하지 않는다.
