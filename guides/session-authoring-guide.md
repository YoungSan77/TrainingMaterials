# Session Authoring Guide

## 1. 목적과 범위

Session Authoring(SA)은 `course-design.md`의 세션 정의를 입력으로 받아, 실제 강의와 Production에 사용할 최종 Session Source Markdown을 작성한다.

- SA는 별도 Curriculum/DD artifact를 만들지 않는다. Human+LLM이 내용을 논의하고, 최종 결과를 하나의 Session Source에 통합한다.
- 모든 세션은 `sw-engineering-principles.md`의 기본 원칙을 따른다. 원고에서는 특히 요구를 **이벤트 관점**에서 시작하고, **다이어그램은 코드와, 코드는 테스트와** 이어서 보이며, 교재 자체도 **KISS·DRY·YAGNI**를 지킨다.
- 이 지침은 **저자가 결정하는 것**을 정한다. 글꼴 크기·배치·분할·자동 검사처럼 Production이 결정하고 검사하는 것은 `production-guide.md`가 정하며, 이 지침은 그 항목을 가리키기만 한다.
- Session Authoring은 Content authority다. renderer의 현재 한계는 원고의 판단 기준이 아니다. 필요한 문법이나 visual 유형이 없으면 Production을 확장한다(「13. Production과의 관계」).

### 입력

- 해당 과정의 `course-design.md` — **과정의 맥락**(대상의 성숙도·깊이의 결정), 세션 목표·Anchor Message·세부 목차와 **공통 전제**(관통 사례의 공통 식별자). 설명의 깊이와 사례·실습의 난이도는 과정의 맥락에서 가져온다.
- 상세화할 세션 번호와 세션명(예: `S01을 상세화하라.`)

## 2. 원고 형식

### 세션명 헤더

모든 Session Source는 파일 최상단에 세션명 헤더를 둔다.

```text
--------------------
Session 명: 01. OOAD 개요
--------------------

## 목차

01. 세션 목표
02. ...

## 01. 세션 목표
...
```

- `Session 명`은 `course-design.md`의 세션명과 번호까지 일치한다. 이 헤더는 topic이 아니며 Production이 슬라이드 우측 상단의 세션명으로 쓴다.
- Session Source 하나가 Production의 입력 authority다. Production 실행 시 metadata를 다시 입력하지 않는다.

### 목차와 topic 번호

- `## 목차` 자체에는 번호를 붙이지 않는다. 목차 항목은 `01.`, `02.` 형식이며 bullet을 붙이지 않는다.
- 첫 항목은 `01. 세션 목표`, 마지막 항목은 `요약`이다. `정리`, `정리와 다음 단계` 같은 변형을 쓰지 않는다.
- 요약 뒤의 **별첨**(`## 별첨. 실습 답`)은 목차에 넣지 않는다(「사례·가정·실습」).
- 본문 topic은 `## NN. 제목`으로 정의한다. 목차와 본문의 번호·제목·순서는 1:1로 같고, 번호는 빠짐없이 연속되며 중복되지 않는다. 축약 제목을 따로 쓰지 않는다.
- **목차는 그룹이다.** 목차가 길어지면 관련 topic을 그룹으로 묶는다. 그룹은 `## NN. 그룹명`(목차 항목)이고, 그 아래 번호 없는 `## 제목`이 **서브 항목**이다. 서브 항목은 자기 제목의 슬라이드가 되고, 제목 둘째 줄(11pt)에 그룹(`05. 연관`)이 표시된다. 목차에는 그룹만 나온다. 그룹 바로 아래 본문이 없으면 그룹만의 슬라이드는 만들지 않는다. 서브 항목이 하나뿐인 그룹은 서브 항목 없이 그룹 자체로 쓴다(제목이 목차 항목 그대로 보인다).
- 서브 항목을 가리킬 때는 번호 없이 「서브 항목 제목」이나 「NN. 그룹명」의 「서브 항목 제목」으로 쓴다.
- topic을 추가·삭제·이동하면 목차·본문 번호와 그 topic을 가리키는 모든 참조를 함께 고친다(Production이 참조를 검증한다).
- topic의 **제목·첫 문장·목록·표·도식·코드**는 같은 질문에 답한다. 첫 문장은 제목의 개념이나 주장을 직접 설명하고, 제목과 다른 설명이 필요하면 알맞은 topic으로 옮기거나 독립 topic으로 분리한다.
- 개념은 먼저 직접 정의하고 사례는 그 정의를 구체화할 때만 쓴다. 사례가 정의를 대신하거나, 관통 사례·식별자를 관련 없는 topic까지 반복해서는 안 된다. 사례를 빼도 설명의 의미가 성립해야 한다.
- 본문은 개념·모델·판단을 주어로 직접 설명한다. `이 세션은`, `이 장에서는`, `여기서는`, `다음 장에서`처럼 발표 순서를 설명하는 문장으로 학습 내용을 대신하지 않는다. 범위를 연결할 때는 정확한 세션명·topic 참조와 그 관계를 함께 쓴다.

### 의미 표식과 블록 경계

- `**인용문**`은 독립된 한 줄에 둔다. 바로 다음의 비어 있지 않은 한 문단만 인용문 그룹이며 다음 빈 줄에서 끝난다. 여러 인용문은 각각 표식을 붙인다. 인용문 안의 bold는 강조만 뜻한다.
- 고객 발언·과제·템플릿의 Markdown `>` 블록은 인용문 그룹이 아니다. 학술 인용으로 렌더할 문장만 `**인용문**`을 쓴다.
- `**강사 노트**`는 독립된 한 줄에 둔다. 이후 내용은 코드 블록 밖의 다음 수평 구분선 또는 다음 `## NN. 제목` 전까지 강사 노트다. 노트 안의 `###`는 본문 복귀 신호가 아니다.
- 본문 `###` 이하 heading은 topic 내부 소제목이다. 별도 topic이나 자동 분할 명령이 아니다. 글머리표 없이 **굵게**, 첫 bullet 단계로 들여 그려지며 아래 내용의 단계를 바꾸지 않는다.
- `**문서 형식**`은 독립된 한 줄이며, 그 topic을 한 장의 **문서**(예: 유스케이스 명세서)로 그린다 — 실습 답처럼 좌우 두 단, 14/12/11pt. 명세서·템플릿 같은 문서는 표로 쪼개지 않고 항목과 번호를 붙인 이벤트 흐름을 그대로 쓴다. 문서에 대한 설명은 문서 뒤 bullet이나 다음 topic에 둔다.
- 템플릿(예: Given-When-Then)은 bullet으로 쪼개지 않고 `text`·`gherkin` 블록으로 원래 모양대로 보인 뒤, 설명을 bullet으로 붙인다.
- `**주석**`은 독립된 한 줄에 두며, 바로 다음 한 문단이 그 topic의 각 슬라이드 아래쪽에 **8pt 주석**으로 표시된다. 본문 흐름에는 들어가지 않는다. 약어의 원어 같은 참고 정보에 쓴다(예: `REP — Release Reuse Equivalency Principle · CCP — Common Closure Principle`).
- `**페이지 분할**`은 독립된 한 줄의 명시적 페이지 분할이다. 분량이 아니라 **의미상 구분**(기본 예와 반례, 서로 다른 소주제)이 있을 때만 쓴다. 성격이 다른 내용이면 여러 장도 좋지만, 한두 줄이나 작은 표 하나를 더하려고 나누지 않는다 — 그 내용을 줄이거나, 맞는 topic으로 옮기거나, 노트로 보낸다. 범례와 그 표, 짧은 표 두 개, 표와 짧은 후속 설명처럼 한 장에 들어갈 수 있는 내용 사이에는 두지 않는다.
- 한 topic이 두 장 이상이면 각 장이 서로 다른 질문에 답하는지 먼저 확인한다. 같은 질문의 설명이 반복되거나 한 장에 들어갈 수 있으면 중복 문장을 줄이고 표·도식을 좌우 또는 상하로 배치해 한 장으로 합친다.
- `**다이어그램 — 시퀀스 다이어그램**`은 제목 둘째 줄에 다이어그램 이름을 보이던 이전 표식이다. 새 원고는 쓰지 않는다 — 제목 둘째 줄은 서브 항목의 그룹을 보이는 자리이고, 다이어그램 이름은 도식 제목(`**도식 — … — 이름**`)이 보인다. 이전 원고는 보완할 때 바꾼다.
- `**배치 — 좌우**`는 독립된 한 줄이며, 그 topic의 도식 하나를 오른쪽 반에 두고 본문을 왼쪽에 둔다. 본문이 도식을 항목별로 짚을 때(예: 유형 목록과 그 예의 도식) 쓴다. 표식이 없으면 도식은 본문 아래에 놓인다. **세로로 긴 도식**에만 쓴다 — 넓은 도식은 오른쪽 반에서 7pt 아래로 줄어, Production이 표식을 무시하고 상하로 배치한 뒤 경고한다.
- `**도식 — Mermaid**`, `**도식 — PlantUML**`, `**도식 — SVG**`는 뒤 visual의 유형 표식이다. 표식 끝에 `— 제목`을 붙이면 도식 바로 위의 제목이 된다(`**도식 — PlantUML — 주문 시스템 패키지(상세화)**`). 표는 바로 앞 줄에 `**표 — 제목**`을 둔다. 표와 도식에는 제목을 단다(「6. 표와 목록」). 렌더할 원본은 `mermaid`, `plantuml:<kind>`(`usecase`, `class`, `package`, `sequence`, `communication`, `state`, `activity`), `svg`, `svg:uml` fenced block이다. `svg:uml`은 SVG로 직접 그린 UML(유스케이스 다이어그램·SSD 등)처럼 넓은 도식이다. `java`, `gherkin`, 일반 text block은 학습자에게 보이는 코드·예시다.
- 새 visual 유형이나 표식을 도입할 때는 SA·Production 지침과 파서를 함께 정의한다. 지침 수정만으로 구현이 끝났다고 보지 않는다.

### 참조 형식

- **세션**은 정확한 세션명을 큰따옴표로 쓴다: `"03. 정적 모델 — 도메인 개념과 관계"`. `S03`, `s03.md` 같은 표기를 쓰지 않는다. 본문에서는 세션명만 쓰고, `("01. …"의 첫 시도)`처럼 괄호 안에 세션명과 장면을 덧붙이지 않는다 — 장면은 문장으로 말한다("01. …"에서 보았듯이 …).
- **같은 세션의 topic**은 번호와 제목을 겹낫표로 쓴다: `「26. 주문 취소 시퀀스」`. 번호만 쓴 `「26」`은 참조가 아니다(Production이 오류로 막는다).
- **다른 세션의 topic**은 세션명 바로 뒤에 쓴다: `"02. 요구 분석과 유스케이스"의 「44. 시스템 오퍼레이션과 계약」`. 여러 topic은 `·`, `,`, `과/와`로 잇는다. 그룹의 서브 항목은 그룹 뒤에 붙인다: `"04. 동적 모델 — 상호작용과 상태"의 「06. 시퀀스 다이어그램」의 「주문 취소 시퀀스」·「08. 상태 기계 다이어그램」`. "같은 세션의" 같은 지시어로 대신하지 않는다.
- 세션의 topic 번호를 바꾸면 그 세션을 참조하는 다른 세션을 `node src/cli.js --check <원고…>`로 함께 검사한다(덱은 만들지 않는다).
- 도식의 라벨에는 topic 번호를 쓰지 않는다. 도식은 개념을 가리키고, 번호는 topic이 옮겨지면 틀린다.

## 3. 세션 구성

### 세션 목표와 요약

세션의 처음과 끝은 세션 전체를 한 장으로 보여 준다(Production이 검사한다).

- `01. 세션 목표`는 한 슬라이드, 목표 bullet **7개 이하**다. 목표가 늘어나면 관련 목표를 한 문장으로 합친다.
- 마지막 topic `요약`은 한 슬라이드이며 `### {세션 핵심}`과 `### 다음 세션`으로 구성한다. 다음 세션은 참조 형식의 세션명과 그 세션이 새로 답하는 결정 한 문장이다. 과정의 마지막 세션만 생략한다. 한 장을 넘으면 핵심 bullet을 줄이지 다음 세션을 빼지 않는다.
- 세션 목표·요약을 바꾸면 `course-design.md`의 세션 목표·세부 목차와 대조한다.

### topic 구성

- `course-design.md`의 세션 목표와 Anchor Message를 벗어나지 않는다. Anchor Message는 별도 블록으로 반복 표기하지 않고 학습자가 읽는 본문에 반영한다.
- 한 topic은 그 주제를 **대화로 설명하듯 충실히** 채운다. 정의·사례·도식·코드를 한 흐름으로 쓰고, 넘치면 줄이거나 자연스럽게 다음 장으로 잇는다. 정의와 적용, 문제·개념·한계 같은 요소별 틀로 topic을 쪼개거나 늘리지 않는다.
- **한 장의 메시지는 하나**다. 글머리표 없는 **lead 문장**(또는 topic을 여는 인용) 하나가 메시지를 말하고, 나머지는 그것을 설명하는 보조 bullet·하위 bullet이다. lead와 같은 급의 문장을 여럿 늘어놓지 않는다 — 같은 수준이 반복되면 무엇이 메시지인지 흐려진다. 이어지는 장에는 lead를 반복하지 않고 그 장의 내용이 맨 위에서 시작한다.
- 충실함은 글의 양이 아니다. **인용문이 아닌 본문 문장은 2줄 이내**(18pt 기준)로 쓰고, 넘으면 하위 bullet이나 별도 문장으로 나눈다. bullet은 도식·코드·표를 직접 가리켜 설명한다. 장황한 설명은 정리한다.
- **topic 제목은 본문 내용을 대표하는 키워드**다. 제목이 말하는 것과 본문이 다루는 것이 어긋나면(예: 제목은 "맥락"인데 본문은 불확실성만) 제목이나 본문을 고친다.
- 시작은 주제에 맞게 고른다 — 출처 있는 정의 인용, 질문, 사례의 상황. 출처 없는 정의 문장을 지어 인용 앞에 두지 않는다.
- topic 수와 분량은 주제가 정하며 균등 분할하지 않는다. 같은 질문에 답하는 topic이 둘 이상이면 하나로 **병합**한다(세션 안의 DRY). 병합은 heading을 이어 붙이지 않고 한 흐름으로 다시 쓴다.
- 학습자가 이해·판단하는 데 필요한 내용은 **모두 본문**에 둔다. 강사 노트에는 출처 검증과 강의 진행 메모만 둔다(「7. 강사 노트」).
- 과정 밖의 기법(예: 생산 관리의 원인 분석 기법)을 끌어오지 않는다. 과정의 판단은 과정의 모델로 설명한다(예: 역추적은 테스트 → 계약 → 상태 기계·시퀀스 → 유스케이스를 거슬러 오른다).
- 모델링을 다루는 세션에는 해당 기법의 **잘못된 관행** topic을 둔다. 잘못된 예와 바른 예는 표준·원전과 업무 의미에 비추어 정확해야 한다.
- 원칙·프로세스·접근법은 이름을 **명시**한다(예: 폭포수, 반복·점진(I&I), 애자일, 디자인 씽킹(DT), Lean Startup, Lean UX). 설계 원칙의 약어(SRP, CCP 등)는 그 약어가 나오는 topic에 원어를 `**주석**`으로 단다.

### 개요 세션과 상세 세션

- 개요 세션은 전체 흐름과 "왜"를 보이고, 다이어그램마다 **한 장의 미리보기**(다이어그램과 짧은 코드)를 둘 수 있다. 표기·작성법·코드 매핑의 상세는 해당 상세 세션이 맡는다.
- 개요의 단순화는 범위를 줄이는 것이지 **이름과 규칙을 바꾸는 것이 아니다**. 개요의 상태 값·이벤트 이름·업무 규칙은 상세 세션과 같다(「관통 사례와 식별자」).

### 관통 사례와 식별자

- 관통 사례의 **공통 식별자**(용어, 상태 값, 흐름 번호, 이벤트·오퍼레이션 이름, 외부 시스템)는 `course-design.md`의 공통 전제가 원천이다. 원고·다이어그램·예시 코드는 그 이름과 값을 그대로 쓴다.
- 앞 세션의 산출물(명세서·SSD·계약·정적 모델 등)을 뒤 세션의 **입력**으로 명시한다.
- 한 세션은 **하나의 구체 사례 값**(예: 주문 O-1 — 펜 2개, 단가 1,000원, 배송지 서울)으로 표·도식·코드·테스트를 관통한다. 일반론만으로 설명하는 topic을 만들지 않는다. 사례는 설명 속에 녹이며, 모든 topic을 사례 표로 만들지 않는다. 세션이 더한 교육용 가정은 `course-design.md` 공통 전제에 한 행으로 남긴다.
- 과정은 **기법을 배우는 것**이 목적이다. 도메인 때문에 복잡도를 높이지 않는다. 관통 사례는 요구 분석에서 정한 장면만 쓰고, 세션마다 새 사례를 더하거나 앞 세션의 가정에 기대는 교육용 가정의 사슬을 만들지 않는다. 필요하면 더 단순하게 한다.
- 뒤 세션이 분석으로 새로 발견한 것은 **진화**다. 앞 세션은 그 시점의 모델로 두고, 뒤 세션이 발견과 원래 산출물로의 되돌림을 해당 topic이나 실습 답의 **보완 (안)**에 함께 적으며, 공통 전제를 갱신한다. 되돌림만을 위한 별도 중간 산출물은 만들지 않는다.
- 뒤 세션의 답에 앞 산출물에 없던 기능·액터·개념이 있으면 먼저 발견 근거와 **보완 (안)**을 확인한다. 분석 과정에서 근거를 갖고 발견한 항목은 앞 산출물에 없다는 이유만으로 삭제하지 않고 진화로 유지한다.
- 같은 대상을 다른 이름·다른 규칙으로 쓴 것은 **오류**다. 공통 전제에 맞춰 앞 세션까지 고친다(Production이 세션 간 코드의 `enum` 값을 대조한다).
- 세션이 다루는 산출물이 **요구에서 코드까지의 경로**에서 어디에 있는지 밝힌다. 불변의 뼈대(요구 → 유저 스토리(수용 기준 포함) → 코드·테스트)인지, 어느 축(도메인·기술 복잡성) 때문에 넣는 중간 산출물인지를 쓴다. 산출물의 이름(요구사항 정의서·작업 명세서·도메인 모델·아키텍처)은 `sw-engineering-principles.md` 7절의 정의를 따른다. 사례에 필요 없는 산출물을 만들지 않으며, 오래 남는 산출물(요구사항 정의서·도메인 모델·의존 규칙)은 가리키고 다시 쓰지 않는다.
- **용어집**(Glossary)은 요구 분석 세션에서 정의하고(용어·정의·영문명), 뒤 세션은 모델마다 그 이름을 쓰는지 **환기**하고 발견한 용어를 되돌린다. 용어집을 세션마다 새로 정의하지 않는다.
- **분석은 한글, 설계는 영문**이다. 분석 모델(도메인 모델·분석 시퀀스·상태 기계)과 분석 예시 코드는 한글 용어를, 설계 모델(패키지·설계 클래스·설계 시퀀스)과 설계 코드는 **용어집의 영문명**과 과정의 **명명 규칙**을 쓴다. 본문 문장은 한국어로 쓰고, 설계 이름을 가리킬 때는 코드 표기(`Order`)를 쓴다. 전환이 처음 일어나는 세션에서 용어집 → 설계 이름의 대응을 보인다.

### 사례·가정·실습

- 사례의 주어진 사실, 교육용 가정, 추가 확인할 사항을 구분한다. 새 가정은 해당 예시 범위에서 명시하며 실제 정책이나 표준 요건처럼 제시하지 않는다.
- 사례를 다른 topic에서 재사용할 때 전제·용어·성공 조건을 유지한다. 성공 경로만 다루는 예시는 그 범위를 밝힌다.
- 실습은 수강생이 **LLM을 사용해** 진행한다. LLM의 초안은 검토 전의 가설이며, 추측으로 채운 정책·구현 요소를 찾아 질문으로 되돌리고 피드백으로 고치는 것이 실습의 핵심이다. 평가는 초안이 아니라 고친 곳과 그 이유를 본다.
- 과정의 실습은 **하나의 시나리오**로 이어진다. 강의 사례와 별개의 신규 개발 사례(과정 설계의 「사례·실습 방향」)를 쓰며, 각 실습의 결과물이 다음 실습의 투입물이다. 실제 수업에서는 수강생이 만든 결과물을 이어 쓴다.
- 실습의 결과물은 **강의 본문이 형식과 예를 보인 산출물**이며 대부분 **다이어그램**이다(모델링 과정의 핵심 산출물). 본문에서 표 한 장으로 지나간 것(대응표·추적표·판단표 등)을 결과물로 만들지 않는다. 결과물의 수는 `course-design.md`가 정하며 필요 이상 늘리지 않는다.
- 실습의 결과물 종류와 범위는 `course-design.md`의 「사례·실습 방향」과 정확히 맞춘다. 강의 본문에서 다룬 산출물이라도 실습 결과물로 정하지 않았다면 답에 추가하지 않는다.
- 투입물은 그 실습에 필요한 앞 산출물만 가리킨다. "산출물 전체"를 주지 않는다.
- **실습 답은 별첨이다.** 과제(`NN. 실습 — …`)는 본문에 두고, 답 "(안)"과 보완 (안)은 요약 뒤 `## 별첨. 실습 답` 아래의 번호 없는 서브 항목으로 둔다. 강의는 과제에서 요약으로 바로 이어지고, 별첨 슬라이드의 우측 상단은 `별첨: 세션명`이다. 별첨은 목차에 넣지 않는다. 답을 가리킬 때는 `별첨의 「시퀀스 다이어그램 (안)」`처럼 쓴다.
- 실습 사례도 도메인 복잡도를 높이지 않는다. 새 업무 개념이나 규모를 들이는 변경을 만들지 않는다.
- 실습은 세션 목표에 맞을 때만 둔다. 어느 세션에 실습이 없는지는 과정 설계의 「사례·실습 방향」이 정한다.
- 실습 과제(`NN. 실습 — …`)는 **한 슬라이드**다. 구성은 다음과 같다.
  - 안내 문장 한 줄 — 무엇을 LLM에 제공해 무엇을 만들고, 점검 항목으로 피드백해 완성하는지
  - `**서비스 개요**`(첫 실습) 또는 `**투입물**`: 본문은 `+ ` 줄로 쓴다. 투입물은 topic 번호가 아니라 **실습 단위**로 가리킨다(예: "실습 3의 도메인 모델 상세").
  - `**프롬프트**`: 본문은 `+ ` 줄로 쓴다. 수강생이 LLM에 그대로 입력하는 문장이며 필요한 만큼만(한두 개) 둔다. 단계가 둘이면 ①·②로 나눈다(예: 초안 → 상세).
  - `**점검 항목**`: 번호 목록 5~6개. 각 항목은 `**핵심어** — 확인할 질문` 한 줄이며, LLM이 흔히 빠뜨리는 **중요한 빈틈**을 가리킨다. 지엽적인 세부나 불필요한 예시·괄호 설명은 넣지 않는다. 점검 항목은 미확정을 질문으로 되돌려 없애게 한다. 불가피한 미확정만 이유와 함께 남긴다.
  - `**결과물**`: 다음 실습의 입력이 무엇인지 적는다.
  - 저장소·파일 경로(`code/…`)는 학습자 본문에 쓰지 않고 강사 노트에 둔다.
  - 세부 검토 기준은 강사 노트에 둔다.
- 답은 별첨(`## 별첨. 실습 답`)의 번호 없는 서브 항목 `<산출물> (안)`이다. 앞 실습의 결과물을 그대로 이어 받는 **하나의 시나리오**로 쓰며, 질문이 남지 않은 확정본이다.
  - 텍스트 답은 산출물 전체를 요약하는 **거버닝 메시지**(글머리표 없는 문단, 예: 명세서의 서비스 개요)로 시작한다. 거버닝 메시지는 두 단 위 전체 폭에 놓이고, 나머지는 한 장에 좌우 두 단으로 배치된다. 넘치면 대표가 아닌 규칙 일부를 생략하고 `......`로 표시한다. 답은 모든 내용을 보이지 않아도 된다.
  - 도식 답은 도식과 글을 상하로 배치한다.
  - 산출물이 여럿이면 (안)을 여러 topic으로 나눈다(예: `유스케이스 다이어그램 (안)`, `유스케이스 명세서 (안)`). 실습하지 않는 설명용 (안)도 둘 수 있다(예: 유스케이스 명세서 뒤의 `시스템 시퀀스 다이어그램 (안)`).
- 두 번째 실습부터는 답 맨 끝에 **보완 (안)** 한 장을 둔다. 이 실습에서 발견해 이전 산출물에 되돌릴 것(새 요구·규칙·개념, 책임 경계, 연관 방향 등)을 산출물별로 적는다.
  - 거버닝 메시지: 새로 발견한 것은 **후속 작업에 영향을 미치는 경우에만** 이전 산출물에 반영한다.
  - `**※ 현행화 기준**`에 **반영**(다음 실습의 입력이 되는 것)과 **기록만**(지나간 산출물이라 비용 대비 가치가 있을 때만 현행화하는 것)을 나눈다.
  - 앞 실습의 판단을 뒤 실습이 고치는 것은 **진화**다(예: 정적 모델에서 배송 회차에 둔 상태를 동적 모델이 정기배송 상태로 되돌림). 앞 (안)은 고치지 않고 보완 (안)에 적는다.
- 필요한 학습 내용과 품질을 먼저 완성한다. 정해진 시간이나 topic 수를 이유로 필요한 설명·사례·실습을 줄이지 않는다. 시간의 적합성은 최종 SA 완성 후 판단한다.

### 원고 수준 유지

- 새 topic도 「topic 구성」의 기준(충실함, 2줄 이내의 문장, 도식과 맞물린 bullet)으로 쓴다. 기존 topic의 형식을 그대로 복제하지 않는다.
- 개편 후에는 전·후 topic 목록을 비교해 **사라진 개념**이 없는지 확인한다. 의도적으로 뺀 개념만 빠져야 한다.

## 4. 문장과 강조

### 문체와 용어

- topic 제목은 **한글 중심의 짧은 키워드**다. 두 줄로 넘어가거나 우측 상단 세션명과 겹치지 않게 하고, 설명은 본문 첫 문장에 둔다.
- 일반 기술 용어는 한국어를 우선한다. 영어가 필요하면 본문 최초 등장 시 `한글(English full term, 약어)`로 쓰고 이후에는 한국어나 약어만 쓴다. 표준명·고유명사·약어·코드 식별자는 원문을 유지한다.
- 도식 안의 텍스트도 불가피한 표준명·고유명사·약어가 아니면 한국어를 우선한다. 한 라벨에 `제목 - 설명`을 담을 때는 `-`로 구분한다.
- 본문에 **사족**을 쓰지 않는다 — "이 과정의 …", "이 과정은 …", "이 과정에서"처럼 과정 자신을 가리키는 말 없이 내용만 쓴다(예: "이 과정의 SDD 지침" → "SDD 지침"). 원고 작업의 내부 용어(group, topic 등)도 본문에 쓰지 않는다(→ "목차"). 출처와 해석을 가르는 말("…는 원전의 분류가 아니다")은 강사 노트에 둔다.
- 명세에 관한 이름은 `sw-engineering-principles.md` 7절을 따른다 — **유저 스토리**("사용자 스토리"·"사용자 이야기"가 아니다), **수용 기준**(테스트 기준. "확인(예)"라고 쓰지 않는다. OOAD는 "인수 조건"), **요구사항 정의서**(시스템 전체·유지), **작업 명세서**(스토리 하나·작업용).
- 질문 문장은 `?`로 끝낸다. topic 제목도 의문문이면(`유저 스토리란?`, `무엇을 누가 쓰는가?`) `?`를 붙인다(Production이 경고한다). 문장을 단순 정의로 끝내기보다 앞뒤 학습 흐름이 이어지게 쓴다.
- 억지 번역보다 **통용되는 발음 표기**를 쓴다(예: round-trip test → 라운드트립 테스트, "왕복 테스트"가 아니다; UML frame → 프레임, "조각"이 아니다). 처음 등장할 때 원어를 병기하고(`프레임(frame)`) 뜻을 한 문장으로 정의한다. 이후에는 음차만 쓴다.
- **업계 표준 용어**를 쓴다. 표준 용어를 은유적 조어로 바꾸지 않는다(예: 인터페이스를 "약속", 변환을 "옮기기", 패키지 나누기를 "묶기"로 부르지 않는다). 처음 쓰는 설계 요소는 무엇인지 한 줄로 밝힌다(예: 연동 — 외부 시스템과 통신하는 클래스).
- 도식에 나온 이름(참여자·클래스·패키지)을 본문에서도 **그대로** 쓴다. 도식에 없는 이름으로 설명하지 않는다.
- 용어는 과정 전체에서 같은 뜻으로 쓴다(예: 유스케이스에서 `이벤트 흐름`이 기본 용어이고 `시나리오`는 특정 경로다).
- 한 bullet에 `라벨 — 설명`을 담을 수 있다. 두 부분이 같은 비중으로 강조돼야 하면 별도 줄과 하위 bullet으로 나눈다.

### 강조(bold)

- bold는 **판단에 필요한 핵심 키워드와 대비되는 개념**에만 쓴다. 한 문장 전체를 bold로 하지 않는다.
- 본문의 lead 문장과 bullet에는 핵심어를 **1~3개** bold로 둔다. 문장은 먼저 문장으로 읽혀야 하며, bold는 핵심어를 보조한다(핵심어만 늘어놓은 문장을 쓰지 않는다). 대비는 양쪽을 모두 bold로 한다.
- 질문 목록은 질문마다 **초점어**를, 절차 목록은 단계마다 **산출물·대상**을 bold로 한다.
- 표의 첫 열이 짧은 **항목명**이면 첫 열을 bold로 한다. 문장·예시·질문으로 된 열은 bold를 두지 않는다.
- 예외 — 유스케이스 흐름의 단계(명세 원문), 인용된 요청(`>`), 명사만 나열한 짧은 bullet, 강사 노트, 코드·도식 안의 텍스트. 코드의 선언된 이름은 Production이 bold로 표시하므로 코드 블록에는 `**`를 쓰지 않는다.

## 5. 인용과 출처

저자·책·논문·표준·공식 문서에 귀속되는 문장이나 수치는 **인용문 그룹**이다. 영어 원문이 없는 통계·정의·주장도 출처가 있으면 같은 형식을 쓴다.

- 인용은 그 topic의 **핵심 메시지를 받칠 때**만 쓴다. 같은 주장을 되풀이하거나 본문이 이미 설명한 것을 장식하는 인용은 두지 않는다.
- 인용문은 길이와 관계없이 **한 문단 하나의 인용**이다. 2줄 규칙을 적용하지 않는다.
- 영어 원문이 길면 한글은 전문을 번역하지 않고 **핵심만 요약**한다. 요약은 따옴표 없이 쓰고(원문처럼 보이지 않게), 쉼표 없이 한 문장으로 쓴다: `핵심 요약, "English original", [저자 연도]`. 한글 요약은 18pt, 원문과 출처는 10pt로 렌더된다.
- topic을 여는 인용은 그 topic의 lead 메시지가 된다(예: 저자의 포지셔닝 문장).
- 정의 인용 아래에서 그 정의의 기준을 주는 인용은 **들여쓴 bullet**로 둘 수 있다. bullet 한 줄이 아래 형식이고 영어 원문과 레이블을 갖추면 `**인용문**` 표식 없이 인용으로 렌더된다(`paragraphs.js`의 `bulletCitation`).

```text
**인용문**

"응집도는 한 요소의 책임들이 얼마나 강하게 관련되고 집중되어 있는가의 척도다", "cohesion … is a measure of how strongly related and focused the responsibilities of an element are.", [Larman 2004]

  - "모듈은 하나의, 오직 하나의 액터에 대해서만 책임져야 한다", "A module should be responsible to one, and only one, actor.", [Martin 2018]
```

- 형식: `"한글 번역", "English original", [저자 연도]` — 영어 원문이 없으면 `"한글 문장 또는 통계", [저자 연도]`. 원전을 직접 확인하지 못하고 재인용처로 확인했으면 `[저자 연도, 재인용]`으로 쓰고, 강사 노트에 **실제로 읽은 재인용처**(문헌명·링크)와 확인 범위를 적는다. "여러 출처가 인용한다"만으로는 근거가 되지 않는다.
- 한글과 영어 원문은 각각 `"..."`로 감싸고 한 문단 안에서 구분한다. `참고:`, `출처:` 같은 별도 줄을 두지 않는다. 원문 안의 따옴표는 `\"`로 쓴다(Production이 `"`로 출력한다).
- **출처는 레이블로 쓴다.** 인용·참조 모두 `[Larman 2004]` 형식이다. 저자는 성만 쓰고(둘이면 `[Beck·Cunningham 1989]`, 셋 이상이면 `[Gamma 외 1994]`), 단체는 약칭(`[OMG 2017]`), 같은 저자·같은 해가 둘 이상이면 `[Martin 2014a]`·`[Martin 2014b]`로 구분한다. 영문 위키백과는 `[Wikipedia: Use case]`로 쓴다. 한글 사이트는 출처로 쓰지 않는다.
- 레이블의 서지(서명·문서명, 판, 저자 전체 이름, 출판사, 연도, URL)는 과정의 별첨 `sessions/references.md`에 한 번만 둔다(「별첨 — 참고 자료」). 장·절·쪽 번호는 어디에도 적지 않는다. 확인하지 못한 연도는 레이블에 넣지 않고 별첨에서 그 사실을 밝힌다.
- 영어 원문은 재작성하지 않는다. 직접 인용은 확인한 문구를 정확히 옮기며, 요약은 따옴표로 원문처럼 제시하지 않고 `요약`으로 식별한다.
- 인용·참고 자료는 **적어도 인터넷에서 찾을 수 있어야** 한다. 확인되지 않은 서지 요소(출판사·URL·제목)는 채워 넣지 않고 지운다.
- 원전을 우선 확인한다. 원전을 확보하지 못하면 실제 본문을 읽은 추적 가능한 2차 인용처를 쓰며, 재인용임을 밝힌다. **검색 결과 요약이나 LLM의 기억은 검증 근거가 아니다.** 2차 인용의 반복 횟수를 독립 검증 횟수로 세지 않는다.
- 통계는 원래의 시점·대상·범위를 보존하고 일반화하지 않는다. 공식 초록·목차만 확인했다면 그 범위의 주장만 한다.
- 근거를 확인하지 못한 귀속·수치는 사실이나 인용으로 남기지 않는다. 학습에 필요한 설명은 확인한 근거로 다시 쓴다. 교육용 가정은 출처를 대신하지 않는다.
- 표준명은 공식 표기 그대로 쓰고(예: `ISO/IEC/IEEE 29148:2018`), 표준에 없는 판본·분류를 만들지 않는다.
- 출처 검증 과정이나 번역 메모는 본문에 넣지 않고 강사 노트에 둔다.

예: `"프로젝트 노력의 약 40~50%를 회피 가능한 재작업에 사용한다", "Current software projects spend about 40 to 50 percent of their effort on avoidable rework.", [Boehm·Basili 2001]`

### 별첨 — 참고 자료

과정마다 교재 맨 끝에 별첨 `courses/<course>/sessions/references.md`를 둔다. 세션 원고가 쓰는 모든 레이블이 여기에 있어야 한다(Production이 검사).

```text
--------------------
Session 명: 별첨. 참고 자료
--------------------

## 참고 자료

**참고 자료 목록**

1. **[Brooks 1986]**  No Silver Bullet, Frederick P. Brooks Jr., 1986
2. **[Larman 2004]**  Applying UML and Patterns, 3rd ed., Craig Larman, Prentice Hall, 2004
3. **[Wikipedia: Use case]**  Use case, Wikipedia, https://en.wikipedia.org/wiki/Use_case
```

- 별첨은 세션과 별도의 문서다(각 세션 끝에 붙이지 않는다). 기준 원전, 수강생이 공부할 책, 세션이 레이블로 인용·참조한 자료를 **하나의 목록**으로 둔다. 주요·인용으로 나누지 않는다. 영문 위키백과는 포함하고 한글 사이트는 쓰지 않는다.
- 항목은 `N. **[레이블]**  서명(문서명), 판, 저자, 출판사(게재지), 연도, URL` 한 줄이다. 없는 요소는 생략한다. 레이블의 알파벳 순서로 처음부터 끝까지 번호를 매긴다.
- 별첨은 목차·세션 목표·요약을 두지 않는다. 강사 노트는 둔다.

## 6. 표와 목록

- 표와 도식에는 **제목**을 단다(`**표 — 제목**`, `**도식 — PlantUML — 제목**`). 표·도식은 본문 문장이 직접 설명하거나 제목만으로도 무엇인지 바로 연결되어야 한다. 연결되지 않는 표·도식은 두지 않는다.
- 표나 목록으로 충분한 내용은 박스나 다이어그램으로 만들지 않는다. 반대로 **관계·흐름·상태·경계**를 표로 나열하면 그 관계가 사라진다 — 그런 내용은 도식으로 보인다(「8. Visual」). 목록은 구조를 보일 때 쓰고, 불필요한 계층을 만들지 않는다.
- 표와 도식은 앞 문장이나 뒤의 bullet이 **무엇을 보여 주는지** 직접 설명한다(예: "위가 도메인 모델, 아래가 물리 모델이다", "왼쪽 `Order`는 두 액터의 요청으로 바뀐다"). "표의 오른쪽 열이 …다" 같은 읽는 법만 말하는 정형 문장으로 대신하지 않는다.
- **설명을 위한 설명을 두지 않는다.** "표는 교육용 가정이다", "뒤 세션은 이 topic을 가리킨다", "자세한 것은 「NN」에서" 같은 범위·출처·참조 문장, 도식 제목과 같은 말을 되풀이하는 문장은 본문이 아니라 강사 노트에 둔다. 같은 내용의 표를 이웃 topic에 두 번 두지 않는다.
- 도식이나 코드로 이미 보이는 것을 표로 다시 만들지 않는다. 표는 비교할 값이 실제로 있을 때만 쓴다.
- 모델·패키지·계층처럼 **분류**하는 표에는 도식이나 코드와 맞춰 읽을 **대응 열**(예: 패키지)을 둔다.
- 짧은 항목이 많으면 의미가 유지되는 범위에서 5~6개 그룹으로 묶는다. 병렬 항목은 `A, B, C`처럼 한 문장으로 쓸 수 있다.
- 두 개 이상의 대비 개념에 각각 세부 항목이 있으면 하위 bullet으로 나눈다(예: 본질적 어려움/우연적 어려움).
- 라벨 아래에 항목을 나열할 때는 **들여쓰기 단계마다 bullet**을 둔다 — 라벨은 상위 bullet, 항목은 하위 bullet이다. 글머리표 없는 들여쓰기(`+ `)로 목록을 만들지 않는다.
- 순서가 있는 단계는 번호 목록(`1. `)으로 쓰고, 그것을 소개하는 문장 아래 **들여 쓴다**. bullet 안에 ①·② 같은 번호를 다시 붙여 글머리표와 번호가 겹치게 하지 않는다.
- 괄호는 **바깥이 주어, 안이 예**다: `개념 클래스(주문)`처럼 유형·개념을 밖에, 사례를 괄호 안에 쓴다. 괄호 안은 작게 렌더되므로 거꾸로 쓰면 핵심이 작아진다.
- 한 흐름의 이벤트를 표로 나열할 때는 행 순서가 이벤트 순서다. "기본 1·기본 2"처럼 번호를 붙여 별개의 흐름처럼 보이게 하지 않고 **기본 흐름 / 대안 흐름**으로 표시한다. 흐름 번호(1a, 3a)는 유스케이스 명세서 안에서 쓴다.
- 번호가 의미를 갖는 절차는 numbered list, 순서가 없는 항목은 bullet을 쓴다. 목차에는 bullet을 쓰지 않는다.
- 표의 **열 이름**은 무엇을 담는지 바로 알게 쓴다(예: "명세 여부", "주문한다(예)"). 목차 번호만 담는 "다루는 곳" 같은 모호한 열을 두지 않는다 — 필요하면 "비고"에 뜻을 쓴다. 질문형 열 이름·셀은 `?`로 끝낸다(Production이 경고한다).
- 표의 셀은 **한 줄**에 들어가게 핵심 구로 쓴다. 근거가 필요해 한 줄을 넘으면 판정만 남기지 말고(예: "높다") 표 대신 bullet로 쓴다. 셀 안의 topic 참조는 강사 노트로 옮긴다. 계약의 사후조건처럼 여러 사실을 담은 셀은 **사실마다 행**을 나누고, 이어지는 행의 첫 칸은 비운다(행 높이는 Production이 정한다).

## 7. 강사 노트

강사 노트는 학습자가 읽는 본문을 **보조**한다. 본문과 모순되는 내용이나 본문에 없는 새 주장을 두지 않는다. 학습자가 알아야 할 설명·통찰은 노트가 아니라 본문에 둔다.

- **모든 topic**에 `**강사 노트**`를 둔다(Production이 검사한다).
- 노트는 **bullet**로 쓰고, bullet 하나는 한 가지 일을 한다.
  - **강의 포인트** — 강조할 판단, 던질 질문, 흔한 오해
  - **근거·출처** — 인용·표준의 서지와 링크, 확인 범위, 재인용 여부
  - **가정·범위** — 교육용 가정, 성공 경로만 다룬다는 등의 범위
  - **연결** — 앞뒤 topic이나 다른 세션과의 관계(참조 형식을 따른다)
- 코드 topic의 노트는 코드가 **보장하는 것과 보장하지 않는 것**, 코드의 요소를 분석 모델에 역수입하지 않는다는 점을 밝힌다.
- Anchor Message는 노트에만 두지 않는다. 노트에만 있는 메시지는 본문 반영으로 보지 않는다.

## 8. Visual

### 쓰는 이유와 도구

- Visual은 **관계·구조·흐름·공간적 의미**를 텍스트보다 명확히 보여줄 때만 쓴다. 해당 개념이 등장하는 바로 그 topic에 두고, 종합 visual 페이지를 따로 만들지 않는다.
- 콘텐츠를 먼저 확정한 뒤 도구를 고른다. UML은 PlantUML(또는 `svg:uml`), 일반 흐름·관계는 Mermaid, 정량 데이터는 chart를 쓴다. 실제 수치 없이 chart를 만들지 않는다. 개념 도식은 개념도임이 드러나게 하고 측정된 관계처럼 보이지 않게 한다. 와이어프레임은 편집 가능한 SVG 등으로 둔다.
- 도구 때문에 내용을 바꾸지 않는다. 필요한 표현이 지원되지 않으면 Production을 확장한다.
- Markdown 하나로 의미와 visual 원본이 전달되도록 원본(PlantUML·Mermaid·SVG 등)을 본문에 둔다. ASCII 테두리를 최종 visual로 취급하지 않는다.
- 정보가 적으면 단순하게 그린다. 서로 다른 개념을 한 도식에 억지로 합치지 않는다.
- 세션의 visual은 **구성안에서 topic마다** 정한다(「12. 검토 절차와 완료 기준」). 표가 여러 topic 이어지면 그중 구조·흐름·상태를 보이는 것이 없는지 다시 본다. 표만 이어지는 세션을 만들지 않는다.

### 그리는 방법

- 배치는 **의미 순서**를 따른다(예: 도메인 모델이 위, 물리 모델이 아래, 업무 경계가 가운데, 연동이 바깥).
- 도식 안의 흐름은 **왼쪽 → 오른쪽**이 기본이다. 가로로 길면 2~3행으로 나누어 상하로 잇고, 의미 없이 세로로 긴 도식은 피한다.
- 화살표가 학습 순서·시간 순서·인과·메시지·분류·의미 연결 중 무엇인지 분명히 한다. 개념의 연관을 필수 개발 순서로 그리지 않는다.
- 선이 행동·상자·레인 경계를 **가로지르지 않게** 배치한다. 자동 배치로 겹침이 풀리지 않으면 `svg:uml`로 직접 배치한다.
- 같은 상호작용을 두 다이어그램으로 비교할 때는 **같은 메시지·같은 번호**로 **한 슬라이드**에 보인다.
- 표기 그림과 그 「표기와 사용법」 표는 한 슬라이드에 둔다.
- 도식의 글자 크기는 Production이 모든 도식에 같게 맞춘다(`production-guide.md`의 「Visual layout 및 가독성」 — 도식 안 글자 10pt). 요소가 적은 도식을 키워 그리지 않고, SVG는 도식 안 글자 크기를 한두 가지로 맞춘다.
- **도식과 제목을 분리한다.** 제목은 도식 밖에 두고 **다이어그램 이름만** 쓴다(예: `활동 다이어그램`). "— 상태를 바꾸는 단계" 같은 설명은 제목·도식 안에 넣지 않고, 필요하면 슬라이드 본문에서 설명한다.
  - 도식 하나는 `**도식 — … — 이름**` 제목(14pt)을 단다.
  - 여러 부분을 한 SVG에 담으면 부분마다 이름을 그 부분의 상자 **밖**(위)에 둔다. 이름은 기본 **14pt**(도식 안 글자의 1.4배로 그린다), 부분이 많아 14pt가 어려우면 **12pt**(1.2배)로 줄인다. Production은 SVG의 가장 작은 글자를 10pt로 맞추기 때문이다.
- 협력 예시는 책임 소유자와 조정 책임을 구분하고, 하나의 설계 대안을 보편적인 책임 배치로 단정하지 않는다.
- Production 가독성 문제를 해결하려고 의미를 훼손하거나 노드·관계를 삭제하지 않는다.

## 9. UML

### 공통

- UML을 설명하는 topic에는 **해당 notation 자체**를 함께 보인다. 다이어그램을 처음 쓰는 topic에서는 표기 요소를 나란히 보이고 요소마다 **이름·의미·사용법**을 표로 설명한다. 문법이 있는 표기(조각·가드·다중성·전이 라벨)는 쓰는 법을 예와 함께 보인다.
- 다이어그램을 소개하는 topic의 제목은 **다이어그램 이름**, 예제 topic은 **대상 + 다이어그램 약칭**(예: `결제 시퀀스`)으로 쓴다.
- 여러 다이어그램을 다루는 세션은 먼저 다이어그램들의 **정의와 정적 모델(또는 요구)과의 관계**를 한 곳에서 보인다.
- 모델을 만드는 다이어그램은 **초안 → 상세화**로 발전시킨다(유스케이스 다이어그램, SSD 초안 → 정제된 SSD, 클래스 다이어그램). 초안은 구조의 합의, 상세화는 규칙의 명시가 목적이다.
- **추상화 수준** — 분석 다이어그램은 업무 의미의 수준에서 그린다. 화면 조작·메서드 시그니처·DB 저장·플래그 조합 같은 구현의 세부를 넣지 않는다. 상태는 **같은 사건에 다르게 반응하는 상황**만 나눈다(상태 의존 객체). 상태·흐름이 늘어나는 문제는 표기법이 아니라 이 수준과 적정 모델링의 문제로 다룬다.
- 하나의 개념을 설명할 때 관련 없는 UML 요소를 함께 넣지 않는다(예: `유스케이스란 무엇인가?`에는 타원만).
- 다이어그램마다 같은 의미의 표현이 다르면 그 차이를 밝힌다(예: 시퀀스의 조각 ↔ 커뮤니케이션의 `[조건]`·`*`).
- UML 표기에는 **바탕색을 쓰지 않는다**. 스테레오타입은 `«enumeration»`, `«interface»`, 유스케이스 다이어그램의 외부 시스템 `«actor»`, 관계의 `«include»`·`«extend»`만 쓴다. 데이터 타입·도메인 유형 같은 분류는 도식에 표시하지 않고 본문에서 대응시킨다. 원형 표시·footbox처럼 표기 규칙을 지키는 렌더 설정은 Production이 넣으므로 원고에 쓰지 않는다.
- **패키지 다이어그램**은 무엇이 어느 패키지에 속하는지를 보인다. 클래스는 **이름만** 보이며 속성·오퍼레이션은 감춘다(Production이 감춘다). 속성과 규칙은 클래스 다이어그램이 보인다.

### 유스케이스 다이어그램

- 시스템 경계를 크게, 액터는 작게 그린다. **초안**은 주 액터(왼쪽), 유스케이스, 시스템 경계, 연관만 쓴다. **상세화**에서 외부 시스템 지원 액터를 오른쪽에 `«actor»` 상자로 더하고, 확인된 관계만 더한다.
- `«include»`는 기본 → 포함 유스케이스, `«extend»`는 확장 → 기본 유스케이스, 일반화는 특수 → 일반(실선·속 빈 삼각형)이다. 포함은 코드 공통화가 아니고, 확장은 기본 유스케이스가 독립적으로 의미를 갖는 전제에서 쓴다.
- 관계를 가르칠 때는 그 관계를 성립시키는 사례 전제를 같은 topic에 둔다. 유스케이스 사이의 일반 화살표로 순서나 흐름을 표현하지 않는다.

### 시퀀스 다이어그램·SSD

- **SSD**는 응답을 그리지 않는다. 외부 시스템에 보내는 메시지는 모두 **요청**(실선 화살표)이며 동기·비동기를 구분하지 않는다. 전달 방식은 설계에서 정한다.
- 메시지를 보내는 객체는 그 시점에 **다른 메시지를 처리하는 중**이어야 한다(처리 안의 호출). 아무 메시지도 처리하지 않는 객체가 요청을 보내게 그리지 않는다 — 커뮤니케이션 다이어그램의 중첩 번호(`1.1`)와 코드의 호출 안의 호출로 옮길 수 없다.
- 분석 시퀀스의 호출은 **동기**가 기본이며 응답을 그리지 않는다. 결과를 기다리지 않는 요청·통보만 비동기(열린 화살촉)로 구분한다.
- SSD 초안은 주 액터와 대상 시스템만, 정제된 SSD는 외부 시스템(지원 액터)까지 그린다. 시스템 안의 객체는 넣지 않는다.
- 분석 시퀀스의 생명선은 **도메인 개념의 인스턴스**(`:주문`)다. 컨트롤러·서비스·저장소 같은 설계 객체는 넣지 않는다. 설계 시퀀스는 설계 객체를 포함하며 용어집의 영문명(`:OrderService`)으로 그린다.

## 10. 코드 매핑

- 요구·분석의 결정이 **코드와 실행 결과에 어떻게 이어지는지** 보인다. 코드는 연결을 확인하는 예이지 최종 구현이나 모델의 자동 변환이 아니다.
- 코드는 **자기 topic**에 두고, 바로 앞에 **그 코드가 표현하는 도식**을 둔다. 도식 없이 코드만 제시하지 않는다.
- 코드는 **컴파일하고 실행해 확인한 것**만 싣는다. 전체 코드는 `courses/<course>/sessions/code/sNN/`에 두고, 슬라이드에는 도식이 표현하는 부분만 **발췌**할 수 있다. 생략은 `// ... <설명> 생략` 줄로 표시한다(Production이 발췌와 원본을 대조한다).
- 식별자는 **공통 전제·용어집의 이름**과 같다. 분석 예시 코드는 한글 용어, 설계 코드는 용어집의 영문명과 명명 규칙을 쓴다(「관통 사례와 식별자」). 용어집에 없는 업무 용어를 코드에서 먼저 만들지 않는다.
- **개념 클래스**는 필드와 생성자를 가진 `class`로 쓴다. 필드가 모델의 속성·연관을 드러낸다. `record`는 **데이터 타입**(금액·수량·주소)처럼 값으로 같은지 판단하는 것에만 쓴다.
- 코드가 **보장하는 것과 보장하지 않는 것**을 구분한다. 미확정 정책을 분기·예외·테스트 기대값으로 대신 결정하지 않는다. 코드의 요소(필드·보조 호출·설계 객체)를 분석 모델에 역수입하지 않는다.
- 학습자가 결과를 먼저 예측한 뒤 실행해 대조하게 한다.

다이어그램마다 코드로 이어지는 요소를 한 가지 이상 보인다. 아래 대응은 설계의 결정이 섞인 "이렇게 이어진다"의 예이지 변환 규칙이 아니다.

- **비동기**의 기준은 반환값이 아니라 호출자가 **완료를 기다리는가**다. **병행**(흐름의 순서)과 비동기를 섞지 않는다. 예제가 전달 방식(큐·이벤트)을 생략하면 그 사실을 밝힌다.
- 상태 기계의 화살표가 없는 이유는 **금지**(확인된 규칙)와 **미정**(요구 질문)으로 구분한다. 금지된 전이만 거절 테스트가 되며, 미정인 전이를 테스트 기대값으로 정하지 않는다.

| 다이어그램 | 모델 요소 | 코드에서 |
|---|---|---|
| **SSD** | 시스템 이벤트 / 외부 시스템에 보내는 요청 | 시스템 경계의 인터페이스 메서드 / 외부 시스템 인터페이스의 메서드(요청 하나가 메서드 하나) |
| **오퍼레이션 계약** | 사전·사후조건 | 호출 전 검사 / 호출 후 도메인 객체의 상태(생성·연관·속성), 계약의 예는 테스트 |
| **클래스** | 개념 / 속성·연관 / 속성 도메인 | 필드와 생성자를 가진 `class` / 필드(연관의 방향은 설계) / 값의 종류(`record`)와 생성 시 규칙 검사 |
| **클래스** | 다중성 `1..*` / 합성 / 파생 속성 / 확정 값 | 빈 값 거절 / 전체가 부분을 만든다 / 저장하지 않는 계산 / 시점의 값을 옮겨 적기 |
| **활동** | 행동 / 결정 / 분기·합류 | 메서드 호출 / `if` / 순서에 의존하지 않는 호출과 모두 끝난 뒤의 진행 |
| **시퀀스** | 메시지 / 생성 / 비동기 / `alt`·`loop` | 받는 객체의 메서드 / `new` / 완료를 기다리지 않는 요청 / `if`·`for` |
| **커뮤니케이션** | 링크 / 번호 `1.1` | 참조 필드 / 호출 안의 호출 |
| **상태 기계** | 상태 / 전이 / 가드 / 금지된 전이 | `enum` 값 / 상태를 바꾸는 메서드 / 전이 전 검사 / 거절과 그 테스트 |

## 11. 원전 기반 작성

교재는 분야별로 검증된 **기준 원전**(모범 서적·문서)을 토대로 강의하고, 수강생이 그 원전을 구해 공부·참고하게 하는 것을 목표로 한다. 여러 원전을 섞거나 작성자(LLM·강사)의 관점을 덧붙이면 초보자가 그 주제를 배우는 데 방해가 된다. 기준 원전과 주요 참고 자료는 `course-design.md`가 정한다(`course-design-guide.md`의 「기준 원전과 참고 자료」).

- 기법의 **정의·템플릿·표기·절차**는 기준 원전대로 쓴다. 원전에 없는 규칙·분류·틀을 만들지 않는다.
- 정의·템플릿 항목·표기·인용 문장은 **확인한 원문**으로 쓴다. LLM의 기억만으로 확정하지 않는다.
- 출처는 **저자·서명(문서명)·연도**로 밝힌다. 장·절·쪽 번호는 어디에도 적지 않는다.
- 원전마다 같은 개념을 다른 이름으로 부르면(예: Extensions·대안 흐름) 같은 것으로 다루고, `course-design.md`가 정한 이름 하나로 쓴다.
- 기준 원전에 없는 관점·비교·주제는 원고에 섞지 않는다. **제안**으로 따로 보이고 승인받은 뒤 넣으며, 넣을 때는 그 출처를 밝힌다.
- **그림은 모두 다시 그린다.** 원전의 사례 대신 관통 사례나 다른·유사한 시나리오를 쓴다.
- 원전의 **표를 가져오면** 표 제목에 출처를 적는다: `**표 — 도메인 규칙 (Larman, 2004)**`.
- 원전 문장은 핵심만 인용한다(「5. 인용과 출처」).
- 기법별 세부 규칙은 이 지침에 두지 않는다. 기준 원전을 따르고, 과정에서 내린 선택(사례에 적용한 방식, 원전 사이의 조정)은 `course-design.md`에 결정으로 기록한다.

## 12. 검토 절차와 완료 기준

### 검토 절차

1. Course Design의 세션 목표·Anchor Message·**공통 전제**를 확인한다.
2. **구성안**을 먼저 합의한다. 인용문만 확인하고 원고를 생성하지 않는다. 구성안은 topic 목록과 topic마다 **핵심 메시지·사례 값·visual 종류**(표, 클래스·시퀀스·상태·패키지·흐름 도식, 코드)·인용 배치를 담고, 채팅 text로 보여 승인받는다.
3. topic별 텍스트와 visual을 같은 위치에서 검토한다.
4. 먼저 충실히 쓰고, 넘치거나 같은 질문에 답하는 topic만 줄이거나 합친다. 병합·압축 후 사라진 개념이 없는지 전·후 topic 목록을 비교한다. 공간을 맞추려고 확인된 직접 인용문을 축약·교체하지 않는다. 중복 설명과 불필요한 사례를 줄이거나 배치를 조정한다.
5. 기본 원칙에 비추어 점검한다 — 이벤트 관점인가, 관점을 섞지 않았는가, 다이어그램이 답하는 질문이 있는가, 코드·테스트와 이어지는가, 같은 지식을 두 곳에 쓰지 않았는가, 추측으로 만든 내용이 없는가, **공통 식별자가 원천과 같은가**.
6. 용어·문체·강조·질문 표현·인용 형식과 강사 노트를 통일한다.
7. visual의 의미·전제·표기·원본 구조를 검토한다. 실제 글꼴·배치·분할·가독성의 판정은 Production이 한다.
8. 표준·인용·통계·기술적 주장의 원전 또는 실제 읽은 재인용처와 확인 범위를 검증한다.
9. 최종 Session Source로 변환하고 Production을 실행한다. **오류는 0개, 경고도 0개**가 되도록 원고를 고친다(`production-guide.md`의 「자동 검사 — 참조와 경고」). 실제 실행한 검사와 하지 않은 검사를 구분해 기록한다.
10. 문제의 원인이 공통 지침의 누락·모호함이면 지침을 함께 보완하고, 과정 고유 판단은 과정 문서에 반영한다.

검토 중에는 사용자가 요청하지 않는 한 임의의 PPT 시안이나 Production과 다른 이미지를 만들지 않는다.

### 완료 기준

- 세션명 헤더가 있고, 목차와 본문 topic이 1:1로 일치한다.
- 각 topic의 제목·첫 문장·본문·visual·코드가 같은 질문에 답하고, 사례 없이도 핵심 설명이 성립한다.
- 세션 목표(한 장·7개 이하)와 요약(한 장·다음 세션 포함)이 규칙을 따른다.
- Course Design의 세션 목표와 Anchor Message를 학습자가 읽는 본문에서 충족한다.
- 강의에 필요한 설명·사례·비교·코드·visual·실습이 충분하고 순서가 자연스럽다.
- 공통 식별자가 `course-design.md`의 공통 전제와 같고, 진화는 발견과 되돌림이 보인다.
- 인용·통계·표준이 확인한 근거에 기반하며, 직접 인용·요약·교육용 가정이 구분된다.
- 코드는 컴파일·실행으로 확인되었고 도식과 짝을 이룬다.
- 모든 topic에 규칙에 맞는 강사 노트가 있다.
- Production 자동 검사의 오류·경고가 0개다(제작 검증은 선행 조건이 아니다, `production-guide.md`의 「SA와 Production의 검증 경계」).
- renderer의 현재 지원 여부와 관계없이 최종 원고로 사용할 수 있다.

## 13. Production과의 관계

- 정상 Production 입력은 최종 Session Source 하나다. 실행 명령·출력·검증 산출물은 `production-guide.md`가 관리하며 이 지침에 중복하지 않는다.
- Session Source를 renderer 한계에 맞추기 위해 수정하지 않는다. renderer 편의를 위한 내용 삭제, 임의의 문법 치환, slide별 수작업 배치 지시를 하지 않는다.
- Production이 원고의 내용·도식 구조·표기 문제를 발견하면 피드백 문서를 사용자와 함께 검토해 학습 목적을 기준으로 수정 여부를 정한다. Production의 렌더링·배치·글꼴 문제는 원고 수정으로 해결하지 않는다.

### 하지 말아야 할 것

- 별도 Curriculum artifact·Session DD 생성
- 세션 끝의 `요약` topic 말고 따로 만드는 중간 정리·요약 slide, notation 종합 slide
- 개념 설명보다 visual을 먼저 만들고 그 visual에 맞춰 내용을 왜곡
- 표준이나 원전에 없는 용어·판본·분류의 창작
- 이벤트 흐름에 내부 처리 단계와 가능한 모든 예외 삽입
- 개요 세션에서 공통 식별자(상태 값·이벤트 이름·규칙)를 다르게 단순화
