# Session Authoring Guide

## 목적

Session Authoring(SA)은 `course-design.md`의 세션 정의를 입력으로 받아, 실제 강의와 Production에 사용할 최종 Session Source Markdown을 작성한다.

SA는 별도 Curriculum/DD artifact를 만들지 않는다. Human+LLM이 내용에 대해 자유롭게 논의하고, 최종 결과를 하나의 Session Source에 통합한다.

모든 세션은 `sw-engineering-principles.md`의 기본 원칙을 따른다. 특히 다음을 원고에서 지킨다.

- 요구는 **이벤트 관점**에서 시작하고, 화면·데이터·기술·해결책을 요구와 섞지 않는다.
- 다이어그램은 질문에 답할 때만 그리고, **다이어그램은 코드와, 코드는 테스트와** 이어서 보인다(「코드 매핑 원칙」).
- 교재 자체도 **KISS·DRY·YAGNI**를 따른다 — 같은 설명을 여러 topic에 반복하지 않고, 필요 없는 슬라이드·도식을 만들지 않으며, 본질적 복잡성은 숨기지 않는다.
- 원칙의 문장·표를 그대로 복사하지 않고, 세션의 사례와 결정에 맞게 적용한다.

## 입력

- 해당 과정의 `course-design.md`
- 상세화할 세션 번호와 세션명

예:

`S01을 상세화하라.`

## Session Source 필수 형식

모든 Session Source Markdown은 파일 최상단에 다음 세션명 헤더를 반드시 포함한다.

```text
--------------------
Session 명: NN. 세션명
--------------------
```

예:

```text
--------------------
Session 명: 01. OOAD 개요
--------------------

## 목차

01. 세션 목표
02. ...

## 01. 세션 목표
...
```

규칙:

- `Session 명`은 `course-design.md`의 해당 세션명과 일치해야 한다.
- 세션 번호를 포함한다. 예: `01. OOAD 개요`.
- 이 헤더는 slide topic이나 본문 content가 아니다.
- Production은 이 값을 읽어 각 슬라이드 우측 상단의 세션명으로 사용한다.
- 사용자가 Production 실행 시 세션명, title, source 등의 metadata를 다시 입력하지 않는다.
- Session Source Markdown 하나가 Production의 입력 authority다.

## 목차와 Topic 번호 규칙

- `목차` 자체에는 번호를 붙이지 않는다.
- 목차 항목은 `01.`, `02.`, `03.` 형식으로 번호만 사용한다. 번호 앞에 bullet(`-`)을 붙이지 않는다.
- 첫 번째 목차 항목은 `01. 세션 목표`부터 시작한다.
- 마지막 목차 항목(topic)의 제목은 `요약`으로 통일한다. `정리`, `정리와 다음 단계` 같은 변형을 쓰지 않는다.
- 목차의 항목명과 실제 본문 heading은 1:1로 정확히 일치해야 한다.
- 목차의 번호와 본문 heading 번호도 정확히 일치해야 한다.
- 목차에서는 축약 제목을 쓰고 본문에서는 다른 제목을 쓰는 식의 변형을 하지 않는다.
- topic을 추가·삭제·이동하면 목차와 본문 번호를 함께 갱신한다.
- 본문 topic은 `## NN. 제목` heading으로 정의하며, `## 목차` 자체는 topic이 아니다.
- 목차와 본문 topic은 `01. 세션 목표`부터 빠짐없이 연속 번호를 사용하고, 번호·제목이 중복되지 않아야 한다.
- 최종 Session Source에서 목차와 본문 heading의 번호·제목·순서가 정확히 대응하는지 확인한다. 불일치를 발견하면 원고를 수정한 뒤 Production에 전달한다.

예:

```text
## 목차

01. 세션 목표
02. 요구공학의 본질
03. 요구공학의 주요 활동

## 01. 세션 목표
...

## 02. 요구공학의 본질
...
```

## Session Source에 포함할 수 있는 내용

세션 목적에 필요한 내용을 자유롭게 구성한다.

- 설명
- 정의
- 사례
- 비교 / 반례
- 코드
- 표
- UML
- Diagram
- Chart
- Image
- 실습
- 강사 노트

내용 구조는 세션의 학습 흐름을 우선한다. Renderer가 현재 지원하는 기능 때문에 내용을 삭제하거나 왜곡하지 않는다.

## 작성 원칙

- `course-design.md`의 세션 목표와 Anchor Message를 벗어나지 않는다.
- Course Design의 Anchor Message는 세션 전체의 방향 기준이다. Session Source에서 `### 앵커 메시지` 같은 별도 블록으로 반복 표기하지 않는다.
- 각 topic은 제목에 직접 답하는 **핵심 설명 또는 정의**로 시작하고, 세부 설명·항목·사례·비교·visual이 뒤따르도록 구성한다.
- 인용문이 해당 개념의 가장 적절한 출발점인 경우에는 인용문을 먼저 제시하고, 바로 뒤에서 그 의미를 설명한다.
- 세션 내부의 topic 수와 분량은 주제에 따라 결정한다. 균등 분할하지 않는다.
- 설명보다 판단과 이해에 필요한 구조를 우선한다.
- 불필요한 산출물이나 중간 artifact를 만들지 않는다.
- 같은 개념을 반복 설명하지 않는다.
- 정의, 사례, 비교, 반례, visual은 학습 목적이 있을 때만 사용한다.
- 코드와 도식은 추상적인 장식이 아니라 개념을 구체화해야 한다.
- 출처가 필요한 주장과 인용은 Session Source 안에 남긴다.
- 강사 노트는 `**강사 노트**` 아래에 작성한다.
- 슬라이드 본문에는 수강생이 이해·판단하는 데 필요한 내용만 둔다. 출처 검증 과정, 저자별 차이, 작성 이유 등은 수강생에게 필요한 경우가 아니면 강사 노트에 둔다.
- 모델링을 다루는 세션에는 해당 기법의 **잘못된 관행** topic을 둔다. 잘못된 예와 바른 예는 표준·원전과 업무 의미에 비추어 **정확해야** 한다. 흔히 쓰이지만 틀린 관행을 바른 예로 제시하지 않는다.
- 앞 세션의 산출물(유스케이스 명세서·SSD·계약, 정적 모델 등)을 뒤 세션의 **입력**으로 명시한다. 분석에서 발견한 누락·모순은 원래 산출물에 **되돌려 보완한다고 언급**하며, 보완을 위한 별도 topic이나 산출물을 만들지 않는다.
- 개념 설명은 과도하게 세분화하지 않는다. 핵심 판단에 기여하지 않는 세부사항은 별도 규칙·강사 노트·후속 세션으로 분리한다.

## 문체와 강조 규칙

- topic 제목은 원칙적으로 **한글만 사용**한다.
- topic 제목은 **짧은 키워드**로 쓴다. 슬라이드 제목이 두 줄로 넘어가거나 우측 상단 세션명과 겹치지 않게 한다. 설명은 제목이 아니라 본문 첫 문장에 둔다.
- 일반적인 기술 용어는 한국어를 우선한다.
- 영어가 필요한 경우 본문 최초 등장 시 `한글(English full term, 약어)` 또는 `한글(English)` 형식을 사용하고, 이후에는 한국어 또는 필요한 약어만 사용한다.
- 이미 앞에서 정의한 약어의 영문 전체 명칭을 뒤 topic에서 반복하지 않는다.
- Mermaid, PlantUML, Chart 내부 텍스트도 불가피한 표준명·고유명사·약어가 아니면 한국어를 우선한다.
- 도식 내부 한 라벨에 `제목 - 설명`을 함께 담을 때는 `-`로 구분한다. Production이 `-` 뒤에서 자동으로 줄바꿈하고 작게 렌더링한다.
- 표준명, 고유명사, 약어, 코드 식별자처럼 원문 유지가 필요한 것은 예외로 한다.
- 질문 문장은 `?`로 끝낸다.
- 한 문장 전체를 불필요하게 bold 처리하지 않는다.
- **판단에 필요한 핵심 키워드와 대비되는 개념**만 bold 처리한다.
- 문장을 단순 정의로 끝내기보다 앞뒤 학습 흐름이 자연스럽게 이어지도록 작성한다.
- 공통 용어는 Course Design과 여러 세션 사이에서도 일관되게 사용한다. 다른 의미를 가진 사례를 이름만 같게 만들지 않는다.
- 세션·topic 교차참조는 번호와 제목을 함께 적고, 이동·제목 변경 시 참조도 갱신한다. 형식은 아래 「참조 형식」을 따른다.

### 참조 형식

- **세션**은 정확한 세션명을 큰따옴표로 쓴다: `"03. 정적 모델 — 도메인 개념과 관계"`. `S03`, `s03.md` 같은 파일명식 표기를 쓰지 않는다.
- **topic**은 번호와 제목을 겹낫표로 쓴다: `「26. 주문 취소 시퀀스」`. 같은 세션의 topic을 가리킨다.
- **다른 세션의 topic**은 세션명 바로 뒤에 쓴다: `"02. 요구 분석과 유스케이스"의 「44. 시스템 오퍼레이션과 계약」`. 여러 topic은 `·`, `,`, `과/와`로 잇는다. "같은 세션의" 같은 지시어로 대신하지 않는다.
- Production은 이 형식으로 모든 참조를 검증한다. 번호·제목이 대상 세션의 heading과 다르면 생성을 중단한다.
- 용어는 해당 세션 전체에서 일관되게 사용한다. 예: 유스케이스에서는 `이벤트 흐름`을 기본 용어로 사용하고, `시나리오`는 특정 경로를 가리킬 때만 사용한다.
- 주제와 설명을 별도 줄과 하위 bullet으로 나눌 필요 없이 한 bullet에 `라벨 — 설명` 형태로 담을 수 있다. Production이 `—` 이후 텍스트를 자동으로 약간 작게 렌더링한다. 두 부분이 동등한 비중으로 강조돼야 하면 대신 별도 줄과 하위 bullet으로 나눈다(예: 본질적 어려움/우연적 어려움).

## 인용문과 출처 규칙

저자·책·논문·표준·공식 문서에 귀속되는 문장이나 수치는 **인용문 그룹**으로 취급한다. 영어 원문이 없는 통계·정의·주장도 출처가 명시되어 있으면 같은 인용문 포맷을 사용한다.

영어 원문이 있는 경우:

`"한글 번역", "English original", 저자, 년도`

영어 원문이 없는 경우:

`"한글 문장 또는 통계", 저자, 년도`

원전을 직접 확인하지 못했지만 여러 독립된 출처가 일관되게 인용하고 있는 경우, 맨 끝에 `www`를 추가한다:

`"한글 번역", "English original", 저자, 년도, www`

규칙:

- 한글(과 있으면 영어 원문)은 각각 `"..."`로 감싼다. 저자·년도·`www` 표시는 감싸지 않는다.
- 한글, 영어 원문, 저자, 년도를 줄바꿈하지 않고 한 문장 안에서 구분한다.
- `참고:`, `출처:` 같은 별도 본문 줄을 추가하지 않는다.
- 영어 원문은 임의로 재작성하지 않는다. 직접 인용은 확인한 문구를 정확히 옮기며, 발췌 범위를 표시한다. 요약은 따옴표로 원문처럼 제시하지 않고 `요약`으로 식별한다.
- 저자명과, 확인된 경우의 발행년도만 기록한다. 책/논문/게시물 제목, 게재지, 페이지, 조항 번호, URL은 슬라이드 본문에 넣지 않는다 — 길어질수록 학습자에게 필요한 정보가 아니라 저작 과정의 흔적이 된다. 발행년도를 확인하지 못했으면 생략한다(추측해서 넣지 않는다).
- 어떤 주장을 뒷받침하는 부연 설명(예: 후속 연구자가 원 자료의 표본 범위를 직접 확인한 결과)은 별도의 `**인용문**`으로 만들지 않는다. 해당 인용문의 저자/년도 뒤에 괄호로 짧게 붙인다.
- 통계는 원래의 시점·대상·범위를 보존한다. 과거 연구나 한 표본의 수치를 현재 모든 프로젝트의 사실로 일반화하지 않는다.
- 공식 공개 초록·목차·범위만 확인했다면 그 범위에서 뒷받침되는 주장만 한다. 표준 본문 전체나 특정 정의·조항까지 검증한 것으로 취급하지 않는다.
- 근거를 확인하지 못한 주장은 최종본에 사실이나 인용으로 남기지 않는다. 원전을 확보하거나, 검증된 근거로 다시 쓰거나, 뒷받침할 수 없는 주장만 제거하면서 학습 목적에 필요한 설명·질문·비교를 보완한다.
- 교육용 가정은 출처를 대신하지 않는다. 저자의 말이나 표준의 사실을 임의 가정으로 바꾸어 유지하지 않는다.
- 원전을 우선 확인한다. 원전을 확보하지 못하면 실제 본문을 읽은 학술 논문·전문지·저자 글·공식 재수록 자료 등 추적 가능한 2차 인용처를 사용할 수 있다. 확인하지 못한 원전을 직접 읽은 것처럼 인용하지 않는다. 검색 결과 요약이나 LLM의 기억은 검증 근거가 아니다.
- 재인용은 원저자·원문헌과 실제 읽은 재인용처의 저자·제목·연도·링크·확인 위치를 구분해 적는다. 원문헌의 연도·판본·페이지도 재인용처에서 확인한 범위만 표시한다. 재인용처 본문 확인과 원전·원자료 검증은 서로 다른 상태다.
- 2차 인용의 반복 횟수를 독립적인 검증 횟수로 세지 않는다. 같은 최초 자료를 반복 인용한 자료인지 확인하고, 문구·귀속·분모·표본·시점·방법의 한계를 보존한다. 신뢰도가 낮거나 귀속이 상충하는 인용 모음은 검증된 원전과 동등하게 취급하지 않는다.
- 원전을 찾지 못했다는 이유만으로 학습에 필요한 정의·역사적 근거를 통째로 제거하지 않는다. 확인한 재인용을 명시하거나 직접 확인한 다른 근거로 보완한다. 어떤 자료에서도 확인하지 못한 귀속·수치는 사실로 넣지 않는다.
- 번역 자료는 확인 가능한 원문과 문맥·범위를 대조하고, 원전 대신 재인용처를 확인했다면 그 사실을 표시한다. 번역·직접 인용·요약·수업의 해석을 구분한다.
- 표준명은 공식 표기 그대로 사용한다. 예: `ISO/IEC/IEEE 29148:2018`.
- 표준에 없는 `제2판`, `제3판` 같은 표현을 임의로 추가하지 않는다.
- 출처 검증 과정이나 “이 인용문은 이렇게 번역했다” 같은 작성 메모는 Session Source 본문에 넣지 않는다.
- Production은 인용문 그룹을 다음과 같이 표현한다.
  - 한글 번역/한글 문장: 18pt
  - 영어 원문: 10pt
  - 출처: 10pt
  - 영어 원문이 없어도 출처는 10pt

예 (원전 확인):

`"프로젝트 노력의 약 40~50%를 회피 가능한 재작업에 사용한다", "Current software projects spend about 40 to 50 percent of their effort on avoidable rework.", Barry Boehm·Victor R. Basili, 2001`

예 (원전 미확인, 여러 출처가 일관되게 인용):

`"재작업 비용의 약 70~85%가 요구사항 결함에서 비롯된다", "70% to 85% of all project rework costs are due to errors in requirements.", Dean Leffingwell, 1997, www`

## 의미 표식과 블록 경계

- `**인용문**`은 독립된 한 줄에 둔다. 바로 다음의 **비어 있지 않은 한 문단만** 인용문 그룹이며, 다음 빈 줄에서 끝난다. 여러 인용문은 각각 표식을 붙인다. 한 문단 안에서 한글 문장, 있으면 영어 원문, 서지·링크 순서로 쓴다. 따옴표 안 쉼표나 링크 내부 문자를 구분자로 잘못 해석하지 않는다.
- 인용문 안의 bold는 강조만 뜻한다. 인용문 그룹이나 한글·영문·출처 영역, 글꼴 크기 규칙을 바꾸지 않는다. 영역을 확실히 판별할 수 없으면 추측하지 않고 해당 문단을 보고한다.
- 고객 발언·과제·템플릿의 Markdown `>` 블록은 인용문 그룹으로 자동 분류하지 않는다. 학술 인용으로 렌더할 문장은 위 표식을 사용한다.
- `**강사 노트**`는 독립된 한 줄에 둔다. 이후 내용은 코드 블록 밖의 다음 수평 구분선 또는 다음 `## NN. 제목` 전까지 강사 노트다. 노트 안의 `###` 소제목은 본문 복귀 신호가 아니다. 파일 끝에서도 종료된다.
- 본문 `###` 이하 heading은 topic 내부 소제목이다. 별도 topic이나 자동 슬라이드 분할 명령이 아니다. 강사 노트 뒤에 학습자 본문을 이어 써야 한다면 본문을 노트 앞으로 옮겨 의미 경계를 명확히 한다.
- `**페이지 분할**`은 독립된 한 줄에 두는 명시적 페이지 분할 지시다. Production의 자동 분량 추정과 무관하게, 이 표식이 있는 지점에서 topic의 현재 페이지를 반드시 닫고 다음 내용을 새 페이지로 시작한다. 한 topic이 여러 페이지로 나뉘어야 하는 이유가 분량이 아니라 의미상 구분(예: 기본 예시 vs 반례, 서로 다른 소주제)일 때만 사용한다. 자동 분량 추정으로 이미 원하는 지점에서 나뉘고 있다면 표식을 추가하지 않는다. 표식 자체는 PPT 본문에 출력하지 않는다.
- 범례와 그 표기 표, 짧은 표 두 개, 표와 짧은 후속 설명처럼 한 장에 들어갈 수 있는 내용 사이에는 `**페이지 분할**`을 두지 않는다. Production이 같은 구간의 표·텍스트·visual을 들어가는 만큼 한 장에 쌓는다.
- `**다이어그램 — 시퀀스 다이어그램**`은 topic 제목에 다이어그램 이름이 없는데 그 topic이 특정 다이어그램을 설명하거나 예로 보일 때, 제목 바로 아래 한 줄에 둔다. 슬라이드 제목의 둘째 줄(11pt)로만 표시되며 목차와 본문에는 나타나지 않는다. 제목에 이미 다이어그램 이름(시퀀스, 활동, 상태 기계 등)이 있으면 쓰지 않는다.
- `**도식 — Mermaid**`, `**도식 — PlantUML**`, `**도식 — SVG**`는 뒤 visual의 유형을 알리는 표식이다. `mermaid`, `plantuml:<kind>`(`usecase`, `class`, `sequence`, `communication`, `state`, `activity`), `svg` fenced block은 렌더할 visual 원본이다. `gherkin`, 일반 코드·text fenced block은 학습자에게 보여주는 코드·예시다. 표식 자체는 PPT 본문에 출력하지 않는다.
- 새 visual 유형을 도입할 때는 원본 문법·블록 경계·출력 의미를 SA와 Production에 함께 정의한다. 기존 미지원 기능을 이유로 원고를 일반 코드나 이미지 설명만으로 대체하지 않는다.
- 수동 목차 정책이나 의미 표식 문법을 변경하면 SA·Production 지침과 실제 파서의 계약을 함께 갱신한다. 지침 수정만으로 파서 구현이 완료됐다고 간주하지 않는다.

## 시간·가정·실습의 작성 기준

- 필요한 학습 내용과 품질을 먼저 완성한다. 정해진 시간이나 topic 수를 이유로 필요한 설명·사례·실습을 줄이거나 세션 밖으로 밀어내지 않는다.
- 설명·실습·검토의 실제 소요 시간과 운영 적합성은 최종 SA 완성 후 판단한다. 실습 시간·휴식 포함 여부를 근거 없이 확정하지 않는다.
- 사례의 주어진 사실, 교육용 가정, 추가 확인할 사항을 구분한다. 새 가정은 해당 예시의 범위에서 명시하며 실제 업무 정책이나 표준 요건처럼 제시하지 않는다.
- 사례를 다른 topic에서 재사용할 때 전제·용어·성공 조건을 유지한다. 범위를 바꾸면 변경한 전제를 함께 설명한다.
- 성공 경로만 다루는 예시는 그 범위를 밝힌다. 실패나 동시성에 관한 보장을 암묵적으로 추가하지 않는다.
- 실습은 목표, 주어진 조건, 수행 과제, 기대 결과물, 검토 기준을 포함한다. 필요한 경우 강사 노트에 전제가 명확한 검토 예를 제공한다.
- 미확인 정책을 임의로 채운 답을 정답으로 취급하지 않는다. 사실·가정·확인 질문과 선택 근거를 평가한다.

## Visual 작성 원칙

- Visual은 해당 개념이 등장하는 **바로 그 topic**에 둔다. 표기법을 설명하기 위해 별도의 종합 visual 페이지를 임의로 추가하지 않는다.
- 사용자가 검토할 때는 Session Source의 text와 필요한 visual을 같은 위치에서 함께 보여준다.
- 검토 단계에서 Production 결과와 다른 임의의 PPT 이미지나 장식용 이미지를 만들어 품질 판단을 혼동시키지 않는다.
- 실제 Session Source에 들어갈 도식은 가능한 한 최종 Production에서 재현 가능한 문법과 구조로 검토한다.
- Visual은 정보가 적으면 단순하게 유지한다. 한 장에 여러 개념을 억지로 합치지 않는다.
- 하나의 topic은 하나의 핵심 메시지를 우선한다.
- 표나 목록으로 충분한 내용은 억지로 박스나 다이어그램으로 만들지 않는다.
- 이미지나 다이어그램을 쓰는 이유가 “보기 좋아서”가 아니라 **관계·구조·흐름·공간적 의미를 텍스트보다 명확히 보여주기 위해서인지** 확인한다.
- 도식 내부 흐름은 특별한 이유가 없으면 **왼쪽 → 오른쪽**을 기본으로 한다.
- 노드·관계가 많아 가로로 지나치게 길어지면 한 줄에 억지로 늘이지 말고 **2~3행으로 나누어 상하로 연결**한다.
- 특별한 의미가 없다면 세로로 길게 늘어진 도식은 피한다.
- SA에서는 visual의 의미·관계·표기와 편집 가능한 원본을 검토한다. 최종 PPT 표시 크기의 **목표 10pt**, 배치·분할·잘림·가독성의 실제 판정은 Production에서 수행한다.
- Production 가독성 문제를 해결하려고 의미를 훼손하거나 노드·관계를 삭제하지 않는다. 실제 결과를 바탕으로 배치·분할을 검토하되, 내용 변경은 학습 목적에 근거한다.
- 화살표가 학습 순서·시간 순서·인과·메시지·분류·의미 연결 중 무엇을 뜻하는지 확인한다. 개념의 연관을 필수 개발 순서나 필수 기술 의존으로 그리지 않는다.
- 협력 예시는 책임 소유자와 조정 책임을 구분하고, 하나의 설계 대안을 보편적인 책임 배치로 단정하지 않는다.
- 와이어프레임은 편집 가능한 SVG 등의 원본 또는 실제 이미지를 본문과 같은 위치에 둔다. ASCII 테두리를 최종 visual로 취급하지 않는다. 정적 화면이 검증할 수 있는 내용과 실제 동작·사용 검증을 구분한다.
- Markdown 하나로 의미와 visual 원본이 전달되도록 필요한 소스를 본문에 포함한다. 예를 들어 `svg` 코드 블록은 편집 가능한 visual 원본이며 Production은 실제 visual로 렌더해야 한다.

## Visual 도구 선택 원칙

콘텐츠를 먼저 확정한 뒤 표현 목적에 맞는 문법을 선택한다.

- **UML**: PlantUML 등 UML 의미와 표기법을 정확히 보존할 수 있는 도구를 사용한다.
- **일반 흐름·관계·프로세스 다이어그램**: Mermaid 등 관계와 흐름을 명확히 표현하는 도구를 사용한다.
- **정량 Chart**: 실제 수치가 있고 차트가 이해를 개선할 때만 chart 도구를 사용한다. 설명 목적을 위해 임의 데이터를 만들지 않는다.
- **개념 도식**: 측정값 없이 개념적 관계를 설명할 수 있다. 개념도임을 표시하고 수치·함수·교차점이 실제 측정된 관계처럼 보이지 않게 한다. 근거 없는 보편적 법칙이나 정확한 최적점을 암시하지 않는다.
- **Wireframe / UI sketch / Image**: 필요한 경우 별도 image/HTML/SVG 등 적절한 표현을 사용한다.

도구 선택 때문에 내용을 바꾸지 않는다. 필요한 표현을 현재 Production이 지원하지 않으면 Production을 확장한다.

관련 세션에서 사용하는 아래 UML·유스케이스·요구사항 원칙은 여러 과정에서 재사용 가능한 공통 작성 기준이다. 모든 세션에 해당 기법을 적용하라는 뜻은 아니다. 특정 과정의 전체 또는 복수 세션에 공통인 추가 전제·용어·사례는 해당 과정의 `course-design.md`에 한 번만 정의하며, 과정별 지침 파일을 별도로 만들지 않는다. 과정 간 기법 규칙이 충돌하거나 공통 규칙으로 적용 범위를 구분하기 어려워지면 분리 필요를 재검토한다. 문서 길이의 임의 비율만으로 분리하지 않는다.

## UML 작성 원칙

- UML을 설명하는 topic에는 개념 설명뿐 아니라 **해당 UML notation 자체**를 함께 보여준다.
- 다이어그램 종류를 처음 쓰는 topic에서는 표기 요소를 **왼쪽에서 오른쪽으로 나란히** 보여주고, 요소마다 **이름·의미·사용법**(언제·어떻게 쓰는지, 주의점)을 표로 설명한다. 조각·가드·다중성·전이 라벨처럼 문법이 있는 표기는 쓰는 법을 예와 함께 설명한다. 표기만 나열하고 학습자가 알아서 쓰게 두지 않는다.
- 표기법은 실제 의미와 방향을 정확히 지킨다.
- **시퀀스 다이어그램·SSD**
  - 분석 단계의 호출은 **동기**가 기본이며 **응답 메시지를 그리지 않는다**. 결과를 기다리지 않는 요청·통보가 실제로 있을 때만 비동기(열린 화살촉)로 구분한다.
  - SSD 초안은 주 액터와 대상 시스템만, 정제된 SSD는 외부 시스템(지원 액터)까지 그린다. 시스템 안의 객체는 넣지 않는다.
  - 분석 시퀀스의 생명선은 **도메인 개념의 인스턴스**(`:주문`)다. 외부 시스템은 지원 액터로 참여할 수 있다. 컨트롤러·서비스·저장소 같은 설계 객체는 넣지 않는다.
- 다이어그램을 소개하는 topic의 제목은 **다이어그램 이름**으로 쓴다(예: `활동 다이어그램`, `상태 기계 다이어그램`). 예제 topic은 **대상 + 다이어그램 약칭**으로 쓴다(예: `결제 시퀀스`, `주문 상태 기계`). 제목에 다이어그램 이름이 없는 설명·예제 topic에는 `**다이어그램 — …**` 표식을 둔다.
- 여러 다이어그램을 다루는 세션은 먼저 다이어그램들의 **정의·요약과 정적 모델(또는 요구)과의 관계**를 한 곳에서 보인 뒤 다이어그램별로 설명한다.
- 모델을 만드는 다이어그램은 **초안 → 상세화**로 발전시킨다(유스케이스 다이어그램, SSD 초안 → 정제된 SSD, 도메인 모델의 클래스 다이어그램). 초안은 구조의 합의, 상세화는 규칙의 명시가 목적이다.
- 한 다이어그램에서 쓰는 표기와 다른 다이어그램에서 같은 의미를 표현하는 방법이 다르면 그 차이를 밝힌다(예: 시퀀스 다이어그램의 조각은 프레임으로, 커뮤니케이션 다이어그램은 메시지 번호의 `[조건]`·`*`로 표현한다).
- 하나의 개념을 설명할 때 관련 없는 UML 요소를 함께 넣지 않는다.
  - 예: `유스케이스란 무엇인가?` topic에는 유스케이스 타원만 보여줄 수 있다.
  - 예: `목표와 액터` topic에는 액터 표기만 보여줄 수 있다.
  - 예: `대상 시스템과 경계` topic에서는 시스템 경계 사각형과 상단 왼쪽 안쪽 시스템 명칭을 보여준다.
- 유스케이스 다이어그램 초안은 기본적으로 액터, 유스케이스, 시스템 경계, 연관만 사용한다.
- `<<include>>`, `<<extend>>`, 일반화는 실제 관계가 상세화 과정에서 확인된 뒤 사용한다.
- `<<include>>`: 기본 유스케이스 → 포함되는 유스케이스.
- `<<extend>>`: 확장 유스케이스 → 기본 유스케이스. 읽기 쉽게 기본 유스케이스를 왼쪽에 둘 수 있다.
- 일반화: 특수 요소 → 일반 요소, 실선과 속 빈 삼각형을 사용한다. 액터나 유스케이스 일반화는 일반 요소의 의미·행위를 이어받는 관계일 때 사용한다.
- 포함은 포함 지점에서 필요한 행위이며 단순 코드 공통화가 아니다. 확장은 기본 유스케이스가 독립적으로 의미를 갖는 전제에서 확장 지점·삽입 행위를 설명한다. 조건이 있으면 명시하고, UML에서 조건을 생략할 수도 있다는 점을 왜곡하지 않는다.
- 관계를 가르칠 때는 실제 표기와 그 관계를 성립시키는 사례 전제를 같은 topic에 제시한다. 전제가 불충분하면 관계를 임의로 추가하지 않는다.
- 유스케이스 사이의 일반 화살표로 호출 순서나 업무 흐름을 표현하지 않는다.
- `include`/`extend`를 코드 재사용이나 호출 관계처럼 설명하지 않는다.

## 코드 매핑 원칙

- 요구·분석의 결정은 **코드와 실행 결과에 어떻게 이어지는지** 설명할 수 있어야 한다. 코드 예시는 그 연결을 확인하는 수단이지 최종 구현 구조나 모델의 자동 변환이 아니다.
- 코드 예시는 **컴파일하고 실행해 확인한 것**만 싣는다. 여러 코드 블록을 한 파일로 합쳐 실행한다면 파일 이름을 본문에 밝힌다.
- 도메인 이름을 한글 식별자로 유지해 모델과 코드를 나란히 읽게 한다.
- 코드가 **보장하는 것과 보장하지 않는 것**을 구분해 적는다. 선언(`enum`, 컬렉션)만으로 규칙이 지켜진다고 쓰지 않는다.
- 미확정 정책을 코드의 분기·예외·테스트 기대값으로 **대신 결정하지 않는다**. 예외로 드러내더라도 정책이 아님을 밝힌다.
- 코드의 요소(필드·보조 호출·설계 객체)를 분석 모델에 **역수입하지 않는다**.
- 코드는 **자기 topic**에 두고, 코드 블록 바로 앞에 **그 코드가 표현하는 도식**(클래스·시퀀스·상태 기계·SSD 등, 필요한 부분만)을 둔다. 도식 없이 코드만 제시하지 않는다.
- 학습자가 결과를 먼저 예측한 뒤 실행해 대조하게 한다.

## 유스케이스 작성 원칙

- **시스템 경계는 소유로 판단한다.** 책임과 데이터를 다른 조직·시스템이 소유하면 외부 시스템(지원 액터)으로 둔다. 경계를 비대하게 만드는 것(대상 시스템이 재고·회계·물류까지 처리)과 기능마다 떼어 액터로 만드는 것(주문 DB, 결제 모듈)을 함께 잘못된 관행으로 다룬다.
- 경계 밖 다른 시스템의 유스케이스는 그 시스템의 경계 안에 따로 그려 범위가 아님을 분명히 한다.
- 유스케이스는 기능 목록이 아니라 **액터의 목표와 가치 있는 결과**를 중심으로 작성한다.
- 목표를 먼저 식별한 뒤 그 목표를 원하는 액터를 찾는다.
- CRUD 기능 목록을 기계적으로 유스케이스로 만들지 않는다.
- 유스케이스 명세는 필요한 항목만 사용한다. 모든 항목을 기계적으로 채우지 않는다.
- 유스케이스는 가능한 모든 상황을 빠짐없이 기록하는 문서가 아니다.
- 모델의 목적은 중요한 요구와 판단을 명확히 하는 것이지 방어 코딩 수준의 경우의 수를 전부 열거하는 것이 아니다.

### 이벤트 흐름

이벤트 흐름은 다음 원칙을 따른다.

- 목표 달성에 필요한 **본질적인 행위만** 기술한다.
- 액터의 의도와 외부에서 의미 있는 결과를 중심으로 작성한다.
- 의미를 추가하지 않는 `요청한다 → 시스템이 처리한다` 반복을 피한다. 액터의 의도와 외부에서 관찰 가능한 시스템 응답은 필요하면 기술한다. 상호작용 자체를 금지하거나 액터의 행위만 남기지 않는다.
- 같은 의미나 결과를 중복해서 쓰지 않는다.
- UI 클릭 순서로 작성하지 않는다.
- 내부 구현의 확인·계산·저장·호출 절차를 이벤트 흐름에 넣지 않는다. 결과에 영향을 주는 업무 판단과 외부 응답은 필요한 수준으로 표현하고, 상세한 규칙·정책은 따로 연결한다.
- 클래스, 객체, 메서드, 서비스 호출 같은 설계 내용을 넣지 않는다.
- 가능한 모든 오류·실패·방어 조건을 이벤트 흐름에 열거하지 않는다.
- 중요한 규칙, 제약, 실패 정책은 필요하면 **비즈니스 규칙·제약·예외 정책**으로 별도 분리한다.
- 대안·예외 이벤트 흐름은 실제 목표 달성 경로가 의미 있게 달라질 때만 사용한다. 단순 방어 규칙이나 모든 예외를 대안 흐름으로 만들지 않는다.

예:

```text
유스케이스: 주문을 취소한다
전제: 결제 완료·배송 시작 전 주문의 전체 취소 성공 경로다.
교육용 가정: 전체 취소 시 결제 금액 전액이 환불된다.

1. 고객이 주문을 취소한다.
2. 환불이 처리된다.
3. 고객은 주문 취소 결과를 확인한다.
```

다음과 같은 내부 절차는 기본 이벤트 흐름에서 제외한다.

- 시스템이 주문을 확인한다.
- 시스템이 취소 가능 여부를 판단한다.
- 시스템이 환불 서비스를 호출한다.

### 규칙·제약·예외 정책

이벤트 흐름과 다음 내용을 혼합하지 않는다.

- 비즈니스 규칙
- 제약
- 예외 처리 정책
- 품질속성

예: `배송 시작 이후에는 주문을 취소할 수 없다.`는 이벤트 흐름이 아니라 필요에 따라 비즈니스 규칙 또는 제약으로 기술한다.

## 시스템 오퍼레이션과 계약 작성 원칙

- 외부 시스템이 소유한 결과는 "했다"가 아니라 "**요청했다**"로 쓴다. 대상 시스템이 보장할 수 있는 것만 계약한다.
- 시스템 오퍼레이션은 구현 함수명이나 객체 메서드를 먼저 정하는 작업이 아니다.
- 시스템 경계를 넘는 **업무 의미의 시스템 이벤트**를 식별하고 이에 응답하는 시스템의 책임을 오퍼레이션으로 표현한다. 이벤트와 오퍼레이션을 동일한 개념으로 정의하지 않는다.
- SA 단계의 예시는 `주문 취소`, `배송지 변경`, `다음 배송 건너뛰기`처럼 한글 업무 의미로 표현한다.
- 중요하고 복잡한 시스템 오퍼레이션에 대해서만 필요 시 계약을 작성한다.
- 계약의 사후조건은 처리 절차보다 **수행 후 시스템 상태의 변화와 유지할 조건**을 기술한다.
- 관련 유스케이스, 입력의 의미, 책임 범위, 사전조건, 성공 사후조건을 함께 제시한다. 일부 상태 변화만 제시한 계약을 유스케이스 전체의 성공 보장으로 읽히게 하지 않는다.
- 사전조건 불충족·실패 시 동작은 성공 계약만으로 보장되지 않는다. 필요한 실패 요구를 별도로 정의한다.
- 시스템 수준 계약과 내부 객체 계약을 구분한다. 어느 세션에서 도메인 개념·상태·관계, 객체 책임·불변조건까지 정제하는지는 Course Design의 세션 경계로 정한다.

## 요구사항 표현 원칙

- 요구사항 수준을 설명할 때 특정 한 종류만 요구사항 전체처럼 표현하지 않는다.
- 예: `요구사항은 하나의 수준에만 존재하지 않는다`보다 실제 구조가 드러나도록 표현한다.
- 예: `요구사항은 이해관계자 요구사항에만 머물지 않는다. 사업 목적에서 해결책, 전환까지 연결해서 본다.`
- 표준별 분류 체계를 소개할 때 서로 다른 표준의 분류를 임의로 일대일 대응시키지 않는다.
- 원문이 말하는 범위를 넘어 의미를 확대하거나 새 분류를 창작하지 않는다.

## 표와 목록 작성 원칙

- 한 장표에서 짧은 항목이 많으면 긴 bullet 목록보다 의미가 유지되는 범위에서 5~6개 그룹으로 통합한다.
- 한 문장에 병렬 항목을 나열하는 편이 더 명확하면 `A, B, C, D`처럼 한 문장으로 작성한다.
- 목록은 구조를 보여줄 때 사용하고, 단순 나열에 불필요한 bullet 계층을 만들지 않는다.
- 제목이 두 개 이상의 대비 개념을 다루고 각 개념에 여러 세부 항목이 있으면, 한 줄 요약으로 뭉개지 말고 의미가 살아나는 수준으로 하위 bullet을 사용한다. 예: 본질적 어려움/우연적 어려움, 책임/경계.
- 목차에는 bullet을 사용하지 않는다.
- 번호가 의미를 갖는 절차는 numbered list를 사용한다.
- 순서가 중요하지 않은 학습 목표 등은 bullet을 사용한다.

## 검토 절차

Session Source Markdown을 만들기 전에 다음 순서로 검토한다.

1. Course Design의 세션 목표와 Anchor Message를 확인한다.
2. 전체 topic 순서와 학습 흐름을 먼저 합의한다.
3. topic별 텍스트와 필요한 visual을 같은 위치에서 검토한다.
4. 수동 `## 목차`와 본문 `## NN. 제목`의 번호·제목·순서가 1:1로 일치하고 중복·누락이 없는지 확인한다.
5. 불필요한 topic, 중복 설명, 과도한 상세를 제거한다.
   - 기본 원칙(`sw-engineering-principles.md`)에 비추어 점검한다: 요구를 이벤트 관점으로 보았는가, 관점을 섞지 않았는가, 다이어그램이 답하는 질문이 있는가, 코드·테스트와 이어지는가, 같은 지식을 두 곳에 쓰지 않았는가(DRY), 추측으로 만든 내용이 없는가(YAGNI).
6. 각 topic이 제목에 직접 답하는 설명·정의로 시작하는지 확인하고, 설명 순서가 자연스러운지 검토한다.
7. 용어, 문체, bold, 질문 표현, 인용 형식을 통일한다.
8. UML·Diagram·Chart 등 visual의 의미·전제·표기·원본 구조를 검토한다. PPT의 실제 글꼴·배치·분할·잘림·가독성은 이 단계의 완료 조건으로 삼지 않는다.
9. 표준·인용·통계·기술적 주장의 원전 또는 실제 읽은 재인용처와 확인 범위를 검증한다. 재인용 여부·표본 한계를 명시하고 어떤 근거에서도 확인하지 못한 귀속·수치는 사실로 남기지 않는다.
10. 콘텐츠가 확정된 뒤 최종 Session Source Markdown으로 변환한다.
11. 마지막으로 목차 번호, heading 번호, 강사 노트, 출처, visual 원본 구조를 다시 확인한다. 문법 검사·렌더링을 실제 수행했는지 구분해 기록한다.
12. 발견된 문제의 원인이 공통 지침의 누락·모호함이면 해당 지침을 함께 보완하고, 과정 고유 판단은 과정 문서에 반영한다. 변경한 지침과 산출물을 다시 대조한다.

검토 중에는 사용자가 요청하지 않는 한 임의의 PPT 시안이나 Production 결과를 만들지 않는다.

## Production과의 계약

정상 Production 입력은 최종 Session Source Markdown 파일 하나다. 세션명·내용·visual 원본을 이 파일에서 읽는다. 실행 명령, 기본 출력 경로, 선택 옵션과 검증 산출물의 상세 계약은 `production-guide.md`에서 관리한다. SA 지침에 CLI 옵션 목록을 중복 유지하지 않는다.

## Production 제약과의 관계

Session Authoring은 Content authority다.

- Session Source를 renderer 한계에 맞추기 위해 수정하지 않는다.
- 필요한 Markdown 문법이나 visual type이 아직 지원되지 않으면 Production을 확장한다.
- renderer의 현재 한계는 Session Source 내용의 판단 기준이 아니다.
- Production은 Session Source를 가능한 한 손실 없이 PPT로 변환해야 한다.

## Production 검증 결과의 반영

Production에서 원고의 내용·도식 구조·표기법 문제를 발견하면 별도로 제공한 Markdown 피드백 문서를 사용자와 LLM이 검토한다. 원고의 의미와 학습 목적을 기준으로 수정 여부를 결정한다. 이 피드백 문서는 Session Source나 새로운 과정별 작성 지침이 아니며, Production의 렌더링·배치·글꼴 문제를 원고 수정으로 해결하지 않는다.

- 사용자가 요청하지 않은 별도 요약 slide나 notation 종합 slide 추가
- 검토 단계에서 최종 renderer와 다른 임의의 PPT 이미지 생성
- 개념 설명보다 visual을 먼저 만들고 그 visual에 맞춰 내용을 왜곡
- 표준이나 원전에 없는 용어·판본·분류를 임의로 창작
- 이벤트 흐름에 내부 처리 단계와 가능한 모든 예외를 과도하게 삽입

## 완료 기준

Session Source가 다음을 만족하면 SA 완료로 본다.

- 세션명 헤더가 존재한다.
- Course Design의 세션 목표와 Anchor Message를 충족한다.
- 수동 `## 목차`가 있으며 본문 topic heading의 번호·제목·순서와 1:1로 일치한다(중복·누락 없음).
- 강의에 필요한 설명, 사례, 비교, 코드, visual, 실습 등이 충분히 포함되어 있다.
- 내용의 순서가 학습 흐름상 자연스럽다.
- 핵심 용어와 강조 규칙이 일관적이다.
- topic 제목은 한글 중심이며, 필요한 영문 전체 명칭과 약어는 본문 최초 등장 시에만 병기한다.
- 별도 `앵커 메시지` 블록 없이 Course Design의 Anchor Message가 학습자가 읽는 본문의 설명·사례·실습에 반영되어 있다. 강사 노트에만 있는 것으로 충족 판정하지 않는다.
- 인용문 그룹이 한글 문장/영문 원문/출처 규칙에 맞게 작성되어 있다.
- UML과 visual이 해당 개념의 의미와 표기법을 정확히 표현한다.
- 인용·통계·표준 관련 표현이 확인한 원문과 출처에 근거하며, 직접 인용·요약·교육용 가정이 구분된다.
- 사례의 전제와 계약의 보장 범위가 일관되며, 실습 결과물을 검토할 기준이 있다.
- 최종 SA의 내용 완료와 이후 시간 평가·Production 완료를 구분한다. 실제 실행하지 않은 검사를 통과했다고 기록하지 않는다.
- 불필요한 상세, 중복, 장식용 visual이 제거되어 있다.
- Production renderer의 현재 지원 여부와 관계없이 최종 원고로 사용할 수 있다.
