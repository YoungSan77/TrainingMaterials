# Production Guide

## 목적

Production은 Human이 승인한 Deck을 PowerPoint로 변환한다. 현재 CLI에서 지원하는 Deck 입력은 Session Source Markdown이다. 제작·승인·변경 경계는 `governance.md`가 정한다.

기본 흐름:

`Session Source Markdown → Production → PowerPoint`

승인 Session Source는 화면에 구현할 문구·표현과 교육 의미의 원천이다. 현재 입력 문법은 향후 필요한 표현과 검사를 설계하는 제약이 아니다.

Production은 변환기이면서 이 저장소의 **센서 집합**이다 — 자동 검사가 재는 것, 증거(`.qa.json`), 회귀 테스트가 저장소의 하네스에서 어느 자리인지는 `agentic-repository-guide.md`가 정한다.

## SA와 Production의 검증 경계

판정과 승인의 분리는 `governance.md`가 정한다. Deck 검토는 DD와 의미·출처·표기를 대조하며 최종 렌더를 기다리지 않고 진행할 수 있다. Production은 사전 자동 검사 증거와 최종 PPTX의 실제 가독성·누락·배치를 따로 기록한다. 현재 Deck 완료의 자동 검사 기준은 적용 검사 오류·경고 0개다. Renderer 결함으로 실패하면 Deck의 의미 검토와 제작 장애를 구분해 보고한다. 교육 시간은 Curriculum이 실제 수업으로 평가한다.

## 입력 / 출력

**시작 확인** — Governance의 「단계 시작 계약」에 따라 이 지침과 적용 제작 기준, 승인 Deck 버전 및 연결 자산, 허용된 제작·Renderer 변경 범위를 확인한다. 임시 검사본은 대상 입력 버전과 검사 범위를 기록한다.

최종 제작 입력은 승인 Deck 버전, 그 Deck이 가리키는 도식·코드·출처 원본 및 적용할 공통·과정별 제작 계약이다. 버전과 승인 근거를 기존 검토 기록에 연결한다. 승인되지 않은 입력으로 만든 검사본은 임시 결과로 구분한다. 현재 CLI는 Session Source Markdown 파일 하나를 단위로 받는다.

```bash
node src/cli.js ../../courses/ooad/sessions/s01.md
```

제목·출처·템플릿 같은 presentation metadata를 따로 받지 않는다. 세션명은 원고의 헤더에서 읽는다.

출력은 입력 Markdown과 같은 디렉터리에 같은 basename으로 생성한다(`s01.md` → `s01.pptx`). `--output`은 결과를 다른 경로에 두어 비교할 때만 쓰며, 원고 하나에만 쓴다.

**승인·다음 사용 조건** — 정식 출력은 PPTX와 QA·렌더 증거다. 승인 입력·출력의 버전과 해시, 판정·실패 위치, 미검증 항목을 기존 제작 기록에 남긴다. 필수 제작 검증을 충족하고 Human이 해당 PPTX를 수락하면 배포한다. 변환 결함은 Production에서 고치고, 승인 Deck의 표현이나 교육 의미 결함은 해당 단계로 되돌린다.

원고를 **여러 개 주면 모두 만든다**(한 과정을 다시 렌더링할 때). 하나라도 실패하면 그 원고를 밝히고 종료 코드 1로 끝낸다.

```bash
node src/cli.js ../../courses/ai-native/sessions/s0*.md
```

## 묶음 덱

과정 전체를 **한 .pptx로 검토**할 때는 `--bundle <출력.pptx>`에 원고를 **보일 순서대로** 준다. 세션 덱을 따로 만드는 일을 대신하지 않는다 — 검토용 묶음이며, 각 세션의 `.pptx`가 여전히 산출물이다.

```bash
node engine/production/src/cli.js --bundle courses/ai-native/out/ai-native-전체.pptx courses/ai-native/sessions/s01.md … courses/ai-native/sessions/s12.md courses/ai-native/sessions/references.md
```

- 각 세션은 **자기 덱과 같게** 구성된다 — 세션마다 자기 목차가 앞에 오고, 표지와 과정 목차는 첫 세션(`01.`)에서 한 번만 나온다. 장수는 따로 만든 덱의 합과 같다.
- 슬라이드의 우측 상단 세션명과 별첨 표시(`별첨: <세션명>`)는 **그 장이 구성된 세션**의 것이다(`builder.js`의 `page()`가 장마다 세션을 기록하고 `inspect.js`가 그 값과 견준다).
- 문서 제목(docProps)은 과정명이다. 참고 자료 별첨(`references.md`)은 목차가 없으므로 마지막에 그대로 붙는다.
- **검사 범위** — 원고마다의 구조·참조·코드 검사는 그 원고를 단독으로 렌더링할 때 하므로 묶음에서 되풀이하지 않는다. 묶음은 다시 읽어 manifest와 맞는지(`inspect`)와 배치 경고만 확인하고 `.qa.json`을 함께 쓴다.
- 출력은 `courses/<course>/out/`에 둔다(git 제외). 저장소에 커밋하는 덱은 세션별 `.pptx`다.

## 템플릿

`engine/production/template/`은 모든 PPT의 뼈대다 — 슬라이드 마스터·레이아웃·테마와 페이지 종류마다 하나의 원형 슬라이드(목차·본문·트리·코드·표, `src/template.js`의 `ORIGIN`). 압축을 푼 OOXML 파일로 두어 변경이 diff로 보인다.

- 템플릿은 renderer의 일부다. 사람이 승인하는 별도 자산이 아니며, 지침을 구현하는 데 필요하면 renderer 코드·테스트와 함께 고친다.
- 원형 슬라이드에는 내용을 남기지 않는다. 위치·크기·글꼴은 지침과 `builder.js`가 정하며, 원형은 도형의 틀만 준다(`src/test/template.test.js`가 검사한다).

## Session 명

Deck은 승인 Curriculum의 세션 번호와 이름을 `session-authoring-guide.md`가 정의한 헤더에 표시한다.

우측 상단에는 부제를 포함한 전체 세션명을 한 줄로 표시한다. 기본 14pt에서 0.5pt 단위로 맞추며 최소 9pt다. 보조 세션명 객체는 비운다.

요약 뒤의 별첨(`## 별첨. …`, 실습 답) 슬라이드는 우측 상단에 `별첨: ` + 전체 세션명을 쓴다(`builder.js`의 `appendixSessionName`). 별첨 그룹은 목차와 대조하지 않는다.

목차 슬라이드 제목에는 세션명의 ` — ` 앞부분만 쓴다. 예: `03. 정적 모델 — 도메인 개념과 관계` → 목차 제목 `03. 정적 모델 목차`. 부제가 없는 세션명은 그대로 쓴다. 승인 Curriculum과 Deck의 세션명은 줄이지 않는다.

Session 명은 slide title, TOC item, body content가 아니다.

## 표지·과정 목차·과정 목표

**과정의 첫 세션**(`01.`) 덱만 3장으로 시작한다 — 1장 표지(과정명), 2장 과정 목차(세션 전체), 3장 과정 목표, 4장이 그 세션의 목차다. 뒤 세션의 덱은 자기 세션 목차가 첫 장이다.

- **표지** — 과정명을 본문 영역 가운데에 40pt 굵게 가운데 맞춤으로 한 줄로 둔다(`builder.js`의 `renderCover`). 제목 자리는 비운다.
- **과정 목표** — 제목은 `<과정명> 목표`이고 일반 18pt 문단·목록으로 표시한다. 승인 Course Design의 목표 표현을 보존한다. 지면 초과는 제작 문제로 기록하고 성과를 임의로 줄이지 않는다.
- **과정 목차** — 제목은 `<과정명> 목차`이고, 항목은 과정의 세션 `NN. 세션명`이다. 세션 목차와 같은 전체 폭 단일 열 16pt 배치를 쓴다(`renderCourseToc`).
- 현재 CLI의 입력 위치와 승인 정본의 차이는 「정본 이관과 현재 구현」을 따른다. 과정명에서 괄호 안의 폴더 표기는 빼고 과정명·목표·목차를 세션 원고에 중복 기입하지 않는다.
- 3장 모두 목차 슬라이드와 같이 우측 상단 세션명을 쓰지 않는다.
- 과정 설계가 없는 입력(과정 밖의 참조 덱, 테스트 fixture)과 목차가 없는 별첨(`references.md`)에는 만들지 않는다. 설계에 「과정 목표 슬라이드」가 없으면 그 장만 만들지 않는다.

## 목차 생성 및 검증

Session Source의 `## 목차`는 `guides/session-authoring-guide.md`에서 정의한 수동 목차다. Production은 **이 목차의 항목과 순서를 그대로 사용하여 PPT 목차 슬라이드를 생성**한다. 본문 heading에서 목차를 새로 작성하거나 목차 제목을 임의로 고치지 않는다.

- `## 목차`와 본문 `## NN. 제목`의 번호·제목·순서를 1:1로 비교한다. 첫 항목 `01. 세션 목표`, 연속 번호, 중복·누락 여부도 검증한다.
- 일치하지 않으면 해당 항목과 불일치 내용을 보고하고, 원고를 묵시적으로 수정하거나 불일치를 감춘 PPT를 정상 완료로 판정하지 않는다. 사용자와 LLM이 Session Authoring에서 원고를 수정한 뒤 다시 검증한다.
- 목차는 번호 있는 topic(그룹)만 담는다. 번호 없는 서브 항목은 목차·대조 대상이 아니며, 본문이 없는 그룹은 슬라이드를 만들지 않는다(`parse.js`, `builder.js`).
- 목차 항목은 **16pt**, 항목 앞뒤 간격 3pt이고, 본문 폭 전체를 사용하는 단일 열로 배치한다. 실제 줄바꿈과 문단 높이를 계산해 넘치면 단일 열 목차를 다음 장에서 이어 간다.
- `## 목차`는 독립적인 내용 topic이 아니다. 목차가 한 슬라이드에 읽기 어렵게 들어가면 목차 슬라이드만 자연스럽게 분할하며 항목을 삭제하거나 축약하지 않는다.
- Topic 번호는 슬라이드 페이지 번호와 동일하지 않다. 본문과 continuation 슬라이드의 분할은 「Visual layout 및 가독성」을 따른다.

## Visual authority

Production의 공통 시각·배치·가독성 기준은 이 지침에서 정한다. 사용자가 수동으로 조정해 지정한 참조 PPTX는 해당 세션의 배치와 교정 위치를 확인하는 자료다. 내용은 최신 Session Source를 따른다. 참조 PPTX가 일부 장만 담으면 주제·소제목·본문으로 대응시켜 수정 장을 찾고, 전체 덱은 원고에 따라 생성한다. `== … ==`는 검토 메모로 읽고 출력에서 제외한다.

**작업 지시는 원고 경로와 조정본 경로만 지정한다.** 작업자는 이 지침의 해당 절을 적용해 생성·검증하고, 조정본의 각 메모에 대해 출력 장·반영 여부·근거를 기록한다. 재현된 Renderer 결함은 기존 구현에서 수정한다. 원고와 조정본 사이에 내용 차이가 있으면 해당 구절과 출력 영향을 기록해 작성자에게 전달한다.

## 기본 원칙

- Session Source의 내용과 순서를 보존한다.
- renderer 한계 때문에 원고를 삭제·왜곡·치환하지 않는다.
- 지원되지 않는 Markdown/visual type이 필요하면 Production을 확장한다.
- 내용이 한 장에 들어가지 않으면 자연스럽게 continuation slide로 분할한다.
- 짧은 마지막 문장이나 출처 하나만 별도 continuation으로 남지 않도록 실제 사용 가능 영역을 기준으로 pagination한다.
- clipping, overflow, content loss를 허용하지 않는다.
- 규칙이 서로 부딪히면 **의미 보존·잘림 없음 → 가독성(최소 글자 크기) → 자연스러운 분할 → 슬라이드 수** 순으로 우선한다.
- 강사 노트는 presentation body와 분리한다.
- Mermaid, PlantUML, Chart, Image, 본문에 내장한 SVG 등 visual source는 최종적으로 실제 visual로 렌더한다. 원본 종류가 미지원이면 Production을 확장하며 ASCII나 소스 코드 출력으로 완료 처리하지 않는다.
- 사례의 가정·적용 범위·예외, 화살표의 의미, 계약의 사전·사후조건을 보존한다. 내용 분할 때문에 전제와 사례의 연결이 사라지지 않도록 한다.
- 인용문의 요약·발췌 여부, 시점·범위, 저자·문헌·직접 링크를 보존한다. 실제 확인 범위를 넘어 권위나 확실성을 강화하지 않는다.


## 블록 해석과 출력 보존

인용문·강사 노트·visual 표식의 경계는 `session-authoring-guide.md`의 「의미 표식과 블록 경계」를 따른다. fenced block 안의 heading·수평선은 구조 구분자로 해석하지 않는다. 강사 노트는 해당 topic의 발표자 노트에 보존하며 continuation에서도 필요한 노트의 연결을 유지한다. 본문 소제목이나 일반 `>` 블록을 인용문 또는 새 topic으로 추정하지 않는다.

독립된 줄의 `**인용문**` 표식은 뒤에 빈 줄이 없어도 다음 문단과 합쳐 출력하지 않는다. Markdown fence는 0~3칸 들여쓴 경우도 코드·도식으로 읽고, fence의 들여쓰기만 제거해 내부 상대 들여쓰기를 보존한다. fence 안의 제목·수평선은 문서 구조로 해석하지 않는다. 들여쓴 Java 발췌도 같은 규칙으로 원본을 대조한다.

출처 링크는 문헌명을 표시하고 클릭 가능한 hyperlink로 보존한다. 원시 URL 전체를 강제로 길게 노출하지 않으며 링크를 제거하지 않는다. 문헌명·재인용 표기·시점·표본 한계는 본문과 연결해 보존한다.

### 표의 칸 맞춤

표 칸의 글은 **세로 가운데**에 둔다. 값은 원형 슬라이드가 아니라 `builder.js`의 `fillTable`이 칸마다 직접 정하며(`anchor="ctr"`), 위아래 여백을 같은 값으로 맞춘다 — 위 여백만 있으면 가운데 맞춤이어도 글이 아래로 치우쳐 보인다.

모든 머리글·본문 셀의 사방 안쪽 여백은 **0.15cm**다. OOXML의 `marL`, `marR`, `marT`, `marB`는 각각 **54000EMU**다. 승인된 과정별 예외의 적용 조건과 근거는 「과정별 제작 기준」을 따른다.

### 표의 행 높이와 열 너비

- 일반 강의·일반 문서·저자 답안의 표는 **맑은 고딕 10pt**, **0.8cm 최소 행 높이**를 쓴다(머리글 포함). 원고는 한 줄을 우선하되 줄바꿈한 행은 표시 내용에 맞춰 높이를 계산한다(`session-authoring-guide.md`의 「6. 표와 목록」).
- **실제 응답·그 응답의 판단표·실제 응답 표식이 있는 별첨 실습 답**의 표는 콘텐츠 역할에 따라 **맑은 고딕 8pt**와 실측 가변 행 높이를 적용한다. 머리글·본문에 같은 크기를 적용하며 일반 표의 고정 최소 높이를 강제하지 않는다. 과정명·세션 번호만으로 역할을 판정하지 않는다(`contentRoles.js`).
- 머리글과 모든 본문 행에서 각 열의 가장 긴 표시 줄을 실제 글꼴·크기·굵기로 재고 좌우 셀 여백을 더해 자연 열 너비를 정한다. 원고의 명시적 줄바꿈이 있으면 각 표시 줄의 최대 폭을 쓴다. 본문 또는 단의 가용 폭에 들어가면 필요한 폭만 사용하며 빈 폭을 균등하게 채우지 않는다.
- 자연 폭의 합이 가용 폭을 넘는 단내 표는 전체 셀 텍스트로 측정한 각 열의 자연 폭에 비례해 배분한다. 배분 결과가 머리글의 단어·본문의 한글 어절·짧은 값·숫자·식별자의 최소 표시 폭보다 작은 열만 최소 폭으로 고정하고, 남은 폭을 나머지 열의 자연 폭에 비례해 다시 배분한다. 최소 폭의 합 자체가 넘으면 문제의 표·열·필요 폭을 보고하며 글자 크기를 임의로 줄이지 않는다. 일반 표의 기존 비례 축소·가장 넓은 열부터 제한·가장 넓은 열만 축소 중 **넘치는 행이 가장 적은** 배분을 고르는 판단에도 실측값을 사용한다.
- 너비를 바꾸면 그 너비로 줄바꿈을 다시 재고, 각 행에서 가장 높은 셀의 텍스트 높이·문단 간격·상하 여백으로 행 높이를 계산한다. 한글은 어절 단위 줄바꿈을 우선한다. 8pt 표에 일반 10pt 추정값을 쓰지 않는다. 다음 내용의 위치와 행 분할에도 같은 높이를 사용한다(`tableRowMetrics.js`).
- PowerPoint 표시 경계에서 재줄바꿈되는 문제는 실측으로 보정한다. 검증한 내용 기반 8pt·일반 10pt 폭 계측은 글리프별 0.25pt 올림과 최종 0.5pt 여유를 사용한다. 단내 표의 줄바꿈·행 높이에도 같은 표시 폭 모델을 적용한다. 이는 셀 여백이나 글꼴 크기를 바꾸는 규칙이 아니다.
- 한 줄을 넘는 셀은 **경고**로 보고한다(`engine/production/src/structure.js`).
  - 콘텐츠 역할 또는 과정별 승인 기준으로 지정된 8pt 실측 표이며 생성 manifest의 해당 topic·표에 모든 행이 대응할 때는 일반 10pt 한 줄 경고를 적용하지 않는다. 누락·글꼴·셀 여백·표 폭 검사와 최종 렌더 검증은 유지한다. 해당 조건이 없거나 일부 행이 대응하지 않으면 기존 경고를 유지한다.
- **칸의 글은 세로 가운데에 둔다.** 모든 칸(제목 행 포함)에 `anchor="ctr"`을 주고 위아래 여백(`marT`·`marB`)을 **같은 값**으로 맞춘다. 원형 슬라이드의 값에 기대지 않고 `fillTable`이 칸마다 직접 정한다 — 원형은 위 여백만 있어 가운데 맞춤이어도 글이 아래로 치우쳐 보였고, 원형에 `tcPr`이 없는 칸은 맞춤 없이 빠졌다.
- **표 뒤의 글은 들어가는 만큼 그 장을 채운다.** 표 아래에 이어지는 bullet이 다 들어가지 않으면 **들어가는 앞부분만** 표 아래에 쌓고 나머지를 다음 장으로 보낸다. 통째로 넘기면 표 아래가 200pt 가까이 비는 장이 생긴다. 하위 bullet은 제 상위 bullet과 같은 장에 두고, 한 bullet도 들어가지 않으면 통째로 넘긴다.
- **표 틀(graphicFrame)의 높이는 행 높이의 합과 같다.** 원형의 높이를 그대로 두면 `cy`를 믿는 뷰어가 남는 높이를 행에 나눠 주어 표가 늘어나고, 글이 제 행의 가운데에서 벗어난다. PowerPoint는 열 때 다시 계산하므로 데스크톱에서만 보면 드러나지 않는다.
- 표 문단에도 `latinLnBrk="0"`을 직접 출력한다. 표는 슬라이드 마스터의 본문 스타일을 상속한다고 가정하지 않는다. 영문 식별자의 실제 글꼴·굵기·셀 여백을 포함한 최소 폭이 열 너비보다 크면 오류로 보고한다. 발췌 실습 답의 단내 표는 출력에만 식별자 내부 밑줄 뒤의 줄바꿈 기회를 넣을 수 있다. 자연 폭은 전체 식별자로 재고 최소 폭과 행 높이는 줄바꿈 기회를 반영해 재며, 검사는 출력과 원문을 대조한다. 원문에 공백·개행을 삽입하거나 글자 크기를 줄여 통과시키지 않는다.
- 표의 최종 열 너비·역할별 글꼴·문단 설정으로 계산한 행 높이를 페이지 분할과 실제 출력에 공통으로 사용한다. 표 다음 객체는 출력된 행 높이 합과 블록 간격에서 시작한다. 이후 폭·높이를 바꾸는 단계도 후속 객체 좌표를 함께 갱신해야 한다. 표와 같은 가로 영역의 본문·계산 예문이 표 틀을 침범하면 오류다(`tableLayoutChecks.js`). QA는 최종 PPTX를 다시 읽어 문단 정책·식별자 최소 폭·표/후속 객체 경계를 검사하고 `table_layout`에 좌표와 간격을 기록한다. 실제 뷰어의 재줄바꿈·자동 행 확장은 PDF 셀 대조와 전 장 시각 검토로 별도 확인한다.
- 이 세 가지는 fixture의 **모든 칸**을 보는 테스트가 지킨다(「Regression」). 글이 실제로 가운데에 놓였는지는 **이미지가 아니라 내보낸 PDF의 좌표로 잰다** — 50dpi 검토 이미지에서는 가운데에 있는 글도 아래로 치우쳐 보인다. `tools/review-pdf.sh`가 PNG와 함께 `<sNN>.pdf`를 남기고, 한 줄로 전수 확인한다.

```bash
python3 -I tools/measure-table-rows.py courses/ai-native/sessions/s04.pptx out/review/s04/s04.pdf
```

렌더 결과의 셀별 원문·경계와 영문 식별자 중간 줄바꿈은 `python3 tools/check-rendered-tables.py <PPTX> <PDF> [검증.json]`으로 전수 검사한다. PowerPoint에서 재계산된 표가 후속 설명을 덮으면 셀 텍스트 혼입·누락 또는 경계 위반으로 실패한다. PDF 원문 대응이 안 되는 경우 시각 판정만으로 통과시키지 않고 해당 셀을 조사한다. 자동 좌표 대조도 전 장 시각 검토를 대신하지 않는다.

### 긴 표의 분할

- 표가 사용 가능 영역을 초과하면 행의 순서를 보존해 **행 단위**로 continuation 슬라이드에 나눈다. 각 분할 표의 상단에 **헤더(제목 행)를 반복**한다. 다중 헤더라면 의미를 이해하는 데 필요한 헤더 전체를 반복한다.
- 같은 표의 열 너비는 분할 전 모든 행으로 한 번 계산하고 모든 분할 표가 공유한다. 새 너비로 줄바꿈·행 높이·분할을 다시 계산한다. 표의 제목·단위·교육용 가정·표본 한계가 각 분할 부분에 적용됨을 알 수 있게 연결한다. 열이나 행을 삭제·요약하거나 값을 변경하지 않는다.
- 단일 행도 한 장에 들어가지 않으면 글꼴을 임의 축소하거나 내용을 잘라내지 않는다. 가용 배치를 먼저 조정하고, 셀 내용의 의미 단위 continuation이 필요하면 행 식별자·열 헤더·이어짐을 반복해 원래 행과 대응시킨다. 의미 보존이 불가능하면 구체적인 원고 검토 항목으로 보고한다.

### 접근성 텍스트

- SVG의 `aria-label`, 유효한 `aria-labelledby` 참조, `<title>`·`<desc>`, Markdown 이미지의 대체 텍스트 등 원고의 접근성 정보를 최종 PPT 객체의 **Alt Text**에 보존한다.
- 같은 visual에 이름과 상세 설명이 함께 있으면 중복을 제거하되 서로 다른 정보를 잃지 않도록 결합한다. 상충하면 임의 선택하지 않고 보고한다. SVG를 raster로 바꿔도 대체 텍스트는 이미지 객체에 전달한다.
- 여러 객체로 분해하면 의미 있는 그룹 또는 대표 객체에 전체 설명을 연결하고, 중복 낭독을 피하도록 읽기 순서를 검토한다. 대체 텍스트가 없다고 임의 설명을 지어내거나 장식용으로 단정하지 않는다.
- 와이어프레임처럼 화면을 그린 SVG의 `aria-label`도 이 규칙의 대상이다. PPT 객체에 값이 실제 보존됐는지 검사한다. 속성 복사만으로 스크린리더 사용성 전체를 검증했다고 판정하지 않는다.

## Typography 계약

Production은 Session Source의 의미 표식을 시각 표현으로 변환한다.

### 인용문

Session Source에서 인용문 그룹으로 명시된 직접 인용·번역·출처를 가진 요약은 다음 규칙을 따른다. 요약을 따옴표로 바꾸거나 영어 원문을 생성하지 않는다.

- 한글 번역 또는 한글 인용문: **18pt**
- 영어 원문: **10pt**
- 출처: **10pt**
- 영어 원문이 없는 인용문도 출처는 **10pt**다.
- 직접 인용의 한글 번역과 영어 원문은 각각 `“ ”` 한 쌍으로 감싼다. 출처는 따옴표 밖에 두고 세 부분은 같은 문단에서 OOXML run 수준으로 크기를 구분한다. 인용 문단에는 글머리표를 달지 않는다. 원고의 구분용 따옴표를 표시용 한 쌍으로 처리하며 원문 안의 따옴표는 보존한다. 요약형 한글의 표시 예외는 과정별 제작 기준을 따른다.
- 한글 내부의 쉼표는 글꼴 크기를 바꾸는 구분자가 아니다. 따옴표로 감싼 영어 원문과 마지막 출처 레이블을 기준으로 영역을 나누며, 쉼표 뒤에 이어지는 한글도 **18pt**로 유지한다. 영어 원문이 없으면 출처 레이블 앞까지 한글 영역이다. 한글의 쉼표를 삭제하거나 다른 기호로 바꾸어 renderer 결함을 우회하지 않는다. bullet 인용의 한글은 같은 방식으로 구분하되 해당 단계의 본문 크기를 따른다.
- 인용문 구분자나 authoring marker는 슬라이드 본문에 출력하지 않는다.
- **bullet 인용** — 표식 없이 bullet 한 줄이 `"한글", "English original", [저자 연도]` 형식이면(`session-authoring-guide.md`의 「5. 인용과 출처」) 인용으로 렌더한다. 한글은 그 bullet 단계의 본문 크기, 영어 원문·레이블은 **10pt**다. 영어 원문이나 레이블이 없으면 일반 bullet이다(`paragraphs.js`의 `bulletCitation`).
- 한글·영어 원문 안의 `\"`는 그 인용 부분의 일부로 나누고 `"`로 출력한다. 백슬래시를 그대로 출력하지 않는다(맑은 고딕에서 `₩`로 보인다, `paragraphs.js`의 `citationParts`).

### 한 장의 메시지

- topic의 첫 본문 문단(또는 topic을 여는 인용)만 글머리표 없는 **lead**로 그리고, 나머지 문단은 보조 bullet로 그린다.
- **문장 전체가 따옴표 안에 있는 한 줄**(`"장바구니에 담은 상품을 결제하면 …"`)은 예외다. 고객에게 받은 말이므로 lead가 아니어도 **글머리표 없이** 본문 크기로 그린다 — 글머리표가 붙으면 저자의 주장으로 읽힌다(`builder.js`의 `SPOKEN_LINE`). 따옴표 밖에 다른 말이 붙은 줄은 보통 본문이다.
- `###` 소제목은 글머리표 없이 굵게 표시한다. 그룹 대표명은 들여쓰기 없이 두고, 기존 소제목의 들여쓰기와 하위 문단의 수준은 해당 서식에 따른다. 소제목 및 첫 설명은 다음 표·도식과 함께 배치한다.
- **이어지는 장**: topic이 여러 장이면 둘째 장부터는 lead를 반복하지 않고, 그 장의 내용이 lead 자리(본문 맨 위)에서 바로 시작한다. 공간을 본문·도식·코드에 쓴다.

### 표·도식 제목

`**표 — 제목**`은 표 바로 위, `**도식 — … — 제목**`의 제목은 도식 바로 위에 **14pt 굵게 가운데** 그린다. 도식은 제목 높이만큼 내려간다. 바로 아래에 표나 코드가 있으면 그것도 함께 내리고, 쪽 번호에 닿아 내릴 수 없을 때는 — 도식이 좁으면 제목을 도식 왼쪽 위에 오른쪽 맞춤으로 두고, 넓으면 자리 안에서 가운데를 기준으로 줄인다. 본문 오른쪽에 놓인 도식(옆 배치)의 제목은 도식의 단 위에만 둔다 — 왼쪽 본문 위로 걸치지 않는다. 쪽 번호에 닿을 때도 줄인다, 쪽 번호에 닿을 때도 줄인다(`builder.js`의 `captionPicture`). 표식은 출력하지 않는다.

**표 제목은 앞 블록이 아니라 뒤의 표에 붙는다.** 코드 블록 다음에 표가 오면 그 사이의 `**표 — 제목**`은 코드의 뒷글이 아니라 표의 제목이다 — 코드가 뒤따르는 글을 모아 갈 때 이 줄에서 멈춘다(`builder.js`의 코드 trail 수집, `code-table-caption.test.js`). 멈추지 않으면 본문에 "표 — 제목"이 그대로 찍히고 표는 제목을 잃는다.

### 문서 형식

`**문서 형식**` 표식이 있는 topic은 실습 답과 같이 한 장에 **좌우 두 단, 14/12/11pt**로 그린다. **왼쪽 단을 끝까지 채우고 남은 내용만 오른쪽 단에 이어 쓴다** — 모두 왼쪽에 들어가면 오른쪽은 비워 둔다. 왼쪽 단의 여유는 `leftFit`이며 답과 문서는 1.04배다(「실습 슬라이드」). 글머리표 없는 첫 문단은 두 단 위 전체 폭에 두고, 원고의 `**페이지 분할**`은 무시한다. 한 장에 들어가지 않으면 18pt 이어지는 장으로 남는다(`builder.js`의 `answerPage`).

`**문서 형식 — 10pt**`는 같은 두 단 배치에서 문서 본문의 제목·목록·설명·괄호를 모두 10pt로 표시한다. 문단 앞뒤 간격은 각각 3pt이며, 소제목 0.2in·본문 0.45in·하위 질문 0.8in으로 들여쓴다. 왼쪽 단에 들어갈 내용을 먼저 채우고 남은 내용만 오른쪽 단에 이어 쓴다(10pt의 `fit`·`leftFit`은 둘 다 0.9배다). 모두 왼쪽에 들어가면 오른쪽은 비워 둔다. 슬라이드 제목은 20pt Bold이며 일반 제목과 같은 폭·겹침 기준을 적용한다. 본문이 한 장을 넘으면 10pt·전후 3pt·왼쪽 우선 흐름을 유지한 이어지는 장으로 나누며, 항목을 생략하거나 개수를 제한하지 않는다. **앞 장을 끝까지 채운 뒤 다음 장으로 넘기고, 마지막 장은 남은 내용만 담는다** — 마지막 장을 고르게 만들려고 앞 장의 끝 항목을 옮기지 않는다. 마지막 장이 한 장의 용량을 넘으면서 앞 장에 자리가 있으면 그 넘치는 만큼만 앞 장의 끝 항목을 마지막 장으로 옮긴다. **둘째 장이 한 장의 30%보다 적게 남을 때는 두 단 상자의 높이를 그대로 쓰면(fit 1.0) 한 장에 들어가는지 먼저 확인하고, 들어가면 한 장으로 합친다** — 96%짜리 장과 21%짜리 장보다 꽉 찬 한 장이 낫다(`documentPages`). `###` 소제목은 슬라이드의 마지막 줄에 남기지 않고 뒤 내용과 함께 다음 장으로 내린다 — 뒤 내용이 코드면 소제목을 코드 장의 lead로 옮긴다(`builder.js`의 `flush`·`documentPages`·`rebalanceTail`·`sourceCode`, 2026-10-25).

`**문서 형식 — 10pt**`는 표·코드가 섞인 문서에서도 앞뒤 본문에 적용한다. 표가 있다는 이유로 본문을 18pt로 되돌리지 않는다. 코드 원본과 순서는 보존하며 코드 자체의 글꼴 정책은 「소스 코드」를 따른다. 이어 붙일 본문의 적합성은 인쇄되는 줄 높이와 바깥 문단 간격으로 판단해, pagination의 여유분만으로 짧은 설명이 별도 장이 되지 않게 한다. 혼합 문서는 앞 장을 먼저 채우고 나머지만 다음 장으로 넘긴다. 표 전체가 남은 영역에 들어가지 않아도 헤더와 데이터 행 하나 이상이 들어가면 그 행까지 현재 장에 넣고, 나머지는 다음 장에서 헤더를 반복해 이어 간다. 헤더만 앞 장에 남기지 않으며 행·문장·코드의 순서를 바꾸지 않는다.

짧은 10pt 혼합 문서(본문·코드·표)는 전체 블록의 실제 표시 높이를 먼저 합산한다. **블록 사이 간격은 모두 8pt**로 맞추고, 문단 앞뒤 3pt·본문과 코드 10pt를 유지한다. 표의 크기와 행 높이는 「표의 행 높이와 열 너비」의 콘텐츠 역할을 따른다. 본문 fit의 안전 여유와 코드 planner의 마지막 빈 줄을 다음 블록의 시작 위치에 다시 더하지 않는다. 전체가 가용 영역에 들어가면 한 장에 배치하고, 넘으면 기존의 순차 채움과 표 행 분할을 적용한다. 원문과 블록 순서는 바꾸지 않는다.

`**문서 형식 — 10pt**` topic에 도식이 있으면 일반 도식처럼 본문과 상하로 배치하되 본문 제목·목록·설명은 모두 10pt를 유지한다. 도식 뒤의 짧은 설명은 한 단과 두 단을 비교하여 7pt 이상으로 도식이 가장 크게 보이는 배치를 택한다. 도식 원본과 설명의 문장·순서는 보존한다. 도식 자체는 일반 도식의 10pt 목표와 7pt 하한을 따른다. 텍스트만 있는 문서의 두 단 배치를 도식에 강제하지 않는다.

번호가 붙은 문서 항목은 둘째 줄부터 번호 뒤 본문에 맞춘다. 실습 프롬프트의 ①~⑤는 PowerPoint 원문자 자동 번호로 표시한다. 기존 한 단 서식의 기준은 본문 위치 981075EMU·내어쓰기 -268288EMU다. 적용하는 단과 글꼴의 실제 번호 폭을 확인하고 내어쓰기와 탭 위치를 보정해 첫 줄과 이어지는 줄의 본문 시작 X좌표를 맞춘다. 점검 번호는 자동 번호 `arabicPeriod`와 본문 위치 1028700EMU·내어쓰기 -304800EMU를 쓴다. 원고의 번호 문자열은 자동 번호로 대체한다.

실습의 `**프롬프트 — 요청사항 포함**`은 서비스 개요·투입물을 프롬프트에 통합한 형식으로 인정한다.

별첨 topic의 `**실제 LLM 응답**`은 실제 실행 결과의 원문 보존 표식이다. parser가 metadata로 소비하며 슬라이드에 출력하지 않는다. 표식만으로 검사를 면제하지 않으며 「자동 검사 — 참조와 경고」의 실행 전문 대조를 통과한 범위에서만 저자 문장과 출처를 구분한다. 그 범위는 원문에 없는 강조·숫자 표기를 추가하지 않도록 해당 저작 검사를 구분하고, 범위 밖 저자 문장과 모든 구조·누락·배치 검사는 유지한다. 실제 응답 문서의 본문·소제목·설명·캡션은 **10pt**, 표는 「표의 행 높이와 열 너비」의 실제 응답 역할을 따른다. 슬라이드 제목과 도식 내부 글자는 각각의 공통 기준을 유지한다. 원문 제목에 `(안)` 같은 접미사를 추가하지 않는다. 본문 문장·순서·원래 강조는 보존하고 제목 단계와 배치만 변환한다. 학습용 최종 MD와 교재 슬라이드는 별개다. 원고가 전체 또는 발췌 범위를 결정하고 Production은 그 범위의 문장·도식 원본을 보존한다. 발췌 여부·범위와 원본 경로는 강사 노트에 남긴다. 지면 때문에 업무 산출물에 PPT 조건을 넣어 재생성하지 않는다(`session-authoring-guide.md`).

단내 표 배치를 지정한 실제 응답의 문서형 별첨은 **왼쪽 단을 위에서부터 채운 뒤 오른쪽 단으로 이어 간다**. 표는 한 단의 실제 가용 폭 안에 두고 글자 크기를 임의로 줄이지 않는다. 소제목과 첫 자료, 마지막 분할 표와 직후 설명은 빈 단에 들어가면 함께 배치한다. 높이가 모자라면 묶음을 다음 단으로 옮기고, 빈 단에도 안 들어가는 표만 「긴 표의 분할」을 따른다. 소제목이나 생략 표시만 남기지 않는다. 도식은 원본을 유지하며 일반 가독성 하한을 지킬 수 없으면 별도 장을 사용한다. 적용을 선택한 과정·세션과 특정 장의 통합 배치 예외는 과정별 제작 기준에 둔다.

실제 응답의 발췌는 원문의 첫 제목·첫 절부터 시작하고 그룹명·항목 번호·순서·강조를 보존한다. 반복 목록은 원고가 선택한 원문 앞 2항목을 유지하고 빠진 자리에 **`.....` 한 줄**을 그대로 출력한다. 서로 다른 수용 사례와 다음 실습의 필수 조건은 원고가 정한 범위를 보존한다. Production이 새 발췌·요약·생략 표시를 만들지 않는다. 발췌 범위와 전문 경로는 강사 노트에서 확인한다.

### 별첨 — 참고 자료

`**참고 자료 목록**` 표식이 있는 topic(과정의 별첨 `references.md`, `session-authoring-guide.md`의 「별첨 — 참고 자료」)은 항목을 **좌우 두 단, 7pt**, 문단 앞뒤 간격 **1pt**로 그린다. 항목의 첫 줄은 단의 왼쪽 끝에서 시작하고, 한 줄을 넘으면 둘째 줄부터 번호 `N. ` 뒤에 맞춰 들여쓴다. **왼쪽 단을 제 아래까지 채운 뒤 오른쪽 단으로 넘기고**, 장도 채울 수 있는 만큼 채운 뒤 `(n/m)` 이어지는 장으로 나눈다 — 항목을 장마다 고르게 나누지 않는다(그렇게 하면 모든 장의 두 단이 아래를 비운 채 끝난다). 왼쪽 단을 채우지 못하는 짧은 목록은 한 단이다(`builder.js`의 `referencePages`). 목차가 없는 원고가 모두 참고 자료 topic이면 목차 슬라이드를 만들지 않는다.

### 주석

`**주석**` 표식 다음 문단은 topic의 모든 슬라이드에서 쪽 번호 바로 위, 본문 폭의 텍스트 상자에 **8pt**로 아래 맞춤해 표시한다. 본문 흐름·분할에는 포함하지 않으며 표식은 출력하지 않는다(`builder.js`의 `footnote`). 주석 문단은 굵게 표시 검사에서 제외한다.
실제 응답의 생략 표시를 설명하는 주석은 발췌 마지막 장에만 한 번 표시한다. 주석이 표시되는 장은 주석 위쪽까지를 본문·표·도식·코드의 사용 가능 영역으로 삼는다. 주석을 나중에 덧씌워 본문이나 visual을 가리지 않는다.

Anchor Message의 승인 원천은 DD다. Deck은 학습자 본문에 그 의미를 구현한다. Production은 별도 표식을 강제하거나 메시지를 생성하지 않는다.

### 줄바꿈

영어 단어·코드 식별자는 줄 끝에서 **단어 중간에 끊지 않는다**. 템플릿의 모든 문단 스타일은 `latinLnBrk="0"`이다(`template/`, 테스트가 확인한다). 한글은 PowerPoint의 기본 한글 줄바꿈을 따른다.

### 괄호

본문, 목차, 슬라이드 제목에 등장하는 모든 괄호 `(...)`는 한글·영어 내용과 관계없이 기준 폰트 크기에서 **-4pt**로 렌더링한다. 예외는 인용문의 영어 원문·출처(10pt) 영역으로, 이 영역의 괄호는 그대로 10pt를 유지한다.

### "라벨 — 설명" 한 줄 표현

본문·목차의 한 줄(bullet 포함)에서 주제를 별도 줄과 하위 bullet으로 나누지 않고 `라벨 — 설명` 형태로 한 줄에 담은 경우, 첫 `—` 이후 텍스트는 기준 크기에서 **-2pt**로 렌더링한다. `**bold**` 범위가 `—`를 걸쳐 있어도 bold marker가 손상되지 않게 처리한다.

### 슬라이드 제목

슬라이드 제목(topic heading)은 **20pt Bold**로 렌더링한다. 제목 영역은 같은 줄의 세션명 객체와 겹치지 않도록 확보한다. 제목이 한 줄에 들어가지 않으면 원고 보완 사항으로 기록한다.

번호 없는 `## 제목`(서브 항목)은 슬라이드 제목의 **둘째 줄에 그룹(`NN. 그룹명`)을 11pt**로 표시한다. 그룹의 내용이 서브 항목 하나뿐이면 둘째 줄 없이 그룹(`NN. 그룹명`)을 20pt 제목으로 보인다. 이전 원고의 `**다이어그램 — …**` 표식은 서브 항목이 아닌 topic에서만 같은 자리에 다이어그램 이름을 보인다. continuation 번호 `(1/2)`는 첫째 줄에 붙는다. 목차 항목은 바꾸지 않는다.
- 직접 번호를 붙인 목록 항목(`1. `, `(1) `)은 번호 자체를 내어쓰기 폭으로 삼는다. 줄이 넘치면 다음 줄은 번호가 아니라 **항목 텍스트의 시작 위치**에 맞춘다. 번호 자리수가 달라도 번호의 시작 위치는 같다.

### 목록 본문 정렬

- **글머리표 기호 기준** — 인용문·업무 요청·품질 예문은 해당 목록의 `○`가 시작하는 X좌표에 맞춘다. 아래에 참조할 목록이 없으면 같은 수준의 목록 기호 위치를 사용한다.
- **글머리표 뒤 본문 기준** — Gherkin과 시연 입력의 첫 글자는 관련 목록의 글머리표 뒤 본문에 맞춘다. 목록에 직접 연결된 코드·예문 블록은 앞뒤의 관련 번호 또는 기호 뒤 본문 시작 X좌표에 맞추며 코드 내부의 상대 들여쓰기는 보존한다. 사용자 스토리 문형·예시와 목록 속 생략 표시도 해당 목록의 본문 위치에 맞춘다.
- Gherkin과 실제 시연 입력은 맑은 고딕 12pt, 줄간격 1줄, 문단 앞뒤 각 3pt의 편집 가능한 텍스트로 표시한다. 원문의 공백·줄바꿈을 보존하며 긴 입력은 같은 서식으로 이어지는 장에 나눈다.
- 문장으로 쓴 수업용 검토 예는 일반 본문 문단 또는 목록으로 렌더한다. 각 문단의 앞뒤 간격은 3pt다. 실제 코드 샘플 내부는 「소스 코드」의 간격을 따른다.
- 글머리표 없는 문단은 첫 줄과 이어지는 줄을 같은 위치에서 시작한다. 실제 X좌표를 대조할 때 객체 위치와 내부 여백을 포함한다. OOXML에서 목록 기호 위치는 `상자 X + 왼쪽 내부 여백 + marL + indent`, 목록 본문 위치는 `상자 X + 왼쪽 내부 여백 + marL`을 기준으로 한다. 해당 값이 상속되면 유효 값을 사용한다. 그룹 대표명과 독립 안내 문장은 각자의 시작점을 적용한다.

## 소스 코드

- ` ```text `·` ```plaintext ` 블록은 학습자에게 보이는 예시(결정 기록, 명세 원문 등)이므로 코드 블록과 같이 렌더링한다. 디렉터리 트리 도식은 ` ```tree ` 또는 가지 문자(`├─`, `└─`)가 있는 블록만이다(`parse.js`).
- Session Source의 코드 fenced block(예: ` ```java `)은 **전체 폭**(본문 폭 9.2in)의 코드 영역에 **기본 10pt**로 렌더링한다. 영문·기호는 고정폭 글꼴(Consolas), 한글 식별자는 본문 한글 글꼴로 표시하고, 줄 사이에 문단 간격을 두지 않는다.
- 코드 바로 앞의 짧은 설명(약 3줄 이하)은 첫 코드 슬라이드의 **코드 위**에 함께 둔다. 길면 설명을 앞 슬라이드에 둔다.
- 코드 바로 앞(사이에 텍스트만 허용)에 도식이 있으면 그 도식을 **코드의 모든 슬라이드에 함께** 둔다. 가로로 넓은 도식(가로:세로 1.3 이상)은 코드 위에 본문 폭으로, 좁은 도식은 코드 왼쪽에 둔다. 코드만 따로 보여 주지 않는다.
- 코드와 앞뒤 설명을 **한 슬라이드에** 두는 것을 우선한다. 들어가지 않으면 다음 순서로 시도한다: 10pt 두 단(좌우) → 9pt 한 단 → 9pt 두 단 → 8pt 한 단 → 8pt 두 단. 9pt·8pt에서는 줄 간격을 글자 크기의 1.2배로 좁힌다. 높이가 들어가는 배치 중 코드 줄이 **줄바꿈되지 않는** 배치를 먼저 고르고, 없으면 줄바꿈이 생기는 배치라도 한 슬라이드를 택한다. 높이를 넘치는 배치는 고르지 않는다.
- 두 단으로 나눌 때는 가운데에 가까운 빈 줄(멤버 사이)에서 나누고, 없으면 들여쓰기가 가장 얕은 `}` 뒤에서 나눈다. 메서드 본문 중간에서 나누지 않는다.
- 코드 옆·위의 도식은 자기 영역을 넘지 않는다. 10% 단위 축소가 영역보다 크게 올림되면 영역에 맞춰 줄인다(도식이 코드를 덮지 않게).
- 코드 위에 도식을 둔 슬라이드에서 8pt 두 단으로도 들어가지 않으면, 도식을 10%씩 **70%까지 줄여** 다시 시도한다. 도식이 반복되는 여러 장보다 조금 작은 도식 한 장이 읽기 쉽다.
- 그래도 들어가지 않으면 10pt로 빈 줄이나 `}` 뒤에서 여러 슬라이드로 나눈다. 이때는 원고의 설명을 압축할 수 있는지 먼저 검토한다.
- 코드 뒤의 짧은 설명·표는 남은 영역에 들어가면 같은 슬라이드에 이어 쌓는다.
- **제목이 붙은 도식은 제목 높이만큼 내려가되 쪽 번호 영역으로 들어가지 않는다**(`captionPicture`). 아래가 모자라면 그림을 줄이기 전에 **위로 올린다** — 올릴 수 있는 한계는 바로 위 내용의 아래 끝이다(`contentAbove`). 위에 여백을 둔 채 아래만 잘리는 장이 있었다(2026-11-04, `caption-fit.test.js`).
- **원고의 SVG는 내용이 viewBox 안에 들어가야 한다.** 밖으로 나간 상자·선·글은 그려지지 않으므로 Production이 넘친 양을 **경고**한다(`svgAdapter.js`의 `outsideViewBox`, `svg-viewbox.test.js`). 배치가 아니라 도식 원본이 잘린 것이어서 슬라이드를 봐야 드러난다.
- **표 바로 뒤의 코드도 표 아래에 쌓는다**(`appendCodeBelow`). 표 아래 남은 띠에 **10pt 한 단**으로 들어가고 뒤의 짧은 설명까지 함께 들어갈 때만이며, 글자를 줄이거나 두 단으로 접어야 들어가면 코드가 제 슬라이드로 간다. 이 규칙이 없을 때는 표만 있는 장과 코드만 있는 장이 둘 다 절반쯤 빈 채로 갈렸다(2026-11-03, `table-code-stack.test.js`).
- 실습 과제 topic(`NN. 실습 M — …`, 검토 예시 제외)은 **한 슬라이드**이며, 기준 서식으로 배치한다(`builder.js` `practicePage`, `PRACTICE_STYLE`).
- `**실습 안내 — 좌우 2단(하나의 슬라이드)**`를 지정한 지시 장은 목적을 위에 두고, 입력·진행·결과물을 왼쪽, 프롬프트·점검을 오른쪽에 둔다. 정확히 한 장이어야 한다. `**표 — 그림에서 직접 찾는 노테이션**`은 실제 PlantUML 도식과 표기 설명 표를 같은 장에 두며 도식의 최소 표시 크기를 적용한다. 기존 4열 비교표 검사는 그 형식을 지정한 원고에 적용한다. 개별 DD가 승인한 Before/After의 비교 대상·범위와 시각 표현은 그대로 보존한다. 적용 가능한 배치 게이트는 최종 PPTX의 실제 위치·개체를 검사한다.
- 초안·중간 검토·결과 확정을 수강생이 슬라이드에서 따라 하는 실습은 `**프롬프트 ① — …**`, `**검토 및 중간 피드백 ② — …**`, `**프롬프트 ⑤ — …**`으로 단계 경계를 밝힌다. 이 형식은 학습자용 요청과 판정 기준을 보존하고 필요하면 이어지는 슬라이드로 배치한다.
  - 목적·투입물·진행 방법·프롬프트·점검 항목·결과물로 구성된 실습은 목적을 상단 전체 폭, 투입물부터 점검 항목까지를 왼쪽, 결과물을 오른쪽에 둔다. 목적·그룹 제목 14pt, 소속 본문 12pt이며 그룹 제목은 Bold다. 열마다 편집 가능한 텍스트 개체와 실제 PowerPoint 목록을 사용한다. 같은 크기에서 열 너비 후보를 계측해 양쪽이 모두 가용 높이에 들어가는 배치를 먼저 선택한다. 후보는 **양방향**으로 계측한다 — 왼쪽을 넓히는 쪽을 먼저 보고, 모두 실패하면 좁히는 쪽을 본다(오른쪽 단이 넘칠 때는 넓히는 쪽만으로 맞출 수 없다). 그래도 넘으면 오류를 보고하며 내용·번호를 지우거나 높이 초과를 통과시키지 않는다. 오류는 **가장 가까운 분할과 그 초과량**을 적는다 — 그 pt가 원고에서 줄여야 할 양이다(`builder.js`, 회귀는 `node --test engine/production/src/test/practice-fixed-columns.test.js`).
  - 다음 수치와 축소 순서는 결과물 그룹이 없는 기존 입력의 호환 서식이다. 기존 한 단(폭 9.43in·높이 6.04in)은 안내 문장 16pt, level 0 18pt, level 1 16pt, level 2 14pt를 쓴다. 문단 간격은 앞뒤 3pt다.
  - `—` 뒤 설명은 본문과 같이 2pt 작게, `(…)`는 4pt 작게(최소 8pt) 쓴다. 점검 항목의 질문이 핵심어보다 크게 작아지지 않게 한다.
  - `+ ` 줄(서비스 개요·프롬프트 본문처럼 글머리표 없는 줄)은 부모 항목의 글자 시작에 맞춘다.
  - 기준 서식으로 넘치면 16pt → 14pt 한 단, 다시 14pt 좌우 두 단으로 배치한다. 복사해 입력할 긴 프롬프트를 보존해야 하면 마지막으로 12pt 한 단·두 단을 시도한다(하위 본문 최소 8pt). 도식은 다른 도식과 같이 7pt까지 줄인다. 그래도 한 장을 넘으면 **오류**다(`structure.js`).
- 실습의 답은 요약 뒤 별첨(`## 별첨. 실습 답`)의 서브 항목으로, 제목은 산출물의 이름이다. 선정한 실제 응답과 저자의 설명은 `session-authoring-guide.md`의 「사례·가정·실습」에 따라 구분하고 원문을 보존한다. `(안)` 같은 초안 표기를 붙이지 않는다. renderer는 제목 끝의 `(안)`을 20pt 제목 옆 18pt로 그리는 처리를 그대로 두어 아직 그 형식인 "객체지향 분석과 설계 실무"의 원고를 지킨다.
  - 아래 텍스트 답·도식 답의 14/12/11pt는 실제 응답 표식이 없는 저자 답안의 기존 호환 서식이다. 실제 응답은 「문서 형식」의 역할별 서식을 따른다.
  - **텍스트 답**(도식·표·코드 없음)은 좌우 두 단으로 한 장에 배치한다(`answerPage`, `ANSWER_STYLE`).
    - 단의 위치: 왼쪽 x 0.255in·폭 4.745in, 오른쪽 x 5.0in·폭 4.855in, 높이는 둘 다 6.04in다.
    - 글자: level 0 14pt, level 1 12pt, level 2 11pt다. `—` 뒤 설명은 2pt 작게, `(…)`는 4pt 작게(최소 8pt) 쓴다.
    - 들여쓰기는 단계마다 0.25in이고, 글머리표는 0.2in 내어쓰기다. 문단 간격은 앞뒤 3pt다.
    - 두 단은 **왼쪽을 먼저 채우고** 넘는 것만 오른쪽에 둔다(`styleFit.js`의 `leftFirst`). 나누는 자리는 level 0 항목 앞을 우선하고, 소제목과 그 아래 내용은 갈라놓지 않는다. 왼쪽 단은 **제 여유(`leftFit`)로 끝까지 채운다** — 답은 1.04배까지다(`fit`의 1.1배는 오른쪽 단과 한 단짜리 장에만 쓴다). 여유를 더 주면 왼쪽 글이 쪽 번호를 덮고, 여유를 빼면 들어갈 항목이 오른쪽으로 넘어가 왼쪽 아래가 빈다.
    - 앞머리의 글머리표 없는 문단(거버닝 메시지)은 두 단 위에 전체 폭 14pt로 둔다.
    - 한 장을 넘으면 **오류**다. 원고에서 규칙 일부를 `......`로 생략하거나 답을 나눈다.
  - **도식이 있는 답**은 일반 topic처럼 글과 도식을 **상하**로 배치하되, 글은 답의 크기(14/12/11pt, `sectionStyle`)로 쓴다. 도식이 글과 함께 7pt 이상으로 들어가지 않으면 도식만의 장으로 옮기므로, 거버닝 메시지는 한 줄로 쓴다.
  - 제목에 `검토 예시`가 있는 topic은 실습 과제로 보지 않는다(테스트 fixture의 옛 형식).
- 실습·답의 한 장 판단은 글 높이 추정(`styledCost`)으로 한다. 맑은 고딕 기준으로 한글 0.9em, 공백 0.25em, 줄 높이 1.25em이며, 추정이 상자 높이의 1.04배(실습)·1.1배(답)까지면 한 장으로 본다. 두 단의 왼쪽만은 `leftFit`으로 따로 재며 답·문서는 1.04배, 10pt 문서는 0.9배다. 추정은 근사치이므로 새 실습 장은 PowerPoint로 내보내 바닥글과 겹치지 않는지 확인한다.

### 코드와 도식의 연계

- 유스케이스 다이어그램은 `plantuml:usecase`로 표식한다. 종류가 없으면 시퀀스로 처리되어 Graphviz가 필요해진다.
- 코드 블록 바로 뒤(사이에 텍스트 없이)의 코드 블록은 앞 코드 아래 남은 영역에 **전부** 들어가면 같은 슬라이드의 같은 코드 열에 쌓는다(`builder.js` `appendCodeBelow`). 들어가지 않으면 새 슬라이드에서 시작한다.
- 세로로 긴 도식 하나와 도식 위에 다 들어가지 않는 설명은 **좌우 배치**(설명 왼쪽, 도식 오른쪽)로 한 슬라이드에 둔다.
- 코드 내용은 한 글자도 바꾸거나 빠뜨리지 않는다(자동 검사).
- 코드에서는 **선언된 이름만 bold**로 한다 — `class`·`record`·`interface`·`enum` 뒤의 타입 이름과, 선언 줄(`{`가 이어지는 머리, 또는 `);`로 끝나는 인터페이스·추상 메서드)의 메서드·생성자 이름. 호출·필드 접근·문장은 bold로 하지 않는다(`richText.js` `declaredNameSpans`).
- 원고의 ` ```java ` 블록은 같은 폴더 `code/sNN/*.java` 원본의 **발췌**여야 한다(`engine/production/src/codeSource.js`). `// ... <설명> 생략` 줄은 생략 표시이며, 그 사이의 각 부분이 원본에 그대로 있어야 한다. 다르면 **오류**, 원본 폴더가 없으면 **경고**다.

## 검토용 원고

- 반영 전 검토를 위해 추가·변경 topic만 모은 `sNN-add.md`를 만들 수 있다. 같은 폴더의 전체 후보 원고 `sNN.md`를 기준으로 번호와 참조를 검증한다. 검토용 원고의 topic 번호는 전체 후보 원고의 번호를 그대로 쓴다.

| Deck 사전 검사와 제작 후 대조 | 현재 CLI의 Markdown 구조·참조·인용 기록·등록된 실제 응답 검증. 일부 형식·출력은 `structure.js`, `inspect.js`의 조건에 해당하는 경우에만 검사한다. | 승인 DD–Deck 추적, 학습자·노트·메타데이터 분리의 전 범위 검사, 미지원 표현의 명시적 실패. |
| Production 후 최종 파일 검사 | `inspect.js`의 PPTX 재독해, 적용 대상의 실습·노테이션 등 배치 게이트와 표 경계 검사. PDF 표 검사는 `tools/check-rendered-tables.py` 실행 증거가 있을 때 확인한다. | 해당 Deck이 요구한 내용·관계·순서·노트의 출력 누락과 노출 여부, 미지원·미검사 항목을 명시한 증거. |

미구현·미실행 자동 검사는 `NOT VERIFIED`로 기록한다. 수동 대조를 수행했다면 그 범위와 판정을 별도로 기록한다. 거버닝 메시지의 의미, 실습 기준의 적합성, 도식·표·코드가 같은 결정을 설명하는지는 저작 단계의 의미 검토 항목이다. 최종 가독성과 Human 수락도 구조 검사 결과와 별도로 기록한다.

### 정본 이관과 현재 구현

| 항목 | 승인 정본 | 현재 실행 경로와 구현 대기 |
|---|---|---|
| 과정명·과정 목표, 과정 공통 영한 용어·코드 이름 | Course Design | 표지와 과정 목표는 기존 `course-design.md`의 과정명·「과정 목표 슬라이드」를 읽는다. 코드 이름 검사도 같은 파일의 용어집을 읽는다. 이 책임은 이관 대상이 아니다. |
| 세션 ID·세션명·순서·시간과 과정 목차 | Curriculum | 표지/목차 판독은 기존 Course Design의 `### SNN — 세션명 (시간)`을 읽고, 묶음 덱은 CLI에 전달된 순서를 사용한다. Curriculum의 직접 판독과 목록·순서 대조는 미구현이다. |
| 세션명·topic 참조 및 다음 세션 | 세션명·다음 연결은 Curriculum, topic 제목은 대상 Deck | 현재 참조 검사는 기존 Course Design 세션 목록에 형제 Deck 헤더 및 topic을 합쳐 사용한다. 다음 세션 검사는 기존 Course Design의 연속 번호를 본다. Curriculum과 Deck의 세션명 불일치 판정 및 승인된 후속 세션 연결의 직접 검사는 미구현이다. |
| 세션의 거버닝 메시지·학습 흐름·실습 계약 | Session Authoring | 원고가 의미를 소유한다. 요약 강사 노트의 모델 보완 줄 등 일부 현행 문법은 검사되지만 승인 입력과 원고의 버전·의미 대조는 미구현이다. |
| 파일·표식의 역할 분리 | DD는 설계, Deck은 제작 입력 | 원고 훅의 세션 Markdown 패턴은 DD도 포함할 수 있다. 좌우 실습 검사 또한 왼쪽의 `진행` 표식을 기대한다. DD의 검사 경로 분리와 세부 시간·제작 메타데이터를 학습자 영역에서 분리한 실습 형식의 검사는 구현 대기다. |

기존 과정을 제작할 때는 현행 입력 위치를 유지한다. 이관 적용 시 승인 Curriculum·DD와 CLI 입력을 수동 대조하고, 입력 경로 변경 후 표지·참조·요약 회귀를 검증한다. 호환 입력을 잠시 유지하는 경우 승인 정본에서 파생된 값인지 확인한다. 기존 필드를 독립 정본으로 편집하지 않는다.

목표·요약의 고정 장수와 7개 목표 상한, 실습 1장과 일부 특수 배열, 파일별 표·도식 배치의 현행 검사 계약은 유지한다. 승인한 교육 내용을 훼손해야만 조건을 맞출 수 있다면 새 기준으로 일방 적용하거나 검사를 넘기지 않고, 승인 범위와 현행 게이트의 불일치로 남긴다.

- 저자 본문의 세션·topic 참조는 `session-authoring-guide.md`의 「참조 형식」을 따른다.
  - 세션명이 다르거나, topic 번호·제목이 대상 세션에 없거나, 제목 없이 번호만 쓴 `「NN」`이거나, `S0x` 식 표기를 쓰면 **오류**로 생성을 중단한다. 번호만 쓴 참조에는 대상 세션의 `「NN. 제목」`을 알려 준다. 같은 제목이 다른 번호로 있으면 고칠 번호를 알려준다.
  - 대상 세션 원고가 아직 없어 확인할 수 없는 참조는 **경고**로 남긴다.
- 실제 실행 응답 발췌는 과정의 `recorded-responses.json`에 원고 파일·응답 topic과 실행 전문의 과정 내 경로·SHA-256을 연결한다(`responseExcerpts.js`, version 1의 `responses` 배열). 이는 행 번호·특정 문장·진단별 예외 목록이 아니다. 실행 전문이 없거나 해시·문구·순서·강조·표·코드·생략 위치가 일치하지 않으면 **오류**다. 출처 중복·누락·범위 모호함과 과정 밖 경로도 오류다.
  - 발췌 범위는 `**실제 LLM 응답**` 뒤부터 `**실제 LLM 응답 끝**`, 강사 노트 또는 다음 topic 앞까지다. 끝 표식은 parser가 소비하며 출력하지 않는다. topic 제목은 실행 전문의 첫 제목과 함께 대조한다. 표식 앞의 저자 설명은 범위에 포함하지 않는다.
  - 제목 단계·목록의 표시 들여쓰기와 문서/페이지 제작 표식만 구분한다. 문구·원래 강조와 fenced 코드의 공백은 보존한다. `.....`는 원본에서 실제로 빠진 하나 이상의 내용 단위와 유일하게 대응해야 한다. 표시 없이 건너뛰거나 길이 0인 생략·모호한 대응은 허용하지 않는다. 대응한 원문 위치와 생략 구간을 QA에 기록한다.
  - 대조를 통과한 응답 범위의 표현은 저자의 세션 참조로 해석하지 않는다. 검증 실패 시 그 범위를 저자 검사에서 빼지 않는다. 범위 밖 저자 문장·강사 노트·다음 topic에는 현행 참조 규칙을 계속 적용한다. 출처 레이블, 구조·배치·내용 누락 검사는 발췌 안팎에서 그대로 실행한다.
- 출처 레이블 `[저자 연도]`·`[Wikipedia: 항목]`을 별첨과 대조한다(`references.js`의 `checkLabels`). 세션의 레이블이 별첨 `references.md`에 없거나 별첨이 없으면, 별첨에 같은 레이블이 두 번 있으면, 별첨을 생성할 때 세션이 쓰는 레이블이 별첨에 없으면 **오류**다. 인용 끝이 레이블이 아닌 `저자, 년도` 형식이면 **경고**다. 영문 원문이 있는 인용이 원문 확인 기록 `references/verified.json`(`tools/verify-quote.js`가 "있음" 판정 때 기록)에 없으면 **경고**다 — 확인하지 않은 인용은 세션 완료 기준(경고 0개)을 넘지 못한다.
  - 코드 블록과 같은 줄에서 짝이 맞는 백틱으로 감싼 인라인 코드의 대괄호는 출처 레이블로 검사하지 않는다. 미정 식별자 같은 코드 표기를 출처로 오인하지 않으며, 코드 밖의 레이블은 계속 검사한다. 백틱이 닫히지 않았으면 인라인 코드로 간주하지 않는다. 이 구분은 원고와 별첨의 사용 레이블 집계에 함께 적용한다.
- `session-authoring-guide.md`의 「세션 목표와 요약」을 검증한다(`engine/production/src/structure.js`). 다음은 **오류**로 생성을 중단한다. 검토용 원고 `sNN-add.md`는 검사하지 않는다.
  - `01. 세션 목표`의 최상위 bullet이 7개를 넘거나 목표가 두 슬라이드 이상으로 나뉜다.
  - 마지막 topic `요약`이 두 슬라이드 이상으로 나뉜다.
  - `요약`에 `### 다음 세션` heading이 없는데 같은 과정의 `course-design.md`에 다음 세션(`### S{NN+1} — `)이 있다. 과정 밖의 덱(`references/sw-engineering-approach/` 같은 참조 자료)은 과정 설계가 없으므로 검사하지 않는다.
- 도식 렌더링이 실패하면 오류에 topic 제목과 도식 제목을 함께 적는다(PlantUML의 "contains errors"만으로는 위치를 알 수 없다).
- `node src/cli.js --check <원고…>`는 여러 원고를 검사만 하고 덱·`.qa.json`을 남기지 않는다. 세션 번호를 바꾼 뒤 참조하는 세션을 함께 검사할 때 쓴다.
- 다음은 **경고**로 보고한다. 경고는 `.qa.json`의 `warnings`와 콘솔에 출력하며 생성을 중단하지 않는다. 원인을 해결해 0개로 만드는 것이 기준이다. 아래의 원고 축약·분할 지시는 내용·의미 구조의 문제로 확인된 경우에 적용한다. renderer의 렌더링·배치·글꼴 결함은 Production에서 수정하며, 경고를 없애려고 원고를 renderer에 맞추지 않는다(「Session Authoring으로의 원고 보완 피드백」).
  - 본문이 한두 줄뿐인 continuation 슬라이드(표·visual·코드 없음) — **뒤에 같은 topic의 글이 더 있을 때만** 경고한다. topic의 마지막 장은 남은 내용을 그대로 받으므로 짧아도 정상이다.
  - **본문 용량 초과** — 도식·표가 차지하는 높이를 반영한 가용 영역과 실제 본문을 비교한다. 마지막 장의 현재 경고 허용치는 10%다. 실제 렌더에서 잘림·겹침이 있으면 경고 유무와 별개로 해결한다.
  - **두 단 가운데 한 단의 높이 초과** — 여유를 빼고 실제 사용 영역과 비교한다. 실습 안내는 페이지를 넘길 수 없으므로 여유를 적용하지 않는다. 참고 자료는 별개 배치 계약을 적용한다.
  - 한 줄을 넘는 표 셀(「표의 행 높이와 열 너비」, `structure.js`).
  - 7pt 미만으로 줄어든 도식(「Visual layout 및 가독성」, `generate.js`).
  - 도식 라벨의 topic 번호(`structure.js`).
  - 굵게 표시한 핵심어가 없는 25자 이상의 본문 문장·bullet(`structure.js`). 번호 단계, 인용된 요청(`>`, `“…”`)은 제외한다.
  - 번호(①·② 등)로 시작하는 bullet — 글머리표와 번호가 겹친다. 번호 목록(`1. `)으로 쓴다(`structure.js`의 `numberedBullets`).
  - 목록을 예고한 머리말(`… 다음과 같다.`·`다음 사항은 …`·`:`로 끝나는 줄) 바로 뒤의 **같은 단 목록** — 머리말을 `- `로 올리고 항목을 두 칸 들여써 묶음을 보인다(`structure.js`의 `flatGroupItems`, `flat-group-items.test.js`).
  - 자바 코드 원본 폴더가 없는 세션(「소스 코드」, `codeSource.js`).
  - 강사 노트가 없는 topic(`structure.js`).
  - "?"가 없는 의문문 topic 제목·표 칸 — "~란·~인가·~는가" 등으로 끝나는 것(`structure.js`의 `unmarkedQuestionTitles`).
  - 별첨 밖에 있는 `(안)`으로 끝나는 topic(`structure.js`의 `answersOutsideAppendix`). 아직 그 형식인 과정을 위한 검사다.
  - 실습 topic에 빠진 구성 — 투입물·프롬프트·점검 항목·결과물과 **결과물의 파일 이름**(`structure.js`의 `practiceShape`). 다른 모양으로 쓴 실습은 렌더 결과만으로는 드러나지 않는다. 실습은 사슬이라 투입물은 프롬프트 문장 안이 아니라 제 항목으로 있어야 하고, 결과물은 다음 실습이 가리킬 파일 이름을 밝혀야 한다. 앞 실습이 없는 **첫 실습**(`NN. 실습 1 — …`)만 투입물이 없어도 된다.
  - **실습이 있는데 답이 없는 세션**(`structure.js`의 `missingPracticeAnswer`). 실습 topic이 있으면 요약 뒤에 `## 별첨. 실습 답`이 있어야 한다. 여러 세션을 모으다 별첨만 빠지면 렌더는 깨끗한데 답이 없는 교재가 된다.
  - **내용이 viewBox를 넘는 SVG**(`svgAdapter.js`의 `outsideViewBox`). 밖으로 나간 상자·선·글은 그려지지 않아 도식 자신의 테두리가 사라진다. 넘친 양을 알려 준다.
  - **한글로 적은 수**(`structure.js`의 `spelledNumbers`) — "세 가지"·"다섯 단계"처럼 2 이상의 수를 한글로 쓴 자리다. 숫자로 바꾼다(`3가지`·`5단계`). '하나'를 뜻하는 관형어(한 번·한 줄)와 횟수의 '번'은 보지 않는다. 일괄 변환은 `node tools/normalize-numbers.js --apply <원고…>`다.
  - **요약의 강사 노트에 「모델에서 보완된 것 — …」 줄이 없는 세션**(`structure.js`의 `missingModelUpdate`). 세션 순서가 개발 절차가 아니라 반복임을 보이는 줄이며, 보완할 것이 없는 세션은 "없다"로 밝힌다. 요약이 없는 원고(별첨)는 검사하지 않는다.
  - **원고가 가리키지 않는 예시 코드**(`codeSource.js`의 `checkOrphanCode`). `code/sNN/` 바로 아래 항목 가운데 같은 과정의 어느 원고도 `code/sNN/<이름>`으로 말하지 않는 것이다 — 해체된 세션이나 버린 사례의 잔여물이 여기서 드러난다. 실행용 의존성 폴더 `lib`는 보지 않는다.
  - **별첨에만 있고 어느 세션도 쓰지 않는 참고 자료 레이블**(`references.js`의 `checkLabels`). 인용하지 않기로 한 자료는 항목 끝에 `(읽을거리)`를 붙여 그 사실을 밝힌다.
  - 슬라이드 자신을 설명하는 본문 문장 — "표는 … 둔 것이다", "표의 오른쪽 열이 …", "셋째 줄이 …", "지금까지 … 나왔다"(`structure.js`의 `slideTalk`). 고치는 방법은 `session-authoring-guide.md`의 「6. 표와 목록」에 있다. 강사 노트는 검사하지 않는다.
  - 무시한 `**배치 — 좌우**` — 본문이 왼쪽 반을 넘거나 도식이 오른쪽 반에서 7pt보다 작아질 때(`builder.js`의 `layoutWarnings`).
  - 앞 세션의 코드와 값이 다른 `enum` — 관통 사례의 공통 식별자가 세션 사이에서 바뀐 것(`codeSource.js`). 뒤 세션이 값을 더하는 것(진화)은 허용한다. 분석 코드의 한글 enum(`주문상태`)과 설계 코드의 영문 enum(`OrderStatus`)은 같은 과정 `course-design.md`의 **영한 용어집** 표로 대응시켜 비교한다. 용어집에 없는 한글 값은 대응을 확인할 수 없다고 보고한다.
- 의도적인 **오답 예시**나 전면 보완 전의 **대체된 코드**는 정상 모델의 enum 연속성 기준이 아니다. 해당 Java 파일에 `// production-enum-baseline: exclude — <구체적인 이유>`를 독립된 줄로 기록하면 그 파일의 enum만 연속성 비교에서 제외한다. 이유 없는 표식은 인정하지 않는다. 정상 모델의 누락·이름 불일치를 감추려고 쓰지 않으며, 코드 발췌 일치 검사는 그대로 수행한다. 같은 이름의 정상 enum 원본이 여럿이면 모든 값의 합집합을 비교해 파일 탐색 순서가 누락을 숨기지 않게 한다(`codeSource.js`).
- 전자 사본이 없어 **사람이 인쇄본에서 확인한** 인용은 `node tools/verify-quote.js --attest "<확인 경위>" "<영문 인용>"`로 기록한다. 기록에 확인 경위가 남아 나중에 근거를 되짚을 수 있다. 확인하지 않고 쓰는 수단이 아니다.
- 과정을 **전면 보완하는 동안**에는 아직 다시 쓰지 않은 원고가 "헤더는 새 세션명, 본문은 옛 축"으로 남는다. 참조 검사가 같은 폴더의 Session Source 헤더를 함께 보므로, 헤더를 먼저 바꿔야 다시 쓴 세션의 참조가 성립하기 때문이다. 그 원고를 `courses/<course>/checks/rewrite-pending.json`의 `pending`에 사유와 함께 적으면 턴 종료 검사(`tools/session-check-hook.js`)가 검사 대상에서 뺀다. 세션을 다시 쓸 때 목록에서 지우고 전부 끝나면 파일을 지운다. **지금 고치는 원고의 완료 기준은 그대로 오류 0·경고 0이며**, `--check`는 목록과 무관하게 모든 원고를 검사한다.
- 원전을 구하지 못해 확인이 **사용자 조치를 기다리는** 인용은 `references/pending-sources.json`에 사유·대기 사항과 함께 적는다. **필요할 때 만들고 해결되면 지우는 파일이므로 없는 것이 정상 상태다** — 턴 종료 검사는 파일이 없으면 면제 목록을 비운 것으로 보고 그대로 진행한다(결함이 아니다). 빈 파일을 미리 만들어 두지 않는다. Production은 그대로 경고하므로 완료 기준(경고 0개)은 충족되지 않으며, 턴 종료 검사(`tools/session-check-hook.js`)만 같은 항목을 반복해 막지 않는다 — 경고를 감추는 수단이 아니다.

## Visual layout 및 가독성

- 도식의 방향·행 나눔·배치 같은 **그리는 방법**은 원고가 정한다(`session-authoring-guide.md`의 「8. Visual」). Production은 크기·위치·분할만 정한다.
- 쌓이는 블록(본문·표·도식·캡션) 사이는 **위아래 모두 한 줄**(18pt)로 같다(`builder.js`의 `BLOCK_GAP_PT`). 도식·표는 남은 공간에 가운데 맞추지 않고 **앞 문장 바로 아래**에서 시작한다(`visualPanel`, `fitTarget(…, "top")`) — 가운데 맞추면 짧은 본문 아래에 빈 구멍이 생기고 표 뒤 문장은 표에 붙는다. 도식 제목과 도식 사이도 한 줄을 띄운다(`CAPTION_GAP`).
- 본문이 끝나는 자리는 글자를 실제로 재지 않고 **추정**한다(`blockCost` → `textEndIn`·`textAdvancePt`). 추정에는 페이지 넘김을 안전하게 하려는 여유가 섞여 있으므로, 상자 높이는 여유를 그대로 쓰고 **다음 블록의 시작점만** 그 일부(`RECLAIM_PT`)를 되돌려 쓴다. 추정이므로 장마다 한 줄 안팎의 차이가 남는다 — 상수를 바꾸면 여러 세션의 실제 PDF를 눈으로 확인한다.
- Production이 Session Source의 노드·관계·의미를 임의로 바꾸지는 않는다. 의미 재구성이 필요하면 Session Source 보완 대상으로 보고한다.
- 슬라이드에 삽입된 최종 표시 크기 기준으로 **모든 도식의 내부 텍스트는 10pt**로 같다. 배치 가능 영역에 여유가 있어도 10pt를 넘겨 키우지 않는다(UML·SVG 포함).
- 10pt로 배치 영역을 넘치면 **9pt → 8pt → 7pt** 순으로 줄여, 영역을 넘지 않는 가장 큰 크기를 고른다. 본문 텍스트나 페이지 분할은 바꾸지 않는다. **최소는 7pt**다. 다른 내용과 함께 놓여 7pt 미만이 되는 도식은 먼저 **다음 장의 남은 영역**으로 옮긴다 — 다음 장 본문이 끝난 자리 아래에 7pt 이상으로 들어가면 그 장에 쌓아, 앞 장을 도식 하나 때문에 비우지 않는다. 그 자리에도 들어가지 않을 때만 **도식만의 슬라이드**(본문 전체 영역)로 옮긴다(`builder.js`). 이 배치 해결은 Production의 책임이다.
- 도식만의 슬라이드에서도 7pt 미만이면 영역에 맞춘 출력은 **진단용**이며 **경고**로 보고한다(`generate.js`). 경고가 남은 원고는 완료할 수 없다. 이 경고는 도식의 **밀도**에 대한 원고 검토 질문이다 — 한 도식이 서로 다른 질문을 함께 담았다면 SA가 의미 단위로 나눈다(`session-authoring-guide.md`의 「8. Visual」). 크기를 맞추려고 노드·관계를 지우지 않는다.
- 표 아래의 남은 영역에는 도식이 7pt 이상으로 들어갈 때만 쌓는다. 아니면 도식은 다음 슬라이드로 간다. 코드 위·옆의 도식도 10 → 9 → 8 → 7pt 중 코드가 한 장에 들어가는 가장 큰 크기를 쓴다.
- 도식의 자리를 예약한 본문 높이는 해당 도식 앞의 글에만 적용한다. 도식이 이미 출력된 뒤의 글은 자기 장의 가용 영역을 사용한다.
- Mermaid, PlantUML, Chart, Image에 같은 가독성 기준(최소 크기와 축소 규칙)을 적용한다.
- **글자 크기는 도식 자신의 단위로 잰다.** mmdc는 어떤 Mermaid 도식이든 **같은 픽셀 너비의 캔버스**에 맞춰 그리므로, PNG의 픽셀 수로 글자 크기를 추정하면 가로로 긴 도식일수록 실제보다 크게 잡힌다(한 줄로 늘어선 도식이 3pt로 그려져도 10pt로 보고되었다, 2026-10-17). Mermaid는 렌더한 SVG의 `viewBox` 너비와 그 SVG의 기본 글자 크기(px)로 10pt에 해당하는 표시 너비를 구한다(`mermaidAdapter.svgMetrics` → `visualFit.naturalSize`). SVG는 자기 원본의 최소 글자 크기를, PlantUML은 렌더러의 고정 비율을 쓴다.
- **도식의 상자와 라벨에는 바탕색을 넣지 않는다**(`session-authoring-guide.md`의 「9. UML」). Mermaid는 neutral 테마에서도 클래스 상자와 연관 라벨에 회색 바탕을 넣으므로, 테마 변수(`mainBkg`·`labelBackground`·`edgeLabelBackground`)를 흰색으로 고정한다(`mermaidAdapter.js`의 `MERMAID_CONFIG`). `themeCSS`는 mermaid가 설정 파일로 덮지 못하게 막아 둔 값이라 쓰지 않는다. 뜻을 나르는 색은 원고가 `style` 줄로 지정하며 그 지정은 그대로 남는다.
- **Mermaid 시퀀스의 메시지 라벨은 줄바꿈한다**(`sequence.wrap` true, `width` 170, `mermaidAdapter.MERMAID_CONFIG`). mermaid는 긴 라벨을 한 줄에 담으려고 참여자 사이를 벌리므로, 라벨 하나가 길면 도식이 가로로 늘어나고 슬라이드 폭에 맞출 때 글자가 7pt 아래로 내려간다(설계 시퀀스의 `approve(orderNumber, order.totalAmount(), …)`가 3.4pt로 보고됐다, 2026-10-24). 줄바꿈은 도식 자신의 너비만 줄이고 글자 크기는 그대로다. 그래도 `alt` 여러 갈래와 참여자 여섯이 함께 있으면 7pt에 닿지 않으므로, 그때는 원고가 의미 단위로 발췌·분할한다(「Visual layout 및 가독성」의 도식 밀도 경고).
- **Mermaid `flowchart`의 노드 간격을 좁힌다**(`nodeSpacing` 22, `rankSpacing` 30, `padding` 6, `mermaidAdapter.MERMAID_CONFIG`). 기본값(50/50)은 `subgraph`가 여럿인 도식을 가로로 벌려 놓고, 캔버스 폭에 맞춰 줄이면 글자가 7pt 아래로 내려간다. 간격을 좁히면 도식 자신의 너비만 줄고 글자 크기는 그대로이므로 표시 글자가 그만큼 커진다. 그래도 `subgraph`를 한 랭크에 늘어놓는 성질은 남으므로, **패키지 다이어그램은 `svg:uml`이나 `plantuml:package`로 쓴다**(`session-authoring-guide.md`의 「패키지 다이어그램」).
- 한 도식 안에서 같은 종류의 박스(클래스·열거형 — 패키지 다이어그램 안의 클래스 포함, 상태, 유스케이스, 시퀀스 참여자, Mermaid 노드)는 라벨 길이에 따라 제각각 크기가 되지 않게 **가장 넓은 박스의 폭과 가장 높은 박스의 높이**에 맞춘다. 글자 크기는 바꾸지 않고 박스만 넓힌다. 클래스는 속성·오퍼레이션 칸의 줄 수도 맞춘다. 액터 아이콘, subgraph·경계 사각형, `-`로 두 줄이 되는 라벨처럼 다른 종류이거나 채우기로 배치가 틀어지는 요소는 제외한다. 구현은 `engine/production/src/uniformSize.js`와 각 adapter의 2단계 렌더(측정 → 재렌더)다.
- Mermaid 클래스 다이어그램의 따옴표는 다중성 값을 감싸므로 flowchart 노드의 HTML 강조·크기 래퍼를 넣지 않는다. `"1"`·`"1..*"` 같은 값을 원문 그대로 보존한다. 클래스 이름의 기본 굵은 표시는 그대로 사용한다.
- 클래스 박스는 이름이 두 글자여도 **한글 4글자 폭 이상**을 확보한다.
- 클래스·패키지 다이어그램은 원형 표시(C·E·I·A)를 숨긴다(`hide circle`, `plantumlAdapter.js`). 원고에 쓰지 않는다. 열거형·인터페이스는 원고의 `«enumeration»`·`«interface»` 스테레오타입으로 구분한다.
- 시퀀스 다이어그램은 참여자를 위쪽에 한 번만 보인다(`hide footbox`, `plantumlAdapter.js`).
- 막대 인형 액터(시퀀스·유스케이스)는 PlantUML 고정 크기의 **50%**로 줄인다. 액터에 닿던 연관·일반화 선은 줄어든 도형에 다시 붙이고, 위쪽에 생긴 빈 공간은 잘라낸다.
- 유스케이스 이름은 타원 가운데에 두고, 연관선 끝은 타원 테두리에 닿게 한다.
- 연관 클래스는 UML 표기대로 그린다. 두 클래스를 잇는 끊기지 않은 실선의 가운데에서 점선이 연관 클래스로 이어지며, 중간점 표시는 없다.
- 액터 축소, 유스케이스 타원, 연관 클래스의 세 항목은 PlantUML(smetana)이 설정으로 지원하지 않거나 잘못 그리는 부분이라, PlantUML SVG를 보정한 뒤 rsvg-convert로 PNG를 만든다(`engine/production/src/umlSvgFix.js`).
- 이미지 크기를 일률적인 비율로 고정하지 않는다.
- **좌우 배치**는 원고가 `**배치 — 좌우**`로 요청한 topic에만 쓴다 — 도식 하나를 오른쪽 반에, 본문을 왼쪽에 둔다. 요청이 없으면 도식은 본문 아래에 둔다. 도식이 오른쪽 반에서 7pt보다 작아지거나 본문이 왼쪽 반을 넘으면 요청을 무시하고 상하로 배치하며 경고한다(본문만 반폭으로 남고 도식이 다음 장으로 밀리는 것을 막는다).
- 본문과 visual의 배치는 내용량과 가독성을 기준으로 결정하며, visual 때문에 짧은 문장 하나가 불필요하게 continuation으로 밀리지 않도록 한다.
- 페이지를 넘길 때 남은 본문이 한 페이지 용량의 **20% 이하**이면 새 페이지로 넘기지 않고 현재 페이지에 붙인다(최대 용량의 120%까지). 한두 줄짜리 continuation 슬라이드를 만들지 않기 위해서다.
- `**페이지 분할**`은 topic을 **구간**으로 나눈다. visual은 원고에서 놓인 구간의 페이지에만 배치하며, 앞 구간의 페이지로 끌어오지 않는다. visual이 없는 구간은 텍스트 전용 페이지로 전체 분량 기준을 쓴다.
- **표 페이지 쌓기**: 같은 구간에서 표 뒤에 오는 텍스트, 두 번째 표(한 페이지 분량), visual은 표 아래 남은 영역에 들어가면 **같은 슬라이드에 이어 쌓는다**. 들어가지 않으면 새 슬라이드에서 시작한다. 쌓은 텍스트는 표의 lead 텍스트와 같은 폭·글꼴 기준을 쓴다.
- **두 표 사이의 글은 뒤 표의 lead이기 전에 앞 표의 뒷글이다**(`builder.js`의 `stackPrefixBelow`). 둘째 표가 앞 장에 들어가지 않을 때 그 사이의 글을 통째로 둘째 표의 lead로 보내면, 앞 장은 표 아래를 비운 채 끝난다. **표 제목(`**표 — 제목**`)만 표와 함께 보내고** 나머지 가운데 들어가는 앞부분은 앞 장의 표 아래에 쌓은 뒤, 줄어든 lead와 함께 표가 앞 장에 들어가는지 다시 본다. 하위 bullet은 제 상위 bullet과, 소제목은 뒤 내용과 같은 장에 둔다(`table-lead-stack.test.js`, 2026-11-05).
- **범례와 표**: visual 바로 뒤에(텍스트만 사이에 두고) 표가 오면 `[앞 텍스트][visual][사이 텍스트][표]` 순서로 한 슬라이드에 배치한다. visual이 최소 크기(7pt) 이상으로 들어갈 공간이 없거나 표가 한 페이지를 넘으면 visual은 앞 텍스트와 함께, 표는 다음 슬라이드에 둔다.
- 표나 범례와 함께 쌓이는 visual은 앞의 텍스트 전용 페이지의 분량 기준을 줄이지 않는다.
- 표와 visual 사이에 `**페이지 분할**`이 있으면 visual은 **새 페이지**에 둔다.
- 일반 강의의 같은 구간에서 이어지는 두 표의 열 수가 같으면 두 표의 **열 너비를 맞춘다**. 한 장에 쌓이든 나뉘든 같은 격자로 읽히게 한다. 실제 응답의 서로 다른 원표는 각 원표의 내용 기반 계측을 유지하며, 같은 원표의 분할 부분만 하나의 폭 벡터를 공유한다(「긴 표의 분할」).
- 본문과 함께 배치하는 visual은 본문의 마지막 줄과 페이지 번호 사이 여백의 중앙에 위치시킨다. 본문에 바로 붙여 배치하지 않는다.
- 도식(Mermaid/PlantUML) 내부 라벨이 `제목 - 설명` 형태로 하나의 노드·참여자에 두 정보를 담을 때는 라벨의 첫 `-` 뒤에서 줄바꿈하고, `-` 이후 텍스트를 약 80% 크기로 렌더링한다.
- 도식 내부에서 노드·참여자·엔티티 등 그 자체가 주제인 라벨은 bold로 렌더링한다. 화살표 위의 흐름·메시지 설명 텍스트는 bold로 렌더링하지 않는다.

## 출력 호환성

- 모든 PPTX 텍스트 본문에는 빈 도형이라도 최소 한 문단이 필요하다. 구조 검사에 빈 입력을 포함하고 실제 PowerPoint 열기나 OOXML 문단 검사로 확인한다.
- 영문 줄바꿈은 슬라이드·마스터·노트 마스터의 유효 속성을 검사한다. 승인된 식별자 분리 지점은 「표의 행 높이와 열 너비」를 따른다.
- PlantUML의 요소별·전역 간격 설정은 레이아웃 엔진에 따라 다르게 적용된다. 조정은 해당 도식 범위로 제한하고 실제 렌더의 글자·테두리·겹침과 페이지 분할을 재확인한다.

## 과정별 제작 기준

과정 고유의 장 배치·글꼴·셀 여백·참조 PPTX·제작 승인 조건은 해당 과정 제작 기준에 둔다. 승인 Deck이나 제작 기록에서 적용 버전을 가리킨다. 기존 Course Design의 제작 기준 참조는 이관 전까지 호환 경로로 유지한다. 공통 Renderer는 적용 범위를 구별해 다른 과정의 기본값을 보존한다.

실행 원문과 일반 저작 검사 규칙이 충돌하면 과정 폴더의 `recorded-checks.json`에 대상 원고·topic·문맥·블록·검사 이름·실행 기록을 명시할 수 있다. 생성 때 원문을 다시 대조하고 일치한 블록에 지정한 검사 하나만 제외한다(`recordedChecks.js`). 프롬프트는 실제 요청 문구, 응답의 목록 소개는 같은 절의 문구·뒤 첫2항목을 대조한다. 미일치·누락·모호함은 경고로 남기며, 저자 문장과 다른 검사·구조·렌더링 검사는 유지한다.

응답 발췌의 출처·범위 판정은 위 개별 검사 호환 목록이 아니라 「자동 검사 — 참조와 경고」의 공통 전문 대조를 사용한다. `recorded-responses.json`에는 진단 이름·무시할 행 번호·허용 문자열을 두지 않는다. 검증된 범위 밖으로 분류 결과가 확장되지 않도록 회귀 fixture로 확인한다.

## 최종 Production 검증과 증거

이 절은 **제작 검증**이다(「SA와 Production의 검증 경계」). SA 완료의 선행 조건이 아니다.

- 최종 PPTX를 대상으로 본문·인용문·표·visual·노트의 누락, 순서, 겹침, clipping, overflow, continuation 연결을 확인한다. 구조 검사와 실제 렌더 결과 검사를 함께 기록한다.
- 최종 입력 버전을 식별하고 같은 버전에서 PPTX·QA를 생성한다. 원고와 검증한 PPTX의 SHA-256 및 실제 경로를 기록하고 QA·렌더 증거가 같은 파일을 대상으로 하는지 대조한다. 임시 출력과 정식 산출물을 구별해 보고한다. 승인 원고 인계 후 의미·문구를 제작 편의로 바꾸지 않는다. 실제 입력·첨부·응답 전문과 발췌를 대조하고 일치하는 실행을 재사용한다. 불일치나 전문 누락이 있는 실행만 다시 수행하며 응답 원문을 보존한다.
- 최종 PPTX는 **전 장을 렌더링**해 읽기 순서·누락·잘림·겹침을 확인한다. 수정 중에는 바뀐 장만 다시 보되 최종 입력·출력 버전의 전 장 렌더 증거를 남긴다. 공통 및 과정별 기준의 글꼴·간격·셀 여백·열 너비·행 높이는 최종 PPTX의 해당 객체를 전수 검사한다. 왼쪽 우선 흐름, 코드·예문 및 프롬프트의 본문 시작 위치도 실제 렌더에서 확인한다. 표 셀은 필요에 따라 PDF 좌표로 전수 대조한다.
- 인용문 그룹 수는 입력 원고에서 다시 센다. 모든 그룹의 한글 기준 크기(독립 인용 18pt, 목록 인용은 해당 단계의 크기)와 영문·출처 10pt를 OOXML run 단위로 검사한다. 과정별 예외는 해당 과정 제작 기준을 참조한다. 일부 표본 검사만으로 전체 통과를 선언하지 않는다. 표시용 큰따옴표·출처 위치·글머리표 유무와 bold가 글꼴 크기를 덮어쓰지 않는지도 확인한다.
- visual 텍스트 목표 10pt는 **슬라이드에 배치한 최종 표시 크기**에서 판단한다. 소스의 font-size, PNG 해상도나 확대 화면만 보고 통과시키지 않는다. 배치 가능 영역을 넘쳐 9·8·7pt로 줄인 경우 그 축소된 최종 크기를 기준으로 판단한다.
- 측정에는 소스 좌표·글꼴 단위, 내부 transform, 이미지·viewBox의 실제 표시 영역과 최종 PPT 크기를 반영한다. 예를 들어 변환 없는 SVG에서 96px가 72pt로 해석되고 원본 폭 Wpx를 PPT 폭 Ppt에 균일 배치한다면 fpx 글자의 최종 크기는 `f × P / W`pt다. 중첩 변환·여백·비균일 축소가 있으면 이 단순식을 그대로 적용하지 않는다.
- raster 또는 윤곽선화된 글자처럼 정확한 원래 크기를 알 수 없는 경우 제작 기록과 배율을 확보한다. 근거 없이 OCR 높이를 글꼴 크기로 단정하지 않는다. 측정 불가능한 항목은 `NOT VERIFIED`로 남기고 시각 확인 결과와 구분한다.
- 판정은 `PASS`(확인된 충족), `FAIL`(확인된 위반), `NOT VERIFIED`(미실행·근거 부족)로 기록한다. 실패나 미확인 필수 항목이 있으면 전체 Production 검증 완료로 표시하지 않는다. 테스트 통과는 실제 가독성 통과를 대신하지 않는다. 요청한 제작 서식의 검증 결과·Human의 원고/제작 승인·전체 QA 판정을 구분해 기록한다.
- 자동 검사의 결과(판정·슬라이드 수·검사한 블록·visual 상태·오류·경고)는 Production이 입력과 같은 디렉터리의 `[basename].qa.json`에 남긴다(`generate.js`).
  - 자동 검사 `PASS`는 **오류 0개**를 뜻하며 경고 0개나 교육자료 제작 완료를 뜻하지 않는다. 콘솔은 자동 검사 판정·오류 수·경고 수와 시각 검증 `NOT_VERIFIED`(미완료)를 구분해 표시한다. 경고는 생성을 중단하지 않으며, SA 완료의 오류·경고 0개 기준은 그대로다.
- 실제 렌더 결과를 사람이 검증한 경우에만 입력·출력 파일의 실제 경로·수정 시각, 입력 식별 정보, 실행 시각, 최종 슬라이드 수, 사용한 renderer/버전, 슬라이드·객체 식별자, 측정값과 단위, 검사 방법·판정·근거를 과정의 `checks/` 폴더(`courses/<course>/checks/[basename]-production-check.md`)에 남긴다. `sessions/`에는 Session Source와 그 산출물(`.pptx`·`.qa.json`)만 둔다 — 검토 기록을 원고 옆에 두면 `--check courses/<course>/sessions/s*.md`가 그 파일을 원고로 읽고 중단한다. 렌더 증거를 저장했다면 실제 경로를 기록한다. 확인하지 않은 경로나 승인 상태를 지어내지 않는다.

## Session Authoring으로의 원고 보완 피드백

Production 검증에서 원고의 **내용·도식 구조·표기법**을 검토해야 하는 문제가 발견되면, 사용자와 LLM의 Session Authoring 논의에 사용할 **별도의 Markdown 피드백 문서**를 제공한다. 이 문서는 원고 수정 지시나 에이전트 간 자동 전달 절차가 아니다.

피드백 파일도 과정의 `checks/` 폴더에 `[basename]-feedback.md`로 생성한다. 예: `s02.md` → `s02-feedback.md`. 다른 세션의 피드백과 합치지 않는다. 재검토 시 해결·미해결 상태와 검토 시점을 갱신하며 수동 기록을 묵시적으로 덮어쓰지 않는다. 실행·렌더 검증 기록인 `[basename]-production-check.md`와 역할을 구분한다.

- 관련 Session Source, topic 번호·제목 및 해당 슬라이드(확인 가능한 경우)
- 발견된 문제, 판단 근거와 학습 내용·가독성에 미치는 영향
- Production 내부의 배치·크기·글꼴 조정으로 해결할 수 없는 이유 및 검토 가능한 대안
- 확인되지 않은 사항은 단정하지 않고 `NOT VERIFIED`로 표시

**사용자와 LLM이** 콘텐츠의 의미와 학습 목적을 기준으로 Session Source의 수정 여부를 결정한다. Production은 원고를 임의 수정하지 않는다. Production 자체의 렌더링·배치·글꼴 문제는 Production에서 해결하며 원고 보완 요청으로 전가하지 않는다. 원고 보완 항목이 없다면 빈 피드백 문서를 만들지 않는다.

## Regression

공통 렌더러를 변경하면 전체 고정 fixture 테스트와 범위 밖 대표 세션의 출력 회귀를 함께 확인한다. 대표 세션은 임시 출력으로 생성해 기존 정식 산출물을 덮어쓰지 않고, 기본값·본문·표·도식의 내용과 서식을 검사한다. 과정별 예외가 같은 세션명을 쓰는 다른 과정에 적용되지 않는지도 fixture로 확인한다.

회귀는 테스트로 막는다. 참조 폴더나 예전 PPT와 눈으로 비교하는 것은 회귀 검증이 아니다.

- renderer를 바꾸면 `node --test src/test/*.test.js` 전체를 통과시킨다. 이 테스트는 이식 원본(lecture-ppt-java)의 원고(`src/test/fixtures/lecture-java-baseline/input.md`), 고정 fixture 세션(`src/test/fixtures/reference-session.md`)의 렌더 결과와 템플릿을 함께 지킨다.
- 결함을 고치면 그 결함을 재현하는 테스트를 함께 추가한다. 다음 수정이 같은 결함을 되살리면 테스트가 실패해야 한다.
- 테스트가 실패하면 기대값을 고쳐 통과시키기 전에, 그 테스트가 지키는 지침 규칙이 바뀌었는지 확인한다. 규칙이 그대로면 코드를 고친다. 규칙을 바꾼다면 지침·코드·테스트를 함께 고친다.
- **테스트는 한 사례가 아니라 그 종류의 전부를 본다.** 칸 하나·장 하나만 확인하는 테스트는 나머지가 빠져도 통과한다 — 표의 맞춤이라면 fixture의 **모든 칸**을 세고(`a:tc` 수 = `a:tcPr` 수), 속성이 원형에 기대는 자리는 **원형에 없을 때도** 붙는지 본다.
- **지침에 없는 계약은 지켜지지 않는다.** 코드의 주석이 지침의 한 절을 가리키면 그 절에 그 규칙이 실제로 적혀 있어야 한다. 적히지 않은 결정은 다음 수정에서 근거 없이 사라진다.
