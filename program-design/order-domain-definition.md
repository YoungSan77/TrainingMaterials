# 예제 도메인 정의 — 쇼핑몰 주문(Order)

## 1. 목적과 위상
- 이 문서는 전 과정이 공유하는 **고정 예제 도메인**을 정의한다.
- 아키텍처는 스파게티 → TS → 리치 도메인으로 바뀌지만, 이 도메인 명세는 바뀌지 않는다. 변하는 것은 "이 규칙을 어디에 두는가"이지 "규칙이 무엇인가"가 아니다.
- 따라서 이 문서에는 **구현·패턴 언급을 넣지 않는다**(레이어 규약과 각 패턴 문서의 몫). 여기서는 업무 규칙만 기술한다.

## 2. 범위
- 대상: 주문(Order) 애그리거트 하나와 그 상태 전이, 직접 규칙.
- 협력자: 결제·재고·배송은 **경계 밖 협력자**로만 참조한다(포트).
- 범위 밖(명시적 제외): 상품 카탈로그, 장바구니, 회원, 결제 수단 내부 처리, 배송 추적, 정산·영수증.
- 제외 이유: 슬라이스를 넘으면 도메인의 우발 복잡도가 아키텍처 패턴을 덮는다.

## 3. 유비쿼터스 용어
| 용어 | 뜻 |
|---|---|
| Order | 한 고객의 한 번 주문. 애그리거트 루트. |
| OrderLine | 주문 안의 품목 한 줄(상품·수량·단가). |
| Money | 금액 값. 통화·정밀도를 가진 값 객체. |
| Quantity | 수량 값. 1 이상 정수. |
| OrderStatus | 주문의 현재 상태. |
| Customer | 주문의 소유 주체. 식별자만 참조(상세는 범위 밖). |

## 4. 애그리거트 경계
- 루트: Order.
- 내부 구성: OrderLine(다수), Money·Quantity(값 객체).
- 불변식 성립 경계: 5절의 규칙은 **Order를 통해서만** 변경될 때 항상 성립해야 한다. OrderLine을 외부에서 직접 바꾸는 경로는 없다.
- 식별: Order는 전역 식별자(OrderId)를 가진다. OrderLine은 Order 내부에서만 의미를 가진다.

## 5. 비즈니스 규칙·불변식
각 규칙은 번호로 참조한다(코드·문서에서 R1 등으로 인용).

- **R1 합계**: 주문 총액 = Σ(라인 단가 × 라인 수량).
- **R2 수량**: 모든 라인 수량 ≥ 1.
- **R3 최소 구성**: 주문은 라인을 최소 1개 가진다(빈 주문 불가).
- **R4 변경 시점**: 라인 추가·수정·삭제는 PENDING 상태에서만 허용한다.
- **R5 취소 조건**: 취소는 SHIPPED 이전 상태에서만 허용한다.
- **R6 전이 규칙**: 상태 전이는 6절 전이표에 정의된 것만 허용한다(그 외 전이는 거부).
- **R7 결제 선행**: PAID를 거치지 않고 SHIPPED로 갈 수 없다(R6에 포함되나 강조).

## 6. 상태 머신
- 상태: PENDING, PAID, SHIPPED, DELIVERED, CANCELLED.
- 허용 전이:

| From | Event | To |
|---|---|---|
| PENDING | 결제 완료 | PAID |
| PENDING | 취소 | CANCELLED |
| PAID | 배송 시작 | SHIPPED |
| PAID | 취소 | CANCELLED |
| SHIPPED | 배송 완료 | DELIVERED |

- 표에 없는 전이는 모두 불법이며 거부한다(R6).
- DELIVERED·CANCELLED는 종료 상태(이후 전이 없음).

## 7. 유스케이스 (얇게)
- 이 목록이 곧 TS 단계의 스크립트 단위이자, 리치 단계의 유스케이스 인터랙터 단위다.
- PlaceOrder(주문 생성), AddOrderLine(라인 추가), Pay(결제 처리), Ship(배송 시작), CompleteDelivery(배송 완료), CancelOrder(취소).
- 각 유스케이스는 하나 이상의 규칙(R1~R7)과 하나의 상태 전이에 대응한다.

## 8. 협력자(포트)
주문은 아래를 **결과만** 알고, 내부 처리는 모른다.

| 포트 | 책임 | 주문이 아는 것 / 모르는 것 |
|---|---|---|
| PaymentPort | 결제 요청·결과 | "결제됨/실패"만 안다. 결제 수단·PG는 모른다. |
| InventoryPort | 재고 확인·차감 | "차감 성공/부족"만 안다. 창고 로직은 모른다. |
| ShippingPort | 배송 지시 | "배송 시작됨"만 안다. 운송사·경로는 모른다. |
| OrderRepository | 주문 영속화·조회 | 저장·복원 계약만 안다. DB·ORM은 모른다. |

- 이 포트들은 MSA 단계(IV)에서 각각 별도 서비스 경계 후보가 된다.
- **협력자 실패 경계(확정)**: 결제 실패·재고 부족 등 외부 상호작용의 실패는 **유스케이스가 처리**한다. 도메인(Order)은 그 결과를 받아 **전이만** 소유한다 — `markPaid()`/`markPaymentFailed()`(R6·R7). 근거: 실패는 Order의 불변식이 아니라 외부 상호작용의 결과다. 판단(외부 실패 대응)=유스케이스, 상태 불변식(전이 정당성)=도메인. 규칙 누수가 아니라 역할 분리.
