# DDD 전술 개념 강의 소스 (교시 15~16 정본)

> 교시 15~16(DDD 전술 개념 개관)의 내용 정본. Code는 이 소스로 덱을 생성한다 — 즉석 생성 금지.
> 이 교시는 **개념 소개**다(craft·깊은 모델링은 DDD 1일 과정 소유). 여기선 탈신비화 + 한계로 DDD 과정을 부르는 복선까지.
> 서술 원칙: 각 개념을 **3단 탈신비화**로 연다 — ①개발자가 이미 풀던 문제 → ②이름 없어 일관성 없던 것 → ③에반스의 명명·패턴화. 새 이론 암기가 아니라 "이미 하던 걸 이렇게 부른다".
> 계보: Larman(OOAD)이 안 다룬 것을 에반스가 얹었다. 이 교시가 그 이음매.

---

## A. 도입 — 왜 전술 개념인가 (탈신비화 선언)
- RDD·GRASP는 "책임을 어디 둘까"까지 줬다. 그러나 **"무엇을 하나의 모델 단위·경계로 볼까"**는 안 줬다 — 이 공백을 에반스가 메웠다.
- 핵심 프레임: 이 개념들은 **새 발명이 아니다.** 개발자들은 이 문제들을 이미 풀어왔다 — 다만 이름이 없어 **패턴화가 안 됐고 일관성이 없었다.** 에반스가 명명·정리했다.
- 그래서 "용어는 새로워도 문제는 오래된 것"(프로그램 명제)의 실물이 이 교시다.

---

## B. VO (Value Object) — 깊게

### 탈신비화 3단
1. **이미 풀던 문제**: 돈·수량·좌표·기간 — 식별자 없이 값 자체로 의미를 갖는 것들. 개발자는 늘 다뤘다.
2. **이름 없어 일관성 없던 것**: 어떤 팀은 원시 타입(int money), 어떤 팀은 공통 모듈·유틸리티로. 값 동등성·불변을 매번 제각각 재발명 — 일관성 없음.
3. **명명·패턴화**: 에반스가 "Value Object"로 명명 — **식별자 없음·값 동등성·불변**을 한 개념으로.

### 문제·추론
- Money를 `int`로 다루면? 통화 혼동·반올림 오류·의미 없는 연산(주문번호+금액)이 컴파일된다. 규칙(R1 합계)이 원시 타입엔 못 산다.
```java
final class Money {                     // VO: 불변·값 동등성
    private final long cents; private final Currency currency;
    Money add(Money o) { requireSameCurrency(o); return new Money(cents + o.cents, currency); }
    boolean equals(Object o) { /* 값으로 비교 */ }
}
```
- **왜 VO인가**: 값에 규칙을 붙일 자리가 생긴다(같은 통화만 더함). Quantity도 VO — R2(수량≥1)를 생성자가 강제.

### 한계
- 모든 것을 VO로 만들면 과잉이다 — 식별자로 추적해야 하는 것(주문·고객)은 Entity다. VO/Entity 구분이 다음 판단.

## C. Aggregate — 깊게 (이 교시의 핵심)

### 탈신비화 3단
1. **이미 풀던 문제**: 연관된 데이터를 한 트랜잭션으로 함께 저장·변경하는 것. 주문과 주문라인은 따로 저장하면 깨진다 — 개발자는 늘 "이건 같이 묶어야 해"를 감으로 해왔다.
2. **이름 없어 일관성 없던 것**: 어디까지 한 단위인지, 누가 그 단위의 규칙을 지키는지 기준이 없었다. 팀마다·개발자마다 경계가 달라 일관성 없음.
3. **명명·패턴화**: 에반스가 "Aggregate"로 명명 — **불변식을 공유하는 객체 묶음, 하나의 루트를 통해서만 접근, 트랜잭션 일관성 경계.**

### 문제·추론 (경계를 무엇이 정하나)
- Order와 OrderLine: R1(합계=Σ라인)·R3(최소 1라인)은 **Order 내부 불변식** → 한 트랜잭션에 즉시 지켜져야 → **Order가 애그리거트, OrderLine은 그 안.**
- "재고 ≥ 주문량"은 Order·Inventory에 걸침 → 즉시가 아니라 결과적 → **애그리거트 밖(최종 일관성).**
- → **불변식이 경계를 정한다.** 즉시 지켜야 할 규칙이 한 애그리거트 안, 결과적이면 밖.
```java
class Order {                          // Aggregate Root
    private List<OrderLine> lines;     // 루트를 통해서만 접근
    void addLine(...) { /* R4 강제 */ }// 외부가 lines를 직접 못 만짐
    Money total() { /* R1 */ }
}
```

### 한계 (DDD 과정을 부르는 복선)
- **경계를 어디 긋느냐가 진짜 어려운 판단이다.** 크게 잡으면 경합, 작게 잡으면 교차 규칙 비용. 이 소개에선 "불변식이 경계를 정한다"까지만 — **실제 경계 설계(이벤트 스토밍·트레이드오프 워크숍)는 DDD 1일 과정이 판다.**
- 여기서 학습자가 "아 이게 어렵겠다"를 느껴야 DDD 과정의 동기가 산다.

## D. Service · Repository — 중간

### Domain Service (탈신비화 + 한계)
1. 이미 풀던 문제: 특정 도메인 객체에 넣기 애매한 연산(예: 두 계좌 간 이체 — 어느 계좌의 메서드?). AOP가 횡단 관심사를 뺐듯, 애매한 도메인 로직을 별도 영역으로.
2. 이름 없어: 억지로 어느 객체에 욱여넣거나 유틸에 흩뿌림.
3. 명명: **Domain Service** — 도메인 로직이지만 한 엔티티/VO에 안 맞는 것. 무상태.
- **한계·재정박 복선**: Domain Service(도메인 층)와 Application Service(유스케이스 층)는 다르다 — **이 구분은 아키텍처 과정에서 재정박된다**(forward-ref, DS≠AS).

### Repository (탈신비화 + 한계)
1. 이미 풀던 문제: 객체를 저장·조회. DAO·매퍼로 늘 해왔다.
2. 이름 없어: 도메인이 SQL·연결을 직접 알거나(결합), 계층이 제각각.
3. 명명: **Repository** — 애그리거트를 마치 메모리 컬렉션처럼 다루는 인터페이스. 영속성을 도메인 뒤로 숨김.
- **한계·복선**: Repository 인터페이스/구현 분리와 레이어링은 **아키텍처 과정이 확정한다**(forward-ref).

## E. Entity · Factory — 개념만
- **Entity**: 식별자로 추적되는 것(VO의 반대). 값이 바뀌어도 같은 것. OO 기초·Order 소개에서 이미 닿음 — 여기선 VO와의 대비로 한 줄.
- **Factory**: 복잡한 애그리거트 생성을 캡슐화. **GRASP Creator의 한계가 부른 것**(교시 9에서 이미 복선) — Creator가 억지가 될 때 Factory. 한 줄로 연결만.

---

## F. 닫기 — 계보와 복선
- 이 여섯(Entity·VO·Aggregate·Service·Repository·Factory)이 Larman이 안 준, 에반스가 얹은 것이다. **개발자가 이미 하던 걸 명명·패턴화해 일관성을 줬다.**
- **한계 총괄**: 여기선 개념을 *알았을* 뿐이다. 이것들을 손으로 *설계*하는 것 — 경계를 긋고 불변식을 배치하는 craft — 는 DDD 1일 과정이 판다. OOAD는 전술 개념 소유, DDD 과정은 craft.
- 이 복선이 DDD 과정의 입구가 된다: "개념은 배웠다. 이제 손으로 경계를 그어보자."

---

## 슬라이드 변환 지침
- 각 개념을 3단 탈신비화로 연다("이미 하던 것 → 이름 없던 것 → 명명"). 이게 걷돌지 않게 하는 핵심.
- VO·Aggregate는 각 2~3장(탈신비화+코드+한계), 특히 Aggregate의 "불변식이 경계를 정한다"를 codepair나 도표로. Service·Repository 각 1장, Entity·Factory 묶어 1장.
- 매 개념의 한계가 DDD 과정을 부르는 복선 — 반드시 남긴다. OOAD가 완벽하다고 닫지 않는다.
- 자세·명제는 canon-stance 참조(교시1 선언, 여기 반복 안 함).
- 15~16 두 교시 분량. 넘치면 조정은 OOAD 완성 후 일괄(번호·시수 정리 때).
