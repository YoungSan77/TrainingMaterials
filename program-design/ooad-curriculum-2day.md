# OOAD 과정 목차 (2일 · 16교시)

## 과정 개요
- 소유: OO 기초 · 요구사항→모델(분석 진입) · 책임 할당·GRASP · SOLID · TDD · 결합/응집(객체 수준) · DDD 전술 **개념**(Entity·VO·Aggregate·Domain Service·Repository·Factory).
- 전제: 없음(프로그램 출발점, 대상 OO 얕음). 후행: SW 아키텍처의 강제 선수.
- 산출: 아키텍처가 전제하는 OOD·DIP·DDD 전술 개념 역량 + 분석(요구사항·정적·동적 모델).
- 도메인: Order(여기서 첫 소개). 편성: 50분 교시+10분 휴식, 무게 기반, 실습 가이드형.
- **경계**: DDD 전술은 여기서 *개념*까지. 모델링 craft(이벤트 스토밍·애그리거트 경계 설계·컨텍스트 매핑)는 DDD 1일 과정 소유. 애그리거트는 OOAD(개념)→아키텍처 리치(적용)→DDD 과정(craft)으로 간격 반복.

## 프로그램 자세 (1교시에서 선언 — 정본: canon-stance.md)
- `stance.necessary-evil`: 완벽한 코드가 가능하면 분석·아키텍처·설계·테스트는 불필요하다. 불가능하기에 도입된 보정이다. 목적에 맞게 아는 채로 하면 도움, 모르거나 지나치면 필요악(순수 오버헤드). 악이 되는 건 도구가 아니라 오용(무지·과잉).
- `stance.just-enough`: 사전 활동은 코드가 요구하는 만큼만. 모자라면 부채가 쌓이고(무지), 넘치면 그 자체가 부채다(과잉). 반복점진·프로토타이핑으로 나머지는 코드로 배운다(BDUF 아님).
- `stance.prevent-repay`: 사전(분석·설계·아키·테스트) = 부채 예방 / 사후(유지보수 리팩토링) = 부채 상환. 서론의 자세는 예방.

## 아키텍처로 넘기는 forward-ref (여기서 플래그만, 아키텍처가 재정박)
- DIP → 의존성 규칙.
- Domain Service ≠ Application Service.
- Repository 개념 → 레이어링.
