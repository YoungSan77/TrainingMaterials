# OOAD 실습 설계

## 위상
- 아키텍처 실습 형식의 복제(3층 · (a)기본/(b)보강 · 코더 빈칸). 렌즈 = **책임 이동**(규칙 이동이 아니라 절차 → 객체 협력).
- Order 공유. 코드는 핵심 로직만.

## 렌즈 차이 (아키텍처와 무엇이 다른가)
- 아키텍처: 규칙이 **레이어를 가로질러** 이동(서비스→도메인). 축 = 의존 방향.
- OOAD: 로직이 **절차에서 객체로** 이동. 축 = 책임 배치. 아직 레이어·의존성 규칙은 안 본다(forward-ref만).

## 부 1 · 분석 진입 — 코드보다 앞
- (a) 대면 = **요구사항 문장 vs 유스케이스 vs 유저 스토리** 세 표현 비교. "같은 요구를 어떻게 담나".
- BDD: 유스케이스 하나(주문 취소)를 **Given-When-Then**으로. R6 전이를 시나리오로. 이게 부5 애그리거트 실습에서 규칙 검증에 재사용된다(고아 방지).

## 부 3 · 책임 주도 설계 (GRASP) — 핵심 실습

### (a) 스니펫 쌍 · 책임이 어디로 갔나

**쌍 O-1 · 합계 계산의 책임**
```java
// 절차적 — 바깥 코드가 데이터를 헤집는다
Money total = Money.ZERO;
for (var line : order.getLines())                  // 남의 데이터를 순회
    total = total.add(line.getPrice().times(line.getQty()));
```
```java
// 객체 — 정보 전문가(Information Expert)가 스스로 계산
Money total = order.total();                       // 데이터를 가진 자가 책임
// Order.total(): lines가 스스로 subtotal을 알고 합산
```
짚기: 계산 책임이 **바깥 절차 → 데이터를 가진 객체**로. GRASP Information Expert. (규칙 위치가 아니라 책임 위치)

**쌍 O-2 · 생성의 책임** — 절차: 바깥에서 `new OrderLine` 조립 → 객체: `Order.addLine`이 생성·검증 소유(Creator).

**쌍 O-3 · 결합/응집** — 절차: 한 클래스가 주문·결제·배송을 다 안다(저응집·고결합) → 객체: 책임을 나눠 협력(Low Coupling·High Cohesion).

### (b) 통짜 대조 (2벌) · 유스케이스 = PlaceOrder
- 절차 버전(모든 로직이 한 서비스 함수) vs 객체 협력 버전(Order·OrderLine·Money가 나눠 가짐).
- 물음: 요구가 바뀔 때(예: 라인 할인 추가) 어느 버전이 덜 흔들리나.

## 부 5 · DDD 전술 (개념)
- (a) = **빈혈 vs 리치** 한 쌍. 게터·세터만 있는 Order(로직은 밖) vs 행위를 가진 Order. "엔티티에 행위가 있나" 손가락으로.
- 깊은 애그리거트 모델링은 안 함(DDD 과정 소유). 여기선 개념 대조까지.

## 코더 층
- (a): 절차 코드를 주고 **객체 메서드로 옮기는 빈칸**. 예 — `Order.total()` 몸통 채우기.
- (b): PlaceOrder 절차 버전을 객체 협력으로 리팩터링.

## forward-ref (플래그만)
- 이 실습들이 "규칙을 객체 안으로" 옮기지만, **왜 그게 의존성 규칙이 되는지는 아키텍처**에서. DIP·DS≠AS·Repository 레이어링은 여기서 다루지 않는다.
