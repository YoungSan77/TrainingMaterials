# 정적 모델 강의 소스 (OOA · 정적 모델 · 약 2.5시간 · 5차 · 나선형 재구성)

> 정적 모델(개념 모델) 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 5차 재구성 사유: 4차까지 순서가 뒤죽박죽(개념 클래스 정의가 표기 뒤에), 클래스 다이어그램 작성 설명 없이 연관 표기에서 완성 다이어그램으로 비약, 클래스 박스 세 칸 설명 부재. 이번엔 흐름을 먼저 정의하고 그 순서로 재구성한다.
> 구성 원리 = Larman의 반복·점진(iterative & incremental, i&i): 각 개념을 한 곳에서 완결하지 않고 여러 주기에 걸쳐 다시 방문하며 심화한다. 반복은 나쁜 중복이 아니라 의도된 심화다.
> 깊이 = Larman 'Applying UML and Patterns' 책 수준. 슬라이드는 그 책의 축약본.
> 층 경계: OOA다. 책임 배치(RDD·GRASP)는 OOD — 한 글자도 안 넣는다. 설명·워크스루=NewPOS, 실습=Order. 한글(영어) 표기. 의문형 물음표. 원작자(Larman) 하단.

## 원작자·출전
- 도메인 모델(Domain Model): Craig Larman (Applying UML and Patterns, 3rd ed.)
- UML 표기: OMG UML 표준

## 1주기 — 무엇을 그리나 (개념 먼저, 얕게 전체 그림)
═══════════════════════════════════════════

### 1-1. 정적 모델·개념 모델이란
- OOA는 도메인을 두 그림으로 본다 — 정적 모델(무엇이 존재하는가: 개념·구조), 동적 모델(무엇이 일어나는가: 행위·시간). 이 강의는 정적.
- 산물 = 개념 모델(Domain Model, 도메인 모델): 문제 영역에 무엇이 존재하고 어떻게 관계 맺는지 그린 그림.
- 개념 모델은 소프트웨어 설계가 아니라 현실의 개념을 그린다. 연산(메서드)이 없다 — 그러나 속성(자료)은 있다. 가시성·타입 세부는 "없다"가 아니라 "아직 정하지 않는다"(설계의 몫).
- 왜 개념부터인가? 구현을 먼저 생각하면 편의가 도메인 이해를 오염시킨다. 먼저 정직하게 이해하고, 그다음 설계로.

### 1-2. 개념 클래스란 무엇인가 (정의 — 표기보다 먼저)
- 개념 클래스(Conceptual Class): 도메인에 실재하는 개념 — 사물·역할·사건·명세. 소프트웨어 객체가 아니라 현실의 명사.
- 유형: 물리적 사물(상품), 역할(고객·계산원), 사건(판매·지불), 명세(상품 명세), 목록/장부(상품 목록).
- 이 강의에서 그릴 것 = 이런 개념 클래스들과 그 관계. "무엇을 그리나"의 답이 개념 클래스다.

### 1-3. 개념 모델의 큰 그림 (미리보기)
- [uml] NewPOS 개념 모델 완성본을 여기서 한 번 크게 보여준다(미리보기) — "이 강의가 끝나면 이걸 스스로 그린다". 세부는 아직, 전체 모습만.
- 이 미리보기가 나침반 — 이후 주기가 이걸 향해 심화된다.

## 2주기 — 어떻게 표기하나 (표기법 + 개념 다시 심화)
═══════════════════════════════════════════

### 2-1. 클래스 박스 (기본 — 빠뜨리면 안 됨)
- 클래스는 세 칸 박스로 그린다:
  - 맨 위: 클래스 이름
  - 가운데: 속성(attribute) — 이름, 그리고 데이터 타입(예: price: Money, quantity: int)
  - 맨 아래: 연산(operation, 메서드)
- 분석(OOA)에서는 연산 칸을 정의하지 않는다 — 연산(행위)은 설계(OOD)의 몫. 개념 모델의 박스는 이름 + 속성만 채운다.
- 속성의 데이터 타입: 분석 단계에선 개념적 타입(금액·수량·날짜)까지. 구현 타입(BigDecimal 등)은 설계에서.
- [uml] Sale 박스(이름 / dateTime: Date / <연산 칸 비움>), SalesLineItem(이름 / quantity: int / 비움) — 세 칸 구조를 크게, 각 칸 라벨.
- 훈련: "총액을 계산한다"는 어느 칸? (연산 — 개념 모델엔 아직 없음)

### 2-2. 연관 (Association)
- 두 개념을 선으로 잇고 관계 이름을 붙인다. 선 = "의미 있게 관계 맺는다".
- 방향/역할: 관계 이름은 동사구. 읽는 방향을 삼각형으로 표시할 수 있다.
- 종류 예: 포함(Sale가 SalesLineItem을 포함), 참조(SalesLineItem이 ProductDescription을 참조).
- [uml] 두 연관 모두 표기: Sale --> SalesLineItem : 포함 / SalesLineItem --> ProductDescription : 참조 (설명한 포함·참조 둘 다 다이어그램에 — 말과 그림 일치)
- 훈련: "계산원이 판매를 기록한다"의 연관은? (Register --> Sale : 기록)

### 2-3. 다중도 (Multiplicity) — 표로
- 연관선 양 끝에 개수 규칙을 적는다:

| 표기 | 뜻 |
|---|---|
| 1 | 정확히 하나 |
| 0..1 | 없거나 하나 (선택적) |
| 1..* | 하나 이상 (상한 없음) |
| * (=0..*) | 0개 이상 (없어도 됨) |
| 2..5 | 2개에서 5개 (범위) |

- 핵심: *(="0개 이상", 없어도 됨) vs 1..*(="하나 이상", 최소 하나). 이 차이가 규칙을 가른다.
- 읽는 법(양 끝 함께): Sale "1" -- "1..*" SalesLineItem → "판매 하나에 항목 하나 이상, 항목 하나는 판매 하나에".
- [uml] Sale "1" -- "1..*" SalesLineItem : 포함

### 2-4. 다중도가 규칙을 드러낸다 (심화)
- "1..*"는 곧 도메인 규칙 "판매는 최소 한 항목을 가져야 한다"? 다중도가 불변식을 미리 드러낸다.
- 훈련: "*"(0개 이상)로 바꾸면 빈 판매를 허용하게 된다. 도메인이 빈 판매를 원하는가? 다중도를 정하는 것이 규칙을 정하는 것.
- (규칙이 코드 어디서 지켜지나는 설계·DDD 몫 — 여기선 "드러난다"까지.)

### 2-5. 속성 (Attribute) — 그리고 개념 클래스 다시 (2번째 방문)
- 속성: 개념이 갖는 단순 값. Sale.dateTime, SalesLineItem.quantity.
- 속성인가, 별도 개념 클래스인가? (개념 클래스를 여기서 다시 만난다, 심화)
  - 규칙: 단순 값은 속성. 자기 속성·관계를 갖는 독립 개념은 별도 클래스 + 연관.
  - price를 SalesLineItem 속성으로? 아니다 — 가격은 "상품이 무엇인가"에 속하므로 ProductDescription으로.
  - 고객 주소는? 단일 문자열이면 속성, 나뉘고 이력 가지면 개념 — 도메인이 정한다.
  - 판단 신호: "자기만의 속성·관계를 갖는가?" Yes=개념, No=속성.

### 2-6. 누락하기 쉬운 개념 클래스 — 명세 개념 (개념 클래스 3번째 방문, 심화)
- 명세 개념은 함정이 아니라 초보가 빠뜨리기 쉬운 전형적 개념 클래스다.
- 물리적 상품(한 개)과 "그 상품이 무엇인가"(명세: 이름·가격·바코드)는 다르다. 재고 0이어도 명세·가격은 존재해야 한다 → 상품 명세(ProductDescription)를 별도 개념으로.
- 놓치면 "재고 0이면 가격도 사라지는" 잘못된 모델. 물리적 사물만 보고 명세를 빠뜨리는 게 흔한 누락.
- 훈련: "메뉴판의 김치찌개"와 "나온 김치찌개 한 그릇"은 같은 개념인가? (명세 vs 물리적 인스턴스 — 다른 개념)

## 3주기 — 어떻게 그리나 (작성법 + 전부 다시, 실전 심화)
═══════════════════════════════════════════

### 3-1. 클래스 다이어그램 작성 절차 (비약 제거 — 이 설명이 그동안 빠졌다)
- 개별 표기(박스·연관·다중도)를 배웠으니, 이제 하나의 다이어그램으로 조립하는 절차:
  1. 개념 클래스 찾기 — 요구/유스케이스 서술의 명사구 추출 → 거르기(속성일 뿐인 것·중복·시스템/UI 용어 제거, 애매하면 다음 반복으로)
  2. 박스로 놓기 (이름 + 속성)
  3. 연관 긋기 (관계 이름)
  4. 다중도 정하기 (규칙 결정)
  5. 속성 채우기 (타입 포함)
- 이 절차 없이 표기에서 완성 다이어그램으로 건너뛰면 수강생이 못 따라온다 — 절차를 먼저 세우고 워크스루로.

### 3-2. 워크스루 — NewPOS Process Sale (절차를 실제로 밟는다)
> 완성본 감상이 아니라, 유스케이스에서 절차대로 개념 모델을 만들어간다. 각 단계를 다이어그램으로 점진 구축.

- 출발 유스케이스: "고객이 상품들을 계산대로 가져온다. 계산원이 각 상품의 항목을 입력한다. 시스템이 항목별 소계와 판매 총액을 계산한다. 고객이 지불한다."
- 단계 1 — 명사구 추출: 고객·상품·계산대·계산원·항목·소계·판매·총액·지불. [원문에 밑줄]
- 단계 2 — 거르기: 소계·총액=계산된 값(속성/파생, 개념 아님). 상품→물리적 vs 명세로 갈림(2-6)→ProductDescription. 남는 개념: Sale·SalesLineItem·ProductDescription·Payment. [uml: 박스만]
- 단계 3 — 연관 긋기: Sale--SalesLineItem:포함, SalesLineItem--ProductDescription:참조, Sale--Payment:지불됨. [uml: 연관, 다중도 아직]
- 단계 4 — 다중도: Sale"1"-"1..*"SalesLineItem(빈 판매 불허), SalesLineItem"*"-"1"ProductDescription, Sale"1"-"1"Payment. [uml: 다중도 붙임]
- 단계 5 — 속성 채우기: Sale(dateTime), SalesLineItem(quantity), ProductDescription(itemID·price·description), Payment(amount). [uml: 완성본, 크게]
- 완성 다이어그램을 1-3 미리보기와 나란히: "한 문단에서 여기까지 — 이게 개념 모델 작성이다."

## 4주기 — 왜 중요한가 (개념 모델 → 코드, 또 다른 각도)
═══════════════════════════════════════════

### 4-1. 세 단계 진화
- 개념 모델(OOA): 개념·관계·속성 → 설계 클래스 모델(OOD): 연산(책임)·가시성·타입 붙임 → 코드.
- 이 강의는 첫 단계까지. 그러나 어디로 가는지 보여준다.

### 4-2. 구조는 코드로 곧장 매핑 (규칙 + codepair)
- 개념 클래스→클래스, 속성→필드, "1" 연관→참조, "1..*"→컬렉션.
- [codepair] 왼쪽=완성 개념 모델(다이어그램 요지), 오른쪽=코드 골격:
  class Sale { Date dateTime; List<SalesLineItem> lines; /* 연산 없음 — OOD에서 채움 */ }
  class SalesLineItem { int quantity; ProductDescription description; }
  class ProductDescription { String itemID; Money price; String description; }
- 구조는 개념 모델에서 왔고 곧 코드다. 연산(행위)은 비어 있다 — OOA/OOD 경계가 코드에서도 보인다.

### 4-3. 그래서 개념 모델이 중요하다
- 개념 모델이 정확하면 코드 골격이 정확. 명세 개념을 놓치면(상품/명세 안 나누면) 코드도 틀린다.
- "지금 그리는 이 다이어그램이 코드의 뼈대다. 대충 그리면 코드가 뒤틀린다."

## 5주기 — 닫기 (동적 모델·설계로 복선)
═══════════════════════════════════════════
- 정적 모델은 "무엇이 있나"를 줬다. "유스케이스 실행 시 이 개념들이 어떤 순서로 협력하는가?"는 동적 모델(다음: 유스케이스·시퀀스·협업·상태 다이어그램).
- 개념에 책임(연산)을 배치해 설계 클래스로 만드는 것은 OOD 몫 — 여기 심은 개념 모델이 그 입력.

## 슬라이드 변환 지침
- 순서 엄수(나선형): 1주기(개념 클래스 정의를 표기보다 먼저) → 2주기(표기, 개념 재방문) → 3주기(작성 절차 먼저, 그다음 워크스루) → 4주기(코드) → 5주기(닫기). 개념 클래스 정의가 앞에 온다.
- 비약 제거: 3-1 작성 절차를 워크스루 앞에 반드시. 표기에서 완성 다이어그램으로 건너뛰지 마라.
- 클래스 박스 세 칸(이름/속성/연산, 분석선 연산 비움, 속성 타입) 반드시 설명(2-1).
- 말과 그림 일치: 연관에서 포함·참조 둘 다 설명하면 다이어그램에도 둘 다(2-2).
- 반복은 심화로: 개념 클래스가 1-2, 2-5, 2-6, 3-2에서 매번 깊어진다(i&i). 중복 아님.
- 다이어그램 uml 타입, 크게(하단 잘림 없이). 다중도 표. 의문형 물음표. 한글(영어). 원작자(Larman) 하단.
- RDD·GRASP 금지(OOA). 깊이는 Larman 책 수준(축약본). 실습=Order(별도).
- 미심한 부분은 pptx 생성 후 확인해 보완.
