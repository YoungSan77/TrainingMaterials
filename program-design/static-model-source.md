## A. 정적 모델이란 무엇인가
### A-1. 두 모델 축
- 객체 분석은 두 축으로 본다 — **정적 모델(무엇이 있는가: 개념·구조)**과 **동적 모델(무엇이 일어나는가: 행위·시간)**. 이 교시는 정적.
- 정적 모델의 산물: **개념 모델(Domain Model) → 클래스 모델**. 도메인의 개념과 관계를 먼저 그리고(분석), 그것을 설계 클래스로 정련한다(설계).

### A-2. 개념 모델 vs 클래스 모델 (핵심 구분)
- **개념 모델(Conceptual/Domain Model)**: 문제 영역의 **개념**을 그린다 — 소프트웨어가 아니라 현실의 명사들. 메서드·가시성이 없다. "이 도메인에 무엇이 존재하고 어떻게 관계 맺나?"의 답.
- **클래스 모델(Design Class Model)**: 그 개념을 **소프트웨어 클래스**로 옮긴다 — 책임(메서드)·가시성·타입이 붙는다. RDD·GRASP가 여기서 책임을 배치한다.
- **왜 나누나?** 개념 모델은 도메인 이해(무엇), 클래스 모델은 해법 설계(어떻게). 섞으면 구현 편의가 도메인 이해를 오염시킨다. 개념을 먼저 정직하게 본 뒤 설계로 넘어간다.

## B. 개념 모델 (Domain Model) — Larman 프레임

### B-1. 개념 클래스 찾기
- **개념 클래스(Conceptual Class)**: 도메인의 명사 — 사물·역할·사건·명세. NewPOS에서: 판매(Sale)·판매 항목(SalesLineItem)·상품 명세(ProductDescription)·상품 목록(ProductCatalog)·계산대(Register)·지불(Payment).
- 찾는 법(Larman): 요구사항·유스케이스의 **명사구**에서 후보를 뽑고, 도메인에 실재하는 개념만 남긴다. (명사 추출은 출발점이지 기계적 규칙이 아니다 — 판단이 든다.)
- **명세 개념(주의점)**: ProductDescription은 왜 필요한가? 특정 상품 한 개(물리적 아이템)와 "그 상품이 무엇인지"(명세)는 다르다. 재고가 0이어도 상품 명세·가격은 존재해야 한다 → 명세를 별도 개념으로. 이게 "개념을 정직하게 본다"의 예다.

### B-2. 연관 (Association)
- **연관**: 개념 사이의 의미 있는 관계. Sale—포함—SalesLineItem, SalesLineItem—참조—ProductDescription.
- **다중도(multiplicity)**: 한 Sale에 SalesLineItem 1..*, 한 SalesLineItem에 ProductDescription 1. 관계의 개수 규칙을 명시한다.
- 왜 중요한가? 연관과 다중도가 **불변식의 자리**를 예고한다 — "판매는 최소 1개 항목"(1..*) 같은 규칙이 여기서 드러난다.

### B-3. 속성 (Attribute)
- **속성**: 개념이 갖는 값. Sale.dateTime, SalesLineItem.quantity, ProductDescription.price·itemID.
- **속성 vs 연관(판단)**: 어떤 것을 속성으로, 어떤 것을 연관된 개념으로? 원칙 — 단순 값(수량·날짜)은 속성, 그 자체가 개념인 것(상품 명세)은 별도 클래스+연관. price를 SalesLineItem 속성으로 두지 않고 ProductDescription으로 미는 이유가 이것.

```
[개념 모델 — 표기 예]
Sale ──1..*── SalesLineItem ──1── ProductDescription
 |dateTime         |quantity          |price, itemID
(메서드 없음 — 개념 수준)
```

### B-4. 한계
- 개념 모델은 **완전·정답이 아니다.** 도메인 이해의 도구이지 명세서가 아니다 — 반복(iteration)마다 다듬어진다. 처음부터 완벽을 추구하면 분석 마비.
- 개념 모델엔 책임(행위)이 없다. "누가 무엇을 하나"는 다음 단계(클래스 모델·GRASP)의 질문이다.

## C. 클래스 모델 (Design Class Model)
### C-1. 개념 → 클래스
- 개념 모델의 각 개념이 소프트웨어 클래스가 된다(전부는 아니다 — 일부는 설계에서 합쳐지거나 나뉜다).
- 붙는 것: **책임(메서드)**·가시성(±)·타입·방향 있는 연관(navigability).
- 책임은 어디서 오나? **RDD·GRASP.** getTotal은 Sale에(정보 전문가), makeLineItem은 Sale에(창조자) — 정적 모델과 GRASP가 여기서 만난다.
```java
class Sale {
    private LocalDateTime dateTime;
    private List<SalesLineItem> lines;   // 방향 있는 연관
    public Money getTotal() { ... }      // 책임 — GRASP가 배치
}
```

### C-2. 정적 모델의 값
- 클래스 모델은 코드의 골격이다 — 구조(무엇이 있고 어떻게 연결되나)를 코드 전에 합의한다.
- 그러나 구조만으론 부족하다 — **객체들이 시간에 따라 어떻게 협력하는가**는 안 보인다. 이것이 동적 모델의 몫.

---

## D. 닫기 — 동적 모델로 (다음 교시 복선)
- 정적 모델은 "무엇이 있는가"를 준다. 그러나 "유스케이스가 실행될 때 이 객체들이 어떤 순서로 메시지를 주고받는가?"는 답하지 못한다.
- 다음 교시(동적 모델): 유스케이스 → 시스템 시퀀스 다이어그램(SSD) → 상호작용 → 상태 머신. 정적 구조 위에서 행위가 흐른다.
- 정적·동적은 한 도메인의 두 그림자다 — 함께 봐야 설계가 선다.

- C(클래스 모델)는 개념→클래스 전환 + 책임이 RDD/GRASP에서 옴을 명시(교시9와 연결). codepair로 개념 모델 표기 vs 클래스 코드 대조 가능.
