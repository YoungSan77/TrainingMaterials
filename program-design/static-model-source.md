# 정적 모델 강의 소스 (OOA · 정적 모델 · 약 2.5시간 정본 · 재작성판)

> 정적 모델(개념 모델)의 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 재작성 사유: 초판이 각 개념을 정의 한 줄로 압축해 슬라이드가 개요 수준(낙제)이었다. 이번엔 **가르치는 밀도** — 각 개념마다 소개→NewPOS 예제→판단 훈련이 돈다. 개념당 여러 슬라이드가 정상.
> 시간: OOA(~5시간) 중 정적 모델이 가장 두껍다(~2.5시간). 요구사항~1h, 정적~2.5h, 동적~1.5h.
> **층 경계(엄수)**: 이것은 OOA(분석)다. 책임 배치(RDD·GRASP)는 OOD 영역 — 여기 한 글자도 안 들어간다. 개념 모델은 "무엇이 있나"까지. 책임(메서드)은 OOD에서 붙는다.
> 프레임: Larman 도메인 모델. 설명=NewPOS, 실습=Order. §8 한글(영어)·물음표. 원작자 하단(slide.origin).

## 원작자·출전
- 도메인 모델(Domain Model): Craig Larman (Applying UML and Patterns, 3rd ed.)
- UML 클래스 다이어그램 표기: OMG UML 표준

## A. 정적 모델이란 무엇이며 왜 그리는가
### A-1. 분석의 두 그림
- OOA는 도메인을 두 그림으로 본다 — **정적 모델(무엇이 존재하는가: 개념과 구조)**, **동적 모델(무엇이 일어나는가: 행위와 시간)**. 이 강의는 정적.
- 정적 모델의 산물 = **개념 모델(Domain Model)**: 문제 영역에 무엇이 존재하고 어떻게 관계 맺는지의 그림.

### A-2. 개념 모델은 코드가 아니다 (핵심 오해 제거)
- 개념 모델은 소프트웨어 설계가 아니라 **현실의 개념**을 그린다. 메서드도, 가시성도, 자료구조도 없다.
- 왜 이렇게 시작하나? 구현을 먼저 생각하면 편의가 도메인 이해를 오염시킨다. **먼저 도메인을 정직하게 이해하고**, 그다음 설계로 넘어간다. 개념 모델은 그 "정직한 이해"의 도구다.
- 이 강의가 답할 질문: 도메인에 어떤 개념이 있는가? 그것들은 어떻게 관계 맺는가? 그 관계에 어떤 규칙이 있는가?

---

## B. 개념 클래스 (Conceptual Class) — 도메인의 명사 찾기
### B-1. 개념 클래스란
- **개념 클래스**: 도메인에 실재하는 개념 — 사물·역할·사건·명세. 소프트웨어 객체가 아니라 현실의 명사.
- NewPOS 예: 판매(Sale)·판매 항목(SalesLineItem)·상품 명세(ProductDescription)·상품 목록(ProductCatalog)·계산대(Register)·지불(Payment).

### B-2. 어떻게 찾나 (절차 + 훈련)
- 출발점: 요구사항·유스케이스 서술의 **명사구**를 뽑는다. "고객이 여러 상품을 계산대에서 구매하고 지불한다" → 고객·상품·계산대·지불·구매(판매).
- 거르기: 명사라고 다 개념 클래스가 아니다. 속성일 뿐인 것(날짜·금액), 중복·모호한 것을 걸러낸다. **명사 추출은 출발점이지 기계적 규칙이 아니다 — 판단이 든다.**
- 훈련: 위 문장에서 "지불"은 개념인가 속성인가? (개념 — 지불 방식·금액·승인을 갖는 독립 개념) "여러"는? (다중도의 신호, 개념 아님)

### B-3. 함정 — 명세 개념 (Larman의 핵심 예)
- 문제: 상품 한 개(물리적 아이템)와 "그 상품이 무엇인가"(명세)는 같은가 다른가?
- 재고가 0이어도 상품의 가격·설명은 존재해야 한다. 물리적 아이템이 하나도 없어도 "이 상품은 무엇이고 얼마다"는 남는다 → **상품 명세(ProductDescription)를 별도 개념으로** 분리한다.
- 왜 중요한가? 이 구분을 놓치면 "재고 0이면 가격도 사라지는" 잘못된 모델이 된다. **개념을 정직하게 보는 것**이 이런 오류를 막는다. 이것이 개념 모델링이 단순 명사 나열이 아닌 이유다.

## C. 연관 (Association)과 다중도 (Multiplicity)
### C-1. 연관이란
- **연관**: 개념 사이의 의미 있는 관계. Sale과 SalesLineItem은 "포함", SalesLineItem과 ProductDescription은 "참조".
- 표기: 두 개념을 선으로 잇고 관계 이름을 붙인다.

### C-2. 다중도 — 관계의 개수 규칙
- **다중도**: 한쪽 개념 하나에 다른 쪽이 몇 개 대응하나. Sale ─1─포함─1..*─ SalesLineItem (판매 하나에 항목 하나 이상), SalesLineItem ─*─참조─1─ ProductDescription (항목 여럿이 한 명세를 가리킴).
- 읽는 법: 1, 0..1, 1..*, * 각각의 의미. "1..*"는 "최소 하나, 상한 없음".

### C-3. 다중도가 규칙을 드러낸다 (불변식 예고)
- Sale에 SalesLineItem이 "1..*"라는 건 곧 **"판매는 최소 한 항목을 가져야 한다"**는 도메인 규칙이다. 다중도가 불변식을 미리 보여준다.
- 훈련: 이 다중도가 "0..*"이면? (빈 판매를 허용 — 도메인이 그걸 원하나?) 다중도를 정하는 것은 규칙을 정하는 것이다.
- (이 규칙들이 나중에 어디서 지켜지는가는 설계·DDD의 몫 — 여기선 규칙이 "드러난다"까지.)

---

## D. 속성 (Attribute)
### D-1. 속성이란
- **속성**: 개념이 갖는 단순한 값. Sale.dateTime, SalesLineItem.quantity, ProductDescription.price·itemID.

### D-2. 속성인가, 개념인가 (핵심 판단)
- 판단 규칙: 단순 값(수량·날짜·금액)은 속성. 그 자체가 독립 개념이고 관계·속성을 갖는 것은 별도 개념 클래스 + 연관.
- 예: price를 SalesLineItem의 속성으로 둘까? 아니다 — 가격은 "상품이 무엇인가"에 속하므로 ProductDescription으로 민다. (B-3 명세 개념과 이어짐)
- 훈련: 고객의 주소는 속성인가 개념인가? (배송·청구 주소로 나뉘고 이력을 가지면 개념, 단일 문자열이면 속성 — 도메인이 정한다)

### D-3. 개념 모델 완성 (표기)
```
[NewPOS 개념 모델]
ProductCatalog ──1──포함──1..*── ProductDescription
                                    │ price, itemID
Register ──1──기록──1── Sale ──1──포함──1..*── SalesLineItem
                        │ dateTime              │ quantity
                                                └─참조─1─ ProductDescription
(개념 수준 — 메서드 없음, 현실의 명사·관계·값만)
```

## E. 개념 모델에서 코드까지 — 진화의 흐름 (수강생 동기)
> 이게 없으면 수강생은 "왜 이 그림을 그리나" 싶어진다. 개념 모델이 결국 코드가 되는 흐름을 보여준다. 단, **흐름의 지도**일 뿐 — 책임 배치(OOD)를 여기서 하진 않는다.

### E-1. 세 단계 진화
- **개념 모델(OOA)**: 현실의 개념·관계·값. "무엇이 있나."
- **설계 클래스 모델(OOD)**: 개념에 **책임(메서드)**·가시성·타입·방향을 붙인다. 여기서 RDD·GRASP가 책임을 배치한다 — **다음 과정(OOD)의 몫.**
- **코드**: 설계 클래스가 소스로 산다.
- 이 강의는 첫 단계까지. 그러나 어디로 가는지는 보여준다.

### E-2. 구조는 코드로 곧장 매핑된다 (규칙 + 예)
- 개념 모델의 **구조**(개념·연관·다중도·속성)는 코드 골격으로 거의 그대로 이어진다:
  - 개념 클래스 → 클래스
  - 속성 → 필드
  - "1" 방향 연관 → 참조 필드
  - "1..*" 다중도 → 컬렉션(List 등)
```java
class Sale {                          // 개념 클래스 → 클래스
    private LocalDateTime dateTime;   // 속성 → 필드
    private List<SalesLineItem> lines;// 1..* 다중도 → 컬렉션
    // 행위(메서드)는 여기 없다 — OOD에서 채워진다
}
class SalesLineItem {
    private int quantity;             // 속성 → 필드
    private ProductDescription description;  // 1 연관 → 참조
}
```
- **핵심**: 구조는 개념 모델에서 왔고 곧 코드다. 그러나 **행위(getTotal 등 메서드)는 비어 있다** — 그 자리는 OOD에서 책임을 배치하며 채운다. OOA/OOD 경계가 코드에서도 보인다.

### E-3. 그래서 개념 모델이 중요하다
- 개념 모델이 정확하면 코드 골격이 정확하다. 개념을 잘못 보면(명세 개념을 놓치면) 코드도 틀린다.
- 수강생 메시지: "지금 그리는 이 그림이 코드의 뼈대다. 대충 그리면 코드가 뒤틀린다."

---

## F. 닫기 — 동적 모델과 설계로 (복선)
- 정적 모델은 "무엇이 있나"를 줬다. 그러나 "유스케이스가 실행될 때 이 개념들이 어떤 순서로 협력하나?"는 답하지 못한다 → **동적 모델**(다음 강의: SSD·상호작용·상태 머신).
- 그리고 이 개념들에 **책임을 배치해 설계 클래스로 만드는 것**은 OOD 과정의 몫 — 여기서 심은 개념 모델이 그 입력이 된다.

---

## 슬라이드 변환 지침
- **각 개념(개념 클래스·연관/다중도·속성)마다 여러 장** — 소개 → NewPOS 예제 → 판단 훈련. 정의 한 줄로 끝내지 마라. 이게 재작성의 핵심.
- B-3(명세 개념), C-3(다중도=규칙), D-2(속성vs개념)는 반드시 "훈련" 슬라이드로 — 수강생이 판단하게.
- E(진화의 흐름)를 강조 파트로 — 개념→설계→코드 3단, 구조 매핑 codepair(개념 모델 표기 vs 코드 골격), 행위는 비움(OOD 예고).
- RDD·GRASP 금지(OOA다). "책임 배치는 OOD"만 예고.
- 원작자(Larman) 개념 장 하단. 의문형 물음표. 한글(영어) 표기. 실습은 Order(별도).
- 분량이 크다(~2.5시간) — 강의가 넘치면 개념 모델/진화·매핑 2강으로 나눈다. 시수는 분량이 정한다(정리는 나중 일괄).
