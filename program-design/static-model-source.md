# 정적 모델 강의 소스 (OOA · 정적 모델 · 약 2.5시간 · 4차 재작성판)

> 정적 모델(개념 모델) 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 4차 재작성 사유: 3차가 다이어그램·표를 넣어 진일보했으나 여전히 개요 밀도라 "이 정도로는 정적 모델을 스스로 작성할 수 없다"(낙제). 이번엔 작성 과정 중심 — NewPOS Process Sale 유스케이스에서 출발해 개념 모델을 단계별로 만들어가는 워크스루, 각 개념을 여러 예제·여러 판별로.
> 정정: 개념 모델엔 연산(메서드)이 없다 — 그러나 속성(자료)은 있다. "자료구조가 없다"는 틀린 표현(속성이 곧 자료). 가시성은 "없다"가 아니라 "아직 정하지 않는다". 모든 의문형 문장에 물음표.
> 층 경계: OOA다. 책임 배치(RDD·GRASP)는 OOD — 한 글자도 안 넣는다. 프레임: Larman 도메인 모델. 설명·워크스루=NewPOS, 실습=Order. 한글(영어) 표기. 원작자(Larman) 하단.

## 원작자·출전
- 도메인 모델(Domain Model): Craig Larman (Applying UML and Patterns, 3rd ed.)
- UML 표기: OMG UML 표준

## A. 정적 모델이란 무엇이며 왜 그리는가
- OOA는 도메인을 두 그림으로 본다 — 정적 모델(무엇이 존재하는가: 개념·구조), 동적 모델(무엇이 일어나는가: 행위·시간). 이 강의는 정적.
- 산물 = 개념 모델(Domain Model, 도메인 모델): 문제 영역에 무엇이 존재하고 어떻게 관계 맺는지 그린 그림.
- 개념 모델은 소프트웨어 설계가 아니다 — 현실의 개념을 그린다. 여기엔 연산(메서드)이 없다. 개념·관계·속성만 담는다. (속성=자료는 있다. 가시성·타입 세부는 아직 정하지 않는다 — 그건 설계 단계의 몫.)
- 왜 개념부터인가? 구현을 먼저 생각하면 편의가 도메인 이해를 오염시킨다. 먼저 도메인을 정직하게 이해하고, 그다음 설계로 넘어간다.
- 표현 수단 = UML 클래스 다이어그램(표기). 이 표기를 읽고 그리는 것이 이 강의의 실질 목표다.

## B. UML 클래스 다이어그램 표기 — 처음부터 (표기 자체가 학습 내용)
### B-1. 클래스 박스
- 클래스 = 세 칸 박스: 이름 / 속성 / 연산. 개념 모델에선 연산 칸을 비운다(연산=행위는 OOD에서 붙는다). 속성 칸은 채운다.
- [uml] class Sale { dateTime }, class SalesLineItem { quantity } — 세 칸 구조를 크게 보여주고 각 칸이 무엇인지 라벨.
- 훈련: 이 박스에서 "dateTime"은 어느 칸? (속성) "총액을 계산한다"는 어느 칸? (연산 — 개념 모델엔 아직 없음)

### B-2. 연관 (Association)
- 두 개념을 선으로 잇고 관계 이름을 붙인다. 선은 "이 둘이 의미 있게 관계 맺는다"를 뜻한다.
- 관계 이름은 동사구: Sale "포함" SalesLineItem, SalesLineItem "참조" ProductDescription.
- [uml] Sale -- SalesLineItem : 포함
- 훈련: "계산원이 판매를 기록한다"에서 연관은? (Register -- Sale, 이름="기록")

### B-3. 다중도 (Multiplicity) — 표로 가르친다
- 연관선 양 끝에 개수 규칙을 적는다. 각 기호의 뜻(처음 배우는 사람 기준):
  - 1 = 정확히 하나
  - 0..1 = 없거나 하나 (선택적)
  - 1..* = 하나 이상 (상한 없음)
  - * (= 0..*) = 0개 이상 (없어도 됨)
  - 2..5 = 2개에서 5개 (범위)
- 핵심: *(="0개 이상")와 1..*(="하나 이상")의 차이. *는 하나도 없을 수 있고, 1..*는 최소 하나가 있어야 한다.
- 읽는 법(양 끝을 함께): Sale "1" -- "1..*" SalesLineItem → "판매 하나에 항목이 하나 이상, 항목 하나는 판매 하나에 속한다".
- [uml] Sale "1" -- "1..*" SalesLineItem : 포함
- 훈련 여럿:
  - 한 고객이 여러 판매를? Customer "1" -- "*" Sale (없을 수도 있으니 *)
  - 한 판매에 지불은? Sale "1" -- "1" Payment (정확히 하나) 또는 "0..1"(외상이면 없을 수도) — 도메인이 정한다
  - 한 상품 명세를 여러 항목이 참조? SalesLineItem "*" -- "1" ProductDescription

### B-4. 다중도가 규칙을 드러낸다 (판단 훈련)
- "1..*"는 곧 도메인 규칙 "판매는 최소 한 항목을 가져야 한다"이다. 다중도가 불변식을 미리 보여준다.
- 훈련: 이 다중도를 "*"(0개 이상)로 바꾸면? 빈 판매를 허용하게 된다. 도메인이 빈 판매를 원하는가? 다중도를 정하는 것은 곧 규칙을 정하는 것이다.
- (이 규칙이 코드 어디서 지켜지는가는 설계·DDD의 몫 — 여기선 "다중도가 규칙을 드러낸다"까지.)

## C. 개념 클래스 찾기 (무엇을 박스로 만드나)
### C-1. 개념 클래스란
- 도메인에 실재하는 개념 — 사물·역할·사건·명세. 소프트웨어 객체가 아니라 현실의 명사.
- 종류 예: 물리적 사물(상품), 역할(고객·계산원), 사건(판매·지불), 명세(상품 명세), 장부/목록(상품 목록).

### C-2. 찾는 절차 — 명사구 추출
- 요구사항·유스케이스 서술에서 명사구를 뽑는다. 이건 출발점이지 기계적 규칙이 아니다 — 뽑은 뒤 판단으로 거른다.
- 거르는 기준:
  - 단순 값일 뿐인 것(날짜·금액·수량)은 개념이 아니라 속성 후보.
  - 중복·동의어는 하나로.
  - 시스템 자신·UI 용어는 도메인 개념이 아니다.
  - 애매하면 남겨두고 반복(iteration)에서 정한다.

### C-3. 함정 — 명세 개념 (Larman 핵심 예)
- 상품 한 개(물리적 아이템)와 "그 상품이 무엇인가"(명세: 이름·가격·바코드)는 다르다.
- 재고가 0이어도 "이 상품은 무엇이고 얼마인가"는 존재해야 한다 → 상품 명세(ProductDescription)를 물리적 상품과 별도 개념으로 분리한다.
- 놓치면? "재고 0이면 가격 정보도 사라지는" 잘못된 모델이 된다. 개념을 정직하게 보는 것이 이런 오류를 막는다 — 이것이 개념 모델링이 단순 명사 나열이 아닌 이유다.
- 훈련: "메뉴판의 김치찌개"와 "지금 나온 김치찌개 한 그릇"은 같은 개념인가? (명세 vs 물리적 인스턴스 — 다른 개념)

## D. 속성 (Attribute)
### D-1. 속성이란
- 개념이 갖는 단순 값. Sale.dateTime, SalesLineItem.quantity, ProductDescription.price·itemID·description.
- 속성은 개념 박스의 속성 칸에 적는다(개념 모델에도 속성은 있다 — 없는 것은 연산뿐).

### D-2. 속성인가, 별도 개념인가 (핵심 판단 훈련)
- 규칙: 단순 값(수량·날짜·금액·이름)은 속성. 그 자체가 독립 개념이고 자기 속성·관계를 갖는 것은 별도 클래스 + 연관.
- 경계 사례 여럿:
  - price를 SalesLineItem 속성으로? 아니다 — 가격은 "상품이 무엇인가"에 속하므로 ProductDescription으로 민다.
  - 고객의 주소는? 단일 문자열이면 속성. 배송·청구로 나뉘고 이력을 가지면 별도 개념. 도메인이 정한다.
  - 판매의 상태(PENDING/PAID…)는? 단순 값이면 속성(enum), 상태별 행동·전이 규칙이 붙으면 별도로 다룬다(동적 모델).
- 판단 신호: "이것이 자기만의 속성이나 관계를 갖는가?"가 Yes면 개념, No면 속성.

## E. 개념 모델 작성 워크스루 — NewPOS Process Sale (핵심 파트)
> 완성 다이어그램을 감상하는 게 아니라, 유스케이스에서 개념 모델을 단계별로 만들어간다. 이 워크스루가 이 강의의 심장이다.

### E-1. 출발 — 유스케이스 서술
- Process Sale(요약): "고객이 상품들을 계산대로 가져온다. 계산원이 각 상품의 항목을 입력한다. 시스템이 항목별 소계와 판매 총액을 계산한다. 고객이 지불한다."
- 이 텍스트에서 개념 모델을 뽑아낸다.

### E-2. 단계 1 — 명사구 추출
- 뽑기: 고객, 상품, 계산대, 계산원, 항목, 소계, 판매, 총액, 지불.
- [화면에 원문 + 밑줄 친 명사들]

### E-3. 단계 2 — 거르기 (개념 vs 속성 vs 잡음)
- 소계·총액 → 계산된 값(속성/파생). 개념 아님.
- 계산대 → 이 범위에선 계산원 역할에 흡수(또는 Register로 남김 — 판단).
- 상품 → 물리적 상품 vs 상품 명세로 갈린다(C-3 함정) → ProductDescription 채택.
- 남는 개념 후보: 판매(Sale), 판매 항목(SalesLineItem), 상품 명세(ProductDescription), 지불(Payment), (계산원/고객은 이 다이어그램 범위에 따라).
- [uml] 아직 연관 없이 박스만: Sale, SalesLineItem, ProductDescription, Payment

### E-4. 단계 3 — 연관 긋기
- 판매는 항목을 포함한다 → Sale -- SalesLineItem : 포함
- 항목은 어떤 상품인지 참조한다 → SalesLineItem -- ProductDescription : 참조
- 판매는 지불된다 → Sale -- Payment : 지불됨
- [uml] 위 세 연관을 선으로(다중도는 아직)

### E-5. 단계 4 — 다중도 정하기 (규칙 결정)
- Sale — SalesLineItem: 판매 하나에 항목 하나 이상 → "1" / "1..*" (빈 판매 불허 규칙)
- SalesLineItem — ProductDescription: 항목 여럿이 한 명세 참조 → "*" / "1"
- Sale — Payment: 판매 하나에 지불 하나 → "1" / "1"
- [uml] 다중도를 붙인 세 연관

### E-6. 단계 5 — 속성 붙이기
- Sale: dateTime / SalesLineItem: quantity / ProductDescription: itemID, price, description / Payment: amount
- [uml — 완성본] 4개 핵심 클래스 + 다중도 + 속성. 크게 렌더.
- 완성 다이어그램을 놓고 "이게 Process Sale의 개념 모델이다 — 유스케이스 한 문단에서 여기까지 왔다"를 짚는다.

## F. 개념 모델에서 코드까지 — 진화의 흐름 (수강생 동기)
> 개념 모델이 결국 코드가 되는 흐름을 보여준다 — "왜 이 그림을 그리나"의 답. 단, 흐름의 지도일 뿐 책임 배치(OOD)는 여기서 안 한다.
### F-1. 세 단계 진화
- 개념 모델(OOA): 현실의 개념·관계·속성. "무엇이 있나."
- 설계 클래스 모델(OOD): 개념에 연산(책임)·가시성·타입을 붙인다 — 다음 과정의 몫.
- 코드: 설계 클래스가 소스로 산다.
### F-2. 구조는 코드로 곧장 매핑된다 (규칙 + 예)
- 개념 클래스 → 클래스, 속성 → 필드, "1" 연관 → 참조, "1..*" → 컬렉션, 다중도 규칙 → (아직 미구현, OOD에서 강제).
- [codepair] 왼쪽=E-6 완성 개념 모델(다이어그램 요지), 오른쪽=코드 골격:
  class Sale { LocalDateTime dateTime; List<SalesLineItem> lines; /* 연산 없음 — OOD에서 채움 */ }
  class SalesLineItem { int quantity; ProductDescription description; }
  class ProductDescription { String itemID; Money price; String description; }
- 구조는 개념 모델에서 왔고 곧 코드다. 연산(행위)은 비어 있다 — OOA/OOD 경계가 코드에서도 보인다.
### F-3. 그래서 개념 모델이 중요하다
- 개념 모델이 정확하면 코드 골격이 정확하다. 명세 개념을 놓치면(상품/명세 안 나누면) 코드도 틀린다.
- 메시지: "지금 그리는 이 다이어그램이 코드의 뼈대다. 대충 그리면 코드가 뒤틀린다."

## G. 닫기 — 동적 모델과 설계로 (복선)
- 정적 모델은 "무엇이 있나"를 줬다. "유스케이스가 실행될 때 이 개념들이 어떤 순서로 협력하는가?"는 답하지 못한다 → 동적 모델(다음 강의: 유스케이스·시퀀스·협업·상태 다이어그램).
- 개념에 책임(연산)을 배치해 설계 클래스로 만드는 것은 OOD 몫 — 여기 심은 개념 모델이 그 입력이 된다.

## 슬라이드 변환 지침
- E(작성 워크스루)가 이 강의의 심장 — 유스케이스→명사추출→거르기→연관→다중도→속성, 각 단계를 uml 다이어그램으로 점진 구축(박스만→연관→다중도→완성). 완성본만 보여주지 마라, 만들어지는 과정을 보여라.
- UML 표기(B절)는 처음부터 가르친다 — 다중도는 반드시 표로(각 기호 뜻, *="0개 이상" vs 1..*="하나 이상").
- 각 개념(개념 클래스·다중도·속성)마다 소개→예제→여러 훈련. 명세 개념·다중도=규칙·속성vs개념은 판단 훈련 슬라이드로(여러 사례).
- 모든 다이어그램은 uml visual.type으로 슬라이드에 렌더 — 말로 때우지 마라. 다이어그램은 크게(하단 잘림 없이).
- F(진화 흐름)는 codepair(완성 개념 모델 vs 코드 골격, 연산 비움).
- RDD·GRASP 금지(OOA). "책임 배치는 OOD"만 예고. 원작자(Larman) 하단. 물음표(의문형 전부). 한글(영어). 실습=Order(별도 실습 강의).
- 분량 크다(~2.5시간) — 한 강의로 두되 충분히 두껍게. 억지 분할 안 함.
