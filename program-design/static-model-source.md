# 정적 모델 강의 소스 (OOA · 정적 모델 · 약 2.5시간 · 3차 재작성판)

> 정적 모델(개념 모델) 내용 정본. Code는 이 소스를 슬라이드로 옮긴다 — 즉석 생성 금지.
> 3차 재작성 사유: 2차가 (1) 표기·개념을 "이미 아는 사람에게 정리"하는 형식이었고 (2) UML 다이어그램을 슬라이드에 안 넣고 말로 때웠다 — 개념 모델이 아니라 업무 설명이 됐다(낙제). 이번엔 ① 표기를 처음부터 표로 가르치고 ② UML 다이어그램을 PlantUML로 슬라이드에 그림으로 담는다.
> 다이어그램은 PlantUML 텍스트로 명세(엔진의 uml visual.type이 렌더). 표기 자체가 학습 내용이다 — 반드시 그림으로.
> 층 경계: OOA다. 책임 배치(RDD·GRASP)는 OOD — 한 글자도 안 넣는다. 프레임: Larman 도메인 모델. 설명=NewPOS, 실습=Order. 한글(영어)·물음표. 원작자 하단.

## 원작자·출전
- 도메인 모델(Domain Model): Craig Larman (Applying UML and Patterns, 3rd ed.)
- UML 표기: OMG UML 표준

## A. 정적 모델이란 무엇이며 왜 그리는가
- OOA는 도메인을 두 그림으로 본다 — 정적 모델(무엇이 존재하는가: 개념·구조), 동적 모델(무엇이 일어나는가: 행위·시간). 이 강의는 정적.
- 산물 = 개념 모델(Domain Model): 문제 영역에 무엇이 존재하고 어떻게 관계 맺는지.
- 개념 모델은 코드가 아니다 — 현실의 개념을 그린다. 메서드·자료구조 없다. 구현을 먼저 생각하면 편의가 도메인 이해를 오염시킨다.
- 표현 수단 = UML 클래스 다이어그램. 이 표기를 읽고 그리는 것이 이 강의의 실질 목표다.

## B. UML 클래스 다이어그램 표기 — 처음부터 (표기가 학습 내용)
### B-1. 클래스 박스
- 클래스 = 세 칸 박스: 이름 / 속성 / 연산. 개념 모델에선 연산 칸을 비운다(행위는 OOD에서).
- PlantUML: class Sale { dateTime }, class SalesLineItem { quantity }
### B-2. 연관 (Association)
- 두 개념을 선으로 잇고 관계 이름을 붙인다.
- PlantUML: Sale -- SalesLineItem : 포함
### B-3. 다중도 (Multiplicity) — 표로 가르친다
- 연관선 양 끝에 개수 규칙. 각 기호의 뜻(처음 배우는 사람 기준):
  - 1 = 정확히 하나
  - 0..1 = 없거나 하나
  - 1..* = 하나 이상 (상한 없음)
  - * (= 0..*) = 0개 이상 (없어도 됨)
  - 2..5 = 2개에서 5개
- *의 의미를 반드시 짚는다: "0개 이상" — 하나도 없을 수 있다. 1..*와의 차이(하나 이상 vs 없어도 됨)가 핵심.
- PlantUML: Sale "1" -- "1..*" SalesLineItem : 포함
### B-4. 다중도가 규칙을 드러낸다 (훈련)
- "1..*"는 곧 도메인 규칙 "판매는 최소 한 항목을 가져야 한다". 다중도가 불변식을 미리 보여준다.
- 훈련: "*"(0개 이상)로 바꾸면? 빈 판매 허용. 도메인이 원하나? 다중도를 정하는 것은 규칙을 정하는 것.

## C. 개념 클래스 찾기
### C-1. 개념 클래스란
- 도메인에 실재하는 개념 — 사물·역할·사건·명세. NewPOS: 판매(Sale)·판매 항목(SalesLineItem)·상품 명세(ProductDescription)·상품 목록(ProductCatalog)·계산대(Register)·지불(Payment).
### C-2. 어떻게 찾나 (절차+훈련)
- 요구사항·유스케이스 서술의 명사구를 뽑는다 → 거른다(속성일 뿐인 것·중복·모호한 것). 판단이 든다.
- 훈련: "지불"은 개념인가 속성인가? (개념) "여러"는? (다중도 신호)
### C-3. 함정 — 명세 개념 (Larman 핵심 예)
- 상품 한 개(물리적 아이템)와 "그 상품이 무엇인가"(명세)는 다르다. 재고 0이어도 가격·설명은 존재 → 상품 명세를 별도 개념으로. 놓치면 "재고 0이면 가격도 사라지는" 잘못된 모델.

## D. 속성 (Attribute)
### D-1. 속성이란
- 개념이 갖는 단순 값. Sale.dateTime, SalesLineItem.quantity, ProductDescription.price·itemID.
### D-2. 속성인가 개념인가 (핵심 훈련)
- 규칙: 단순 값(수량·날짜·금액)은 속성. 독립 개념이고 관계·속성 갖는 것은 별도 클래스+연관.
- 예: price를 SalesLineItem 속성으로? 아니다 — 가격은 "상품이 무엇인가"에 속하므로 ProductDescription으로.
- 훈련: 고객 주소는? (나뉘고 이력 가지면 개념, 단일 문자열이면 속성 — 도메인이 정한다)

## E. 개념 모델 완성 — NewPOS 전체 (다이어그램)
PlantUML 클래스 다이어그램:
  ProductCatalog "1" -- "1..*" ProductDescription : 포함
  Register "1" -- "1" Sale : 기록
  Sale "1" -- "1..*" SalesLineItem : 포함
  SalesLineItem "*" -- "1" ProductDescription : 참조
  Sale "1" -- "1" Payment : 지불됨
  (ProductDescription: itemID, price / Sale: dateTime / SalesLineItem: quantity / Payment: amount)
  개념 수준 — 연산 없음. 명사·관계·다중도·값만.
- 이 다이어그램을 슬라이드에 크게 렌더하고, 각 연관·다중도를 짚으며 읽는 법을 보인다.

## F. 개념 모델에서 코드까지 — 진화의 흐름 (수강생 동기)
### F-1. 세 단계 진화
- 개념 모델(OOA): 현실의 개념·관계·값 → 설계 클래스 모델(OOD): 책임(연산)·가시성·타입 붙임 → 코드.
### F-2. 구조는 코드로 곧장 매핑 (규칙+예)
- 개념 클래스→클래스, 속성→필드, "1" 연관→참조, "1..*"→컬렉션.
- 예: class Sale { LocalDateTime dateTime; List<SalesLineItem> lines; /*연산 비어있음 — OOD에서 채움*/ }
- 행위는 비어 있다 — OOA/OOD 경계가 코드에서도 보인다.
### F-3. 그래서 개념 모델이 중요하다
- 개념 모델이 정확하면 코드 골격이 정확. 명세 개념 놓치면 코드도 틀림. "이 다이어그램이 코드의 뼈대다."

## G. 닫기 — 동적 모델과 설계로 (복선)
- 정적 모델은 "무엇이 있나". "유스케이스 실행 시 어떤 순서로 협력하나?"는 동적 모델(유스케이스·시퀀스·협업·상태 다이어그램). 책임 배치는 OOD 몫.

## 슬라이드 변환 지침
- UML 표기(B절)를 처음부터 가르친다 — 다중도는 반드시 표로(각 기호 뜻), *="0개 이상" 명시.
- 모든 다이어그램은 uml visual.type으로 슬라이드에 렌더 — 말로 때우지 마라. B의 표기 예, E의 NewPOS 전체, F의 매핑.
- 각 개념(개념 클래스·다중도·속성)마다 소개→예제→훈련. 명세 개념·다중도=규칙·속성vs개념은 훈련 슬라이드로.
- F(진화 흐름)를 강조 파트 — 개념→설계→코드, 매핑 codepair(다이어그램 vs 코드 골격, 행위 비움).
- RDD·GRASP 금지(OOA). "책임 배치는 OOD"만 예고. 원작자(Larman) 하단. 물음표. 한글(영어). 실습=Order(별도).
- 분량 크다(~2.5시간) — 넘치면 2강으로. 시수는 분량이 정한다(OI-5).
