# MSA 실습 설계

## 위상
- 형식 복제. 렌즈 = **로컬 → 원격, 인프로세스 이벤트 → 메시지.** 아키텍처가 심은 포트·이벤트를 승격하는 대조.
- Order를 분해로 확장. 코드는 핵심 로직만.

## 렌즈 차이
- 아키텍처: 규칙이 레이어를 가로지른다(한 프로세스 안).
- MSA: 경계가 **프로세스를 가로지른다.** 같은 클린 구조가 서비스마다 반복되고, 바뀌는 건 어댑터(로컬→원격)뿐.

## 부 1 · 경계 긋기 (모듈러 모놀리스)

### (a) 대조 · 경계가 진짜인가

**쌍 M-1 · 가짜 경계 vs 진짜 경계**
```java
// 가짜 — 모듈이 남의 테이블을 직접 읽는다
class BillingModule {
    Money amount = jdbc.query("SELECT total FROM orders WHERE id=?", id);  // access 테이블 침범
}
```
```java
// 진짜 — 공개 포트로만
class BillingModule {
    private final OrderFacade orders;                 // 인터페이스로만
    Money amount = orders.totalOf(id);                // 데이터 소유 존중
}
```
짚기: 모듈이 데이터를 공유하면 경계는 가짜다. **데이터 소유**가 진짜 경계의 시금석. 이 검증을 프로세스 비용 없이 여기서.

**쌍 M-2 · 동기 vs 이벤트 선택** — 대조: "출차 시 요금계산"(강한 시간 결합→동기) vs "결제 확정→영수증"(→이벤트). 물음: 사용자가 문 앞에서 기다리나?

### (b) 통짜 · 경계안 대조
- Order 모놀리스를 두 방식으로 모듈 분할(주문/결제/재고/배송) — 데이터 공유 있음 vs 없음. 어느 쪽이 나중에 잘라내기 쉬운가.

## 부 2 · 추출과 분산

### (a) 대조 · 무엇이 바뀌나

**쌍 M-3 · 인프로세스 이벤트 → 메시지**
```java
// 아키텍처가 준 것 — 인프로세스
domainEvents.publish(new OrderPaid(orderId));     // 같은 프로세스, 동기 구독
```
```java
// MSA — 메시지로 승격
outbox.record(new OrderPaid(orderId));            // Outbox → 브로커 → 원격 구독
```
짚기: **같은 이벤트, 다른 배송.** 클린 구조는 그대로, 어댑터만 로컬→원격. 여기에 최종 일관성·Outbox가 따라온다.

**쌍 M-4 · 로컬 포트 → 원격 어댑터** — `PaymentPort`(아키텍처의 인터페이스) 그대로, 구현이 `LocalPayment` → `HttpPaymentAdapter`. 인터페이스 불변이 추출을 기계적으로 만든다.

### (b) 통짜 3벌 · 유스케이스 = Pay
- 모놀리스(인프로세스) / 모듈러 모놀리스(모듈 경계) / 서비스 추출(원격+Saga). 
- 물음: 결제 서비스가 죽으면 각 벌은 어떻게 되나(네트워크 실패). 분산이 산 것과 진 것.

## 코더 층
- (a): 로컬 포트 구현을 주고 **원격 어댑터 빈칸** 채우기(같은 인터페이스).
- (b): 인프로세스 이벤트 발행을 Outbox 기록으로 바꾸기.

## 소유 경계
- 여기 실습의 산출 = **분해 결정과 분산 트레이드오프**. 컨텍스트 매핑의 craft(워크숍)는 DDD 과정, 여기선 경계를 **적용**해 자른다.
